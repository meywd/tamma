## Summary

The Blocker Diagnosis workflow (Story 7-1G) collects signals and classifies blockers correctly, but the AI diagnosis and progressive resolution prompts operate in a vacuum -- they receive no project context, no story context, no resolution history, and no code snippets. This story enriches every LLM call in the blocker diagnosis pipeline with project-aware, story-specific, history-informed context.

## Problem Statement

### Current State of Blocker Diagnosis Prompts

The `BlockerDiagnosisWorkflow` makes 4-5 LLM calls during a full resolution cycle. Each one suffers from context poverty.

#### 1. Main Diagnosis Prompt (`BuildDiagnosisPrompt`)

The current prompt tells the LLM to "Diagnose what is blocking this junior developer (skill level X/5)" and provides raw signal data (commit counts, CI status, inactivity duration). It does NOT provide:

- **What the developer is working on.** The LLM does not know the story title, description, acceptance criteria, or expected files. It cannot distinguish "stuck on a database migration" from "stuck on a UI component."
- **What the project is.** The LLM does not know the tech stack, architecture, or conventions. A CI build failure in a TypeScript strict-mode project means something different than in a Python project.
- **What has already been tried.** When the workflow loops through progressive resolution levels (Hint -> Guidance -> Assistance -> Escalation), each subsequent diagnosis call starts from scratch. The LLM cannot learn from the failure of previous interventions.

#### 2. Hint Prompt (Socratic Level)

**Current (verbatim from `BuildHintLevel`):**
```
Provide Socratic hints for: {rootCauseHypothesis}.
Blocker type: {blockerType}.
Use guiding questions, not direct answers. Employ the Socratic method.
```

This is 3 sentences. It provides no code context, no relevant files, no project patterns. The LLM is forced to generate generic Socratic questions like "What do you think is happening?" instead of targeted questions like "Looking at line 42 of event-store.ts, what type does the `tags` parameter expect?"

#### 3. Guidance Prompt (Direct Level)

**Current:**
```
Provide direct guidance for: {rootCauseHypothesis}.
Blocker type: {blockerType}.
Give clear, step-by-step instructions. Be specific and actionable.
```

"Be specific and actionable" is impossible without code context. The LLM cannot reference specific files, functions, or patterns.

#### 4. Assistance Prompt (Code Examples Level)

**Current:**
```
Provide code example for: {rootCauseHypothesis}.
Blocker type: {blockerType}.
Include a working code example with detailed explanation.
Show the solution step by step.
```

The LLM cannot produce a correct code example when it does not know the language, framework, file structure, or conventions. It will generate generic JavaScript/Python snippets unrelated to the actual project.

### Additional Issues

#### 5. No Resolution History Accumulation

The workflow tracks `feedbackProvided` as a list of strings like `"[Hint] Socratic hints provided for TechnicalKnowledgeGap"`. This is metadata, not content. The actual hints, guidance, and code examples generated by the LLM are never stored or fed back into subsequent calls. Each resolution level starts fresh.

#### 6. `ClassifyBlockerActivity` Rule-Based Fallback is Naive

The signal-based fallback in `ClassifyBlockerActivity.ClassifyFromSignals` uses simple rules:
- Build failure -> EnvironmentIssue or TechnicalKnowledgeGap (based on whether error contains "CS" or "syntax")
- 3+ test failures -> DebuggingStuck
- 60+ minutes inactive + no communication -> PersonalBlocker

These rules are reasonable as fallbacks but do not consider:
- The specific build error message content
- Which tests are failing (unit vs. integration, which module)
- Whether the developer was active in other channels (GitHub comments, PR reviews)
- The developer's history: have they been stuck on similar issues before?

#### 7. No Code Context in Signal Collection

The signal collection activities (`CollectGitActivityActivity`, `CollectCIStatusActivity`, etc.) collect metadata (commit counts, build status, inactivity duration) but never the actual error messages, failing test output, or recent code diffs. The LLM receives "Build=Failed" but not the build error text.

## Acceptance Criteria

1. **Diagnosis prompt** includes story title, description, expected files, project tech stack summary, and resolution history from previous attempts in the current session.

2. **Hint prompt** includes relevant code snippets from the files the developer is working on, existing patterns in the project that demonstrate the correct approach, and the specific error message (if CI is failing).

3. **Guidance prompt** includes everything from the hint prompt plus the actual hints that were given and why they did not work.

4. **Assistance prompt** includes everything from the guidance prompt plus the actual guidance that was given. The code example instruction specifies the exact language, framework, and conventions to follow.

5. **Resolution history** is accumulated as structured data: each level stores the actual LLM-generated content (hints, steps, code examples), not just metadata strings. Subsequent levels receive the full history.

6. **`ClassifyBlockerActivity`** rule-based fallback is enhanced to parse CI build error messages for specific error patterns (TypeScript compilation errors, missing imports, test assertion failures) and adjust classification confidence accordingly.

7. **Signal collection activities** capture richer data:
   - `CollectCIStatusActivity`: captures actual build error text (first 2000 chars) and failing test output (first 5000 chars).
   - `CollectGitActivityActivity`: captures the diff summary of the most recent commit (files changed, lines added/removed, commit message).

8. All existing blocker diagnosis tests continue to pass. New tests cover the enriched prompt construction.

## Technical Design

### New Data Models

```csharp
/// <summary>
/// Structured resolution history entry for context accumulation.
/// </summary>
public class ResolutionAttempt
{
    public string Level { get; set; } = "";           // Hint, Guidance, Assistance
    public DateTime AttemptedAt { get; set; }
    public string LlmResponse { get; set; } = "";     // The actual content generated
    public bool ProgressDetected { get; set; }
    public string ProgressDetails { get; set; } = "";  // What changed (or didn't)
}
```

### Modified Variables in `BlockerDiagnosisWorkflow`

Add:
```csharp
var resolutionHistory = builder.WithVariable<List<ResolutionAttempt>>();
var storyContext = builder.WithVariable<string>();       // From context gathering
var projectConventions = builder.WithVariable<string>(); // From convention detection
var relevantCode = builder.WithVariable<string>();       // From file content fetch
```

### New Pre-Steps in Workflow

Before the parallel signal collection, add:
1. **Fetch Story Context** -- dispatch to context-gathering workflow to get story title, description, acceptance criteria, and relevant file contents.
2. **Detect Project Conventions** -- run `DetectProjectConventionsActivity` to get the `CompactSummary`.

These run in parallel with signal collection (add to the `ParallelSignals` activity or as a separate parallel group).

### Modified `BuildDiagnosisPrompt`

Add parameters for `storyTitle`, `storyDescription`, `expectedFiles`, `projectConventions`, `resolutionHistory`. See Story 2-17 implementation plan Phase 6 for the exact prompt template.

### Modified Hint/Guidance/Assistance Levels

Each level now:
1. Stores the LLM response in `resolutionHistory` (structured).
2. Passes the accumulated `resolutionHistory` to the next level's LLM call.
3. Includes `relevantCode` and `projectConventions` in the prompt.

### Enhanced Signal Collection

#### `CollectCIStatusActivity`

Add:
```csharp
public string BuildErrorText { get; set; } = "";      // First 2000 chars of build error
public string FailingTestOutput { get; set; } = "";    // First 5000 chars of test output
```

Fetch from GitHub Actions API: `GET /repos/{owner}/{repo}/actions/runs/{run_id}/jobs` and extract `conclusion`, `steps[].output`.

#### `CollectGitActivityActivity`

Add:
```csharp
public string LastCommitDiff { get; set; } = "";       // Compact diff summary
public string LastCommitMessage { get; set; } = "";     // Last commit message
public List<string> LastCommitFiles { get; set; }       // Files in last commit
```

Fetch from GitHub API: `GET /repos/{owner}/{repo}/commits/{sha}`.

### Enhanced `ClassifyBlockerActivity`

Add pattern matching for specific CI errors:

```csharp
// TypeScript-specific error patterns
if (buildError.Contains("TS2322") || buildError.Contains("TS2345"))
    return BlockerCategory.TechnicalKnowledgeGap; // Type mismatch

if (buildError.Contains("TS2304") || buildError.Contains("Cannot find name"))
    return BlockerCategory.TechnicalKnowledgeGap; // Missing import/declaration

if (buildError.Contains("ENOENT") || buildError.Contains("MODULE_NOT_FOUND"))
    return BlockerCategory.EnvironmentIssue; // Missing file/module

if (buildError.Contains("EACCES") || buildError.Contains("permission denied"))
    return BlockerCategory.EnvironmentIssue; // Permission issue
```

## Risks

- CI log retrieval may be slow or rate-limited. Add timeout and fallback to metadata-only signals.
- Resolution history accumulation increases LLM context size per call. Cap history at the 3 most recent attempts to stay within token budgets.
- Enhanced CI error parsing is language-specific. Start with TypeScript/JavaScript patterns (primary Tamma tech stack) and add others later.
