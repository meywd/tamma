## Audit Summary

A line-by-line audit of the five Git-related Elsa workflows and their backing activities uncovered the following systemic weaknesses:

### 1. Branch Creation: Hardcoded Naming, No Issue-Type Awareness

**Current state** (`CreateBranchActivity.cs` lines 61-62):
```csharp
var sanitized = SanitizeBranchName(issueTitle);
var branchName = $"adl/{issueNumber}-{sanitized}";
```

**Problems**:
- Prefix is hardcoded to `adl/`. The story spec (2-4) defines configurable patterns like `feature/{issue-number}-{issue-title}`, `bugfix/...`, etc. The Elsa activity ignores this entirely.
- No issue-type awareness. A bug fix produces `adl/42-fix-null-pointer` instead of `bugfix/42-fix-null-pointer`.
- No conflict detection. If the branch already exists, the GitHub API call fails and the workflow exits with `Error`. The story spec calls for suffix/timestamp/abort strategies -- none are implemented.
- `SanitizeBranchName` only strips non-alphanumeric characters and hyphens, truncates to 40 chars. No word-boundary truncation. No double-hyphen collapse.
- The workflow has no `baseBranch` input -- it relies on the GitHub API default. The `SingleIssueCycleWorkflow` has a `baseBranch` variable but never passes it to the branch-creation sub-workflow.

### 2. PR Description: Dumps Raw JSON, No Structured Summary

**Current state** (`CreatePullRequestActivity.cs` lines 112-125):
```csharp
private static string BuildPrBody(int issueNumber, string? planJson)
{
    var body = $"## Autonomous Development\n\nCloses #{issueNumber}\n\n";
    body += "This PR was generated by Tamma's ADL.\n\n";
    if (!string.IsNullOrEmpty(planJson))
    {
        body += "### Implementation Plan\n\n";
        body += $"```json\n{planJson}\n```\n\n";
    }
    body += "---\n_Generated by Tamma ADL_\n";
    return body;
}
```

**Problems**:
- Dumps raw plan JSON into a code block. Reviewers must parse JSON to understand what the PR does.
- No test results summary. The story spec (2-8) specifies `TestingSummary` with `testsRun`, `testsPassed`, `testCoverage`. None of these are passed to or rendered by the activity.
- No file-change summary. The spec calls for `ChangeSummary` with `filesAdded`, `filesModified`, `linesAdded`. The activity has no access to diff stats.
- No breaking changes section, no migration notes, no reviewer checklist.
- Title format `[ADL] #42: Issue Title` is acceptable but not configurable. No conventional-commit prefix (feat/fix/chore).
- The PR is created as non-draft. The spec calls for `draftMode` configuration. There is no mechanism to create draft first, then mark ready.
- `PlanJson` is passed as a string input but never validated or structured. If null, the plan section is simply omitted.
- No labels beyond `tamma-auto` and `adl` are derived from issue content.

### 3. Review Analysis: No Comment Classification, Everything is "normal" Priority

**Current state** (`AnalyzeReviewActivity.cs` lines 74-89):
```csharp
var analysis = new ReviewAnalysisResult
{
    TotalComments = comments.Count,
    HasActionableComments = comments.Count > 0,
    ActionableComments = comments.Count,
    FixItems = comments.Select(c => new ReviewFixItem
    {
        FilePath = c.Path ?? "",
        Line = c.Line,
        Comment = c.Body,
        Priority = "normal"
    }).ToList(),
    ...
};
```

**Problems**:
- Every comment is blindly treated as actionable. A "nice work!" comment triggers the fix loop.
- All comments get `Priority = "normal"`. No categorization by type (style, bug, design, security, nitpick).
- No AI analysis. The activity just maps comments to `ReviewFixItem` with zero interpretation. The `SuggestedFix` field on `ReviewFixItem` is never populated.
- No distinction between inline code comments (with `Path` and `Line`) and general PR-level comments.
- No filtering of resolved/outdated threads.

### 4. Review Fix Loop: Prompt is Bare, No Context Injection

**Current state** (`ReviewFixWorkflow.cs` lines 45-56):
```csharp
var generateFixes = new DispatchWorkflow
{
    WorkflowDefinitionId = new("llm-call"),
    Input = new(ctx => new Dictionary<string, object>
    {
        ["agentRole"] = "implementer",
        ["taskPrompt"] = $"Apply fixes for the following review comments:\n{SecurityHelpers.SanitizeForPrompt(analysisJsonVar.Get(ctx))}",
        ["sessionId"] = $"adl-review-fix-{ctx.GetInput<int>("prNumber")}"
    }),
    ...
};
```

**Problems**:
- The prompt is "Apply fixes for the following review comments:" followed by raw JSON. No file content, no diff context, no explanation of what the reviewer meant.
- `ApplyReviewFixesActivity` is a stub -- it immediately sets `FixesApplied = true` and completes. It does not actually apply anything.
- No categorization of fixes by effort (trivial rename vs. architectural redesign).
- No verification step after applying fixes (re-run linter, type-check).
- When fixes are applied and CI is re-run (via the `hasReviewComments -> dispatchCiRetry` loop in `SingleIssueCycleWorkflow`), the `ciRetryCount` is NOT reset. This is documented as a known bug in the code comments.

### 5. Merge: Hardcoded Squash, No Conflict Handling

**Current state** (`MergePullRequestActivity.cs` lines 66-73):
```csharp
var mergeResult = await _github!.MergeGitHubPullRequestAsync(repository, prNumber);
```

**Problems**:
- `MergeGitHubPullRequestAsync` takes only `repository` and `prNumber`. The merge strategy (squash/merge/rebase) is presumably hardcoded in the integration service. No configuration exposed.
- No pre-merge conflict check. If the base branch has moved forward, the merge will fail at the API level with no recovery path.
- No pre-merge rebase or update-branch step.
- Branch deletion failure is caught but not reported back to the workflow (best-effort).
- No merge commit message customization (e.g., including issue number, PR title, co-authors).

### 6. Merge Approval: No Decision Context

**Current state** (`WaitForMergeApprovalActivity.cs`):
- The bookmark payload only carries `decision` and `feedback`. There is no context about CI status, review status, or diff stats provided to the human making the decision.
- The `PrUrl` input is accepted but never surfaced to the human (no notification, no dashboard integration from this workflow).

### 7. CI Debug Retry: Known Bug, Limited Error Analysis

**Current state** (`CiWithDebugRetryWorkflow.cs`):
- `ciRetryCount` persists across re-entries (documented bug, lines 52-55).
- `GetTestErrorOutput` extracts a single `errorMessage` string. No structured error categorization (build error vs. test failure vs. lint error vs. timeout).
- The debugging sub-workflow receives `debugContextMode = "RuntimeError"` regardless of the actual failure type.
- No differentiation between "tests failed because code is wrong" and "CI infrastructure is flaky."

### 8. Missing Flows

- **No draft PR flow**: PRs are created as final immediately. Best practice is draft first, CI passes, then mark ready for review.
- **No pre-merge update**: No rebase/merge-base-update before final merge.
- **No review-request activity**: After creating the PR, no reviewers are assigned or notified. The story spec (2-8) defines reviewer selection strategies (code ownership, round-robin) but nothing is implemented.
- **No mergeability check**: The workflow does not verify `mergeable` status before attempting merge.
- **No conflict resolution**: If merge conflicts exist, the workflow fails with no recovery.

## User Story

As a **platform operator**,
I want the autonomous development workflows to produce high-quality branch names, informative PR descriptions, intelligent review interpretation, configurable merge strategies, and structured CI failure analysis,
So that the output of autonomous development is indistinguishable from skilled human developer output.

## Acceptance Criteria

### Branch Creation
1. Branch prefix derived from issue labels: `feat/`, `fix/`, `chore/`, `docs/`, `refactor/`, `test/`, or configurable `adl/` fallback
2. Branch name follows configurable pattern with variable substitution (`{type}`, `{issue-number}`, `{issue-title}`)
3. Conflict detection: if branch exists, apply suffix strategy (configurable: numeric suffix, timestamp, abort)
4. `baseBranch` input wired through from `SingleIssueCycleWorkflow`
5. Sanitization handles consecutive hyphens, leading/trailing hyphens, and enforces configurable max length with word-boundary truncation

### PR Description
6. PR body includes structured sections: Summary, Changes Made, Test Results, Implementation Plan (human-readable, not raw JSON), Breaking Changes, Checklist
7. PR title follows conventional-commit format: `feat(scope): description (#issue)`
8. Diff stats (files added/modified/deleted, lines +/-) included in PR body
9. Test results (pass/fail counts, coverage %) included in PR body
10. PR created as draft when configured; separate step to mark ready-for-review after CI passes
11. Labels derived from issue type and content (beyond static `tamma-auto`)

### Review Interpretation
12. AI-powered comment classification: each comment categorized as `bug`, `style`, `design`, `security`, `nitpick`, `question`, `praise`
13. Priority assignment: `critical` (security, logic bugs), `high` (functional issues), `medium` (style, naming), `low` (nitpick, praise)
14. Non-actionable comments (praise, questions) filtered out of the fix queue
15. Suggested fixes populated on each `ReviewFixItem` by AI before dispatching to the fix-generation LLM call
16. Resolved/outdated review threads excluded

### Review Fix Generation
17. Fix-generation prompt includes: the review comment, the surrounding code context (file content around the commented line), the reviewer's intent classification, and the priority
18. After fixes are applied, a verification step runs (type-check, lint) before committing
19. Fix commit messages reference the review comment: `fix: address review - <summary> (PR #N)`

### Merge Strategy
20. Merge strategy configurable: `squash`, `merge`, `rebase`
21. Pre-merge conflict detection: check `mergeable` status before attempting merge
22. Pre-merge branch update: rebase or merge base branch into feature branch when behind
23. Merge commit message includes issue number, PR title, and co-author attribution
24. `ciRetryCount` reset when re-entering CI after review fixes (fix known bug)

### CI Failure Analysis
25. Error categorization: `build_error`, `test_failure`, `lint_error`, `type_error`, `timeout`, `infrastructure`
26. `debugContextMode` set based on categorized error type (not hardcoded `RuntimeError`)
27. Structured error output passed to debugging workflow: error category, failing file/test, error message, stack trace snippet

## Technical Context

### Current Architecture

The five sub-workflows are dispatched by `SingleIssueCycleWorkflow.cs` in this sequence:

```
issue-selection -> context-gathering -> plan-generation -> branch-creation
-> tdd-with-debug-retry -> pull-request -> ci-with-debug-retry
-> review-fix -> (loop to ci-with-debug-retry if fixes applied)
-> merge-approval -> merge-complete -> finish
```

Each sub-workflow is a `DispatchWorkflow` call that passes inputs as `Dictionary<string, object>` and receives results as `IDictionary<string, object>`.

### Key Files

| File | Role |
|------|------|
| `Tamma.ElsaServer/Workflows/BranchCreationWorkflow.cs` | Branch creation sub-workflow |
| `Tamma.ElsaServer/Workflows/PullRequestWorkflow.cs` | PR creation sub-workflow |
| `Tamma.ElsaServer/Workflows/ReviewFixWorkflow.cs` | Review analysis + fix sub-workflow |
| `Tamma.ElsaServer/Workflows/MergeWorkflow.cs` | Merge + cleanup sub-workflow |
| `Tamma.ElsaServer/Workflows/MergeApprovalWorkflow.cs` | Human approval bookmark |
| `Tamma.ElsaServer/Workflows/CiWithDebugRetryWorkflow.cs` | CI + debug retry loop |
| `Tamma.ElsaServer/Workflows/SingleIssueCycleWorkflow.cs` | Parent orchestrator |
| `Tamma.Activities/ADL/CreateBranchActivity.cs` | Branch creation logic |
| `Tamma.Activities/ADL/CreatePullRequestActivity.cs` | PR creation logic |
| `Tamma.Activities/ADL/AnalyzeReviewActivity.cs` | Review comment analysis |
| `Tamma.Activities/ADL/ApplyReviewFixesActivity.cs` | Fix application (stub) |
| `Tamma.Activities/ADL/MergePullRequestActivity.cs` | Merge + cleanup logic |
| `Tamma.Activities/ADL/WaitForMergeApprovalActivity.cs` | Approval bookmark |
| `Tamma.Activities/ADL/Models/AdlModels.cs` | Shared DTOs and enums |
| `Tamma.Core/Interfaces/IIntegrationService.cs` | GitHub API interface |

### Integration Service Gaps

The `IGitHubIntegrationService` interface is missing methods needed by this story:
- `GetPullRequestDiffStatsAsync(repository, prNumber)` -- for diff stats in PR description
- `UpdatePullRequestAsync(repository, prNumber, updates)` -- for marking draft -> ready
- `CheckMergeabilityAsync(repository, prNumber)` -- for pre-merge conflict check
- `MergeGitHubPullRequestAsync(repository, prNumber, strategy, commitMessage)` -- merge with strategy
- `RebaseBranchAsync(repository, branchName, baseBranch)` -- for pre-merge update

These will need to be added to the interface and implemented in the integration service.

## Implementation Notes

### Key Considerations

1. **Backward compatibility**: Existing workflows must continue to function. New features should be additive (new inputs with defaults, new optional fields on models).
2. **AI call budget**: Comment classification adds one LLM call per review-fix cycle. Keep the prompt concise to stay within the session budget.
3. **Prompt injection safety**: All review comment text must pass through `SecurityHelpers.SanitizeForPrompt()` before inclusion in any LLM prompt.
4. **Configuration surface**: New config fields (branch prefix mapping, merge strategy, draft mode) should be addable to `AdlConfig` without breaking existing serialized configs.

## Logging Requirements

All modified activities MUST log via `ILogger` (C#):

- **INFO**: Branch prefix selected, PR description generated (section count, char count), review comments classified (counts by category), merge strategy selected, conflict detected
- **DEBUG**: Full branch name derivation steps, PR body markdown (truncated), individual comment classification results, merge commit message
- **WARN**: Branch conflict resolved via fallback strategy, non-actionable comments filtered, merge conflict detected (pre-merge check), ciRetryCount reset triggered
- **ERROR**: Branch creation failed after conflict resolution, PR description generation failed (AI or template), review classification failed (fallback to "normal"), merge failed after conflict resolution attempt
- **Structured context**: Always include `{ issueNumber, repository, branchName, prNumber, workflowInstanceId }`
