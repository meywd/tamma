# Migration Ordering — Story 28-1 (DB-per-Tenant Foundations)

**Status**: Compile-only (Story 28-1, 2026-04-22). Migrations are
generated but **not yet applied** in any environment. Story 28-2 wires
DI; Story 28-4 ships the per-tenant connection resolver; Story 28-5
ships the `CreateTenantWorkflow` that runs the tenant migration on
fresh per-tenant DBs.

## Migration sets shipped in 28-1

| Set | Path | Context | Target DB | Migrations history table |
|---|---|---|---|---|
| **ControlPlane** | `apps/tamma-elsa/src/Tamma.Data/Migrations/ControlPlane/` | `ControlPlaneDbContext` | `tamma_control` (new) | `__ControlPlaneMigrationsHistory` |
| **Tenant** | `apps/tamma-elsa/src/Tamma.Data/Migrations/Tenant/` | `TenantDbContext` | `tamma_tenant_<guid>` (one per tenant — provisioned in Story 28-5) | `__TenantMigrationsHistory` |
| **Global Elsa** | (deferred to Story 28-5) | Elsa EF provider | `tamma_global_elsa` (new) | Elsa default |
| **Per-tenant Elsa** | (deferred to Story 28-5) | Elsa EF provider | `tamma_tenant_<guid>_elsa` (one per tenant) | Elsa default |

The Elsa migration sets are auto-generated by Elsa's own EF provider on
first boot of the configured Elsa server. Story 28-5 will register two
Elsa servers (global + per-tenant) and capture the generated migration
files, mirroring the convention here.

## Existing legacy migrations

The legacy `TammaDbContext` migrations under
`apps/tamma-elsa/src/Tamma.Data/Migrations/` (16 migrations through
`20260420120000_Phase2RlsNullPolicyTightening`) keep running against the
single shared `tamma` Postgres. **They are unaffected by this story.**
Story 28-3 deletes the `TammaDbContext` once endpoints have been
migrated to the new contexts (Story 19-6 thread + Epic 28 follow-ups).

Until that point all three contexts coexist:

| Context | Tables | DB |
|---|---|---|
| `TammaDbContext` (legacy) | All 22 entities, RLS-aware | `tamma` (existing shared DB) |
| `ControlPlaneDbContext` (new) | 14 CP entities | `tamma_control` (new — empty until 28-2 cuts over) |
| `TenantDbContext` (new) | 16 tenant entities | `tamma_tenant_<guid>` (one per tenant — created by 28-5) |

## Boot-time application order (eventual)

Once Stories 28-2 → 28-5 land, the deploy sequence is:

1. **Postgres up** (existing).
2. **Bootstrap shared DBs** (Story 28-1 ships scripts; Story 28-5 wires
   them into `docker-compose`):
   - `CREATE DATABASE tamma_control` (idempotent).
   - `CREATE DATABASE tamma_global_elsa` (idempotent).
   - `dotnet ef database update -c ControlPlaneDbContext`.
   - Bring global Elsa up once to materialise its EF schema.
3. **Run `PlansSeeder`** (idempotent — guarded by `EXISTS` check).
4. **API + Elsa start** — bind to `tamma_control` for CP traffic; tenant
   traffic resolves a per-tenant connection on-demand via the LRU pool
   (Story 28-4).
5. **First tenant signup** triggers `CreateTenantWorkflow` (Story 28-5),
   which:
   - `CREATE DATABASE tamma_tenant_<guid>`,
   - applies the **Tenant** migration set,
   - `CREATE DATABASE tamma_tenant_<guid>_elsa`,
   - applies Elsa's per-tenant migration set,
   - flips `tenants.Status = 'active'`.


## Rollback plan

- **Pre-cutover (today)**: The new migrations have not run anywhere.
  Rolling 28-1 back is a `git revert` of the migration files +
  `ControlPlaneDbContext.cs` / `TenantDbContext.cs`. Zero environmental
  impact.
- **Post-cutover (after 28-5)**: Both new contexts target *new*
  databases (`tamma_control`, `tamma_tenant_*`). Rollback means
  `DROP DATABASE` on the new DBs and reverting the runtime DI
  registration. Existing tenants on the legacy `tamma` DB are not
  touched — the legacy `TammaDbContext` keeps serving until Story 28-3
  removes it.

## Open follow-ups

- **Plans seed timing**: Story 28-2 will register `PlansSeeder` as a
  `IHostedService` that runs after `EnsureCreated`/migrations.
- **Elsa migrations**: Story 28-5 captures and version-locks the Elsa
  EF migration outputs (per the design doc §1.2 rows 20–21).
- **Bootstrap scripts**: `scripts/db/bootstrap-shared-dbs.{sh,ps1}` and
  `scripts/db/reset-all.{sh,ps1}` are deferred to Story 28-5 alongside
  the docker-compose `db-bootstrap` one-shot service.
- **Per-finding migrations** (e.g. `api_keys.RateLimitRpm`): the
  `RateLimitRpm` shadow column is declared on `ControlPlaneDbContext`
  but Story 28-7 owns the lookup index work and will generate any
  follow-up migration if the field needs to be promoted from shadow
  property to first-class column.
