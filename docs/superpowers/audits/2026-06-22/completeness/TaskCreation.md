# Completeness Audit — `TaskCreationWorkflow`

**File:** `apps/tamma-elsa/src/Tamma.ElsaServer/Workflows/TaskCreationWorkflow.cs`
**Definition ID:** `task-creation`
**Audit date:** 2026-06-22
**Verdict:** **PARTIAL** — the core happy path is real and correctly mediated (single senior-developer LLM call via the `llm-call` sub-workflow, JSON extraction that normalizes both array- and `{tasks:[...]}`-object shapes, field validation, and a bounded retry-with-error-feedback loop with a distinct success/error output contract). But it has one **P0 tenant-isolation bug that its near-twin `PlanGenerationWorkflow` does NOT have** — it drops `tenantId` entirely, so in SaaS mode the tenant's prompt/convention overrides and BYOK credential are silently bypassed and the *system* default is used instead. On top of that it shares the PlanGeneration gaps: it ignores the sub-workflow's `success`/cost/tokens/provider signals (can't tell "LLM failed" from "tasks invalid"), emits no workflow-level DCB audit events, validates only the loosest shape (a bare `[{}]` passes), and implements essentially none of the *richer* per-task content the autonomous loop needs (the dependency DAG, per-task files/test-approach/acceptance, topological-orderability).

---

## 1. Purpose & owner

**Purpose (one line):** Decompose an approved implementation plan into an ordered set of detailed, self-contained implementation tasks — a senior-developer-role LLM (prompt resolved from the Epic-27 registry, `role=senior-developer` / `action=create-tasks`) breaks `planJson` into a `tasks` array (each task: files to modify, code changes, test approach, dependencies), the workflow extracts + validates the JSON, retries up to `maxRetries` feeding validation errors back into the prompt, and returns either `tasksJson` (valid) or `tasksJson:"[]"` + `error` (gave up).

**Owning epic/story:** This is the **task-decomposition step** that bridges `PLAN_GENERATION` and the per-task TDD loop in the **14-step autonomous loop** (`docs/architecture.md`; the cycle invokes it between plan-approval and the TDD `ForEach`). `RolePhaseMap.cs` maps `AgentAction.CreateTasks → Plan` phase; `AgentAction.cs:45` defines `[Wire("create-tasks")] CreateTasks`. The product story is **Epic 2** (autonomous development workflow — plan→tasks→TDD). The LLM mediation it rides on is owned by **Epic 32** (revised agent architecture, `docs/superpowers/specs/2026-06-20-epic-32-revised-agent-architecture.md`) — the `call-LLM` mediation (32-5) and tenant/BYOK threading (32-3/32-16), today fulfilled by `LlmCallWorkflow`.

**Consumer contract (from `SingleIssueCycleWorkflow.cs` lines 277-302):** input `{ repository, issueNumber, planJson, contextIds, conventions, tenantId, workItemJson?, validationErrors?, maxRetries? }`; output `{ tasksJson }` on success or `{ tasksJson:"[]", error }` on give-up. The parent **silently drops the `error` output**: `extractTasks` (cycle line 296) reads only `tasksJson`; the downstream **task-review** panel runs on whatever it gets, and the TDD loop's `InitTaskLoop` (cycle line 441) parses the tasks array for a count — an empty `"[]"` yields `totalTasks=0`, so the TDD `ForEach` no-ops and the cycle proceeds to PR/merge **with zero code written**. A failed task-creation therefore degrades into a *false-success* at the cycle level (the cycle's gap, but this workflow's `[]`-on-failure contract enables it).

---

## 2. Maturity: **PARTIAL**

Not a stub and not merely "thin": it has a real, non-trivial control structure — generate → extract → validate → branch on validity → bounded retry that **feeds `validationErrors` back into the next generation** (genuine self-correction, not a blind re-roll) → distinct valid/error output sequences. It correctly routes **all** LLM work through the `llm-call` sub-workflow and holds no provider key (the cross-cutting Epic-32 rule §1 is honored). The prompt comes from the registry, not inline. The extractor is slightly more robust than PlanGeneration's — it handles both a top-level JSON array **and** a `{ "tasks": [...] }` object, normalizing the latter to the array. That is more than a happy-path skeleton.

But it is not complete. It (a) **never threads `tenantId`** — `PlanGenerationWorkflow` reads `tenantId` in Init and passes it to `llm-call`; this workflow's Init (lines 62-77) never reads it and `generateTasks` (lines 83-103) has no `["tenantId"]` key, so `ResolveConventionsActivity`/`ResolvePromptFromRegistryActivity` resolve at **system** scope (`ResolveConventionsActivity.cs:164` logs `source = string.IsNullOrEmpty(tenantId) ? "system" : tenantId`) and BYOK falls through to the platform key — a SaaS tenant-isolation defect; (b) ignores the sub-workflow's `success`/`providerUsed`/`costUsd`/`tokensUsed` outputs, so a hard provider failure ("all providers failed", empty response) is indistinguishable from "LLM returned malformed tasks" — both funnel through the same retry-then-`validationErrors` path; (c) emits **no** workflow-level DCB audit events; (d) validates only the loosest shape — a non-empty array of empty objects (`[{}]`) passes, since it checks only "array length > 0", never per-task `files`/`dependencies`/`testApproach`; and (e) returns `tasksJson:"[]"` on give-up, which the parent treats as "0 tasks" rather than a fault.

## 3. Current capabilities (what it does today)

- **Init** (`SetVariable "Init"`, lines 62-77): reads `repository`, `issueNumber`, `planJson`, `contextIds`, `workItemJson`, and optional `maxRetries` (default 2) into variables. **Does NOT read `tenantId`** (the parent passes it but it is dropped).
- **Generate Tasks** (`DispatchWorkflow("llm-call")`, lines 83-103): role `senior-developer`, action `create-tasks`, `enableTools=true`, passes `variables { planJson, contextIds, workItemJson, repository, validationErrors }`. **Mediation-correct** (engine never calls a provider directly) **but tenant-blind** (no `tenantId` key → system-scope resolution + platform credential).
- **Extract & Validate** (`SetVariable "ExtractValidate"`, lines 109-183): pulls `llmResponse`; extracts the outermost `[...]` array first, else the outermost `{...}` object; parses JSON; if an object with a `tasks` property, normalizes to that inner array; validates **only** that the array is present and non-empty (and that a `tasks` object property, if present, is a non-empty array). Sets `tasksValid` + `validationErrors`.
- **Valid?** (`FlowDecision` on `tasksValid`, lines 189-191): True → set `tasksJson` output → `Finish`.
- **Retry loop** (`IncrRetry` → `CanRetry` on `retryCount < maxRetries`, lines 196-206): on invalid, increment and — if budget remains — loop **back to Generate Tasks with the validation errors now in the prompt variables** (informed regeneration). Exhausted → error output.
- **Outputs:** valid → `SetOutput tasksJson`. Give-up → `Sequence` emitting `tasksJson:"[]"` + `error = validationErrors`. Both reach a single `Finish`.

## 4. Intended full scope (with citations)

1. **It is the decomposition bridge of the 14-step loop.** Its output is the contract the per-task TDD loop consumes: `SingleIssueCycleWorkflow` parses `tasksJson` for a count (`InitTaskLoop`, line 441-452), slices each task by index (`extractCurrentTask`, line 461-468), and feeds each one-task slice into `ExecuteAgentActivity` as `PlanJson` (line 504). It is also fed verbatim into **task-review** (cycle line 316) and **test-case-creation** (cycle line 423). A complete task set must therefore be *structurally* trustworthy enough that (a) the count is meaningful, (b) each element is a self-contained, executable unit, and (c) the order is a valid topological order of the dependency DAG.
2. **The workflow's own docstring promises a DAG, files, code changes, test approach.** The class summary (lines 18-31): "Each task includes: files to modify, code changes, test approach, and dependencies (DAG)." The current validator enforces **none** of these — it accepts `[{}]`. A complete validation contract must require per-task `id`, `files[]` (with usable paths), `testApproach`/`acceptance`, and a `dependencies[]` that references only earlier/known task ids, plus a check that the array is topologically orderable (no cycles, no dangling deps) since the TDD loop walks tasks **in array order** and a mis-ordered DAG silently runs dependents before dependencies.
3. **Tenant-scoped resolution is mandatory in SaaS (the "two scoping models" rule).** `CLAUDE.md` §"Universal rule for any tenant-aware feature": every feature must answer who owns it in single-user **and** SaaS mode. Prompt resolution (Epic 27) and BYOK (32-3/32-16) are keyed by `tenantId`. `PlanGenerationWorkflow` threads it (`PlanGenerationWorkflow.cs` lines 51, 77, 96); `TaskCreationWorkflow` does not. With `tenantId` empty, `ResolveConventionsActivity` resolves **system** conventions (`ResolveConventionsActivity.cs:164`) and `ResolvePromptFromRegistryActivity` resolves the **system** prompt — a tenant that customized its `create-tasks` prompt/conventions silently gets the platform default, and a BYOK tenant's call is billed/keyed to the **platform** (markup applied, wrong credential). This violates `MEMORY` `feedback_resolution_no_empty_fallback` (resolution is tenant→system→error) by collapsing the tenant tier entirely.
4. **Audit trail / DCB events (architecture mandate).** `docs/architecture.md` Logging Requirements: "Every state transition must emit a corresponding DCB event"; `CLAUDE.md` §"Emitting Events for Audit Trail" mandates it for every operation, with the canonical pattern `AGGREGATE.ACTION.STATUS`. A complete task-creation step emits **`TASKS.CREATED.SUCCESS`** (tags `issueId/issueNumber/tenantId`; data `taskCount/fileCount/retryCount/provider/costUsd/tokensUsed/durationMs`) and **`TASKS.CREATION.FAILED`** (data `reason: invalid-after-retries | llm-failure`, `validationErrors`, `retryCount`). The workflow emits **zero** workflow-level events today.
5. **Cost / usage metering must not be discarded.** `LlmCallWorkflow` returns `success`, `providerUsed`, `costUsd`, `tokensUsed`, `workflowOutput` (`LlmCallWorkflow.cs` lines 583-681). The revised agent architecture (`2026-06-20-epic-32-revised-agent-architecture.md` §0 rule 2(e)) makes metering a first-class output of the mediated call; Epic 36 analytics + 32-9 usage events consume per-step cost/tokens. TaskCreation reads only `llmResponse` (line 117) and throws the rest away, so the task-decomposition step is invisible to cost analytics.
6. **No-false-success / no-silent-failure.** Project rule (`MEMORY` `feedback_resolution_no_empty_fallback`; `CLAUDE.md`): failures must surface, not be papered over. Returning `tasksJson:"[]"` on give-up is an **empty fallback** — the parent reads it as "0 tasks to do" and proceeds to create a PR and wait for approval **without implementing anything**. A hard provider failure (sub-workflow `success=false`, empty `llmResponse`) currently degrades into the *same* "Empty tasks output" validation error and burns retry attempts re-prompting a dead provider chain, then emits the same generic `error`.
7. **Mediated, tenant/BYOK-correct LLM path (Epic 32).** §1 of the pivot spec: "A workflow STEP MUST NEVER call an external API/provider directly… the engine never holds a provider key." The mediation half is **honored** (dispatch to `llm-call`); the tenant/BYOK half is **not** (no `tenantId`).
8. **Determinism / reproducibility of validation.** Because this output drives autonomous code generation, the validation contract should be a single shared, versioned schema agreed by plan-generation, task-creation, task-review, and test-case-creation. Today the check is an ad-hoc "non-empty array" that no other component references.

## 6. Ordered build-out spec (to reach complete + robust)

Ordered so each step's prerequisites land first. All changes honor: **steps never call providers directly** (keep dispatching `llm-call`), **tenant→system→error** (never empty/plain), **no false-success / no silent failure**, **emit DCB events**.

1. **Wire `tenantId` (P0, #1).** In `Init` add `tenantId.Set(ctx, ctx.GetInput<string>("tenantId") ?? "")` (new `string` variable, default `""`). In `generateTasks` Input add `["tenantId"] = tenantId.Get(ctx)`. Also thread `conventions` (#9) the same way for parity. *Outcome:* SaaS tenants resolve their own `create-tasks` prompt/conventions and BYOK credential. *Verify:* `llm-call`'s `ResolveConventionsActivity` logs `source=<tenantId>` not `system`.

2. **Capture the mediated-call result fully (P0/P1, #2, #6).** In `ExtractValidate`, after reading `llmResponse`, also read `success` (bool), `providerUsed`, `costUsd`, `tokensUsed` from the `llmResult` dictionary into new variables (`llmSucceeded`, `providerUsed`, `costUsd`, `tokensUsed`). These feed the new fault branch and the success event.

3. **Add the LLM-fault branch (P0, #2).** Insert a `FlowDecision "LlmSucceeded"` immediately after `generateTasks` (before `ExtractValidate`): `ctx => llmSucceeded.Get(ctx)`.
   - **True** → `ExtractValidate` (existing path).
   - **False** → new `SetVariable "MarkLlmFault"` setting `validationErrors = $"LLM call failed (provider chain exhausted): {providerUsed}"` and a new `llmFault=true` flag → go straight to the failure-output sequence (step 6), **skipping the validation-retry loop** so we don't re-prompt a dead chain.

4. **Tighten validation to the DAG/consumer contract (P0, #5).** Replace the "array non-empty" check in `ExtractValidate` with a shared validator (mirror the `PlanValidationHelper` pattern — add e.g. `TaskValidationHelper.ValidateTasks`): for each task require `id`, non-empty `files[]` with usable `path`, `testApproach`/`acceptance`, and `dependencies[]` referencing only known ids; reject cycles/dangling deps; enforce `1 ≤ count ≤ MaxTasks` (#8). Accumulate per-task error messages into `validationErrors` so the retry feedback is specific. Keep the array/object normalization that already exists.

5. **Topologically order the validated tasks (P1, #7).** On valid, before emitting, run a topo-sort over the dependency DAG and write the sorted array back to `tasksJson` (or emit `taskOrder` as a separate output). *Outcome:* the cycle's index-order TDD loop runs dependencies before dependents. Fail the validation (back to retry) if no valid topo order exists.

6. **Replace the empty-fallback failure output (P0, #3).** Change the give-up/fault `Sequence` to emit a non-deceptive contract: keep `error = validationErrors` (now specific), and **add** `SetOutput "taskCreationFailed" = true`. Do **not** emit `tasksJson:"[]"` as the primary signal of failure (or emit it but require the parent to read `taskCreationFailed` first). *Parent change (separate report — SingleIssueCycle):* gate `InitTaskLoop`/TDD-loop/PR creation on `taskCreationFailed`; route a true to needs-human/abort instead of no-op'ing the loop.

7. **Emit DCB events (P0, #4).** Add an event-emit activity (reuse the codebase's event pattern) on each terminal edge:
   - On the valid edge (after topo-sort, before `Finish`): **`TASKS.CREATED.SUCCESS`** — tags `{ issueId/issueNumber, tenantId, provider: providerUsed }`, data `{ taskCount, fileCount, retryCount, costUsd, tokensUsed, durationMs }`.
   - On the give-up edge: **`TASKS.CREATION.FAILED`** — data `{ reason: "invalid-after-retries", validationErrors, retryCount }`.
   - On the LLM-fault edge (step 3): **`TASKS.CREATION.FAILED`** — data `{ reason: "llm-failure", provider: providerUsed, validationErrors }`.
   Include a stable `taskSetId` (issue+revision) tag for correlation (#10).

8. **Surface metering outputs (P1, #6).** On the valid edge add `SetOutput`s for `providerUsed`, `costUsd`, `tokensUsed` so the cycle and Epic-36 analytics can meter the task-decomposition step (parity with the `llm-call` output contract).

9. **Add the count clamp + oversized-task flag (P2, #8).** Within the validator (step 4), reject/flag a count outside `[1, MaxTasks]` and tasks whose `files[]` exceed a size threshold (candidate for split), feeding a specific `validationErrors` message so the retry can correct it.

10. **(P3, #10) Idempotency tag.** Compute `taskSetId = $"{issueNumber}-rev{revisionNumber}"` (thread `revisionNumber` from the parent like PlanGeneration does) and tag all events + the success output with it, so task-review `needsChanges` regenerations and cycle replays correlate cleanly.

## 7. Cross-workflow note

`TaskCreationWorkflow`, `TestCaseCreationWorkflow`, and `TaskReviewWorkflow` **all** omit `tenantId` (verified: `grep tenantId` returns nothing in any of the three), whereas `PlanGenerationWorkflow` threads it. The `tenantId`-drop (gap #1) is therefore a **family defect** across the post-plan creation/review workflows, not unique to TaskCreation — fixing it should be done consistently across the three. The DCB-event, fault-distinction, and validation-tightening gaps (#2/#4/#5) are likewise shared with `PlanGenerationWorkflow` and should reuse the same shared helper/event pattern once built.
