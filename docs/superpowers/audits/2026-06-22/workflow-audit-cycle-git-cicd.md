## SingleIssueCycleWorkflow  (`apps/tamma-elsa/src/Tamma.ElsaServer/Workflows/SingleIssueCycleWorkflow.cs`)
- **Purpose / owner story:** Top-level orchestrator: processes one work item validate→context→plan→review→tasks→branch→PR→TDD→approval→merge→deploy. Dispatches 11 sub-workflows + the `ExecuteAgentActivity` TDD loop. Still needed and is the spine of the ADL. (Epic 2 issue-cycle; TDD step updated by Story 19-5.)
- **Health:** NEEDS-WORK
- **Findings:**
  - [P1] Architecture/pivot — All git/issue effects this orchestrator triggers go through sub-workflows whose activities (`CreateBranchActivity`, `CreatePullRequestActivity`, `MergePullRequestActivity`, `UpdateIssueStatusActivity` via the `NotifyIssue` dispatches) call `IGitHubIntegrationService` directly in-engine — Epic 38 Class A violators-by-co-hosting. The TDD step's `ExecuteAgentActivity`→`GitHubActionsExecutor` is Class C. — `SingleIssueCycleWorkflow.cs:124-608` (sub-dispatches), `:495-512` (TDD). — **Fix:** no change to this orchestrator file; the fix lands in the leaf activities under Epic 38-1/38-2. Tracked here so the cluster picture is complete. **Depends on: Epic 38-1, Epic 38-2.**
  - [P1] Structural correctness — After `waitForApproval`, `dispatchMerge` (fire-and-forget `merge` sub-workflow) and `waitForMerged` (bookmark `pr-merged-{n}`) are connected as **two parallel edges** (`:854-855`). The merge sub-workflow performs the squash-merge and is supposed to trigger the webhook that resumes `waitForMerged`. If the merge sub-workflow *fails* (e.g. `MergePullRequestActivity`→Error), nothing resumes the bookmark and the cycle hangs forever — there is no failure edge from the merge dispatch and no timeout on `waitForMerged`. — `SingleIssueCycleWorkflow.cs:551-581, 854-855`. — **Fix:** make `dispatchMerge` `WaitForCompletion=true` and branch on its success/failure (or add a timeout + failure path on `waitForMerged`) so a failed merge routes to `reportError`/`notifyError` instead of dangling.
  - [P1] Structural correctness — The PR-approval gate is hard-wired to "approved → merge". The richer human decision (`merge` / **`test`** / `reject`) modeled by `WaitForMergeApprovalActivity` + the orphaned `merge-approval` sub-workflow is **not reachable** from here; a human cannot ask for "more tests" or reject from the cycle. — `SingleIssueCycleWorkflow.cs:541-548, 853-855`. — **Fix:** either dispatch `merge-approval` (3-way) and route `test`→re-enter CI/TDD, `reject`→`reportNeedsHuman`, `merge`→dispatchMerge; or formally delete `MergeApprovalWorkflow`/`WaitForMergeApprovalActivity` as dead (see those entries).
  - [P1] Error handling — The only error sink is `reportError`, reached **only** from `validateItem`→`Invalid` (`:756`). None of the sub-workflow dispatches (gatherContext, generatePlan, createTasks, createBranch, createPR, createTestCases, dispatchMerge, deploymentPipeline) have a failure/Error edge — a sub-workflow that finishes with `success=false` is silently ignored and the cycle proceeds (e.g. branch never created → PR dispatch runs with empty `branchName`). This is silent-failure, contrary to fail-closed. — `SingleIssueCycleWorkflow.cs:759-863`. — **Fix:** after each extract step, add a `FlowDecision` on the sub-result `success`/non-empty key and route failures to `notifyError`+`reportError`; never advance on an empty `branchName`/`prNumber`.
  - [P2] Structural correctness — Redundant terminal notification: both `closeIssue` (a `NotifyIssue` adding `tamma-completed`, `:586-588`) and `notifyMerged` (identical labels+message, `:703-704, :862`) fire, plus `deploymentPipeline` runs before `notifyMerged`. The "merged!" notice is emitted twice and the second only after deployment finishes. — `SingleIssueCycleWorkflow.cs:586-588, 703-704, 858-862`. — **Fix:** drop `closeIssue` or `notifyMerged`; send a distinct "deployed" notice after the pipeline.
  - [P2] Event emission — Sub-workflow dispatches and the `Assign`/`SetVariable` extract steps emit no DCB event; the cycle's auditability depends entirely on the leaf activities, several of which (git ADL) emit none either (see Branch/PR/Merge entries). The cycle has no `CYCLE.STARTED`/`CYCLE.COMPLETED` envelope event tagged with `issueId`/`tenantId`. — **Fix:** wrap entry/exit in a Tamma event-emitting activity (`CYCLE.ISSUE.STARTED/SUCCESS/FAILED`) carrying `issueId`, `tenantId`, `mode`.
  - [P2] Per-mode — `tenantId` is read at init (`:91`) and threaded into the LLM-bearing sub-workflows (context/plan/review/tasks/test-cases/code-review) but is **not** passed to `branch-creation`, `pull-request`, `merge`, or `deployment-pipeline` dispatches (`:358-364, :386-394, :558-564, :598-604`). Once Epic 38 mediates git writes per-tenant, those dispatches will need `tenantId` for the cross-tenant guard. — **Fix:** thread `tenantId` into all git/deploy sub-workflow inputs now.
- **Depends on:** Epic 38-1 (git activities), Epic 38-2 (agent-dispatch / TDD executor).

## MergeWorkflow  (`apps/tamma-elsa/src/Tamma.ElsaServer/Workflows/MergeWorkflow.cs`)
- **Purpose / owner story:** Squash-merge PR, close issue, delete branch via `MergePullRequestActivity`; outputs `success`+`mergeSha`. Story 2-10 (done). Still needed.
- **Health:** NEEDS-WORK
- **Findings:**
  - [P1] Architecture/pivot — `MergePullRequestActivity` calls `IGitHubIntegrationService.MergeGitHubPullRequestAsync` + `CloseGitHubIssueAsync` + `DeleteGitHubBranchAsync` directly in-engine (`MergePullRequestActivity.cs:67,80,85`). This is the **highest-blast-radius** git write in the cluster — a mis-scoped token = cross-tenant merge (§1.3, Epic 38 README "load-bearing cross-tenant guard"). — **Fix:** re-point to `PUT /api/v1/git/{repo}/pull-requests/{n}/merge` (+ issue PATCH) via `TammaApiClient`; API authorizes tenant↔repo before resolving a token. **Depends on: Epic 38-1.**
  - [P1] Event emission — `MergePullRequestActivity : Activity` (no Tamma base, `:26`) → no `GIT.PR.MERGED.*` DCB event for a merge/close/delete that mutates three resources. Most audit-critical missing event in the cluster. — **Fix:** emit terminal DCB event from the Epic 38-1 endpoint (tags: `prNumber`, `issueNumber`, `mergeSha`, `tenantId`, `repo`).
  - [P1] Error handling — Branch-delete failure is caught and swallowed to a warning (`MergePullRequestActivity.cs:83-90`) — acceptable as "best-effort" — but the *issue-close* call's result is **not checked** (`:80`): if `CloseGitHubIssueAsync` fails the activity still reports `Merged`, leaving the issue open with no signal. — **Fix:** check the close result; on failure emit a degraded event/warning but do not claim full success, or surface a `partial` outcome.
  - [P2] Structural correctness — `success` is keyed on non-empty `mergeSha` (`MergeWorkflow.cs:37`) rather than the activity's `Merged`/`Error` outcome; the `Error` outcome is unwired. — **Fix:** route `Error` to a failure output explicitly.

## TestingWorkflow  (`apps/tamma-elsa/src/Tamma.ElsaServer/Workflows/TestingWorkflow.cs`)
- **Purpose / owner story:** Skill-level-aware quality pipeline: trigger CI → wait (bookmark) → evaluate → coverage/lint/security checks → quality report, with a bounded MajorIssues auto-fix loop. Epic 3/12 quality gates. Actively used (dispatched by CiWithDebugRetry, Debugging, Mentorship, Tdd).
- **Health:** NEEDS-WORK
- **Findings:**
  - [P1] Error handling — `WaitForCIResultsActivity.TimeoutMinutes` (default 30) is **declared but never enforced**: the activity only `CreateBookmark`s and waits for external resume (`WaitForCIResultsActivity.cs:66`), with no scheduled timeout/wakeup. A CI run that never reports (crashed runner, dropped webhook) suspends the workflow **forever** — no fail-closed path. The workflow passes `TimeoutMinutes=30` (`TestingWorkflow.cs:99, :280`) believing it is honored. — **Fix:** implement a real timeout (Elsa `Timer`/scheduled bookmark or a parallel `Delay` race) that resumes with a `timeout`→fail result; or document and surface that the bookmark is unbounded.
  - [P1] Error handling — CI-results parse failure **fails open into a default** `CIResultsPayload { BuildPassed=false, Status="Unknown" }` (`WaitForCIResultsActivity.cs:115-119, 125-134`) and the activity completes normally; downstream `EvaluateResults` treats it as a real (failing) result. Swallowing a parse error into a fabricated payload violates fail-closed/no-silent-success — at least it defaults to *fail* (not pass), but with no error event. — **Fix:** emit a `CI.RESULTS.PARSE_FAILED` event and route to an explicit error/critical outcome rather than a silent default payload.
  - [P1] Structural correctness — On the retry path, `EvaluateRetryResults`→`MajorIssues` loops back into the **shared** `maxAttemptGuard` (`TestingWorkflow.cs:545`). The guard compares `attemptNumber < maxAttempts`, and `incrementAttempt` runs inside the loop, so it does terminate — but the *first-pass* `MajorIssues` also enters the same guard (`:521`) and the `commitFix` activity is shared, so the loop's `attemptNumber` semantics depend on `commitFix.AttemptNumber`/`MaxAttempts` matching the guard. The wiring is correct but fragile (one guard, two entries, shared mutable counter). — **Fix:** add a unit/replay test asserting the loop bounds at exactly `maxAttempts`; consider a dedicated retry-guard node per entry for clarity.
  - [P2] Naming / maintainability — Massive activity duplication: `CheckCoverage`/`CheckLinting`/`CheckSecurity`/`GenerateQualityReport` exist in three near-identical copies (base, `…Critical`, `…Retry`) plus triplicated `SetOutput` blocks (`TestingWorkflow.cs:131-450`). ~250 lines are copy-paste. — **Fix:** extract a reusable "checks→report→outputs" sub-sequence or sub-workflow invoked from each outcome.
  - [P2] Event emission — The quality checks and CI wait are not DCB-event-emitting Tamma activities; the only durable record is the serialized `QualityReport` output. No `GATE.*`/`CI.*` events per check. — **Fix:** emit per-gate `GATE.<NAME>.PASS/FAIL` events for the audit trail.

- **Findings:**
  - [P1] Architecture/pivot — GOOD on the LLM rule: each stage dispatches the centralized `llm-call` workflow with `role=devops`, `action=deploy` (`DeploymentPipelineWorkflow.cs:227-242`) rather than calling a provider directly — compliant with rule 1/2. ## Cross-cutting observations (patterns shared across this cluster)

1. **Git-platform writes are uniformly Epic-38 Class-A violators-by-co-hosting.** `CreateBranchActivity`, `CreatePullRequestActivity`, `MergePullRequestActivity` all inject and call `IGitHubIntegrationService` directly in the engine (§1.2 rows confirmed). They are latent (the service is null/unregistered in a standalone engine) but become live cross-tenant write hazards the moment the engine is per-tenant dedicated compute. All three are owned by **Story 38-1**; the merge write is the highest blast radius. No change needed in the workflow `.cs` files — the cutover is in the activities.

2. **The git ADL activities emit no DCB events.** `CreateBranchActivity`, `CreatePullRequestActivity`, `MergePullRequestActivity`, and `WaitForMergeApprovalActivity` all extend plain `Elsa…Activity`, NOT `TammaActivity`/`TammaOutcomeActivity`/`TammaAsyncActivity`. State-changing git writes (branch, PR, merge) and a human merge decision therefore leave no audit-trail event — a systemic hole vs the DCB 100%-audit goal. The Epic 38-1 endpoints should emit the terminal events from `Tamma.Api`; until then these should be re-based on a Tamma activity. (Contrast: `UpdateIssueStatusActivity`, `WaitForPRApprovalActivity`, `WaitForPRMergedActivity`, `ExecuteAgentActivity`, `DispatchAgentWorkflowActivity` are all event-emitting.)

3. **Two whole workflows are orphaned (dead).** `MergeApprovalWorkflow` (`merge-approval`) and `CiWithDebugRetryWorkflow` (`ci-with-debug-retry`) have **no dispatch caller** anywhere in `apps/tamma-elsa/src`. SingleIssueCycle long ago migrated to the inline `WaitForPRApprovalActivity` (binary approval) and to running CI inside `ExecuteAgentActivity`. Both orphans encode capabilities the live path lacks (human "needs-more-testing" decision; auto-debug CI retry). A deliberate decision is needed per workflow: re-wire to restore the capability, or delete to remove confusion. They are the two STALE entries.

4. **Fail-open gating in the two highest-stakes gates.** The deployment pipeline defaults stage status to `"success"` and the CI wait fabricates a default payload / has an unenforced timeout. Both contradict the brief's fail-closed / no-silent-success rule. Deploy gating especially must default to fail and require an explicit success token; the CI wait must enforce its declared timeout. These are the two non-git P1s most worth fixing regardless of Epic 38.

5. **Outcome-vs-derived-success mismatch in the thin git wrappers.** Branch/PR/Merge workflows each ignore the activity's declared `Created`/`Merged` vs `Error` outcome and instead derive `success` from "non-empty output" with a `SetVariable`. The `Error` outcome edges are dangling. Functionally tolerant today, but it discards the explicit failure signal and is the reason the orchestrator can't easily branch on sub-workflow failure (see SingleIssueCycle error-handling P1).

6. **`tenantId` is threaded into LLM sub-workflows but dropped on the git/deploy path.** SingleIssueCycle forwards `tenantId` to context/plan/review/tasks/test-cases/code-review but not to branch-creation/pull-request/merge/deployment-pipeline; DeploymentPipeline never forwards it to its `llm-call`. Once Epic 38 mediates git per-tenant and the deploy LLM needs per-tenant resolution, these omissions become correctness bugs in SaaS mode. Thread `tenantId` everywhere now (cheap, forward-compatible).
