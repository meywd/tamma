## DeleteTenantWorkflow  (`apps/tamma-elsa/src/Tamma.ElsaServer/Workflows/DeleteTenantWorkflow.cs`)
- **Purpose / owner story:** Story 28-5 — tear down a tenant (mark deleting → evict pool → optional pg_dump backup → drop schema → drop role → soft-delete CP row + terminal event + release placement). Triggered by `TENANT.DELETE_REQUESTED`. Still needed.
- **Health:** GOOD
- **Findings:**
  - [P1] Structural correctness / idempotency — The sequence is linear with no failure edge (lines 126-138). The activities are individually idempotent (probe-before-destroy / `IF EXISTS`), and the terminal `EmitDeletedSuccessActivity` correctly soft-deletes the CP row + emits `TENANT.DELETED.SUCCESS` via `IPlatformEventPublisher` **to the control-plane store** (`EmitDeletedSuccessActivity.cs:43-79`) — so the terminal event does NOT land in the doomed tenant store (a concern raised in prior sessions; **resolved here, confirmed sound**).   - [P2] Naming — Step A's activity is `MarkTenantDeletingActivity` but the inline comment (line 69) says it emits `TENANT.DELETE.REQUESTED`; verify the event name matches the `AGGREGATE.ACTION.STATUS` convention and the dashboard's expected name (`TENANT.DELETE.REQUESTED` vs `TENANT.DELETING.STARTED`). — `DeleteTenantWorkflow.cs:69` — **Fix:** confirm + document the exact emitted event type in the activity.
- **Depends on:** none.

- **Health:** NEEDS-WORK (the saga itself is well-built; the surrounding lifecycle is broken/dormant)
- **Findings:**
  - [P0] Structural correctness / silent data loss — **`RETIRE_SECRET_VERSION` tasks the saga enqueues are never drained in production.** The saga schedules retirement via `IRetireScheduler.ScheduleRetireAsync` (saga lines 320 / `ScheduleRetireOldActivity.cs:48`), which inserts a `platform_queued_tasks` row of type `RETIRE_SECRET_VERSION` (`RetireScheduler.cs:54-85`). The only code that drains it is `RetireScheduler.SweepDueRetireTasksAsync` (`RetireScheduler.cs:87`) — but **no hosted service or endpoint ever calls `SweepDueRetireTasksAsync`** (verified: the only references are the interface decl, the impl, and doc-comments; there is no `RotationSweeper` BackgroundService in either `Program.cs`). If the saga is superseded by `ISecretRevealService`/`KekRotationCoordinator`, mark it deprecated and remove the enqueue so no orphan rows accrue.
  - [P1] Error handling / resilience — The saga's `MintPendingVersionActivity` / `ActivateVersionAsync` calls are NOT retried (only push + probe have retry ladders — `TryPushAsync` lines 369-410, `TryProbeAsync` 412-452). A transient DB blip during mint or activate fails/compensates the whole rotation. The compensation path itself is correct (rollback push before deleting the pending version, lines 454-507; compensation-failed is terminal + alerted, never rethrown into a false success). — `RotateSecretSagaActivity.cs:228` — **Fix:** add a small retry around the gateway mint/activate calls, or document that those are single-attempt by design.

- **Health:** GOOD — **the feared shared-cross-tenant-cursor P0 pattern is NOT present here.**
- **Findings:**
  - **No shared-cursor bug.** Each tenant rollup is **window-bounded** (`CreatedAt >= hour && < hourEnd`) and upserted on the `(Hour, TenantId)` unique index (`ComputeTenantRollupActivity.cs:104-190`), reading each tenant's own `domain_events` via `ITenantDbContextFactory.CreateAsync(tenantId)`. ## Cross-cutting observations (patterns shared across this cluster)

1. **"Wired but not turned on" is the dominant state.** Three of the seven (ProvisionTenantV2, RotateSecret + its sweeper, and the cron side of HourlyAnalyticsRollup) are registered in DI/Elsa but have no live production trigger or drainer. This is mostly deliberate staged rollout (Epic 30 cutover; Epic 28 cron-off-by-default) — but it hides the one genuine bug: a dormant producer (`ScheduleRetireAsync`) with **no consumer** means any rotation that *does* fire leaks an un-retired secret version (the P0). When auditing "is it wired?", check producer AND consumer, not just registration.

2. **Two shared, type-blind task queues + two workers is fragile.** `platform_queued_tasks` (drained by `PlatformTaskWorker`, gated off) and the per-tenant queue (drained by `TaskQueueProcessor`, on) both use type-blind `ReserveNextAsync`. `RetireScheduler.SweepDueRetireTasksAsync` *also* calls `ReserveNextAsync` on the platform queue and "puts back" non-matching rows via `FailAsync(maxRetries: int.MaxValue)`. If/when both the platform worker and the sweeper run, they will race for each other's rows and churn retry counts. The repeatedly-documented prerequisite — **type-aware reservation** (a worker reserves only types it has handlers for) — is the right cross-cutting fix and unblocks both the RotateSecret P0 and the safe enablement of `PlatformTaskWorker:RunOnStartup`.

3. **Terminal-event store placement is correct for tenant lifecycle.** A prior-session worry was that tenant-terminal events land in the tenant's own (post-delete unreachable) store. Verified false for this cluster: `EmitDeletedSuccessActivity`, `MarkTenantActiveActivity`, and the v2 workflow's `TENANT.PROVISIONED.SUCCESS`/`TENANT.PROVISION.FAILED` all emit via `IPlatformEventPublisher` to the **control-plane** store. Good pattern — keep it.

4. **Audit-trail emission is uneven across the two provisioning paths.** The v2 workflow emits a full `TENANT.PROVISION.<STEP>.<OUTCOME>` DCB trail; the live v1 `CranlProvisioningWorkflow` emits none (row-state + logs only). Until the v2 cutover, the production provisioning path has the weaker audit trail — worth noting for any SOC2/compliance claim about provisioning observability.

5. **No rule-1 / pivot violations.** None of these workflows touch LLM, git-platform, Slack, or agent-dispatch surfaces, so the agent-architecture pivot (Epics 32/34/37/38) does not impose changes on this cluster. The external API calls that exist (Cranl) are the legitimate purpose of provisioning, mediated through a typed client inside `Tamma.Api`, and the Elsa engine itself holds no provider keys here.
