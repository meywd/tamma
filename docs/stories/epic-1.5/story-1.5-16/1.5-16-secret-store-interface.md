# Story 1.5-16: Secret Store Interface + Commitment Hash Protocol

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / LLM Safety)
**Status**: ready-for-dev
**Priority**: High

## Context — Why this story exists

Tamma is an LLM-driven autonomous development platform. Its workflows routinely
need to **create, rotate, verify, and deploy secrets** — database passwords, JWT
signing keys, OAuth client secrets, API keys, TLS certs — as part of
provisioning and deployment tasks.

The hard problem is: **the LLM driving the workflow must never see the secret
value**, because anything the LLM sees is a candidate for echoing back to the
user, being persisted into logs, or leaking via a subsequent tool call. Yet the
LLM still needs to:

- Request that a secret be created.
- Refer to a secret across workflow steps.
- Verify that a secret it created earlier is still intact.
- Confirm a secret has been deployed to its target (git provider secret store,
  K8s Secret, VPS `.env` file, etc.).
- Rotate, revoke, or retire a secret.
- Debug failures involving secrets **without** requesting the plaintext.

This story defines the TypeScript interface (`ISecretStore`), the commitment
hash protocol, the per-tenant key derivation chain, the scope model, and the
audit event shape that together form the contract every backend implementation
must satisfy. It is **interface-only** — no backend is implemented in this
story. Implementation stories follow as 1.5-17 (TammaVaultStore), 1.5-18
(GitHub), 1.5-19 (GitLab), etc.

This story supersedes the LLM-facing concerns of Story 1.5-4 (Secret Management
Integration). 1.5-4 remains valid for the "integrate with external enterprise
vault" use case; 1.5-16 is the layer above it that makes secret operations
LLM-safe.

### Architecture summary

Tamma is workflow-first: every secret operation (create, rotate, verify, probe,
cascade, leak-triggered rotation) is an Elsa workflow that invokes activities
as primitives. LLM-facing tools do not perform secret operations directly —
they start workflows and poll until terminal state.

Isolation is enforced by **process boundary**, not by type-system splits:
`packages/platforms/` defines the types (`ISecretStore` and friends), a new
`packages/secret-broker/` package hosts the implementation as a separate
service, and `packages/api/` never imports broker internals. The main API
process cannot materialise plaintext because it has no dependency on the
broker's crypto module. This story creates the types in `@tamma/platforms`
and scaffolds the broker package with the crypto primitives; the
`TammaVaultStore` implementation and HTTP service live in Story 1.5-17.

Three storage modes govern where a secret's encrypted value actually lives.
See *Implementation Guidance → Key Design Decisions → Decision 1* for the
full spec; briefly: `platform_only` (default — value in the git platform's
native store, Tamma keeps metadata + commitment only), `vault_copy` (opt-in
— value in both platform and TammaVault), `vault_only` (forced for
`tenant_root` scope, plain-git platform, or JWT signing keys — value only
in TammaVault, no platform mirror).

## User Story

As a **Tamma orchestrator workflow author**,
I want **a normalized secret store interface with a commitment-hash protocol**,
so that **LLM-driven workflows can create, verify, and manage secrets without
ever handling the plaintext values themselves, and so that every git platform
Tamma supports can be a pluggable backend.**

## Acceptance Criteria

### AC1: The `ISecretStore` interface is defined and exported

- [ ] An `ISecretStore` interface exists in
      `packages/platforms/src/secret-store.ts` with the exact method signatures
      specified in *Implementation Guidance → Interface Definition* below.
- [ ] The interface has NO method that returns plaintext secret values to its
      caller. `getSecretValue()` does not exist. Plaintext materialisation
      is confined to `packages/secret-broker/` (a separate process) and is
      reachable only via the CI fetch HTTP endpoint (Story 1.5-21) after
      OIDC validation (Story 1.5-20). `packages/api/` has no dependency on
      `packages/secret-broker/` — isolation is enforced by the dependency
      graph, not by type-system tricks.
- [ ] All method return types use the typed result shapes
      (`CreatedSecret`, `VerifyResult`, `RotationResult`, `SecretMetadata`,
      `ProbeResult`) defined in the same file.
- [ ] TypeScript strict mode compiles with zero errors including
      `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess`.
- [ ] The interface is exported from `packages/platforms/src/index.ts`.
- [ ] A CI lint rule blocks any import of `@tamma/secret-broker/*` from
      files inside `packages/api/` or `packages/orchestrator/` (the
      LLM-facing code paths). Failing the rule fails the PR.

### AC2: Commitment hash protocol is specified and implemented

- [ ] A pure helper module exists at
      `packages/platforms/src/secret-store-crypto.ts` containing:
  - `deriveTenantKeys(rootKey: Buffer, tenantId: string): TenantKeys` — HKDF
    expansion producing `{ encKey, hmacKey, fingerprintKey }`.
  - `computeCommitment(value: Buffer, hmacKey: Buffer): string` — hex
    HMAC-SHA256 of the full 32-byte output.
  - `computeFingerprint(value: Buffer, fingerprintKey: Buffer): string` —
    12-hex-char truncated HMAC, no plaintext characters leaked.
  - `generateSecretValue(type: SecretType, length?: number): Buffer` — type-
    aware random generation using `crypto.randomBytes`.
- [ ] HKDF uses RFC 5869 with `salt = "tamma-vault-v1"` and
      `info = tenantId + ":" + <purpose>` where `<purpose>` is one of
      `"enc"`, `"hmac"`, `"fingerprint"`.
- [ ] The three derived keys are proven independent by a unit test that
      confirms flipping one bit in the root key changes all three outputs and
      that the three outputs for the same root key are distinct.
- [ ] A unit test confirms that the same (rootKey, tenantId, value) always
      produces the same commitment, and that different tenantIds produce
      different commitments for the same value.
- [ ] All test vectors for HKDF derivation are documented in
      `secret-store-crypto.test.ts` so future refactors preserve compatibility.

### AC3: Scope model covers all supported platforms

- [ ] A `SecretScope` discriminated union is defined supporting all scope
      kinds Tamma needs: `'repo'`, `'org'`, `'project'`, `'environment'`,
      `'tenant_root'`.
- [ ] Each variant carries exactly the fields needed to address a secret
      uniquely on a given platform (e.g. `{kind: 'repo', platform, owner, repo}`).
- [ ] A `tenant_root` scope exists for secrets that must never live in any
      repo (JWT signing keys, Tamma service API keys, GitHub App private
      keys). These can only be stored in `TammaVaultStore`.
- [ ] A helper `isScopeAddressableOn(scope, platform)` returns whether a given
      scope is valid for a given backend (e.g. `'environment'` on Gitea returns
      false because Gitea ≤ 1.21 has no environment secrets).

### AC4: Audit event shape is defined

- [ ] A `SecretAuditEvent` type is defined matching the DCB event schema
      (`type`, `timestamp`, `tags`, `metadata`, `data`).
- [ ] The following audit event types are enumerated as constants in
      `secret-store-events.ts`:
  - `SECRET.CREATED.SUCCESS`, `SECRET.CREATED.FAILED`
  - `SECRET.ROTATED.SUCCESS`, `SECRET.ROTATED.FAILED`
  - `SECRET.VERIFIED.MATCH`, `SECRET.VERIFIED.MISMATCH`
  - `SECRET.REVOKED.SUCCESS`, `SECRET.REVOKED.FAILED`
  - `SECRET.DEPLOYED.SUCCESS`, `SECRET.DEPLOYED.FAILED`
  - `SECRET.LISTED` (read-only audit)
  - `SECRET.PROBED.SUCCESS`, `SECRET.PROBED.FAILED` (active probe outcome)
  - `SECRET.LEAK_DETECTED` (emitted by Story 1.5-28's leak scanner)
  - `SECRET.CI_FETCHED.SUCCESS`, `SECRET.CI_FETCHED.DENIED`
  - `SECRET.WORKFLOW.STARTED`, `SECRET.WORKFLOW.COMPLETED`,
    `SECRET.WORKFLOW.FAILED`, `SECRET.WORKFLOW.STALLED`,
    `SECRET.WORKFLOW.BLOCKED_DUPLICATE` (workflow-level audit, emitted
    by the LLM tool wrapper or the `LlmWorkflowLaunchRegistry` when a
    workflow is started, ends in terminal state, is escalated via
    `alert_orchestrator`, or is blocked because a duplicate-goal
    workflow is already running)
  - `SECRET.DRIFT_DETECTED` (opt-in background monitoring — see Story 1.5-33)
- [ ] Every audit event carries: `secretId`, `tenantId`, `scope`, `actor` (user
      or service), `rootKeyVersion`. Event data NEVER contains the secret
      value or encrypted blob — only the commitment hash for correlation.
- [ ] A helper `emitSecretEvent(eventStore, type, payload)` wraps event
      emission so backends can call one function to produce a schema-valid
      audit record.

### AC5: Fingerprint format is specified and tested

- [ ] Fingerprint is exactly 12 hex characters (48 bits of HMAC output).
- [ ] Default display format is `xxxx-xxxx-xxxx` (three groups of four,
      separated by `-`), produced by a `formatFingerprint(fingerprint: string)`
      helper. API-returned form is unformatted.
- [ ] A unit test verifies that for a 32-byte random value, the fingerprint
      contains no characters from the original value (contrast with the
      legacy first-4-last-4 pattern).
- [ ] A collision-analysis test confirms that with 100,000 random 32-byte
      values and a single tenant key, fingerprint collisions are below 1%
      (documents the 48-bit collision curve for reviewers).

### AC6: `root_key_version` field is present on all writes

- [ ] Every `CreatedSecret` return value includes `rootKeyVersion: number`.
- [ ] The interface explicitly supports multi-version root keys via a
      `getRootKey(version?: number): Buffer` helper in the crypto module that
      reads `TAMMA_VAULT_ROOT_KEY` (implicit v1) and any
      `TAMMA_VAULT_ROOT_KEY_V<N>` env vars for higher versions.
- [ ] If no `TAMMA_VAULT_ROOT_KEY` is set and `NODE_ENV === 'production'`, the
      helper throws at first call with a clear error (fail-fast, consistent
      with the JWT_SECRET fix in commit `126dfdf`).
- [ ] In non-production, a loud warning is emitted and a deterministic
      development-only key is synthesized (separate from JWT_SECRET — do not
      reuse). Document the dev key explicitly so it's never mistaken for a
      real root.

### AC7: `verifySecret` is multi-level + fails closed on all edge cases

- [ ] `verifySecret(id, expectedCommitment)` performs the highest-fidelity
      check the secret's storage mode permits. Return value always includes
      a `verificationLevel` field so the caller can reason about trust:
  - `'vault_value'` — for `vault_only` and `vault_copy` modes: reads the
    encrypted blob, decrypts with the tenant `encKey`, recomputes the
    commitment from the decrypted plaintext, compares to `expectedCommitment`
    via `crypto.timingSafeEqual`. Catches rotations and re-encryptions
    performed via Tamma.
  - `'metadata'` — for `platform_only` mode: compares the stored
    `metadata.commitment` against `expectedCommitment` via `timingSafeEqual`.
    Cannot detect out-of-band edits because GitHub/GitLab/Gitea secret APIs
    are write-only — there is no way to read a value back through the API.
  - `'unavailable'` — the secret is `not_found` or the vault is unreachable;
    `matches` must be `false`.
- [ ] `verifySecret(id, commitment)` on an unknown `id` returns
      `{ matches: false, status: 'not_found', verificationLevel: 'unavailable' }`
      — never throws and never reveals whether the id ever existed.
- [ ] `verifySecret(id, commitment)` on a revoked secret still computes
      `matches` against the stored commitment and returns
      `{ matches: <bool>, status: 'revoked', revokedAt, revokedReason, verificationLevel }`.
      This lets the LLM distinguish "I'm pointing at a revoked secret and
      should refresh my handle" from "I'm holding a wrong commitment".
- [ ] `existsInTarget(id)` on a revoked secret returns `{ present: false }`.
- [ ] Commitment comparison uses `crypto.timingSafeEqual`. A buffer-length
      mismatch returns `false` without calling `timingSafeEqual` (which
      requires equal lengths).
- [ ] `verificationLevel: 'metadata'` results explicitly do NOT guarantee
      "the live value at the git-platform target matches." The LLM must
      escalate to `probeSecret()` (AC11) if it needs a functional check.

### AC8: Documentation + ADR entry

- [ ] `.dev/decisions/YYYY-MM-DD-secret-store-commitment-hash-protocol.md`
      documents the design decisions: why HKDF, why HMAC rather than plain
      SHA-256, why 48-bit fingerprints, the three-mode storage model, the
      LLM workflow polling contract, the process-boundary isolation model.
- [ ] `packages/platforms/src/secret-store.ts` has a top-of-file comment
      (≤30 lines) linking to the ADR and summarising the invariants:
  1. No method returns plaintext to its caller.
  2. All derivations are stateless (no stored per-tenant keys).
  3. Commitments are computed with `timingSafeEqual`.
  4. Fingerprints reveal zero bits of the value.
  5. Plaintext handling is isolated to `packages/secret-broker/` process.

### AC9: Three-mode storage model + config schema

- [ ] A `SecretStoreMode` type is defined as
      `'platform_only' | 'vault_copy' | 'vault_only'`.
- [ ] `CreatedSecret` and `SecretMetadata` both include `mode: SecretStoreMode`
      so callers always know which mode applied to a given write.
- [ ] A config schema is defined under `secrets` in `.tamma/config.yaml`:
  ```yaml
  secrets:
    default_mode: platform_only      # platform_only | vault_copy | vault_only
    mode_overrides:
      - match: { scope_kind: tenant_root }
        mode: vault_only
      - match: { type: jwt_signing_key }
        mode: vault_only
      - match: { platform: plain_git }
        mode: vault_only
      - match: { name_pattern: "^DB_PROD_" }
        mode: vault_copy
  ```
- [ ] `resolveMode(input: CreateSecretInput, config: SecretsConfig): SecretStoreMode`
      is a pure function that applies the first matching override, falling
      back to `default_mode`. Unit tests cover: default application, single
      override match, multiple-match precedence (first match wins), all
      `match` predicate types (`scope_kind`, `type`, `platform`,
      `name_pattern`), and the forced overrides for `tenant_root`/plain-git/
      JWT that cannot be disabled by config.
- [ ] The three forced-`vault_only` cases (`tenant_root` scope, `plain_git`
      platform, `jwt_signing_key` type) are enforced in `resolveMode` itself,
      not left to backend implementations — a user config that tries to
      override them to `platform_only` is rejected at config-load time with
      a clear error.

### AC10: LLM workflow-polling contract + enforcement

**The contract:**

- [ ] Every LLM-facing tool that triggers a workflow returns
      `{ workflowId: string, status: 'running' | 'completed' | 'failed', result?, error? }`.
      If `status === 'running'`, the LLM MUST call `checkWorkflow(workflowId)`
      with exponential backoff (500ms → 5s, max wall clock 10 minutes per
      workflow unless overridden).
- [ ] While waiting for a workflow `W` targeting goal `G`, the LLM MUST NOT
      attempt any alternative path to achieve the same goal `G`. Specifically:
      no direct DB writes, no manual config-file edits, no shell-out to
      `openssl`/`ssh-keygen`/similar, no spawning a different workflow that
      duplicates `W`'s effect.
- [ ] While waiting, the LLM MAY work on other goals `G' ≠ G` in parallel —
      different tickets, different review items, different features, other
      non-workflow tasks. The constraint is scoped to "don't side-channel
      around the pending workflow", not "don't do anything."
- [ ] If the workflow exceeds its polling wall-clock budget (default 10 min,
      or hits a soft delay threshold at 2 min with no progress), the LLM
      MUST raise an `alert_orchestrator` tool call with payload
      `{workflowId, reason: 'delay' | 'timeout' | 'stuck', lastStatus, elapsedMs}`
      and switch to parallel-safe work until the orchestrator responds. The
      LLM MUST NOT attempt to kill the workflow, restart it with different
      parameters, or work around it.
- [ ] If the workflow terminates as `'failed'`, the LLM surfaces the error
      verbatim to the user/operator and awaits instruction. It does not
      retry with modified inputs unless explicitly authorised.
- [ ] A `checkWorkflow(workflowId): WorkflowStatus` tool exists as a
      companion to every workflow-triggering tool.
- [ ] An `alert_orchestrator(payload): void` tool exists for the delay/
      timeout/stuck escalation path. The orchestrator surface (human
      operator, higher-level agent, on-call rotation) receives these alerts
      via a channel defined in Story 1.5-18 (Secret Activities) — this
      story only fixes the tool signature.
- [ ] The `SECRET.WORKFLOW.STARTED`, `SECRET.WORKFLOW.COMPLETED`,
      `SECRET.WORKFLOW.FAILED`, and `SECRET.WORKFLOW.STALLED` audit events
      (AC4) are emitted by the tool wrapper, not by the workflow itself.
      An LLM that invokes a tool, waits, and gets a result produces
      exactly one `STARTED` and one `COMPLETED/FAILED/STALLED` event in
      the audit stream regardless of how many `checkWorkflow` polls it did.

**Enforcement:**

- [ ] The LLM's tool catalog for secret-management roles is restricted to
      **workflow-triggering tools only**: `create_secret`, `rotate_secret`,
      `verify_secret`, `probe_secret`, `deploy_secret_to`, `revoke_secret`,
      `list_secrets`, `check_workflow`, `alert_orchestrator`. No raw
      `exec_shell`, no `write_file` pointing at `.env` or `k8s/secret*.yaml`,
      no direct SQL tool, no HTTP tool that can reach the secret broker's
      internal endpoints. Tool catalog curation is enforced in the
      orchestrator's role-to-tool map (Story 1.5-19).
- [ ] A `LlmWorkflowLaunchRegistry` records every workflow started by the
      LLM with `{workflowId, role, tool, goalHash, startedAt, terminalAt?, status}`.
      `goalHash` is an HMAC of the serialized tool input used to detect
      "same goal, second workflow" attempts. The registry lives in the
      orchestrator, not the secret broker — it's enforcement infrastructure,
      not a secret-store concern. Interface defined in 1.5-16, implementation
      in Story 1.5-19.
- [ ] A guard rule in the orchestrator blocks a `create_secret`/`rotate_secret`/
      `revoke_secret` call if the registry shows an existing `running`
      workflow with the same `(role, goalHash)`. The guard emits
      `SECRET.WORKFLOW.BLOCKED_DUPLICATE` and returns an error to the LLM
      pointing at the pending workflowId.
- [ ] The system-prompt snippet under `system.secret-management` role is
      authored in the prompt store with verbatim text covering all seven
      contract rules above. A test asserts the snippet is rendered into
      every agent role that has access to any secret-management tool. If
      a role gains a secret tool without the snippet, the test fails.

### AC11: `probeSecret` tool interface (implementation deferred to 1.5-27)

- [ ] A `probeSecret(secretId, probeType, probeConfig?): Promise<ProbeResult>`
      method is defined on `ISecretStore` (or on a sibling
      `ISecretProber` interface if that keeps the types cleaner — the
      implementer decides and documents).
- [ ] `ProbeType` is a string-literal union covering the v1 probe types:
      `'http_bearer' | 'database_connect' | 'jwt_sign_verify' | 'smtp_auth' | 'github_token'`.
      Backends MAY implement a subset; unsupported types return
      `{ success: false, errorCategory: 'not_supported' }`.
- [ ] `ProbeResult` shape:
  ```typescript
  interface ProbeResult {
    success: boolean;
    verificationLevel: 'runtime_probe';
    lastProbedAt: string;
    errorCategory?: 'auth_failed' | 'unreachable' | 'timeout' | 'config_error' | 'not_supported';
    /** Always scrubbed via the redaction pipeline. Never contains the secret value. */
    errorMessage?: string;
  }
  ```
- [ ] The interface contract requires that ALL `errorMessage` strings pass
      through `packages/shared/src/telemetry/utils.ts:redactSensitiveKeys`
      (or an equivalent helper) before being returned. A unit test injects
      a known secret value into a simulated probe failure path and asserts
      the value does not appear in the `errorMessage`.
- [ ] Probe implementations themselves are OUT of scope for this story —
      they land in Story 1.5-27. This story only defines the interface so
      `verifySecret` can meaningfully return
      `verificationLevel: 'metadata'` and signal that the caller should
      escalate to probing.

## Dev Notes

### Requirements Context Summary

**Epic Context:** Epic 1.5 covers foundation & core infrastructure. Secret
handling was partially addressed in Story 1.5-4 (Secret Management
Integration) which describes generic integration with enterprise vaults
(HashiCorp Vault, AWS Secrets Manager, Azure Key Vault). That story does
not address the LLM-safety question — specifically, how an LLM-driven
workflow can request, verify, and deploy secrets without the plaintext ever
entering LLM context. This story fills that gap by defining the interface and
protocol; follow-on stories (1.5-17 through 1.5-22) implement specific
backends.

**Technical Context:** Tamma already abstracts seven git platforms behind
`IGitPlatform` (GitHub, GitLab, Gitea, Forgejo, Bitbucket, Azure DevOps,
plain Git). `ISecretStore` is a sibling abstraction using the same pattern:
platform-agnostic interface, pluggable backends per platform plus a native
`TammaVaultStore`. The commitment hash protocol is the cryptographic
primitive that enables LLM-safe verification — it lets the LLM hold a
short, non-reversible reference to a secret it once created, then later
prove to the store "the secret at this id is still what I created" without
ever handling the value.

**Integration Points:**

- **Event store (Epic 4)**: Audit events defined here feed into the DCB event
  stream. Schema must match existing DCB patterns exactly.
- **Auth (Story 16-7)**: Service API keys will migrate to being tracked via
  `ISecretStore` commitments — a unified audit trail across all secret types.
- **Platform adapters (Stories 1-5 through 1-11)**: Existing
  `GitHubPlatform`, `GitLabPlatform`, etc. will gain a companion
  `GitHubSecretStore`, `GitLabSecretStore`, etc. in follow-on stories. They
  share the same `@octokit/rest` / GitLab SDK client as their parent
  `IGitPlatform` where possible.
- **MCP tool surface (follow-on story)**: An MCP server will wrap
  `ISecretStore` methods as LLM-facing tools. That's a separate story;
  this one is interface-only and does not expose any tool surface yet.

### Implementation Guidance

**Key Design Decisions:**

1. **Three-mode storage: TammaVault is the authoritative *ledger*; value
   location is per-secret.** TammaVault always stores metadata (id, scope,
   name, type, commitment, fingerprint, audit trail). Whether it also stores
   the encrypted value is operator-selectable per secret via three modes:

   - **`platform_only`** (default) — encrypted value lives only in the git
     platform's native secret store (GitHub Actions secrets, GitLab CI/CD
     variables, etc.). TammaVault holds just the metadata. This is what an
     operator who "trusts GitHub Secrets more than our Postgres" wants.
     `verifySecret` runs at `verificationLevel: 'metadata'` — it compares
     against the commitment Tamma recorded at write time. Out-of-band edits
     (someone edited the secret in GitHub's UI) are not detectable at verify
     time because GitHub's secret API is write-only; the LLM must escalate
     to `probeSecret` if it needs a live check.

   - **`vault_copy`** (opt-in) — encrypted value is in both the git platform
     AND TammaVault. Writes are two-phase: if one fails, the row is flagged
     `out_of_sync` and the next `verifySecret` returns the flag so the LLM
     knows to escalate. Useful for critical secrets where operators want
     independent backup + higher-fidelity verification
     (`verificationLevel: 'vault_value'`).

   - **`vault_only`** (forced for `tenant_root` scope, plain-git platform,
     `jwt_signing_key` type) — encrypted value only in TammaVault. No
     platform mirror exists. Required for secrets that must not live in any
     repo (tenant root keys, JWT signing keys read at runtime by the API
     process itself) or for platforms with no native secret store. Config
     cannot override these forced cases — attempting to do so fails at
     config-load time.

   The name "source of truth" from the earlier design draft was inaccurate —
   TammaVault is always the authoritative **ledger** (commitment + audit),
   but not always the authoritative **value store**. See `resolveMode` in
   AC9 for the precedence rules.

2. **Per-tenant HMAC keys are derived, never stored.** HKDF-SHA256 from a
   single `TAMMA_VAULT_ROOT_KEY` (32 random bytes in an env var). On every
   secret operation we re-derive the tenant's three keys — encryption, HMAC,
   fingerprint — from the root key plus `tenantId`. Stateless. No per-tenant
   key table, no migration, no backup surface.

3. **Commitment hash is HMAC, not plain SHA-256.** HMAC with a tenant-specific
   key prevents offline brute-force even if a commitment leaks into a log
   line — an attacker would need both the hash and the HMAC key (which never
   leaves the secret broker process). Plain SHA-256 of a short password is
   rainbow-table attackable.

4. **Commitment comparison uses `crypto.timingSafeEqual`.** A timing oracle
   that lets an attacker distinguish "first byte matches" from "no bytes
   match" is a known class of vulnerability in auth systems. Not load-bearing
   for our threat model (remote attackers don't typically see verify latency
   at microsecond resolution), but free defence in depth.

5. **Fingerprint is a 12-hex-char truncated HMAC, not `first-4 + last-4`.**
   Traditional fingerprints reveal 25% of a 32-char password's characters.
   Truncated HMAC reveals zero. 48 bits of fingerprint space means collisions
   only become likely above ~2.4 million secrets per tenant — well beyond
   any plausible fleet size.

6. **Three derived keys per tenant via HKDF domain separation.** `encKey`,
   `hmacKey`, `fingerprintKey` all derive from the same root via HKDF with
   different `info` strings. Domain separation ensures that compromising one
   derivation context does not compromise the others — a useful property if
   any specific helper ends up exposed via a side channel we didn't foresee.

7. **No `getSecretValue()` on `ISecretStore`.** The interface has no method
   that returns plaintext. Plaintext materialisation is confined to
   `packages/secret-broker/` — a separate package that hosts the
   `TammaVaultStore` implementation, the AES-256-GCM encrypt/decrypt path,
   and the CI fetch HTTP endpoint. `packages/api/` and
   `packages/orchestrator/` (the LLM-facing code paths) have **no dependency**
   on `@tamma/secret-broker` — the main API process literally cannot decrypt
   a stored secret because it doesn't import the crypto module. This is
   enforced structurally by the package dependency graph and backed by a CI
   lint rule that rejects cross-package imports. It replaces the earlier
   proposal of splitting `ISecretStore` from a hypothetical
   `IRuntimeSecretReader` interface — the package boundary gives the same
   isolation with less type-system gymnastics.

8. **`verifySecret` is multi-level, not a simple ledger lookup.** Returns a
   `verificationLevel` field describing how deep the check went:
   `'vault_value'` (decrypt + recompute + compare — available in
   `vault_only`/`vault_copy` modes), `'metadata'` (compare stored commitment
   to expected — available in all modes), `'unavailable'` (secret not found
   or vault unreachable). This gives callers an honest trust signal. An LLM
   holding a `'metadata'` result knows the check is only as good as "Tamma's
   ledger is consistent with what I'm holding"; for high-fidelity checks it
   escalates to `probeSecret`. Active drift detection (background monitoring
   via platform webhooks) is a separate opt-in feature in Story 1.5-33 that
   surfaces its results as `driftDetected: true` on `VerifyResult` when
   enabled.

9. **`probeSecret` exists as a debugging escape hatch without breaking
   invariant 7.** Probes run server-side inside the broker: the broker
   decrypts the value (for `vault_*` modes) or triggers a one-shot test
   workflow with runtime access (for `platform_only` mode), performs the
   probe, and returns only `{success, errorCategory, errorMessage}`. The
   `errorMessage` is always passed through the redaction pipeline before
   return. Probes are rate-limited per secret to prevent a misbehaving
   LLM from using them as a brute-force signal. Implementation lives in
   Story 1.5-27; this story defines the interface so `verifySecret` can
   meaningfully point callers at it.

10. **Every LLM-driven secret operation is a workflow; the LLM polls, may
    work on unrelated goals in parallel, and escalates on delay.** Tools
    that start workflows return
    `{workflowId, status: 'running' | 'completed' | 'failed', result?}`.
    If `'running'`, the LLM polls `checkWorkflow(workflowId)` with
    exponential backoff (500ms→5s, 10 min wall clock).

    **Scoped non-improvisation.** While waiting for workflow `W` targeting
    goal `G`, the LLM cannot attempt any alternative path to achieve `G` —
    no direct DB writes, no manual config edits, no `openssl` shell-out,
    no second workflow duplicating `W`. The LLM *can* work on other goals
    `G' ≠ G` in parallel (different tickets, unrelated review comments,
    other non-workflow work). The constraint is narrow: don't side-channel
    around the pending workflow, not "don't do anything."

    **Delay handling.** At a soft threshold (2 min with no terminal state)
    or hard timeout (10 min), the LLM calls `alert_orchestrator(payload)`
    to escalate to a human or higher-level agent. It does NOT kill the
    workflow, restart it, or work around it. It switches to parallel-safe
    work and awaits instructions.

    **Structural enforcement** (not just prompt). The LLM's tool catalog
    for secret-management roles is curated so that only workflow-triggering
    tools are exposed: no `exec_shell`, no raw SQL, no `write_file` to
    `.env` or `k8s/secret*.yaml`, no HTTP tool that can reach the broker's
    internal endpoints. An `LlmWorkflowLaunchRegistry` in the orchestrator
    tracks every started workflow keyed by `(role, goalHash)` where
    `goalHash = HMAC(serialized_input)`. A guard blocks a second workflow
    with the same `(role, goalHash)` while the first is still running —
    "same goal, second attempt" attempts fail loudly with a pointer at the
    pending workflowId.

    **Procedural enforcement** (complementing the structural). A mandatory
    system-prompt directive under `system.secret-management` role spells
    out the contract verbatim and is injected into every agent role with
    secret-tool access. A test fails if a role gains a secret tool without
    the directive.

    **Layering note.** `ISecretStore` is the **internal synchronous
    interface** the broker implements. Its methods return concrete results
    (`CreatedSecret`, `VerifyResult`, etc.) — not `WorkflowStatus`. The
    workflow wrapping happens one layer up: Elsa activities call
    `ISecretStore` methods directly and return their results into the
    workflow state; LLM-facing tools (Story 1.5-19) wrap *workflow
    invocations*, not `ISecretStore` calls, and return `WorkflowStatus<T>`
    to the LLM. This split matters because it means the broker service
    implementing `ISecretStore` has no dependency on Elsa or workflow
    semantics — it's a plain HTTP service with a synchronous request/
    response model. The workflow/polling/alerting layer is strictly above.

**Technical Specifications — Interface Definition:**

```typescript
// packages/platforms/src/secret-store.ts

/**
 * ISecretStore — LLM-safe secret management interface.
 *
 * INVARIANTS:
 *   1. No method returns plaintext values to its caller.
 *   2. All tenant keys are derived from TAMMA_VAULT_ROOT_KEY via HKDF.
 *      Per-tenant keys are never stored.
 *   3. Commitment hashes use HMAC-SHA256 with tenant-scoped keys and
 *      timingSafeEqual comparison.
 *   4. Fingerprints reveal zero characters of the underlying value.
 *   5. Plaintext handling is isolated to `packages/secret-broker/` process.
 *      `@tamma/api` and `@tamma/orchestrator` do not depend on
 *      `@tamma/secret-broker` — enforced by a CI lint rule.
 *
 * See .dev/decisions/YYYY-MM-DD-secret-store-commitment-hash-protocol.md
 * for the full rationale.
 */

export type SecretType =
  | 'password'
  | 'api_key'
  | 'jwt_signing_key'
  | 'tls_cert'
  | 'ssh_key'
  | 'arbitrary';

export type SecretStatus = 'active' | 'rotating' | 'revoked' | 'not_found';

export type SecretStoreMode = 'platform_only' | 'vault_copy' | 'vault_only';

export type VerificationLevel = 'vault_value' | 'metadata' | 'unavailable';

export type ProbeType =
  | 'http_bearer'
  | 'database_connect'
  | 'jwt_sign_verify'
  | 'smtp_auth'
  | 'github_token';

export type SecretScope =
  | { kind: 'repo'; platform: string; owner: string; repo: string }
  | { kind: 'org'; platform: string; owner: string }
  | { kind: 'project'; platform: string; projectId: string }
  | { kind: 'environment'; platform: string; owner: string; repo: string; env: string }
  | { kind: 'tenant_root'; tenantId: string };

export interface CreatedSecret {
  /** Opaque handle the caller stores. Never contains plaintext. */
  secretId: string;
  /** HMAC-SHA256 commitment, hex. Safe to carry in LLM context. */
  commitmentHash: string;
  /** 12-hex-char truncated HMAC for human disambiguation. */
  fingerprint: string;
  /** Root key version that produced this commitment. */
  rootKeyVersion: number;
  /** Which storage mode applied to this write — determines verify fidelity. */
  mode: SecretStoreMode;
  createdAt: string;
  expiresAt?: string;
}

export interface VerifyResult {
  /** True if the stored commitment matches `expectedCommitmentHash`,
   *  compared via `crypto.timingSafeEqual`. */
  matches: boolean;
  /** How deep the check went — see Decision 8 in Dev Notes. */
  verificationLevel: VerificationLevel;
  status: SecretStatus;
  mode?: SecretStoreMode;
  createdAt?: string;
  lastRotatedAt?: string;
  revokedAt?: string;
  revokedReason?: string;
  /** Populated only when drift monitoring is enabled (Story 1.5-33). */
  driftDetected?: boolean;
  driftDetectedAt?: string;
}

export interface RotationResult {
  /** Handle remains the same after rotation — only the value changes. */
  secretId: string;
  /** New commitment, reflecting the post-rotation value. */
  newCommitmentHash: string;
  newFingerprint: string;
  mode: SecretStoreMode;
  gracePeriodEndsAt: string;
  rootKeyVersion: number;
}

export interface SecretMetadata {
  secretId: string;
  scope: SecretScope;
  name: string;
  type: SecretType;
  commitmentHash: string;
  fingerprint: string;
  mode: SecretStoreMode;
  status: SecretStatus;
  createdAt: string;
  lastRotatedAt?: string;
}

export interface ProbeResult {
  success: boolean;
  verificationLevel: 'runtime_probe';
  lastProbedAt: string;
  errorCategory?: 'auth_failed' | 'unreachable' | 'timeout' | 'config_error' | 'not_supported';
  /** Always scrubbed via redactSensitiveKeys() before returning. */
  errorMessage?: string;
}

export interface WorkflowStatus<R = unknown> {
  workflowId: string;
  status: 'running' | 'completed' | 'failed';
  startedAt: string;
  completedAt?: string;
  result?: R;
  error?: { code: string; message: string };
}

export interface DeployTarget {
  /** Where to deploy: the same SecretScope kinds as addressable targets. */
  scope: SecretScope;
  /** Name the secret should have at the target (may differ from source name). */
  targetName: string;
}

export interface CreateSecretInput {
  scope: SecretScope;
  name: string;
  type: SecretType;
  /** Optional override for default length. Only honoured for `password`,
   *  `api_key`, and `arbitrary` types. */
  length?: number;
  /** Metadata the caller can attach. Never logged alongside values. */
  metadata?: Record<string, string>;
  /** ISO-8601 expiry. Backends SHOULD enforce but are not required to. */
  expiresAt?: string;
  /** Optional config-overriding mode hint. Subject to forced-override rules
   *  in resolveMode — tenant_root, plain-git, jwt_signing_key cannot be
   *  downgraded from `vault_only`. */
  modeOverride?: SecretStoreMode;
}

export interface ISecretStore {
  /**
   * Generate a secret server-side and persist it in this store. The value
   * is produced by `generateSecretValue()` and is never returned to the
   * caller. Returns a handle + commitment + fingerprint.
   *
   * Emits `SECRET.CREATED.SUCCESS` on success.
   */
  createSecret(input: CreateSecretInput): Promise<CreatedSecret>;

  /**
   * Rotate a secret in place. The `secretId` is stable across rotations
   * (callers keep the same handle). The old value enters `rotating` status
   * for a backend-specified grace period; callers holding the old commitment
   * will see `matches: false, status: 'rotating'` from `verifySecret`.
   *
   * Emits `SECRET.ROTATED.SUCCESS` on success.
   */
  rotateSecret(secretId: string): Promise<RotationResult>;

  /**
   * Multi-level verification. Performs the highest-fidelity check the
   * secret's mode permits:
   *   - `vault_only` / `vault_copy`: decrypt stored blob, recompute
   *     commitment, compare via `timingSafeEqual`. Returns
   *     `verificationLevel: 'vault_value'`.
   *   - `platform_only`: compare `metadata.commitmentHash` against
   *     `expectedCommitmentHash`. Returns `verificationLevel: 'metadata'`.
   *   - Unknown id or vault unreachable: returns
   *     `verificationLevel: 'unavailable'` with `matches: false`.
   *
   * NEVER throws. On unknown id returns `status: 'not_found'` without
   * revealing whether the id ever existed.
   *
   * Emits `SECRET.VERIFIED.MATCH` or `SECRET.VERIFIED.MISMATCH`.
   */
  verifySecret(
    secretId: string,
    expectedCommitmentHash: string,
  ): Promise<VerifyResult>;

  /**
   * Get metadata for a single secret by id. Returns `null` for
   * unknown id — matches the fail-closed semantics of verifySecret and
   * never reveals whether the id ever existed.
   *
   * Use this instead of `listSecrets` when you have a specific
   * secretId — it's a single indexed lookup instead of a scope scan.
   */
  getSecretMetadata(secretId: string): Promise<SecretMetadata | null>;

  /**
   * Find all secrets whose stored fingerprint matches the given value,
   * scoped to a single tenant. Used by the leak detection workflow
   * (Story 1.5-28): the scanner computes an HMAC fingerprint of a
   * suspicious string observed in an LLM response or git commit, then
   * queries this method to find matching secrets for auto-rotation.
   *
   * Fingerprints are tenant-keyed — a fingerprint from tenant A cannot
   * match a secret under tenant B even if both secrets share the same
   * plaintext. This is an O(log N) indexed lookup in Postgres (the
   * schema has `idx_vault_secrets_fingerprint`).
   *
   * Returns metadata only. NEVER returns the value or encrypted blob.
   */
  findSecretsByFingerprint(
    fingerprint: string,
    tenantId: string,
  ): Promise<SecretMetadata[]>;

  /**
   * Is this secret deployed anywhere at all? Returns true if at least
   * one deploy target exists (regardless of sync status) and the secret
   * is `active`.
   */
  isDeployed(secretId: string): Promise<boolean>;

  /**
   * Is this secret deployed at this specific target? Checks the
   * tamma_vault_deploy_targets row for `sync_status='synced'`.
   * Does not compare values — use `verifySecret` for that.
   */
  isDeployedAt(secretId: string, target: DeployTarget): Promise<{
    present: boolean;
    lastSyncAt?: string;
    syncStatus?: 'pending' | 'synced' | 'failed' | 'out_of_sync';
  }>;

  /**
   * Add an additional mirror target for an already-created secret.
   * Reads the value from this store and writes it to the target
   * without the calling code ever observing the plaintext. Used for
   * fan-out: "I created this for repo A, also mirror it to repo B".
   *
   * For the common case of a secret with exactly one target,
   * `createSecret` writes to that target directly in `platform_only` /
   * `vault_copy` modes and this method is not needed.
   *
   * Emits `SECRET.DEPLOYED.SUCCESS` on success.
   */
  mirrorSecretTo(secretId: string, target: DeployTarget): Promise<{
    syncedAt: string;
  }>;

  /**
   * Revoke a secret. Removes the active status but retains metadata +
   * commitment for audit. Cascades to all known deployed targets via the
   * audit log (backends SHOULD implement cascade; if they cannot, the
   * revocation is logged but the operator is responsible for cleanup).
   *
   * Emits `SECRET.REVOKED.SUCCESS` on success.
   */
  revokeSecret(secretId: string, reason: string): Promise<void>;

  /**
   * List secrets in a given scope with cursor-based pagination.
   * Returns metadata + commitment hash. NEVER returns the value or
   * encrypted blob. Used for audit and debugging.
   *
   * Default `limit` is 100; max is 1000. `cursor` is an opaque token
   * returned in the previous page's result — pass it unchanged to
   * fetch the next page. Omit for the first page. `nextCursor` is
   * null when there are no more pages.
   *
   * Emits `SECRET.LISTED`.
   */
  listSecrets(
    scope: SecretScope,
    options?: { limit?: number; cursor?: string },
  ): Promise<{
    secrets: SecretMetadata[];
    nextCursor: string | null;
  }>;

  /**
   * Active probe of a secret by actually exercising it. Probe runs
   * server-side inside the secret broker — the plaintext is never
   * returned to the caller. Returns a success/failure signal with a
   * redacted error message.
   *
   * Implementation of probe types lives in Story 1.5-27; this story
   * defines only the interface. An interface-conforming stub that
   * returns `{ success: false, errorCategory: 'not_supported' }` for
   * every probe type is acceptable for 1.5-16's tests.
   *
   * Rate-limited per secret to prevent brute-force via probe.
   *
   * Emits `SECRET.PROBED.SUCCESS` or `SECRET.PROBED.FAILED`.
   */
  probeSecret(
    secretId: string,
    probeType: ProbeType,
    probeConfig?: Record<string, unknown>,
  ): Promise<ProbeResult>;
}
```

**Technical Specifications — LLM Tool Wrapper Contract:**

Every LLM-facing tool that triggers a secret-management workflow follows
this shape. The tool is a thin wrapper around a workflow invocation; it
does not execute the operation itself.

The system-prompt directive for `system.secret-management` role, authored
in the prompt store and injected into every agent with tool access, reads
(verbatim, subject to ADR approval):

> **Secret management workflow rules**
>
> When you call any `create_secret`, `rotate_secret`, `verify_secret`,
> `probe_secret`, `deploy_secret_to`, `revoke_secret`, or `list_secrets`
> tool, the response may return `status: 'running'`. Follow these rules
> exactly — deviation is reported to the orchestrator as a policy
> violation.
>
> 1. **Poll until terminal.** Call `check_workflow(workflowId)` with
>    exponential backoff starting at 500ms, capping at 5 seconds.
>    Total wall clock must not exceed 10 minutes per workflow.
>
> 2. **No side-channel to the same goal.** While waiting for a workflow
>    targeting goal G, you must not take any alternative action intended
>    to achieve G. This includes, non-exhaustively: writing directly to
>    a `.env` file, running `openssl rand`/`ssh-keygen`/`pwgen`, issuing
>    SQL statements that modify credentials, calling non-workflow HTTP
>    endpoints to mutate secrets, or starting a second workflow that
>    duplicates the first's effect.
>
> 3. **Parallel work on unrelated goals is allowed.** You may continue
>    working on other tickets, unrelated review comments, documentation,
>    tests, or any goal G' that is not the one the pending workflow is
>    achieving. Do not block on a single workflow if there is other
>    independent work you can make progress on.
>
> 4. **Escalate on delay, do not improvise.** If a workflow has not
>    reached terminal state after 2 minutes with no progress, or hits
>    the 10-minute hard timeout, call
>    `alert_orchestrator({workflowId, reason, lastStatus, elapsedMs})`
>    to notify the orchestrator. Then switch to parallel-safe work until
>    the orchestrator responds. Do NOT kill the workflow, restart it, or
>    attempt to work around it.
>
> 5. **On failure, surface and await.** If the workflow terminates as
>    `'failed'`, report the error verbatim to the user or orchestrator
>    and await instruction. Do not retry with modified inputs unless
>    explicitly authorised.
>
> 6. **Never request plaintext.** The result object contains handles,
>    commitment hashes, fingerprints, and status codes — never the
>    underlying secret value. Do not attempt to request, guess, or
>    reconstruct the value under any circumstances. If you think you
>    need the value to complete a task, the correct response is to
>    redesign the task so that it uses a handle instead.
>
> 7. **Duplicate-workflow attempts will be blocked.** The orchestrator
>    tracks every workflow you launch. If you call a secret-management
>    tool with inputs that hash to an already-running workflow for your
>    role, the call is rejected with a pointer at the pending
>    workflowId. Resume polling the original rather than retrying.

**Technical Specifications — Commitment Hash Protocol:**

Note the module location: crypto lives in `@tamma/secret-broker`, not
`@tamma/platforms`. The types above are public (anyone can import
`ISecretStore`), but the crypto implementation is private to the broker
package — only the broker's own vault-store implementation and its
internal tests import it. This is how Decision 7's process isolation is
enforced at the package level.

```typescript
// packages/secret-broker/src/crypto.ts

import { hkdfSync, createHmac, randomBytes, timingSafeEqual } from 'node:crypto';

export interface TenantKeys {
  encKey: Buffer;         // 32 bytes — AES-256-GCM key
  hmacKey: Buffer;        // 32 bytes — HMAC-SHA256 key for commitments
  fingerprintKey: Buffer; // 32 bytes — HMAC-SHA256 key for fingerprints
}

/**
 * Derive three tenant-scoped keys from the root key using HKDF-SHA256.
 * Stateless: same inputs produce same outputs on every call.
 *
 *   ikm  = rootKey
 *   salt = "tamma-vault-v1"                              (domain version)
 *   info = tenantId + ":" + ("enc" | "hmac" | "fingerprint")
 */
export function deriveTenantKeys(rootKey: Buffer, tenantId: string): TenantKeys {
  const salt = Buffer.from('tamma-vault-v1');
  const derive = (purpose: 'enc' | 'hmac' | 'fingerprint'): Buffer => {
    const info = Buffer.from(`${tenantId}:${purpose}`);
    return Buffer.from(hkdfSync('sha256', rootKey, salt, info, 32));
  };
  return {
    encKey: derive('enc'),
    hmacKey: derive('hmac'),
    fingerprintKey: derive('fingerprint'),
  };
}

/**
 * Compute a commitment hash: full 32-byte HMAC-SHA256 output, hex-encoded.
 * Safe for an LLM to carry in context — not reversible without the hmacKey.
 */
export function computeCommitment(value: Buffer, hmacKey: Buffer): string {
  return createHmac('sha256', hmacKey).update(value).digest('hex');
}

/**
 * Compute a 12-hex-char (48-bit) fingerprint via truncated HMAC-SHA256.
 * Reveals zero characters of the original value.
 */
export function computeFingerprint(value: Buffer, fingerprintKey: Buffer): string {
  return createHmac('sha256', fingerprintKey)
    .update(value)
    .digest()
    .subarray(0, 6)
    .toString('hex');
}

/**
 * Format a raw 12-char fingerprint as `xxxx-xxxx-xxxx` for display.
 */
export function formatFingerprint(fingerprint: string): string {
  return fingerprint.match(/.{4}/g)?.join('-') ?? fingerprint;
}

/**
 * Compare two commitment hashes in constant time.
 */
export function commitmentsEqual(a: string, b: string): boolean {
  const ab = Buffer.from(a, 'hex');
  const bb = Buffer.from(b, 'hex');
  if (ab.length !== bb.length) return false;
  return timingSafeEqual(ab, bb);
}

/**
 * Read TAMMA_VAULT_ROOT_KEY_V<version> or TAMMA_VAULT_ROOT_KEY (v1).
 * Fails fast in production when missing/empty. Synthesises a deterministic
 * dev key otherwise.
 */
export function getRootKey(version = 1, env: NodeJS.ProcessEnv = process.env): Buffer {
  const name = version === 1 ? 'TAMMA_VAULT_ROOT_KEY' : `TAMMA_VAULT_ROOT_KEY_V${version}`;
  const raw = env[name];
  if (raw && raw.length > 0) return Buffer.from(raw, 'base64');
  if (env['NODE_ENV'] === 'production') {
    throw new Error(
      `${name} environment variable is required in production. ` +
      `Refusing to start with a synthesized dev key. Generate one with: ` +
      `\`openssl rand -base64 32\` and set it in the deployment environment.`,
    );
  }
  // Dev-only deterministic key, never usable in production due to the
  // fail-fast check above. Loudly warn every invocation so it's visible.
  console.warn(`[secret-store] DEV MODE: using synthesized ${name}. NEVER deploy to prod.`);
  return Buffer.alloc(32, 0x5a); // "Z" pattern, obviously non-random
}

/**
 * Generate a secret value of the requested type.
 * Callers should zero this out as soon as possible (Node has no true zeroize,
 * but dropping references minimizes lifetime).
 */
export function generateSecretValue(type: SecretType, length?: number): Buffer {
  switch (type) {
    case 'password':
      return generateBase62Password(length ?? 32);
    case 'api_key':
      return randomBytes(length ?? 32);
    case 'jwt_signing_key':
      return randomBytes(32);
    case 'arbitrary':
      if (length === undefined || length < 16) {
        throw new Error('arbitrary secret type requires explicit length ≥ 16');
      }
      return randomBytes(length);
    case 'tls_cert':
    case 'ssh_key':
      throw new Error(`${type} generation not supported in v1 — import externally`);
  }
}

function generateBase62Password(length: number): Buffer {
  const alphabet = 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789';
  const bytes = randomBytes(length);
  const out = Buffer.alloc(length);
  for (let i = 0; i < length; i++) {
    // Rejection-free modulo with a bias ≤ 1/2^53 for 62-char alphabet.
    // For stronger uniformity, switch to rejection sampling in a follow-up.
    out[i] = alphabet.charCodeAt((bytes[i] ?? 0) % alphabet.length);
  }
  return out;
}
```

  - HKDF determinism (same inputs → same outputs).

**Edge cases:**

- Empty tenant id → should derive a specific "no-tenant" key family, used
  for `tenant_root` scope. Test that this path works.
- Zero-length value → helpers should accept (HMAC of empty is valid) but
  `generateSecretValue` should reject.
- Mismatched commitment length → `commitmentsEqual` returns false without
  calling `timingSafeEqual` (which requires equal buffer lengths).
- Multi-version root key: two env vars `TAMMA_VAULT_ROOT_KEY` and
  `TAMMA_VAULT_ROOT_KEY_V2` both set → `getRootKey(1)` and `getRootKey(2)`
  return different buffers.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Incorrect HKDF parameters produce weak keys | High | Follow RFC 5869 exactly; document test vectors; peer-review the crypto module before merging |
| Timing side-channel in commitment comparison | Medium | Use `crypto.timingSafeEqual`; test that length mismatch returns early without leaking |
| `TAMMA_VAULT_ROOT_KEY` accidentally logged | High | Never pass the raw key buffer through any logger; only log version number + derived key fingerprints; add a lint rule excluding the variable name from log output |
| Fingerprint collisions in large tenants | Low | 48-bit space covers ~2.4M secrets at 1% collision; document the scaling limit; upgrade path to 64-bit fingerprints is a schema change with no rotation needed |
| Dev key accidentally used in production | Medium | `getRootKey` throws in production when env var missing; additional CI check should grep compiled output for the dev key pattern |
| Interface bloat — `ISecretStore` grows over time | Medium | Explicit "what's NOT in this story" section below; follow-on stories MUST NOT extend the interface without amending this story + bumping a version constant |

### What's NOT in this story

To keep scope tight, the following are explicitly out:

- **No backend implementations.** `TammaVaultStore`, `GitHubSecretStore`, etc.
  are separate stories (1.5-17 through 1.5-26).
- **No LLM tool implementations.** This story defines tool signatures and
  the wrapper contract; actual tool-surface plumbing (MCP server, Elsa
  activity wrappers, orchestrator bindings) lives in Stories 1.5-18,
  1.5-19, and the MCP story in Epic 12.
- **No HTTP endpoint implementations.** `POST /api/v1/ci/fetch-secrets`
  is Story 1.5-21. This story doesn't stand up any HTTP server; the
  `packages/secret-broker/` scaffold has no service entry point yet.
- **No OIDC validation.** Story 1.5-20 owns the OIDC validator, JWKS
  fetching, and trust registry. This story doesn't import `jose` or any
  JWT library.
- **No probe type implementations.** `probeSecret` interface is defined;
  concrete probes (`http_bearer`, `database_connect`, `jwt_sign_verify`,
  `smtp_auth`, `github_token`) land in Story 1.5-27.
- **No leak detection or rotation cascade.** `SECRET.LEAK_DETECTED`
  event type is declared here so downstream stories have something to
  subscribe to, but the scanner and webhook handlers live in 1.5-28.
  Rotation handlers and the cascade workflow are 1.5-29 / 1.5-30.
- **No active drift detection.** Background monitoring via platform
  audit webhooks is Story 1.5-33, explicitly opt-in. `VerifyResult`
  declares `driftDetected?` so 1.5-33 has somewhere to populate, but
  this story does not fetch any webhook.
- **No KMS integration.** Root key lives in `TAMMA_VAULT_ROOT_KEY` env var
  only. KMS-backed variants (AWS KMS, GCP KMS, Azure Key Vault) are
  deferred to a future story.
- **No Shamir secret sharing for HA root key.** Out of scope.
- **No key-rotation-with-reencryption pass.** The `rootKeyVersion` field
  on `CreatedSecret` enables versioned storage; the actual re-encryption
  admin command is implemented in Story 1.5-17.
- **No TLS cert or SSH key generation.** `generateSecretValue` rejects
  these types. Import via an out-of-band tool only.
- **No revocation cascade to platform mirrors.** `revokeSecret` marks
  revoked in the ledger; platform-side cleanup is the responsibility of
  each mirror story (1.5-23 through 1.5-26).
- **No rate limiting on `verifySecret`.** HMAC-keyed commitments make
  brute force infeasible even without rate limiting. `probeSecret` IS
  rate-limited (AC11 requires it) because probes actually exercise the
  secret end-to-end.
