# Story 1.5-16: Secret Store Interface + Commitment Hash Protocol

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / LLM Safety)
**Status**: ready-for-dev
**Priority**: High

## Context — Why this story exists

Tamma is an LLM-driven autonomous development platform. Its workflows routinely
need to **create, rotate, verify, and deploy secrets** — database passwords, JWT
signing keys, OAuth client secrets, API keys, TLS certs — as part of
provisioning and deployment tasks.

The hard problem is: **the LLM driving the workflow must never see the secret
value**, because anything the LLM sees is a candidate for echoing back to the
user, being persisted into logs, or leaking via a subsequent tool call. Yet the
LLM still needs to:

- Request that a secret be created.
- Refer to a secret across workflow steps.
- Verify that a secret it created earlier is still intact.
- Confirm a secret has been deployed to its target (git provider secret store,
  K8s Secret, VPS `.env` file, etc.).
- Rotate, revoke, or retire a secret.
- Debug failures involving secrets **without** requesting the plaintext.

This story defines the TypeScript interface (`ISecretStore`), the commitment
hash protocol, the per-tenant key derivation chain, the scope model, and the
audit event shape that together form the contract every backend implementation
must satisfy. It is **interface-only** — no backend is implemented in this
story. Implementation stories follow as 1.5-17 (TammaVaultStore), 1.5-18
(GitHub), 1.5-19 (GitLab), etc.

This story supersedes the LLM-facing concerns of Story 1.5-4 (Secret Management
Integration). 1.5-4 remains valid for the "integrate with external enterprise
vault" use case; 1.5-16 is the layer above it that makes secret operations
LLM-safe.

## User Story

As a **Tamma orchestrator workflow author**,
I want **a normalized secret store interface with a commitment-hash protocol**,
so that **LLM-driven workflows can create, verify, and manage secrets without
ever handling the plaintext values themselves, and so that every git platform
Tamma supports can be a pluggable backend.**

### AC2: Commitment hash protocol is specified and implemented

- [ ] A pure helper module exists at
      `packages/platforms/src/secret-store-crypto.ts` containing:
  - `deriveTenantKeys(rootKey: Buffer, tenantId: string): TenantKeys` — HKDF
    expansion producing `{ encKey, hmacKey, fingerprintKey }`.
  - `computeCommitment(value: Buffer, hmacKey: Buffer): string` — hex
    HMAC-SHA256 of the full 32-byte output.
  - `computeFingerprint(value: Buffer, fingerprintKey: Buffer): string` —
    12-hex-char truncated HMAC, no plaintext characters leaked.
  - `generateSecretValue(type: SecretType, length?: number): Buffer` — type-
    aware random generation using `crypto.randomBytes`.
- [ ] HKDF uses RFC 5869 with `salt = "tamma-vault-v1"` and
      `info = tenantId + ":" + <purpose>` where `<purpose>` is one of
      `"enc"`, `"hmac"`, `"fingerprint"`.
- [ ] The three derived keys are proven independent by a unit test that
      confirms flipping one bit in the root key changes all three outputs and
      that the three outputs for the same root key are distinct.
- [ ] A unit test confirms that the same (rootKey, tenantId, value) always
      produces the same commitment, and that different tenantIds produce
      different commitments for the same value.
- [ ] All test vectors for HKDF derivation are documented in
      `secret-store-crypto.test.ts` so future refactors preserve compatibility.

      audit record.

### AC5: Fingerprint format is specified and tested

- [ ] Fingerprint is exactly 12 hex characters (48 bits of HMAC output).
- [ ] Default display format is `xxxx-xxxx-xxxx` (three groups of four,
      separated by `-`), produced by a `formatFingerprint(fingerprint: string)`
      helper. API-returned form is unformatted.
- [ ] A unit test verifies that for a 32-byte random value, the fingerprint
      contains no characters from the original value (contrast with the
      legacy first-4-last-4 pattern).
- [ ] A collision-analysis test confirms that with 100,000 random 32-byte
      values and a single tenant key, fingerprint collisions are below 1%
      (documents the 48-bit collision curve for reviewers).

### AC6: `root_key_version` field is present on all writes

- [ ] Every `CreatedSecret` return value includes `rootKeyVersion: number`.
- [ ] The interface explicitly supports multi-version root keys via a
      `getRootKey(version?: number): Buffer` helper in the crypto module that
      reads `TAMMA_VAULT_ROOT_KEY` (implicit v1) and any
      `TAMMA_VAULT_ROOT_KEY_V<N>` env vars for higher versions.
- [ ] If no `TAMMA_VAULT_ROOT_KEY` is set and `NODE_ENV === 'production'`, the
      helper throws at first call with a clear error (fail-fast, consistent
      with the JWT_SECRET fix in commit `126dfdf`).
- [ ] In non-production, a loud warning is emitted and a deterministic
      development-only key is synthesized (separate from JWT_SECRET — do not
      reuse). Document the dev key explicitly so it's never mistaken for a
      real root.

### AC7: Failing-closed semantics on all edge cases

- [ ] `verifySecret(id, commitment)` on an unknown `id` returns
      `{ matches: false, status: 'not_found', ... }` — never throws and never
      reveals whether the id ever existed.
- [ ] `verifySecret(id, commitment)` on a revoked secret returns
      `{ matches: <correct>, status: 'revoked', revokedAt, revokedReason }`.
      A revoked secret still has its commitment computed; this lets the LLM
      distinguish "you're looking at a revoked secret" from "you're looking at
      a wrong secret".
- [ ] `existsInTarget(id)` on a revoked secret returns `{ present: false }`.
- [ ] A commitment comparison uses `crypto.timingSafeEqual` to avoid a timing
      oracle that could let an attacker distinguish "commitment is close to
      correct" from "commitment is completely wrong".

### AC8: Documentation + ADR entry

- [ ] `.dev/decisions/YYYY-MM-DD-secret-store-commitment-hash-protocol.md`
      documents the design decisions: why HKDF, why HMAC rather than plain

- [ ] `packages/platforms/src/secret-store.ts` has a top-of-file comment

  2. All derivations are stateless (no stored per-tenant keys).
  3. Commitments are computed with `timingSafeEqual`.
  4. Fingerprints reveal zero bits of the value.

## Dev Notes

### Requirements Context Summary

**Epic Context:** Epic 1.5 covers foundation & core infrastructure. Secret
handling was partially addressed in Story 1.5-4 (Secret Management
Integration) which describes generic integration with enterprise vaults
(HashiCorp Vault, AWS Secrets Manager, Azure Key Vault). That story does
not address the LLM-safety question — specifically, how an LLM-driven
workflow can request, verify, and deploy secrets without the plaintext ever
entering LLM context. This story fills that gap by defining the interface and
protocol; follow-on stories (1.5-17 through 1.5-22) implement specific
backends.

**Technical Context:** Tamma already abstracts seven git platforms behind
`IGitPlatform` (GitHub, GitLab, Gitea, Forgejo, Bitbucket, Azure DevOps,
plain Git). `ISecretStore` is a sibling abstraction using the same pattern:
platform-agnostic interface, pluggable backends per platform plus a native
`TammaVaultStore`. The commitment hash protocol is the cryptographic
primitive that enables LLM-safe verification — it lets the LLM hold a
short, non-reversible reference to a secret it once created, then later
prove to the store "the secret at this id is still what I created" without
ever handling the value.

**Integration Points:**

- **Event store (Epic 4)**: Audit events defined here feed into the DCB event
  stream. Schema must match existing DCB patterns exactly.
- **Auth (Story 16-7)**: Service API keys will migrate to being tracked via
  `ISecretStore` commitments — a unified audit trail across all secret types.
- **Platform adapters (Stories 1-5 through 1-11)**: Existing
  `GitHubPlatform`, `GitLabPlatform`, etc. will gain a companion
  `GitHubSecretStore`, `GitLabSecretStore`, etc. in follow-on stories. They
  share the same `@octokit/rest` / GitLab SDK client as their parent
  `IGitPlatform` where possible.
- **MCP tool surface (follow-on story)**: An MCP server will wrap
  `ISecretStore` methods as LLM-facing tools. That's a separate story;
  this one is interface-only and does not expose any tool surface yet.

### Implementation Guidance

**Key Design Decisions:**

1. **TammaVault is the source of truth; git-platform stores are mirrors.**
   When an LLM creates a secret via `TammaVaultStore`, the authoritative
   encrypted copy lives in our Postgres. A `deploySecretTo()` call then
   propagates it to one or more platform-native stores (GitHub Actions
   secrets, GitLab CI/CD variables, etc.) as mirrors. Rotation and revocation
   cascade from the vault out. This inverts the naive "store in GitHub, read
   from GitHub" pattern but matters because:
   - Not all platforms have secret APIs (plain Git has none).
   - Some secrets must never live in a repo (tenant root keys, JWT signing
     keys).
   - A single source-of-truth makes rotation atomic.

2. **Per-tenant HMAC keys are derived, never stored.** HKDF-SHA256 from a
   single `TAMMA_VAULT_ROOT_KEY` (32 random bytes in an env var). On every
   secret operation we re-derive the tenant's three keys — encryption, HMAC,
   fingerprint — from the root key plus `tenantId`. Stateless. No per-tenant
   key table, no migration, no backup surface.

3. **Commitment hash is HMAC, not plain SHA-256.** HMAC with a tenant-specific
   key prevents offline brute-force even if a commitment leaks into a log
   line — an attacker would need both the hash and the HMAC key (which never
   leaves the secret broker process). Plain SHA-256 of a short password is
   rainbow-table attackable.

4. **Commitment comparison uses `crypto.timingSafeEqual`.** A timing oracle
   that lets an attacker distinguish "first byte matches" from "no bytes
   match" is a known class of vulnerability in auth systems. Not load-bearing
   for our threat model (remote attackers don't typically see verify latency
   at microsecond resolution), but free defence in depth.

5. **Fingerprint is a 12-hex-char truncated HMAC, not `first-4 + last-4`.**
   Traditional fingerprints reveal 25% of a 32-char password's characters.
   Truncated HMAC reveals zero. 48 bits of fingerprint space means collisions
   only become likely above ~2.4 million secrets per tenant — well beyond
   any plausible fleet size.

6. **Three derived keys per tenant via HKDF domain separation.** `encKey`,
   `hmacKey`, `fingerprintKey` all derive from the same root via HKDF with
   different `info` strings. Domain separation ensures that compromising one
   derivation context does not compromise the others — a useful property if
   any specific helper ends up exposed via a side channel we didn't foresee.

7. **No `getSecretValue()` on `ISecretStore`.** The interface explicitly
   forbids returning plaintext to its caller. The only way to move a secret
   out of the store is via `deploySecretTo()`, which writes directly to a
   backend runtime (GitHub Actions secrets, K8s Secret, systemd
   `EnvironmentFile`, VPS `.env` via atomic SSH write) without passing the
   value through the calling code. This is a structural, not procedural,
   enforcement of the "LLM never sees plaintext" invariant — the interface
   makes the unsafe operation physically impossible to call.

**Technical Specifications — Interface Definition:**

```typescript
// packages/platforms/src/secret-store.ts

/**
 * ISecretStore — LLM-safe secret management interface.
 *
 * INVARIANTS:
 *   1. No method returns plaintext values to its caller.
 *   2. All tenant keys are derived from TAMMA_VAULT_ROOT_KEY via HKDF.
 *      Per-tenant keys are never stored.
 *   3. Commitment hashes use HMAC-SHA256 with tenant-scoped keys and
 *      timingSafeEqual comparison.
 *   4. Fingerprints reveal zero characters of the underlying value.
 *
 * See .dev/decisions/YYYY-MM-DD-secret-store-commitment-hash-protocol.md
 * for the full rationale.
 */

export type SecretType =
  | 'password'
  | 'api_key'
  | 'jwt_signing_key'
  | 'tls_cert'
  | 'ssh_key'
  | 'arbitrary';

export type SecretStatus = 'active' | 'rotating' | 'revoked' | 'not_found';

export type SecretScope =
  | { kind: 'repo'; platform: string; owner: string; repo: string }
  | { kind: 'org'; platform: string; owner: string }
  | { kind: 'project'; platform: string; projectId: string }
  | { kind: 'environment'; platform: string; owner: string; repo: string; env: string }
  | { kind: 'tenant_root'; tenantId: string };

export interface CreatedSecret {
  /** Opaque handle the caller stores. Never contains plaintext. */
  secretId: string;
  /** HMAC-SHA256 commitment, hex. Safe to carry in LLM context. */
  commitmentHash: string;
  /** 12-hex-char truncated HMAC for human disambiguation. */
  fingerprint: string;
  /** Root key version that produced this commitment. */
  rootKeyVersion: number;
  createdAt: string;
  expiresAt?: string;
}

export interface VerifyResult {
  /** True if the stored value's commitment matches the expected value,
   *  compared via `crypto.timingSafeEqual`. */
  matches: boolean;
  status: SecretStatus;
  createdAt?: string;
  lastRotatedAt?: string;
  revokedAt?: string;
  revokedReason?: string;
}

export interface RotationResult {
  /** Handle remains the same after rotation — only the value changes. */
  secretId: string;
  /** New commitment, reflecting the post-rotation value. */
  newCommitmentHash: string;
  newFingerprint: string;
  gracePeriodEndsAt: string;
  rootKeyVersion: number;
}

export interface SecretMetadata {
  secretId: string;
  scope: SecretScope;
  name: string;
  type: SecretType;
  commitmentHash: string;
  fingerprint: string;
  status: SecretStatus;
  createdAt: string;
  lastRotatedAt?: string;
}

export interface DeployTarget {
  /** Where to deploy: the same SecretScope kinds as addressable targets. */
  scope: SecretScope;
  /** Name the secret should have at the target (may differ from source name). */
  targetName: string;
}

export interface CreateSecretInput {
  scope: SecretScope;
  name: string;
  type: SecretType;
  /** Optional override for default length. Only honoured for `password`,
   *  `api_key`, and `arbitrary` types. */
  length?: number;
  /** Metadata the caller can attach. Never logged alongside values. */
  metadata?: Record<string, string>;
  /** ISO-8601 expiry. Backends SHOULD enforce but are not required to. */
  expiresAt?: string;
}

export interface ISecretStore {
  /**
   * Generate a secret server-side and persist it in this store. The value
   * is produced by `generateSecretValue()` and is never returned to the
   * caller. Returns a handle + commitment + fingerprint.
   *
   * Emits `SECRET.CREATED.SUCCESS` on success.
   */
  createSecret(input: CreateSecretInput): Promise<CreatedSecret>;

  /**
   * Rotate a secret in place. The `secretId` is stable across rotations
   * (callers keep the same handle). The old value enters `rotating` status
   * for a backend-specified grace period; callers holding the old commitment
   * will see `matches: false, status: 'rotating'` from `verifySecret`.
   *
   * Emits `SECRET.ROTATED.SUCCESS` on success.
   */
  rotateSecret(secretId: string): Promise<RotationResult>;

  /**
   * Verify that the currently-stored value, when HMAC'd with the tenant
   * key, matches the `expectedCommitmentHash`. Uses `crypto.timingSafeEqual`
   * for comparison. Never throws on unknown id — returns
   * `{ matches: false, status: 'not_found' }`.
   *
   * Emits `SECRET.VERIFIED.MATCH` or `SECRET.VERIFIED.MISMATCH`.
   */
  verifySecret(secretId: string, expectedCommitmentHash: string): Promise<VerifyResult>;

  /**
   * Presence check at a deployed target. Confirms the secret is still
   * deployed to the specified scope. Does not compare values — use
   * `verifySecret` for that.
   */
  existsInTarget(secretId: string, target?: SecretScope): Promise<{
    present: boolean;
    lastSyncAt?: string;
  }>;

  /**
   * Deploy an existing secret to a target scope. The value is read from
   * this store and written to the target without the calling code ever
   * observing it. Used to propagate from TammaVault to platform mirrors.
   *
   * Emits `SECRET.DEPLOYED.SUCCESS` on success.
   */
  deploySecretTo(secretId: string, target: DeployTarget): Promise<{
    syncedAt: string;
  }>;

  /**
   * Revoke a secret. Removes the active status but retains metadata +
   * commitment for audit. Cascades to all known deployed targets via the
   * audit log (backends SHOULD implement cascade; if they cannot, the
   * revocation is logged but the operator is responsible for cleanup).
   *
   * Emits `SECRET.REVOKED.SUCCESS` on success.
   */
  revokeSecret(secretId: string, reason: string): Promise<void>;

  /**
   * List all secrets in a given scope. Returns metadata + commitment hash.
   * NEVER returns the value or encrypted blob. Used for audit and debugging.
   *
   * Emits `SECRET.LISTED`.
   */
  listSecrets(scope: SecretScope): Promise<SecretMetadata[]>;
}
```

**Technical Specifications — Commitment Hash Protocol:**

```typescript
// packages/platforms/src/secret-store-crypto.ts

import { hkdfSync, createHmac, randomBytes, timingSafeEqual } from 'node:crypto';

export interface TenantKeys {
  encKey: Buffer;         // 32 bytes — AES-256-GCM key
  hmacKey: Buffer;        // 32 bytes — HMAC-SHA256 key for commitments
  fingerprintKey: Buffer; // 32 bytes — HMAC-SHA256 key for fingerprints
}

/**
 * Derive three tenant-scoped keys from the root key using HKDF-SHA256.
 * Stateless: same inputs produce same outputs on every call.
 *
 *   ikm  = rootKey
 *   salt = "tamma-vault-v1"                              (domain version)
 *   info = tenantId + ":" + ("enc" | "hmac" | "fingerprint")
 */
export function deriveTenantKeys(rootKey: Buffer, tenantId: string): TenantKeys {
  const salt = Buffer.from('tamma-vault-v1');
  const derive = (purpose: 'enc' | 'hmac' | 'fingerprint'): Buffer => {
    const info = Buffer.from(`${tenantId}:${purpose}`);
    return Buffer.from(hkdfSync('sha256', rootKey, salt, info, 32));
  };
  return {
    encKey: derive('enc'),
    hmacKey: derive('hmac'),
    fingerprintKey: derive('fingerprint'),
  };
}

/**
 * Compute a commitment hash: full 32-byte HMAC-SHA256 output, hex-encoded.
 * Safe for an LLM to carry in context — not reversible without the hmacKey.
 */
export function computeCommitment(value: Buffer, hmacKey: Buffer): string {
  return createHmac('sha256', hmacKey).update(value).digest('hex');
}

/**
 * Compute a 12-hex-char (48-bit) fingerprint via truncated HMAC-SHA256.
 * Reveals zero characters of the original value.
 */
export function computeFingerprint(value: Buffer, fingerprintKey: Buffer): string {
  return createHmac('sha256', fingerprintKey)
    .update(value)
    .digest()
    .subarray(0, 6)
    .toString('hex');
}

/**
 * Format a raw 12-char fingerprint as `xxxx-xxxx-xxxx` for display.
 */
export function formatFingerprint(fingerprint: string): string {
  return fingerprint.match(/.{4}/g)?.join('-') ?? fingerprint;
}

/**
 * Compare two commitment hashes in constant time.
 */
export function commitmentsEqual(a: string, b: string): boolean {
  const ab = Buffer.from(a, 'hex');
  const bb = Buffer.from(b, 'hex');
  if (ab.length !== bb.length) return false;
  return timingSafeEqual(ab, bb);
}

/**
 * Read TAMMA_VAULT_ROOT_KEY_V<version> or TAMMA_VAULT_ROOT_KEY (v1).
 * Fails fast in production when missing/empty. Synthesises a deterministic
 * dev key otherwise.
 */
export function getRootKey(version = 1, env: NodeJS.ProcessEnv = process.env): Buffer {
  const name = version === 1 ? 'TAMMA_VAULT_ROOT_KEY' : `TAMMA_VAULT_ROOT_KEY_V${version}`;
  const raw = env[name];
  if (raw && raw.length > 0) return Buffer.from(raw, 'base64');
  if (env['NODE_ENV'] === 'production') {
    throw new Error(
      `${name} environment variable is required in production. ` +
      `Refusing to start with a synthesized dev key. Generate one with: ` +
      `\`openssl rand -base64 32\` and set it in the deployment environment.`,
    );
  }
  // Dev-only deterministic key, never usable in production due to the
  // fail-fast check above. Loudly warn every invocation so it's visible.
  console.warn(`[secret-store] DEV MODE: using synthesized ${name}. NEVER deploy to prod.`);
  return Buffer.alloc(32, 0x5a); // "Z" pattern, obviously non-random
}

/**
 * Generate a secret value of the requested type.
 * Callers should zero this out as soon as possible (Node has no true zeroize,
 * but dropping references minimizes lifetime).
 */
export function generateSecretValue(type: SecretType, length?: number): Buffer {
  switch (type) {
    case 'password':
      return generateBase62Password(length ?? 32);
    case 'api_key':
      return randomBytes(length ?? 32);
    case 'jwt_signing_key':
      return randomBytes(32);
    case 'arbitrary':
      if (length === undefined || length < 16) {
        throw new Error('arbitrary secret type requires explicit length ≥ 16');
      }
      return randomBytes(length);
    case 'tls_cert':
    case 'ssh_key':
      throw new Error(`${type} generation not supported in v1 — import externally`);
  }
}

function generateBase62Password(length: number): Buffer {
  const alphabet = 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789';
  const bytes = randomBytes(length);
  const out = Buffer.alloc(length);
  for (let i = 0; i < length; i++) {
    // Rejection-free modulo with a bias ≤ 1/2^53 for 62-char alphabet.
    // For stronger uniformity, switch to rejection sampling in a follow-up.
    out[i] = alphabet.charCodeAt((bytes[i] ?? 0) % alphabet.length);
  }
  return out;
}
```

**Testing Strategy:**

- **Unit tests** for `secret-store-crypto.ts`:
  - HKDF determinism (same inputs → same outputs).
  - Tenant isolation (different tenantId → different commitment).
  - Domain separation (three derived keys pairwise distinct).
  - Fingerprint non-leakage (no char of value appears in fingerprint).
  - Fingerprint collision rate (100k random values → < 1% collision at 48-bit).
  - `timingSafeEqual` usage (wrong commitment comparison takes same time).

**Edge cases:**

- Empty tenant id → should derive a specific "no-tenant" key family, used
  for `tenant_root` scope. Test that this path works.
- Zero-length value → helpers should accept (HMAC of empty is valid) but
  `generateSecretValue` should reject.
- Mismatched commitment length → `commitmentsEqual` returns false without
  calling `timingSafeEqual` (which requires equal buffer lengths).
- Multi-version root key: two env vars `TAMMA_VAULT_ROOT_KEY` and
  `TAMMA_VAULT_ROOT_KEY_V2` both set → `getRootKey(1)` and `getRootKey(2)`
  return different buffers.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Incorrect HKDF parameters produce weak keys | High | Follow RFC 5869 exactly; document test vectors; peer-review the crypto module before merging |
| Timing side-channel in commitment comparison | Medium | Use `crypto.timingSafeEqual`; test that length mismatch returns early without leaking |
| `TAMMA_VAULT_ROOT_KEY` accidentally logged | High | Never pass the raw key buffer through any logger; only log version number + derived key fingerprints; add a lint rule excluding the variable name from log output |
| Fingerprint collisions in large tenants | Low | 48-bit space covers ~2.4M secrets at 1% collision; document the scaling limit; upgrade path to 64-bit fingerprints is a schema change with no rotation needed |
| Dev key accidentally used in production | Medium | `getRootKey` throws in production when env var missing; additional CI check should grep compiled output for the dev key pattern |
| Interface bloat — `ISecretStore` grows over time | Medium | Explicit "what's NOT in this story" section below; follow-on stories MUST NOT extend the interface without amending this story + bumping a version constant |

### What's NOT in this story

To keep scope tight, the following are explicitly out:

- **No backend implementations.** `TammaVaultStore`, `GitHubSecretStore`, etc.
  are separate stories (1.5-17 through 1.5-22).
- **No LLM-facing MCP tools.** The tool surface (`create_secret`,
  `verify_secret`, etc.) is a separate story — this one defines the
  server-side interface, not the tool wrapper.
- **No KMS integration.** Root key lives in `TAMMA_VAULT_ROOT_KEY` env var
  only. KMS-backed variants (AWS KMS, GCP KMS, Azure Key Vault) are explicitly
  deferred to a future story.
- **No Shamir secret sharing for HA root key.** Out of scope.
- **No key-rotation-with-reencryption.** The `rootKeyVersion` column on
  `CreatedSecret` enables versioned storage; the actual re-encryption pass
  is an admin command implemented in Story 1.5-17.
- **No TLS cert or SSH key generation.** `generateSecretValue` rejects these
  types. Import via an out-of-band tool only.
- **No revocation cascade.** `revokeSecret` marks as revoked in the vault;
  propagation to deployed targets is the responsibility of each backend
  implementation in its own story.
- **No rate limiting** on `verifySecret` calls. If an attacker gets a
  commitment and tries to brute-force the underlying value, the HMAC key
  makes this infeasible even without rate limiting. Add rate limiting in a
  follow-up only if monitoring shows suspicious patterns.
