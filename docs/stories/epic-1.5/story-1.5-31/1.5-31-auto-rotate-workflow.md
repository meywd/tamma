# Story 1.5-31: AutoRotateWorkflow — wires leak events to rotation cascade

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / Rotation)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-28 (LeakDetectionWorkflow — scanner + webhook handlers), Story 1.5-29 (IRotationHandler + handlers), Story 1.5-30 (RotationCascadeWorkflow)

## Story

As a **Tamma operator deploying a multi-tenant instance with live secrets in the wild**,
I want **an Elsa workflow that consumes `SECRET.LEAK_DETECTED` events and automatically triggers rotation when leak detection is high-confidence, with a short operator-override window for medium-confidence detections and manual-review escalation for low-confidence detections**,
so that **leaked secrets are neutralised within seconds of detection without waiting for a human to click a button, while false-positive rotations remain recoverable during the override window.**

## Context — Why this story exists

Story 1.5-28 built the leak detection pipeline: a scanner that watches
git commits, CI logs, and webhook feeds, emits `SECRET.LEAK_DETECTED`
events with a confidence score when it matches a fingerprint from the
vault.

Story 1.5-30 built the rotation cascade: given a rotation, propagate the
new value to every configured downstream system with audit events and
rollback on partial failure.

This story is the glue that closes the loop: when the scanner finds a
leak, immediately rotate the secret (high confidence) or give the
operator 30 seconds to cancel (medium confidence) or flag for manual
review (low confidence). Without this story, leak detection stops at
"logged and notified" — the actual rotation still requires a human to
trigger it, which defeats the purpose of automated detection.

The cost asymmetry is central: an unnecessary rotation is cheap (mild
service disruption, fresh value in the vault, operators learn to
recognise false positives). A leaked secret sitting in the wild while
waiting for human action is expensive (attackers can use it, compliance
violations, audit failures). Default bias is toward rotating, not
waiting.

### Architecture summary

`AutoRotateWorkflow` lives in `packages/workflows/src/secrets/auto-rotate-workflow.ts`
(or the C# equivalent) and is registered as an Elsa event-triggered
workflow subscribing to `SECRET.LEAK_DETECTED`. When Elsa receives that
event, it starts a new `AutoRotateWorkflow` instance, passing the
event's payload (secret id, tenant id, confidence score, detection
context).

The workflow branches on confidence:
- **High** (≥ 0.95): immediately invoke `RotateSecretWorkflow` (Story 1.5-19)
  which in turn invokes `RotationCascadeWorkflow` (Story 1.5-30). No
  override window.
- **Medium** (0.7 ≤ confidence < 0.95): start a 30-second operator-override
  timer, emit `SECRET.AUTO_ROTATED.OVERRIDE_WINDOW_OPEN`. If the operator
  cancels via the admin API during the window, abort with
  `SECRET.AUTO_ROTATED.CANCELLED`. Otherwise at expiry, proceed to
  rotation.
- **Low** (< 0.7): do NOT auto-rotate. Create an `operator_alerts` record
  and wait for manual action via the admin API. Emit
  `SECRET.AUTO_ROTATED.MANUAL_REVIEW_REQUIRED`.

When rotation completes, emit `SECRET.AUTO_ROTATED.SUCCESS` with a
back-reference to the leak event, or `SECRET.AUTO_ROTATED.FAILED` with
the cascade's terminal state. In both cases, the full causal chain
(leak → decision → rotation → cascade → per-target outcomes) is visible
in the event store.

## User Story

As a **Tamma security operator**,
I want **leaked secrets automatically rotated at high confidence with a short human-override window at medium confidence and manual escalation at low confidence**,
so that **the time-to-remediate a leak is measured in seconds, not hours, while I retain the ability to catch false positives before they cause unnecessary rotations.**

## Acceptance Criteria

### AC1: Confidence threshold dispatch

- [ ] A `ConfidenceClassifier` module at
      `packages/workflows/src/secrets/confidence-classifier.ts` exports:
  ```typescript
  export type AutoRotateAction =
    | { kind: 'auto_rotate_immediate' }
    | { kind: 'auto_rotate_with_override'; overrideWindowMs: number }
    | { kind: 'manual_review_required'; alertLevel: 'warning' | 'critical' };

  export function classifyConfidence(
    confidence: number,
    config: AutoRotateConfig,
  ): AutoRotateAction;
  ```
- [ ] Default thresholds:
  - `confidence >= 0.95` → `auto_rotate_immediate`
  - `0.7 <= confidence < 0.95` → `auto_rotate_with_override` (30s window)
  - `confidence < 0.7` → `manual_review_required`
- [ ] Thresholds are configurable via
      `.tamma/config.yaml` under `secrets.auto_rotate`:
  ```yaml
  secrets:
    auto_rotate:
      high_confidence_threshold: 0.95
      medium_confidence_threshold: 0.70
      override_window_ms: 30000
      manual_review_alert_level: warning  # 'warning' | 'critical'
  ```
- [ ] `loadAutoRotateConfig` validates thresholds:
  - `0 < medium < high <= 1`
  - `override_window_ms >= 5000` (5-second minimum to prevent
    accidentally-zero windows) and `<= 300000` (5-minute maximum to
    prevent leaks sitting for hours)
- [ ] Unit tests cover: each threshold range, boundary conditions
      (exactly 0.95, exactly 0.70), config validation rejecting invalid
      thresholds, config validation rejecting `medium >= high`,
      override window clamp to min/max.

### AC2: Elsa event subscription for `SECRET.LEAK_DETECTED`

- [ ] `AutoRotateWorkflow` is registered as an Elsa event-triggered
      workflow subscribing to event type `SECRET.LEAK_DETECTED`.
- [ ] The subscription is declarative (via Elsa's event trigger API,
      not a polling loop) so workflows start immediately on event
      emission.
- [ ] Each `SECRET.LEAK_DETECTED` event spawns exactly one workflow
      instance. Duplicate events (scanner re-emits the same detection)
      are deduplicated by a `{secretId, detectionId}` key — the second
      event's workflow short-circuits immediately with
      `SECRET.AUTO_ROTATED.SKIPPED_DUPLICATE`.
- [ ] Workflow input variables are populated from the event payload:
      `secretId`, `tenantId`, `confidence`, `detectionId`, `leakSource`
      (`git_commit` | `ci_log` | `webhook_feed` | `manual_report`),
      `leakContext` (free-form detection metadata).
- [ ] Integration test: emit a synthetic `SECRET.LEAK_DETECTED` event via
      the broker's event emitter, assert an `AutoRotateWorkflow` instance
      starts within 1 second, assert the input variables match the
      event payload.

### AC3: High-confidence path — immediate rotation

- [ ] When `classifyConfidence` returns `auto_rotate_immediate`, the
      workflow:
  1. Emits `SECRET.AUTO_ROTATED.DECIDED` with
     `{decision: 'immediate', confidence, detectionId}`.
  2. Invokes `RotateSecretWorkflow` as a child workflow with
     `{secretId, tenantId, reason: 'leak_auto_rotation', triggeringEventId}`.
  3. Waits for the child workflow to terminate (Elsa awaits the child).
  4. Branches on the child's terminal state:
     - Child success → go to AC6 (emit success)
     - Child failure → go to AC7 (emit failure + escalate)
- [ ] The child workflow invocation is a first-class Elsa activity, not
      an HTTP call. This keeps the parent-child relationship visible to
      Elsa's replay engine and ensures the cascade's progress events
      flow through to the parent's audit trail.
- [ ] Integration test: inject a high-confidence leak event, assert
      `RotateSecretWorkflow` is invoked within 500ms, assert no
      `OVERRIDE_WINDOW_OPEN` event appears (no override window for
      high-confidence).

### AC4: Medium-confidence path — 30-second override window

- [ ] When `classifyConfidence` returns `auto_rotate_with_override`, the
      workflow:
  1. Emits `SECRET.AUTO_ROTATED.DECIDED` with
     `{decision: 'with_override', confidence, detectionId, overrideWindowMs}`.
  2. Emits `SECRET.AUTO_ROTATED.OVERRIDE_WINDOW_OPEN` which includes
     a cancellation token usable by the admin API.
  3. Waits for EITHER a cancel signal via the admin API OR the
     `overrideWindowMs` timer to expire.
  4. If cancelled: emit `SECRET.AUTO_ROTATED.CANCELLED` with
     `{cancelledBy, cancelReason}` and terminate the workflow success
     without rotating. Also emit `SECRET.AUTO_ROTATED.OVERRIDE_WINDOW_CLOSED`.
  5. If window expires: emit `SECRET.AUTO_ROTATED.OVERRIDE_WINDOW_CLOSED`
     and proceed to AC3's rotation flow.
- [ ] The cancel signal is delivered via a new admin endpoint:
      `POST /api/admin/secrets/auto-rotate/:workflowId/cancel` with body
      `{reason: string}`. Owner role required. Tenant-scoped.
- [ ] The cancel endpoint calls Elsa's `SendSignalAsync` to deliver a
      `cancel_auto_rotate` signal to the waiting workflow. The workflow
      races this signal against the timer.
- [ ] If the signal arrives AFTER the window has expired (race), the
      endpoint returns 409 with `{error: 'override_window_already_closed'}`
      and does NOT interrupt the in-flight rotation. Interrupting an
      in-flight rotation is a decision: won't do — Story 1.5-30's
      cascade rollback is the only recovery mechanism once the
      rotation has started.
- [ ] Integration test for cancel-during-window: inject a medium-confidence
      leak, within 10 seconds call the cancel endpoint, assert workflow
      terminates with `CANCELLED` event and no rotation occurred.
- [ ] Integration test for window-expiry: inject a medium-confidence
      leak, wait 35 seconds without cancelling, assert workflow proceeds
      to rotation with `OVERRIDE_WINDOW_CLOSED` preceding the rotation.
- [ ] Race test: inject medium-confidence leak, at ~29.5s call the cancel
      endpoint, assert one of two deterministic outcomes based on which
      event reaches the workflow first. The test asserts consistency
      (workflow either cancelled OR rotated, never both) rather than
      a specific outcome.

### AC5: Low-confidence path — manual review required

- [ ] When `classifyConfidence` returns `manual_review_required`, the
      workflow:
  1. Emits `SECRET.AUTO_ROTATED.DECIDED` with
     `{decision: 'manual_review', confidence, detectionId, alertLevel}`.
  2. Inserts a row into `operator_alerts` table (migration 025 — AC9):
     ```sql
     INSERT INTO operator_alerts
     (tenant_id, kind, severity, secret_id, detection_id,
      message, created_at, status)
     VALUES ($1, 'secret_leak_low_confidence', $2, $3, $4, $5, now(), 'open');
     ```
  3. Notifies the operator via the notification channel configured in
     Story 1.5-30 (or via the shared `alert_orchestrator` activity if
     no dedicated notification channel is yet configured). Message
     includes: secret id, leak source, confidence score, a link to
     the admin UI review page (future UI story).
  4. Emits `SECRET.AUTO_ROTATED.MANUAL_REVIEW_REQUIRED` with the alert
     id for cross-reference.
  5. Terminates workflow success — the alert exists independently of
     the workflow's lifecycle, and the operator can act on it via
     different endpoints.
- [ ] The workflow does NOT wait for the operator's response. The alert
      is a durable record; acting on it triggers a fresh workflow (see
      AC8) rather than resuming the auto-rotate workflow. This keeps
      workflows bounded in duration and avoids infinite-running
      workflows waiting for human action.
- [ ] Integration test: inject a low-confidence leak, assert workflow
      terminates in < 2 seconds, assert `operator_alerts` row exists
      with the correct fields, assert no rotation occurred.

### AC6: Rotation success emission

- [ ] When a rotation triggered by this workflow completes successfully:
  1. Emit `SECRET.AUTO_ROTATED.SUCCESS` with:
     ```json
     {
       "autoRotateWorkflowId": "...",
       "rotationWorkflowId": "...",
       "cascadeWorkflowId": "...",
       "secretId": "...",
       "tenantId": "...",
       "confidence": 0.97,
       "triggeringLeakEventId": "...",
       "triggeringDetectionId": "...",
       "decision": "immediate" | "with_override",
       "cascadeOutcome": { "targetsTotal": 3, "targetsSucceeded": 3 }
     }
     ```
  2. Terminate workflow success.
- [ ] `triggeringLeakEventId` is the event id of the original
      `SECRET.LEAK_DETECTED` event, so operators can trace the full
      causal chain: query the event store for the leak event, then
      follow the `autoRotateWorkflowId` tag to the auto-rotate workflow,
      then follow `rotationWorkflowId` → `cascadeWorkflowId` → per-target
      outcomes.
- [ ] Integration test: high-confidence leak → rotation → cascade success
      → assert the success event contains all the expected IDs and the
      cascade outcome summary.

### AC7: Rotation failure emission and escalation

- [ ] When a rotation triggered by this workflow fails (cascade failure,
      vault write failure, handler timeout exceeded):
  1. Emit `SECRET.AUTO_ROTATED.FAILED` with:
     ```json
     {
       "autoRotateWorkflowId": "...",
       "rotationWorkflowId": "...",
       "cascadeWorkflowId": "...",
       "secretId": "...",
       "tenantId": "...",
       "confidence": 0.97,
       "triggeringLeakEventId": "...",
       "failureReason": "cascade_failed" | "vault_write_failed" | "timeout",
       "cascadeOutcome": { ... per-target details ... }
     }
     ```
  2. Fire `alert_orchestrator` (shared activity from Story 1.5-16) with
     `{reason: 'auto_rotate_failed', workflowId, lastStatus, severity: 'critical'}`
     so the operator is notified loudly.
  3. Insert an `operator_alerts` row with
     `kind: 'auto_rotate_failed'`, `severity: 'critical'`.
  4. Terminate workflow failed.
- [ ] The alert fires regardless of whether the operator has a
      notification channel configured — `alert_orchestrator` is the
      canonical escalation primitive.
- [ ] Integration test: configure a rotation target that always fails,
      inject a high-confidence leak, assert cascade fails, assert
      `SECRET.AUTO_ROTATED.FAILED` is emitted, assert an
      `operator_alerts` row exists, assert `alert_orchestrator` was
      invoked.

### AC8: Missing rotation targets fallback — revoke-only mode

- [ ] If the secret has zero enabled rotation targets when the workflow
      reaches the "invoke rotation" step, the workflow does NOT skip
      — it falls back to **revoke-only** mode:
  1. Emit `SECRET.AUTO_ROTATED.REVOKE_ONLY_FALLBACK` with a loud warning
     about the missing targets.
  2. Invoke `revokeSecret` on the vault store with
     `reason: 'leak_detected_no_rotation_targets_configured'`.
  3. Emit `SECRET.REVOKED.SUCCESS` (from the standard revoke path).
  4. Insert an `operator_alerts` row with `kind: 'revoke_only_fallback'`,
     `severity: 'critical'`, message explaining that the secret was
     revoked but no new value was provisioned, so services depending
     on this secret are now broken until the operator manually creates
     a replacement and configures rotation targets.
  5. Fire `alert_orchestrator` with the alert details.
  6. Terminate workflow — success from a workflow-execution perspective
     (the revoke happened as intended), but the outcome event is
     labelled clearly so downstream consumers can distinguish
     "successfully auto-rotated" from "fell back to revoke-only".
- [ ] Rationale: the alternative — doing nothing when targets are
      missing — would leave a leaked secret live and usable in the
      wild. Revoke-only breaks the dependent services but closes the
      leak. An operator would rather deal with a broken service than a
      live leaked secret. The loud warning ensures operators know to
      configure rotation targets for every secret that matters.
- [ ] Integration test: create a secret with zero rotation targets,
      inject a high-confidence leak, assert the workflow falls back to
      revoke-only, assert the secret's status is `revoked` in the vault,
      assert the operator alert exists.

### AC10: Full causal chain in the event store

- [ ] Every event in this story includes correlation tags that let an
      operator reconstruct the chain:
  - `leakEventId`: the original `SECRET.LEAK_DETECTED` event id
  - `detectionId`: the scanner's detection UUID
  - `autoRotateWorkflowId`: this workflow's instance id
  - `rotationWorkflowId`: the child `RotateSecretWorkflow` instance id (when rotation ran)
  - `cascadeWorkflowId`: the grandchild `RotationCascadeWorkflow` instance id (when cascade ran)
- [ ] A causal-chain test:
  1. Inject a high-confidence leak event.
  2. Wait for the rotation cascade to complete.
  3. Query the event store for all events with `detectionId` matching.
  4. Assert the chain is: `SECRET.LEAK_DETECTED` → `SECRET.AUTO_ROTATED.DECIDED`
     → `SECRET.ROTATION_STARTED` → `SECRET.ROTATION_CASCADE.STARTED` →
     N × `SECRET.ROTATION_CASCADE.TARGET_SUCCESS` →
     `SECRET.ROTATION_CASCADE.SUCCESS` → `SECRET.ROTATED.SUCCESS` →
     `SECRET.AUTO_ROTATED.SUCCESS`.
  5. Assert no plaintext values appear in any event in the chain.

## Dev Notes

### Requirements Context Summary

**Epic Context**: This is the third and final story in the rotation
trilogy (1.5-29 handlers, 1.5-30 cascade, 1.5-31 auto-rotate). Together
they deliver the full "detect → decide → rotate → propagate → audit"
pipeline. Story 1.5-28 (leak detection) is the upstream producer; this
story is the consumer that closes the loop.

**Technical Context**: `AutoRotateWorkflow` is a thin orchestrator —
it makes a decision based on confidence, invokes the existing rotation
workflow, and emits audit events. It does NOT reimplement rotation or
cascade logic; it composes them. The workflow's logic is almost entirely
in the event emissions and the branch selection, which keeps it easy
to test via replay.

**Integration Points**:
- **Story 1.5-28 (LeakDetectionWorkflow)**: produces `SECRET.LEAK_DETECTED`
  events; this workflow subscribes to them.
- **Story 1.5-19 (RotateSecretWorkflow)**: invoked as a child workflow
  on the high- and medium-confidence paths.
- **Story 1.5-30 (RotationCascadeWorkflow)**: invoked transitively via
  `RotateSecretWorkflow`; this workflow's audit events reference the
  cascade's outcome.
- **Story 1.5-17 (TammaVaultStore)**: `revokeSecret` is called on the
  missing-targets fallback path.
- **Story 1.5-16 (alert_orchestrator, LlmWorkflowLaunchRegistry)**:
  escalation on failure uses the shared `alert_orchestrator` activity.
- **Story 16-7 (owner-role RBAC)**: admin cancel + alerts routes gated
  by owner role.

### Key Design Decisions

1. **Auto-rotation is the default for high-confidence detections**.
   The cost asymmetry is stark: an unnecessary rotation disrupts service
   briefly, while a leaked secret in the wild is an active compromise
   vector that may be exploited before a human can react. Default bias
   is toward rotating. The thresholds are tunable so operators with
   especially noisy scanners can raise the bar, but the default is
   "rotate aggressively at high confidence." Note: the 0.95 threshold
   is a **judgement call** — we don't have historical data on
   Story 1.5-28's scanner false-positive rate yet, and the correct
   value may turn out to be 0.90 or 0.98. The ADR explicitly frames
   this as tunable and lists what data should drive the tuning.

2. **The 30-second override window for medium-confidence cases** is
   crucial for operators who are online and watching alerts. It gives
   them a chance to cancel a false-positive rotation without requiring
   them to be ALWAYS online. 30 seconds is short enough that a leaked
   secret isn't exposed for long if the operator is offline, but long
   enough for a human to notice an alert and react. Alternatives
   considered: 10 seconds (too short for human reaction), 5 minutes
   (too long for exposure), no window at all (too aggressive for
   medium confidence). 30 seconds is a judgement call informed by
   typical on-call response SLAs. Configurable to override.

3. **Low-confidence detections do NOT auto-rotate, they notify**.
   Below the medium threshold, the false-positive rate is high enough
   that auto-rotation would be more disruptive than beneficial. The
   workflow creates an `operator_alerts` row and lets a human review
   and act. This is the safety valve that prevents the scanner from
   triggering a rotation storm on a noisy regex match. Operators can
   tune the threshold down if their scanner is more accurate.

4. **Rotation target configuration is REQUIRED for full auto-rotate**.
   If a leaked secret has no rotation targets, the workflow falls back
   to **revoke-only**: it marks the secret as revoked (closing the
   leak) but cannot propagate a new value because there's nothing to
   propagate to. This breaks dependent services but neutralises the
   leak. A loud warning tells the operator to configure targets. The
   alternative — doing nothing when targets are missing — would leave
   the leak live, which violates the story's core invariant.

5. **Every auto-rotation emits the full chain of causal events**: leak
   detection → auto-rotate decision → rotation workflow → cascade →
   per-target results. The correlation tags (`leakEventId`,
   `detectionId`, `autoRotateWorkflowId`, `rotationWorkflowId`,
   `cascadeWorkflowId`) let an operator reconstruct exactly why a
   secret was rotated by querying the event store with a single
   `detectionId` filter. This is critical for post-incident audits
   and for building operator trust in the auto-rotate system.

6. **Duplicate event dedup at workflow level**. The scanner may re-emit
   the same detection (e.g. if a webhook retries). The workflow uses
   `{secretId, detectionId}` as an idempotency key — the second
   workflow short-circuits with `SECRET.AUTO_ROTATED.SKIPPED_DUPLICATE`
   rather than triggering a second rotation. This matches the
   `LlmWorkflowLaunchRegistry` pattern from Story 1.5-16 for workflow
   deduplication, reusing the same primitive.

7. **The cancel path uses Elsa signals, not a separate workflow
   variable**. Elsa's `SendSignalAsync` is the canonical way to deliver
   a cancel to a waiting workflow; a DB-polled flag would be fragile
   and slower. The signal race against the timer is a primitive Elsa
   supports natively — the workflow DSL is `Race(WaitForSignal('cancel_auto_rotate'),
   Timer(overrideWindowMs))`.

8. **Workflow does not wait for manual review response**. Low-confidence
   path creates an alert and terminates the workflow success. The
   alternative — a workflow that waits for the operator — would be
   potentially infinite in duration, which complicates Elsa's
   long-running workflow storage. Instead, acting on the alert
   triggers a NEW workflow (e.g. a manual rotation) that's independent
   of the auto-rotate workflow. This keeps each workflow instance
   bounded and makes the state machine easier to reason about.

### Testing Strategy

- **Unit tests** for `ConfidenceClassifier` and config loader.
- **Workflow replay tests** for every branch of the state machine using
  Elsa's deterministic replay harness.
- **Integration tests** exercising the event subscription via a live
  Elsa engine — asserting that injecting a synthetic leak event
  actually starts the workflow and routes through the correct branch.
- **End-to-end tests** with a real Postgres testcontainer as the
  downstream system, a real broker, and a real Elsa. These are the
  smoke tests that catch cross-process coordination bugs.
- **Causal chain tests** querying the event store after a full run and
  asserting the complete chain of events is present and correctly
  correlated.
- **Taint-tracking tests** scanning the event stream for plaintext.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| False-positive rotation storm from noisy scanner | High | Default threshold 0.95 is intentionally conservative. Operators can monitor `SECRET.AUTO_ROTATED.CANCELLED` events — a high cancel rate indicates the threshold needs tuning up. Story 1.5-39 surfaces this metric on the operator dashboard |
| Operator misses the 30-second override window | Medium | Window is configurable; operator can set it to 60s or 120s via config if their on-call response time is slower. Cancel endpoint is straightforward (single POST) and can be scripted |
| Scanner confidence score is not calibrated | High | Story 1.5-28 owns confidence scoring; this story trusts it. If the scores are miscalibrated, operators can compensate via threshold config. The ADR explicitly calls out that threshold tuning is expected after deployment |
| Revoke-only fallback breaks dependent services | Medium | Documented as expected behaviour; loud operator alert; operator procedures should mandate rotation target configuration for every secret. Story 1.5-39 operator dashboard surfaces "secrets without rotation targets" as a compliance panel |
| Duplicate event causing double rotation | Critical | `{secretId, detectionId}` idempotency key + `LlmWorkflowLaunchRegistry` pattern; integration test for duplicate dedup |
| Cancel signal arriving after rotation started | Medium | Cancel endpoint returns 409 if workflow has already exited the override window; cancel CANNOT interrupt an in-flight rotation. Documented clearly in README. The race test verifies deterministic outcome |
| Workflow replay non-determinism | High | Timer + signal race is deterministic in Elsa's replay engine; all emitted events are captured; workflow variables are populated from the event payload at workflow start and never mutated. Replay tests exercise every branch |
| Low-confidence alert flood overwhelming operator | Medium | `operator_alerts` API supports filtering + batch acknowledge; Story 1.5-39 (operator dashboard) provides the UI for triage. For this story, the risk is bounded because operators can adjust `medium_confidence_threshold` downward if volume is too high |
| Correlation tag drift over time | Low | Correlation tags are defined once in a shared type and used consistently across all emissions; test asserts every emitted event has all expected tags |
| `RotateSecretWorkflow` child returning ambiguous failure reasons | Medium | Parent interprets any terminal failure as "rotation failed" and escalates; the specific reason is captured in the child's own events and referenced via `rotationWorkflowId`. Parent doesn't need to parse child failure shapes |

This story delivers `AutoRotateWorkflow` + operator override window
+ cancel endpoint. Every other concern has a dedicated story number:

**Operator surface + notifications:**

  Story 1.5-39 (this story provides events + admin API, the
  dashboard consumes them)
- **Notifications beyond `alert_orchestrator`** (Slack, email,
  PagerDuty, HTTP webhook) → Story 1.5-37 (`alert_orchestrator` is
  the interface; concrete channels plug in behind it)

**Confidence + health:**
- **Confidence scoring algorithm tuning** → Story 1.5-28 (this story
  only consumes the score)
- **Post-rotation health checks** → Story 1.5-42 (verifying the
  downstream system is reachable with the new password via probes
  from Story 1.5-27)

**Explicit "won't do" decisions:**

- **Multi-stage override windows** ("first 30s allow cancel, next
  60s allow delay"): keeping the state machine simple — one window,
  one outcome — is the whole design win of this story. Multi-stage
  adds replay non-determinism hazards and operator confusion for no
  demonstrated benefit.
- **Per-secret override of thresholds**: tenant-wide config only. A
  per-secret override would let operators game the system by marking
  secrets as "never auto-rotate even at high confidence" — a
  mis-feature. Operators who need that can disable leak detection
  for specific secrets entirely via Story 1.5-28's rule config.
- **Cancel endpoint for low-confidence alerts**: low-confidence
  alerts don't trigger rotation, so there's nothing to cancel.
  Acknowledging / resolving the alert is via the `operator_alerts`
  PATCH route.
- **Automatic re-queuing of failed auto-rotates**: if the cascade
  fails, the auto-rotate terminates failed and a new leak event is
  required to retry. Automatic retry could cause cascading failures
  if the root cause (e.g. a broken downstream) isn't fixed.
  Operator intervention is the correct recovery.
