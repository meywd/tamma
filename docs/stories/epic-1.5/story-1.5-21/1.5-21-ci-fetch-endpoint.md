# Story 1.5-21: CI Fetch HTTP Endpoint

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / CI Integration)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-17 (broker), Story 1.5-20 (OIDC validator)

## Story

As a **CI runtime executing a Tamma-integrated workflow**,
I want **a single HTTP endpoint I can call with my ambient OIDC token
to pull the exact set of secrets my job needs into my environment**,
so that **I never have to carry long-lived credentials in my runner
configuration and every secret fetch is cryptographically bound to the
specific workflow run performing it**.

## Context

Story 1.5-17 built the secret broker as an internal-only service bound
to `127.0.0.1` with a shared `TAMMA_BROKER_API_KEY`. That trust model
is correct for server-to-server calls from `tamma-api` but unsuitable
for CI runtimes, which need a public-facing, workload-identity-authenticated
endpoint to fetch secret values.

Story 1.5-20 added OIDC relying-party support: a trust registry that
maps `(issuer, subject_pattern)` to an allowed scope, and an
`OidcValidator` that turns a JWT into a resolved identity.

This story builds the endpoint that actually materializes secret values
for CI consumers: **`POST /api/v1/ci/fetch-secrets`**. This is the
**one controlled exception** to the "no plaintext out of the broker"
invariant. The response body contains plaintext secret values, because
that is literally the endpoint's purpose. Everything else in the broker
is hardened *so that this endpoint is the only place plaintext crosses
the process boundary*.

Three design consequences flow from that:

1. The endpoint lives on a **separate port** from the `/internal/*`
   surface. Different port, different bind host, different auth model,
   different rate limits. One surface cannot accidentally expose the
   other.
2. The endpoint is its own file, its own handler, and its own test
   suite. No shared helpers with `/internal/*` routes beyond
   standardized DB / crypto primitives.
3. A CI lint rule asserts that the low-level `readValueForRuntime`
   helper — the only function in the broker that decrypts and emits
   plaintext bytes in a response body — is called **only** from
   `packages/secret-broker/src/routes/ci/fetch-secrets.ts`.

This story does NOT cover:

- The GitHub Action that produces OIDC tokens and parses the response
  (Story 1.5-22)
- Platform mirror implementations (Stories 1.5-23 through 1.5-26) —
  fetch operates against whatever the vault store knows; mirrors affect
  write/rotate paths, not fetch
- GitLab-specific or Gitea-specific Actions equivalents

## Acceptance Criteria

### AC1: Endpoint lives on a separate port

- [ ] `packages/secret-broker/src/server-ci.ts` exports
      `startCiServer(options)` and runs a Fastify instance on a
      configurable port (default 3201, env var `TAMMA_BROKER_CI_PORT`).
- [ ] This is a **separate** Fastify app from the `/internal/*` server
      created by `packages/secret-broker/src/server.ts`. They share
      the same `TammaVaultStore` instance via DI but have independent
      route registration, middleware, and rate-limit state.
- [ ] The CI server binds to `0.0.0.0` by default (external-facing).
      The internal server still binds to `127.0.0.1`. No overlap.
- [ ] Both servers are started by the same `bootBroker()` entry point
      in `boot.ts` but in separate Fastify instances.
- [ ] `docker-compose.yml` exposes port `3201` on the `tamma-secret-broker`
      service but NOT port `3200`. Nginx is configured to proxy
      `https://api.tamma.dev/api/v1/ci/*` to port 3201.
- [ ] A health route `GET /api/v1/ci/health` returns
      `{status: 'ok'}` without auth (used by reverse-proxy health checks).

### AC2: Route definition and request/response shape

- [ ] The one route that matters: `POST /api/v1/ci/fetch-secrets`.
- [ ] Request body schema (validated via Zod):
  ```typescript
  const FetchSecretsRequest = z.object({
    scope: SecretScopeSchema,           // kind, platform, owner, repo, ...
    secretIds: z.array(z.string().uuid()).min(1).max(200),
    repo: z.string().min(1).max(256),
    workflow: z.string().min(1).max(256),
    job: z.string().min(1).max(256),
    runId: z.string().min(1).max(128),
    sha: z.string().regex(/^[a-f0-9]{7,64}$/),
  });
  ```
- [ ] Response body shape:
  ```typescript
  interface FetchSecretsResponse {
    secrets: Array<{
      id: string;
      envVarName: string;
      value: string;          // plaintext — this is the controlled exception
      commitment: string;     // for Action-side verification
      fingerprint: string;
      rootKeyVersion: number;
    }>;
    meta: {
      runId: string;
      fetchedAt: string;      // ISO 8601
      count: number;
    };
  }
  ```
- [ ] The response NEVER contains error messages, log strings, or free-form
      text that could have been derived from a secret value. The only
      plaintext bytes in the response are the `value` fields inside
      the `secrets` array.
- [ ] On ANY error, the response is the generic error shape `{error,
      code}` with no `secrets` array present. A test asserts the
      error response body never contains the literal bytes of any
      secret returned earlier in the same test run.

### AC3: Authentication — OIDC preferred, bootstrap token fallback

- [ ] Auth middleware on the route tries in order:
  1. Check `Authorization: Bearer <token>` header.
  2. If token parses as a JWT → invoke `OidcValidator.validate(token,
     {tenantId, expectedAudience: 'https://api.tamma.dev'})`. On
     success → build `request.authPrincipal = {scope: 'oidc', ...}`.
  3. If token does NOT look like a JWT → treat as a bootstrap token:
     look up in `ci_bootstrap_tokens` table, verify not revoked /
     not expired, build `request.authPrincipal = {scope: 'ci-bootstrap',
     tokenId, allowedScope, tenantId}`.
  4. If neither works → 401.
- [ ] `tenantId` is derived from a required `X-Tenant-Id` header on
      this endpoint. Rejecting with 400 if absent. The header value
      must match the resolved trust / bootstrap token record — a
      mismatch is a 403 with code `TENANT_MISMATCH`.
- [ ] OIDC is the **preferred** path. Bootstrap tokens exist only for
      bootstrap situations (first-time onboarding, non-OIDC-capable
      runners) and carry a loud metric `CI_FETCH_BOOTSTRAP_USED` that
      operators can alert on.
- [ ] Bootstrap tokens live in a new table:
  ```sql
  CREATE TABLE IF NOT EXISTS ci_bootstrap_tokens (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id     UUID NOT NULL,
    token_hash    TEXT NOT NULL UNIQUE,
    token_prefix  TEXT NOT NULL,
    allowed_scope JSONB NOT NULL,
    description   TEXT,
    created_by    UUID NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at    TIMESTAMPTZ NOT NULL,
    revoked_at    TIMESTAMPTZ,
    last_used_at  TIMESTAMPTZ
  );
  ```
  Tokens are stored as SHA-256 hashes, not plaintext, matching the
  `api_keys` table pattern from Story 16-7.
- [ ] Bootstrap tokens are minted via a new admin route
      `POST /api/v1/ci/bootstrap-tokens` (on `@tamma/api`, gated by
      `requirePermission('settings:manage')`) — covered in AC8.

### AC4: Scope validation — allowed_scope must cover every secretId

- [ ] After authentication, the handler validates that every requested
      `secretId` falls within the caller's `allowedScope`:
  1. If `allowedScope.secretIds` is an explicit array → every requested
     id must be a member.
  2. If `allowedScope.scopePatterns` is present → every requested
     secret's stored `scope` field must match at least one pattern
     (same wildcard engine as Story 1.5-20).
  3. If neither — fail closed with `SCOPE_NOT_DEFINED` (should be
     impossible due to AC1 on Story 1.5-20).
- [ ] The check is all-or-nothing: if ONE secretId is outside the
      scope, the entire request fails with `SECRET_SCOPE_VIOLATION`
      and no secrets are returned. Partial fulfillment is not
      supported — prevents an attacker from probing the scope
      boundary by asking for secrets they might have access to.
- [ ] The first unauthorized secretId is included in the structured
      audit event (but not the error response body) so operators can
      debug misconfigured allowed_scopes.
- [ ] A test matrix exercises:
  - All secrets authorized → 200 with full batch
  - One secret unauthorized → 403 `SECRET_SCOPE_VIOLATION`, zero
    secrets returned
  - All secrets unauthorized → 403 with same code
  - Unknown secretId (not in DB) → 404 `SECRET_NOT_FOUND`, zero
    secrets returned
  - Secret exists but is `status='revoked'` → treated as not-found
  - Secret belongs to a different tenant → 404 (never leaks
    existence across tenant boundaries)

### AC5: Rate limiting

- [ ] Per-principal rate limit: **60 requests per minute** sliding
      window, keyed by:
  - For OIDC: `(trustId, repo, runId)` — so a single workflow run
    can fetch at startup and retry a few times, but can't hammer
  - For bootstrap: `(tokenId)`
- [ ] On limit exceeded → 429 with `Retry-After` header and code
      `RATE_LIMITED`. Audit event emitted.
- [ ] Per-request limit: **200 secretIds max** in a single call
      (enforced by the Zod `.max(200)` on the array). Validation
      happens before any DB lookups.
- [ ] The rate limit state lives in Postgres in a new
      `ci_fetch_rate_limit` table with an INSERT-and-count-recent
      approach — not Redis. One less dependency. Sweeper removes
      rows older than 2 minutes every minute.
- [ ] A load test inserts 100 requests in rapid succession and asserts
      the first 60 succeed and the next 40 are rate-limited.
- [ ] Rate limit bypass for specific trust IDs is configurable via
      a `rate_limit_override` field on the trust record (default
      null = no override). Useful for high-throughput CI setups.

### AC6: Nonce tracking — one `runId` per workflow

- [ ] After scope validation succeeds, the handler claims
      `(tenantId, repo, workflow, runId)` in a new `ci_run_nonces`
      table before returning secrets. Duplicate claim → 403 with code
      `RUN_ID_ALREADY_USED`.
- [ ] `ci_run_nonces` schema:
  ```sql
  CREATE TABLE IF NOT EXISTS ci_run_nonces (
    tenant_id   UUID NOT NULL,
    repo        TEXT NOT NULL,
    workflow    TEXT NOT NULL,
    run_id      TEXT NOT NULL,
    claimed_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at  TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (tenant_id, repo, workflow, run_id)
  );
  CREATE INDEX IF NOT EXISTS idx_ci_run_nonces_expires
    ON ci_run_nonces (expires_at);
  ```
- [ ] Nonce TTL is **48 hours** — long enough for a workflow to
      retry, short enough that the table doesn't grow unbounded.
      Sweeper deletes expired rows every 10 minutes.
- [ ] The claim is the LAST step before plaintext materialization,
      NOT the first. If a claim succeeds but plaintext retrieval
      fails, the nonce is consumed and the run cannot retry. This
      is the correct trade-off: replay safety > retry ergonomics.
- [ ] Replay prevention is configurable per trust via
      `allowed_scope.enforceRunIdNonce: boolean` (default true).
      Tests at orchestration edge cases (stuck workflows, polling
      behavior) can opt out; production trusts should always have
      it on and the admin UI warns loudly.
- [ ] Test: two back-to-back requests with identical `runId` → first
      200, second 403 `RUN_ID_ALREADY_USED`.

### AC7: Wrap fetch in `CiSecretFetchWorkflow` for audit

- [ ] Per Decision 10 ("everything is a workflow"), the secret fetch
      is internally wrapped in a one-shot Elsa workflow called
      `CiSecretFetchWorkflow`. The handler does:
  1. Build workflow input from the validated request
  2. Start the workflow via `IWorkflowClient.startAndWait()`
  3. Return the workflow's output to the HTTP response
- [ ] The workflow has two steps:
  1. `LoadSecretsActivity` — batch-loads all requested secrets via
     `TammaVaultStore.getSecretMetadata` + internal decrypt
  2. `RecordFetchActivity` — emits `SECRET.CI_FETCHED.SUCCESS`
     event with full metadata
- [ ] On any error in the workflow, it transitions to a failed terminal
      state and emits `SECRET.CI_FETCHED.DENIED` with the error code.
- [ ] The workflow is the only code path that invokes
      `readValueForRuntime` — the low-level plaintext-materialization
      helper. The handler does NOT call this helper directly; it
      only starts the workflow.
- [ ] For latency-sensitive CI (GitHub Actions has a ~60s request
      timeout on third-party services), the workflow runs
      **in-process** in the broker — not via the Elsa HTTP server.
      A dedicated `InProcessWorkflowExecutor` handles `CiSecretFetchWorkflow`
      synchronously. Integration with the full Elsa engine is deferred
      to a future story if latency allows.
- [ ] A test asserts that:
  - Every successful fetch emits exactly one `SECRET.CI_FETCHED.SUCCESS`
    event per request (not per secret — one event with all secret ids)
  - Every denied fetch emits exactly one `SECRET.CI_FETCHED.DENIED`
    event with the reason code
  - Event data contains `caller`, `repo`, `workflow`, `job`, `runId`,
    `sha`, `secretIds`, `trustId` (or `bootstrapTokenId`), `tenantId`
  - Event data NEVER contains secret values, commitments of
    unrequested secrets, or the raw OIDC token

### AC8: Admin endpoints for bootstrap tokens

- [ ] New routes in `packages/api/src/routes/ci-bootstrap-tokens/`
      (operator-facing, `requirePermission('settings:manage')`):
  - `POST   /api/v1/ci/bootstrap-tokens` — mint a new token, returns
    plaintext ONCE in the response, never retrievable again
  - `GET    /api/v1/ci/bootstrap-tokens` — list (no plaintext, only
    metadata + prefix)
  - `DELETE /api/v1/ci/bootstrap-tokens/:id` — revoke (sets
    `revoked_at`)
- [ ] Request body for mint:
  ```typescript
  {
    description: string;
    allowedScope: AllowedScope;  // same shape as OIDC trusts
    expiresInDays: number;       // max 90
  }
  ```
- [ ] Response for mint:
  ```typescript
  {
    id: string;
    token: string;               // the plaintext — shown ONCE
    tokenPrefix: string;
    expiresAt: string;
  }
  ```
- [ ] Plaintext generation uses `crypto.randomBytes(32)` encoded as
      base32 for human-readability, prefixed with `tamma_ci_`.
      Stored as SHA-256 hash.
- [ ] Events: `SECRET.CI_BOOTSTRAP_TOKEN.MINTED`,
      `SECRET.CI_BOOTSTRAP_TOKEN.REVOKED`. No plaintext in events.

### AC9: Error response redaction pipeline

- [ ] The CI server uses the same shared redaction helper introduced
      in the broker security hardening path. On every error response:
  1. Error message passes through the redaction function
  2. Any token, commitment, or fingerprint present in the error
     context is replaced with `<redacted>`
  3. The resulting response body is serialized AFTER redaction
- [ ] A dedicated test injects a known plaintext into a failing code
      path and asserts it never appears in:
  - The HTTP response body
  - The Pino log output
  - The audit event data
- [ ] Error logs are structured (Pino) with fields:
  `method`, `path`, `statusCode`, `errorCode`, `principalType`,
  `trustId?`, `bootstrapTokenId?`, `tenantId?`, `durationMs`. Never
  `secretIds` in the error log beyond the first violating id, never
  response body, never raw token.

### AC10: CI lint rule — only one caller of `readValueForRuntime`

- [ ] `readValueForRuntime` is a new private helper in
      `packages/secret-broker/src/vault-store.ts` that, given a
      `secretId` and `tenantId`, loads the row, decrypts, and returns
      `{value: Buffer, commitment, fingerprint, rootKeyVersion}`.
      The function is explicitly marked `@internal` in its JSDoc.
- [ ] An ESLint custom rule `no-external-read-value-for-runtime` asserts
      that references to `readValueForRuntime` from outside
      `packages/secret-broker/src/routes/ci/` fail lint with a
      descriptive error. The rule checks both direct imports and
      property access patterns (`vaultStore.readValueForRuntime`).
- [ ] The rule is wired into `packages/secret-broker/.eslintrc.json`
      and runs as part of `pnpm lint`.
- [ ] A negative-test fixture at
      `packages/secret-broker/src/test-fixtures/forbidden-read-value.ts.disabled`
      contains a deliberate violation. A dedicated test enables the
      fixture, runs lint, asserts failure, then restores it.
- [ ] Discussion in the README: the goal is not to prevent an
      attacker who has source-modification rights (they can turn off
      the lint rule). The goal is to prevent **accidental** regressions
      where a future PR adds a second caller because "just this once".
      A lint rule flashes red in code review.

### AC11: Integration tests end-to-end

- [ ] `packages/secret-broker/src/routes/ci/__tests__/fetch-secrets.e2e.test.ts`
      runs the full stack: boot the CI server, register an OIDC trust
      via the internal API, craft a JWT with a local keypair + mock
      JWKS, call `POST /api/v1/ci/fetch-secrets`, assert the response
      matches expectations.
- [ ] Test scenarios (minimum):
  - Happy path: valid OIDC, valid scope, valid secrets → 200 with
    all secrets
  - Happy path: valid bootstrap token → 200
  - Invalid JWT signature → 401
  - Unregistered issuer → 403
  - Subject doesn't match trust pattern → 403
  - One secretId outside scope → 403, zero secrets
  - Duplicate runId → 403 `RUN_ID_ALREADY_USED`
  - Rate limit exceeded → 429
  - Unknown secretId → 404
  - Revoked secret → 404
  - Missing tenant header → 400
  - Tenant mismatch between header and trust → 403
  - Plaintext taint test: inject known value, trigger error, grep
    response + logs + events for the plaintext
  - Audit event emitted for every success and failure
- [ ] A load test fires 100 concurrent valid requests and asserts

## Dev Notes

### Requirements Context Summary

**Epic Context**: Story 1.5-21 is where CI actually gets to fetch
secrets. 1.5-17 made the broker capable of storing and verifying.
1.5-20 made it capable of authenticating CI workload identities.
1.5-21 makes it capable of handing plaintext back to a legitimate
caller. This is the hot path that CI users experience — latency,
rate limits, error messages, and audit trail all matter.

**Technical Context**: Fastify on a second port, sharing DB and
vault-store instances with the internal broker server but with
independent auth, middleware, and rate limiting. Nginx upstream
terminates TLS and proxies the public path to the broker container.
Workflow execution is in-process for latency but retains the
"everything is a workflow" audit property.

**Integration Points**:
- **OIDC validator** (Story 1.5-20): called as middleware on every
  request that presents a JWT
- **Vault store** (Story 1.5-17): reads via `readValueForRuntime`
- **Event store**: audit events per request
- **Nginx / reverse proxy**: new upstream for port 3201
- **docker-compose**: new port mapping
- **`@tamma/api`**: admin routes for bootstrap tokens

### Key Design Decisions

1. **Separate port for CI fetch.** The `/internal/*` surface and the
   CI surface have different threat models. Internal binds to
   localhost, uses a single shared secret, trusts the caller. CI
   binds to public, uses workload identity, verifies every caller.
   Mixing them on one port invites misconfiguration — a single
   "bind to 0.0.0.0" env var flip would expose internal routes
   if they shared a Fastify app.

2. **All-or-nothing scope enforcement.** If a request asks for five
   secrets and one is outside the allowed scope, we reject the whole
   request. This prevents scope probing: an attacker who can compose
   an OIDC token can't binary-search over secret IDs to discover
   which are in-scope.

3. **Cross-tenant 404 masquerade.** Secrets belonging to a different
   tenant are returned as 404, not 403. This prevents existence
   oracles across tenant boundaries — an attacker on tenant B
   cannot confirm whether a particular UUID is a real secret on
   tenant A.

4. **Run ID nonce consumed before plaintext retrieval.** If the
   nonce check passed and then plaintext retrieval fails, we would
   rather the run_id be burned than allow a retry that could
   potentially succeed and leak. The claim-before-fetch ordering is
   deliberate.

5. **In-process workflow executor for CI fetches.** The full Elsa
   engine is perfect for long-running workflows but overkill for a
   20ms fetch. The `CiSecretFetchWorkflow` class is the same shape
   as an Elsa workflow (inputs, activities, terminal states, events)
   but runs directly in the handler's async context. If the full
   Elsa engine later reaches the latency targets, we can switch
   backends without changing the workflow definition.

6. **One caller, one file.** `readValueForRuntime` is the only way
   plaintext leaves the broker. It is called from exactly one file
   — `routes/ci/fetch-secrets.ts` — and that invariant is enforced
   by a CI lint rule. The lint rule does not defend against a
   determined insider; it defends against the common failure mode
   where future refactors add a helper "for reuse" and plaintext
   escapes via a path nobody noticed.

7. **Bootstrap tokens as a deliberate second-class auth.** We offer
   them because the cost of requiring OIDC on day one is that Tamma
   can't be adopted by any CI platform that doesn't support OIDC,
   and operators need a way to try things out before writing a
   trust registration. But bootstrap tokens have a max 90-day TTL,
   a loud metric, and operator docs that explicitly recommend
   migrating to OIDC as soon as possible.

8. **Rate limit storage in Postgres, not Redis.** We already have
   Postgres. Adding Redis for this one feature means a new
   dependency, a new backup story, a new monitoring story, and a
   new failure mode. Postgres-based sliding windows are fast enough
   at the scale this endpoint operates (< 10k req/min across all
   tenants). If we hit a scaling wall, we can swap in Redis behind
   the `IRateLimiter` interface.

### Testing Strategy

- **Unit tests** for schema validation, scope-check logic, redaction
  helpers.
- **Integration tests** against real Postgres for nonce claims, rate
  limiting, bootstrap token lookup.
- **End-to-end tests** boot the full CI server, use the OIDC validator
  with a mock JWKS endpoint and local keypair, exercise every error
  path.
- **Taint-tracking tests** inject known plaintexts and scan response
  bodies, log output, and event data.
- **Load tests** assert p95 < 500ms under 100 concurrent requests.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Plaintext leak via error message | Critical | Shared redaction helper; taint-tracking test on every error path |
| Rate limit bypass via multiple trust IDs | High | Rate limit key includes `(trustId, repo, runId)` — one workflow run still hits the same key across bursts |
| Nonce table unbounded growth | Medium | 48h TTL + 10-min sweeper; `expires_at` index |
| In-process workflow executor diverges from real Elsa | Medium | Contract tests on both implementations — same workflow class, same audit events |
| Scope check has off-by-one on pattern match | High | Exhaustive test matrix against the wildcard engine (shared with 1.5-20) |
| Bootstrap token reuse after revoke | High | `revoked_at` checked in auth middleware; integration test covers revoke-then-use |
| Cross-tenant disclosure via 403 vs 404 | High | Cross-tenant 404 masquerade; test asserts identical response for "unknown id" and "wrong tenant id" |
| Attacker spams bootstrap token mint endpoint | Low | `requirePermission('settings:manage')` already gates it; ordinary RBAC applies |
| `readValueForRuntime` added to a second file | High | CI lint rule + code review checklist |
| Workflow audit event omits a field | Medium | Event schema validated against a Zod schema at emit time |
