# Story 1.5-24: GitLab CI/CD Variables Mirror (`GitLabSecretStore`) + CI Template

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / LLM Safety)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-16 (interface), Story 1.5-17 (`IMirrorStore` + broker service), Story 1-6 (GitLab Platform Implementation)

## Story

As a **Tamma operator using GitLab as my primary git platform**,
I want **a real `GitLabSecretStore` that mirrors Tamma-managed secrets
into GitLab CI/CD variables at project and group scope, plus a
reusable `.gitlab-ci.yml` template that fetches runtime secrets from
Tamma's CI fetch endpoint**,
so that **GitLab pipelines can consume Tamma-provisioned secrets
without the provisioning LLM ever handling the plaintext**.

## Context

Story 1.5-17 stood up the broker with a `MockMirrorStore`. Story 1.5-23
replaced the mock with a real GitHub implementation. This story does the
same for GitLab, plus ships the GitLab CI template equivalent of the
`actions/fetch-secrets/` Action from Story 1.5-22 — GitLab pipelines
cannot directly consume "secrets" in the GitHub sense; they consume
**CI/CD variables**, which are set via a REST API and then available
as environment variables in pipeline jobs.

Unlike GitHub, GitLab does **not** require client-side encryption of
variable values. Values are POSTed in plaintext over TLS and GitLab
encrypts them at rest. This is fine for Tamma's threat model —
TLS 1.3 protects transit, GitLab's at-rest encryption protects storage.
The broker still never sees a decrypted value come back through the API
(GitLab's endpoint does not return variable values once set, though it
does return masked placeholders in the UI).

The implementation reuses the existing `@gitbeaker/rest` (or whichever
GitLab SDK is chosen by Story 1-6) client from `GitLabPlatform`, the
same way 1.5-23 reuses `Octokit`.

This story explicitly does NOT cover:
- GitHub, Gitea, Forgejo, Bitbucket, Azure DevOps — separate stories.
- GitLab Dedicated or self-managed version detection — assume GitLab
  ≥ 15.0 (CE/EE). Older versions may lack the `environment_scope`
  field and are out of scope.
- OIDC-based runtime fetch from inside GitLab jobs — that's a sibling
  to Story 1.5-21, tracked separately.

## Acceptance Criteria

### AC1: `GitLabSecretStore` class shape + DI wiring

- [ ] `packages/secret-broker/src/mirrors/gitlab-mirror-store.ts` exports
      `GitLabSecretStore implements IMirrorStore`.
- [ ] Constructor signature:
      ```typescript
      constructor(options: {
        platform: GitLabPlatform;  // from @tamma/platforms, already initialised
        logger: pino.Logger;
        eventStore: IEventStore;
      })
      ```
- [ ] Reuses the existing GitLab SDK client from `GitLabPlatform` via a
      public accessor `platform.getAuthenticatedClient()`. The store does
      not construct its own `Gitlab` instance.
- [ ] Registered in the broker's `PlatformMirrorRegistry` under key
      `'gitlab'`.

### AC2: Project-scoped variable CRUD

- [ ] `write(target, value, commitment)` where
      `target.scope.kind === 'project'` POSTs to
      `/projects/:id/variables` with body:
      ```json
      {
        "key": "<secret_name>",
        "value": "<plaintext>",
        "variable_type": "env_var",
        "protected": true,
        "masked": true,
        "environment_scope": "<optional, defaults to '*'>"
      }
      ```
- [ ] If a variable with the same `key` already exists for the given
      `environment_scope`, the store calls PUT
      `/projects/:id/variables/:key?filter[environment_scope]=...`
      instead of POST. A helper `upsertProjectVariable()` handles the
      "POST on 404, PUT on conflict" logic.
- [ ] GitLab's `masked` flag enforces a character-class restriction
      (the value must match `^[a-zA-Z0-9+/=@:_.-]{8,}$` or the API
      returns 400). The store validates the value against this regex
      before the call and, if it fails, falls back to `masked: false`
      with a `logger.warn({ key, reason: 'value_unmaskable' })` line.
      A unit test covers the fallback path.
- [ ] `delete(target)` calls
      `DELETE /projects/:id/variables/:key` — optionally filtered by
      `environment_scope` if the target carries one.
- [ ] `listAt(scope)` where `scope.kind === 'project'` calls
      `GET /projects/:id/variables` and returns the list of keys.
      GitLab's list response *does* include values by default — the
      store MUST discard the `value` field before returning. A unit
      test asserts `value` is never present in the returned array.

### AC3: Group-scoped variable CRUD

- [ ] `write` with `target.scope.kind === 'org'` (mapped to GitLab's
      "group" concept) POSTs to `/groups/:id/variables` with the same
      body shape as project variables.
- [ ] `delete` calls `DELETE /groups/:id/variables/:key`.
- [ ] `listAt` calls `GET /groups/:id/variables` and strips `value`.
- [ ] Unit tests parallel the project-scope tests.

### AC4: Environment-scoped addressing

- [ ] GitLab does not have a separate "environment secrets" endpoint —
      environment scoping is achieved via the `environment_scope`
      field on a regular project variable. `target.scope.kind ===
      'environment'` is mapped to a project-scope API call with
      `environment_scope = target.scope.env`.
- [ ] The store validates that `env` matches GitLab's environment-name
      rules (printable ASCII, no spaces, max 255 chars, wildcards
      allowed) and throws a typed `InvalidEnvironmentScopeError`
      otherwise.
- [ ] A unit test covers both an exact env name (`production`) and a
      wildcard (`review/*`).

### AC5: `tenant_root` scope is refused

- [ ] Same rule as Story 1.5-23 AC6: `target.scope.kind === 'tenant_root'`
      throws `UnsupportedScopeError` before any API call.

### AC6: Default `protected` + `masked`

- [ ] All variables created by this store default to
      `protected: true` and `masked: true`. This matches GitLab's
      recommended best practice for CI secrets — protected means only
      pipelines on protected branches/tags can read the variable, and
      masked means the value is scrubbed from pipeline logs.
- [ ] Operators can opt out per-variable by setting
      `target.metadata.protected = false` or `target.metadata.masked = false`
      on the deploy target. Opting out emits a `logger.warn` with the
      target coordinates so the audit trail captures the decision.
- [ ] A test asserts that a target without metadata produces a
      `protected=true, masked=true` variable.

### AC7: Error mapping

- [ ] `packages/secret-broker/src/mirrors/gitlab-error-mapper.ts`
      defines `mapGitLabMirrorError(error: unknown): MirrorStoreError`:
  | HTTP status | Error class |
  |---|---|
  | 401 | `GitLabAuthError` — "invalid token or 2FA required" |
  | 403 | `GitLabPermissionError` — "insufficient role (need Maintainer on project or Owner on group)" |
  | 404 | `GitLabTargetNotFoundError` — "project, group, or variable not found" |
  | 409 | `GitLabConflictError` — "variable with this key already exists at this scope" (upsert handler catches this) |
  | 400 | `GitLabValidationError` — "invalid key format, unmaskable value, or missing field" |
  | 429 | `GitLabRateLimitError` — retryable with `Retry-After` backoff |
- [ ] Unit tests per mapping. Error messages never include the value
      or commitment hash.

### AC8: Rate limit handling

- [ ] GitLab returns `RateLimit-Remaining` and `RateLimit-Reset`
      headers on every authenticated request, plus an explicit
      `Retry-After` header on a 429 response.
- [ ] The store wraps all calls in a `withGitLabRateLimit` helper (add
      to `packages/platforms/src/gitlab/` if not already present — this
      mirrors the GitHub pattern from Story 1-5).
- [ ] On a 429, the store honours `Retry-After` and retries with
      exponential backoff (1s, 2s, 4s, 8s, 16s; max 5 attempts).
- [ ] Unit test simulates the 429 sequence and asserts correct
      back-off.

### AC9: Sync status tracking + audit events

- [ ] Matches Story 1.5-23 AC9 and AC10 verbatim for GitLab: update
      `tamma_vault_deploy_targets.sync_status` to `synced` or `failed`
      on every write; emit `SECRET.DEPLOYED.*`, `SECRET.REVOKED.*`,
      `SECRET.LISTED` audit events with `platform: 'gitlab'` tag.
- [ ] Audit event tags include project/group coordinates (`project_id`,
      `group_id`, `environment_scope`), the variable `key`, and the
      broker-side `secretId`.

### AC10: GitLab CI template (`fetch-secrets.yml`)

- [ ] `ci-templates/fetch-secrets.yml` in the Tamma monorepo defines a
      reusable GitLab CI template that users include via:
      ```yaml
      include:
        - remote: https://tamma.dev/ci/fetch-secrets.yml
      ```
- [ ] The template defines a `.tamma-fetch-secrets` hidden job and a
      `tamma:fetch-secrets` concrete job that:
  1. Runs on an `alpine:3.19` image (or configurable via
     `TAMMA_FETCH_IMAGE` variable).
  2. Installs `curl` and `jq` via `apk add`.
  3. Calls Tamma's CI fetch endpoint (Story 1.5-21):
     `POST https://$TAMMA_API_HOST/api/v1/ci/fetch-secrets`
     with headers:
     - `Authorization: Bearer $CI_JOB_JWT_V2` (GitLab's OIDC token)
     - `X-Tamma-Tenant-Id: $TAMMA_TENANT_ID`
     with body:
     ```json
     {
       "project_id": "$CI_PROJECT_ID",
       "environment": "$CI_ENVIRONMENT_NAME",
       "secret_names": ["$TAMMA_REQUESTED_SECRETS"]
     }
     ```
  4. Writes the response to `$CI_PROJECT_DIR/.tamma-secrets.env` as
     `KEY=VALUE\n` lines.
  5. Saves the file as a job artifact with `expire_in: 30 minutes` and
     `access: developer` — the file is only readable by users with
     developer access to the pipeline.
- [ ] The concrete job exposes the secrets via a `dotenv` artifact so
      subsequent jobs in the pipeline can consume them:
      ```yaml
      artifacts:
        reports:
          dotenv: .tamma-secrets.env
      ```
- [ ] The template has a top-of-file comment explaining:
  - What the template does and why it exists
  - The required CI/CD variables (`TAMMA_API_HOST`, `TAMMA_TENANT_ID`,
    `TAMMA_REQUESTED_SECRETS`)
  - The minimum GitLab version (15.7+ for `CI_JOB_JWT_V2`)
  - The security model (OIDC, no long-lived tokens in pipeline vars)
- [ ] The template is validated against `gitlab-ci-lint` in CI:
      `packages/secret-broker/src/__tests__/gitlab-ci-template.test.ts`
      shells out to `curl -X POST https://gitlab.com/api/v4/ci/lint`
      (or uses the `@gitbeaker/rest` lint method against a fake
      endpoint in unit mode) and asserts `status: 'valid'`.

## Dev Notes

### Requirements Context Summary

**Epic Context**: Third in the mirror series (after interface + mock in
1.5-17 and real GitHub in 1.5-23). GitLab's API is different enough in
shape from GitHub's that a shared abstraction would be premature — each
mirror is its own class with its own error mapping and rate-limit
handling, held together only by the `IMirrorStore` contract.

**Technical Context**: GitLab variables are plaintext over TLS with
at-rest encryption on GitLab's side. No client-side crypto needed,
which simplifies the implementation compared to GitHub. The complexity
moves to the `protected` / `masked` flags, the `environment_scope`
field, and the upsert semantics (POST-or-PUT based on existence).

**Integration Points**:
- **Story 1-6 (`GitLabPlatform`)**: reuses the SDK client.
- **Story 1.5-17 (broker)**: `PlatformMirrorRegistry` wiring.
- **Story 1.5-18 (Elsa activities)**: `DeploySecretActivity` dispatches
  to this store when `target.scope.platform === 'gitlab'`.
- **Story 1.5-22 (`actions/fetch-secrets/`)**: this story's CI template
  is the GitLab-side twin of that GitHub Action. They serve the same
  purpose for their respective platforms and both call the same Tamma
  CI fetch endpoint (Story 1.5-21).

### Key Design Decisions

1. **No client-side encryption.** GitLab's variables API does not
   require it. Adding encryption would be strictly worse: we'd need
   to manage a client-side key, GitLab still can't decrypt it at read
   time, and the variable would appear as gibberish in the GitLab UI
   (breaking operator debugging). TLS 1.3 + GitLab's at-rest
   encryption is the right trade-off.

2. **`masked: true` is the default with a fallback.** GitLab enforces
   a character-class rule on masked values (a subset of base64). Some
   plaintext values — especially `arbitrary` secrets or passwords
   containing `$`, `%`, `#` — cannot be masked. Rather than failing
   the write, the store detects the case in advance, falls back to
   `masked: false`, and logs a warning. The operator sees the warning
   in the audit stream and can either accept the unmasked variable
   (it's still encrypted at rest) or rotate to a maskable value.

3. **Upsert via POST-or-PUT.** GitLab's API has separate endpoints for
   create (POST) and update (PUT) and returns 400 / 409 if you use the
   wrong one. A helper absorbs this: try POST first, catch the specific
   conflict error, retry with PUT. This keeps the caller side simple
   and matches the "idempotent write" semantics that Tamma's broker
   expects from every mirror.

4. **`environment_scope` instead of a separate env-secrets API.**
   GitLab unifies environment scoping into the project-variables API
   via a single field. Tamma's `scope.kind === 'environment'` maps
   cleanly to a project-scope call with that field populated. No
   separate code path — good for maintainability.

5. **Group-scope maps to `org`.** GitLab calls them "groups"; Tamma's
   `SecretScope` discriminated union calls them `org`. The store maps
   between the two at its boundary. A future refactor could add a
   `scope.kind === 'group'` variant if the ambiguity causes bugs, but
   for now the mapping is explicit and tested.

6. **CI template is a remote include, not a local file.** Including
   from `https://tamma.dev/ci/fetch-secrets.yml` means operators get
   updates without syncing a local file. The trade-off is that a
   network failure during pipeline setup blocks the pipeline —
   acceptable because Tamma-managed secrets are required for the
   job anyway. The template is versioned via URL path
   (`/ci/fetch-secrets-v1.yml` for future breaking changes).

7. **Uses `CI_JOB_JWT_V2`, not long-lived pipeline tokens.** V2 is
   GitLab's OIDC token with per-pipeline claims. It's the right
   primitive for the CI fetch endpoint (Story 1.5-21) to validate
   against GitLab's JWKS. Requires GitLab ≥ 15.7; older versions
   would need the legacy `CI_JOB_JWT` with different validation logic
   and are out of scope.

8. **No separate rate limiter class — reuse platform pattern.** Like
   `github-rate-limiter.ts`, the GitLab version lives under
   `packages/platforms/src/gitlab/` and is shared between the platform
   and the mirror. Adding it to the platforms package (rather than the
   secret-broker) keeps rate-limit logic near its API client.

### Testing Strategy

- **Unit tests** with a mocked `@gitbeaker/rest` client (or `msw`
  intercepting its underlying `fetch`).
- **Property tests** for the masking regex.
- **Integration tests** against real GitLab gated on `GITLAB_TEST_TOKEN`.
- **Template lint test** against GitLab's CI lint endpoint.
- **Taint-tracking tests** for plaintext in logs, errors, DB rows, and
  events.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Value logged inadvertently (no client-side encryption to catch us) | High | Taint-tracking test across all layers; logger redaction of the `value` field by name |
| `masked: true` rejection loops | Medium | Pre-validate the masking regex; fall back to unmasked with explicit warning |
| Upsert race condition between two broker replicas | Medium | GitLab's PUT is idempotent on the key; worst case both replicas write the same value and only one audit event matters; later stories can add a DB-level lock if needed |
| Template lint failures mid-flight | Low | Template is pinned in the monorepo; lint runs in CI pipeline, blocks merge |
| CI fetch endpoint unreachable in a pipeline | High | Template documents the dependency; operators can override the include to a vendored local copy in locked-down environments |
| `CI_JOB_JWT_V2` disabled by operator | Medium | Template documents minimum GitLab version and the required Instance Settings toggle |

### What's NOT in this story

- **No other git platforms.** Stories 1.5-25, 1.5-26 follow.
- **No revocation cascade.** Story 1.5-30.
- **No GitLab runner auto-registration.** Out of scope; the template
  assumes the user has a runner that can pull `alpine:3.19`.
- **No Dependency Proxy integration** for the fetch image. Out of scope.
- **No GitLab audit-log webhooks** for drift detection. Story 1.5-33.
- **No support for GitLab < 15.7.** Documented as a minimum version.
- **No write to CI/CD variables via the `project.secrets` endpoint**
  (which is a separate preview API as of GitLab 16.x) — the classic
  variables API is chosen for stability.
- **No File-type variables.** Only `env_var` type. File-type support
  would require base64 handling and a separate test matrix;
  deferred to a future story.
