# Story 1.5-33: Drift detection via platform audit webhooks

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / Audit)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-17 (TammaVaultStore), Stories 1.5-23 through 1.5-26 (platform mirrors)

## Story

As a **Tamma operator running secrets in `platform_only` or `vault_copy` mode across GitHub / GitLab / Gitea where a human admin can edit a secret directly through the platform's own UI**,
I want **Tamma to detect out-of-band edits within seconds of them happening and mark the affected secret as drifted**,
so that **`verifySecret` reflects reality, audit trails include who edited the platform copy, and the operator can choose to auto-rotate the drifted secret instead of discovering the inconsistency during a production failure.**

## Context — Why this story exists

Stories 1.5-16, 1.5-23, 1.5-24, 1.5-25, and 1.5-26 all called out a gap:

> `platform_only` mode cannot detect when a secret is edited through the
> platform's UI (GitHub Actions secret edited by an admin in the
> settings page). We have no way to know the commitment hash is stale.
> Deferred to follow-up drift-detection story.

That follow-up is this story. Every supported platform publishes audit
events when secrets are created, updated, or deleted — GitHub Enterprise
via audit log streaming, GitHub.com orgs via organization audit log API
(polled) and webhook, GitLab via system hooks / audit events API, Gitea
via webhooks. This story wires those event sources into Tamma and turns
them into drift signals.

### Architecture summary

```
GitHub org audit event ──► POST /api/v1/webhooks/github/audit
GitLab system hook     ──► POST /api/v1/webhooks/gitlab/audit
Gitea hook             ──► POST /api/v1/webhooks/gitea/audit
                                       │
                                       ▼
                       ┌────────────────────────────┐
                       │ PlatformAuditWebhookRouter │
                       │  - verify signature        │
                       │  - parse event             │
                       │  - match to secret row     │
                       └────────────────────────────┘
                                       │
                                       ▼
                       ┌────────────────────────────┐
                       │ DriftDetector              │
                       │  - update drift_status     │
                       │  - emit SECRET.DRIFT_DETECTED │
                       │  - optional auto-rotate    │
                       └────────────────────────────┘
```

The webhook endpoints live in `@tamma/api` because they're HTTP surface.
Drift detection logic lives in `packages/secret-broker/` because that's
where the secret metadata is queried and updated. The API acts as a thin
router: it validates the webhook signature, parses the platform event
into a normalized `PlatformAuditEvent` shape, and RPCs the broker.

Trust registry: operators register which `(platform, org/project)` pairs
Tamma should monitor. A webhook from a platform+org combination that is
not in the registry is logged + rejected. This prevents rogue webhooks
from flooding the drift detector with false signals.

## User Story

As a **Tamma platform engineer who mirrors secrets to GitHub Actions but allows security engineers to edit those secrets directly via GitHub's UI during incident response**,
I want **Tamma to detect those out-of-band edits within seconds, mark the secret `drift_status='drifted'`, and optionally auto-rotate to re-sync**,
so that **my `verifySecret` probes don't lie about the state of production secrets and my audit log shows every edit regardless of which surface made it.**

## Acceptance Criteria

### AC1: Webhook endpoints for each supported platform

- [ ] Four Fastify routes registered in `@tamma/api`:
  - `POST /api/v1/webhooks/github/audit`
  - `POST /api/v1/webhooks/gitlab/audit`
  - `POST /api/v1/webhooks/gitea/audit`
  - `POST /api/v1/webhooks/forgejo/audit`
- [ ] Each route validates the platform-specific webhook signature:
  - GitHub: `X-Hub-Signature-256` HMAC over raw body with the operator-configured webhook secret
  - GitLab: `X-Gitlab-Token` header match against configured token (GitLab's model is token equality, not HMAC)
  - Gitea: `X-Gitea-Signature` HMAC (SHA-256 over raw body)
  - Forgejo: same as Gitea
- [ ] Signature validation failure returns 401 and emits `PLATFORM.WEBHOOK.SIGNATURE_INVALID` audit event with the `platform`, `org`, and source IP. Never logs the raw signature or the payload body.
- [ ] Each route reads the raw body for signature validation BEFORE JSON parsing — Fastify content-type parser is bypassed via `addContentTypeParser('application/json', { parseAs: 'buffer' }, ...)` for these routes specifically.
- [ ] Body size cap: 256 KiB per webhook (platforms rarely exceed 10 KiB; larger payloads are suspicious and rejected).
- [ ] Rate limit: 100 webhooks per minute per source IP via the rate limiter from Story 16-10, falling back to in-process token bucket.

### AC2: Per-platform event parsers

- [ ] `PlatformAuditEventParser` is an interface at `packages/secret-broker/src/drift/parser.ts`:
  ```typescript
  interface PlatformAuditEventParser {
    readonly platform: 'github' | 'gitlab' | 'gitea' | 'forgejo';
    parse(rawBody: Buffer): PlatformAuditEvent[] | 'not_secret_related' | 'unparseable';
  }
  ```
- [ ] `PlatformAuditEvent` shape:
  ```typescript
  interface PlatformAuditEvent {
    platform: 'github' | 'gitlab' | 'gitea' | 'forgejo';
    eventType: 'secret.created' | 'secret.updated' | 'secret.deleted';
    scope: {
      kind: 'org' | 'repo' | 'environment' | 'project';
      ref: string;    // 'acme/backend', 'group/subgroup/project', etc.
    };
    secretName: string;
    actor: {
      type: 'user' | 'app' | 'service_account';
      id: string;
      login?: string;
    };
    occurredAt: string;  // ISO 8601
    rawEventId: string;  // platform's own event id for dedup
  }
  ```
- [ ] Four parser implementations:
  - `GithubAuditParser`: handles GitHub's `secret.created`, `secret.updated`, `secret.removed` audit event types for org, repo, and environment secrets. GitHub wraps audit events inside an array in the webhook body; the parser returns one `PlatformAuditEvent` per array entry. Events for non-secret actions return `'not_secret_related'`.
  - `GitlabAuditParser`: handles GitLab's system hook events for CI/CD variables (`variable_created`, `variable_updated`, `variable_deleted`) and group-level variables. GitLab's webhook shape differs between CI variables and protected variables; the parser handles both.
  - `GiteaAuditParser`: handles Gitea's `secret` hook event type (introduced in Gitea 1.21). For older Gitea versions without native secret events, the parser returns `'not_secret_related'` + logs a warning suggesting Gitea upgrade.
  - `ForgejoAuditParser`: behaviour identical to Gitea parser — Forgejo inherits Gitea's hook format.
- [ ] Unit tests per parser with real captured webhook bodies (anonymized) in `packages/secret-broker/test/fixtures/webhooks/`.
- [ ] Research-at-implementation-time note: the exact event names and JSON shapes MUST be verified via `WebFetch` against each platform's current documentation at implementation time. Event shapes have changed historically; the fixtures in the test suite are ground truth.

### AC3: Trust registry for webhook sources

- [ ] A new config section in `.tamma/config.yaml`:
  ```yaml
  secrets:
    drift_detection:
      enabled: true
      sources:
        - platform: github
          org: acme
          webhook_secret_id: 'vault:platform/github/acme/drift-webhook-secret'
        - platform: gitlab
          project: acme/backend
          webhook_token_id: 'vault:platform/gitlab/acme/drift-webhook-token'
  ```
- [ ] The registry is stored as a Postgres table `drift_detection_sources` (for runtime updates via API) and bootstrapped from the YAML config at broker boot:
  ```sql
  CREATE TABLE drift_detection_sources (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL,
    platform TEXT NOT NULL CHECK (platform IN ('github','gitlab','gitea','forgejo')),
    org_or_project TEXT NOT NULL,
    webhook_secret_id TEXT NOT NULL,
    enabled BOOLEAN DEFAULT true,
    created_at TIMESTAMPTZ DEFAULT now(),
    UNIQUE (tenant_id, platform, org_or_project)
  );
  ```
- [ ] The `webhook_secret_id` / `webhook_token_id` are themselves Tamma-managed secrets — the same recursive-but-bounded pattern Story 1.5-29 establishes for rotation handler admin credentials. A validation step rejects drift sources whose webhook secret is `platform_only` (the broker couldn't read it back).
- [ ] Webhook handler looks up `(platform, org)` in the trust registry before validating the signature. Unknown sources return 404 with an audit event `PLATFORM.WEBHOOK.UNKNOWN_SOURCE`.
- [ ] Changes to the trust registry emit `DRIFT_SOURCE.REGISTERED`, `DRIFT_SOURCE.UPDATED`, `DRIFT_SOURCE.REVOKED`.

### AC4: Secret lookup and drift flagging

- [ ] `DriftDetector.recordEvent(event: PlatformAuditEvent): Promise<DriftDetectionResult>` at `packages/secret-broker/src/drift/detector.ts`:
  1. Maps the platform event's `(scope, secretName)` to a Tamma secret row via the existing platform mirror tables (Stories 1.5-23 through 1.5-26 store `(platform, platform_scope, platform_secret_name) → secret_id` mappings).
  2. If no Tamma secret matches, emits `SECRET.DRIFT_UNMATCHED` with the platform event details and returns `{ matched: false }`. Unmatched events are expected — not every platform secret is a Tamma secret.
  3. If a match is found, updates `drift_status='drifted'`, `drift_detected_at = now()`, `drift_source_event_id = rawEventId`, and `drift_actor = JSON of event.actor`.
  4. Emits `SECRET.DRIFT_DETECTED` with `secret_id`, `tenant_id`, `platform`, `actor`, `event_type`.
  5. Returns `{ matched: true, secretId, autoRotated: false | true }` — the `autoRotated` flag is set if AC6 triggers.
- [ ] Drift events are **deduplicated** by `rawEventId`: two webhook deliveries with the same platform event id update `drift_detected_at` to the most recent but do not emit a second `SECRET.DRIFT_DETECTED` event. A new audit event `SECRET.DRIFT_REDELIVERY` fires for the duplicate for observability.
- [ ] A migration `database/migrations/033_drift_detection.sql` adds:
  ```sql
  ALTER TABLE tamma_vault_secrets
    ADD COLUMN drift_detected_at    TIMESTAMPTZ,
    ADD COLUMN drift_source_event_id TEXT,
    ADD COLUMN drift_actor          JSONB;

  CREATE INDEX idx_vault_secrets_drift
    ON tamma_vault_secrets (tenant_id, drift_status)
    WHERE drift_status = 'drifted';
  ```

### AC5: `verifySecret` integration

- [ ] `TammaVaultStore.verifySecret(secretId, candidate)` grows a `driftDetected` field in its result:
  ```typescript
  interface VerifySecretResult {
    match: boolean;
    secretId: string;
    commitmentMatch: boolean;
    driftDetected: boolean;            // NEW
    driftDetectedAt?: string;          // NEW
    driftActor?: { type: string; id: string };  // NEW
  }
  ```
- [ ] When `drift_status='drifted'`, the verification result includes the drift metadata. The match result itself is unchanged (the commitment is still whatever it was); the drift flag is an orthogonal signal that says "the platform copy may no longer match".
- [ ] Callers that currently treat `match: true` as authoritative SHOULD check `driftDetected` and fail closed on drift. Story 1.5-27 (probes) is updated to propagate drift status through probe results.
- [ ] Unit tests: verify returns `driftDetected: true` after a drift event, returns `driftDetected: false` after a successful re-rotation clears drift.

### AC6: Optional auto-rotate on drift

- [ ] A new per-secret config flag `auto_rotate_on_drift: boolean` stored in the metadata row. Default: `false`.
- [ ] When `DriftDetector.recordEvent` processes an event for a secret with `auto_rotate_on_drift: true`, it:
  1. Fires `SECRET.DRIFT_AUTO_ROTATE_TRIGGERED` event.
  2. Invokes `RotationCascadeWorkflow` (Story 1.5-30) via the shared event bus — NOT directly as a function call, so the rotation runs through the standard durable-workflow path.
  3. Returns `{ matched: true, secretId, autoRotated: true }`.
- [ ] Loop prevention: if the rotation cascade itself propagates to the same platform that fired the drift event, the resulting platform audit webhook will be suppressed by checking `rawEventId` against an in-process LRU cache of `rotation_id → expected_platform_events`. The cache entry is populated by `RotationCascadeWorkflow` just before it calls the platform mirror. A matching webhook is tagged `SECRET.DRIFT_IGNORED_SELF_ROTATION` and does not re-trigger drift.
- [ ] Manual opt-in only: drift-triggered auto-rotation is OFF by default. Enabling it per secret requires a specific API call `PATCH /secrets/:id { auto_rotate_on_drift: true }` with `owner` or `secret_admin` role.
- [ ] Unit + integration tests: drift event on a secret without the flag marks drifted but does NOT rotate; drift event on a secret with the flag marks drifted AND triggers the cascade; self-rotation webhook does NOT re-trigger.

### AC7: Taint tracking + observability

- [ ] Every audit event emitted by this story goes through `redactSensitiveKeys` — the platform event body may include comments, descriptions, or metadata that happens to contain secret-adjacent strings, and we never want those in our own audit trail.
- [ ] Prometheus metrics (via the observability package from Story 16-3 if landed, or raw counters otherwise):
  - `tamma_drift_webhook_received_total{platform, result}`
  - `tamma_drift_events_matched_total{platform}`
  - `tamma_drift_events_unmatched_total{platform}`
  - `tamma_drift_auto_rotations_triggered_total{platform}`
  - `tamma_drift_detection_latency_ms` histogram — time from webhook receipt to drift flag update.
- [ ] A property-based test using `fast-check` generates random webhook payloads containing known plaintext strings and asserts those strings do not appear in logs or audit event payloads (they live in `X-Hub-Signature-256` validation at the edge but never inside the broker's own logs).

### AC8: End-to-end integration test

- [ ] A Vitest integration test spins up:
  1. A real Postgres via `testcontainers`
  2. `@tamma/api` and `secret-broker` instances via `tsx`
  3. A mocked GitHub Actions platform using `msw` that sends a realistic `secret.updated` audit webhook
- [ ] The test:
  1. Creates a Tamma secret in `platform_only` mode mirrored to the mock GitHub
  2. Sends the mocked drift webhook
  3. Asserts `drift_status='drifted'` on the row within 500 ms
  4. Asserts `SECRET.DRIFT_DETECTED` event is in the event store
  5. Repeats with `auto_rotate_on_drift: true` and asserts `RotationCascadeWorkflow` gets enqueued

## Dev Notes

### Requirements Context Summary

This story closes the `platform_only` mode gap that Stories 1.5-16 and the
four platform-mirror stories all acknowledged but deferred. Without drift
detection, `platform_only` is a footgun: operators can't tell whether the
commitment hash reflects reality or an out-of-band edit that happened two
weeks ago during an incident. Drift detection turns the platform into
another event source, so Tamma's audit trail matches the platform's own.

### Key Design Decisions

1. **Webhooks over polling**. GitHub, GitLab, and Gitea all publish audit
   events as webhooks. Polling the audit log API would add latency
   (minutes, not seconds), require additional credentials with audit-read
   scope, and incur rate-limit pressure on every tenant. Webhooks are
   near-real-time, signature-validated at the edge, and scale naturally
   with platform activity.

2. **Webhook handlers live in `@tamma/api`, drift logic in the broker**.
   The API is already the HTTP surface; adding four routes there is
   cheap. The broker owns the vault schema and already has the platform
   mirror tables, so lookups happen where the data lives. The API RPCs
   the broker via the existing internal protocol from Story 1.5-17 — no
   new transport invented.

3. **Trust registry is explicit**. An operator must register every
   `(platform, org)` pair they want monitored. Unknown sources are
   rejected. This is a defense against malicious actors who discover the
   webhook URL: without being in the registry, they can't make noise.
   The registry lives in Postgres (not just YAML) so it can be updated
   at runtime without a broker restart.

4. **Webhook secrets are themselves Tamma-managed secrets**. Same
   recursive-but-bounded pattern as Story 1.5-29 rotation handler admin
   creds. The webhook secret is stored in `vault_only` or `vault_copy`
   mode so the broker can read it back at validation time. Config
   validation rejects `platform_only` webhook secrets because the broker
   couldn't read them.

5. **Auto-rotate on drift is opt-in per secret, OFF by default**. Drift
   might be legitimate (a security engineer rotating during incident
   response). Auto-rotating every drift event would fight the human
   operator. The flag is per-secret so operators can enable it for
   production secrets where drift genuinely means "out-of-sync" and
   leave it off for human-managed secrets.

6. **Self-rotation loop prevention via rotation-id LRU**. When the
   cascade rotates through a platform mirror, that platform emits its
   own audit webhook — which would re-trigger drift — which would
   re-rotate — infinite loop. Breaking the loop requires tagging
   Tamma-initiated platform edits so the incoming webhook can be
   recognized as "I did this, don't react". The LRU cache stores
   `rotation_id → (platform, secret_name)` tuples for 60 seconds, which
   is longer than any realistic webhook delivery delay.

7. **Dedup by `rawEventId`**. Every platform provides its own audit
   event id; webhook deliveries can be retried by the platform, leading
   to duplicate calls. Deduping by id prevents double-counting drift
   events and avoids triggering auto-rotate twice. Dedup cache is an
   in-process LRU with 10k entry capacity — large enough for any
   realistic incident burst.

8. **Raw body access is required for HMAC validation**. Fastify's
   default JSON parser consumes the body before the handler can see it.
   The webhook routes use `addContentTypeParser` to override this for
   webhook paths specifically, reading the raw `Buffer` and making it
   available for HMAC computation before JSON.parse.

### Testing Strategy

- **Unit tests**: parsers against fixture webhook bodies (real webhook
  samples captured and anonymized); signature validators against
  valid/invalid signatures; `DriftDetector.recordEvent` against a mocked
  vault store.
- **Integration tests**: real Postgres via `testcontainers`, mocked
  platform via `msw`, full webhook → drift → auto-rotate chain.
- **Taint-tracking tests**: property-based assertions that webhook body
  content does not appear in Tamma logs.
- **Manual smoke tests** (documented in package README): real webhook
  from a real GitHub test org, because platform webhook shapes change.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Platform changes audit event shape breaking parser | High | Fixtures in test suite are ground truth; WebFetch current docs at impl time; parsers return `unparseable` rather than crashing; smoke test against real platform on release |
| Webhook signature bypass via timing attack | Critical | `crypto.timingSafeEqual` for all HMAC comparisons; signature validation happens before any other processing |
| Unknown source spam flooding drift detector | Medium | Trust registry + rate limit + `PLATFORM.WEBHOOK.UNKNOWN_SOURCE` metric alerting |
| Self-rotation loop from auto-rotate on drift | Critical | Rotation-id LRU prevents recursion; integration test asserts loop breaker fires |
| Missed drift events during broker downtime | Medium | Platforms retry webhooks with backoff (GitHub retries for 8 hours); additional reconciliation job in a future story scans platform audit logs for events older than the last-seen webhook timestamp |
| Drift false positive from description-only edits | Low | Parser filters out edit events where only description/metadata changed, not the value. GitHub, GitLab, and Gitea all emit distinct event types for metadata-only vs value changes |
| Actor field in webhook containing PII | Low | Redaction bindings on audit events; operators are told the drift actor is logged |
| Webhook retry races creating duplicate `SECRET.DRIFT_DETECTED` | Medium | Dedup by `rawEventId`; integration test asserts idempotency under redelivery |
| Trust registry bootstrap from YAML clobbering runtime-added sources | High | Bootstrap is `INSERT ... ON CONFLICT DO NOTHING`, not `UPSERT`. Runtime additions survive reboots |
| Older Gitea versions without native secret events | Medium | Parser returns `not_secret_related` + warning; drift detection is documented as "Gitea 1.21+" in the README |
