# Story 1.5-19: Secret workflows + `LlmWorkflowLaunchRegistry` + `alert_orchestrator`

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / LLM Safety)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-16 (interface, audit events, LLM polling contract),
Story 1.5-17 (broker HTTP service), Story 1.5-18 (Elsa secret activities)

## Context — Why this story exists

Stories 1.5-16 through 1.5-18 built the foundation:

- 1.5-16 defined `ISecretStore`, the commitment hash protocol, and —
  critically — the LLM workflow polling contract in Decision 10
  (workflows are the unit of secret mutation; LLMs start workflows and
  poll; duplicate-goal attempts must be blocked; soft/hard delay
  thresholds require `alert_orchestrator` escalation).
- 1.5-17 delivered the broker HTTP service.
- 1.5-18 delivered the C# Elsa activities that call it.

What's still missing after those three stories:

1. **The actual workflows.** A secret mutation in Tamma must be a
   workflow, not a bare activity call. The workflows are where
   validation, audit, compensation, grace-period handling, and
   cross-activity orchestration live. This story delivers
   `CreateSecretWorkflow`, `RotateSecretWorkflow`, and
   `RevokeSecretWorkflow`.

2. **The `LlmWorkflowLaunchRegistry`.** Story 1.5-16 Decision 10 and AC10
   specify that the orchestrator must track every LLM-initiated
   secret workflow by `(role, goalHash)` and block a second concurrent
   workflow with the same goal. The interface was defined in 1.5-16
   Task 8.2 as a forward reference; this story implements it in
   TypeScript, backed by a new Postgres table, with a middleware that
   wraps every LLM secret-tool call.

3. **The `alert_orchestrator` tool.** Story 1.5-16 AC10 requires an
   `alert_orchestrator(payload)` tool for the LLM to call on delay,
   timeout, or "stuck" workflow states. This story implements it in v1
   form: persist the alert to a new `orchestrator_alerts` table and
   emit a DCB event. Operator notification channels (email, Slack,
   PagerDuty) are explicitly deferred to a later story — v1 is
   "durable storage + audit, human operators query the table."

The combination of these three pieces is what closes the "LLM-safe
secret operations" loop end-to-end. After this story, an LLM can call
`create_secret` from its MCP tool surface, the call routes through the
orchestrator's workflow launcher, the registry checks for duplicates,
an Elsa workflow runs, activities call the broker, the broker mutates
Postgres, audit events flow to the DCB stream, and the LLM polls
`check_workflow` until terminal state. If the workflow stalls, the LLM
calls `alert_orchestrator` and the entry lands in `orchestrator_alerts`
for an operator to review.

### Architecture summary

```
  LLM (via MCP) → create_secret(input)
        │
        ▼
  Orchestrator TS — LLM workflow launcher wrapper
        │  computes goalHash
        │  checks LlmWorkflowLaunchRegistry
        │  if dup running → returns SECRET.WORKFLOW.BLOCKED_DUPLICATE
        │  else → records entry, dispatches to Elsa
        ▼
  Elsa — CreateSecretWorkflow
        │  ValidateScope → ResolveMode → CreateSecretActivity
        │  → EmitAudit → Return CreatedSecret
        ▼
  Secret Activities (1.5-18) → Broker HTTP (1.5-17) → Postgres
```

`alert_orchestrator` sits alongside `check_workflow` as a plain
tool the LLM can invoke at any point. It's not a workflow trigger —
just a durable write + event emission.

## User Story

As an **orchestration developer wiring LLM-driven secret operations**,
I want **durable Elsa workflows for create / rotate / revoke secret,
a Postgres-backed registry that blocks duplicate-goal attempts, and an
`alert_orchestrator` tool the LLM can call on delay**,
so that **the workflow polling contract from Story 1.5-16 is actually
enforced — duplicates are rejected, alerts are durable, and every
secret mutation goes through a workflow with validation, audit, and
compensation**.

## Acceptance Criteria

### AC1: `CreateSecretWorkflow` exists and runs end-to-end

- [ ] A workflow `CreateSecretWorkflow` exists at
      `apps/tamma-elsa/workflows/secrets/CreateSecretWorkflow.cs` (or as
      a `.json` / `.yaml` definition in the same directory if the team
      prefers the designer-authored format — the existing workflow
      conventions in `apps/tamma-elsa/workflows/` determine which).
- [ ] The workflow has these steps in order:
  1. **ValidateScope** — a code step that runs `isScopeAddressableOn(scope, platform)`
     (from Story 1.5-16) and faults the workflow with
     `SECRET.WORKFLOW.INVALID_SCOPE` if the scope is not addressable on
     the requested platform. Also checks the scope/type combination is
     allowed (e.g. `jwt_signing_key` must be `tenant_root`).
  2. **ResolveMode** — a code step that calls the broker's mode
     resolution via an HTTP `POST /internal/secrets/resolve-mode` call
     (a new helper endpoint added to the broker in this story — see
     AC5) OR a local C# port of `resolveMode` that reads the same
     config. The story's default is to add a broker endpoint so
     config stays in one place.
  3. **CreateSecret** — `CreateSecretActivity` from Story 1.5-18.
  4. **EmitAuditStarted / EmitAuditCompleted** — bracketing
     `SECRET.WORKFLOW.STARTED` and `SECRET.WORKFLOW.COMPLETED` audit
     events. These wrap the whole workflow, not the inner
     `SECRET.CREATED.SUCCESS` emitted by the activity.
  5. **Return** — the workflow output is `CreatedSecret` (plus the
     workflow-level audit correlation fields).
- [ ] **Compensation on failure**: if `CreateSecretActivity` faults
      after the broker has already written the secret (e.g. audit
      emission fails), a compensation step calls `RevokeSecretActivity`
      to undo the create. This is the "don't leave orphan secrets"
      guarantee. A test case forces a post-create fault and asserts
      the secret ends up in `revoked` status.
- [ ] **Input schema**: `CreateSecretWorkflowInput` includes
      `scope: SecretScope`, `name: string`, `type: SecretType`,
      `length?: number`, `expiresAt?: string`, `modeOverride?: SecretStoreMode`,
      `tenantId: string`, `initiatedBy: { kind: 'user' | 'llm', id: string, role?: string }`.
- [ ] **Output schema**: `CreatedSecret` from Story 1.5-16 plus
      `workflowId`, `startedAt`, `completedAt`.
- [ ] An integration test runs the workflow against `MockBrokerFixture`
      from Story 1.5-18, asserts terminal state is `Completed`, and
      verifies all four expected audit events fire in order
      (`SECRET.WORKFLOW.STARTED`, `SECRET.CREATED.SUCCESS`,
      `SECRET.WORKFLOW.COMPLETED`, plus the launcher's
      `SECRET.WORKFLOW.STARTED` noted in AC7).

### AC2: `RotateSecretWorkflow` with grace-period handling

- [ ] A workflow `RotateSecretWorkflow` exists at
      `apps/tamma-elsa/workflows/secrets/RotateSecretWorkflow.cs`.
- [ ] Steps in order:
  1. **LoadExisting** — `GetSecretMetadataActivity` to load the
     current state. Fault with `SECRET.WORKFLOW.NOT_FOUND` if the
     secret doesn't exist. Fault with `SECRET.WORKFLOW.NOT_ACTIVE` if
     `status !== 'active'`.
  2. **Rotate** — `RotateSecretActivity`. The broker handles the
     shadow-row creation per Story 1.5-17 AC2.
  3. **MarkOldAsRotating** — no-op at the workflow level; the broker
     already marks the pre-rotation state as `rotating` with a 24-hour
     grace period end. The workflow just reads the
     `gracePeriodEndsAt` from the rotation result and stores it in
     workflow state for later use.
  4. **ScheduleGracePeriodEnd** — an Elsa durable timer that suspends
     the workflow until `gracePeriodEndsAt` (24 hours by default). When
     it fires, the workflow resumes.
  5. **TriggerRotationCascade** — invokes a child workflow
     `RotationCascadeWorkflow` with the `(secretId, newCommitmentHash)`
     pair. The cascade is the real "fan out the new value to
     dependent services" logic and lives in Story 1.5-30 — this story
     provides a **stub** child workflow that logs the invocation and
     completes immediately with `cascadeStatus: 'deferred'`. The
     `RotateSecretWorkflow` does NOT block on the cascade's real
     success in v1. A TODO comment in the stub points at Story 1.5-30.
  6. **EmitAuditCompleted** — `SECRET.ROTATED.SUCCESS` and
     `SECRET.WORKFLOW.COMPLETED`.
- [ ] **Durable timer behaviour**: the test suite uses Elsa's
      time-skip mechanism (or a mock `IClock` in tests) to assert that
      after the timer fires, the workflow resumes and runs the
      cascade step. The real 24-hour wait is never exercised in
      tests.
- [ ] **Compensation on failure**: if `RotateSecretActivity` faults
      after a successful broker rotate (e.g. the audit emit step
      throws), there is no automatic compensation — the broker's
      shadow row already holds the old state for the grace period, so
      an operator can manually resume. The decision is documented in
      the workflow XML doc comment and the ADR in AC10.
- [ ] **Input schema**: `RotateSecretWorkflowInput` includes
      `secretId`, `tenantId`, `initiatedBy`, and an optional
      `reason: string` carried into the audit event data.
- [ ] An integration test asserts the workflow completes correctly
      when the broker is healthy, faults correctly when the secret is
      not found, and (using time-skip) resumes after the grace period
      to invoke the cascade stub.

### AC3: `RevokeSecretWorkflow` with deploy-target cleanup

- [ ] A workflow `RevokeSecretWorkflow` exists at
      `apps/tamma-elsa/workflows/secrets/RevokeSecretWorkflow.cs`.
- [ ] Steps in order:
  1. **LoadExisting** — `GetSecretMetadataActivity`. Skip if not
     found (idempotent revoke — revoking an already-revoked secret
     is a no-op with a WARN log).
  2. **Revoke** — `RevokeSecretActivity`.
  3. **CleanupDeployTargets** — a code step that iterates the deploy
     targets recorded in `tamma_vault_deploy_targets` (via the broker's
     `is-deployed-at` endpoint; a listing endpoint is added if
     necessary — see AC5) and attempts to remove each one. In v1
     this calls `mirrorSecretTo` with a `null` value (unsupported),
     OR — better — emits a `SECRET.CLEANUP.REQUESTED` event that the
     real mirror stories (1.5-23 through 1.5-26) will consume. This
     story implements the event emission path.
  4. **EmitAudit** — `SECRET.REVOKED.SUCCESS` and
     `SECRET.WORKFLOW.COMPLETED`.
- [ ] **Idempotency**: calling the workflow twice for the same
      `secretId` is safe. A test verifies double-invocation results
      in exactly one `SECRET.REVOKED.SUCCESS` event (the second
      invocation is a no-op that emits only `SECRET.WORKFLOW.STARTED`
      and `SECRET.WORKFLOW.COMPLETED`).
- [ ] **Input schema**: `RevokeSecretWorkflowInput` includes
      `secretId`, `reason`, `tenantId`, `initiatedBy`.
- [ ] An integration test asserts the workflow completes for a valid
      active secret, is idempotent for an already-revoked secret, and
      emits a `SECRET.CLEANUP.REQUESTED` event for each prior deploy
      target.

### AC4: `LlmWorkflowLaunchRegistry` is implemented and wired

- [ ] The interface from Story 1.5-16 Task 8.2 is implemented as a
      concrete class at
      `packages/orchestrator/src/llm-workflow-launch-registry.ts`:
      ```typescript
      export class PgLlmWorkflowLaunchRegistry implements LlmWorkflowLaunchRegistry {
        constructor(private pool: pg.Pool, private hmacKey: Buffer) {}

        async record(entry: {
          workflowId: string;
          role: string;
          tool: SecretWorkflowTool;
          goalHash: string;
          startedAt: string;
        }): Promise<void>;

        async findRunningByGoal(
          role: string,
          goalHash: string,
        ): Promise<string | null>;

        async markTerminal(
          workflowId: string,
          status: 'completed' | 'failed' | 'stalled',
          at: string,
        ): Promise<void>;

        async computeGoalHash(
          tool: SecretWorkflowTool,
          input: unknown,
        ): string;
      }
      ```
- [ ] `computeGoalHash` canonicalises `input` via
      `packages/shared/src/canonical-json.ts` (or creates a new helper
      if one doesn't exist: sorted keys, stable string representation,
      no whitespace) and then HMACs with `this.hmacKey` using SHA-256.
      The hmacKey is derived from `TAMMA_VAULT_ROOT_KEY` via HKDF with
      `info = "llm-workflow-launch-registry"` (domain-separated from
      the secret-store keys in Story 1.5-16).
- [ ] `findRunningByGoal` runs a single indexed SELECT against the
      `llm_workflow_launches` table filtered on
      `role = $1 AND goal_hash = $2 AND status = 'running'`. Returns
      the first matching `workflow_id` or `null`. Uses the index
      defined in AC5.
- [ ] `record` inserts a new row with `status='running'`. A UNIQUE
      constraint on `(role, goal_hash, status)` partial-indexed by
      `status = 'running'` prevents a race window where two parallel
      `record` calls both succeed — the second one errors with a
      constraint violation that `findRunningByGoal` would have caught
      a moment earlier. A wrapper function handles both the check and
      the constraint violation as the same "blocked" outcome.
- [ ] `markTerminal` updates `status`, `terminal_at`, and emits a
      `SECRET.WORKFLOW.COMPLETED` / `FAILED` / `STALLED` event to the
      DCB stream.
- [ ] Unit tests cover:
  - Record → findRunning returns the workflowId
  - Two parallel `record` calls for the same `(role, goalHash)` —
    one succeeds, one raises a "blocked" error
  - `markTerminal` transitions status and a subsequent `findRunning`
    returns `null` (cleared)
  - `computeGoalHash` determinism: same input → same hash
  - `computeGoalHash` input ordering: `{a:1, b:2}` and `{b:2, a:1}`
    produce the same hash
  - Different tools or different roles with the same input produce
    different hashes

### AC5: Postgres migration 021 — `llm_workflow_launches`

- [ ] A migration file at
      `database/migrations/021_llm_workflow_launches.sql` creates:
      ```sql
      CREATE TABLE llm_workflow_launches (
        id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
        workflow_id     TEXT NOT NULL UNIQUE,
        role            TEXT NOT NULL,
        tool            TEXT NOT NULL CHECK (tool IN (
          'create_secret','rotate_secret','verify_secret','probe_secret',
          'deploy_secret_to','revoke_secret','list_secrets'
        )),
        goal_hash       TEXT NOT NULL,
        status          TEXT NOT NULL CHECK (status IN (
          'running','completed','failed','stalled'
        )) DEFAULT 'running',
        started_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
        terminal_at     TIMESTAMPTZ,
        tenant_id       UUID NOT NULL,
        metadata        JSONB NOT NULL DEFAULT '{}'::jsonb
      );

      CREATE UNIQUE INDEX idx_llm_workflow_running_goal
        ON llm_workflow_launches (role, goal_hash)
        WHERE status = 'running';

      CREATE INDEX idx_llm_workflow_tenant_started
        ON llm_workflow_launches (tenant_id, started_at DESC);
      ```
- [ ] The unique partial index on `(role, goal_hash) WHERE status = 'running'`
      is the race-prevention mechanism from AC4.
- [ ] RLS is enabled on the table with a policy tying
      `tenant_id` to `current_setting('app.current_tenant_id')::uuid`
      — consistent with Story 17-2's pattern and Story 1.5-17's
      `tamma_vault_secrets` table.
- [ ] The migration is idempotent.
- [ ] A rollback file `021_llm_workflow_launches.down.sql` exists.

### AC6: LLM tool-call middleware enforces the registry

- [ ] A middleware function at
      `packages/orchestrator/src/llm-workflow-launcher.ts` wraps every
      LLM secret-tool invocation:
      ```typescript
      export async function launchLlmWorkflow<T>(
        ctx: LaunchContext,
        tool: SecretWorkflowTool,
        input: unknown,
        dispatcher: (wfInput: unknown) => Promise<{ workflowId: string }>,
      ): Promise<WorkflowStatus<T>>;
      ```
- [ ] The middleware's behaviour:
  1. Computes `goalHash = registry.computeGoalHash(tool, input)`
  2. Calls `registry.findRunningByGoal(ctx.role, goalHash)`
  3. If a running workflowId is returned, emits
     `SECRET.WORKFLOW.BLOCKED_DUPLICATE` and throws a typed
     `DuplicateWorkflowError(workflowId)` that the MCP tool surface
     catches and returns as a tool error to the LLM with the pending
     workflowId in the error message
  4. Otherwise, calls `dispatcher(input)` to actually start the Elsa
     workflow, gets back a `workflowId`
  5. Calls `registry.record({workflowId, role, tool, goalHash, startedAt})`
     — on a UNIQUE constraint violation (a race case), marks the
     just-started workflow as redundant, cancels it via the Elsa API,
     and surfaces the original running workflowId to the LLM as a
     duplicate block (this resolves the race window between step 2
     and step 4)
  6. Emits `SECRET.WORKFLOW.STARTED` to the DCB stream
  7. Returns `{workflowId, status: 'running', startedAt}`
- [ ] The middleware is wrapped around every LLM-facing secret tool in
      the orchestrator's tool map. Specifically: `create_secret`,
      `rotate_secret`, `verify_secret`, `probe_secret`,
      `deploy_secret_to`, `revoke_secret`, `list_secrets`. The tool
      map is updated in `packages/orchestrator/src/tools/registry.ts`
      (or wherever the existing tool registry lives — the Dev Notes
      section documents the exact location after investigating the
      current code).
- [ ] Unit tests cover:
  - Happy path: record succeeds, workflow dispatched, `STARTED` event
    emitted
  - Duplicate: `findRunningByGoal` returns an existing id, middleware
    throws `DuplicateWorkflowError`, `BLOCKED_DUPLICATE` event emitted,
    dispatcher NEVER called
  - Race: `findRunningByGoal` returns null, dispatcher called,
    `record` fails with constraint violation, middleware cancels the
    just-started workflow and surfaces the original
  - Non-secret tools are NOT wrapped (a test verifies that wrapping a
    non-`SecretWorkflowTool` throws at compile time via the type
    system)

### AC7: `alert_orchestrator` tool — v1 durable implementation

- [ ] A migration file `database/migrations/022_orchestrator_alerts.sql`

- [ ] RLS is enabled scoped by `tenant_id`.
- [ ] The migration is idempotent and has a matching
      `022_orchestrator_alerts.down.sql`.
- [ ] An implementation at
      `packages/orchestrator/src/alert-orchestrator.ts` exposes:
      ```typescript
      export async function alertOrchestrator(
        pool: pg.Pool,
        eventStore: IEventStore,
        input: {
          workflowId: string;
          tenantId: string;
          role: string;
          reason: 'delay' | 'timeout' | 'stuck';
          lastStatus: string;
          elapsedMs: number;
          payload?: Record<string, unknown>;
        },
      ): Promise<{ alertId: string; createdAt: string }>;
      ```
- [ ] Behaviour:
  1. Validates inputs (reason is one of the three enum values,
     `elapsedMs > 0`)
  2. Inserts a row into `orchestrator_alerts`
  3. Emits a DCB event of a new type `ORCHESTRATOR.ALERT.RAISED` with
     `{workflowId, role, reason, elapsedMs}` in the tags
  4. Returns the new `alertId` and `createdAt`
- [ ] The tool is exposed in the LLM tool surface as
      `alert_orchestrator` alongside `check_workflow`. Both are
      non-workflow-triggering tools so they are NOT wrapped by the

- [ ] **Operator notification (out of scope for v1)**: emails, Slack,
      PagerDuty, etc. are deferred. A `// TODO(1.5-32):` comment in the

      notification channels reading from the `orchestrator_alerts`
      table.
- [ ] A read API at `GET /api/v1/orchestrator/alerts?acknowledged=false`
      returns pending alerts for operators to query. A separate
      `PATCH /api/v1/orchestrator/alerts/:id` sets `acknowledged_at`,
      `acknowledged_by`, `resolution`. These are existing-pattern
      Fastify routes in `packages/api/src/routes/`.
- [ ] Unit tests cover:
  - Happy path: insert succeeds, event emitted, alertId returned
  - Invalid reason → throws validation error, no row inserted
  - Read API returns pending alerts only when `acknowledged=false`
  - ACK API marks alert acknowledged and subsequent reads exclude it
- [ ] Integration test uses a real Postgres instance and asserts the
      alert row + DCB event are both written transactionally (or
      at least eventually consistent within the same transaction
      scope).

### AC8: Workflow audit event correlation

- [ ] Every workflow in this story emits `SECRET.WORKFLOW.STARTED`
      (via the launcher middleware) and one terminal event
      (`SECRET.WORKFLOW.COMPLETED`, `SECRET.WORKFLOW.FAILED`, or
      `SECRET.WORKFLOW.STALLED`).
- [ ] The launcher middleware emits `STARTED` before dispatching the
      workflow. The `markTerminal` call in the registry emits the
      terminal event after the workflow reaches terminal state — this
      is observed via an Elsa `WorkflowCompleted` / `WorkflowFaulted`
      handler at
      `packages/orchestrator/src/elsa-terminal-handler.ts` that
      subscribes to the Elsa event bus and calls
      `registry.markTerminal(workflowId, status, at)`.
- [ ] The terminal handler is idempotent — if it fires twice for the
      same `workflowId`, the second call is a no-op (status is already
      terminal).
- [ ] A correlation test asserts that for a successful run of
      `CreateSecretWorkflow`, exactly these events appear in the DCB
      stream in order, keyed by the same `workflowId` tag:
  1. `SECRET.WORKFLOW.STARTED`
  2. `SECRET.CREATED.SUCCESS`
  3. `SECRET.WORKFLOW.COMPLETED`
- [ ] A failure-path test asserts:
  1. `SECRET.WORKFLOW.STARTED`
  2. `SECRET.CREATED.FAILED`
  3. `SECRET.WORKFLOW.FAILED`

## Dev Notes

### Requirements Context Summary

**Epic Context**: Secret operations in Tamma are workflow-first — a
hard requirement from Story 1.5-16 Decision 10. The LLM never mutates
secrets directly; it starts workflows and polls. This story closes the
loop by implementing the workflows themselves (in Elsa), the
TypeScript-side launcher middleware that enforces the duplicate-goal
guard, and the v1 `alert_orchestrator` tool.

**Technical Context**: The workflows live in `apps/tamma-elsa/workflows/`
alongside the existing 30 Tamma workflows. They compose activities from
Story 1.5-18. The registry lives in `packages/orchestrator/` (TypeScript)
and is backed by a new Postgres table. The `alert_orchestrator` tool
has its own table + API routes + LLM tool definition.

**Integration Points**:
- **Story 1.5-16** (upstream): provides type definitions, audit event
  constants, and the polling contract that this story implements.
- **Story 1.5-17** (upstream): the broker HTTP service the workflows
  ultimately call via activities.
- **Story 1.5-18** (upstream): the Elsa activities the workflows compose.
- **Story 1.5-30** (downstream): the real `RotationCascadeWorkflow`
  that replaces the stub in AC2.
- **Story 1.5-32** (downstream, to be written): operator notification
  channels (email, Slack, PagerDuty) reading from `orchestrator_alerts`.
- **Epic 4 / DCB event store**: the target for all `SECRET.WORKFLOW.*`
  and `ORCHESTRATOR.ALERT.*` audit events.
- **Story 17-2**: the RLS pattern that both new tables follow.
- **MCP tool surface** (Epic 12): the layer that exposes
  `create_secret`, `check_workflow`, `alert_orchestrator`, etc. as
  LLM-callable tools. This story wires the orchestrator side; the
  MCP server that presents them to the LLM is in Epic 12, and the
  wiring between this story's middleware and that MCP surface is a
  separate story in Epic 12. For v1 testing in 1.5-19, the middleware
  is exercised via unit tests that stub the tool-call pathway.

### Key Design Decisions

1. **Workflows are the unit of secret mutation.** A bare
   `createSecret` call from anywhere — LLM, API route, CLI — goes
   through a workflow. This centralises validation, audit, compensation,
   and timer handling in one place, and gives us replay-ability if the
   worker dies mid-operation. The alternative (activities called
   directly from API routes) would duplicate all this logic and make
   partial failures harder to recover from.

2. **`LlmWorkflowLaunchRegistry` uses `(role, goalHash)` as the dedup
   key.** Not `(tenantId, tool, goalHash)` because Tamma's model of LLM
   identity is "role within a tenant" — e.g. `developer-for-tenant-X`,
   `reviewer-for-tenant-X`. Two different roles legitimately running
   parallel workflows for the same goal is a valid case (e.g. reviewer
   verifying what developer created). Two instances of the same role
   running parallel workflows for the same goal is the case we block.
   The role field captures this.

3. **Race prevention via partial unique index, not application-side
   check-and-insert.** A pure application-side check `SELECT ... FOR
   UPDATE` risks deadlocks and requires transaction coordination.
   Postgres's partial unique index on `(role, goal_hash) WHERE status = 'running'`
   lets us try the insert, let the DB reject duplicates, and treat
   the constraint violation as the authoritative "blocked" signal.
   Simpler, faster, race-free.

4. **The race-window workflow cancellation is a v1 trade-off.** If two
   calls hit `findRunningByGoal` before either has `record`ed, both
   see null, both dispatch Elsa workflows, and one of the `record`
   calls loses to the constraint violation. The losing caller then
   cancels its just-started Elsa workflow. This wastes a tiny amount
   of work (the losing workflow runs a few activities before being
   cancelled). A tighter synchronisation (advisory lock on the
   `(role, goalHash)` pair) would eliminate the waste but adds
   complexity — we're accepting the waste for v1 and documenting the
   trade-off.

5. **`RotationCascadeWorkflow` is a stub in this story.** The real
   cascade fan-out to dependent services is Story 1.5-30's scope.
   Stubbing it lets `RotateSecretWorkflow` be fully wired end-to-end
   without blocking on 1.5-30. The stub logs its invocation, completes
   immediately with `cascadeStatus: 'deferred'`, and leaves a TODO
   pointing at the real story. The `RotateSecretWorkflow` does NOT
   treat the stub's deferred completion as failure — it's
   intentionally a successful no-op in v1.

6. **Compensation on rotate failure is deliberately manual.** If the
   broker successfully rotates a secret and then some downstream step
   (audit emit, timer scheduling) faults, we do NOT auto-revoke the
   rotation. The broker's shadow-row mechanism from Story 1.5-17 AC2
   keeps the old state available for the 24-hour grace period, and an
   operator can manually decide whether to proceed with the new
   commitment or revert. Auto-compensation here would be high-risk
   (rotate-rollback interactions with deploy targets, potential
   cascading inconsistencies with downstream services that may have
   already picked up the new value). Manual compensation is the safer
   v1 default; the ADR documents this explicitly.

7. **`alert_orchestrator` is a durable-storage tool, not a notification
   channel.** v1 writes to Postgres and emits a DCB event. Operators
   query the `orchestrator_alerts` table (or the GET endpoint) to see
   pending alerts. Push channels (email, Slack, PagerDuty) are
   explicitly out of scope because they require credential management,
   retry logic, templating, and per-tenant configuration — a whole
   sub-system of its own. Durable storage + audit is the minimum
   invariant for the polling contract to be meaningful, and that's
   what v1 delivers.

8. **Terminal-state event emission is handled by an Elsa event
   subscriber, not the workflow itself.** Workflows can end in
   `Completed`, `Faulted`, `Cancelled`, or `Stalled` (suspended past
   a soft deadline). Making every workflow responsible for emitting
   its own terminal event would be repetitive and error-prone. Instead,
   a single `elsa-terminal-handler.ts` subscribes to Elsa's workflow
   lifecycle events and calls `registry.markTerminal` + emits the
   event. Idempotent so double-firing is safe. This is the standard
   Elsa pattern for lifecycle observation.

### Technical Specifications — `launchLlmWorkflow` outline

```typescript
// packages/orchestrator/src/llm-workflow-launcher.ts

export interface LaunchContext {
  role: string;
  tenantId: string;
  initiatedBy: { kind: 'user' | 'llm'; id: string };
}

export class DuplicateWorkflowError extends Error {
  constructor(public pendingWorkflowId: string) {
    super(`A workflow with the same goal is already running: ${pendingWorkflowId}`);
    this.name = 'DuplicateWorkflowError';
  }
}

export async function launchLlmWorkflow<T>(
  deps: {
    registry: LlmWorkflowLaunchRegistry;
    eventStore: IEventStore;
    elsaClient: IElsaClient;
  },
  ctx: LaunchContext,
  tool: SecretWorkflowTool,
  input: unknown,
  dispatcher: (wfInput: unknown) => Promise<{ workflowId: string }>,
): Promise<WorkflowStatus<T>> {
  const goalHash = deps.registry.computeGoalHash(tool, input);
  const existing = await deps.registry.findRunningByGoal(ctx.role, goalHash);
  if (existing !== null) {
    await emitSecretEvent(deps.eventStore, 'SECRET.WORKFLOW.BLOCKED_DUPLICATE', {
      tenantId: ctx.tenantId,
      role: ctx.role,
      tool,
      pendingWorkflowId: existing,
    });
    throw new DuplicateWorkflowError(existing);
  }

  const { workflowId } = await dispatcher(input);
  const startedAt = dayjs.utc().toISOString();
  try {
    await deps.registry.record({ workflowId, role: ctx.role, tool, goalHash, startedAt });
  } catch (err) {
    if (isUniqueViolation(err)) {
      await deps.elsaClient.cancelWorkflow(workflowId);
      const original = await deps.registry.findRunningByGoal(ctx.role, goalHash);
      throw new DuplicateWorkflowError(original ?? workflowId);
    }
    throw err;
  }

  await emitSecretEvent(deps.eventStore, 'SECRET.WORKFLOW.STARTED', {
    tenantId: ctx.tenantId,
    workflowId,
    role: ctx.role,
    tool,
    startedAt,
  });

  return { workflowId, status: 'running', startedAt };
}
```

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Race window between `findRunningByGoal` and `record` allows duplicate workflows briefly | Medium | Partial unique index catches the race; losing caller cancels its workflow; unit test for the race path exists |
| Cancelled workflow from race handling leaves orphan state | Medium | Elsa `cancelWorkflow` is transactional; a cancelled workflow's partial state is GC'd by the Elsa engine; worst case an operator sees a brief "cancelled" entry in workflow history |
| Durable timer fails to resume `RotateSecretWorkflow` after 24h | High | Elsa's persistence layer handles timer resume; a time-skip test verifies the mechanism; operator can manually resume via Elsa's admin API if the timer subsystem has a bug |
| `alert_orchestrator` table grows unbounded | Low | Add a retention policy in a follow-up (acknowledged alerts older than 90 days → delete); the read API filters on unacknowledged so list queries stay fast via the partial index |
| Tool catalog curation test misses a new forbidden tool | Medium | The test is parameterised over the forbidden-tool list; when a new dangerous tool is added to the codebase, the list must be updated (code review checklist item) |
| Workflow compensation on create failure double-revokes | Low | `RevokeSecretWorkflow` is idempotent (AC3); double-revoke is a WARN log and a no-op |
| `RotationCascadeWorkflow` stub misleads reviewers into thinking the cascade is real | Medium | Stub logs a clear WARN on every invocation ("deferred — see Story 1.5-30"); workflow file has a TODO banner at top; the workflow README explicitly calls out the stub status |
| Registry HMAC key reuse between domains | Low | HKDF domain separation: `info = "llm-workflow-launch-registry"`, distinct from any secret-store info string; test asserts the derived key differs from secret-store tenant keys |

### What's NOT in this story

To keep scope tight, the following are explicitly out:

- **No real rotation cascade.** `RotationCascadeWorkflow` is a stub.
  Story 1.5-30 implements the real fan-out to dependent services.
- **No operator notification channels.** `alert_orchestrator` writes
  to Postgres and emits a DCB event. Email, Slack, PagerDuty, SMS,
  and any other push channels are deferred. An operator must query
  the table or the read API to see pending alerts.
- **No MCP server wiring.** The MCP server that exposes the secret
  tools to the LLM is Epic 12. This story provides the orchestrator-
  side middleware the MCP server will call; the MCP-to-orchestrator
  glue is its own story.
- **No leak-driven auto-rotate.** Story 1.5-28 implements the leak
  scanner; Story 1.5-31 wires its output to `RotateSecretWorkflow`.
  This story has no awareness of leak events.
- **No drift-driven rotate.** Story 1.5-33 (opt-in background drift
  monitoring) is a follow-up.
- **No `alert_orchestrator` retry on partial failure.** If the DB
  insert succeeds but the DCB event emit fails, we log but don't
  retry. The alert is durably recorded; the event can be
  reconstructed from the table if needed.
- **No acknowledge-with-resolution workflow.** The PATCH API lets
  operators set `acknowledged_at` and a free-form `resolution` string,
  but there's no approval-gated workflow tying alert resolution to
  workflow resumption. That's a separate operational-UX story.
- **No retention policy on either new table.** Operators managing
  the database can add pg_partman or similar; automated retention is
  a follow-up.
- **No cross-tenant alert visibility for platform admins.** RLS is
  tenant-scoped; a platform admin who needs to see all alerts across
  tenants uses a separate superuser query. A dedicated "platform
  admin dashboard" is a separate story.
- **No registry entries for non-LLM-initiated workflows.** The
  registry tracks LLM-launched workflows for duplicate-goal guarding.
  A CLI-initiated or API-initiated workflow bypasses the launcher
  middleware entirely — it goes through a different code path and
  does not contend with LLM workflows for dedup. This is intentional:
  the dedup rule is "don't let the LLM improvise around a pending
  workflow", not "don't let anyone run two workflows with the same
  input ever."
- **No stall detection.** The `SECRET.WORKFLOW.STALLED` event type
  is declared but emission is deferred. The LLM contract says "call
  `alert_orchestrator` on delay" — that's the v1 stall surface.
  Server-side automatic stall detection (e.g. reaping workflows that
  haven't progressed in 30 min) is a follow-up.
