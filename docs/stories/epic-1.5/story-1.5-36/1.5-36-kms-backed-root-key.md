# Story 1.5-36: KMS-backed root key — envelope encryption via AWS KMS, GCP KMS, Azure Key Vault

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / Key Management)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-17 (TammaVaultStore + broker HTTP service)

## Story

As a **Tamma operator running a production broker on a cloud provider where the platform already offers a managed KMS**,
I want **the Tamma vault's root encryption key to be stored wrapped by a KMS-held key-encryption-key, unwrapped only in memory at broker boot via the KMS API**,
so that **a disk image compromise or environment variable leak does not expose the root key, and key rotation can be driven by the platform's own KMS rotation tooling without a Tamma-side migration.**

## Context — Why this story exists

Story 1.5-16 defined the vault's cryptographic model: AES-256-GCM
envelope encryption with a single root key (`TAMMA_VAULT_ROOT_KEY`)
used to encrypt a per-secret data encryption key. The root key is
currently sourced from an environment variable:

```yaml
secrets:
  vault:
    root_key_env: TAMMA_VAULT_ROOT_KEY
```

This is fine for development and simple single-tenant deploys. For
production cloud deploys, operators explicitly asked for envelope
encryption backed by KMS: the root key lives encrypted-at-rest as a
wrapped blob (on disk, in an env var, in a Kubernetes secret), and
the broker calls KMS at startup to unwrap it into memory. The
unwrapped bytes never touch disk, and disk-level compromise doesn't
expose the key.

Story 1.5-16 acknowledged this as future work. This story implements
it, with three cloud KMS providers and a pluggable abstraction that
keeps the env-var path as the default.

### Architecture summary

```
┌──────────────────────┐
│ broker boot          │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐      ┌─────────────────┐
│ RootKeyProvider      │ ───► │ KMS (AWS/GCP/AZ)│
│ .unwrap()            │      │ Decrypt/Unwrap  │
└──────────┬───────────┘      └─────────────────┘
           │ plaintext root key (in-memory only)
           ▼
┌──────────────────────┐
│ TammaVaultStore      │
│ (uses root key for   │
│  envelope encryption)│
└──────────────────────┘
```

The wrapped (encrypted-with-KMS) root key is stored in a file path or
environment variable — either is fine, both are encrypted ciphertext,
neither is useful without the KMS permission to unwrap. At broker
startup, the `IRootKeyProvider` implementation calls the KMS to
decrypt the wrapped blob, receives the plaintext root key, and hands
it to the vault store. The plaintext lives only in the broker
process's memory.

When the broker restarts or crashes, the unwrapped key is gone; the
next boot goes through the same unwrap flow. There is no "cache the
unwrapped key to disk" path — that would defeat the purpose.

## User Story

As a **Tamma platform engineer running the broker on AWS EC2 with an instance profile granting it KMS decrypt permission on a specific key**,
I want **to generate a wrapped root key once via `aws kms encrypt`, commit the wrapped blob to the deploy manifest, and have the broker unwrap it at startup without any plaintext key material ever landing on disk or in an env var**,
so that **stealing the EC2 disk image does not give an attacker the vault root key — they would also need to compromise the IAM role.**

## Acceptance Criteria

### AC1: `IRootKeyProvider` interface

- [ ] An `IRootKeyProvider` interface at `packages/secret-broker/src/crypto/root-key-provider.ts`:
  ```typescript
  interface IRootKeyProvider {
    readonly name: 'env_var' | 'aws_kms' | 'gcp_kms' | 'azure_key_vault';

    /**
     * Resolve the plaintext root key at broker startup. Called exactly
     * once per broker process lifetime. The returned Buffer is owned
     * by the caller; the provider must not retain a reference.
     */
    unwrap(): Promise<Buffer>;

    /**
     * Lifecycle hook for providers that need to release resources
     * (SDK clients, sockets). Called at broker shutdown. Idempotent.
     */
    dispose(): Promise<void>;

    /**
     * Describe the provider for observability — NEVER includes any
     * key material or wrapped-blob contents.
     */
    describe(): {
      provider: string;
      keyRef?: string;       // e.g. 'arn:aws:kms:...:key/...'
      wrappedSource?: 'file' | 'env';
    };
  }
  ```
- [ ] The interface is exported from `packages/secret-broker/src/index.ts`.
- [ ] TypeScript strict mode compiles with zero errors including `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess`.
- [ ] Unit tests: type-level test that `unwrap()` returns `Promise<Buffer>`, never `undefined`, never `null`.

### AC2: `EnvVarRootKeyProvider` (default / current behaviour)

- [ ] `EnvVarRootKeyProvider` at `packages/secret-broker/src/crypto/providers/env-var-root-key-provider.ts` reads the root key from a process environment variable.
- [ ] Config:
  ```yaml
  secrets:
    root_key:
      provider: 'env_var'
      env_var_name: 'TAMMA_VAULT_ROOT_KEY'   # default
  ```
- [ ] `unwrap()` reads the env var, decodes it as base64, asserts length is exactly 32 bytes (AES-256), returns a `Buffer`.
- [ ] Missing env var throws `RootKeyUnavailableError` with a clear message directing the operator to set the var or switch providers.
- [ ] Invalid length throws `RootKeyFormatError` with the observed length and the expected length in the message.
- [ ] After reading, the provider SHOULD `delete process.env[envVarName]` to remove the plaintext from the process environment table. This is defense-in-depth: it does not affect child processes that were already forked, but it does prevent later calls to `process.env` from seeing the key.
- [ ] This provider is the **default** — existing configs that do not specify `secrets.root_key.provider` continue to work exactly as they did before Story 1.5-36.
- [ ] Unit tests: happy path, missing env var, wrong length, wrong encoding, env var unset after read.

### AC3: `AwsKmsRootKeyProvider`

- [ ] `AwsKmsRootKeyProvider` at `packages/secret-broker/src/crypto/providers/aws-kms-root-key-provider.ts`.
- [ ] Config:
  ```yaml
  secrets:
    root_key:
      provider: 'aws_kms'
      key_id: 'arn:aws:kms:us-east-1:123456789012:key/abcd1234-...'
      region: 'us-east-1'
      wrapped_source: 'file'         # 'file' | 'env'
      wrapped_path: '/var/secrets/tamma-root-key.wrapped'
      wrapped_env_var: 'TAMMA_VAULT_ROOT_KEY_WRAPPED'    # if wrapped_source: 'env'
      encryption_context:            # optional, passed to KMS Decrypt
        app: 'tamma-broker'
        env: 'production'
      endpoint?: 'https://localstack:4566'    # for testing
  ```
- [ ] `unwrap()` flow:
  1. Read the wrapped blob from `wrapped_path` (base64 or raw binary — auto-detected from file content) or `wrapped_env_var` (base64).
  2. Construct `KMSClient` from `@aws-sdk/client-kms` with the configured region and optional endpoint (for LocalStack).
  3. Call `DecryptCommand({ CiphertextBlob, EncryptionContext, KeyId })` and await the response.
  4. Assert the returned `Plaintext` is exactly 32 bytes. Fail fast on mismatch.
  5. Return the plaintext buffer.
- [ ] Authentication: the provider uses the default AWS credential chain (instance profile, env vars, shared credentials file) — it does NOT accept explicit credentials in config. Operators who want explicit credentials for the broker set env vars via their deploy system. This is deliberate: KMS-backed root key is the "production-grade" path, and production deploys should use instance roles or workload identity.
- [ ] Encryption context: the `EncryptionContext` field is passed to KMS Decrypt. KMS enforces that the context on Decrypt matches the context the blob was encrypted with, providing an AEAD-style integrity check. Operators configure this to tag the root key with app+environment metadata.
- [ ] **Minimum KMS permissions** documented in provider source and README:
  ```
  kms:Decrypt
  ```
  Resource: the configured `key_id`. Broker IAM role must have this and
  nothing else. The README documents a sample policy.
- [ ] Unit tests: happy path with mocked `@aws-sdk/client-kms` via `aws-sdk-client-mock`, failure on malformed blob, failure on wrong length plaintext, failure on encryption context mismatch, failure on KMS AccessDenied.
- [ ] Integration test: runs against **LocalStack** via `testcontainers`:
  1. Spin up LocalStack with `kms` service.
  2. `CreateKey` to get a key id.
  3. `Encrypt` with a 32-byte test key + encryption context.
  4. Write the ciphertext blob to a temp file.
  5. Construct the provider pointing at the temp file + LocalStack endpoint.
  6. Call `unwrap()`, assert the returned bytes match the original.
  7. Wrong encryption context: assert `unwrap()` fails.

### AC4: `GcpKmsRootKeyProvider`

- [ ] `GcpKmsRootKeyProvider` at `packages/secret-broker/src/crypto/providers/gcp-kms-root-key-provider.ts`.
- [ ] Config:

  5. Return the buffer.

- [ ] Integration test: SKIPPED in CI unless `GCP_INTEGRATION_TEST_PROJECT` is set (GCP has no local KMS emulator that supports real decryption).

### AC5: `AzureKeyVaultRootKeyProvider`

- [ ] `AzureKeyVaultRootKeyProvider` at `packages/secret-broker/src/crypto/providers/azure-key-vault-root-key-provider.ts`.
- [ ] Config:
  ```yaml
  secrets:
    root_key:
      provider: 'azure_key_vault'
      vault_url: 'https://my-vault.vault.azure.net'
      key_name: 'tamma-root-kek'
      key_version?: '<uuid>'         # optional pin
      wrapped_source: 'file' | 'env'
      wrapped_path: '/var/secrets/tamma-root-key.wrapped'
      wrapped_env_var: 'TAMMA_VAULT_ROOT_KEY_WRAPPED'

  ```
- [ ] Uses `@azure/keyvault-keys` (`KeyClient`, `CryptographyClient`) and `@azure/identity` (`DefaultAzureCredential`).
- [ ] `unwrap()` flow:
  1. Read the wrapped blob.
  2. Construct `DefaultAzureCredential` — supports managed identity, workload identity, env vars, Azure CLI, etc.
  3. Construct `CryptographyClient` for the specific key version.
  4. Call `unwrapKey(algorithm, wrappedBlob)` — Azure Key Vault supports key-wrapping primitives directly, so this is a single operation.
  5. Assert the resulting key material is 32 bytes.
  6. Return the buffer.
- [ ] **Minimum RBAC permissions** documented:
  - Role: `Key Vault Crypto User` (or custom role with `Microsoft.KeyVault/vaults/keys/unwrap/action`) scoped to the specific key.
- [ ] Unit tests with mocked `@azure/keyvault-keys`.
- [ ] Integration test: SKIPPED in CI unless `AZURE_INTEGRATION_TEST_VAULT` and `AZURE_INTEGRATION_TEST_KEY` are set.

### AC6: Provider registry + boot integration

- [ ] A small `RootKeyProviderRegistry` at `packages/secret-broker/src/crypto/root-key-provider-registry.ts` with:
  ```typescript
  function constructRootKeyProvider(config: RootKeyConfig): IRootKeyProvider;
  ```
  Pure factory function that switches on `config.provider` and instantiates the correct class.
- [ ] `bootBroker()` calls `constructRootKeyProvider(config.secrets.root_key)` as one of its first steps, awaits `unwrap()`, and passes the resulting buffer to `TammaVaultStore`'s constructor.
- [ ] **Fail-fast on unwrap failure, no automatic fallback to env_var**. If the configured provider fails (KMS unreachable, permission denied, malformed wrapped blob), boot aborts with a clear error. Automatic fallback would silently downgrade security. An operator who wants a fallback path can configure a second provider and manually switch, but that's not this story's scope.
- [ ] Boot logs (at INFO) the result of `describe()` but NEVER the key material. Example log:
  ```
  {"level":30,"msg":"root key unwrapped","provider":"aws_kms","keyRef":"arn:aws:kms:us-east-1:...:key/abcd","wrappedSource":"file"}
  ```
- [ ] Broker shutdown calls `provider.dispose()` before exiting.
- [ ] Integration test: `bootBroker({provider: 'env_var'})`, `bootBroker({provider: 'aws_kms', endpoint: <LocalStack>})`, and a failing config (KMS AccessDenied) each produce the expected outcome.

### AC7: Wrapped key rotation via re-wrap

- [ ] Rotating the root key means:
  1. Generate new 32-byte random plaintext.
  2. KMS `Encrypt` the new plaintext with the KMS key (AWS) or `wrapKey` (Azure).
  3. Write the new wrapped blob to the configured `wrapped_path` (or update the env var in the deployment system — operator's responsibility).
  4. Restart the broker to pick up the new wrapped blob.
  5. Re-encrypt every secret in the vault with the new root key — this is done by `RotateRootKeyWorkflow` (a new workflow in this story) which bumps the `root_key_version` column on every secret row.
- [ ] A new CLI command `tamma vault rotate-root-key`:
  ```
  tamma vault rotate-root-key \
      --provider <env_var|aws_kms|gcp_kms|azure_key_vault> \
      [--key-id <kms-key-id>] \
      --output-wrapped-path <path>          # where to write the new wrapped blob
      [--dry-run]
  ```
- [ ] The CLI command:
  1. Generates a new 32-byte key locally.
  2. Wraps it via the target KMS.
  3. Writes the wrapped blob to `--output-wrapped-path`.
  4. Prints instructions: "restart the broker, then run `tamma vault migrate-root-key` to re-encrypt existing secrets".
  5. Never prints the plaintext.
- [ ] A second command `tamma vault migrate-root-key` drives the re-encryption workflow. It iterates every `tamma_vault_secrets` row, decrypts with the old root key (version N), re-encrypts with the new root key (version N+1), updates `root_key_version` to N+1. The workflow is idempotent and resumable — if it crashes partway, restarting continues from the last committed row.
- [ ] During migration, the broker holds BOTH root keys in memory. The old one is obtained from a deprecated-provider config; the new one from the current provider. A new config section `secrets.root_key_migration.previous_provider` lets operators keep the old provider definition during the migration window.
- [ ] Unit tests: CLI command dry-run, wrap + unwrap round trip with each provider, migration workflow with mocked vault store, idempotency on resume.
- [ ] Integration test: LocalStack KMS, wrap + unwrap + migrate + verify all secrets still decrypt with the new key.

## Dev Notes

### Requirements Context Summary

Envelope encryption backed by cloud KMS is the standard pattern for
vault-style secret stores when deployed on cloud providers. Tamma's
current env-var-only root key is fine for development and self-hosted
on-prem deployments, but it's a hard blocker for operators who want
production cloud deploys with defense-in-depth: disk image compromise
should not equal root key compromise.

### Key Design Decisions

1. **`IRootKeyProvider` is an abstraction specifically for the unwrap
   step at boot**. It is NOT a generic KMS abstraction. Each
   implementation calls exactly one KMS operation: Decrypt (AWS),
   Decrypt (GCP), UnwrapKey (Azure). The shape is narrow because the
   use case is narrow: get the root key plaintext into broker memory
   at startup. Broader KMS operations (signing, additional encryption
   steps, key generation) are out of scope for this interface; if
   future stories need them, they use the SDKs directly.

2. **Env var remains the default**. Most existing Tamma deployments
   use env var mode and we must not break them. Configs that don't
   specify `secrets.root_key.provider` continue to work exactly as
   before — the env var provider is selected implicitly. Operators
   opt into KMS by adding the config block.

3. **Plaintext root key exists ONLY in broker memory, never on disk**.
   Even the KMS-backed providers don't cache the unwrapped key to
   disk. If the broker restarts, the next boot re-unwraps. This is
   more expensive than caching (one KMS call per boot) but it's the
   right security model: a stolen disk image gives zero useful key
   material.

4. **Fail-fast on unwrap failure, no fallback**. If KMS is unreachable
   at boot, the broker refuses to start. Falling back to env_var
   would silently downgrade security: operators might not notice that
   their KMS provider is broken, and start issuing secrets under an
   env-var root key, leaving a mixed-state vault. Explicit failure is
   better than silent downgrade. Operators who want high availability
   set up KMS replication or multi-region KMS keys at the platform
   level, not in Tamma.

5. **Wrapped blob source is file OR env, not both**. Letting the
   operator choose — but forcing one choice — keeps the boot logic
   simple and obvious. The file path is recommended for production
   (easier to mount via Kubernetes secrets, Docker bind-mounts, cloud
   storage CSI drivers). The env var path is for environments without
   a good file delivery mechanism.

6. **No automatic credential chain config options**. Cloud providers
   all have well-defined default credential chains (instance profile
   → env → shared config for AWS, ADC for GCP, DefaultAzureCredential
   for Azure). Letting operators override via Tamma config would
   duplicate credential-loading code and add a surface area for
   misconfiguration. The decision: "use the default chain, period."
   Operators control credentials via platform mechanisms (IAM roles,
   service accounts, managed identities).

7. **Root key rotation requires a broker restart**. Hot-reloading a
   new root key would require the broker to simultaneously serve
   requests with both keys, keep track of which secrets use which
   version, and swap over atomically. That's a significant complexity
   for an operation that happens once a year. A restart is simpler
   and, with the migration workflow iterating over rows, doesn't
   cause secret availability loss — the old key is held alongside
   the new one during migration. After migration the old wrapped blob
   can be destroyed.

8. **Encryption context / AAD is forwarded to KMS where supported**.
   AWS KMS supports encryption context as AEAD-style authenticated
   data; GCP KMS supports `additionalAuthenticatedData`; Azure Key
   Vault's key-wrapping primitive supports AAD via the algorithm
   choice. The provider config accepts an AAD value per provider and
   passes it through. Operators tag their root key with app + env
   context to prevent ciphertext-swap attacks across tenants.

9. **LocalStack covers AWS integration testing, GCP and Azure
   integration tests are opt-in**. Same tradeoff Story 1.5-35 makes:
   no realistic local emulator exists for GCP KMS or Azure Key Vault
   key operations. The unit tests with mocked clients cover
   correctness of the flow; operators running GCP/Azure in production
   can opt into the real-provider tests before release.

### Testing Strategy

- **Unit tests**: each provider with mocked SDKs, happy path + every
  error category, blob loader (file + env), length assertions,
  encryption context propagation.
- **Integration tests**: LocalStack KMS for AWS (full round-trip),
  opt-in real-provider tests for GCP and Azure.
- **Taint tracking**: property-based test with 100 random 32-byte keys;
  error-path plaintext absence; env var deletion assertion.
- **Boot integration**: `bootBroker()` with each provider; failing
  provider aborts boot cleanly; shutdown calls `dispose()`.
- **Migration test**: full wrap → boot → migrate-all-secrets →
  verify cycle against a seeded vault.
- **Smoke test**: manual real-AWS test documented in the runbook.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| KMS unavailable at boot time blocking broker startup | High | Fail-fast with a clear error; operators run broker on infra with HA KMS; runbook documents "KMS down" scenario |
| Plaintext root key leaked via provider retention | Critical | Interface contract: provider does not retain; unit test asserts provider instance has no key-shaped fields after `unwrap`; code review rule |
| Wrong KMS key id in config producing a decrypt error that looks like corruption | Medium | `describe()` output at INFO level shows `keyRef`; error message includes the key id the broker tried to use |
| Migration workflow crash leaving vault in a half-migrated state | High | Workflow is idempotent and resumable; `root_key_version` column is committed per row; resume picks up from last committed row; integration test covers crash-and-resume |
| Operator deletes the wrapped blob file while broker is running | Low | Broker already has the plaintext in memory; shutdown and subsequent boot fail explicitly with "wrapped blob not found" |
| Operator loses the wrapped blob AND the KMS key | Critical | Documented as "vault is unrecoverable" in the runbook; operators keep wrapped blob backups out-of-band; KMS key lifecycle managed outside Tamma |
| Automatic IAM policy drift revoking the broker's KMS access | Medium | Describe output logs key ref; boot failure logs the exact KMS error; operators set up monitoring on broker boot failures |
| Encryption context mismatch after operator config edit | Medium | KMS Decrypt returns a clear error; boot fails with the full context mismatch message; runbook documents "change encryption context" procedure (requires re-wrap) |
| Env var provider delete fails due to read-only environ | Low | `delete process.env` is best-effort; failure is logged at WARN but doesn't fail boot; test specifically covers the Node behaviour |
| Azure `DefaultAzureCredential` picking up the wrong credential source | Medium | Provider's `describe()` output includes the credential chain that succeeded; operators can set `AZURE_CLIENT_ID` to force a specific managed identity |
| Migration workflow doubling vault storage during dual-key window | Low | Migration is in-place: each row is decrypted, re-encrypted, and updated in a single transaction. Storage footprint is unchanged during migration |
| Integration test flakiness from LocalStack KMS latency | Low | Use `testcontainers` ready-check for KMS service before test; retry on transient 5xx; proven pattern from Story 1.5-35 |
