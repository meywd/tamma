# Story 1.5-23: GitHub Actions Secrets Mirror (`GitHubSecretStore`)

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / LLM Safety)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-16 (interface), Story 1.5-17 (`IMirrorStore` + broker service), Story 1-5 (GitHub Platform Implementation)

## Story

As a **Tamma operator using GitHub as my primary git platform**,
I want **a real `GitHubSecretStore` that mirrors Tamma-managed secrets into
GitHub Actions secrets (repo, org, and environment scopes) via Octokit**,
so that **workflows running on GitHub-hosted runners can consume secrets
Tamma provisioned without ever exposing the plaintext to the LLM that
drove the provisioning workflow**.

## Context

Story 1.5-17 scaffolded the broker with a `MockMirrorStore` — secrets in
`platform_only` and `vault_copy` modes pretend to sync to their target but
actually just record a row and return. This story replaces the mock with
a real GitHub implementation: `GitHubSecretStore implements IMirrorStore`
writes to the GitHub Actions secrets API using libsodium sealed-box
encryption with the public key returned by GitHub.

The implementation reuses the existing authenticated `Octokit` client
owned by `GitHubPlatform` (Story 1-5). It does NOT construct its own
Octokit — when the broker bootstraps, the platform registry hands the
already-initialised client to the mirror store factory. This keeps
credentials in one place and means rate-limit bookkeeping (Story 1-5's
`github-rate-limiter.ts`) applies uniformly across PR, issue, and
secret operations.

GitHub's secrets API is **write-only**: there is no endpoint that returns
a decrypted value. That is fine for Tamma's model — `verifySecret` in
`platform_only` mode is a metadata-only check (`verificationLevel:
'metadata'`) per Story 1.5-16 AC7. This story does not implement a
read-back path and does not need to.

This story explicitly does NOT cover:
- GitLab, Gitea, Forgejo, Bitbucket, or Azure DevOps (Stories 1.5-24,
  1.5-25, 1.5-26).
- Revocation cascade to platform mirrors — that's Story 1.5-30.
- Drift detection via GitHub audit-log webhooks — that's Story 1.5-33.
- OIDC-based CI fetch — that's Story 1.5-21. This story is purely about
  *mirroring writes* from the broker into GitHub; runtime fetch from CI
  goes through a different code path.

## Acceptance Criteria

### AC1: `GitHubSecretStore` class shape + DI wiring

- [ ] `packages/secret-broker/src/mirrors/github-mirror-store.ts` exports
      `GitHubSecretStore implements IMirrorStore`.
- [ ] Constructor signature:
      ```typescript
      constructor(options: {
        platform: GitHubPlatform;  // already-initialised, from @tamma/platforms
        logger: pino.Logger;
        eventStore: IEventStore;
      })
      ```
- [ ] The class does NOT construct its own `Octokit`. It calls
      `options.platform.getClient()` (or a newly-added public accessor
      `platform.getAuthenticatedClient()` if `getClient` is private) on
      every request. A unit test confirms that calling
      `new GitHubSecretStore({platform: stub})` without ever touching
      the platform's auth flow does not fail until the first method
      invocation.
- [ ] The broker's `bootBroker()` (from 1.5-17) is extended to register
      `GitHubSecretStore` in a `PlatformMirrorRegistry` keyed by
      `platform: 'github'`. When a `DeployTarget.scope.platform === 'github'`
      arrives, the registry resolves to this store. Stories 1.5-24/25/26
      add their own entries in the same registry.
- [ ] The old `MockMirrorStore` from 1.5-17 remains available for tests
      that don't want to hit a real GitHub, injected via the same
      `IMirrorStore` slot.

### AC2: Sealed-box encryption of secret values

- [ ] `packages/secret-broker/src/mirrors/github-sealed-box.ts` exports
      `sealSecret(plaintext: Buffer, publicKeyBase64: string): { encrypted_value: string; }`
      using libsodium's `crypto_box_seal` primitive. The `encrypted_value`
      returned is base64-encoded — GitHub's API requires that exact shape.
- [ ] Implementation uses `libsodium-wrappers` (`sodium.ready` awaited
      at module load) or the equivalent WASM binding — **not** a
      hand-rolled NaCl implementation. Document the chosen package in
      the file's top-of-file comment with a link to its npm page.
- [ ] A round-trip unit test proves the sealed-box contract:
  1. Generate a fresh `crypto_box_keypair()` (known private + public key).
  2. Call `sealSecret(knownPlaintext, publicKey)`.
  3. Decrypt the result with `crypto_box_seal_open(encrypted, publicKey, privateKey)`.
  4. Assert the decrypted bytes equal `knownPlaintext`.
- [ ] The plaintext buffer passed into `sealSecret` is never logged and
      is zeroised (`.fill(0)`) immediately after the call returns. A
      taint-tracking test asserts the plaintext does not appear in any
      pino log line, error message, or thrown exception produced by the
      function.
- [ ] If the public-key fetch from GitHub fails (404, 500, rate-limit),
      the function throws a typed `SealedBoxEncryptError` with a
      `cause: GitHubApiError` chain. The plaintext is zeroised before
      the throw.

### AC3: Repo-scoped secret CRUD

- [ ] `GitHubSecretStore.write(target, value, commitment)` where
      `target.scope.kind === 'repo'` performs these steps:
  1. `GET /repos/{owner}/{repo}/actions/secrets/public-key` to fetch
     `{ key, key_id }` for the repo.
  2. Call `sealSecret(value, key)` to produce `encrypted_value`.
  3. `PUT /repos/{owner}/{repo}/actions/secrets/{secret_name}` with body
     `{ encrypted_value, key_id }`.
  4. Verify the response status is 201 (new) or 204 (update).
  5. Update the corresponding `tamma_vault_deploy_targets` row:
     `sync_status = 'synced'`, `last_synced_at = now()`, `last_error = null`.
  6. Emit `SECRET.DEPLOYED.SUCCESS` audit event with tags
     `{secretId, platform: 'github', scope_kind: 'repo', owner, repo, name: secret_name}`.
     Event data carries commitment hash only, never the value.
  7. Return `{syncedAt: <iso>}`.
- [ ] `GitHubSecretStore.delete(target)` calls
      `DELETE /repos/{owner}/{repo}/actions/secrets/{secret_name}` and
      removes the row from `tamma_vault_deploy_targets` on 204. On 404
      the call is treated as "already deleted" — the row is removed and
      no error is thrown, matching Story 1.5-16's fail-closed semantics.
- [ ] `GitHubSecretStore.listAt(scope)` where `scope.kind === 'repo'`
      calls `GET /repos/{owner}/{repo}/actions/secrets` and returns the
      list of secret **names** only. GitHub does not return values — a
      unit test pins this expectation by asserting the mapped output
      does not contain any `value`, `encrypted_value`, or `plaintext`
      field.

### AC4: Org-scoped secret CRUD

- [ ] `write` with `target.scope.kind === 'org'` calls the org endpoints:
  1. `GET /orgs/{org}/actions/secrets/public-key`
  2. `PUT /orgs/{org}/actions/secrets/{secret_name}` with body
     `{ encrypted_value, key_id, visibility, selected_repository_ids? }`.
- [ ] The `visibility` field defaults to `'private'` (only the org's
      private repos can consume the secret). If the caller passes
      `target.metadata.visibility === 'selected'`, the store reads the
      list of repository IDs from `target.metadata.selectedRepositoryIds`
      (must be a `number[]`) and includes them in the PUT body. `'all'`
      visibility is refused with a typed `UnsafeOrgVisibilityError` —
      setting a Tamma-managed secret to be readable by every repo in an
      org is almost always a misconfiguration and requires an explicit
      operator-mode override (not in scope for this story).
- [ ] `delete` calls `DELETE /orgs/{org}/actions/secrets/{secret_name}`.
- [ ] `listAt` with `scope.kind === 'org'` calls
      `GET /orgs/{org}/actions/secrets`.
- [ ] Unit tests cover all three visibility variants (private, selected,
      all-rejected).

### AC5: Environment-scoped secret CRUD

- [ ] `write` with `target.scope.kind === 'environment'` uses the
      environment endpoints:
  1. Resolve `repository_id` from `owner/repo` via
     `GET /repos/{owner}/{repo}` (cached per-process for TTL 5 minutes
     so repeated writes to the same repo's envs don't hammer the API).
  2. `GET /repositories/{repository_id}/environments/{env_name}/secrets/public-key`
  3. `PUT /repositories/{repository_id}/environments/{env_name}/secrets/{secret_name}`
     with body `{ encrypted_value, key_id }`.
- [ ] If the target environment does not exist (404 on the public-key
      fetch), `write` returns a typed `EnvironmentNotFoundError` with
      a message pointing the operator at GitHub's environment creation
      UI. It does NOT auto-create the environment — that's a policy
      decision belonging to a higher layer.
- [ ] `delete` and `listAt` use the corresponding environment endpoints.
- [ ] An integration test (gated on `GITHUB_TEST_TOKEN`) creates a real
      environment in a test repo, writes a secret, lists it, and deletes
      it end-to-end.

### AC6: `tenant_root` scope is refused

- [ ] `write` with `target.scope.kind === 'tenant_root'` returns a typed
      `UnsupportedScopeError` with code `UNSUPPORTED_SCOPE` and message
      "tenant_root secrets must not be mirrored to any git platform — use
      vault_only mode instead". This matches Story 1.5-16 AC9's forced
      `vault_only` for `tenant_root`. The error is thrown before any
      GitHub API call is made.
- [ ] A unit test asserts that passing a `tenant_root` scope never
      triggers an outbound HTTP call (verify via the mock Octokit
      adapter's call counter).

### AC7: Rate limit handling

- [ ] All requests go through the existing `withRateLimit` wrapper from
      `packages/platforms/src/github/github-rate-limiter.ts` (Story 1-5).
      The wrapper inspects `X-RateLimit-Remaining` and `X-RateLimit-Reset`
      headers on each response and enforces a back-off when remaining
      drops below 10% of limit.
- [ ] On a `403` with `x-ratelimit-remaining: 0`, the store retries with
      exponential back-off (1s, 2s, 4s, 8s, 16s, max 30s) up to 5
      attempts. On the 6th failure it throws a typed
      `GitHubRateLimitExhaustedError` with `retryAfterMs` extracted from
      the `x-ratelimit-reset` header.
- [ ] A unit test with a mocked Octokit simulates the 403 + reset flow
      and asserts the retry sequence, sleep durations (allowing ±100ms),
      and final error type.

### AC8: Error mapping

- [ ] `packages/secret-broker/src/mirrors/github-error-mapper.ts`
      defines `mapGitHubMirrorError(error: unknown): MirrorStoreError`
      mapping Octokit error codes to typed broker errors:
  | HTTP status | Error class |
  |---|---|
  | 401 | `GitHubAuthError` — "invalid or expired GitHub token" |
  | 403 (not rate-limit) | `GitHubPermissionError` — "insufficient permissions to write secrets at this scope" |
  | 404 | `GitHubTargetNotFoundError` — "repository, org, or environment not found" |
  | 422 | `GitHubValidationError` — "invalid secret name or body"; includes the GitHub `message` verbatim if safe |
  | 5xx | `GitHubServerError` — retryable, wrapped in the back-off path |
- [ ] Unit tests assert each mapping given a fabricated Octokit error
      of the corresponding shape.
- [ ] Error messages are audited against Story 1.5-16's rule: no
      plaintext or commitment hash leaks into `.message` — only
      target coordinates (owner/repo/scope kind/secret name).

### AC9: Sync status tracking

- [ ] After every successful `write`, the store updates the
      `tamma_vault_deploy_targets` row matching `(secret_id,
      target_scope, target_name)`:
      ```sql
      UPDATE tamma_vault_deploy_targets
         SET sync_status = 'synced',
             last_synced_at = now(),
             last_error = null
       WHERE secret_id = $1
         AND target_scope = $2::jsonb
         AND target_name = $3;
      ```
- [ ] On `write` failure (any typed error above), the row is updated with
      `sync_status = 'failed'` and `last_error = <error.message>` (never
      including the value or commitment).
- [ ] A unit test creates a row in `pending`, triggers a successful
      write, and asserts the row moves to `synced`. A second test
      triggers a failure and asserts the row moves to `failed`.

### AC10: Audit events

- [ ] Every `write`, `delete`, and `listAt` call emits exactly one
      audit event via the broker's `emitSecretEvent` helper:
  - `SECRET.DEPLOYED.SUCCESS` or `SECRET.DEPLOYED.FAILED` for `write`
  - `SECRET.REVOKED.SUCCESS` or `SECRET.REVOKED.FAILED` for `delete`
  - `SECRET.LISTED` for `listAt`
- [ ] Audit event `tags` always include `platform: 'github'`, the scope
      coordinates (`owner`, `repo`, `org`, `env_name`), the secret name,
      and the `secretId` from the broker's ledger.
- [ ] Event `data` carries the commitment hash and the tamma-side
      `rootKeyVersion` — never the plaintext, never the base64 encrypted
      value sent to GitHub, never the libsodium public key (public keys
      are safe to log but aren't load-bearing for audit).

### AC11: Integration test against real GitHub

- [ ] `packages/secret-broker/src/mirrors/__tests__/github-mirror-store.integration.test.ts`
      runs against real GitHub when `GITHUB_TEST_TOKEN` is set in the
      environment. Otherwise the suite is `describe.skip`'d with a clear
      console message.
- [ ] The test uses a throwaway repo under `tamma-test-github` org (or
      repo name configurable via `GITHUB_TEST_REPO`).
- [ ] Scenarios covered by the integration test:
  1. Repo-scoped secret: write → list (present) → delete → list (absent).
  2. Org-scoped secret with `visibility: 'private'`: write → list → delete.
  3. Environment-scoped secret: create environment (via Octokit), write →
     list → delete, tear down environment.
  4. Tampered commitment: verify remains `matches: true` on the
     broker side because GitHub's API is write-only — this test exists
     to document the limitation, not to fail.
  5. Rate-limit drill: fire 100 rapid writes, assert at least one
     back-off was triggered by inspecting the logger mock's captured
     events.

### AC12: Unit test coverage

- [ ] All public `IMirrorStore` methods have unit tests with a mocked
      Octokit (no network). Use `msw` (Mock Service Worker) to intercept
      Octokit's underlying `fetch` so the test surface matches what
      Octokit actually produces.
- [ ] Coverage targets: 90% line, 85% branch for
      `github-mirror-store.ts` and `github-sealed-box.ts`.
- [ ] A taint-tracking test seeds a known plaintext, runs all three
      CRUD ops against the mock, captures all logger output and all
      audit events, and asserts the plaintext bytes do not appear in
      any string in either stream.

## Dev Notes

### Requirements Context Summary

**Epic Context**: Story 1.5-17 stood up the broker service with a
`MockMirrorStore`. That mock is fine for local dev and CI, but in
production a Tamma operator using GitHub needs actual secrets written
to GitHub Actions' secret store so their workflows can read them via
the standard `${{ secrets.FOO }}` syntax. This story provides the first
real mirror implementation, for GitHub.

**Technical Context**: GitHub's Actions secrets API uses libsodium
sealed-box encryption (Curve25519 + XSalsa20-Poly1305). The client
fetches a per-scope public key, encrypts the secret value with it, and
PUTs the base64-encoded ciphertext along with the `key_id`. GitHub's
backend decrypts using its matching private key and stores the plaintext
encrypted at rest with its own KMS. Tamma never handles GitHub's private
key — we only encrypt, not decrypt, from the client side.

**Integration Points**:
- **Story 1-5 (`GitHubPlatform`)**: reuses the same authenticated
  `Octokit` client. No new auth flow. Rate-limit bookkeeping is shared.
- **Story 1.5-17 (broker service)**: swaps out `MockMirrorStore` at DI
  time via the `PlatformMirrorRegistry` — a `Map<string, IMirrorStore>`
  keyed by platform name.
- **Story 1.5-18 (Elsa activities)**: the `DeploySecretActivity` will
  call `POST /internal/secrets/mirror-to` on the broker, which
  dispatches to this store based on `target.scope.platform`.
- **Story 1.5-28 (leak scanner)**: after a leak is detected and a
  rotation triggered, the cascade workflow (1.5-30) calls this store's
  `write` method with the new value.

### Key Design Decisions

1. **Reuse the platform's Octokit client, do not create a new one.**
   Credentials, rate-limit bookkeeping, and Octokit plugins (retry,
   throttle) live in one place. If the broker constructed its own
   Octokit, a PR author could forget to add a new plugin to one of
   them and get divergent behaviour. Rule of thumb: "one client per
   git-platform auth per process."

2. **Sealed-box encryption via `libsodium-wrappers`, not hand-rolled
   NaCl.** The libsodium WASM binding is tiny (~100KB gzipped),
   maintained, and correct by construction. Writing a sealed-box
   implementation is not hard but is unnecessary risk — it's the kind
   of code where a single off-by-one in a length prefix leaks bits.

3. **`tenant_root` is refused at the class boundary, not deferred to
   `resolveMode`.** Even though Story 1.5-16's `resolveMode` also
   forces `vault_only` for `tenant_root`, this store additionally
   refuses the write — defence in depth. If a future bug in
   `resolveMode` accidentally lets a `tenant_root` secret through, the
   mirror still rejects it. Two independent checks are cheap.

4. **Org `visibility: 'all'` is refused by default.** GitHub's org
   secret API allows a secret to be visible to every private repo in
   the org, including repos Tamma does not manage. For a platform
   that's supposed to manage LLM-safe secrets, this is almost always
   a misconfiguration. Operators who really want it can override via
   a Story 1.5-39 policy knob on the operator dashboard, but this
   story refuses the unsafe default.

5. **No auto-creation of environments.** If an operator points a
   `DeployTarget` at an environment that doesn't exist, the mirror
   returns `EnvironmentNotFoundError` rather than quietly creating
   the environment. Environments carry deployment-protection rules
   (required reviewers, branch restrictions) — silently creating one
   without those rules is a security regression.

6. **Repository-id cache with 5-minute TTL.** The environment secrets
   API uses `repository_id`, not `owner/repo`. Resolving the id costs
   a `GET /repos/{owner}/{repo}` call every time otherwise. A small
   in-memory cache keyed by `owner/repo` with a 5-minute TTL makes
   bulk writes to the same repo's environments O(1) after the first.
   The TTL is deliberately short: if a repo is renamed the stale id
   is still valid for a while (GitHub keeps the mapping), and 5
   minutes is short enough that operational drift is bounded.

7. **`verifySecret` for GitHub secrets always returns
   `verificationLevel: 'metadata'`.** This is not a GitHub-specific
   choice, it follows from Story 1.5-16 AC7: GitHub's API is
   write-only, there is no way to read a value back to verify it.
   Callers needing high-fidelity verification must use
   `probeSecret` (Story 1.5-27) or switch the secret to `vault_copy`
   mode so the broker has a local copy to decrypt.

8. **Error messages strip plaintext and commitment hashes.** The
   mapper builds messages from safe coordinates only — owner, repo,
   org, env name, secret name, status code. A lint-like unit test
   instantiates each error class with a fabricated plaintext in the
   original Octokit error payload and asserts it does not appear in
   the resulting `.message`.

### Testing Strategy

- **Unit tests** for every method with a mocked Octokit via `msw`.
- **Property tests** for the sealed-box round trip with random inputs
  (use `fast-check` if available; fall back to a fixed corpus).
- **Rate-limit drill** with fabricated 403 responses and time-travel
  via `vi.useFakeTimers()`.
- **Integration tests** against real GitHub, gated on `GITHUB_TEST_TOKEN`.
  The suite self-documents what it covers in its top-of-file comment
  so a developer without the token can still see what's being tested.
- **Taint-tracking tests** across unit and integration layers —
  plaintext must not appear in logger output, audit events, error
  messages, or `tamma_vault_deploy_targets` rows.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Sealed-box bug leaks plaintext | Critical | Use `libsodium-wrappers` (audited); round-trip test with known keypair; taint-tracking test on zeroisation |
| Broker OOM under rapid rotation across many repos | Medium | Repository-id cache bounds memory; per-call sealed-box allocation is transient and GC'd |
| GitHub API response shape drifts | Low | Snapshot the response shape in fixtures; pin `@octokit/rest` major version; nightly integration test runs are scheduled in Story 1.5-33 alongside drift detection |
| Rate-limit exhaustion during cascade | Medium | Shared rate limiter from `GitHubPlatform`; exponential back-off; typed error surfaces cleanly |
| Operator accidentally sets `visibility: 'all'` | High | Refused by default with typed error; test pins the refusal |
| Octokit plugin drift between platform and mirror | Low | Mirror reuses platform's client, so there's exactly one Octokit instance |
| Tampered response from a MITM proxy | Low | GitHub API is HTTPS + certificate-pinned by Octokit; sealed-box is end-to-end encrypted to GitHub's public key, so MITM cannot decrypt |
