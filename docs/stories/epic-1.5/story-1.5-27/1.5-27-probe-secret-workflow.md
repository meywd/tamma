## Story

As a **Tamma operator or tenant owner**,
I want Tamma's secret broker to actively exercise stored secrets against the real systems they protect (databases, HTTP APIs, SMTP servers, JWT signing, GitHub),
so that I can detect rotations, revocations, or misconfigurations before a workflow depends on a broken secret — without ever exposing the plaintext to the caller, the orchestrator, or any LLM tool.

## Overview

Story 1.5-16 defined the `ISecretStore.probeSecret()` contract and the `ProbeResult` type. Story 1.5-17 implemented the `TammaVaultStore` with `probeSecret()` as a `not_supported` stub. This story replaces the stub with a real pluggable probe dispatcher, implements the v1 set of probe handlers, and wires the Elsa `ProbeSecretWorkflow` to orchestrate probes end-to-end.

The key property: **probes execute entirely inside the broker process**. The broker already has either a local encrypted copy of the plaintext (`vault_only` / `vault_copy` modes from 1.5-17) or can fetch it from GitHub Actions secrets via an ephemeral flow (`platform_only` mode). In both cases, the plaintext is loaded into an in-memory `Buffer`, handed to a probe handler for a single active attempt, and discarded. The result returned to the caller is always a shape-constrained `ProbeResult` — success/failure + error category + redacted error message + latency — never the plaintext and never an oracle signal that can be used for brute force.

v1 probe types (each a separate handler module):
1. **`http_bearer`** — GET/POST an arbitrary URL with `Authorization: Bearer <secret>`, assert the status code is 2xx or matches a user-supplied allowed range
2. **`database_connect`** — open TCP + authenticate to Postgres, MySQL, or Redis (driver determined by probe config)
3. **`jwt_sign_verify`** — sign a test payload using the secret as an HMAC signing key, verify the resulting signature, confirm roundtrip
4. **`smtp_auth`** — open an SMTP connection, issue `EHLO` + `AUTH LOGIN` or `AUTH PLAIN`, confirm the server accepts the credentials
5. **`github_token`** — call GitHub's `/user` endpoint with `Authorization: token <pat>` (or `Bearer <pat>`), confirm 200 OK

The `ProbeSecretWorkflow` (Elsa C# side) orchestrates: load secret → rate-limit check → dispatch to handler → return `ProbeResult` → emit `SECRET.PROBED.*` audit event.

## Acceptance Criteria

1. `IProbeHandler` interface defined in `packages/secret-broker/src/probes/types.ts`:
   ```typescript
   interface IProbeHandler {
     readonly type: ProbeType;
     probe(value: Buffer, config: Record<string, unknown>, timeoutMs: number): Promise<ProbeResult>;
     validateConfig(config: Record<string, unknown>): { valid: boolean; errors: string[] };
   }
   ```
2. `ProbeHandlerRegistry` maps `ProbeType` → `IProbeHandler`; `TammaVaultStore.probeSecret()` delegates to the registry instead of returning `not_supported`
3. `http_bearer` handler: issues a `fetch` to `config.url` with `Authorization: Bearer <secret>`, configurable method (`GET`|`POST`), configurable allowed status codes (default `[200..299]`), configurable request body; returns `success=true` if status in allowed range, otherwise `errorCategory: 'auth_failed' | 'not_found' | 'rate_limited' | 'server_error'` derived from status code
4. `database_connect` handler: accepts `config.driver: 'postgres' | 'mysql' | 'redis'`, uses `pg` / `mysql2/promise` / `ioredis` respectively, opens a connection, runs a trivial query (`SELECT 1` / `PING`), closes connection; returns `errorCategory: 'auth_failed' | 'network_error' | 'not_found'` on failure
5. `jwt_sign_verify` handler: uses `jsonwebtoken` to sign `{ sub: 'tamma-probe', iat: <now> }` with HS256 using the secret as key, verifies the signature roundtrip, returns `success=true` only when both sign and verify succeed
6. `smtp_auth` handler: uses `nodemailer` `createTransport({ auth: { user, pass: <secret> } }).verify()` to open a connection + AUTH + close; accepts `config.host`, `config.port`, `config.username`, `config.secure`
7. `github_token` handler: issues `GET https://api.github.com/user` with `Authorization: token <secret>`, returns `success=true` on 200, `auth_failed` on 401, `rate_limited` on 403+`x-ratelimit-remaining: 0`
8. **Rate limiting is mandatory.** A `ProbeRateLimiter` (token bucket per `secretId`) enforces a default of **10 probes per secret per minute**. Exceeding the limit returns `ProbeResult { success: false, errorCategory: 'rate_limited', errorMessage: 'probe rate limit exceeded' }` WITHOUT dispatching to the handler. The limit is configurable per-tenant but capped at 60/min.
9. **Redaction is mandatory.** Every `ProbeResult.errorMessage` is run through `redactSensitiveKeys` from `@tamma/shared/telemetry/utils` before being returned to the caller. A dedicated test injects a known secret value into a handler's failure path and asserts the secret does NOT appear anywhere in the returned `ProbeResult` (see Taint-Tracking Test).
10. **Timeouts are mandatory.** Each probe call accepts a `timeoutMs` parameter. Default: 10,000 ms. The caller may override up to a ceiling of 60,000 ms; any higher value is rejected at workflow-input validation with `errorCategory: 'config_error'`. If a handler exceeds `timeoutMs`, it is aborted (via `AbortController` for HTTP, connection `destroy()` for DB, transport `close()` for SMTP) and returns `errorCategory: 'timeout'`.
11. **Config validation happens before any network call.** Each handler's `validateConfig()` is invoked first; invalid config returns `ProbeResult { success: false, errorCategory: 'config_error', errorMessage: <validation errors joined, redacted> }` without issuing any network request.
12. `ProbeSecretWorkflow` (Elsa) orchestrates: `LoadSecret → CheckRateLimit → ValidateConfig → DispatchProbe → EmitAuditEvent → Return`. Workflow replay is deterministic (the probe result is an activity output, not embedded logic).
13. Audit events: every probe emits `SECRET.PROBED.SUCCESS` or `SECRET.PROBED.FAILED` with tags `{ secretId, tenantId, probeType }` and data `{ durationMs, errorCategory?, errorMessage? }` (errorMessage already redacted at AC-9)
14. Per-handler test file at `packages/secret-broker/src/probes/<handler>.test.ts` covering: happy path, auth failure, network error, timeout, config validation error, taint-tracking
15. Rate-limit unit test: 11 probes in quick succession against the same `secretId` → 11th returns `rate_limited`
16. Integration test fixtures: ephemeral Postgres via `pg-mem` or testcontainers, HTTP via `nock` / MSW, SMTP via `smtp-tester`, GitHub via MSW, Redis via `ioredis-mock`

### Requirements Context Summary

**Epic Context:** The secret broker is the piece of infrastructure that lets Tamma's autonomous workers hold tenant credentials without exposing them to the LLM. Stories 1.5-16 and 1.5-17 built the storage and retrieval paths — this story closes the loop by making secrets *verifiable*. Without an active probe, a rotated-but-not-updated secret would silently fail at the first production-workflow call, which is the worst possible failure mode (wasted orchestration, wasted LLM tokens, wasted human triage).

**Technical Context:** Probes must run somewhere that has the plaintext. We already have this restriction solved by the broker process (Story 1.5-17 stores the encrypted plaintext for `vault_only` / `vault_copy` modes, and has an ephemeral fetch path for `platform_only`). The novelty here is that we're *actively using* those bytes rather than just ferrying them — which introduces two new attack surfaces that this story explicitly defends against: (1) brute-force-via-probes, mitigated by rate limiting, and (2) error-message leak, mitigated by the `redactSensitiveKeys` + taint-tracking pipeline.

**Integration Points:**
- Story 1.5-16 (ISecretStore interface): `probeSecret()` contract, `ProbeResult` type, audit event shape — unchanged
- Story 1.5-17 (TammaVaultStore): the `not_supported` stub is replaced; `_getPlaintext()` private is reused
- Story 1.5-18 (Secret Activities): `ProbeSecretActivity` wraps this story's HTTP endpoint from the Elsa side
- Story 1.5-19 (Workflow infrastructure): audit event bus
- Story 1.5-28 (Leak Detection): does NOT depend on this — leak detection is pattern-based, not probe-based

### Implementation Guidance

**Key Design Decisions:**

1. **Probes run in the broker, not in the main API or orchestrator.** The broker is the only process with decryption keys. Moving probes anywhere else would require duplicating that trust boundary. The main API exposes only high-level verbs (`probe this secret id`) and receives back a `ProbeResult`; it never sees bytes.

2. **Rate limiting is a security requirement, not a politeness feature.** Without it, a misbehaving LLM could invoke `probeSecret` in a loop with a crafted probe config to use the target system as an oracle (e.g., "does the token have `repo` scope?"). 10/min is low enough that no legitimate workflow needs more, and high enough that rotation testing and health checks work. The ceiling of 60/min exists so a burst-recovery scenario (rotating 50 secrets in a row) doesn't deadlock.

3. **Redaction is layered: keyed AND literal.** `redactSensitiveKeys` only handles object-shaped error payloads. Probe handlers may surface plaintext in error strings (e.g., `pg` library sometimes echoes the password in connection error messages). So we add a second pass: a literal substring scan for the plaintext bytes (both as raw UTF-8 and as base64), replaced with `[REDACTED]`. A dedicated **taint-tracking test** injects the sentinel `tamma-probe-taint-sentinel-xyz123` into each handler's failure path and asserts the sentinel never appears in any field of the returned `ProbeResult`.

4. **Timeouts are enforced in two places: the handler and the workflow.** Handlers use `AbortController` / connection `destroy()` so they release resources cleanly. The workflow also has its own upper bound (60s hard cap) so a misbehaving handler that ignores `timeoutMs` still cannot hang a worker thread. Ceiling is 60s, not 30s, because SMTP handshakes against slow servers legitimately need that much.

5. **Config validation is a distinct phase before dispatch.** An invalid config must fail *without* loading the plaintext. This matters because loading plaintext is itself a security-audited operation (it decrypts an envelope, emits a `SECRET.ACCESSED` event, etc.); we don't want to emit that event for a request that was going to be rejected anyway. Order: `validateConfig` → `rate-limit check` → `loadSecret` → `dispatch`.

6. **Each handler type is its own file, not a switch statement.** This is critical for (a) per-type test isolation, (b) the "what's NOT in this story" boundary — custom/plugin probe types can be added by dropping a new file in `packages/secret-broker/src/probes/` and registering it, (c) keeps individual handler files under 200 lines so the security review can audit each in isolation.

7. **No `tamma_api_key` probe type in v1.** Tempting, but would create a circular dependency (probing the Tamma API requires the Tamma API). Deferred to follow-up once we have a dedicated internal validation endpoint.

**Technical Specifications:**

- **Probe dispatch flow:**
  ```
  ProbeSecretWorkflow (Elsa)
    → ExecuteProbeActivity
      → POST /internal/v1/probe { secretId, probeType, config, timeoutMs }
        → TammaVaultStore.probeSecret(secretId, probeType, config, timeoutMs)
          → handler.validateConfig(config)             [synchronous, no plaintext]
          → rateLimiter.check(secretId)                [synchronous, no plaintext]
          → plaintext = _getPlaintext(secretId)        [decrypts envelope, emits SECRET.ACCESSED]
          → handler.probe(plaintext, config, timeoutMs)
          → sanitizeProbeResult(result, plaintext)     [keyed + literal redaction]
          → plaintext.fill(0)                          [zero buffer]
          → return sanitized result
        → emit SECRET.PROBED.SUCCESS|FAILED audit event
  ```

- **`ProbeResult` shape** (from 1.5-16, unchanged):
  ```typescript
  type ProbeErrorCategory =
    | 'auth_failed'
    | 'not_found'
    | 'network_error'
    | 'rate_limited'
    | 'server_error'
    | 'timeout'
    | 'config_error'
    | 'not_supported';

  interface ProbeResult {
    success: boolean;
    probedAt: string;        // ISO 8601
    durationMs: number;
    errorCategory?: ProbeErrorCategory;
    errorMessage?: string;   // redacted
  }
  ```

- **Error code constants** (add to existing `PROVIDER_ERROR_CODES` pattern):
  ```typescript
  export const PROBE_ERROR_CODES = {
    PROBE_CONFIG_INVALID: 'PROBE_CONFIG_INVALID',
    PROBE_RATE_LIMITED: 'PROBE_RATE_LIMITED',
    PROBE_TIMEOUT: 'PROBE_TIMEOUT',
    PROBE_UNSUPPORTED_TYPE: 'PROBE_UNSUPPORTED_TYPE',
  } as const;
  ```

- **Timeout defaults:**
  - HTTP bearer / github_token: 10s default, 30s ceiling (GitHub can be slow under load)
  - database_connect: 10s default, 30s ceiling
  - smtp_auth: 10s default, 60s ceiling (SMTP banner grabs over slow links)
  - jwt_sign_verify: 1s default, 5s ceiling (purely local CPU work)

- **Rate limiter state:** in-memory only in v1. Broker runs as a single process per node; multiple broker replicas would each have their own bucket. Distributed rate limiting is a known follow-up (1.5-27.1).

### Testing Strategy

**Unit Tests (per-handler, colocated `*.test.ts`):**
- Happy path (success)
- Each error category the handler can produce (auth, not_found, network, timeout, server)
- Config validation: missing field, wrong type, invalid URL, etc.
- Timeout enforcement (use fake timers or real short timeouts)
- **Taint-tracking test** (one per handler): inject sentinel into the secret value, force a failure that would naively include the value in the error message, assert sentinel is absent from every field of the returned `ProbeResult`. Sentinel string: `tamma-probe-taint-sentinel-${randomHex(16)}` — sufficiently unique that a `.includes()` check is conclusive.

**Rate Limiter Tests:**
- 10 rapid calls succeed
- 11th call returns `rate_limited` without invoking handler (assert handler spy not called)
- Bucket refills after 60s (fake timers)
- Independent buckets per `secretId`
- Configurable per-tenant cap enforced

**Integration Tests:**
- `pg-mem` for Postgres probes
- `ioredis-mock` for Redis probes
- `smtp-tester` or `nodemailer-mock` for SMTP
- `nock` or MSW for HTTP and GitHub
- Full workflow replay test: run `ProbeSecretWorkflow` against a mock broker, record activity outputs, replay, assert deterministic

**Security Tests (taint tracking, grouped in `probes/security.test.ts`):**
- Loop over every registered handler
- Inject the same sentinel secret into each
- Force a failure in each
- Assert sentinel never appears in `ProbeResult.errorMessage`, `ProbeResult.errorCategory`, or any other field — even after JSON serialization

### Risks and Mitigations

| Risk | Severity | Mitigation |
| ---- | -------- | ---------- |
| **Brute-force-via-probes**: a malicious or hallucinating LLM uses `probeSecret` as an oracle to brute-force token scopes, database schemas, etc. | **Critical** | Mandatory rate limiter (10/min default, 60/min ceiling). Audit event `SECRET.PROBED.*` on every attempt — alerting rule in 1.5-30 fires on >5 `PROBED.FAILED` in 5 min for a single secret. Taint-tracking test ensures plaintext never leaks in error messages even if the oracle is built from error-shape differentiation. |
| **Plaintext leakage in error messages**: DB drivers, HTTP libraries, and SMTP clients have been known to echo credentials in exceptions. | **High** | Double-layer redaction: `redactSensitiveKeys` (keyed) + literal-substring scan for the plaintext bytes. Dedicated taint-tracking test per handler. Buffer zeroing after handler returns. |
| **Probe handler hangs on a slow target**, consuming broker worker threads. | **High** | Mandatory `AbortController` / connection `destroy()` on timeout. Handler-level timeout (default 10s, ceiling 60s) + workflow-level timeout (hard cap 60s). Test: assert handler respects timeout with a deliberately-hanging mock target. |
| **Config injection**: user-supplied probe config targets an internal IP (SSRF) via `http_bearer`. | **High** | `validateConfig` for `http_bearer` rejects non-`https://` URLs in production, and rejects any URL whose hostname resolves to RFC1918, loopback, or link-local addresses. Allowlist-based: tenant config specifies which URLs are probeable for that tenant. |
| **Plaintext persists in memory** after handler completes (V8 string interning, etc.). | **Medium** | Use `Buffer` (not `string`) throughout the plaintext code path. Call `buf.fill(0)` in `finally` before the function returns. Document that V8 string interning is a known residual risk and is accepted for v1 (would require native code to fully mitigate). |
| **Third-party probe libraries add supply-chain risk.** | **Medium** | All probe dependencies (`pg`, `mysql2`, `ioredis`, `jsonwebtoken`, `nodemailer`) are already in the monorepo and already reviewed. No new production deps. |
| **Test flakiness from network mocks.** | **Low** | Use `pg-mem` / `ioredis-mock` / `msw` — all in-process, no real sockets. `smtp-tester` spins up a local process on a random port. |
| **Rate limiter state lost on broker restart** (DoS via repeated bouncing). | **Low** | Accepted for v1. Follow-up story 1.5-27.1 will add a Redis-backed distributed limiter when we go multi-broker. |

### What's NOT in This Story

- **Custom / plugin probe types** — the registry supports dynamic registration, but the plugin loading infrastructure (sandboxing, signing, config schema validation) is a separate story
- **Remote-worker probes** — probes that run on a tenant-owned GitHub Actions runner instead of the broker. This would be needed to probe secrets against tenant-private networks. Follow-up.
- **Tamma-specific `tamma_api_key` probe type** — circular dependency (requires a dedicated internal validation endpoint in the Tamma API). Follow-up once that endpoint exists.
- **Distributed rate limiter** — in-memory per-process only in v1. Redis-backed follow-up: 1.5-27.1.
- **Probe scheduling / periodic health checks** — this story implements on-demand probes only. Scheduled health checks are the job of a separate Elsa workflow (1.5-29 `SecretHealthCheckWorkflow`).
- **Probe result caching** — every `probeSecret` call actually hits the target. Caching could be added later but would weaken the freshness guarantee that is the whole point of an active probe.

## Logging Requirements

Infrastructure and deployment components MUST use structured logging via pino/ILogger (never `console.log` in production code).

- **INFO**: Probe dispatched (`secretId`, `probeType`), probe succeeded (`durationMs`), rate-limit bucket refilled
- **DEBUG**: Handler selected, config validated, timeout value applied, buffer zeroed
- **WARN**: Probe returned failure (`errorCategory`), rate-limit exceeded for a secret, probe exceeded soft-timeout but completed before hard cap, taint-scan replaced bytes in error message (indicates a latent leak in a dependency — must be investigated)
- **ERROR**: Handler threw unexpected exception, config validation crashed, rate limiter state corrupted, plaintext decryption failed
- **Structured context**: Always include `{ secretId, tenantId, probeType, durationMs }`. NEVER log `plaintext`, `value`, or any field from the probe config that might echo a credential. Error messages are logged only AFTER passing through `sanitizeProbeResult()`.
- **Credential safety**: Plaintext buffers are zeroed in `finally` blocks; log statements must reference `secretId` only, never the buffer contents. The taint-tracking test suite covers log capture as well as return values.
- **Audit events**: `SECRET.PROBED.SUCCESS` / `SECRET.PROBED.FAILED` are the canonical record — log lines are for debugging only and can be sampled.
