# Story 1.5-18: Secret Activities — Elsa C# wrappers over the secret broker HTTP API

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / LLM Safety)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-16 (interface + crypto primitives), Story 1.5-17 (broker HTTP service)

## Context — Why this story exists

Stories 1.5-16 and 1.5-17 stood up `packages/secret-broker/` as a
stand-alone TypeScript HTTP service that implements `ISecretStore`. Every
secret operation the broker exposes lives at `POST /internal/secrets/*`
and is authenticated via `TAMMA_BROKER_API_KEY`. That service is only
useful if the orchestration layer can actually call it.

Tamma's orchestrator is an Elsa Workflows instance running in the
`apps/tamma-elsa/` .NET solution. Elsa workflows are authored in C#
(or in the visual Studio designer) and composed of **activities** —
reusable, replay-safe steps that accept typed inputs, do some work, and
write typed outputs back to workflow variables. All of Tamma's existing
orchestration (LLM calls, code review, TDD loop, context assembly,
diagnostic queues, MCP tool invocation, security scans) is built from
activities under `apps/tamma-elsa/src/Tamma.Activities/`.

This story adds the **C# activity wrappers** that let Elsa workflows
perform secret operations. Each activity is deliberately thin: it takes
inputs, makes one authenticated HTTP call to the broker, deserializes the
typed response, writes outputs to the workflow context, emits one audit
event via `IEventStore`, and returns. No business logic lives in the
activity — the business logic is in the workflows themselves (Story
1.5-19) and in the broker (Story 1.5-17).

The activities defined here are the primitives that Story 1.5-19's
`CreateSecretWorkflow`, `RotateSecretWorkflow`, and `RevokeSecretWorkflow`
compose into end-to-end flows. They are also the primitives that every
follow-on secret-management workflow (Stories 1.5-27 probe, 1.5-28 leak
scan, 1.5-30 rotation cascade) will reuse.

### Architecture summary

```
  LLM tool call (via MCP)
        │
        ▼
  Orchestrator TS layer (Story 1.5-19)
        │  starts a workflow, returns WorkflowStatus
        ▼
  Elsa workflow (Story 1.5-19)
        │  composes activities
        ▼
  Secret Activities  ← THIS STORY
        │  HTTP POST with Bearer TAMMA_BROKER_API_KEY
        ▼
  Secret broker HTTP service (Story 1.5-17)
        │
        ▼
  TammaVaultStore → Postgres
```

Every activity calls exactly one broker endpoint. A shared
`HttpBrokerClient` helper class centralises auth header injection, JSON
serialization, HTTP error translation, and response deserialization so
each activity body stays ≤ 30 lines of meaningful code.

Elsa replay tests (exercised against every activity in this story) assert
that re-running a suspended workflow from a saved state yields identical
outputs without re-triggering the HTTP side effect — that's the whole
reason Elsa demands activities be idempotent or at least side-effect-free
on replay. We get this correctly by making activities **read-from-context
on replay** rather than re-calling the broker.

## User Story

As a **workflow author building secret-management flows in Elsa**,
I want **a set of typed C# activities that wrap every `ISecretStore` method**,
so that **workflows can create, rotate, verify, revoke, list, and mirror
secrets by composing activities in the Elsa designer or in C# code, with
every call emitting an audit event and every replay producing the same
outputs from the saved workflow state.**

## Acceptance Criteria

### AC1: `HttpBrokerClient` helper class

- [ ] A class `HttpBrokerClient` exists at
      `apps/tamma-elsa/src/Tamma.Activities/Security/HttpBrokerClient.cs`.
- [ ] Constructor: `HttpBrokerClient(IHttpClientFactory factory, IOptions<BrokerOptions> options, ILogger<HttpBrokerClient> logger)`.
      No `new HttpClient()` anywhere — use `IHttpClientFactory` so
      connection pooling and socket reuse work correctly.
- [ ] `BrokerOptions` is bound from configuration with these fields:
  - `BaseUrl` — default `http://127.0.0.1:3200`
  - `ApiKey` — required; the value of `TAMMA_BROKER_API_KEY`
  - `TimeoutMs` — default `5000`
  - `MaxRetries` — default `3`
- [ ] `HttpBrokerClient` fails fast at startup if `ApiKey` is null or
      empty when `ASPNETCORE_ENVIRONMENT=Production`. In Development it
      logs a WARN and uses a deterministic dev-only key
      (`dev-broker-key-do-not-use-in-prod`) so local `dotnet test` runs
      without operator setup.
- [ ] The client exposes one generic method:
      ```csharp
      Task<TResponse> PostAsync<TRequest, TResponse>(
          string path,
          TRequest request,
          CancellationToken ct);
      ```
- [ ] `PostAsync` behaviour:
  1. Prepends `BaseUrl` to `path` (`path` must start with `/internal/`).
  2. Sets `Authorization: Bearer {ApiKey}`.
  3. Serializes `request` to JSON using `System.Text.Json` with
     `PropertyNamingPolicy = JsonNamingPolicy.CamelCase` to match the
     broker's Fastify conventions.
  4. On non-2xx response, throws a typed `BrokerHttpException(statusCode, body)`.
  5. On network error / timeout, retries up to `MaxRetries` with
     exponential backoff (100ms, 400ms, 1600ms) for 5xx and connect errors
     only. Never retries on 4xx — those are caller errors.
  6. Deserializes the response body to `TResponse`.
- [ ] `BrokerHttpException` carries `StatusCode`, the response body as a
      redacted string (pass through `RedactSecrets` helper — no bearer
      token, no ciphertext, no commitment hash beyond its first 8 chars),
      and a bool `Retryable` computed from the status code.
- [ ] Unit tests using `Microsoft.AspNetCore.TestHost` + a mock handler:
  - Happy path: 200 response is deserialized correctly
  - 4xx: no retry, throws `BrokerHttpException` with `Retryable=false`
  - 5xx: retries the configured number of times, then throws
  - Network timeout: retries, then throws
  - Missing ApiKey in Production: constructor throws at DI resolution

### AC2: Typed request / response DTOs

- [ ] All broker DTOs live in
      `apps/tamma-elsa/src/Tamma.Activities/Security/BrokerModels.cs`.
- [ ] The following C# types exist and match the TypeScript types from
      `packages/platforms/src/secret-store.ts` (Story 1.5-16) field-for-field:
  - `SecretScope` (discriminated union modeled as a sealed record
    hierarchy: `RepoScope`, `OrgScope`, `ProjectScope`, `EnvironmentScope`,
    `TenantRootScope`, all deriving from `SecretScope`, with a `Kind`
    discriminator for JSON (de)serialization)
  - `SecretType` enum: `Password`, `ApiKey`, `JwtSigningKey`, `TlsCert`,
    `SshKey`, `Arbitrary`
  - `SecretStatus` enum: `Active`, `Rotating`, `Revoked`, `NotFound`
  - `SecretStoreMode` enum: `PlatformOnly`, `VaultCopy`, `VaultOnly`
  - `VerificationLevel` enum: `VaultValue`, `Metadata`, `Unavailable`
  - `ProbeType` enum: `HttpBearer`, `DatabaseConnect`, `JwtSignVerify`,
    `SmtpAuth`, `GithubToken`
  - `CreateSecretInput`, `CreatedSecret`, `VerifyResult`,
    `RotationResult`, `SecretMetadata`, `ProbeResult`, `DeployTarget`,
    `WorkflowStatus<T>`
- [ ] A custom `SecretScopeJsonConverter` handles the discriminated-union
      (de)serialization so the JSON shape matches what the broker's
      Fastify routes expect (`{kind: "repo", platform: "github", owner, repo}`).
- [ ] Enum values serialize as `snake_case` strings (not integers and not
      PascalCase) to match the broker's `System.Text.Json`
      `JsonStringEnumConverter` output. Round-trip tests prove that
      every enum value survives serialize → deserialize unchanged.
- [ ] A dedicated `BrokerModelCompatTest` parses canonical JSON fixtures
      (captured from the broker via `curl` during Story 1.5-17 smoke
      testing, stored under `apps/tamma-elsa/tests/Tamma.Activities.Tests/Fixtures/broker/`)
      into the C# DTOs and asserts no fields are dropped. If the broker
      ever adds a field, this test fails and tells the author to update
      the DTO.

### AC3: Eleven activities, one per broker endpoint

All activities live under
`apps/tamma-elsa/src/Tamma.Activities/Security/` and inherit from Elsa's
`CodeActivity<TOutput>` or `Activity` base class following the pattern of
existing activities (`apps/tamma-elsa/src/Tamma.Activities/LlmCall/*`,
`apps/tamma-elsa/src/Tamma.Activities/Security/*`, etc.).

For each of the activities listed below:

- [ ] The activity has an `[Activity(Category = "Tamma/Security", DisplayName = "...", Description = "...")]` attribute
- [ ] Inputs use `Input<T>` typed fields with `[Input]` attributes and
      human-readable names, as required by the Elsa designer
- [ ] Outputs use `Variable<T>` or `Output<T>` written to the workflow
      context via `context.Set(...)` and `context.SetResult(...)`
- [ ] Every activity injects `HttpBrokerClient` and `IEventStore` via the
      standard Elsa DI pattern (constructor or `[Inject]`) — same as
      existing activities like `LlmCallActivity`
- [ ] Every activity wraps the broker call in a `try/catch BrokerHttpException`
      and on non-retryable failures calls `context.FaultAsync(code, message)`
      (NOT `context.CancelAsync` — workflows must remain replayable and
      must not be cancelled on business failures)
- [ ] Every activity emits **one** audit event via `IEventStore.AppendAsync`
      using the event names defined in Story 1.5-16 AC4
- [ ] Every activity has an XML doc comment linking to Story 1.5-16 and
      1.5-17 and describing the preconditions / postconditions

**The eleven activities:**

- [ ] `CreateSecretActivity.cs`
  - Inputs: `Input<SecretScope> Scope`, `Input<string> Name`,
    `Input<SecretType> Type`, `Input<int?> Length`, `Input<string?> ExpiresAt`,
    `Input<SecretStoreMode?> ModeOverride`, `Input<string> TenantId`
  - Endpoint: `POST /internal/secrets/create`
  - Output: `CreatedSecret` bound to `context.SetResult(...)`
  - Audit event: `SECRET.CREATED.SUCCESS` or `SECRET.CREATED.FAILED`
  - Compensation: none (the broker's `createSecret` is atomic)

- [ ] `RotateSecretActivity.cs`
  - Inputs: `Input<string> SecretId`, `Input<string> TenantId`
  - Endpoint: `POST /internal/secrets/rotate`
  - Output: `RotationResult`
  - Audit event: `SECRET.ROTATED.SUCCESS` or `SECRET.ROTATED.FAILED`

- [ ] `VerifySecretActivity.cs`
  - Inputs: `Input<string> SecretId`, `Input<string> ExpectedCommitmentHash`,
    `Input<string> TenantId`
  - Endpoint: `POST /internal/secrets/verify`
  - Output: `VerifyResult`
  - Audit event: `SECRET.VERIFIED.MATCH` or `SECRET.VERIFIED.MISMATCH`
    (selected from the `matches` field of the response)

- [ ] `RevokeSecretActivity.cs`
  - Inputs: `Input<string> SecretId`, `Input<string> Reason`, `Input<string> TenantId`
  - Endpoint: `POST /internal/secrets/revoke`
  - Output: `{RevokedAt: string}` as a typed record
  - Audit event: `SECRET.REVOKED.SUCCESS` or `SECRET.REVOKED.FAILED`

- [ ] `GetSecretMetadataActivity.cs`
  - Inputs: `Input<string> SecretId`, `Input<string> TenantId`
  - Endpoint: `POST /internal/secrets/get-metadata`
  - Output: `SecretMetadata?` (null if the broker returned `{metadata: null}`)
  - Audit event: `SECRET.LISTED` with `secretId` in the tags (this is a
    read operation; reuses the `LISTED` event name to keep the event
    vocabulary compact)

- [ ] `ListSecretsActivity.cs`
  - Inputs: `Input<SecretScope> Scope`, `Input<string> TenantId`,
    `Input<int?> Limit`, `Input<string?> Cursor`
  - Endpoint: `POST /internal/secrets/list`
  - Output: `{Secrets: SecretMetadata[], NextCursor: string?}`
  - Audit event: `SECRET.LISTED`
  - The activity MUST validate that the caller-supplied `Limit` is within
    `[1, 1000]` and defaults to 100 if null — same constraint as the broker,
    fail loudly at the activity boundary rather than leaking to the broker.

- [ ] `FindSecretsByFingerprintActivity.cs`
  - Inputs: `Input<string> Fingerprint`, `Input<string> TenantId`
  - Endpoint: `POST /internal/secrets/find-by-fingerprint`
  - Output: `{Secrets: SecretMetadata[]}`
  - Audit event: `SECRET.LISTED` with `fingerprint` (first 4 chars only)
    in the tags
  - This activity is called by the leak-detection workflow (Story 1.5-28).
    A unit test asserts that the full 12-char fingerprint is NEVER written
    to the audit event payload — only the first 4 chars for correlation.

- [ ] `IsDeployedActivity.cs`
  - Inputs: `Input<string> SecretId`, `Input<string> TenantId`
  - Endpoint: `POST /internal/secrets/is-deployed`
  - Output: `bool`
  - Audit event: none (this is a pure read used in decision branches; the
    broker emits no event for it either)

- [ ] `IsDeployedAtActivity.cs`
  - Inputs: `Input<string> SecretId`, `Input<DeployTarget> Target`,
    `Input<string> TenantId`
  - Endpoint: `POST /internal/secrets/is-deployed-at`
  - Output: `{Present: bool, LastSyncAt: string?, SyncStatus: string?}`
  - Audit event: none

- [ ] `MirrorSecretToActivity.cs`
  - Inputs: `Input<string> SecretId`, `Input<DeployTarget> Target`,
    `Input<string> TenantId`
  - Endpoint: `POST /internal/secrets/mirror-to`
  - Output: `{SyncedAt: string}`
  - Audit event: `SECRET.DEPLOYED.SUCCESS` or `SECRET.DEPLOYED.FAILED`

- [ ] `ProbeSecretActivity.cs`
  - Inputs: `Input<string> SecretId`, `Input<ProbeType> ProbeType`,
    `Input<Dictionary<string,object>?> ProbeConfig`, `Input<string> TenantId`
  - Endpoint: `POST /internal/secrets/probe`
  - Output: `ProbeResult`
  - Audit event: `SECRET.PROBED.SUCCESS` (when `success=true`) or
    `SECRET.PROBED.FAILED`
  - The activity asserts that `ProbeResult.ErrorMessage` never contains
    the substring of any input value (taint-tracking check — even though
    the broker is responsible for redaction, the activity double-checks
    at the trust boundary)

### AC4: Audit event emission is consistent across all activities

- [ ] A shared helper `SecretAuditEventEmitter` exists at
      `apps/tamma-elsa/src/Tamma.Activities/Security/SecretAuditEventEmitter.cs`
      that centralises audit event construction:
      ```csharp
      Task EmitAsync(
          IEventStore store,
          string eventType,
          string tenantId,
          string? secretId,
          string actor,
          int rootKeyVersion,
          Dictionary<string, object>? data = null);
      ```
- [ ] The emitter builds the event with these mandatory tags:
      `{tenantId, secretId?, actor, rootKeyVersion}` — matching Story
      1.5-16 AC4.
- [ ] The emitter's `data` field NEVER contains the raw secret value,
      encrypted blob, or commitment hash beyond its first 8 characters
      (for correlation). A unit test injects a known plaintext into the
      `data` field and asserts the serialized JSON does not contain it.
- [ ] Event `type` must be one of the constants enumerated in
      `packages/platforms/src/secret-store-events.ts` from Story 1.5-16 AC4.
      A unit test uses reflection (or a hand-maintained copy) to assert
      that every string literal passed to `EmitAsync` from every activity
      is in the allow-list.
- [ ] The `actor` field is derived from the workflow context's
      `executionContext.WorkflowDefinitionId + ":" + workflowInstanceId`
      — the orchestrator treats every Elsa-originated event as a service
      actor, not a user actor. Human user IDs are carried via the
      workflow input payload when available and added as an additional
      tag `initiatingUserId`.

### AC5: Workflow replay tests for every activity

**This is a hard acceptance criterion.** Elsa workflows are durable and
replay saved state on worker restart. An activity that's not
replay-safe will cause a silent rerun of its HTTP side effect on every
resume — a catastrophic failure mode for secret operations (imagine
`createSecret` firing twice).

- [ ] Each activity has a dedicated replay test at
      `apps/tamma-elsa/tests/Tamma.Activities.Tests/Security/{ActivityName}ReplayTests.cs`.
- [ ] Each replay test follows this pattern:
  1. Build a tiny workflow containing exactly the activity under test
     as its only step
  2. Register a `MockHttpBrokerClient` that records every call and
     returns a canned response
  3. Execute the workflow to completion (call #1 hits the mock)
  4. Serialize the full workflow state (Elsa's `WorkflowState` snapshot)
  5. Instantiate a fresh workflow host, deserialize the state,
     and resume the workflow from the terminal state
  6. Assert: (a) the workflow completes with the same outputs, (b) the
     mock recorded exactly ONE call, (c) no new audit events were emitted
     on replay
- [ ] A shared `MockHttpBrokerClient` test helper lives at
      `apps/tamma-elsa/tests/Tamma.Activities.Tests/TestSupport/MockHttpBrokerClient.cs`.
      It implements the same public surface as `HttpBrokerClient` but
      routes calls to an in-memory dictionary keyed by `(path, requestJson)`
      and records call counts for replay assertions.
- [ ] A parameterised replay test covers the failure path: activity runs,
      broker returns 500, activity faults, workflow state saves the fault,
      replay resumes, workflow remains faulted with no additional retries.
      This is the critical "replay does not re-execute HTTP" guarantee.
- [ ] The replay test suite runs as part of `dotnet test` in the
      `apps/tamma-elsa/tests/Tamma.Activities.Tests/` project and is
      wired into `.github/workflows/elsa-ci.yml`. A failing replay test
      fails the PR.

### AC6: Error propagation — failures are activity faults, not workflow cancellations

- [ ] When `HttpBrokerClient.PostAsync` throws `BrokerHttpException`, the
      activity catches it and calls
      `context.FaultAsync("SECRET.ACTIVITY.BROKER_ERROR", ex.Message)`.
      This surfaces the error as a **retryable activity fault** in Elsa's
      state machine — NOT as a workflow-level cancellation.
- [ ] A unit test asserts that after a simulated broker 500 error:
  - The workflow enters the `Faulted` state (not `Cancelled`)
  - A subsequent call to `workflow.ResumeAsync()` re-invokes the activity
  - A manual `workflow.CancelAsync()` is still the only way to move to
    `Cancelled`
- [ ] `BrokerHttpException.Retryable=true` (5xx / network) results in an
      activity fault with a retry hint. `Retryable=false` (4xx) results
      in an activity fault with `retryAfter=null` — Elsa's outer retry
      policy knows not to retry.
- [ ] 401 from the broker (bad or missing API key) is classified as
      **non-retryable** (no amount of retrying will fix auth). The activity
      faults with a specific code `SECRET.ACTIVITY.AUTH_FAILED` so the
      orchestrator's alert handler can page an operator.

- [ ] A fixture-level test verifies:

## Dev Notes

### Requirements Context Summary

**Epic Context**: Story 1.5-16 defined the `ISecretStore` interface and the
LLM-safe commitment hash protocol. Story 1.5-17 delivered the
TypeScript-side broker — a Fastify HTTP service backed by Postgres that
implements every `ISecretStore` method under `/internal/secrets/*`. This
story bridges from the C# Elsa orchestrator to that broker service,
providing the activity primitives that Story 1.5-19's workflows compose
into `CreateSecretWorkflow`, `RotateSecretWorkflow`, and
`RevokeSecretWorkflow`.

**Technical Context**: The Elsa orchestrator runs in a separate .NET
process from the TypeScript API and broker. It already has a mature
activity registry pattern (`apps/tamma-elsa/src/Tamma.Activities/LlmCall/*`,
`Review/*`, `Context/*`, etc.). This story adds a new `Security/`
activity family following the same conventions: typed `Input<T>` / `Output<T>`,
DI-injected dependencies, XML doc comments, Elsa `[Activity]` attribute,
consistent audit event emission.

**Integration Points**:
- **Broker HTTP service** (Story 1.5-17): every activity is a thin
  wrapper over one `/internal/secrets/*` call. Auth via
  `TAMMA_BROKER_API_KEY` bearer token.
- **Event store** (Epic 4 / existing Elsa `IEventStore` DI): audit
  events flow into the same DCB stream used by the rest of the platform.
- **Elsa workflow engine**: activities must be replay-safe. The failure
  mode this story guards against is "workflow resumes, activity re-runs,
  broker sees a duplicate `createSecret` call." The mechanism is: on
  replay, Elsa supplies the previously-captured result from workflow
  state and the activity short-circuits without calling the broker again.
  This is the standard Elsa pattern and the replay tests in AC5 verify it.
- **Story 1.5-19** (consumer): the workflows in that story are built
  entirely from these activities. If an activity has the wrong signature
  or wrong behaviour on replay, 1.5-19 has to be rewritten.

### Key Design Decisions

1. **Activities are thin HTTP wrappers, not independent implementations.**
   The broker is the single source of truth for how secret operations
   work. Duplicating any logic (scope validation, mode resolution,
   HKDF derivation) in the C# side would be a drift risk. If the broker
   changes its behaviour, every activity must re-derive the same new
   behaviour — that's a bad pattern. Instead, the activity does nothing
   but serialize inputs, make the HTTP call, deserialize the output,
   and write it to workflow state. All business logic lives on the
   broker side.

2. **One `HttpBrokerClient` class, shared by all activities.** Centralising
   auth, serialization, and retry logic in one place means a change
   (add a new retry code, rotate the API key mechanism, switch to mTLS
   later) touches one file instead of eleven. The activities have no
   direct knowledge of `HttpClient` or JSON serialization — they call
   `_client.PostAsync<Req, Resp>("/internal/secrets/create", req, ct)`
   and that's it.

3. **`BrokerHttpException` is a fault, not a cancellation.** Elsa
   distinguishes between activity faults (recoverable, resumable) and
   workflow cancellations (terminal, non-resumable). A broker 500 is
   recoverable — the operator can fix the broker and resume the
   workflow. A broker 401 is also recoverable *in principle* (fix the
   key, restart), though in practice an operator will probably cancel
   and restart. Crucially: we never turn HTTP errors into
   `context.CancelAsync` because that would lose the workflow state
   and make the failure non-resumable. The replay tests verify this
   behaviour explicitly.

4. **Replay tests are mandatory and non-negotiable.** Elsa's
   durability model re-executes activities from saved state on worker
   restart. If a `CreateSecret` activity runs, the worker restarts, and
   the activity re-runs — the broker will receive two create-secret
   calls, possibly with the same name, possibly creating a duplicate
   secret. The first call's `secretId` is lost. This is a
   data-integrity catastrophe. Elsa's replay-safety contract is: on
   resume, activities read their previous result from workflow state
   instead of re-executing. The replay tests in AC5 verify this
   contract holds for every one of our eleven activities. A missing
   replay test is blocker-severity.

5. **`MockHttpBrokerClient` and `MockBrokerFixture` serve different
   purposes.** The former is for replay tests — it's a pure C# class
   with no HTTP, no Kestrel, no sockets. It lets replay tests run in
   tens of milliseconds and assert exact call counts. The latter is
   for activity integration tests that exercise the full `HttpClient`
   path — serialization, headers, retry logic — by actually running
   a local HTTP server. Both are needed; neither is a replacement for
   the other.

6. **Audit events go through a single emitter.** Eleven activities
   writing events directly to `IEventStore` means eleven places to
   update when we rename an event or add a tag. The
   `SecretAuditEventEmitter` centralises this and enforces the
   allow-list of event types from Story 1.5-16 AC4. If a reviewer
   sees a new activity with a call to `_eventStore.AppendAsync(...)`
   that bypasses the emitter, that's a review comment.

7. **DTOs match the TypeScript broker field-for-field.** We do NOT
   rename fields to C# conventions (e.g. `commitmentHash` → `CommitmentHash`
   with `[JsonPropertyName]`). Instead we rely on
   `JsonNamingPolicy.CamelCase` so C# code reads naturally
   (`result.CommitmentHash`) but wire format stays camelCase. The
   `BrokerModelCompatTest` guards against drift — if the broker adds
   a field and the C# DTO doesn't have it, the test fails with a
   clear message pointing at the offending fixture file.

### Technical Specifications — `HttpBrokerClient` outline

```csharp
// apps/tamma-elsa/src/Tamma.Activities/Security/HttpBrokerClient.cs

public sealed class HttpBrokerClient
{
    private readonly HttpClient _http;
    private readonly BrokerOptions _options;
    private readonly ILogger<HttpBrokerClient> _logger;

    public HttpBrokerClient(
        HttpClient http,
        IOptions<BrokerOptions> options,
        ILogger<HttpBrokerClient> logger,
        IHostEnvironment env)
    {
        _options = options.Value;
        if (string.IsNullOrEmpty(_options.ApiKey))
        {
            if (env.IsProduction())
            {
                throw new InvalidOperationException(
                    "TAMMA_BROKER_API_KEY is required in Production. " +
                    "Refusing to start with a dev key.");
            }
            _logger.LogWarning(
                "DEV MODE: Tamma.Broker.ApiKey is missing. Using dev-only key. " +
                "NEVER deploy to production without setting TAMMA_BROKER_API_KEY.");
            _options.ApiKey = "dev-broker-key-do-not-use-in-prod";
        }
        _http = http;
        _http.BaseAddress = new Uri(_options.BaseUrl);
        _http.Timeout = TimeSpan.FromMilliseconds(_options.TimeoutMs);
        _logger = logger;
    }

    public async Task<TResponse> PostAsync<TRequest, TResponse>(
        string path,
        TRequest request,
        CancellationToken ct)
    {
        if (!path.StartsWith("/internal/"))
            throw new ArgumentException("broker path must start with /internal/", nameof(path));

        using var msg = new HttpRequestMessage(HttpMethod.Post, path);
        msg.Headers.Authorization = new AuthenticationHeaderValue("Bearer", _options.ApiKey);
        msg.Content = JsonContent.Create(request, options: JsonOpts);

        var resp = await _http.SendAsync(msg, ct);
        if (!resp.IsSuccessStatusCode)
        {
            var body = await resp.Content.ReadAsStringAsync(ct);
            var redacted = RedactSecrets.Apply(body);
            throw new BrokerHttpException((int)resp.StatusCode, redacted);
        }
        var result = await resp.Content.ReadFromJsonAsync<TResponse>(JsonOpts, ct);
        return result ?? throw new InvalidOperationException("broker returned null body");
    }

    private static readonly JsonSerializerOptions JsonOpts = new()
    {
        PropertyNamingPolicy = JsonNamingPolicy.CamelCase,
        Converters = { new JsonStringEnumConverter(JsonNamingPolicy.SnakeCaseLower),
                       new SecretScopeJsonConverter() }
    };
}
```

### Technical Specifications — Activity outline (CreateSecretActivity)

```csharp
// apps/tamma-elsa/src/Tamma.Activities/Security/CreateSecretActivity.cs

[Activity(
    Category = "Tamma/Security",
    DisplayName = "Create Secret",
    Description = "Creates a new secret via the Tamma secret broker. " +
                  "Never materialises plaintext in the workflow process.")]
public sealed class CreateSecretActivity : CodeActivity<CreatedSecret>
{
    private readonly HttpBrokerClient _broker;
    private readonly SecretAuditEventEmitter _audit;

    public CreateSecretActivity(HttpBrokerClient broker, SecretAuditEventEmitter audit)
    {
        _broker = broker;
        _audit = audit;
    }

    [Input] public Input<SecretScope> Scope { get; set; } = default!;
    [Input] public Input<string> Name { get; set; } = default!;
    [Input] public Input<SecretType> Type { get; set; } = default!;
    [Input] public Input<int?> Length { get; set; } = default!;
    [Input] public Input<SecretStoreMode?> ModeOverride { get; set; } = default!;
    [Input] public Input<string> TenantId { get; set; } = default!;

    protected override async ValueTask ExecuteAsync(ActivityExecutionContext context)
    {
        var req = new CreateSecretRequest {
            Scope = Scope.Get(context),
            Name = Name.Get(context),
            Type = Type.Get(context),
            Length = Length.Get(context),
            ModeOverride = ModeOverride.Get(context),
            TenantId = TenantId.Get(context),
        };
        try
        {
            var resp = await _broker.PostAsync<CreateSecretRequest, CreatedSecret>(
                "/internal/secrets/create", req, context.CancellationToken);
            context.SetResult(resp);
            await _audit.EmitAsync(
                context.GetRequiredService<IEventStore>(),
                "SECRET.CREATED.SUCCESS",
                req.TenantId, resp.SecretId,
                actor: context.WorkflowInstanceActor(),
                rootKeyVersion: resp.RootKeyVersion,
                data: new() { ["mode"] = resp.Mode.ToString() });
        }
        catch (BrokerHttpException ex)
        {
            var code = ex.StatusCode == 401
                ? "SECRET.ACTIVITY.AUTH_FAILED"
                : "SECRET.ACTIVITY.BROKER_ERROR";
            await _audit.EmitAsync(
                context.GetRequiredService<IEventStore>(),
                "SECRET.CREATED.FAILED",
                req.TenantId, secretId: null,
                actor: context.WorkflowInstanceActor(),
                rootKeyVersion: 0,
                data: new() { ["status"] = ex.StatusCode, ["code"] = code });
            await context.FaultAsync(code, ex.Message);
        }
    }
}
```

### Testing Strategy

- **Unit tests** for `HttpBrokerClient`:
  - Happy path deserialization
  - 401 → non-retryable fault
  - 5xx → retry with exponential backoff, then throw
  - Network timeout → retry, then throw
  - Missing API key in Production → DI throws at startup
- **Unit tests** for each activity:
  - Happy path: input mapped to request, response mapped to context,
    audit event emitted once
  - Failure path: broker 500 → `FaultAsync` called, workflow remains
    `Faulted`, one `*.FAILED` audit event emitted, zero `*.SUCCESS` events
  - Input validation: invalid inputs (e.g. `Limit=-1` on `ListSecrets`)
    throw before touching the broker
- **Replay tests** (AC5 — hardest):
  - One per activity, built on the `ReplayTestHarness`
  - Each asserts: call count = 1 after resume, outputs identical, no
    extra audit events on resume
- **DTO compatibility test**:
  - Load every JSON fixture in `Fixtures/broker/`
  - Deserialize into the C# DTO
  - Re-serialize to JSON
  - Assert bytewise equality (or semantic equality via a JSON diff tool)
  - Fails with a pointer to the offending fixture if new broker fields
    aren't mirrored
- **Taint-tracking tests**:
  - Inject a known 32-char plaintext into a simulated `ProbeSecret`
    failure path
  - Serialize the resulting audit event and `ProbeResult`
  - Assert the plaintext bytes do not appear anywhere in the output
- **Integration-style tests** against `MockBrokerFixture`:
  - End-to-end through the real `HttpClient` to a local Kestrel server
  - Auth header verification, 401 rejection
  - One end-to-end smoke: Create → Verify → Rotate → Verify → Revoke
    (this is also implemented as the smoke workflow from AC10)

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Activity re-executes on replay, creating duplicate secrets | Critical | Mandatory replay tests (AC5) for every activity; `ReplayTestHarness` enforces call-count assertions; a failing replay test fails the PR |
| `TAMMA_BROKER_API_KEY` leaks to logs via exception messages | High | `RedactSecrets.Apply` on all error bodies; `BrokerHttpException.Message` is pre-redacted; a log-capture test asserts the key value never appears in stdout/stderr |
| DTO drift from broker causes silent field loss | Medium | `BrokerModelCompatTest` parses canonical fixtures captured from the real broker; any new broker field fails the test with a clear pointer |
| `FaultAsync` vs `CancelAsync` confusion turns recoverable errors into terminal ones | High | Explicit unit tests asserting workflow state is `Faulted` (not `Cancelled`) after broker errors; documented in the ADR; code review checklist item |
| Broker is down when workflow runs | Medium | Activity faults cleanly, workflow enters `Faulted` state, operator can resume once broker is back. Retry policy absorbs transient errors; persistent outages escalate via `alert_orchestrator` (Story 1.5-19) |
| Audit event type typo ships to prod | Medium | `SecretAuditEventEmitter` enforces an allow-list from Story 1.5-16 AC4; a unit test iterates every event string literal in the activity codebase and asserts it's in the list |
| Elsa DI registration order breaks at startup | Low | Integration test spins up `Tamma.ElsaServer` and asserts `/activity-registry` exposes all eleven activities |
