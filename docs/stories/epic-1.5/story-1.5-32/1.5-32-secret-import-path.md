# Story 1.5-32: Secret import path — TLS certs, SSH keys, and externally-generated credentials

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / Migration)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-17 (TammaVaultStore + broker HTTP service)

## Story

As a **Tamma operator migrating from an existing secret manager (1Password, AWS Secrets Manager, HashiCorp Vault, Doppler, plain `.env` files) or bringing in operator-generated TLS certificates and SSH keys**,
I want **a first-class import path that gets externally-generated plaintext into the broker without the LLM, the orchestrator, or the `@tamma/api` process ever seeing it**,
so that **I can onboard real secrets that Tamma's `generateSecretValue` refuses to produce (TLS certs, SSH keys, pre-existing passwords) and retire my old secret manager without writing glue code or pasting plaintext into Claude.**

## Context — Why this story exists

Story 1.5-16 defined `ISecretStore` and `generateSecretValue(type)`, which
covers `password`, `api_key`, `jwt_signing_key`, and `arbitrary`. Two types
are explicitly rejected:

- `tls_cert`: certificate issuance requires a CA, a CSR, or a pre-existing
  cert. Tamma is not a CA and won't become one.
- `ssh_key`: while Tamma could generate keypairs, users typically want
  specific key formats (ed25519 vs RSA, specific key-comment fields,
  FIDO-backed keys) and existing identity trails. Generating a new keypair
  just shifts the problem — the public half still needs to be distributed.

Story 1.5-16 says for these cases: "import externally." But no import
method exists. An operator with a folder full of `.pem` files and an old
secret manager has no path into Tamma's vault — and the LLM cannot help,
because the cardinal rule is **plaintext never crosses the LLM boundary**.

This story adds the missing path: a handle-based import flow where the
plaintext is delivered to the broker out-of-band (CLI, dashboard UI, or
OIDC-authenticated endpoint), the broker stores it in a short-lived handle
store, and any subsequent workflow step — including LLM-driven ones — can
reference the secret via the **handle**, never the plaintext.

### Architecture summary

```
┌──────────────┐   (1) uploads plaintext      ┌──────────────────┐
│ Operator CLI │ ───────────────────────────► │ secret-broker    │
│  / Web UI    │     POST /import/upload      │  HandleStore     │
│  / CI OIDC   │                              │ (Valkey-backed)  │
└──────────────┘ ◄─────────────────────────── │                  │
                     handle: "imp_abc123"     └──────────────────┘
                                                       │
                                                       ▼
┌──────────────┐   (2) import_secret(handle)  ┌──────────────────┐
│   LLM /      │ ───────────────────────────► │ TammaVaultStore  │
│  workflow    │                              │ .importSecret()  │
└──────────────┘                              │  consumes handle │
                                              │  → encrypts      │
                                              │  → stores        │
                                              └──────────────────┘
```

Handles are opaque strings (`imp_` + 32 hex chars) that index plaintext
held in an ephemeral store with strict TTL (5 minutes, no extension).
Each handle is **single-use**: the first `importSecret(handle)` call
consumes and zeroises the plaintext. A second call returns
`handle_consumed`. A handle that expires before consumption is zeroised
at expiry and the broker emits `SECRET.IMPORT_HANDLE.EXPIRED`.

The ephemeral store is Valkey-backed once Story 16-8 lands. Until then
this story ships with an **in-memory** handle store gated behind a clear
config flag (`secrets.import.handle_store: 'memory' | 'valkey'`) and a
boot-time warning if memory mode is used in production. Re-reading the
handle from disk is **not supported** — a broker restart zeroises all
pending handles and callers must re-upload.

## User Story

As a **Tamma platform engineer onboarding a repo with existing TLS certs, SSH deploy keys, and pre-generated database passwords**,
I want **to upload those secrets via `tamma vault import` from my laptop or a one-shot dashboard form, receive a handle, and have the workflow call `import_secret(handle)` to persist them**,
so that **I can migrate real production secrets into Tamma without writing code, without pasting plaintext to an LLM, and without a plaintext-over-wire path that bypasses the broker's trust boundary.**

## Acceptance Criteria

### AC1: `ISecretStore.importSecret` method added

- [ ] `ISecretStore` gains an `importSecret(input: ImportSecretInput): Promise<ImportSecretResult>` method.
- [ ] `ImportSecretInput` shape:
  ```typescript
  interface ImportSecretInput {
    scope: SecretScope;               // from Story 1.5-16
    name: string;
    type: SecretType;                 // 'tls_cert' | 'ssh_key' | 'password' | ...
    mode: SecretMode;                 // 'vault_only' | 'vault_copy' | 'platform_only'
    handle: string;                   // 'imp_<32hex>' from handle store
    actorId: string;                  // who authorised the import
    importSource: 'cli' | 'web_ui' | 'oidc_api';
    metadata?: Record<string, string>;
  }
  ```
- [ ] `ImportSecretResult` shape mirrors `createSecret`'s return: `secretId`, `commitmentHash`, `fingerprint`, `status: 'active'`.
- [ ] `TammaVaultStore.importSecret` is the first concrete implementation.
  Behaviour:
  1. Validates the handle exists in the handle store and has not expired.
  2. Consumes the handle (atomic `GETDEL` semantics — see AC2).
  3. Passes the plaintext to the existing encrypt path from Story 1.5-17.
  4. Writes the metadata row with `imported_at`, `import_source`, `import_actor_id` columns.
  5. Emits `SECRET.IMPORTED.SUCCESS` audit event on success, `SECRET.IMPORTED.FAILED` on any failure path, with `reason` field populated.
  6. Zeroises the plaintext buffer immediately after encryption.
- [ ] TypeScript strict mode compiles with zero errors including `exactOptionalPropertyTypes`.

### AC2: `HandleStore` abstraction with memory and Valkey implementations

- [ ] `HandleStore` interface at `packages/secret-broker/src/import/handle-store.ts`:
  ```typescript
  interface HandleStore {
    put(plaintext: Buffer, ttlMs: number): Promise<string>;    // returns handle
    consume(handle: string): Promise<Buffer | 'consumed' | 'expired' | 'not_found'>;
    revoke(handle: string): Promise<void>;
    stats(): Promise<{ active: number; total_issued: number }>;
  }
  ```
- [ ] `MemoryHandleStore` implementation holds handles in a `Map<string, { buf: Buffer; expiresAt: number }>` with a timer that sweeps expired entries every 10 seconds. Every sweep zeroises expired buffers via `buf.fill(0)` before removing them.
- [ ] `ValkeyHandleStore` implementation (landing alongside Story 16-8 but stubbed here behind `secrets.import.handle_store: 'valkey'` config; the stub throws `ValkeyHandleStoreNotYetAvailable` at boot if selected before 16-8 lands). When Valkey is available the store uses `SETEX` to put + `GETDEL` to atomically consume.
- [ ] `MemoryHandleStore.consume` is atomic with respect to concurrent `consume` calls on the same handle — second caller must receive `consumed`, not a duplicated buffer. Tested with a deterministic race via `Promise.all`.
- [ ] Handle identifier format: `imp_` + 32 hex chars (128 bits of entropy from `crypto.randomBytes(16)`). Handles are URL-safe and log-safe.
- [ ] TTL is **fixed at 5 minutes** for MVP. The put API accepts a TTL parameter but `ImportUploadController` rejects any value other than 300_000 ms. A config flag `secrets.import.max_handle_ttl_ms` can extend this in future; the AC locks it for now.
- [ ] Unit tests cover: put/consume happy path, consume-after-consume returns `consumed`, consume-after-expiry returns `expired`, concurrent consume races, memory sweep zeroises, `stats` counts correctly.

### AC3: Broker HTTP upload endpoint `POST /import/upload`

- [ ] Fastify route at `packages/secret-broker/src/routes/import-upload.ts`:
  `POST /import/upload` accepting `multipart/form-data` with a single `file` field.
- [ ] Authentication: same mTLS / service-token model used by other broker endpoints in Story 1.5-17. An operator-issued token with scope `secrets:import` is required.
- [ ] Request body limit: 1 MiB (configurable via `secrets.import.max_upload_bytes`). Larger files return 413.
- [ ] Server reads the file into a `Buffer`, calls `handleStore.put(buf, 300_000)`, and returns:
  ```json
  {
    "handle": "imp_abc123...",
    "expires_at": "2026-04-15T12:05:00.000Z",
    "bytes": 1847,
    "sha256_fingerprint": "e3b0c442..."
  }
  ```
- [ ] The response includes a `sha256_fingerprint` so the operator (and any downstream UI) can verify the bytes actually transferred match what was uploaded. The fingerprint is NOT the commitment hash from Story 1.5-16; it's a plain SHA-256 of the uploaded bytes, used as a transfer-integrity check only.
- [ ] Rate limit: 10 uploads per minute per token via Story 16-10's rate limiter (if landed) or in-process token-bucket fallback.
- [ ] Audit event on successful upload: `SECRET.IMPORT_HANDLE.ISSUED` with `actor_id`, `bytes`, `import_source`. The event NEVER contains the plaintext.
- [ ] Integration test: upload a file, receive handle, call `importSecret(handle)`, assert secret persists with expected `commitment_hash`.

### AC4: `tamma vault import` CLI command

- [ ] Command signature:
  ```
  tamma vault import \
      --file <path>                      # required: file on local disk
      --scope <scope>                    # e.g. repo:foo/bar, org:acme
      --name <SECRET_NAME>               # required
      --type <tls_cert|ssh_key|...>      # required
      --mode <vault_only|vault_copy|platform_only>  # default vault_only
      [--metadata key=value ...]
  ```
- [ ] The CLI reads the file locally, POSTs the bytes to `/import/upload` with the operator's auth token, receives the handle, then calls the broker's existing `/secrets/import` RPC with `{scope, name, type, mode, handle, actor_id: whoami, import_source: 'cli'}`.
- [ ] The CLI never writes plaintext to disk, never logs it, and `Buffer.fill(0)`s the local buffer before exit.
- [ ] If the `--file` argument points at a symlink, the CLI resolves it with `fs.realpath` and emits a warning. If the resolved path points outside the current working directory, the CLI refuses unless `--allow-outside-cwd` is passed.
- [ ] CLI exits non-zero on: upload failure, auth failure, handle expiry (should not happen on fast CLI paths), import failure at the broker.
- [ ] Documentation updated in `packages/cli/README.md` under a new "Importing existing secrets" section.

### AC5: Dashboard web-UI upload form (stub)

- [ ] A page at `/settings/secrets/import` in `apps/dashboard/` (or `packages/dashboard/`, whichever is canonical) with:
  - Scope picker (reuses existing scope selector from secret management UI)
  - Name + type + mode form fields
  - File picker (`<input type="file">`)
  - Submit button
- [ ] On submit, the browser POSTs the file to `/api/v1/secrets/import-upload-proxy` — a thin pass-through in `@tamma/api` that forwards to the broker's `/import/upload` on behalf of the logged-in dashboard user. **The API does NOT read the file bytes into its own memory**: it streams the multipart body directly to the broker using `undici`'s streaming upload. The API never has plaintext in a `Buffer`, only in a transient stream.
- [ ] **Owner-only access**: the UI route and the proxy endpoint both require the caller to have the `owner` or `secret_admin` role on the current tenant (from Story 16-5 RBAC). Non-owners get a 403 with a clear message.
- [ ] The UI is wired in this story but polish, accessibility review, and production-UX work live in Story 1.5-39 (dashboard secret management — future work). This story ships a functional stub, not a designed surface.
- [ ] Integration test: Playwright or Vitest + supertest drives a full upload-then-import flow through the dashboard → api proxy → broker chain.

### AC6: OIDC-authenticated import endpoint for CI runners

- [ ] A second upload path `POST /import/upload-oidc` that accepts an OIDC token (GitHub Actions, GitLab CI, Buildkite) instead of a service token.
- [ ] OIDC token validation reuses Story 1.5-20's `OidcValidator`. The token's `sub` claim is required to match an entry in `secrets.import.oidc_allowlist` in the broker config: a list of `{issuer, repository, ref_pattern}` tuples.
- [ ] This endpoint is for CI-driven migration scripts: "run a one-shot GitHub Action that reads every secret from the old manager and POSTs it to `/import/upload-oidc`". The operator must explicitly enable OIDC import per tenant (`secrets.import.oidc_enabled: true`); it is OFF by default.
- [ ] Audit event `SECRET.IMPORT_HANDLE.ISSUED` includes `actor_type: 'oidc'` and `oidc_sub`, `oidc_issuer`, `oidc_repository` claims.
- [ ] Rate limit is stricter than the operator-token path: 5 uploads per minute per `oidc_sub`.
- [ ] Integration test uses a self-signed JWT with a mocked JWKS endpoint (same pattern Story 1.5-20 establishes).

    ADD COLUMN import_actor_id  TEXT;

- [ ] The `TammaVaultStore.importSecret` path populates these three columns. The `createSecret` path leaves them NULL (a secret generated by Tamma was not imported).
- [ ] `GET /secrets/:id/metadata` includes imported-secret fields in the response when present.

### AC8: Taint tracking across the upload + import path

- [ ] Taint-tracking tests assert plaintext never appears in:
  - `POST /import/upload` response body (only handle + fingerprint)
  - Broker logs during upload and import
  - `@tamma/api` logs during dashboard proxy uploads
  - The handle-store's `stats()` output
  - Audit event payloads for any of the six new event types
- [ ] A property-based test using `fast-check` generates 100 random byte sequences up to 1 MiB, uploads each, consumes each, and asserts that the original bytes never appear (as UTF-8 or base64) in any logged string or serialized audit event.

## Dev Notes

### Requirements Context Summary

This story fills the gap left by Story 1.5-16's `generateSecretValue`
rejection of TLS certs and SSH keys, and unblocks migration-driven
onboarding from any existing secret manager. Without it, a real operator
has literally no path to get existing credentials into Tamma's vault.

### Key Design Decisions

1. **Handle-based indirection keeps plaintext out of the LLM loop**. The
   LLM, the orchestrator, and any workflow step that calls `importSecret`
   only ever sees a handle string. Plaintext lives in the handle store
   (broker process) and in the caller's own memory during upload — never
   crosses the LLM or the `@tamma/api` process boundary. The dashboard
   proxy is the one exception: plaintext transits through `@tamma/api`
   via a streaming passthrough, but is never held in a `Buffer`.

2. **Handles are single-use, short-lived, and atomic to consume**.
   Five-minute TTL is long enough for a human to copy-paste a handle
   into a CLI invocation if needed, but short enough that a leaked handle
   is not a long-lived liability. Atomic consume (via Valkey `GETDEL` or
   the memory store's mutex) prevents race conditions where two callers
   both read the plaintext and one of them replays it.

3. **In-memory handle store is a deliberate MVP choice**. Spinning up
   Valkey/Redis purely for import handles would block this story on
   Story 16-8. Memory mode is gated behind a boot-time warning and is
   explicitly not intended for multi-replica brokers. Once Story 16-8
   lands, the config flag flips to `valkey` and the implementation is
   already wired.

4. **Three ingestion surfaces, one handle store**. CLI (operator on
   laptop), web UI (operator via dashboard), OIDC API (CI-driven
   migration). All three produce the same handle shape and all three
   flow through the same `importSecret` call. No code duplication, one
   audit trail, one taint boundary.

5. **Owner-only import in the UI, service-token only in the CLI/API**.
   The dashboard UI gates behind RBAC because the session cookie is
   ambiently available in the browser; we can't let any logged-in user
   import arbitrary secrets. The CLI and OIDC paths require explicit
   credential presentation per request, so the RBAC check is implicit
   in who holds the token.

6. **Transfer-integrity fingerprint is SHA-256 of raw bytes, NOT the
   commitment hash**. The upload endpoint returns a fingerprint the
   operator can verify: "did the bytes I uploaded match what the broker
   saw?" This is a TOCTOU and network-corruption check. The commitment
   hash from Story 1.5-16 is a separate concept — it's the proof-of-value
   that survives after plaintext is discarded. Both are computed; the
   fingerprint is returned at upload time, the commitment is returned
   after `importSecret` completes.

7. **The dashboard proxy streams, doesn't buffer**. Using `undici`'s
   streaming request body to pipe multipart uploads through `@tamma/api`
   means the API process never materialises the full file in memory.
   This is a defense-in-depth move: even if some future bug lets an
   attacker read `@tamma/api` heap, there's no complete plaintext blob
   to steal during a live upload.

### Testing Strategy

- **Unit tests**: `HandleStore` implementations with race conditions,
  `TammaVaultStore.importSecret` with mocked vault, CLI argument parsing.
- **Integration tests**: full upload → handle → import chain through a
  real broker instance + Postgres via testcontainers. OIDC path with
  a mocked JWKS endpoint.
- **End-to-end test**: Playwright drives the dashboard upload form all
  the way through to a queryable metadata row in the vault DB.
- **Taint-tracking suite**: property-based test covering 100 random
  byte sequences and asserting plaintext absence across all logged
  and serialized surfaces.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Handle leaked in logs or error messages | Critical | Redaction bindings on broker Pino logger; taint tests assert handle-regex absence in log output |
| Plaintext materialised in `@tamma/api` during dashboard proxy | Critical | Streaming passthrough via `undici`; unit test asserts zero Buffer allocation in the proxy path |
| Memory-mode handle store used in multi-replica production | High | Boot-time warning; documented gotcha; Story 16-8 replaces with Valkey |
| CLI reading file outside CWD as a footgun | Medium | `fs.realpath` resolution + `--allow-outside-cwd` guard |
| OIDC token replay after expiry | High | Story 1.5-20's validator enforces `exp` and `iat` claims; import endpoint adds a 60s clock skew cap |
| Handle race condition returning plaintext to two callers | Critical | Atomic `consume` API, deterministic race test in CI, Valkey path uses `GETDEL` |
| Unbounded uploads filling broker memory | Medium | 1 MiB body cap, 10/minute rate limit, memory sweep timer bounds pending handle count |
| TLS cert PEMs with embedded private keys treated as plaintext | High | Import UI / CLI emit a warning when the type is `tls_cert` and the uploaded content contains `BEGIN PRIVATE KEY` / `BEGIN RSA PRIVATE KEY`, but proceed — that's usually what the operator wants |
| Import endpoint accepting garbage bytes (corrupted file, wrong type) | Low | Type-specific validators run at import time: `tls_cert` must parse as PEM or DER, `ssh_key` must parse as OpenSSH or PEM. Validation failure returns `import_failed` and emits `SECRET.IMPORTED.FAILED` |
