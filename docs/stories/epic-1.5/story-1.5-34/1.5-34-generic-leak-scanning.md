# Story 1.5-34: Non-GitHub git leak scanning — trufflehog + bundled rule set

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / Leak Prevention)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-17 (TammaVaultStore), Story 1.5-28 (LLM-output leak detection + GitHub secret-scanning webhook), Story 1.5-31 (AutoRotateWorkflow)

## Story

As a **Tamma operator running secrets across GitLab, Gitea, Forgejo, Bitbucket, Azure DevOps, and plain Git, where GitHub's native secret scanning does not exist**,
I want **Tamma to run trufflehog (or an equivalent scanner) against every PR Tamma creates — before the branch is pushed — and refuse to publish any PR that contains a Tamma-managed secret**,
so that **a Tamma-authored PR never leaks a managed secret into a git history on any platform, regardless of whether that platform has its own scanning service.**

## Context — Why this story exists

Story 1.5-28 implemented two leak-detection surfaces:

1. **LLM-output scanner** — every chunk the LLM emits is run through a
   commitment-hash check and a known-fingerprint check. Catches
   accidental echoing of secrets from prompts or tool output.
2. **GitHub Secret Scanning webhook integration** — GitHub's native
   scanner sends a webhook when it detects a secret in a public repo;
   Tamma maps it to a managed secret and triggers `AutoRotateWorkflow`.

Both surfaces have a gap. The LLM scanner catches direct echoes but
cannot catch secrets hidden in files the LLM writes (config files, test
fixtures, migration SQL) that the LLM never "said" out loud. The GitHub
webhook only fires for GitHub, and only for patterns GitHub knows about.

For every platform except GitHub — GitLab, Gitea, Forgejo, Bitbucket,
Azure DevOps, plain Git — there is no equivalent. A Tamma-generated PR
containing a secret on one of those platforms would simply ship.

Story 1.5-28 deferred trufflehog integration to a follow-up. This is
that follow-up. It runs a static leak scanner as a pre-push gate on
every Tamma-created PR, regardless of platform.

### Architecture summary

```
┌─────────────────────┐
│ PR creation         │
│ workflow (1.5-9)    │
└──────────┬──────────┘
           │ branch ready, files staged
           ▼
┌─────────────────────┐     ┌────────────────────────┐
│ LeakScanner         │ ──► │ trufflehog binary      │
│ .scan(workdir)      │     │ (bundled in image)     │
└──────────┬──────────┘     └────────────────────────┘
           │
           ▼
      ┌─────────┐
      │ result  │
      └────┬────┘
           │
   ┌───────┴───────┐
   │               │
matched         unmatched
   │               │
   ▼               ▼
AutoRotate    alert operator
+ abort PR    + abort PR
```

The scanner runs in the orchestrator or worker process that is about to
push the branch. It reads the working directory, invokes trufflehog over
a set of rules that include Tamma's own managed-secret commitment
hashes, and blocks the push if anything matches. Tamma's commitment
hashes are fed to trufflehog via a runtime-generated rule file.

## User Story

As a **Tamma platform engineer managing secrets across GitLab-hosted repos**,
I want **every Tamma-authored PR to be scanned for leaked secrets before the branch is pushed, with managed-secret matches triggering auto-rotation and unmatched-but-suspicious hits alerting the operator**,
so that **I get leak prevention equivalent to GitHub's native scanning on every platform I use.**

## Acceptance Criteria

### AC1: Scanner abstraction + trufflehog implementation

- [ ] An `ILeakScanner` interface at `packages/gates/src/leak-scanner/leak-scanner.ts`:
  ```typescript
  interface ILeakScanner {
    readonly name: string;           // 'trufflehog' | 'gitleaks' | ...
    scan(workdir: string, opts: ScanOptions): Promise<ScanResult>;
    version(): Promise<string>;
  }

  interface ScanOptions {
    managedSecretFingerprints: string[];   // commitment hashes
    managedSecretCommitmentRules: CommitmentRule[];
    includePatterns?: string[];
    excludePatterns?: string[];
    timeoutMs: number;                      // default 60_000
  }

  interface ScanResult {
    scanner: string;
    scannerVersion: string;
    durationMs: number;
    findings: ScanFinding[];
  }

  interface ScanFinding {
    file: string;
    line: number;
    column?: number;
    ruleId: string;
    category: 'managed_secret' | 'generic_pattern' | 'custom_rule';
    managedSecretId?: string;      // set when category === 'managed_secret'
    confidence: 'high' | 'medium' | 'low';
    redactedSnippet: string;       // plaintext redacted; shows byte offsets
  }
  ```
- [ ] `TrufflehogScanner` is the first implementation. It shells out to the
      `trufflehog` binary with `filesystem --directory=<workdir>`, passing a
      rule file generated at scan time containing Tamma's commitment-hash
      rules plus trufflehog's built-in rule set.
- [ ] The scanner binary is bundled in the orchestrator/worker Docker image
      at `/usr/local/bin/trufflehog`, pinned to a specific version via
      `TRUFFLEHOG_VERSION` build arg. Development environments can install
      via `pnpm exec tamma dev:install-trufflehog` which downloads the
      binary and verifies the checksum against `packages/gates/tools/trufflehog.checksums.json`.
- [ ] `version()` runs `trufflehog --version` and parses the output.
- [ ] `scan()` never logs the raw scanner output; it parses the JSON
      stream and transforms findings into `ScanFinding` shapes before any
      logging.
- [ ] Unit tests cover: happy path with a synthetic workdir containing a
      known-managed secret, happy path with no findings, timeout handling,
      binary not found, malformed trufflehog output, very large finding
      counts (truncation at 1000 findings with a `truncated: true` flag).

### AC2: Rule file generation for managed-secret detection

- [ ] A helper `generateRuleFile(fingerprints: string[], commitmentRules: CommitmentRule[]): string` writes a trufflehog-compatible rule YAML at `/tmp/tamma-leak-rules-<pid>-<uuid>.yml`.
- [ ] Rules include:
  1. One rule per managed-secret fingerprint: a regex or exact-string match that would fire on the plaintext. **BUT** the broker cannot put plaintext in the rule file (trust boundary). Instead, the rule file uses a content-addressable hash scheme: trufflehog runs with a custom detector that computes the commitment hash over every candidate token and compares against Tamma's known hashes. This requires a small trufflehog "custom detector" (Go plugin) or a post-processing step.
  2. **Implementation choice**: because trufflehog's plugin model is heavy (Go + rebuild), this story uses a **two-pass approach**:
     - Pass 1: trufflehog runs with its built-in detectors to find potential secret-shaped strings (entropy > 4.0, known patterns, etc.). Output: candidate tokens with file+line.
     - Pass 2: for each candidate, the Tamma post-processor hashes the token via the same commitment-hash function from Story 1.5-16 and compares against the broker-supplied `managedSecretFingerprints` list. Matches become `category: 'managed_secret'` findings. Non-matches become `category: 'generic_pattern'` findings.
- [ ] The rule file is deleted in a `finally` block after scan completion.
- [ ] The post-processor pass runs in the orchestrator process (not shelled out), because it needs access to the `CommitmentHasher` from `packages/secret-broker/src/crypto/`.
- [ ] Unit tests: rule file generation produces valid YAML, post-processor correctly matches managed secrets by commitment hash, handles unicode tokens, handles binary files gracefully.

### AC3: Integration into PR-creation workflow

- [ ] The `CreatePullRequestWorkflow` (from Story 1.5-9 or its Elsa equivalent) gains a new `LeakScanActivity` step BEFORE `git push`.
- [ ] The activity:
  1. Queries the broker for the list of managed-secret fingerprints visible to the current tenant.
  2. Invokes `LeakScanner.scan(workdir)` with those fingerprints.
  3. On any `category: 'managed_secret'` finding: aborts the workflow with `LeakDetectedError`, emits `SECRET.LEAK_DETECTED` with `source: 'trufflehog'`, triggers `AutoRotateWorkflow` (Story 1.5-31) for each matched `managedSecretId`, and does NOT push the branch.
  4. On any `category: 'generic_pattern'` finding (unknown secret-shaped token): does NOT block the push by default. Instead, emits `SECRET.LEAK_SUSPICIOUS` with the redacted snippet, and notifies the operator via `alert_orchestrator` (Story 1.5-27's alert hook). Operator can configure `secrets.leak_scan.block_on_generic: true` to make generic findings also block.
  5. On scanner errors (binary missing, timeout, malformed output): follows the configured `secrets.leak_scan.fail_mode`: `'fail_closed'` (default, abort push) or `'fail_open'` (log warning, proceed). Fail-closed is the default because "we didn't scan" is a security regression.
- [ ] The activity is idempotent: the same workflow run re-invoking the activity after a partial failure gets the same result (the work dir state is unchanged).
- [ ] Integration test: create a workdir with a known managed secret in a `.env.test` file, run the full CreatePullRequestWorkflow with a mocked git pusher, assert the push is NOT invoked, assert `AutoRotateWorkflow` is triggered, assert the managed secret commitment matches the leaked value.

### AC4: Performance budget — 10 second cap

- [ ] The scan must complete within 10 seconds for a workdir of up to 100 MiB or 10,000 files. Beyond those bounds, the scanner emits `SECRET.LEAK_SCAN.BUDGET_EXCEEDED` and continues the push if `fail_mode: 'fail_open'`, or aborts if `fail_mode: 'fail_closed'`.
- [ ] Performance test: `packages/gates/test/perf/leak-scanner-perf.test.ts` generates synthetic workdirs of 10 MiB / 100 files, 100 MiB / 1000 files, 100 MiB / 10000 files, runs the scanner 5 times per size, asserts p95 < 10 seconds for the largest.
- [ ] Performance techniques:
  - Exclude `.git/`, `node_modules/`, `dist/`, `build/` by default via `excludePatterns`.
  - Trufflehog runs with `--no-verification` flag (skip network calls to verify candidate API keys — we don't want side effects and we don't need verification for managed-secret matching).
  - Parallelism: trufflehog's internal concurrency is left at the default (8 workers); the orchestrator process runs only one scan at a time.
- [ ] The 10-second budget is measured wall-clock from activity start to activity end, including rule file generation and post-processing.

### AC5: Historical scan CLI command

- [ ] A new CLI command `tamma gates leak-scan`:
  ```
  tamma gates leak-scan \
      --repo <url>                       # git clone URL
      --ref <branch|tag|commit>          # default HEAD
      [--scanner trufflehog]             # future: gitleaks, etc.
      [--output json|text]               # default text
      [--rotate-on-match]                # trigger AutoRotateWorkflow
  ```
- [ ] Use case: run against historical branches to find legacy leaks. Clones the repo into a temp directory, runs `LeakScanner.scan`, prints findings. When `--rotate-on-match` is passed, managed-secret findings trigger `AutoRotateWorkflow`.
- [ ] The CLI command reuses the same `LeakScanner` implementation as the PR workflow — no code duplication.
- [ ] Command exits 0 on no findings, 1 on unmatched findings (suspicious), 2 on managed-secret findings (critical).
- [ ] Documentation in `packages/cli/README.md`.

### AC6: Scanner selection + alternative evaluation

- [ ] The config accepts a scanner selection:
  ```yaml
  secrets:
    leak_scan:
      scanner: 'trufflehog'   # 'trufflehog' | 'gitleaks' — one supported in this story
      version: 'v3.x'
      fail_mode: 'fail_closed'
      block_on_generic: false
      include_patterns: ['**/*']
      exclude_patterns: ['**/node_modules/**', '**/.git/**', '**/dist/**']
  ```
- [ ] Only `trufflehog` is implemented in this story. The abstraction exists so that `gitleaks`, `detect-secrets`, or `git-secrets` could land in a follow-up. A boot-time check rejects unrecognized scanner names with a clear error.
- [ ] **Dev Notes include an evaluation of all four scanners** (trufflehog, gitleaks, detect-secrets, git-secrets) with the selection rationale. See Dev Notes → Scanner Evaluation.
- [ ] Integration test is explicitly written against `trufflehog`. When a second scanner is added in a future story, the same test gets parameterized.

### AC7: Taint tracking in scan results

- [ ] `ScanFinding.redactedSnippet` never contains full plaintext. Format:
  ```
  "redactedSnippet": "AWS_KEY=AKIA...**REDACTED 24 bytes**...XYZ0"
  ```
- [ ] The redaction keeps the first 4 and last 4 bytes of the candidate token for debugging, and replaces the middle with `**REDACTED N bytes**`. For tokens shorter than 16 bytes, the entire token is replaced.
- [ ] Taint-tracking tests assert that full plaintext never appears in:
  - `ScanFinding` JSON serialization
  - Orchestrator logs during scan
  - Alert notifications to operators
  - Audit event payloads (`SECRET.LEAK_DETECTED`, `SECRET.LEAK_SUSPICIOUS`, `SECRET.LEAK_SCAN.BUDGET_EXCEEDED`)
- [ ] A property-based test generates 100 random "secrets" of varying lengths, plants them in synthetic workdirs, runs the scanner, and asserts none appear in logs.

### AC8: End-to-end leak-to-rotation integration test

- [ ] A Vitest integration test:
  1. Spins up a real Postgres via `testcontainers`
  2. Creates a Tamma-managed secret with a known value
  3. Creates a synthetic git workdir containing that value in `config/database.yml`
  4. Invokes `CreatePullRequestWorkflow` against the workdir with a mocked git pusher
  5. Asserts the push is blocked
  6. Asserts `SECRET.LEAK_DETECTED` event with the correct `managedSecretId`
  7. Asserts `AutoRotateWorkflow` runs and the secret's commitment hash changes
  8. Runs the scan a second time against a clean workdir — no findings, push proceeds

## Dev Notes

### Scanner Evaluation

| Scanner | Pros | Cons | Decision |
|---|---|---|---|
| **trufflehog** | Active project (Truffle Security), rich detector library including cloud APIs, JSON output, filesystem + git mode, active verification of candidates (which we disable) | Go binary bundled (~30 MB), no native Node integration, JSON output can be verbose | **Selected**. Best balance of detector quality, output format, and platform support. |
| **gitleaks** | Written in Go, rules are pure TOML (easy to extend), good performance, supports baseline files | Fewer detectors than trufflehog, no active verification (irrelevant for us), rule authoring requires regex skills | Alternative, parameterized in future |
| **detect-secrets** | Python, pluggable detector model, good false-positive suppression via `.secrets.baseline` | Python runtime dependency in our Node image, slower on large repos, fewer platform-specific detectors | Rejected: adds Python dependency |
| **git-secrets** | Simple, AWS-maintained, easy config | Only regex-based, no entropy detection, limited detector library, mostly AWS-focused | Rejected: too narrow |

**Selection**: trufflehog. The `--no-verification` flag disables trufflehog's
network calls (which would side-effect: verifying an AWS key by calling
STS leaks our scanning activity to AWS), leaving the detector library
and output format we want.

### Key Design Decisions

1. **Two-pass matching via commitment hashes**. The broker cannot give
   the scanner plaintext managed-secret values (trust boundary), but the
   scanner needs to recognize them in workdir content. Solution: the
   scanner finds candidate tokens using its built-in detectors (entropy
   threshold, pattern matching), and a second pass computes the
   commitment hash for each candidate and compares to the broker's
   fingerprint list. This preserves the trust boundary (plaintext stays
   in the broker) while still catching managed-secret leaks.

2. **Scanner runs in the orchestrator/worker process, not the broker**.
   The orchestrator has the workdir; the broker doesn't. Shipping the
   scanner to where the data is avoids a plaintext-over-wire protocol.
   The orchestrator has access to the broker-supplied fingerprint list,
   which is just a set of hex hashes — no plaintext.

3. **Fail-closed by default**. If the scanner is missing, malformed,
   times out, or produces bad output, the default is to abort the push.
   "We didn't scan" equals "we don't know if it's safe" equals "don't
   ship." Operators who want faster CI can opt into `fail_open`, but
   they own the risk.

4. **Generic findings don't block by default**. An unknown
   entropy-shaped token in a Tamma PR might be a legitimate random
   string (UUID, test fixture, computed hash). Blocking every generic
   finding would make Tamma unusable. Managed-secret findings (our
   secret, leaking) always block; generic findings alert the operator
   for review. Operators can flip `block_on_generic: true` for high-
   security tenants.

5. **Historical scan CLI uses the same scanner as the PR workflow**.
   One implementation, two entry points. The CLI path is operator-
   driven: someone says "scan the main branch for legacy leaks" and
   gets a report. The PR workflow path is automated: every new PR is
   scanned before push.

6. **Trufflehog binary bundled at build time, not downloaded at
   runtime**. Runtime downloads create supply-chain risk (mitm, binary
   swap, network dependency). Bundling the binary into the Docker image
   with a checksum-verified version pin means the scanner ships with
   the orchestrator and is reproducible.

7. **10-second performance budget**. PR creation is already a multi-
   second operation; adding 10 seconds to every PR is noticeable but
   acceptable. Exceeding the budget triggers a hard warning (and abort
   if fail-closed). If real workloads blow the budget, the fix is
   better exclusion patterns, not a larger budget.

8. **Rule files are per-scan and deleted in `finally`**. The rule file
   contains the full fingerprint list for the current tenant, which is
   non-sensitive metadata (hashes, not plaintext), but leaving it on
   disk indefinitely is still untidy. `finally` deletion ensures
   cleanup even on crash.

### Testing Strategy

- **Unit tests**: scanner shell-out with mocked `child_process`; rule
  file generation; post-processor hash matching; `ScanFinding`
  redaction utility.
- **Integration tests**: real trufflehog binary in CI (installed via the
  dev-install script), synthetic workdirs with planted secrets,
  end-to-end PR workflow abort + auto-rotate.
- **Performance tests**: three workdir sizes, p95 latency assertions.
- **Property-based taint tests**: 100 random planted secrets, assert
  none appear in logs or audit events.
- **Smoke test**: manual run against a real Tamma repo via the
  historical-scan CLI, checked into `.dev/findings/` as a reference.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Trufflehog binary missing in image | Critical | Build-time check in Dockerfile: `RUN trufflehog --version` fails the image build if missing; fail-closed default in config |
| Trufflehog output format changes in a minor version | High | Version pin in build arg; JSON parser tests against recorded fixture output; CI rebuilds image on every main push so drift is caught |
| 10-second budget blown on large monorepos | Medium | Exclude patterns tuned for common build dirs; `SECRET.LEAK_SCAN.BUDGET_EXCEEDED` event surfaces the issue; operator can extend exclusions |
| False positive on generic detector blocking legitimate PRs | Medium | Generic findings don't block by default; operator reviews via alert; `block_on_generic: false` is the default |
| Commitment-hash post-processor missing a match due to encoding | High | Unit tests cover UTF-8, UTF-16, base64, hex, url-encoded plaintext; a known-leak integration test runs a round trip |
| Scanner verification calls leaking scan activity to third parties | High | `--no-verification` flag; integration test asserts no network calls during scan via `nock`/`msw` interception |
| Plaintext appearing in trufflehog's raw output and leaking into logs | Critical | Parser transforms findings before logging; raw output is never logged at INFO level; taint tests enforce |
| Runtime download supply chain attack if dev-install is misused in prod | High | Dev-install is a dev command only, not a production bootstrap path; production image has the binary pre-baked; docs call this out |
| Scan results piling up in an event store during a leak storm | Low | Findings capped at 1000 per scan with `truncated: true` flag; audit events emit one per scan, not one per finding |
| PR abort breaking the autonomous loop's forward progress | Medium | Abort emits enough context (file, line, redacted snippet) that the LLM's next iteration can avoid the offending content; `LeakDetectedError` carries the findings so the workflow can loop back to the code-generation step |
