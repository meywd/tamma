## Story

As a **Tamma tenant owner managing a growing inventory of secrets**,
I want **three metadata-level operations — edit a secret's tags/description/expiry without
touching the value, transfer a secret between scopes (repo → org, environment → project), and
merge two accidentally-split secrets into one canonical record**,
so that **I can reorganize my secret inventory as my team structure changes without having to
rotate, re-deploy, or re-verify every affected secret, and without losing the audit trail that
ties historical events to the surviving record.**

## Overview

The Story 1.5-16 design review flagged three `ISecretStore` methods as deferred because they
weren't blockers for the initial broker MVP: `updateSecretMetadata`, `transferSecret`, and
(raised in operational planning) `mergeSecrets`. They're not critical-path operations, but
each represents a real workflow that tenant owners run into as their inventory grows:

- A secret's description is outdated and its tags need updating to match a new project naming
  convention — but rotating the value to force a re-create would break every dependent
  workflow.
- A secret was created at `repo` scope during initial setup; the team later realizes it
  should be shared across three repos in an `org`, so it needs to migrate without a change of
  value.
- Two secrets were created with slightly different names (`db_password` and `DB_PASSWORD`) by
  two different operators; one needs to survive, the other needs to fold into it without
  losing its audit history.

This story adds all three methods to `ISecretStore` and wires them through activities (Story
1.5-18), workflows (Story 1.5-19), and the MCP tool surface (Story 1.5-45). Every method
preserves the commitment hash (no value ever changes through any of these paths), emits the
appropriate audit event, and is gated behind explicit admin-level authorization for the
destructive operations (`transferSecret` and `mergeSecrets`).

## Acceptance Criteria

### AC1: `updateSecretMetadata(secretId, changes)` is added to `ISecretStore`

- The method signature is:
  ```typescript
  interface ISecretStore {
    updateSecretMetadata(
      secretId: string,
      changes: SecretMetadataChanges,
      actor: Actor
    ): Promise<SecretMetadata>;
  }

  interface SecretMetadataChanges {
    tags?: Record<string, string>;           // full replacement of tag map
    description?: string;
    expiresAt?: string | null;                // ISO 8601 or null to clear
    rotationConfig?: RotationConfigPatch;     // partial update
    postRotationHealthCheck?: 'required' | 'advisory' | 'disabled';
    ownerUserId?: string;                     // transfer of responsibility, NOT of scope
  }
  ```
- The method NEVER touches `commitment_hash`, `encrypted_value`, `fingerprint`, `rootKeyVersion`,
  or any value-bearing field. A post-update assertion confirms the commitment is unchanged;
  any implementation that violates this throws `SECRET_METADATA_UPDATE_TOUCHED_VALUE`.
- The returned `SecretMetadata` reflects the new state.
- Emits `SECRET.METADATA_UPDATED` with tags `{ secretId, tenantId, actor }` and data
  `{ fieldsChanged: string[] }` — fields are listed but their OLD and NEW values are NOT
  placed in the event (tags and descriptions can contain secret names, URLs, etc. — we only
  record WHICH fields changed).
- Fails with `SECRET_NOT_FOUND` if the secret does not exist or is not readable by `actor`.
- Concurrent `updateSecretMetadata` calls are serialized by `secretId` via
  `SELECT FOR UPDATE` to prevent lost updates.

### AC2: `transferSecret(secretId, newScope, actor)` is added to `ISecretStore`

- The method signature is:
  ```typescript
  interface ISecretStore {
    transferSecret(
      secretId: string,
      newScope: SecretScope,
      actor: Actor
    ): Promise<SecretMetadata>;
  }
  ```
- Authorization: the actor must have `secrets:admin` permission on BOTH the source scope
  and the destination scope. A rejection is `TRANSFER_NOT_AUTHORIZED`.
- Pre-flight checks:
  - Destination scope is addressable on the secret's current backend
    (`isScopeAddressableOn(newScope, platform)` returns true)
  - No existing secret with the same `name` in the destination scope — rejects with
    `TRANSFER_NAME_CONFLICT` if one exists
  - The secret is not currently locked by an in-flight rotation — rejects with
    `TRANSFER_LOCKED_ROTATION` if any rotation workflow is in a non-terminal state
- Execution steps, in order:
  1. Copy secret metadata row to the new scope (`secretId` is PRESERVED — same UUID)
  2. Re-deploy the encrypted value to the new scope's platform mirror if the secret uses
     `platform_only` or `vault_copy` storage mode
  3. Verify the new deployment by reading back the commitment hash from the new mirror
     (`verifySecret` at `platform_mirror` level)
  4. Delete the old scope's platform mirror (if any)
  5. Update the metadata row's `scope` field atomically
- Any failure in steps 1-3 rolls back: delete the new-scope mirror, leave metadata pointing
  at the original scope, emit `SECRET.TRANSFER.FAILED`.
- Emits `SECRET.TRANSFERRED` with data `{ fromScope, toScope }` on success (scopes are
  safe to log — they're addressing metadata, not secrets).
- The commitment hash is preserved end-to-end. A post-transfer assertion confirms
  `oldCommitment === newCommitment`; any violation throws
  `TRANSFER_COMMITMENT_DRIFT` and triggers immediate rollback.

### AC3: `mergeSecrets(keepId, mergeId, actor)` is added to `ISecretStore`

- The method signature is:
  ```typescript
  interface ISecretStore {
    mergeSecrets(
      keepId: string,
      mergeId: string,
      actor: Actor
    ): Promise<SecretMetadata>;
  }
  ```
- Authorization: the actor must have `secrets:admin` permission on BOTH secrets. A rejection
  is `MERGE_NOT_AUTHORIZED`.
- Pre-flight checks:
  - `keepId` and `mergeId` must both exist and belong to the same tenant
    (`MERGE_TENANT_MISMATCH` otherwise)
  - Both secrets must have the same commitment hash — merging is only permitted for genuine
    duplicates, not for "make these two secrets the same by picking one." Rejects with
    `MERGE_COMMITMENT_MISMATCH` if they differ.
  - Neither secret is locked by an in-flight rotation
- Execution steps:
  1. Union the `deployTargets` lists (deduplicated)
  2. Re-parent any events tagged with `mergeId` to `keepId` in the event store (by adding a
     `merged_into` tag to existing events, NOT by rewriting them — events are immutable)
  3. Mark `mergeId`'s metadata row as `state: 'merged', merged_into: keepId`
  4. Delete `mergeId`'s platform mirror if it has one distinct from `keepId`'s
- Emits `SECRET.MERGED` with data `{ keepId, mergeId, eventsReparented: N }`.
- The event history of the merged secret remains queryable via the `merged_into` tag, so
  audit-trail tools can follow the chain.

- A dedicated test file `secret-metadata-crud.test.ts` runs the following assertion on

### AC11: Concurrency tests

- Concurrent `transferSecret` calls race cleanly — exactly one succeeds, the other gets
  `TRANSFER_LOCKED_OPERATION`
- `transferSecret` during an in-flight rotation rejects with `TRANSFER_LOCKED_ROTATION`

### AC12: Admin gating tests

- Non-admin actor calling `transferSecret` gets `TRANSFER_NOT_AUTHORIZED`
- Non-admin actor calling `mergeSecrets` gets `MERGE_NOT_AUTHORIZED`
- Non-admin actor calling `updateSecretMetadata` SUCCEEDS (metadata edits are not
  destructive and are allowed for any actor with `secrets:write` permission)

## Dev Notes

### Requirements Context Summary

**Epic Context:** The secret broker was built to handle high-value operations first —
create, rotate, verify, probe, revoke, cascade. The "boring CRUD" operations got skipped
because they're not security-critical in the same way, but skipping them forces operators
to work around gaps. Updating a secret's tags requires a rotation + re-create today. Moving
a secret between scopes requires an export + import flow that doesn't exist. Two split
secrets must be manually reconciled in the event store. All three are real needs.

**Technical Context:** The common thread across all three methods is that the value never
changes. `updateSecretMetadata` is pure SQL. `transferSecret` moves the encrypted value
between mirrors without decrypting it. `mergeSecrets` touches only the metadata and event
tags. The commitment hash is the single source of truth for "has the value changed" and
it's asserted at the start and end of every operation — any drift is a bug and fails
loudly.

**Integration Points:**
- **Story 1.5-16** — extends `ISecretStore` with three new methods; the interface
  file gains new method signatures but existing methods are unchanged
- **Story 1.5-17** — `TammaVaultStore` implements the new methods
- **Story 1.5-18** — activity wrappers live alongside existing secret activities
- **Story 1.5-19** — workflows wrap activities and register with
  `LlmWorkflowLaunchRegistry`
- **Story 1.5-30** — consumes `SECRET.TRANSFER.FAILED` and similar events for alerting;
  human-approval alerts route through the operator alert bus
- **Story 1.5-45** — MCP tool surface exposes the three operations; this story owns the
  underlying workflows, 1.5-45 owns the tool definitions
- **Story 1.5-42** — post-rotation health checks are unaffected (commitment doesn't change
  on any of these operations)

### Implementation Guidance

**Key Design Decisions:**

1. **Commitment preservation is an invariant, not an afterthought.** Every code path
   asserts the commitment hash before and after the operation. Any drift means the
   implementation is broken and the operation must abort. This is the single most
   important guarantee that makes these operations safe — without it, "metadata update"
   could silently re-encrypt the value and lose the audit trail.

2. **Merge only operates on genuine duplicates.** Refusing to merge secrets with different
   commitment hashes is the safety net against "use merge as a shortcut to promote one
   value over another" — that's what `rotate` + `transfer` are for. If two secrets
   genuinely hold the same value, merging them is safe; if they don't, merging is an
   operator mistake and we fail loudly.

3. **Event history is preserved via re-parenting tags, not rewriting.** Events are
   immutable; we never delete or modify them. A `merged_into` tag added to the merged
   secret's events lets audit tools follow the chain without losing the original context.

4. **`updateSecretMetadata` is NOT admin-gated, but transfer and merge are.** Tag edits
   and description changes are routine operator work. Moving a secret to a different
   scope changes who has access. Merging two secrets collapses event streams. The
   latter two are destructive in ways the former is not.

5. **Human approval by default, opt-out by tenant config.** The destructive-ops approval
   gate is on by default because the typical customer running Tamma for the first time
   wants the extra safety. Power users can disable it per-tenant; the disable action is
   itself audited, so the audit trail makes clear when the guard was off.

6. **Transfer preserves the `secretId`.** This is a deliberate choice: historical events
   and dashboards continue to work without re-linking. The scope changes, but the
   identity doesn't. If we minted a new ID on transfer, we'd break every consumer that
   remembered the old one.

7. **Concurrent updates serialize via `SELECT FOR UPDATE`.** Postgres row-level locking
   is sufficient for the expected call volume (CRUD ops are rare compared to probe/rotate).
   A distributed lock is overkill.

**Technical Specifications:**

- **New error codes:**
  ```typescript
  export const SECRET_CRUD_ERROR_CODES = {
    SECRET_METADATA_UPDATE_TOUCHED_VALUE: 'SECRET_METADATA_UPDATE_TOUCHED_VALUE',
    TRANSFER_NOT_AUTHORIZED: 'TRANSFER_NOT_AUTHORIZED',
    TRANSFER_NAME_CONFLICT: 'TRANSFER_NAME_CONFLICT',
    TRANSFER_LOCKED_ROTATION: 'TRANSFER_LOCKED_ROTATION',
    TRANSFER_LOCKED_OPERATION: 'TRANSFER_LOCKED_OPERATION',
    TRANSFER_COMMITMENT_DRIFT: 'TRANSFER_COMMITMENT_DRIFT',
    MERGE_NOT_AUTHORIZED: 'MERGE_NOT_AUTHORIZED',
    MERGE_TENANT_MISMATCH: 'MERGE_TENANT_MISMATCH',
    MERGE_COMMITMENT_MISMATCH: 'MERGE_COMMITMENT_MISMATCH',
  } as const;
  ```

- **`updateSecretMetadata` SQL:** `BEGIN; SELECT commitment_hash ... FOR UPDATE;
  UPDATE secrets SET description = COALESCE(...), tags = COALESCE(...), expires_at = $4,
  rotation_config = COALESCE(...), post_rotation_health_check = COALESCE(...),
  owner_user_id = COALESCE(...), updated_at = now() WHERE id = $1; -- assert commitment
  unchanged; COMMIT;`

- **Transfer sequence:** `beginTransaction → validateAuth(fromScope, toScope) →
  checkNameConflict → checkRotationLock → copyMirror(from, to) → verifyMirrorAt(to)
  → (mismatch: rollback + emit SECRET.TRANSFER.FAILED) → updateMetadata(scope = to) →
  deleteMirror(from) → commitTransaction → emit SECRET.TRANSFERRED`.

### Risks and Mitigations

| Risk | Severity | Mitigation |
| ---- | -------- | ---------- |
| `updateSecretMetadata` accidentally re-encrypts and drifts commitment | **Critical** | Hard assertion pre/post, unit test via injected-bug fork, negative integration test |
| `transferSecret` leaves orphaned mirror if rollback fails mid-flight | High | Saga pattern with explicit rollback step; orphaned-mirror cleanup job follows up (tracked as operational runbook item) |
| `mergeSecrets` collapses event streams in a way that breaks historical queries | High | Events preserved, `merged_into` tag added; audit tools documented; integration test asserts `find_events_by_secret(keepId)` returns both original streams |
| Human-approval gate blocks legitimate automation | Medium | Opt-out per-tenant config, documented in runbook, audit event emitted when guard is disabled |
| Concurrent transfer + rotation race | High | Explicit rotation-lock check; `transferSecret` rejects during non-terminal rotation workflow |
| Tag values leak through `SECRET.METADATA_UPDATED` event data | High | Event data only contains field NAMES, not values; taint-tracking test verifies |
| Transfer to a scope the destination platform doesn't support | Medium | `isScopeAddressableOn` pre-flight check; explicit error `TRANSFER_SCOPE_UNSUPPORTED` |
| Merge used as a shortcut to change values | Medium | Commitment-match requirement makes this structurally impossible |

## Logging Requirements

Infrastructure and deployment components MUST use structured logging via pino/ILogger
(never `console.log` in production code).

- **INFO**: Metadata update succeeded (`secretId`, `fieldsChanged`), transfer succeeded
  (`fromScope`, `toScope`), merge succeeded (`keepId`, `mergeId`, `eventsReparented`),
  human-approval gate reached / granted / denied
- **DEBUG**: `SELECT FOR UPDATE` acquired, commitment assertion passed, rotation-lock check,
  saga step completed
- **WARN**: Transfer rollback triggered (`reason`), merge rejected on commitment mismatch,
  `TRANSFER_NAME_CONFLICT`, unauthorized attempt, approval skipped (tenant opted out)
- **ERROR**: Commitment drift detected (critical — implementation bug), saga rollback failed,
  broker HTTP handler threw, DB constraint violation on transfer
- **Structured context**: Always include `{ secretId, tenantId, actor, operation }`. NEVER
  log tag values, description content, secret names that might contain sensitive hints, or
  commitment hashes in error strings. Commitment drift is logged as
  `{ driftDetected: true, secretId }`; the hashes themselves go only to the audit event.
- **Audit events**: `SECRET.METADATA_UPDATED`, `SECRET.TRANSFERRED`, `SECRET.TRANSFER.FAILED`,
  `SECRET.MERGED`, `SECRET.MERGE.FAILED` are the canonical record; log lines are for
  debugging only and can be sampled.
