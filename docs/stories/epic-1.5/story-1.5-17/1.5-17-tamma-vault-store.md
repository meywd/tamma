# Story 1.5-17: TammaVaultStore + Postgres schema + secret-broker HTTP service

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / LLM Safety)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-16 (interface + crypto primitives + broker package skeleton)

## Story

As a **Tamma operator deploying a multi-tenant instance**,
I want **a working `TammaVaultStore` implementation running as a separate
HTTP service with a Postgres-backed encrypted store**,
so that **secret operations from workflows can actually create, rotate,
verify, and retrieve secrets — with plaintext handling isolated to the
broker process and never reachable from `@tamma/api`**.

## Context

Story 1.5-16 defined `ISecretStore`, the commitment hash protocol, and
scaffolded `packages/secret-broker/` with the crypto helpers. This story
turns that scaffold into a running service: the vault schema, the concrete
`TammaVaultStore` class, the three-mode write path, the HTTP surface that
Elsa activities call, and the boot sequence.

This story explicitly does NOT cover:
- OIDC validation (Story 1.5-20)
- CI fetch endpoint for GitHub Actions runners (Story 1.5-21)
- Platform mirror implementations (Stories 1.5-23 through 1.5-26) —
  those will implement `deploySecretTo` for their specific platforms;
  this story provides an in-process stub that records the intent.
- Probe type implementations (Story 1.5-27)
- Leak detection and rotation cascade (Stories 1.5-28, 1.5-29, 1.5-30)

The goal is: at the end of 1.5-17, an engineer can `curl` the broker's
HTTP API to create a `vault_only` secret, retrieve its metadata + commitment,
verify it against the commitment, rotate it, and revoke it — entirely
within `packages/secret-broker/` and its Postgres DB, with no platform
integration required.

## Acceptance Criteria

### AC1: Postgres schema migration

- [ ] A migration file at `database/migrations/019_tamma_vault_secrets.sql`
      creates the `tamma_vault_secrets` table with this exact shape:
  ```sql
  CREATE TABLE tamma_vault_secrets (
    secret_id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id         UUID NOT NULL,
    scope_kind        TEXT NOT NULL CHECK (scope_kind IN ('repo','org','project','environment','tenant_root')),
    scope_ref         JSONB NOT NULL,
    name              TEXT NOT NULL,
    type              TEXT NOT NULL CHECK (type IN ('password','api_key','jwt_signing_key','tls_cert','ssh_key','arbitrary')),
    mode              TEXT NOT NULL CHECK (mode IN ('platform_only','vault_copy','vault_only')),
    encrypted_value   BYTEA,
    commitment_hash   TEXT NOT NULL,
    fingerprint       TEXT NOT NULL,
    root_key_version  INT  NOT NULL DEFAULT 1,
    status            TEXT NOT NULL CHECK (status IN ('active','rotating','revoked'))
                      DEFAULT 'active',
    drift_status      TEXT CHECK (drift_status IN ('in_sync','drifted','unknown'))
                      DEFAULT 'unknown',
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_rotated_at   TIMESTAMPTZ,
    revoked_at        TIMESTAMPTZ,
    revoked_reason    TEXT,
    metadata          JSONB NOT NULL DEFAULT '{}'::jsonb,
    UNIQUE (tenant_id, scope_kind, scope_ref, name, status)
  );

  CREATE INDEX idx_vault_secrets_tenant_status
    ON tamma_vault_secrets (tenant_id, status);
  CREATE INDEX idx_vault_secrets_scope
    ON tamma_vault_secrets USING GIN (scope_ref);
  CREATE INDEX idx_vault_secrets_fingerprint
    ON tamma_vault_secrets (fingerprint);
  ```
- [ ] `encrypted_value` is NULLable — `platform_only` rows leave it NULL,
      `vault_copy` and `vault_only` rows populate it.
- [ ] A CHECK constraint enforces: `mode = 'platform_only' → encrypted_value IS NULL`
      and `mode IN ('vault_copy','vault_only') → encrypted_value IS NOT NULL`.
- [ ] The migration is idempotent (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`).
- [ ] Row-level security is enabled on the table, with a policy that
      limits SELECT / UPDATE / DELETE to rows where
      `tenant_id = current_setting('app.current_tenant_id')::uuid`.
      This matches Story 17-2's RLS pattern and means the broker must
      `SET app.current_tenant_id` per connection.
- [ ] A companion `tamma_vault_deploy_targets` table records fan-out
      destinations for `vault_copy` mode:
  ```sql
  CREATE TABLE tamma_vault_deploy_targets (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    secret_id     UUID NOT NULL REFERENCES tamma_vault_secrets(secret_id) ON DELETE CASCADE,
    target_scope  JSONB NOT NULL,
    target_name   TEXT NOT NULL,
    last_synced_at TIMESTAMPTZ,
    sync_status   TEXT NOT NULL DEFAULT 'pending'
                  CHECK (sync_status IN ('pending','synced','failed','out_of_sync')),
    last_error    TEXT,
    UNIQUE (secret_id, target_scope, target_name)
  );
  ```

### AC2: `TammaVaultStore` implements `ISecretStore`

- [ ] `packages/secret-broker/src/vault-store.ts` exports
      `TammaVaultStore implements ISecretStore`.
- [ ] Constructor takes `{ pool: pg.Pool, config: SecretsConfig }`. No
      global state, no singletons.
- [ ] Every method passes `tenant_id` through via a `SET LOCAL app.current_tenant_id`
      at the start of its transaction, so RLS applies to every query.
- [ ] `createSecret` implementation:
  1. Validates input (`name` length, `type` enum, `scope` shape).
  2. Calls `resolveMode(input, this.config)` — the forced overrides for
     `tenant_root` / plain-git / `jwt_signing_key` cannot be bypassed
     even if caller passes `modeOverride`.
  3. Calls `generateSecretValue(type, length)` from `crypto.ts`.
  4. Calls `deriveTenantKeys(rootKey, tenantId)` and computes
     `commitment_hash` and `fingerprint`.
  5. For `vault_copy` / `vault_only`: encrypts with AES-256-GCM using
     `encKey` and a 96-bit random nonce. Encrypted value is
     `nonce || ciphertext || authtag` (12 + N + 16 bytes).
  6. Inserts the row. For `platform_only`, `encrypted_value` is NULL.
  7. For `vault_copy` / `platform_only`, inserts a `tamma_vault_deploy_targets`
     row with `sync_status='pending'` pointing at the requested scope.
     Actual sync to the platform is handled by Stories 1.5-23 through
     1.5-26 (the per-platform mirror implementations); this story uses a
     `MockMirrorStore` stub that marks the row as `synced` immediately.
  8. Emits `SECRET.CREATED.SUCCESS` via the event store.
  9. Zeroises the plaintext Buffer (`.fill(0)`) before returning.
  10. Returns `CreatedSecret` with `secretId`, `commitmentHash`,
      `fingerprint`, `mode`, `rootKeyVersion`, `createdAt`.
- [ ] `rotateSecret` implementation:
  1. Loads the existing row (must be `status='active'`, else throw).
  2. Generates a new value via `generateSecretValue`.
  3. For `vault_copy` / `vault_only`: re-encrypts with the new value
     and overwrites `encrypted_value` in place. `encKey` re-derived via
     HKDF so it is deterministic for the tenant.
  4. Marks the pre-rotation state as `status='rotating'` in a shadow
     row (new UUID for audit), timestamped with
     `grace_period_ends_at = now() + interval '24 hours'`.
     The primary row keeps the same `secret_id` and carries the new
     commitment.
  5. Updates `last_rotated_at` on the primary row.
  6. Marks all deploy targets `sync_status='pending'`.
  7. Emits `SECRET.ROTATED.SUCCESS`.
  8. Zeroises both old and new plaintext Buffers.
- [ ] `verifySecret` implementation:
  1. Loads the row by `secret_id`. Unknown id →
     `{matches: false, status: 'not_found', verificationLevel: 'unavailable'}`.
  2. If `mode in ('vault_only','vault_copy')` and `encrypted_value` is
     non-null: decrypts, recomputes commitment via `computeCommitment`,
     compares to `expectedCommitmentHash` via `commitmentsEqual`
     (which wraps `timingSafeEqual`). Returns `verificationLevel: 'vault_value'`.
  3. If `mode = 'platform_only'`: compares `row.commitment_hash` against
     `expectedCommitmentHash` via `commitmentsEqual`. Returns
     `verificationLevel: 'metadata'`.
  4. Populates `driftDetected` from `row.drift_status != 'in_sync'` when
     present.
  5. Emits `SECRET.VERIFIED.MATCH` or `SECRET.VERIFIED.MISMATCH`.
  6. Zeroises decrypted plaintext before returning.
- [ ] `revokeSecret` implementation:
  1. Sets `status='revoked'`, `revoked_at=now()`, `revoked_reason=reason`.
  2. Deletes from `tamma_vault_deploy_targets` (CASCADE handled by FK).
  3. Leaves `encrypted_value` in place (retained for audit, not readable
     after status change because all read paths filter on `status='active'`).
  4. Emits `SECRET.REVOKED.SUCCESS`.
- [ ] `listSecrets` returns `{secrets, nextCursor}` with cursor-based
      pagination. Default `limit` 100, max 1000. Query SELECTs
      `secret_id, tenant_id, scope_kind, scope_ref, name, type, mode,
      commitment_hash, fingerprint, status, created_at, last_rotated_at`
      — explicit no-`encrypted_value` in the SELECT list; a test asserts
      the query string does not contain `encrypted_value`.
- [ ] `getSecretMetadata(secretId)` is a single indexed lookup by primary
      key. Returns metadata shape identical to `listSecrets` items, or
      `null` if the row doesn't exist or is revoked.
- [ ] `findSecretsByFingerprint(fingerprint, tenantId)` uses
      `idx_vault_secrets_fingerprint` for an O(log N) lookup. Returns
      all active secrets whose fingerprint matches, scoped to the
      given tenant. Enables Story 1.5-28's leak detection scanner.
- [ ] `isDeployed(secretId)` returns `true` if at least one row exists
      in `tamma_vault_deploy_targets` for this secret AND the secret
      is `status='active'`.
- [ ] `isDeployedAt(secretId, target)` queries the specific
      `(secret_id, target_scope, target_name)` row and returns
      `{present, lastSyncAt, syncStatus}`.
- [ ] `mirrorSecretTo(secretId, target)` creates a new deploy-target row
      and delegates the actual write to the injected `IMirrorStore`
      (`MockMirrorStore` in this story, real mirrors in 1.5-23+).
- [ ] `probeSecret` returns `{success: false, errorCategory: 'not_supported'}`
      for every probe type — real probes are 1.5-27.

### AC3: AES-256-GCM encryption path

- [ ] `packages/secret-broker/src/crypto.ts` (extended from 1.5-16) adds:
  ```typescript
  export function aesGcmEncrypt(plaintext: Buffer, key: Buffer): Buffer;
  export function aesGcmDecrypt(ciphertext: Buffer, key: Buffer): Buffer;
  ```
- [ ] Output format: `nonce(12) || ciphertext(N) || authtag(16)`. A helper
      `parseEncryptedValue(buf)` returns `{nonce, ciphertext, authtag}`.
- [ ] `aesGcmEncrypt` generates a fresh random 96-bit nonce via
      `randomBytes(12)` on every call. Nonce reuse under the same key
      breaks AES-GCM; a unit test generates 10,000 encryptions with the
      same plaintext and asserts all outputs are distinct.
- [ ] `aesGcmDecrypt` throws on authentication failure (tampered ciphertext,
      wrong key, wrong nonce). The error type is a typed
      `VaultDecryptError` so the service can distinguish it from other
      failures.
- [ ] A round-trip test asserts `decrypt(encrypt(x)) === x` for random
      plaintexts of lengths 0, 1, 16, 32, 256, 1024, 4096.
- [ ] A cross-tenant test confirms that an encrypted blob produced under
      tenant A's `encKey` cannot be decrypted with tenant B's `encKey`
      (throws `VaultDecryptError`).

### AC4: Broker HTTP service

- [ ] `packages/secret-broker/src/server.ts` exports `startBrokerServer(options)`
      and runs a Fastify instance on a configurable port (default 3200,
      env var `TAMMA_BROKER_PORT`).
- [ ] The service exposes these routes, all POST with JSON body:
  - `POST /internal/secrets/create` — takes `CreateSecretInput` + `tenantId`,
    returns `CreatedSecret`.
  - `POST /internal/secrets/rotate` — takes `{secretId, tenantId}`,
    returns `RotationResult`.
  - `POST /internal/secrets/verify` — takes `{secretId, expectedCommitmentHash, tenantId}`,
    returns `VerifyResult`.
  - `POST /internal/secrets/revoke` — takes `{secretId, reason, tenantId}`,
    returns `{revokedAt}`.
  - `POST /internal/secrets/get-metadata` — takes `{secretId, tenantId}`,
    returns `{metadata: SecretMetadata | null}`.
  - `POST /internal/secrets/list` — takes `{scope, tenantId, limit?, cursor?}`,
    returns `{secrets: SecretMetadata[], nextCursor: string | null}`.
  - `POST /internal/secrets/find-by-fingerprint` — takes `{fingerprint, tenantId}`,
    returns `{secrets: SecretMetadata[]}`. Used by leak detection (1.5-28).
  - `POST /internal/secrets/is-deployed` — takes `{secretId, tenantId}`,
    returns `{deployed: boolean}`.
  - `POST /internal/secrets/is-deployed-at` — takes `{secretId, target, tenantId}`,
    returns `{present, lastSyncAt?, syncStatus?}`.
  - `POST /internal/secrets/mirror-to` — takes `{secretId, target, tenantId}`,
    returns `{syncedAt}`.
  - `POST /internal/secrets/probe` — takes `{secretId, probeType, probeConfig?, tenantId}`,
    returns `ProbeResult` (always `not_supported` in this story).
- [ ] All routes are prefixed `/internal/` to signal "not for external
      consumption." External-facing routes (CI fetch, admin) land in
      later stories. The broker's listen interface is restricted to
      `127.0.0.1` by default; network-facing binding requires explicit
      `TAMMA_BROKER_BIND_HOST` env var.
- [ ] Every route requires an `Authorization: Bearer <broker-api-key>`
      header. The broker API key lives in `TAMMA_BROKER_API_KEY` env
      var and is the trust boundary between the main API (which calls
      the broker) and the broker (which holds plaintext). Fail-fast in
      production if missing, matching the JWT_SECRET / vault root key
      pattern.
- [ ] `@fastify/helmet` and `@fastify/cors` are configured. CORS is
      disabled by default (broker is not browser-facing).
- [ ] Structured Pino logging for every request. Log fields include
      `method`, `path`, `tenantId`, `secretId` (when present), `statusCode`,
      `durationMs`. NEVER log `encryptedValue`, `commitmentHash`, the
      auth header, or the request body beyond the fields named here.
- [ ] A `GET /internal/health` route returns
      `{status: 'ok', rootKeyVersion, dbReachable}`. No auth required
      (used by readiness probes). `rootKeyVersion` is included so
      operators can verify the process loaded the expected key version.

### AC5: Mock mirror store for `platform_only` and `vault_copy` modes

- [ ] `packages/secret-broker/src/mirrors/mock-mirror-store.ts` defines:
  ```typescript
  export interface IMirrorStore {
    write(target: DeployTarget, value: Buffer, commitment: string): Promise<{ syncedAt: string }>;
    delete(target: DeployTarget): Promise<void>;
    listAt(scope: SecretScope): Promise<string[]>;
  }
  export class MockMirrorStore implements IMirrorStore;
  ```
- [ ] `MockMirrorStore` records writes to an in-memory map keyed by
      `(platform, scope, name)` and returns an immediate `syncedAt`.
      No network calls. No persistence across process restarts.
- [ ] The vault store is constructed with an `IMirrorStore` instance via
      DI. Stories 1.5-23+ provide real implementations; 1.5-17 wires
      the mock.
- [ ] A unit test confirms that creating a `platform_only` secret invokes
      `mock.write` once and sets the deploy-target row to
      `sync_status='synced'`. For `vault_only`, `mock.write` is never
      called.

### AC6: Boot sequence + fail-fast

- [ ] `packages/secret-broker/src/boot.ts` exports `bootBroker()` which:
  1. Reads `TAMMA_VAULT_ROOT_KEY` (fail-fast in production if missing).
  2. Reads `TAMMA_BROKER_API_KEY` (fail-fast in production if missing).
  3. Reads `DATABASE_URL` (required; broker has no in-memory fallback).
  4. Reads `secrets.*` config via `loadSecretsConfig()`.
  5. Connects to Postgres, runs migration 019 if not yet applied (using
     the same pattern as `packages/api`'s migration runner).
  6. Constructs `TammaVaultStore` with the pool + config + `MockMirrorStore`.
  7. Calls `startBrokerServer({store, port})`.
  8. Logs `Tamma secret broker started, listening on ...` at INFO level.
- [ ] A dedicated `packages/secret-broker/src/serve.ts` is the Docker
      entrypoint — equivalent to `packages/api/src/serve.ts` — and
      invokes `bootBroker()`.
- [ ] `packages/secret-broker/Dockerfile` (mirroring `docker/Dockerfile.ts`
      pattern) builds the broker as a standalone image.
- [ ] `docker/docker-compose.yml` gets a new `tamma-secret-broker` service
      definition with:
  - `image: ghcr.io/tamma-dev/tamma-secret-broker:pr-N` (matching the
    existing tag strategy)
  - Depends on `postgres` healthy
  - Env: `TAMMA_VAULT_ROOT_KEY`, `TAMMA_BROKER_API_KEY`, `DATABASE_URL`,
    `NODE_ENV`
  - Not exposed externally — only reachable on the `tamma-net` Docker

  - Health check: `curl -sf http://127.0.0.1:3200/internal/health`
- [ ] `.github/workflows/docker-publish.yml` adds the broker to the

### Requirements Context Summary

**Epic Context**: Story 1.5-16 defined the interface and crypto primitives
and scaffolded `packages/secret-broker/`. This story makes the broker a
real service: DB schema, vault store implementation, HTTP surface,
Dockerfile, compose integration. At the end of this story, secrets can be
created, rotated, verified, and revoked via HTTP — with nothing connected
to git platforms yet (that's Stories 1.5-23 through 1.5-26).

**Technical Context**: Postgres is the only persistent dependency. No
Redis, no Vault, no external KMS in this story — those are explicit
deferrals. The broker is a separate Node.js process running alongside
`tamma-api`, `tamma-engine`, and `elsa-server` in docker-compose. It
listens on an internal-only port (3200, bound to `127.0.0.1` by default)
and all callers authenticate with a shared `TAMMA_BROKER_API_KEY`.

**Integration Points**:
- **Postgres**: same instance as `tamma-api`, new tables in a new schema
  migration sequence (019, 020). RLS configured matching Story 17-2.
- **Event store**: audit events go to the same DCB stream used by
  `tamma-api`. Shared schema via `@tamma/api`'s `IEventStore` type — the
  broker imports that type only, not any implementation code.
- **`tamma-api`**: calls the broker via HTTP for secret operations
  triggered by workflow activities. Does NOT import `@tamma/secret-broker`
  directly — lint-enforced.
- **Elsa activities (Story 1.5-18)**: C# activities call the broker HTTP
  API using the same `TAMMA_BROKER_API_KEY`. The broker API is designed
  for this consumer.

### Key Design Decisions

1. **Broker is a separate Fastify service, not a library linked into
   `tamma-api`.** The process boundary is the enforcement mechanism for
   "plaintext never reaches the main API process." A library could be
   accidentally imported from a future PR; a process requires an HTTP
   call with explicit auth, which is loud and visible in logs.

2. **All routes are `/internal/*` and bind to localhost by default.** The
   broker is not an externally-facing service. The CI fetch endpoint
   (Story 1.5-21) will add a separate `/api/v1/*` surface that binds to
   a different port and has its own OIDC auth. Keeping these surfaces
   isolated prevents a misconfiguration in one from exposing the other.

3. **Mock mirror store is first-class.** Real mirrors are 5 stories away
   (1.5-23 through 1.5-26); we cannot block 1.5-17 on them. The
   `IMirrorStore` interface + `MockMirrorStore` implementation lets
   `vault_copy` and `platform_only` modes work end-to-end in tests and
   in docker-compose development, with real platform writes swapped in
   later via DI.

4. **Encrypted value format is `nonce(12) || ciphertext || authtag(16)`.**
   Single opaque BYTEA column. Storing nonce + ciphertext + tag separately
   would require three columns and invite schema drift. The parse helper
   handles the split at read time. 12-byte nonces are the AES-GCM
   standard.

5. **Rotation creates a shadow row for the old state rather than
   overwriting in-place with history.** The primary row keeps the stable
   `secret_id` and the new commitment; a new row with status='rotating'
   records the previous commitment + fingerprint for the grace period.
   Readers filter on `status='active'` so the shadow row is invisible
   to normal lookups but queryable for audit.

6. **RLS is enabled from day one, matching Story 17-2.** Tenant isolation
   is non-negotiable for a multi-tenant secret store. The broker sets
   `app.current_tenant_id` per transaction and never connects as a
   superuser.

7. **Taint-tracking tests are mandatory.** For any test that touches
   plaintext, inject a known value and assert it does not appear in any
   serialized output (DB row, HTTP response, log line, audit event).
   This is the verification of Invariant 7 from Story 1.5-16.

### Testing Strategy

- **Unit tests** for `TammaVaultStore` methods in isolation (with in-memory
  Postgres via `pg-mem` where feasible, or a disposable real Postgres
  via `pg-test-helper` otherwise).
- **Integration tests** against real Postgres for the full CRUD +
  rotation + revocation lifecycle.
- **HTTP e2e tests** via Fastify inject for the broker service.
- **CI lint test** for the cross-package import guard.
- **Taint-tracking tests** across unit, integration, and HTTP layers.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Nonce reuse breaking AES-GCM | Critical | `randomBytes(12)` on every encrypt; unit test verifies 10k distinct nonces |
| RLS bypass via superuser in tests | High | `setAppRole('tamma_app')` in test helper (matching 1.5-4 fix from earlier in this PR) |
| Broker API key leaks to logs | High | Redaction middleware strips `authorization` header; log output test asserts the header value never appears |
| Mirror stub divergence from real mirrors | Medium | `IMirrorStore` interface is narrow; contract tests are reusable — when real mirrors land in 1.5-23+, they run against the same test suite |
| Migration 019 conflicts with other in-flight migrations | Medium | Coordinate with PR authors; the number 019 is claimed in this story's branch to avoid races |
| Broker process crashes mid-rotation | High | Rotation is wrapped in a single SQL transaction; if the broker dies before commit, the row retains old state. Deploy-target rows in `pending` status are reconciled at boot via a startup job |
