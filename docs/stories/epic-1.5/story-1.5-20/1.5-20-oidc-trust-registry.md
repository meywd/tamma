# Story 1.5-20: OIDC Trust Registry + Validator

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / Identity Federation)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-17 (broker HTTP service exists)

## Story

As a **Tamma operator wiring up a CI pipeline that needs to pull secrets
during a workflow run**,
I want **Tamma to act as an OIDC relying party that validates short-lived
JWTs issued by GitHub Actions, GitLab CI, or Gitea 1.21+**,
so that **my CI jobs can authenticate to the Tamma secret broker using
ambient workload identity, without shipping a long-lived `TAMMA_CI_TOKEN`
into the runner environment**.

## Context

The end goal of Epic 1.5's secret subsystem is that a GitHub Action
running in a user's repo can call
`POST https://api.tamma.dev/api/v1/ci/fetch-secrets` and get back a batch
of secret values injected into its job environment. That fetch endpoint
(Story 1.5-21) needs an authenticator. We do **not** want that
authenticator to be a plain bearer token, because:

1. Long-lived bearer tokens in CI environments leak constantly (via `set
   -x`, `env` dumps, log echoing, third-party actions, workflow YAML
   history).
2. We already have short-lived, cryptographically-verifiable, workload-bound
   identity tokens available for free: every major CI platform now issues
   OIDC ID tokens against a well-known issuer.
3. Validating those tokens and binding them to a scoped set of secrets is
   strictly better: the token is ephemeral (5–15 min), bound to a specific
   repo + workflow + run, and the mapping from `sub` claim to allowed
   secrets is auditable.

This story adds OIDC relying-party support to Tamma. It covers:

- The Postgres trust registry that maps issuers + subject patterns to
  allowed scopes
- The `OidcValidator` class that fetches JWKS, validates signatures, and
  resolves a token to a scope
- Admin endpoints on `packages/api` for operators to register/list/delete
  trusts (gated by `settings:manage`)
- Integration with the existing unified auth middleware so OIDC coexists
  with API keys

This story explicitly does NOT cover:

- The `/api/v1/ci/fetch-secrets` endpoint that consumes validated tokens
  (Story 1.5-21)
- The GitHub Action that produces OIDC tokens (Story 1.5-22)
- Platform-specific runner onboarding docs (lands alongside 1.5-22)

Nothing in Epic 16 (OAuth/RBAC) or Epic 18 (user registration/login)
covers OIDC relying-party. Those epics treat Tamma as an *OAuth client*
against identity providers for human login. This story treats Tamma as
an *OIDC relying party* for machine-to-machine workload identity — a
different trust model that deserves its own registry.

## Acceptance Criteria

### AC1: `oidc_trusts` table migration

- [ ] A migration file at `database/migrations/023_oidc_trusts.sql`
      creates the `oidc_trusts` table:
  ```sql
  CREATE TABLE IF NOT EXISTS oidc_trusts (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id         UUID NOT NULL,
    issuer            TEXT NOT NULL,
    subject_pattern   TEXT NOT NULL,
    audience          TEXT NOT NULL,
    allowed_scope     JSONB NOT NULL,
    description       TEXT,
    enabled           BOOLEAN NOT NULL DEFAULT true,
    created_by        UUID NOT NULL,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, issuer, subject_pattern, audience)
  );

  CREATE INDEX IF NOT EXISTS idx_oidc_trusts_issuer
    ON oidc_trusts (issuer) WHERE enabled = true;
  CREATE INDEX IF NOT EXISTS idx_oidc_trusts_tenant
    ON oidc_trusts (tenant_id) WHERE enabled = true;
  ```
- [ ] `allowed_scope` is a JSONB document of shape
      `{secret_ids?: string[], scope_patterns?: [{kind, platform?, owner?, repo?}]}`.
      At least one must be present. Validation enforced at the API layer,
      not as a CHECK constraint (JSONB CHECKs are brittle).
- [ ] `subject_pattern` is a glob string like
      `repo:tamma-dev/tamma:ref:refs/heads/main`,
      `repo:tamma-dev/tamma:environment:production`, or
      `repo:tamma-dev/*:*`. The pattern engine supports literal strings
      and the `*` wildcard (no `?`, no `[]`, no regex — too much rope).
- [ ] `audience` defaults to `https://api.tamma.dev` for each tenant's
      primary install but is configurable per trust — GitLab by default
      emits `sub` tokens with a custom `aud` and operators need to pin
      that explicitly.
- [ ] Row-level security is enabled on the table matching Story 17-2's
      pattern: `tenant_id = current_setting('app.current_tenant_id')::uuid`.
- [ ] The migration is idempotent and uses `CREATE TABLE IF NOT EXISTS` /
      `CREATE INDEX IF NOT EXISTS` so re-running it is a no-op.
- [ ] A rollback file at `database/migrations/023_oidc_trusts.down.sql`
      drops the table and its indexes, matching the migration-runner
      convention from earlier stories.

### AC2: `OidcValidator` class

- [ ] `packages/secret-broker/src/auth/oidc-validator.ts` exports
      `OidcValidator` with the following shape:
  ```typescript
  export interface OidcValidatorDeps {
    trustStore: IOidcTrustStore;
    jwksCache?: IJwksCache;          // defaults to in-memory LRU
    clock?: () => number;             // injectable for tests
    clockSkewSeconds?: number;        // default 60
    nonceStore?: INonceStore;         // required for replay prevention
  }

  export class OidcValidator {
    constructor(deps: OidcValidatorDeps);
    async validate(token: string, opts: {
      tenantId: string;
      expectedAudience: string;
    }): Promise<ResolvedOidcIdentity>;
  }

  export interface ResolvedOidcIdentity {
    issuer: string;
    subject: string;
    audience: string;
    trustId: string;
    allowedScope: AllowedScope;
    rawClaims: Record<string, unknown>;
    runId?: string;            // from `run_id` claim when present
    repository?: string;       // from `repository` claim when present
    workflowRef?: string;      // from `workflow_ref` claim when present
  }
  ```
- [ ] `validate()` performs, in order:
  1. Parse JWT header to extract `kid` and `alg`. Reject any `alg` not
     in the allowlist `['RS256', 'RS384', 'RS512', 'ES256', 'ES384']`.
     `none` is rejected explicitly — no "algorithm confusion" via the
     underlying JWT library's defaults.
  2. Decode the payload to read `iss` and look up all enabled trusts
     matching `(tenant_id, issuer)`. If zero matches → throw
     `OidcValidationError('ISSUER_NOT_REGISTERED', 403)`.
  3. Fetch JWKS for `iss` via the cache (see AC3).
  4. Find the signing key by `kid`. If absent → refresh the cache once
     (handles key rotation) and retry. If still absent → throw
     `OidcValidationError('KID_NOT_FOUND', 401)`.
  5. Verify the signature. On failure → throw
     `OidcValidationError('BAD_SIGNATURE', 401)`.
  6. Validate `exp`, `nbf`, `iat` against `clock()` with
     `clockSkewSeconds` tolerance on both sides. Throw
     `OidcValidationError('TOKEN_EXPIRED', 401)` or
     `OidcValidationError('TOKEN_NOT_YET_VALID', 401)`.
  7. Validate `aud` claim equals `opts.expectedAudience` (string
     equality; arrays handled by checking membership). Throw
     `OidcValidationError('BAD_AUDIENCE', 401)` on mismatch.
  8. Match `sub` against every trust's `subject_pattern` from step 2
     using the wildcard engine. The first match wins; if none match,
     throw `OidcValidationError('SUBJECT_NOT_AUTHORIZED', 403)`.
  9. Replay prevention: if the trust record has
     `require_nonce = true` (via the `allowed_scope` JSON) and the
     token carries a `run_id` claim, consult `nonceStore.claim(runId,
     issuer, ttlSec)`. On duplicate → throw
     `OidcValidationError('REPLAY_DETECTED', 403)`.
  10. Return the resolved identity with `allowedScope` copied from the
      matched trust.
- [ ] `OidcValidationError` is a typed error class carrying `code`,
      `httpStatus`, and a `publicMessage`. The public message NEVER
      reveals which step failed in a way that helps an attacker probe
      the registry — the HTTP layer translates all non-401 failures
      into a generic "forbidden" response with the code attached to
      logs only. Internal structured logs carry full detail.
- [ ] A unit test matrix covers every throw path with golden JWTs
      generated from a local keypair (RSA-2048, ES256).
- [ ] Wildcard engine is a pure function tested exhaustively:
      `matchSubjectPattern('repo:foo/bar:ref:refs/heads/main',
      'repo:foo/*:ref:refs/heads/*')` → true;
      `matchSubjectPattern('repo:evil/bar:...', 'repo:foo/*:...')` →
      false. No regex engine — substring walk only.

### AC3: JWKS cache with TTL + forced refresh

- [ ] `packages/secret-broker/src/auth/jwks-cache.ts` defines
      `IJwksCache` and an in-memory implementation `MemoryJwksCache`:
  ```typescript
  export interface IJwksCache {
    get(issuer: string): Promise<JwkSet>;
    refresh(issuer: string): Promise<JwkSet>;
  }
  ```
- [ ] `get()` returns cached keys if the entry is < `ttlSeconds` old
      (default 900, configurable via `TAMMA_OIDC_JWKS_TTL_SEC`).
      Otherwise it fetches fresh from `<issuer>/.well-known/openid-configuration`,
      reads the `jwks_uri`, fetches the JWKS document, and caches it.
- [ ] `refresh()` always bypasses the cache and re-fetches. The
      validator calls `refresh()` exactly once on `kid` miss, to handle
      key rotation without waiting for the TTL to expire. Repeated
      refresh attempts within 30 seconds are coalesced to prevent a
      runaway fetch storm if an attacker sends floods of tokens with
      bogus `kid`s.
- [ ] Fetches are performed with a 5-second timeout. On timeout or
      network error, `get()` returns stale cached data if available
      (fail-open for availability) but emits a `OIDC.JWKS_STALE`
      metric. `refresh()` fails hard on network error because it's
      only called from the `kid` miss path where we have no fallback.
- [ ] `ttlSeconds`, `staleFallbackEnabled`, and `fetchTimeoutMs` are
      all config-driven.
- [ ] A dedicated test suite uses `nock` (or Fastify inject against a
      local test issuer) to simulate:
  - Normal fetch + cache hit
  - TTL expiry → re-fetch
  - `kid` miss → forced refresh → resolution
  - Network failure → stale fallback
  - Network failure with no stale cache → throw
- [ ] **Pre-registered issuers** — the cache pre-warms at boot for the
      issuers in a well-known list (hardcoded constants for
      `token.actions.githubusercontent.com`, `gitlab.com`, plus any
      `TAMMA_OIDC_PREWARM_ISSUERS` env var) so the first CI fetch of
      the day doesn't pay cold-start latency.

### AC4: Admin endpoints on `packages/api`

- [ ] Four new routes in `packages/api/src/routes/oidc-trusts/`:
  - `POST   /api/v1/oidc-trusts` — register
  - `GET    /api/v1/oidc-trusts` — list (filter by `issuer`, `enabled`)
  - `GET    /api/v1/oidc-trusts/:id` — fetch one
  - `PATCH  /api/v1/oidc-trusts/:id` — update (toggle enabled,
    update allowed_scope, update description)
  - `DELETE /api/v1/oidc-trusts/:id` — soft-delete (sets `enabled=false`
    and keeps the row for audit)
- [ ] All five routes are gated by
      `preHandler: [requirePermission('settings:manage')]`. They are
      operator-facing, not end-user facing.
- [ ] Request bodies are validated via Fastify schema + Zod:
  ```typescript
  const RegisterOidcTrustBody = z.object({
    issuer: z.string().url(),
    subjectPattern: z.string().min(1).max(512),
    audience: z.string().min(1).max(256),
    description: z.string().max(1024).optional(),
    allowedScope: z.object({
      secretIds: z.array(z.string().uuid()).optional(),
      scopePatterns: z.array(SecretScopeSchema).optional(),
    }).refine(v => v.secretIds !== undefined || v.scopePatterns !== undefined, {
      message: 'allowedScope must contain at least one of secretIds or scopePatterns',
    }),
  });
  ```
- [ ] The routes live in `packages/api`, NOT in the broker. This is
      deliberate: the broker holds plaintext and has a tiny attack
      surface by design. Trust management is operator workflow and
      belongs with the rest of the admin console.
- [ ] The API calls the broker's `IOidcTrustStore` via HTTP on the
      existing `/internal/*` broker channel. New routes on the broker:
  - `POST /internal/oidc-trusts/upsert`
  - `POST /internal/oidc-trusts/list`
  - `POST /internal/oidc-trusts/get`
  - `POST /internal/oidc-trusts/delete`
  All protected by `TAMMA_BROKER_API_KEY` as in Story 1.5-17.
- [ ] Events are emitted for every write:
  `SECRET.OIDC_TRUST.REGISTERED`, `SECRET.OIDC_TRUST.UPDATED`,
  `SECRET.OIDC_TRUST.DELETED`, with `tenantId`, `actor`, `trustId`,
  `issuer`, `subjectPattern` in the event data. The `allowedScope`
  JSONB is NOT copied into event data verbatim — only its hash — so
  audit events stay small.
- [ ] An integration test against real Postgres creates a trust, lists
      it, updates it, soft-deletes it, and asserts every step emits
      the expected event via the shared event store stub.

### AC5: Unified auth integration — OIDC as second auth method

- [ ] `packages/api/src/auth/unified-auth.ts` grows a second
      authentication path **without breaking the existing path**. New
      control flow:
  1. Read `Authorization: Bearer <token>` header.
  2. **API key path** (existing): if the token starts with a known API
     key prefix (`tamma_sk_`, `tamma_ik_`, `tamma_uk_`, etc.) or
     matches the length/shape of a 43-char base64url hash — try the
     existing api-key lookup first. If found → build principal, done.
  3. **OIDC path** (new): if step 2 returned "not found" AND the token
     parses as a JWT (three base64url segments, valid header JSON) —
     invoke `OidcValidator.validate(token, {tenantId: ??, expectedAudience})`.
  4. If the OIDC path succeeds, build a new principal variant:
     ```typescript
     { scope: 'oidc';
       trustId: string;
       issuer: string;
       subject: string;
       tenantId: string;
       allowedScope: AllowedScope;
       runId?: string }
     ```
     Attach to `request.authPrincipal`. Downstream `requirePermission`
     works for this variant only if the underlying trust's
     `allowedScope` grants the permission — for 1.5-20 that means
     `oidc` principals have NO general API access; they are only
     usable on the `/api/v1/ci/fetch-secrets` route (Story 1.5-21),
     which checks the scope explicitly.
- [ ] The OIDC path derives `tenantId` from the URL (`?tenant=` query
      param) or header (`X-Tenant-Id`), then confirms the resolved
      trust's `tenant_id` matches. Mismatch → 403.
- [ ] `AuthPrincipal` type in `packages/api/src/auth/principal.ts`
      grows the `oidc` variant. All existing switch statements that
      exhaustively handle scope variants are updated; TypeScript
      strict mode catches any missed case.
- [ ] The existing api-key middleware is **not** touched in its core
      logic — the OIDC path is a fall-through that runs after api-key
      lookup fails, not before. This preserves the fast path for
      normal requests and keeps the change low-risk.
- [ ] An integration test verifies:
  - An api-key request works unchanged
  - An OIDC-token request against a registered trust works
  - An OIDC-token request against an unregistered issuer → 403
  - An OIDC-token request against a trust from a different tenant → 403
  - An OIDC request on a non-CI route → 403 (no general permission)
  - An OIDC request with a malformed JWT → 401
  - An api-key request that happens to start with `ey` (JWT-like
    prefix) is not misrouted — the prefix check precedes the JWT
    parse attempt

### AC6: Replay prevention via nonce store

- [ ] `packages/secret-broker/src/auth/nonce-store.ts` defines:
  ```typescript
  export interface INonceStore {
    claim(nonce: string, namespace: string, ttlSec: number): Promise<boolean>;
  }
  ```
  `claim()` returns `true` if this is the first time the nonce has
  been seen (and records it), `false` otherwise.
- [ ] Implementation uses Postgres with a dedicated `oidc_nonces` table:
  ```sql
  CREATE TABLE IF NOT EXISTS oidc_nonces (
    nonce     TEXT NOT NULL,
    namespace TEXT NOT NULL,
    seen_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (nonce, namespace)
  );
  CREATE INDEX IF NOT EXISTS idx_oidc_nonces_expires
    ON oidc_nonces (expires_at);
  ```
- [ ] `claim()` uses `INSERT ... ON CONFLICT DO NOTHING RETURNING` to
      atomically detect duplicates without a separate SELECT.
- [ ] A background sweeper deletes rows where `expires_at < now()` every
      10 minutes. This is a lightweight cron in the broker process —
      no new infrastructure.
- [ ] `namespace` is `issuer` so GitHub and GitLab can have colliding
      `run_id` values without interference.
- [ ] An integration test asserts that calling `claim(x, y, 60)` twice
      returns `true` then `false`, and that after the TTL expires the
      same nonce can be claimed again.
- [ ] Replay prevention is **opt-in per trust** — not every OIDC
      consumer gives us a usable nonce. The `allowed_scope` JSON carries
      `requireNonce: true` and names the claim (`run_id`, `job_id`, or a
      generic fallback to `jti`). If the flag is off, no nonce check.

- [ ] The translation table from `OidcValidationError.code` to HTTP

  | `TOKEN_EXPIRED` | 401 | `Token expired` |
  | `TOKEN_NOT_YET_VALID` | 401 | `Token not yet valid` |
  | `KID_NOT_FOUND` | 401 | `Unknown signing key` |
  | `BAD_AUDIENCE` | 401 | `Invalid audience` |
  | `ISSUER_NOT_REGISTERED` | 403 | `Issuer not trusted for this tenant` |
  | `SUBJECT_NOT_AUTHORIZED` | 403 | `Subject does not match any trust pattern` |
  | `REPLAY_DETECTED` | 403 | `Token already used` |

- [ ] Error responses include a `code` field for machine consumption

## Dev Notes

### Requirements Context Summary

**Epic Context**: Epic 1.5's secret subsystem needs a workload-identity
authentication path for CI. Story 1.5-17 built the broker with a single
static `TAMMA_BROKER_API_KEY` suitable for server-to-server calls from
`tamma-api`. That key is the wrong trust model for CI: it's long-lived,
shared, and not bound to any specific repo or workflow. This story
introduces a second auth path where every request carries a short-lived
JWT issued by the CI platform itself, tied to the exact workflow run
performing the fetch.

**Technical Context**: The validator lives in `packages/secret-broker/`
because the broker is where fetch-secrets will be enforced (Story
1.5-21). The admin endpoints live in `packages/api/` because they are
operator workflow and belong with the rest of RBAC-gated admin
surface. The two halves communicate via the existing `/internal/*`
HTTP channel.

**Integration Points**:
- **Existing unified auth** (`packages/api/src/auth/unified-auth.ts`):
  new fall-through path, existing logic untouched. Preserves the fast
  path for normal requests.
- **`requirePermission`** (`packages/api/src/auth/require-permission.ts`):
  unchanged. OIDC principals are restricted to routes that check
  `allowed_scope` explicitly (Story 1.5-21), so they never need the
  role-based permission grid.
- **Event store**: audit events join the existing DCB stream.
- **JWKS HTTP fetches**: new outbound network dependency. Mitigated by
  caching + stale fallback + timeouts.

### Key Design Decisions

1. **OIDC trusts live in Postgres, not a config file.** Operators add
   and revoke trusts at runtime, often in response to a new CI
   pipeline being onboarded. A config-file approach would require a
   service restart per trust change — unworkable at scale.

2. **Subject patterns use glob, not regex.** Regex is too much rope
   for a trust boundary. A single "repo:foo/*:*" pattern is readable,
   auditable, and cheaply matchable. If operators need more
   expressiveness later, we can add a second `subject_regex` column
   with a feature flag, but we start narrow.

3. **Fall-through auth, not replacement.** The existing api-key path
   is well-tested and heavily used. Adding OIDC as a fall-through
   means the common case (api-key request) pays zero cost for the new
   feature, and the OIDC path can't accidentally break api-key auth.

4. **Admin endpoints in `@tamma/api`, validator in `@tamma/secret-broker`.**
   Keeps the broker's attack surface minimal — only the endpoints
   that actually need to touch secrets live there. CRUD over JSON
   data is safe to do in the main API.

5. **Replay prevention is opt-in but strongly recommended.** Not
   every OIDC platform gives us a usable nonce. GitHub Actions does
   (`run_id` + `job_id`). GitLab does. Plain OAuth2 OIDC providers
   often don't. So we make the check opt-in and surface a loud
   warning in the admin UI when a trust is registered without it.

6. **Pre-warm JWKS for well-known issuers.** The GitHub Actions
   issuer (`token.actions.githubusercontent.com`) is used by every
   Tamma customer. Fetching its JWKS lazily would add ~200ms to the
   first CI fetch of every day, which is exactly the latency budget
   that the CI experience can't afford. Pre-warm at boot.

7. **Fail-open JWKS stale fallback.** If the IdP's JWKS endpoint is
   down, we accept cached keys past TTL rather than blocking every
   CI job. This is the standard relying-party practice per RFC 8414
   (OAuth Server Metadata) and avoids outages caused by upstream
   blips. The `JWKS_STALE` metric alerts operators.

8. **`audience` is per-trust, not a single global constant.** GitHub
   Actions by default signs with `aud = <your-repo-url>`, but the
   `actions/fetch-secrets` Action (Story 1.5-22) explicitly requests
   `aud = https://api.tamma.dev`. GitLab has a different default.
   Making it configurable per trust avoids a one-size-fits-all hack.

### Testing Strategy

- **Unit tests** for the validator's decision tree and the wildcard
  matcher. Golden JWTs generated from a local RSA keypair committed
  to the test fixtures dir.
- **Integration tests** against real Postgres + a test HTTP server
  standing in for the JWKS endpoint. Use `nock` where feasible.
- **End-to-end tests** via the unified auth fall-through: register a
  trust via the admin API, craft a token, hit a fake CI-scoped route
  that asserts `request.authPrincipal.scope === 'oidc'`.
- **Replay tests** inject duplicate `run_id`s and assert the second
  call is rejected with `REPLAY_DETECTED`.
- **Token redaction test** greps log output to confirm the raw token
  never appears, only `iss`, `sub`, and `trustId`.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| JWT library accepts `alg: none` | Critical | Explicit allowlist in header parse step; test with `alg: none` token asserts 401 |
| JWKS cache poisoning via stale data | High | TTL + forced refresh on `kid` miss; metric alerts on stale serve |
| Wildcard pattern too permissive (e.g. `*`) | High | Admin API rejects bare `*` patterns; require minimum one literal segment |
| Replay attack via log-leaked token | High | Nonce store with `run_id` claim; strong recommendation in docs |
| Cross-tenant trust leak via tenant confusion | Critical | Tenant ID verified against trust record; RLS on `oidc_trusts`; integration test asserts tenant A cannot validate a token under tenant B's trust |
| IdP JWKS rotation causes mass failures | High | Forced refresh on `kid` miss handles it seamlessly; monitoring on `OIDC.JWKS_REFRESH` rate |
| Clock skew between IdP and Tamma | Medium | Configurable `clockSkewSeconds` (default 60); NTP recommended |
| Attacker triggers unbounded JWKS refreshes | Medium | 30-second coalescing on refresh attempts per issuer |
| Confusion between api-key and JWT in fall-through | Medium | Prefix-based fast path for api-keys; fall-through only on explicit "not found" |
