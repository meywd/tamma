# Story 1.5-38: Cascade scheduling — cron-based automatic rotation

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / Rotation)
**Status**: ready-for-dev
**Priority**: Medium
**Depends on**: Story 1.5-17 (TammaVaultStore + broker HTTP service), Story 1.5-19 (`RotateSecretWorkflow`), Story 1.5-30 (`RotationCascadeWorkflow`)

## Story

As a **Tamma operator running a production deployment with compliance requirements**,
I want **to schedule automatic secret rotations on a cron expression, with per-secret timezone support and blackout windows for known-busy periods**,
so that **database passwords and API keys rotate every 30 days without me having to run the rotation manually, and without rotations firing during a customer demo or a code freeze.**

## Context — Why this story exists

Story 1.5-30 shipped `RotationCascadeWorkflow` with a note in its
"What's NOT in this story" section: *"Cascade scheduling (running
rotations on a cron): future work. This story only handles
operator-triggered rotations."* That's the gap this story closes.

Manual rotation is the right default for high-stakes secrets where an
operator wants to eyeball the cascade as it runs. But for routine
rotations — "rotate the read-replica database user every 30 days to
satisfy the SOC2 auditor" — waiting for an operator to remember is
both fragile and expensive. A scheduled-rotation feature gives
operators a declarative way to say "this secret rotates on Monday at
03:00 UTC every four weeks" and walk away.

The feature reuses the existing rotation pipeline end-to-end:
schedules fire `RotateSecretWorkflow`, which in turn fires
`RotationCascadeWorkflow` to propagate to downstream systems. The new
piece is the scheduler itself — a worker that polls for due schedules,
enforces timezone and blackout constraints, and kicks off the workflow
with `reason: 'scheduled'`.

### Architecture summary

```
  Scheduler worker (polls every 60s)
        │  SELECT * FROM secret_rotation_schedules
        │  WHERE enabled = true AND next_run_at <= now()
        │
        ▼
  For each due schedule:
    1. Check blackout calendar (skip if blocked)
    2. Acquire advisory lock on schedule id
    3. Start RotateSecretWorkflow(secretId, reason='scheduled', scheduleId)
    4. Update last_run_at = now()
    5. Compute next_run_at via cron-parser
    6. Release lock
        │
        ▼
  RotateSecretWorkflow (Story 1.5-19)
        │
        ▼
  RotationCascadeWorkflow (Story 1.5-30)
        │
        ▼
  alert_orchestrator on failure → notification channels (Story 1.5-37)
```

Schedules are per-secret, stored in `secret_rotation_schedules`, and
admin-managed via a CRUD API. The scheduler runs inside the broker
process so it has direct access to the vault store and the rotation
pipeline. No external cron daemon is needed.

## User Story

As a **Tamma platform administrator**,
I want **a declarative schedule attached to each secret that triggers rotation automatically on the cron expression I configure, with timezone, blackout, and opt-out support**,
so that **I can meet rotation policy requirements without running manual commands and without surprise rotations during maintenance windows.**

### AC2: `SecretRotationScheduleStore` Postgres adapter

- [ ] `packages/secret-broker/src/rotation-schedules/schedule-store.ts`
      exports `SecretRotationScheduleStore` implementing:
  ```typescript
  interface IScheduleStore {
    list(tenantId: string): Promise<RotationSchedule[]>;
    get(tenantId: string, secretId: string): Promise<RotationSchedule | null>;
    create(input: CreateScheduleInput): Promise<RotationSchedule>;
    update(tenantId: string, secretId: string, patch: UpdateScheduleInput): Promise<RotationSchedule>;
    delete(tenantId: string, secretId: string): Promise<void>;
    listDue(now: Date, limit: number): Promise<RotationSchedule[]>;
    markRun(scheduleId: string, status: RunStatus, workflowId: string | null, nextRunAt: Date): Promise<void>;
  }
  ```
- [ ] Every method sets `SET LOCAL app.current_tenant_id` at the start
      of its transaction so RLS applies. `listDue` is the scheduler's
      workhorse and runs WITHOUT tenant context — it's a system-level
      query across all tenants, so it runs as the `tamma_broker_admin`
      Postgres role that bypasses RLS.
- [ ] `create` validates `cron_expression` by parsing it with
      `cron-parser`. If the cron is invalid or produces a next-run
      more than 1 year out, rejects with a typed
      `ScheduleValidationError`.
- [ ] `create` also validates `timezone` against the IANA tz database
      (via `Intl.DateTimeFormat` — Node 22 has full tz data). Rejects
      invalid zones.
- [ ] `create` also validates `blackout_calendar` if set — must
      reference an existing enabled calendar in the same tenant.
- [ ] `listDue` uses `SELECT ... FOR UPDATE SKIP LOCKED` to prevent
      two concurrent schedulers from picking the same row. This lets
      the scheduler scale horizontally (more than one broker pod can
      run the scheduler concurrently without double-firing).
- [ ] `markRun` updates `last_run_at`, `last_run_status`,
      `last_run_workflow_id`, recomputes `next_run_at` via
      `cron-parser`, and bumps or resets `consecutive_failures`.
- [ ] Unit tests with a mocked `pg.Pool` cover all validation paths.
- [ ] Integration tests against real Postgres (reusing the Story
      1.5-17 test harness) cover RLS isolation, the full CRUD lifecycle,
      and the `SKIP LOCKED` contention behaviour under concurrent load.

### AC4: `RotationScheduler` worker

- [ ] `packages/secret-broker/src/rotation-schedules/scheduler.ts`
      exports `RotationScheduler` with method:
  ```typescript
  class RotationScheduler {
    constructor(deps: {
      store: IScheduleStore;
      blackoutStore: IBlackoutStore;
      workflowLauncher: IWorkflowLauncher;
      logger: Logger;
    });

    async start(): Promise<void>;    // begins polling
    async stop(): Promise<void>;     // graceful shutdown
    async tick(): Promise<TickResult>;  // manual tick for testing
  }
  ```
- [ ] `start()` begins a polling loop that runs `tick()` every 60
      seconds. The interval is configurable via
      `broker.scheduler.tickIntervalMs` with a minimum of 10 seconds
      (to prevent runaway CPU on misconfiguration).
- [ ] `tick()` performs:
  1. Call `store.listDue(now, 100)` — pulls up to 100 due schedules
     with `SKIP LOCKED`.
  2. For each due schedule:
     a. Check the blackout calendar (if configured): if `now` falls
        inside any blackout window, mark as `skipped_blackout` and
        set `next_run_at` to the end of the window (or the next cron
        run, whichever is later).
     b. Check if a workflow for this `secretId` is already running
        (via `LlmWorkflowLaunchRegistry` from Story 1.5-19): if so,
        mark as `skipped_busy` and leave `next_run_at` unchanged
        (retry on the next tick).
     c. Call `workflowLauncher.launchRotate({secretId, tenantId,
        reason: 'scheduled', scheduleId})` and capture the returned
        workflowId.
     d. Call `store.markRun(scheduleId, 'success', workflowId, nextRunAt)`
        where `nextRunAt` is computed via `cron-parser.parseExpression`
        with the schedule's timezone.
  3. Return a `TickResult` summarising the per-schedule actions.
- [ ] `tick()` is idempotent: if called twice in rapid succession,
      the `SKIP LOCKED` ensures no schedule is processed twice. The
      scheduler's only mutation is `markRun`, which is atomic.
- [ ] `stop()` sets a shutdown flag and waits for the current `tick()`
      to complete before returning. A `tick()` in progress is never
      aborted mid-iteration.
- [ ] Scheduler integration with the broker process lifecycle:
      `start()` is called during broker boot, `stop()` during
      graceful shutdown, both wired into the existing broker
      lifecycle hooks.

### AC5: Blackout window evaluation

- [ ] Blackout calendar evaluation happens in
      `packages/secret-broker/src/rotation-schedules/blackout-evaluator.ts`:
  ```typescript
  class BlackoutEvaluator {
    isInBlackout(calendarName: string, now: Date, tz: string): Promise<BlackoutResult>;
  }
  interface BlackoutResult {
    blocked: boolean;
    window?: { startDate: string; endDate: string; reason: string };
    nextAvailable?: Date;
  }
  ```
- [ ] A blackout window is a `{startDate, endDate, reason}` triple.
      Dates are IS 8601 date-time strings; they're interpreted in
      the calendar's timezone, not the secret's.
- [ ] Evaluator walks all windows in the calendar and returns the
      first window that contains `now`, plus the earliest `endDate`
      across overlapping windows so the scheduler knows when the
      blackout period ends.
- [ ] Recurring windows are expressed as individual windows for
      now (e.g. "every Friday" = one row per Friday for the next
      year). A future story can add cron-like recurring windows;
      today, operators either script the insert or use the admin UI
      (once Story 1.5-39 lands) to populate a year at a time.
- [ ] Blackout evaluation is cached for 60 seconds per calendar to
      avoid hitting Postgres on every tick for the same calendar.
- [ ] Unit tests: inside window, outside window, overlapping windows,
      calendar disabled (evaluator returns `blocked: false`),
      timezone conversion edge cases (schedule in Europe/Istanbul,
      calendar in America/Los_Angeles).

### AC6: `RotateSecretWorkflow` accepts scheduled invocations

- [ ] `RotateSecretWorkflow` from Story 1.5-19 is extended to accept
      input field `scheduleId: string | null`. When present, the
      workflow:
  1. Sets the audit event tag `reason: 'scheduled'` (or
     `'scheduled_manual'` for run-now).
  2. Includes `scheduleId` in every emitted event so operators can
     trace a workflow back to the schedule that spawned it.
  3. On terminal failure, the workflow writes the failure back to
     the schedule via `store.markRun(scheduleId, 'failed', ...)`.
     The `consecutive_failures` counter increments.
  4. On terminal success, writes `markRun(scheduleId, 'success', ...)`.
     `consecutive_failures` resets to 0.
- [ ] If `consecutive_failures >= 3`, the workflow emits
      `SECRET.ROTATION_SCHEDULE.CIRCUIT_OPEN` and disables the
      schedule (`enabled = false`) to prevent a failing schedule from
      hammering the rotation pipeline every cycle. The alert goes out
      via `alert_orchestrator` so operators know a schedule was
      automatically paused.

### AC7: Opt-out / pause

- [ ] Setting `enabled = false` on a schedule pauses it without
      deleting configuration. A paused schedule does NOT appear in
      `listDue` results.
- [ ] The `PATCH` route accepts `{enabled: false}` to pause and
      `{enabled: true}` to resume. Resuming recomputes `next_run_at`
      from the cron starting at the current time (never looks
      backward for "missed" runs — the operator presumably paused
      deliberately).
- [ ] A workflow that has been manually forced (e.g. via
      `RotateSecretWorkflow` triggered from the CLI) does NOT
      reset the schedule's `next_run_at`. Manual rotation and
      scheduled rotation are independent.
- [ ] Integration test: pause a schedule, advance time past
      `next_run_at`, verify `tick()` does not fire it; resume,
      verify `next_run_at` is recomputed to the future.

## Dev Notes

### Requirements Context Summary

**Epic Context**: This story completes the automation trio for the
rotation pipeline: 1.5-29 gave us handlers, 1.5-30 gave us the cascade,
1.5-31 gave us auto-rotate on leak detection, and 1.5-38 gives us
cron-based scheduled rotation for routine rotations. Together they
cover operator-initiated, leak-triggered, and schedule-triggered
rotation — the three reasons a secret changes in Tamma.

**Technical Context**: The scheduler lives inside the broker process
and reuses the existing rotation pipeline. No new workflow type is
needed — scheduled rotations fire the existing `RotateSecretWorkflow`
with a new `reason` tag. The only novelty is the due-schedule query
and the next-run computation via `cron-parser`.

**Integration Points**:
- **Story 1.5-17 (TammaVaultStore)**: the scheduler queries Postgres
  hosted by the broker.
- **Story 1.5-19 (`RotateSecretWorkflow`)**: scheduled runs fire this
  workflow with `reason: 'scheduled'`.
- **Story 1.5-30 (`RotationCascadeWorkflow`)**: invoked automatically
  by `RotateSecretWorkflow`; scheduled rotations propagate the same
  way as manual rotations.
- **Story 1.5-37 (Notification channels)**: circuit-breaker and
  blackout-skip alerts flow through `alert_orchestrator` and out to
  the configured channels.
- **Story 16-7 (RBAC)**: admin routes use the existing owner-role gate.

### Key Design Decisions

1. **Scheduler runs inside the broker, not as a separate pod**. The
   broker already owns the vault store and the rotation pipeline; a
   separate scheduler pod would need to talk to the broker over HTTP
   anyway, which is strictly more moving parts for zero benefit. A
   60-second tick loop is trivial to run in-process.

2. **One schedule per secret (UNIQUE constraint)**. If an operator
   genuinely needs two triggers on the same secret, they can express
   it in a single cron expression or use the blackout calendar to
   carve out the unwanted periods. The simpler data model is worth
   losing the edge case.

3. **`SKIP LOCKED` for horizontal scaling**. Even though the MVP runs
   one scheduler per broker, the `SELECT ... FOR UPDATE SKIP LOCKED`
   pattern lets us scale out to multiple broker pods later without
   any changes — each pod picks up whatever rows the others haven't
   locked. This is cheap insurance against a future deployment
   topology.

4. **Timezone is per-schedule, not global**. Operators in different
   geographies need different rotation windows. A single global
   timezone would force operators to do mental math. Per-schedule
   timezone is the right default, and `cron-parser` supports it
   natively.

5. **Blackout windows are explicit date intervals, not recurrence
   rules**. RFC 5545 RRULE is powerful but complex; most operators
   want to express "don't rotate during the March release freeze"
   or "skip Thanksgiving week." Explicit intervals handle those
   cleanly. A future story can add recurrence support if the
   operator feedback warrants it.

6. **Circuit breaker at 3 consecutive failures**. A schedule that
   fails three cycles in a row is almost certainly broken (the
   cascade target is unreachable, the handler is misconfigured, the
   secret was revoked). Auto-disabling prevents the broken schedule
   from hammering the pipeline every cycle and fires a loud alert
   so the operator notices. The operator re-enables manually once
   they fix the underlying issue.

7. **`run-now` does not reset `next_run_at`**. Operators testing a
   schedule want to verify it works without skipping the next
   scheduled run. Leaving `next_run_at` untouched preserves the
   contract that "the next scheduled run happens on the cron, period."

8. **Scheduled rotation cannot be skipped by being "in progress"**.
   If a manual rotation is already running when the schedule fires,
   the scheduler marks the run as `skipped_busy` and retries on the
   next tick. It does NOT try to queue up multiple scheduled
   rotations — there's no benefit to "firing the same rotation twice
   back-to-back because the first time the schedule was busy."

### Testing Strategy

- **Unit tests** for cron parsing with a fixture of timezone edge
  cases (DST transitions in every supported zone), for blackout
  evaluation, for the scheduler tick loop with mocked stores.
- **Integration tests** against real Postgres for the schedule
  store, the RLS isolation, and the admin CRUD routes.
- **Fake-timer tests** for the scheduler using `vi.useFakeTimers()`
  to advance through a day's worth of ticks in milliseconds.
- **End-to-end test** (AC9) boots the broker, creates a schedule,
  advances time, verifies the rotation pipeline fires, then
  exercises the blackout and circuit-breaker paths.
- **Concurrency test** for `SKIP LOCKED`: start two scheduler
  instances, both call `listDue` simultaneously, verify each row is
  picked up by exactly one scheduler.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Cron expression misparsed silently → wrong rotation cadence | High | Validate on create/update via `cron-parser`; reject cron expressions that produce `next_run_at` more than 1 year out; `/preview` endpoint lets operators eyeball the upcoming runs |
| DST transition causes a rotation to fire twice or not at all | Medium | `cron-parser` handles DST correctly; test fixture covers the "spring forward" and "fall back" edge cases in multiple zones |
| Scheduler crashes mid-tick and a rotation is lost | Low | `markRun` is the only mutation and it happens AFTER the workflow launches; a crash before `markRun` leaves `next_run_at` unchanged and the rotation re-fires on the next tick (workflow idempotency from 1.5-30 handles the double-launch) |
| Two broker pods fire the same schedule simultaneously | High | `SELECT ... FOR UPDATE SKIP LOCKED` ensures at most one pod picks the row; concurrent pods are tested explicitly |
| Circuit breaker disables a schedule and operator doesn't notice | Medium | `SECRET.ROTATION_SCHEDULE.CIRCUIT_OPEN` event fires `alert_orchestrator`, which (after Story 1.5-37) pushes to PagerDuty/Slack; operator dashboard (Story 1.5-39) also surfaces disabled schedules |
| Blackout cache returns stale data after an operator edits the calendar | Low | 60-second cache is short enough that a manual edit propagates within a minute; operators doing urgent blackout changes can call `scheduler.tick()` manually after editing |
| Invalid timezone slips through validation and fails at runtime | Medium | `Intl.DateTimeFormat` validation at create time; integration test with a fixture of invalid zones (e.g. `America/NonExistent`) |
| `run-now` bypass lets an unprivileged user trigger rotation | Critical | Owner-role gate on the admin route; same audit events as normal rotation; rate limit 30/min/tenant |
| Schedule fires during the cascade's own timeout window | Medium | In-flight detection via `LlmWorkflowLaunchRegistry` marks `skipped_busy` and retries on next tick |
