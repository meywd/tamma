# Story 1.5-30: RotationCascadeWorkflow

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / Rotation)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-17 (TammaVaultStore + broker HTTP service), Story 1.5-19 (`CreateSecretWorkflow` + `RotateSecretWorkflow`), Story 1.5-29 (`IRotationHandler` + built-in handlers)

## Story

As a **Tamma operator running a multi-tenant deployment**,
I want **an Elsa workflow that propagates a rotated secret value to every downstream system configured for that secret, with parallel fan-out, rollback on partial failure, and the same workflow-polling contract as the LLM-facing workflows**,
so that **a single `RotateSecretWorkflow` invocation reliably updates all dependent systems (Postgres, MySQL, Redis, webhooks) as a single logical operation, or rolls back cleanly if any target fails.**

## Context — Why this story exists

Story 1.5-29 built the per-handler primitives: "given an old and new value,
update a Postgres server." This story builds the orchestration layer on
top: when a secret is rotated, find all the downstream systems configured
for it, fan out to them in parallel, collect results, and commit or roll
back as a unit.

Today, if Tamma rotates a database password but forgets to update the
application's connection string, the app breaks. The operator has to
either manually update every consumer of the secret or accept downtime.
`RotationCascadeWorkflow` makes this automatic: the operator configures
rotation targets once (via an admin API), and every subsequent rotation
propagates automatically.

The cascade runs as an Elsa child workflow invoked by `RotateSecretWorkflow`
(Story 1.5-19). This story adds:
1. The `secret_rotation_targets` table (migration 024) that maps a secret
   to its downstream systems.
2. The admin CRUD endpoints for configuring rotation targets.
3. The Elsa workflow activities that resolve targets, invoke handlers,
   collect results, and emit audit events.
4. The rollback path for partial-failure cases.
5. The polling/alert contract (consistent with 1.5-16) so the LLM-facing
   workflows can monitor cascades without side-channelling around them.

### Architecture summary

`RotationCascadeWorkflow` is an Elsa workflow living in
`packages/workflows/src/secrets/rotation-cascade-workflow.ts`. It's
invoked by `RotateSecretWorkflow` as a child after the vault-side rotation
commits (commitment hash updated, new value encrypted and stored). The
cascade queries `secret_rotation_targets` for all enabled targets, fans
out to each via parallel Elsa branches, and gates a commit/rollback
decision on the aggregate outcome.

Handler invocation goes through a new Elsa activity `InvokeRotationHandlerActivity`
which in turn calls the broker's `/internal/rotation/invoke` HTTP endpoint
— the broker is where handlers actually run (they need plaintext, see
Story 1.5-29). The activity only passes `secretId`, `targetId`, and a
handler type hint; the broker resolves the plaintext values from its
vault store and invokes the in-process handler. No plaintext crosses
the HTTP boundary.

Rollback follows the "partial-success, partial-rollback" model: if M of
N targets succeed and one fails, the workflow invokes rollback on the
M successful targets. Rollback is best-effort per handler (some can't,
some fail during rollback); the cascade records each target's rollback
status individually in the audit trail.

## User Story

As a **Tamma secret-management workflow author**,
I want **a workflow that ties rotation to downstream propagation with atomic-if-possible / clearly-audited-if-not semantics**,
so that **rotation is a complete operation, not a half-done change that leaves the operator guessing which systems picked up the new value.**

- [ ] A migration file at
      `database/migrations/024_secret_rotation_targets.sql` creates the
      `secret_rotation_targets` table:
  ```sql
  CREATE TABLE IF NOT EXISTS secret_rotation_targets (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id         UUID NOT NULL,
    secret_id         UUID NOT NULL REFERENCES tamma_vault_secrets(secret_id) ON DELETE CASCADE,
    handler_type      TEXT NOT NULL,
    handler_config    JSONB NOT NULL,
    enabled           BOOLEAN NOT NULL DEFAULT true,
    allow_unsupported_rollback BOOLEAN NOT NULL DEFAULT false,
    priority          INT NOT NULL DEFAULT 100,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    created_by        TEXT NOT NULL,
    UNIQUE (secret_id, handler_type, handler_config)
  );

  CREATE INDEX IF NOT EXISTS idx_rotation_targets_secret
    ON secret_rotation_targets (secret_id, enabled);
  CREATE INDEX IF NOT EXISTS idx_rotation_targets_tenant
    ON secret_rotation_targets (tenant_id);
  ```
- [ ] Row-level security is enabled matching the Story 17-2 pattern:
      `SELECT / UPDATE / DELETE` restricted to
      `tenant_id = current_setting('app.current_tenant_id')::uuid`.
- [ ] `ON DELETE CASCADE` from `tamma_vault_secrets`: revoking a secret
      also removes its rotation targets.
- [ ] `handler_config` is JSONB; its shape is handler-specific (Postgres
      config differs from HTTP webhook config). Schema validation is
      handler-side, applied at target-creation time (see AC3).
- [ ] `priority` orders parallel targets when deterministic ordering is
      required (e.g. for tests or for cascades where an operator wants
      one target to complete before others start — see AC5 note on
      parallel vs sequential).
- [ ] Migration is idempotent and includes a rollback script.

### AC4: `LoadRotationTargetsActivity` Elsa activity

- [ ] A new C# Elsa activity
      `Tamma.Workflows.Activities.LoadRotationTargetsActivity` fetches
      enabled targets for a given `secretId` by calling the broker HTTP
      endpoint `POST /internal/rotation-targets/list-enabled` with
      `{secretId, tenantId}`.
- [ ] Returns a list of target descriptors: `{id, handler_type,
      priority, allow_unsupported_rollback}`. **The `handler_config` is
      NOT returned to Elsa.** Config stays in the broker; the workflow
      only passes the target `id` through subsequent activities, and the
      broker looks up `handler_config` on each `InvokeRotationHandlerActivity`
      call.
- [ ] This is a deliberate narrowing: the workflow engine and the
      orchestrator process do not need to know about handler configs,
      which may contain sensitive references (secret ids, URLs, admin
      creds). Limiting what crosses the process boundary limits blast
      radius.
- [ ] Activity logs number of targets loaded and their types, but never
      their configs.
- [ ] Unit tests (C# side) mock the broker HTTP call and verify the
      activity populates workflow variables correctly.

### AC5: `InvokeRotationHandlerActivity` Elsa activity

- [ ] A new C# Elsa activity
      `Tamma.Workflows.Activities.InvokeRotationHandlerActivity` takes
      inputs `{targetId, secretId, tenantId, rotationId, attemptNumber}`
      and calls the broker endpoint
      `POST /internal/rotation/invoke-target` which:
  1. Loads the target row from `secret_rotation_targets`.
  2. Loads `handler_config` (JSONB) from the row.
  3. Looks up the handler in `RotationHandlerRegistry` by `handler_type`.
  4. Resolves `adminPasswordSecretId` (if present in config) to plaintext
     via the vault store.
  5. Loads the secret's current encrypted value from the vault (this is
     the NEW value, post-rotation, because the cascade runs after the
     vault-side rotation commits).
  6. Loads the previous encrypted value from the rotation shadow row
     (the `status='rotating'` row created by `rotateSecret` in 1.5-17).
  7. Decrypts both values.
  8. Invokes `handler.rotate(oldValue, newValue, config, context)`.
  9. Zeroises both plaintext buffers.
  10. Emits `SECRET.ROTATION_CASCADE.TARGET_SUCCESS` or
      `SECRET.ROTATION_CASCADE.TARGET_FAILED` based on result.
  11. Returns a non-sensitive result: `{success, errorCategory?,
      errorMessage?, sideEffects?, durationMs}`.
- [ ] Activity retry: 2 additional retries with 2s / 5s backoff if
      the result is `success: false` AND `errorCategory in
      ('connection_failed', 'timeout')`. No retry for `auth_failed`,
      `permission_denied`, `config_error`.
- [ ] After final attempt, activity returns result to workflow; workflow
      branches on success/failure.
- [ ] Timeout: 120s per activity invocation. If exceeded, the workflow
      fires `alert_orchestrator` (via the shared alert activity from
      Story 1.5-16) and the cascade proceeds to rollback.

### AC6: `RotationCascadeWorkflow` Elsa workflow definition

- [ ] `packages/workflows/src/secrets/rotation-cascade-workflow.ts` (or
      equivalent C# path) defines `RotationCascadeWorkflow` with this flow:
  1. **LoadTargets**: `LoadRotationTargetsActivity` loads targets for
     the secret.
  2. **ShortCircuitIfEmpty**: if zero enabled targets, emit
     `SECRET.ROTATION_CASCADE.SKIPPED_NO_TARGETS` and terminate success.
  3. **FanOut**: Elsa `ForEach` (parallel mode) over the target list,
     invoking `InvokeRotationHandlerActivity` for each.
  4. **Collect**: aggregate results into a `TargetResults[]` array.
  5. **Decide**:
     - If ALL targets succeeded → go to **Commit**.
     - Otherwise → go to **Rollback**.
  6. **Commit**: emit `SECRET.ROTATION_CASCADE.SUCCESS` with the list of
     target outcomes. Update `secret_rotation_targets.last_success_at`
     for each target. Terminate.
  7. **Rollback**: for each target that succeeded in step 3, invoke
     `RollbackRotationHandlerActivity` (a sibling activity that calls
     `handler.rollback`). Collect rollback results. Emit
     `SECRET.ROTATION_CASCADE.FAILED` with per-target rotation outcome
     AND rollback outcome. Also emit `SECRET.ROTATION_CASCADE.PARTIAL_ROLLBACK`
     if any rollback failed. Terminate failed.
- [ ] The workflow has a **hard timeout** of 10 minutes. If it hasn't
      reached a terminal state by then, it fires `alert_orchestrator`
      with `reason: 'timeout'` and transitions to failed with
      `SECRET.ROTATION_CASCADE.STALLED` audit. The pending targets are
      marked for operator review.
- [ ] The workflow has a **soft alert** at 2 minutes: if any target is
      still running at the 2-minute mark, the workflow fires
      `alert_orchestrator` with `reason: 'delay'` but continues running
      (does not abort). This matches the LLM-facing polling contract
      from Story 1.5-16.
- [ ] Workflow replay (Elsa's built-in) is deterministic: the target
      list order is sorted by `priority, created_at` inside
      `LoadRotationTargetsActivity`, so a replay produces the same
      fan-out order. Handler invocations are idempotent (see AC8), so
      a replay after a crash produces the same terminal state.

### AC7: Rollback semantics

- [ ] `RollbackRotationHandlerActivity`:
  1. Loads the target row, resolves the handler.
  2. If the handler doesn't have a `rollback` method OR its
     `supportsRollback` is false, returns
     `{rolledBack: false, reason: 'unsupported'}` without throwing.
     This target is reported in the audit as "committed, rollback unavailable".
  3. Otherwise, calls `handler.rollback(oldValue, newValue, config, context)`
     and returns `{rolledBack: true}` on success.
  4. On rollback failure, returns `{rolledBack: false, reason: 'failed',
     errorCategory, errorMessage}`. The target is reported in the audit
     as "committed, rollback failed, manual reconcile required".
- [ ] The cascade workflow's `Rollback` branch aggregates rollback
      outcomes and emits a single `SECRET.ROTATION_CASCADE.FAILED` event
      with a per-target breakdown: which succeeded in rotation, which
      rolled back cleanly, which could not roll back (unsupported),
      which failed to roll back.
- [ ] If any rollback returned `rolledBack: false` with reason `'failed'`,
      the cascade ALSO emits `SECRET.ROTATION_CASCADE.PARTIAL_ROLLBACK`
      as a loud alert and fires `alert_orchestrator` with the details
      so an operator is notified to reconcile manually.
- [ ] Rollback ordering is the REVERSE of rotation ordering (sort by
      `-priority, -created_at`). Tests verify this.

### AC8: Handler idempotency

- [ ] The cascade assumes handler rotation is idempotent: calling
      `handler.rotate(oldValue, newValue, config, context)` twice in
      succession should leave the downstream system with the new value,
      not cause an error. For Postgres/MySQL/Redis, this is naturally
      idempotent — setting a password to a value that's already set
      succeeds as a no-op.
- [ ] Each handler from Story 1.5-29 declares `idempotent: true` on its
      interface OR implements an internal idempotency check (e.g. "if
      the current value already matches newValue, return success without
      doing anything"). The cascade relies on this for crash recovery:
      if the broker dies mid-cascade and the workflow replays, the
      already-completed targets see a "rotate to value that's already
      set" and return success, while the un-started targets run normally.
- [ ] A cascade-level integration test verifies: start cascade, kill the
      broker after the first target succeeds, restart, replay workflow
      — final state matches single-pass cascade. No target is invoked
      in a way that leaves the downstream broken.

### AC9: `RotateSecretWorkflow` integration

- [ ] `RotateSecretWorkflow` from Story 1.5-19 is extended to invoke
      `RotationCascadeWorkflow` as a child workflow after the vault-side
      rotation commits.
- [ ] Invocation is unconditional: once a secret has been configured
      with any enabled rotation target, every rotation propagates.
      There is no "skip cascade" option. Rationale: skipping cascade
      would violate the operator's configured intent and leave the
      system in an inconsistent state.
- [ ] If the cascade terminates with failure, `RotateSecretWorkflow`
      ALSO fails, even though the vault-side rotation already committed.
      The final audit event is `SECRET.ROTATED.FAILED` with subcause
      `rotation_cascade_failed` and a pointer to the cascade workflow's
      terminal event. The operator can see both the rotation commit
      and the cascade failure in the event stream.
- [ ] If the cascade terminates with partial rollback, `RotateSecretWorkflow`
      fails and the operator is alerted loudly — the secret is in a
      partially-rotated state and requires manual reconciliation.
- [ ] Integration test: configure a secret with one working target and
      one deliberately-failing target; rotate; assert both the rotation
      workflow and cascade workflow fail, the working target rolled back
      cleanly, and `SECRET.ROTATION_CASCADE.FAILED` appears in the event
      stream.

## Dev Notes

### Requirements Context Summary

**Epic Context**: This is the middle of three rotation stories (1.5-29 =
handlers, 1.5-30 = cascade, 1.5-31 = auto-rotate). It ties handler
primitives to workflow orchestration and to the operator-facing admin
API. After this story, an operator can configure targets and see them
propagate automatically on every subsequent rotation. Story 1.5-31
builds on this to trigger rotation automatically on leak detection.

**Technical Context**: The cascade workflow runs in Elsa (C#), but the
handlers run in the broker (TypeScript). This cross-process split is
deliberate: Elsa orchestrates, the broker holds plaintext. The only HTTP
calls between them pass non-sensitive identifiers (`secretId`, `targetId`,
`rotationId`) — the broker loads plaintext and handler config on its
own side.

**Integration Points**:
- **Story 1.5-17 (TammaVaultStore)**: broker loads current + previous
  encrypted values for the secret being cascaded.
- **Story 1.5-18 (Secret Activities)**: the `InvokeRotationHandlerActivity`
  is registered alongside the existing secret activities in the Elsa
  activity DLL.
- **Story 1.5-19 (Create/Rotate Workflows)**: `RotateSecretWorkflow` is
  extended to invoke the cascade as a child workflow.
- **Story 1.5-29 (Rotation handlers)**: the cascade queries the broker's
  registered handlers by type.
- **Story 16-7 (RBAC)**: the admin CRUD routes use the owner-role gate
  from the existing RBAC system.
- **Event store**: audit events flow to the same DCB stream as all other
  secret events.

### Key Design Decisions

1. **Cascade is part of `RotateSecretWorkflow`, not a separate opt-in**.
   Once a secret has rotation targets configured, they're always used
   when rotating. Making cascade opt-in would allow an operator to
   rotate a secret in Tamma without propagating to downstream systems,
   leaving dependent services broken and the secret in a state that
   contradicts the operator's configured intent. The cascade is
   inseparable from rotation; to skip it, remove the targets.

2. **Configuration of rotation targets is an admin endpoint, not a
   workflow**. CRUD via `POST /api/admin/secrets/:secretId/rotation-targets`
   gated by the owner role. Adding a target IS a mutation on the
   secret's rotation policy, but it's not a rotation itself — rotation
   is what runs when the target list changes. Keeping target
   configuration as a synchronous REST call avoids the complexity of
   "is my target change committed yet?" questions and keeps the
   workflow count small.

3. **Rollback is best-effort per handler**. If a handler can't roll back
   (GitHub App, some HTTP webhooks), the cascade records "committed,
   rollback unavailable" for that target and alerts the operator.
   The alternative — refusing to cascade to handlers that can't roll
   back — would block operators from configuring rotation for systems
   that genuinely don't support it, and the feature would be
   near-useless. Best-effort with loud alerts is the right trade-off.

4. **Rotation is idempotent from the cascade's perspective**. If a
   target's current value already matches the new value (maybe someone
   ran rotate twice, or the workflow is replaying after a crash), the
   handler returns success without doing anything. This is a contract
   on every handler, enforced by the Story 1.5-29 handler tests. The
   cascade trusts this contract so that crash recovery and Elsa replay
   produce correct final state.

5. **Cascade uses the same polling/alert contract as the LLM-facing
   workflows**. Progress events every 10 seconds, soft alert at 2
   minutes via `alert_orchestrator`, hard timeout at 10 minutes with
   stalled status. This means the LLM can monitor a cascade via
   `checkWorkflow(cascadeId)` just like any other workflow, and won't
   side-channel around it. If the operator is online, they see the
   same alerts. If not, the workflow still terminates cleanly (either
   success, failed, or stalled) and the audit stream captures the full
   state.

6. **Handler configs stay in the broker**. `LoadRotationTargetsActivity`
   returns only target IDs and `handler_type` + `priority` + rollback
   capability. When `InvokeRotationHandlerActivity` runs, it passes
   only the target ID; the broker loads the config, resolves any
   `adminPasswordSecretId` references, and invokes the handler in
   process. This keeps handler configs (which may contain sensitive
   references) off the workflow wire. The orchestrator process never
   sees them.

7. **Rollback ordering is the reverse of rotation**. Sort rotation by
   `priority, created_at` ascending; sort rollback by `-priority,
   -created_at` descending. This matches the "undo in reverse order"
   pattern common in transaction systems and helps when targets have
   implicit dependencies (e.g. a higher-priority target is a DB that
   serves a lower-priority target that caches it).

8. **Target uniqueness is `(secret_id, handler_type, handler_config)`**.
   An operator can add two `http_webhook` targets to the same secret
   if they have different URLs, but not two identical targets. This
   prevents double-invocation from configuration errors while allowing
   fan-out to multiple instances of the same handler type.

### Testing Strategy

- **Unit tests** for `RotationTargetStore`, admin routes, activities
  (with mocked broker HTTP), workflow replay logic.
- **Integration tests** for the Postgres target store against real
  Postgres; for the admin routes against a running API + broker pair;
  for the workflow against a running Elsa engine.
- **Workflow replay tests** using Elsa's deterministic replay harness to
  validate each branch of the cascade state machine.
- **End-to-end test** (AC12) that exercises the full stack: Postgres
  container as downstream system + HTTP webhook receiver + broker +
  API + Elsa + real HTTP calls. This is the integration smoke test
  that catches issues workflow replay alone cannot.
- **Taint-tracking tests** in the e2e path: scan every event in the
  stream and assert no plaintext appears anywhere.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Cascade leaves downstream in inconsistent state after partial rollback | Critical | Loud `SECRET.ROTATION_CASCADE.PARTIAL_ROLLBACK` event + `alert_orchestrator` + operator dashboard surfacing (future UI story); document the manual reconciliation procedure in the README |
| Handler not idempotent → replay produces wrong state | High | Handler contract from Story 1.5-29 mandates idempotency; cascade integration test includes crash-during-cascade replay; any handler that violates idempotency fails its own test suite |
| Hard timeout truncates a legitimate long-running rotation | Medium | 10-minute default is generous; operator can override per-target via config; soft alert at 2 minutes gives visibility before the hard cut; stalled state is audited clearly so operator can reconcile |
| Config cycle (A depends on B's admin creds and B depends on A's) | High | `RotationTargetStore.create` walks the dependency graph and rejects cycles at configure time; unit test for cycle detection; hard to accidentally create because admin creds are rare and usually tied to a single secret |
| Cross-tenant leak via admin API | Critical | RLS on `secret_rotation_targets`, tenant context set per request, zod validation on every input, integration test for cross-tenant access (expects 404) |
| Handler config validation falsely accepts invalid config | Medium | Per-handler zod schemas registered alongside the handler class; `RotationTargetStore.create` uses the handler's schema, not a generic validator; unit test per handler type |
| Workflow non-determinism breaks replay | High | Target list sorted by stable keys (`priority, created_at`); activities are pure given their inputs; handler idempotency covers the crash-in-the-middle case; workflow replay tests exercise every branch |
| `RotateSecretWorkflow` retries the cascade after a failure | High | The workflow is NOT retried automatically on cascade failure; failed cascade terminal state is terminal, and the operator must manually decide whether to retry. Document this — auto-retry of a failed cascade could re-rotate targets that already succeeded, causing further inconsistency |
| Progress events flood the event store | Low | Progress events are emitted every 10s and tagged with `progress: true` so they can be filtered out of most queries; storage impact is minor relative to the rotation events themselves |

### What's NOT in this story

- **Cascade scheduling** (running rotations on a cron): future work. This
  story only handles operator-triggered rotations.
- **Operator dashboard UI for reviewing cascades**: a separate dashboard
  story. This story only emits events; the dashboard story consumes them.
- **Dependency ordering between targets** (e.g. "rotate Postgres before
  HTTP webhook because the webhook depends on the DB"). All targets run
  in parallel. A future story can add `depends_on` for sequential
  ordering; today, operators achieve it with `priority` + multiple
  cascade passes.
- **Automatic rollback retry**: if a rollback fails, the cascade alerts
  the operator once and does not retry. Operator decides whether to
  retry manually or reconcile by other means.
- **Metrics dashboards** for cascade success rate, target failure rate,
  etc.: future observability story.
- **Cross-cascade coordination** (e.g. "cascades A and B share a target
  and should serialise"): not in scope. Each cascade is independent; if
  two cascades hit the same target concurrently, the handler's
  idempotency contract handles the race.
