## Story

As a **Tamma operator running secret rotations in production**,
I want **every rotation — manual, scheduled, or leak-triggered — to be followed by an end-to-end
health check that exercises the newly-rotated secret against the real dependent system**,
so that **I discover a broken cascade within seconds of the rotation, not hours later when the
first production workflow fails, and so that I can automatically roll back when a "required"
health check fails.**

## Overview

Stories 1.5-29 (`RotationHandlers`) and 1.5-31 (`AutoRotateWorkflow`) both enumerated a deferred
item: "post-rotation health checks — after rotating, verifying the dependent system is still
healthy." Story 1.5-30 (`RotationCascadeWorkflow`) also flagged it. Every rotation path today
ends at "new value committed + cascaded to deploy targets" — there is no runtime evidence that
the new value actually *works* against the systems that depend on it.

This story closes the gap by introducing a `PostRotationHealthWorkflow` that runs as the final
phase of every rotation path. It reuses the `probeSecret` machinery from Story 1.5-27 (the same
`IProbeHandler` registry, the same rate limiter, the same redaction pipeline) and drives one
probe per (rotation target × deploy target) combination after the cascade settles.

The key property: **health checks are treated as first-class workflow activities, not
fire-and-forget afterthoughts.** A failed `required` health check triggers the rollback path
from Story 1.5-30 automatically. A failed `advisory` check emits an alert but does not roll
back. A `disabled` secret is skipped entirely — you opted out on purpose.

Health probes run *after* a 5-second settle delay so that eventually-consistent deploy targets
(GitHub Actions repository secrets, K8s Secret propagation, CDN cache warmup) have a chance to
finish applying the new value before we try to exercise it. The settle delay is configurable
per deploy target and capped at 60 seconds (longer propagation is a platform bug, not something
we paper over).

## Acceptance Criteria

1. A new Elsa workflow `PostRotationHealthWorkflow` exists at
   `apps/tamma-elsa/src/Tamma.Workflows/Secrets/PostRotationHealthWorkflow.cs` with inputs
   `{ secretId, tenantId, rotationId, triggerSource: 'manual' | 'scheduled' | 'auto_leak' }`
   and terminal states `HealthOk`, `HealthDegraded`, `HealthFailed`.

2. The workflow reads the secret's `post_rotation_health_check` config field (`required` |
   `advisory` | `disabled`). When the field is missing, the default is `advisory`. When the
   value is `disabled`, the workflow completes immediately with `HealthOk` and emits
   `SECRET.ROTATION.HEALTH_SKIPPED`.

3. Before running any probe, the workflow waits `settleDelayMs` (default 5000, configurable per
   deploy target, hard-capped at 60000). The delay is implemented as an Elsa `Delay` activity so
   that it is checkpointable and replay-safe — no timer state lives in handler code.

4. For every active deploy target on the secret (from Story 1.5-29's rotation plan), the
   workflow resolves a `healthProbeType` and `healthProbeConfig` via a new
   `HealthProbeResolver` that maps rotation targets to probe types. The mapping is:
   - `postgres_password` rotation target → `database_connect` probe (driver: `postgres`,
     host/port/database from the rotation target config)
   - `mysql_password` rotation target → `database_connect` probe (driver: `mysql`)
   - `redis_password` rotation target → `database_connect` probe (driver: `redis`)
   - `http_webhook_signing_secret` rotation target → `http_bearer` probe (URL from the
     rotation target config, expected status `2xx`)
   - `github_app_private_key` rotation target → `github_token` probe hitting the GitHub `/app`
     endpoint with a JWT signed by the newly-rotated private key
   - `jwt_signing_key` rotation target → `jwt_sign_verify` probe (roundtrip sign + verify)
   - `smtp_password` rotation target → `smtp_auth` probe
   - Custom rotation targets supply their own `healthProbeType` + `healthProbeConfig` via the
     rotation handler plugin interface (Story 1.5-43 defines the plugin framework; this story
     only consumes a `probeType?: string` field on the rotation target config)

5. For each resolved (target, probe) pair, the workflow invokes `ProbeSecretActivity` (from
   Story 1.5-27) with a fresh `correlationId = rotationId + ":" + targetId`. The probe result
   is captured verbatim — success/failure + errorCategory + redacted errorMessage + durationMs.

6. Aggregation rules for the workflow's terminal state:
   - If **every** probe returns `success: true` → `HealthOk`, emit `SECRET.ROTATION.HEALTH_OK`
     with tags `{ secretId, tenantId, rotationId }` and data
     `{ probesRun, probesSucceeded: N, durationMs }`.
   - If **any** probe returns `success: false` and the secret's config is `required` →
     `HealthFailed`, emit `SECRET.ROTATION.HEALTH_FAILED`, then trigger `RollbackRotationActivity`
     from Story 1.5-30 to restore the prior secret value across all deploy targets. Emit
     `SECRET.ROTATION.ROLLBACK_TRIGGERED` with the failing target list attached.
   - If **any** probe returns `success: false` and the secret's config is `advisory` →
     `HealthDegraded`, emit `SECRET.ROTATION.HEALTH_DEGRADED` with the failing target list, do
     NOT roll back, but DO trigger an operator alert via the alert bus from Story 1.5-30.

7. Partial success (e.g. 3 of 4 deploy targets healthy) is always treated as failure — no
   "mostly healthy" terminal state exists. The operator must either fix the failing target and
   re-trigger a rotation, or explicitly mark the target disabled.

8. A `rotation_health_checks` table captures the outcome for audit and dashboard display:
   ```sql
   CREATE TABLE rotation_health_checks (
     id UUID PRIMARY KEY,
     rotation_id UUID NOT NULL,
     secret_id UUID NOT NULL,
     tenant_id UUID NOT NULL,
     trigger_source TEXT NOT NULL,
     terminal_state TEXT NOT NULL,             -- HealthOk|HealthDegraded|HealthFailed|HealthSkipped
     probes_run INT NOT NULL,
     probes_succeeded INT NOT NULL,
     duration_ms INT NOT NULL,
     rolled_back BOOLEAN NOT NULL DEFAULT FALSE,
     created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
     INDEX idx_rhc_secret (secret_id, created_at DESC),
     INDEX idx_rhc_rotation (rotation_id)
   );
   ```

9. Rotation paths in Stories 1.5-29, 1.5-30, and 1.5-31 are updated to invoke
   `PostRotationHealthWorkflow` as their final child workflow. This is a non-optional wiring
   change — the rotation workflows do not reach terminal `Success` state until
   `PostRotationHealthWorkflow` has reached one of its own terminal states.

10. Replay test: record the activity outputs of a full rotation + health check sequence, replay
    the workflow from scratch, assert byte-identical state across both runs. Required and
    advisory semantics are both covered.

11. Taint-tracking test: inject a sentinel plaintext into a rotation target, force a health
    probe failure that would naively echo the plaintext in the error message, assert the
    sentinel never appears in any field of `SECRET.ROTATION.HEALTH_FAILED` audit data, any log
    line emitted by the workflow, or any `rotation_health_checks` row.

12. Integration test against a real Postgres (testcontainers): create a `postgres_password`
    secret, rotate it, run `PostRotationHealthWorkflow`, assert a `database_connect` probe is
    issued and succeeds. Then repeat with a deliberately broken cascade (rotation handler
    returns success but does not actually update the Postgres user password), assert the
    health check fails and triggers rollback in `required` mode.

13. End-to-end alert test in `advisory` mode: rotate a secret where the cascade is silently
    broken, assert an operator alert fires (via the bus from Story 1.5-30) with the failing
    target list, assert NO rollback occurs.

14. Rate limiter interaction: the post-rotation health check must NOT consume the per-secret
    probe rate limit budget. A new rate-limit bucket `post_rotation_health` is reserved with
    its own quota (default: unlimited within the workflow, since there is at most one health
    check per rotation). Document this in `secret-broker/README.md`.

## Dev Notes

### Requirements Context Summary

**Epic Context:** Rotations without health checks are the most common way a silently broken
cascade reaches production. Story 1.5-29 rotates the value; Story 1.5-30 distributes it to
deploy targets; neither stops to ask "does this new value actually open the door it needs to
open?" Past incidents in similar systems make it clear that the gap between "cascade reported
success" and "secret works end-to-end" is exactly where rotations go silently wrong: a GitHub
Actions repository secret is updated, but the workflow that needs it caches the old value in an
environment variable; a Postgres password is rotated on the primary, but pgbouncer still holds
an old-password connection pool; a JWT signing key rotates, but the downstream verifier hasn't
refreshed its JWKS cache. The only robust mitigation is an active check that exercises the new
secret against the real dependent system.

**Technical Context:** The piece we're missing is *orchestration*, not detection. Story 1.5-27
already built the probe primitives and the handler registry. Story 1.5-30 already built the
rollback path. This story composes them into a deterministic, replay-safe workflow that runs as
the final phase of every rotation and is itself audited as a first-class event.

**Integration Points:**
- **Story 1.5-27** — reuses `ProbeSecretActivity`, `ProbeHandlerRegistry`, probe rate limiter
  (with a new bucket), and the redaction pipeline
- **Story 1.5-29** — reads rotation plan metadata to enumerate (target, deployTarget) pairs
- **Story 1.5-30** — invokes `RollbackRotationActivity` on `required` failure; consumes the
  operator alert bus on `advisory` failure
- **Story 1.5-31** — auto-rotate workflow is updated to wait for health check before marking
  rotation complete
- **Story 1.5-16** — adds `post_rotation_health_check` to the secret metadata schema

### Implementation Guidance

**Key Design Decisions:**

1. **Health checks are mandatory by default.** The config field defaults to `advisory` (alert
   on failure, no rollback) so that *all* secrets get a post-rotation probe even when the
   operator has not explicitly opted in. `disabled` must be a deliberate choice — this way the
   safer default is the default.

2. **Settle delay is workflow-visible, not hidden in handler code.** An Elsa `Delay` activity
   is replay-safe: re-running the workflow produces the same timeline. A `Thread.Sleep` inside
   a handler would produce a race condition on replay.

3. **`required` triggers rollback, `advisory` does not.** This is the entire point of having
   two modes. Operators who have battle-tested their cascade can opt into `required`; new
   secrets start at `advisory` until they've been through a few rotations without issue.

4. **Partial failure is failure.** There is no "3 of 4 targets healthy" middle ground. Either
   the cascade is fully healthy or it isn't — anything else is false confidence that will
   bite us later.

5. **Rate limiter bypass for health checks.** A rotation of 20 secrets in a row, each with 3
   deploy targets, would otherwise consume 60 slots out of a 10/min per-secret bucket. That
   is unacceptable for a scheduled bulk rotation. The `post_rotation_health` bucket is
   reserved specifically for this path and is unlimited within the workflow — but the probe
   still emits the same audit events, so the observability story is unchanged.

6. **Rollback is a workflow activity, not a hook.** Making rollback a distinct
   `RollbackRotationActivity` call ensures it is audited, retried on transient failure, and
   visible in the Elsa UI. Hidden rollback-on-failure inside an exception handler would
   disappear from the audit trail.

7. **`HealthProbeResolver` is a lookup table, not a plugin interface.** Plugin probe types
   come from Story 1.5-43; this story only consumes a `probeType?: string` override on the
   rotation target config. That keeps the resolver simple — if custom, use it as-is; if
   built-in, map via the 7-entry table.

**Technical Specifications:**

- **Workflow shape:**
  ```
  PostRotationHealthWorkflow
    → ReadSecretConfigActivity
      → if disabled: terminal HealthSkipped
    → Delay(settleDelayMs)
    → ForEach deployTarget:
        → ResolveHealthProbeActivity
        → ProbeSecretActivity
    → AggregateResultsActivity
      → all pass: terminal HealthOk
      → any fail + required: RollbackRotationActivity → terminal HealthFailed
      → any fail + advisory: FireAlertActivity → terminal HealthDegraded
    → PersistHealthCheckRowActivity
    → EmitAuditEventActivity
  ```

- **`rotation_health_checks` querying patterns:**
  - Dashboard: `SELECT * FROM rotation_health_checks WHERE secret_id = ? ORDER BY created_at DESC LIMIT 20`
  - Alerting: `SELECT count(*) FROM rotation_health_checks WHERE terminal_state = 'HealthDegraded' AND created_at > now() - interval '24 hours'`

- **Settle delay per rotation target (defaults):**
  - `postgres_password`: 5000 ms (pgbouncer pool refresh)
  - `github_app_private_key`: 10000 ms (GitHub Actions secret propagation)
  - `http_webhook_signing_secret`: 2000 ms (CDN cache)
  - `jwt_signing_key`: 15000 ms (JWKS endpoint cache)
  - `smtp_password`: 1000 ms
  - default: 5000 ms

### Risks and Mitigations

| Risk | Severity | Mitigation |
| ---- | -------- | ---------- |
| Settle delay too short for eventually-consistent targets (CDN, JWKS) → false negative | High | Per-target settle delay with sensible defaults; hard-cap at 60s so operators can't paper over propagation bugs |
| `required` mode triggers rollback on a transient network blip → rollback loop | High | Rollback only fires on `auth_failed` / `not_found` error categories; `network_error` and `timeout` are treated as advisory failures regardless of config (documented exception) |
| Bulk rotations exhaust probe rate limit budgets | Medium | Reserved `post_rotation_health` bucket with bypass; see AC14 |
| Rollback itself fails → stuck in inconsistent state | High | Rollback activity has its own retry + escalation path (covered by Story 1.5-30); this story only invokes it |
| Probe plaintext leakage via error messages | Critical | Reuses Story 1.5-27 redaction + taint-tracking tests; no new plaintext handling introduced |
| Replay non-determinism from wall-clock settle delay | Medium | Elsa `Delay` activity, not `Thread.Sleep`; timer state is workflow-owned |

## Logging Requirements

Infrastructure and deployment components MUST use structured logging via pino/ILogger (never
`console.log` in production code).

- **INFO**: Health check started (`rotationId`, `secretId`, `triggerSource`), settle delay
  elapsed, each probe dispatched (`targetId`, `probeType`), terminal state reached
  (`HealthOk` | `HealthDegraded` | `HealthFailed` | `HealthSkipped`), rollback triggered
- **DEBUG**: Resolver selected probe type for target, rate-limit bucket used, row persisted
  to `rotation_health_checks`
- **WARN**: Probe returned failure (`errorCategory`), advisory mode alert fired, settle delay
  exceeded configured value but within hard cap, taint scan replaced bytes (latent leak in a
  dependency — escalate)
- **ERROR**: Rollback activity failed, audit event emission failed, `rotation_health_checks`
  insert failed, workflow replay produced non-deterministic state
- **Structured context**: Always include
  `{ rotationId, secretId, tenantId, triggerSource, terminalState, durationMs }`. NEVER log
  plaintext, probe config content that might echo a credential, or raw error strings from
  probe handlers (those are already redacted upstream but log lines must reference the
  `sanitizedErrorMessage` field, not the raw `err.message`).
- **Credential safety**: Health checks never handle plaintext directly — all handling is
  delegated to Story 1.5-27's broker internal endpoint. Log lines reference `secretId` and
  `rotationId` only.
- **Audit events**: `SECRET.ROTATION.HEALTH_OK` / `HEALTH_DEGRADED` / `HEALTH_FAILED` /
  `HEALTH_SKIPPED` / `ROLLBACK_TRIGGERED` are the canonical record; log lines are for
  debugging only and can be sampled.
