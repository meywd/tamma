# Story 1.5-41: mTLS transport between Elsa and the secret broker

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / Transport)
**Status**: ready-for-dev
**Priority**: Medium
**Depends on**: Story 1.5-17 (TammaVaultStore + broker HTTP service), Story 1.5-18 (Elsa `HttpBrokerClient`), Story 1.5-29 (rotation handler framework — for cert rotation)

## Story

As a **Tamma operator running a high-assurance deployment in a PCI or HIPAA scope**,
I want **mutual TLS between the C# Elsa workflow engine and the TypeScript secret broker, so that the broker only accepts requests from Elsa pods with a valid client certificate issued by a Tamma-controlled CA**,
so that **an attacker who compromises an orchestrator container cannot forge broker requests even if they steal the current bearer token, and my auditors can see cryptographic proof that only authorised services talk to the vault.**

## Context — Why this story exists

Story 1.5-18 shipped the Elsa-to-broker HTTP surface with a deliberate
simplification: *"Plain Bearer token over internal Docker network."*
That's the right default for the single-host Hetzner VPS deployment
where all traffic stays on a Docker bridge network and the attack
surface is the host itself. For regulated deployments — PCI DSS, HIPAA,
SOC 2 Type II environments with external auditors — the auditor will
ask for defence-in-depth on internal service-to-service traffic. A
bearer token is a single shared secret; if it leaks, every request
signed with it is valid. mTLS binds the caller to a certificate that
must be presented at TLS handshake time, so a leaked token is useless
without also stealing the private key.

This story adds mTLS as a transport-level option on the broker HTTP
interface. When enabled, the broker rejects requests without a valid
client cert at handshake time (before any application code runs), and
Elsa's `HttpBrokerClient` presents its cert on every call. When NOT
enabled — the default for simple deployments — the broker falls back
to the existing Bearer token behaviour. Operators opt in via a single
config flag.

The subtle piece is **certificate lifecycle**: client and server certs
have their own expiry and need rotation. This story wires the broker's
own server cert and every Elsa client cert into the existing rotation
handler framework from Story 1.5-29, so cert rotation is a native
cascade like any other secret.

### Architecture summary

```
Config flag: broker.transport
  = 'plain'   (default) → Bearer token auth, existing 1.5-18 behaviour
  = 'mtls'    (opt-in)  → mTLS handshake required; bearer token optional fallback

Broker:
  - Fastify HTTPS server with `requestCert: true, rejectUnauthorized: true`
  - CA bundle loaded from Tamma vault (bounded recursion; cert is itself a secret)
  - Client cert subject validated against `service_identities` table
  - Optional bearer token as fallback for plain-transport callers (if configured)

Elsa HttpBrokerClient:
  - HttpClient configured with client cert from disk OR from Elsa's own vault
  - Cert subject is assigned at bootstrap; renewed via rotation handler
  - On handshake failure: log + retry once, then fall back to bearer if plain is allowed

Certificate rotation:
  - BrokerTlsCertHandler implements IRotationHandler (Story 1.5-29)
  - ElsaClientTlsCertHandler implements IRotationHandler
  - Both are configured as rotation targets on their respective cert secrets
  - On rotation: new cert is issued, services swap, old cert is revoked
```

## User Story

As a **Tamma security engineer**,
I want **the broker to authenticate every incoming call cryptographically via TLS client certificates, issued by a CA I control, with automatic rotation and a clean fallback path for non-mTLS environments**,
so that **the transport between the orchestrator and the vault has cryptographic integrity, the audit trail captures cert identity on every call, and I can show the auditor a rotation schedule on the broker's own server cert.**

## Acceptance Criteria

### AC1: `broker.transport` config flag

- [ ] The broker's config schema gains a new top-level field:
  ```typescript
  interface BrokerConfig {
    transport: 'plain' | 'mtls';      // default 'plain'
    mtls?: {
      serverCertSecretRef: string;    // Tamma secret containing PEM {cert, key}
      caBundleSecretRef: string;      // Tamma secret containing PEM CA bundle
      allowBearerFallback: boolean;   // default false; if true, accept bearer-only requests when no client cert is presented
      minTlsVersion: 'TLSv1.2' | 'TLSv1.3';  // default 'TLSv1.3'
      clientCertRequired: boolean;    // default true; if false, client cert is requested but not mandatory
    };
    plainBearerToken?: {
      tokenSecretRef: string;
    };
  }
  ```
- [ ] When `transport === 'mtls'`, `mtls` config MUST be set. Missing
      sub-fields produce a clear boot-time config error.
- [ ] When `transport === 'plain'`, `mtls` config is ignored and the
      broker boots in the existing Story 1.5-18 mode.
- [ ] `allowBearerFallback: true` is documented as a migration
      convenience: operators can deploy mTLS incrementally (broker
      first, then each Elsa pod) with fallback enabled, then flip it
      off once every caller has a client cert.
- [ ] Config validation (zod) at startup. If `transport === 'mtls'`
      and the referenced secrets are not available, the broker
      fails to start with a typed `BrokerTransportConfigError`.

### AC2: Server-side mTLS termination in Fastify

- [ ] `packages/secret-broker/src/server.ts` (or equivalent) accepts
      an optional HTTPS config block. When `transport === 'mtls'`:
  1. Resolve `serverCertSecretRef` to plaintext `{cert, key}`.
  2. Resolve `caBundleSecretRef` to plaintext PEM bundle.
  3. Construct Fastify with:
     ```typescript
     Fastify({
       https: {
         cert: serverCert.cert,
         key: serverCert.key,
         ca: caBundle,
         requestCert: true,
         rejectUnauthorized: clientCertRequired,
         minVersion: minTlsVersion,
       },
     });
     ```
- [ ] Cert + key are loaded into a Node `Buffer`, passed to Fastify,
      and then the Buffer is zeroised. Fastify clones the key into
      its own memory before the zeroise, so the broker's copy no
      longer holds plaintext.
- [ ] When `transport === 'plain'`, the broker starts a plain HTTP
      server exactly as today. No TLS at all — no accidental mixed
      mode.
- [ ] Boot log clearly states the transport mode: `"broker starting
      in mtls mode; server cert fingerprint=sha256:..."` or
      `"broker starting in plain mode; bearer-token auth"`. No
      ambiguity in ops logs.

### AC3: Client cert validation middleware

- [ ] A new middleware `packages/secret-broker/src/auth/mtls-auth.ts`
      runs BEFORE the existing bearer-token middleware in the Fastify
      preHandler chain:
  1. Extract the peer certificate via `request.raw.socket.getPeerCertificate(true)`.
  2. If no cert is present:
     - If `clientCertRequired === false` AND `allowBearerFallback === true`,
       fall through to the bearer middleware.
     - Otherwise reject with 401 `{error: 'client_cert_required'}`.
  3. Validate the cert's issuer chain against the configured CA bundle
     (Node already does this at the TLS layer; this is a defence-in-depth
     check).
  4. Extract the cert subject's Common Name (CN) and Subject Alternative
     Name (SAN) entries.
  5. Look up the subject in the `service_identities` table
     (AC4). If found and enabled, attach the service identity to the
     request context. If not found, reject with 403 `{error: 'unknown_service_identity'}`.
  6. Emit audit event `BROKER.MTLS.AUTHENTICATED` with
     `{subject, serviceIdentityId, certFingerprint, tlsVersion}`.
- [ ] If a request is authenticated via BOTH client cert AND bearer
      token (belt-and-suspenders mode), the cert identity wins and
      the bearer is logged as "also present" but not used for
      authorisation. Dual-presentation is a smooth migration path.
- [ ] Audit events capture the cert fingerprint (SHA-256 of DER),
      not the cert itself — the cert is not sensitive but the
      fingerprint is a stable identifier that's compact enough to
      index.
- [ ] Unit tests mock the Fastify request socket and cover: valid
      cert + known identity, valid cert + unknown identity, no cert
      + fallback disabled (reject), no cert + fallback enabled
      (bearer path), invalid issuer (reject at TLS layer — test
      via integration).

### AC4: `service_identities` schema + store

- [ ] Migration `database/migrations/028_service_identities.sql`:
  ```sql
  CREATE TABLE IF NOT EXISTS service_identities (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id         UUID,                   -- NULL for system-level identities
    name              TEXT NOT NULL,          -- 'elsa-orchestrator', 'elsa-worker-1'
    subject_dn        TEXT NOT NULL,          -- the full X.509 subject DN
    cert_fingerprint  TEXT NOT NULL,          -- SHA-256 of current cert DER
    client_cert_secret_id UUID REFERENCES tamma_vault_secrets(secret_id) ON DELETE SET NULL,
    enabled           BOOLEAN NOT NULL DEFAULT true,
    allowed_routes    TEXT[] NOT NULL DEFAULT ARRAY['*'],  -- route patterns the identity may call
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (subject_dn)
  );
  ```
- [ ] System-level identities (tenant_id = NULL) are for cross-tenant
      services like Elsa. Tenant-scoped identities are a future
      extension; MVP only uses system identities.
- [ ] `allowed_routes` is a whitelist of Fastify route patterns the
      identity is authorised to call. Default `*` means "any route."
      Operators can restrict: e.g. an `elsa-worker-1` identity gets
      only `['/internal/rotation/*', '/internal/secrets/get']`,
      while `elsa-orchestrator` gets everything.
- [ ] `packages/secret-broker/src/auth/service-identity-store.ts`
      exports `ServiceIdentityStore` with methods:
  ```typescript
  interface IServiceIdentityStore {
    findBySubject(subjectDn: string): Promise<ServiceIdentity | null>;
    findByFingerprint(fingerprint: string): Promise<ServiceIdentity | null>;
    list(): Promise<ServiceIdentity[]>;
    create(input: CreateServiceIdentityInput): Promise<ServiceIdentity>;
    updateFingerprint(id: string, newFingerprint: string): Promise<void>;
    disable(id: string): Promise<void>;
  }
  ```
- [ ] The auth middleware calls `findBySubject` on every request,
      cached for 30 seconds to avoid hitting Postgres on every call.
- [ ] `updateFingerprint` is called by the cert rotation handler
      (AC7) when a service's cert is renewed.
- [ ] Unit + integration tests against Postgres.

### AC5: Admin CRUD for service identities

- [ ] Fastify route module at
      `packages/api/src/routes/admin/service-identities.ts`:
  - `GET    /api/admin/service-identities` — list
  - `POST   /api/admin/service-identities` — create
  - `GET    /api/admin/service-identities/:id` — get
  - `PATCH  /api/admin/service-identities/:id` — update
  - `DELETE /api/admin/service-identities/:id` — delete
  - `POST   /api/admin/service-identities/:id/issue-cert` — issue a new client cert for this identity (invokes the internal CA)
- [ ] Gated by `requirePermission('settings:manage')` (owner role).
- [ ] `POST /:id/issue-cert` response body contains the newly-issued
      cert + key in PEM format. The operator MUST save this response
      before closing — the key is NEVER stored in a form the operator
      can retrieve later (vault-only mode on the Tamma side, then
      flushed from the response buffer). A warning banner in the
      response reminds the operator.
- [ ] Alternative flow: `POST /:id/issue-cert?autoInstall=true`
      stores the new cert + key as a Tamma secret referenced by
      `client_cert_secret_id` and returns only the fingerprint +
      reference. This is the preferred flow for Elsa workers, which
      read their cert from the Tamma vault on boot.
- [ ] Audit events: `SERVICE_IDENTITY.CREATED`, `.UPDATED`,
      `.DELETED`, `.CERT_ISSUED`, `.DISABLED`.
- [ ] Integration tests cover owner vs member, cert issuance,
      auto-install flow.

### AC6: Elsa `HttpBrokerClient` presents a client cert

- [ ] The C# `HttpBrokerClient` from Story 1.5-18 is extended to
      load a client cert from one of two sources:
  1. **Disk**: `TAMMA_BROKER_CLIENT_CERT_PATH` +
     `TAMMA_BROKER_CLIENT_KEY_PATH` env vars pointing at PEM files.
     Used for legacy deploys where the cert comes from a k8s secret
     mount.
  2. **Vault**: `TAMMA_BROKER_CLIENT_CERT_SECRET_ID` env var
     referencing a Tamma secret. The client calls the broker with
     bearer auth on first boot to fetch its own cert, then swaps
     to mTLS for all subsequent calls. Bootstrap chicken-and-egg
     problem is solved by accepting bearer on the first call via
     a time-limited bootstrap token.
- [ ] The client's `HttpClientHandler` is configured with
      `ClientCertificates.Add(cert)` and
      `SslProtocols = SslProtocols.Tls12 | SslProtocols.Tls13`.
- [ ] The client caches the `HttpClient` instance for the process
      lifetime — reconstructing per call would leak sockets and
      defeat connection pooling. On cert rotation, the client is
      notified via a callback from the rotation handler and the
      `HttpClient` is replaced atomically.
- [ ] When `transport === 'plain'` on the broker side, the client
      uses a bearer token exactly as today. The client's config has
      a flag `useMtls: bool` that operators set to match the broker.
- [ ] Handshake failure handling: if the broker is in mTLS mode and
      the client presents no cert (or a bad cert), the TLS handshake
      fails. The client logs the failure and retries ONCE after a
      500ms delay (gives room for transient network issues). After
      that, it throws `BrokerMtlsHandshakeError`.
- [ ] Unit tests in C# cover: cert loading from disk, cert loading
      from vault, cert rotation callback, handshake retry.
- [ ] Integration test with a real mTLS broker boots both processes
      and exercises a full secret-create round trip.

### AC7: Cert rotation via `IRotationHandler` framework

- [ ] A new rotation handler `BrokerServerCertHandler` in
      `packages/secret-broker/src/rotation-handlers/broker-server-cert-handler.ts`:
  - Implements `IRotationHandler<ServerCertPayload>`.
  - On rotation: generates a new server cert signed by the CA,
    writes it to the vault, and reloads the broker's TLS context
    in-place (no restart). Reload uses Fastify's
    `server.setSecureContext()` (Node TLS hot-reload API).
  - Verifies the new cert matches the old CA — if the CA has been
    rotated, the handler fails and requires a full redeploy (CA
    rotation is a rarer, more disruptive operation handled
    manually).
- [ ] A second handler `ElsaClientCertHandler` in the same directory:
  - Implements `IRotationHandler<ClientCertPayload>`.
  - On rotation: issues a new client cert via the internal CA,
    writes it to the vault under the same `client_cert_secret_id`,
    notifies the Elsa client via HTTP callback `POST
    /internal/broker/reload-cert` which the Elsa `HttpBrokerClient`
    listens on.
- [ ] Both handlers are registered in the handler registry from
      Story 1.5-29 and configurable as rotation targets via the
      cascade workflow (Story 1.5-30). This means an operator can
      schedule cert rotation on a cron (Story 1.5-38) — e.g.
      "rotate broker server cert every 90 days, rotate Elsa client
      certs every 30 days" — and it happens automatically.
- [ ] The internal CA is itself a Tamma secret. A separate
      `InternalCaHandler` is NOT in scope here; CA rotation is
      manual and rare.
- [ ] Integration test rotates the broker server cert end-to-end
      and verifies every in-flight connection (via a long-running
      streaming response mock) is gracefully drained while new
      connections use the new cert.

### AC8: Internal certificate authority (bounded recursion)

- [ ] An internal CA is bootstrapped on first run when
      `transport === 'mtls'` is enabled and no CA exists in the
      vault. The CA key is generated via Node's `crypto.generateKeyPairSync`
      with RSA 4096 or ECDSA P-384.
- [ ] The CA cert + key are stored as a Tamma secret with
      `mode: 'vault_copy'` — the cert is retrievable (it's
      distributed to every peer), but the key is revocation-only
      after first read by the CA module.
- [ ] The bounded-recursion concern ("the broker stores its own
      auth credential in a vault it's trying to protect") is
      addressed by:
  1. Bootstrapping the CA before enabling mTLS. On first boot with
     `transport === 'mtls'`, the broker starts in plain mode,
     generates the CA, issues its own server cert, then restarts
     into mtls mode. Subsequent boots skip this dance.
  2. The CA key is gated behind a separate encryption key (the
     broker's master key, already present from Story 1.5-17) so
     a database dump alone doesn't expose it.
  3. Operators who want a pre-existing corporate CA instead of
     the Tamma-generated one can provide it via
     `broker.mtls.caBundleSecretRef` pointing at a pre-seeded
     secret. The broker uses the provided CA exclusively and
     does not generate its own.
- [ ] CA is scoped to the broker process. Cross-broker federation
      (multiple broker pods sharing a CA) is not in scope — the
      MVP assumes one broker instance. A future story can add a
      shared CA model.
- [ ] `openssl x509 -in ca.pem -noout -subject` and
      `openssl verify -CAfile ca.pem broker-server.pem` are used
      in the integration test to verify the issuance chain
      independent of the broker's own code.

### AC9: Fallback + migration path

- [ ] The `allowBearerFallback: true` flag in `broker.mtls` config
      lets operators migrate incrementally:
  1. Day 0: broker in plain mode, Elsa uses bearer. Baseline.
  2. Day 1: flip broker to `mtls` with
     `allowBearerFallback: true` and `clientCertRequired: false`.
     Broker accepts both mTLS and bearer; Elsa continues on bearer.
  3. Day 2: update Elsa pods one at a time to present client certs.
  4. Day 3: flip `clientCertRequired: true` so every caller MUST
     present a cert, but keep `allowBearerFallback: true` for any
     stragglers (e.g. an admin CLI).
  5. Day 4: flip `allowBearerFallback: false`. mTLS is now the
     only auth path.
- [ ] Integration test exercises the migration: boot broker with
      fallback on, make a bearer-only request → succeeds; make a
      mTLS request → succeeds; flip fallback off; bearer-only request
      → 401.
- [ ] Operator dashboard (Story 1.5-39) surfaces the current
      transport mode and fallback state so the flip is visible.

## Dev Notes

### Requirements Context Summary

**Epic Context**: This story completes the transport security story
for the Elsa-to-broker channel. Story 1.5-18 shipped bearer-token
auth as a deliberate simplification; this story adds mTLS on top as
an opt-in for high-assurance environments. After this story, the
broker can be configured for either transport mode, and operators
have a clear migration path.

**Technical Context**: mTLS termination happens at the Fastify level
via Node's TLS socket. The broker's own server cert is stored as a
Tamma secret and rotated via the same rotation handler framework as
every other cert. The Elsa client cert is similarly stored and
rotated. The internal CA is bootstrapped on first run and lives in
the vault, which is a bounded recursion that's addressed by a
one-time plain-mode bootstrap.

**Integration Points**:
- **Story 1.5-17 (TammaVaultStore)**: server cert, client certs,
  and CA are stored as Tamma secrets.
- **Story 1.5-18 (Elsa HttpBrokerClient)**: extended to present a
  client cert and respond to rotation callbacks.
- **Story 1.5-29 (IRotationHandler)**: cert rotation uses the same
  handler framework as DB password rotation.
- **Story 1.5-30 (RotationCascadeWorkflow)**: cert rotation flows
  through the cascade for coordinated updates across broker +
  Elsa workers.
- **Story 1.5-38 (Cascade scheduling)**: cert rotation can be
  scheduled on a cron.
- **Story 1.5-39 (Operator dashboard)**: surfaces transport mode
  + service identities + cert expiry warnings.

### Key Design Decisions

1. **mTLS is opt-in, not the default**. A single-host Hetzner VPS
   deploy running everything on a Docker bridge network does not
   need mTLS; a bearer token over loopback is sufficient. Making
   mTLS the default would force every operator to bootstrap a CA
   and rotate certs for no added security benefit. Opt-in via a
   single config flag keeps the simple path simple and the
   high-assurance path available.

2. **Cert rotation uses the existing `IRotationHandler` framework**.
   Certs are secrets; secrets rotate via handlers; therefore certs
   rotate via handlers. Reusing the framework means cert rotation
   gets cascade, scheduling, notification, and audit for free.
   Writing a second cert-specific rotation pipeline would
   duplicate all of that.

3. **Internal CA bootstraps on first boot via plain-mode
   stepping-stone**. The chicken-and-egg problem ("the broker
   stores the CA in a vault it wants to protect with the CA") is
   solved by a one-time plain-mode boot that generates the CA,
   issues the server cert, then restarts into mtls mode. After
   that, the broker reads the CA from the vault exactly like any
   other secret. Operators with an existing corporate CA can
   bypass the generation step entirely.

4. **`allowBearerFallback` is explicitly documented as a migration
   aid, not a permanent state**. Operators who flip it on and
   never flip it off have worse security than plain mode — an
   attacker with a bearer token can bypass mTLS. The fallback is
   meant for the migration window only; the operator dashboard
   (Story 1.5-39) displays a banner when fallback is on for more
   than 7 days.

5. **Per-identity route whitelists default to `*`**. Route-level
   authorisation adds another layer but it's optional. Most
   operators will grant Elsa `*` and call it done; operators with
   tighter requirements (e.g. PCI) can restrict individual
   identities to specific routes. The default is permissive
   because the identity check itself is already a meaningful
   boundary.

6. **The Elsa client caches its `HttpClient` and replaces it on
   cert rotation via callback, not poll**. Recreating the
   `HttpClient` per request would leak sockets; polling for cert
   changes would waste resources. A rotation callback is fast
   and simple.

7. **Cert fingerprint is SHA-256 of DER, not CN**. CNs can collide;
   fingerprints are cryptographically unique. The fingerprint is
   the stable identifier for audit events and cache keys. CN /
   subject DN are only used for the initial identity lookup.

8. **`clientCertRequired` is separate from `transport === 'mtls'`**.
   A broker in `mtls` mode with `clientCertRequired: false` will
   request a cert but not reject if none is presented. This is
   useful during migration: enable the mTLS listener, but don't
   break existing bearer-only callers yet. Combined with
   `allowBearerFallback`, this gives a smooth upgrade path.

### Testing Strategy

- **Unit tests** for config validation, cert loading, middleware
  logic, service identity lookup, route whitelist enforcement.
- **Integration tests** boot a real Fastify HTTPS server and
  exercise the handshake with various client cert configurations
  (valid, invalid issuer, self-signed, no cert, disabled identity).
- **Rotation tests** exercise the cert rotation handlers with a
  long-running traffic generator; assert no in-flight request is
  interrupted and new requests use the new cert.
- **Migration path test** steps through the 5-day migration
  sequence in a single test run, flipping config flags between
  sub-tests.
- **C# tests** for the Elsa `HttpBrokerClient` cover disk + vault
  cert loading, rotation callback, handshake retry.
- **End-to-end test** runs broker + Elsa + API together in mtls
  mode and exercises a full `create_secret` → `rotate_secret` flow.
- **Taint tracking**: assert no cert key material appears in any
  log line, any event payload, or any response body (except
  `POST /issue-cert` which returns it exactly once).

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Bounded-recursion bootstrap bug leaves broker unable to start | Critical | First-boot flow is test-covered with a fresh Postgres + empty vault; failure leaves a clear error log with recovery instructions; operators can always regenerate the CA via a documented manual procedure |
| Cert rotation hangs mid-rotation and breaks traffic | Critical | Hot reload via `setSecureContext` is atomic; rotation integration test runs with traffic; rollback to previous cert is a handler-level capability from Story 1.5-30 |
| Client cert leak via `POST /issue-cert` response | High | Response is rendered once, never stored; auto-install flow is preferred and stores in vault; operator dashboard surfaces recent issuances so an unintended call is visible |
| `allowBearerFallback` left on permanently → no security gain | Medium | Dashboard banner after 7 days of fallback-enabled state; migration runbook explicitly warns; ADR documents the temporary nature |
| Service identity cache staleness after admin disable | Low | 30-second cache TTL is short enough that a disable propagates within 30s; emergency use case (immediate revoke) can call `POST /api/admin/service-identities/:id/flush-cache` to invalidate immediately |
| Corporate CA bundle malformed → broker refuses to start | Medium | Config validation parses the CA bundle at boot time via `crypto.X509Certificate`; a malformed bundle produces a clear error before the listener binds |
| Internal CA key compromised → attacker can issue arbitrary client certs | Critical | CA key encrypted with the broker's master key; access to the CA key is gated through a dedicated `InternalCaManager` class with audit logging on every issuance; consider HSM backing for the CA in a future story |
| Multiple broker pods disagree on CA state | High | MVP assumes a single broker pod. Multi-pod broker scaling is an explicit won't-do for v1 — rationale: current deploys run one broker per instance, and scaling out requires shared session state from Story 1.5-38 (which also solves cron leader election). If multi-pod becomes needed, revisit as a new story that builds on 1.5-38's leader-election primitive. Integration test for 1.5-41 boots a single broker only. |
| Migration from plain to mtls breaks CI/CD calls that use bearer | Medium | `allowBearerFallback: true` explicitly supports hybrid mode; migration runbook walks operators through the 5-day flow; CI/CD callers are identified via the admin dashboard's service identity view |
| `BrokerServerCertHandler` cannot reload without restart on older Node | Low | Minimum Node version is already 22 LTS (project requirement); `setSecureContext` is supported; test asserts on Node 22 |

## Related follow-on work

- **A future story for HSM-backed CA keys**: store the internal CA
  key in an HSM (PKCS#11 or cloud KMS) so even a broker compromise
  doesn't leak the CA. Worthwhile for the highest-assurance
  deployments but not needed for MVP mTLS.
- **A future story for cross-broker CA federation**: multi-pod
  broker deployments need a shared CA or a trust-on-first-use
  model. Not in scope because MVP is single-broker.
- **A future story for per-tenant service identities**: tenant-scoped
  service identities that can only access their own tenant's data.
  MVP uses system-wide identities only.
- **Story 1.5-30 (RotationCascadeWorkflow)**: cert rotation flows
  through the cascade; this story wires the handlers but doesn't
  change the cascade itself.
- **Story 1.5-38 (Cascade scheduling)**: cert rotation can be
  scheduled on a cron after this story lands. No changes to 1.5-38
  required.
- **Story 1.5-39 (Operator dashboard)**: surfaces transport mode,
  service identities, cert expiry warnings, and the
  `allowBearerFallback` banner. This story emits the state; 1.5-39
  renders it.
