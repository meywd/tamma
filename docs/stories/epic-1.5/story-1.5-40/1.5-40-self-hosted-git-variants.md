# Story 1.5-40: Self-hosted git platform variants (GHES / GitLab SM / Bitbucket Server / Azure DevOps Server)

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / Platform Integration)
**Status**: ready-for-dev
**Priority**: Medium
**Depends on**: Story 1.5-23 (GitHub Actions secret store), Story 1.5-24 (GitLab CI/CD variables store), Story 1.5-25 (Bitbucket Pipelines secret store), Story 1.5-26 (Azure DevOps variable groups store)

## Story

As a **Tamma operator running on-premises in a regulated environment**,
I want **the existing git-platform secret mirrors to work against self-hosted GitHub Enterprise Server, GitLab Self-Managed, Bitbucket Server, and Azure DevOps Server endpoints — not just the SaaS instances — so that my secrets can flow to CI/CD pipelines hosted entirely inside my network perimeter**,
so that **compliance requirements that forbid data leaving our datacenter are satisfied and Tamma is usable beyond the github.com + gitlab.com + bitbucket.org + dev.azure.com happy path.**

## Context — Why this story exists

Stories 1.5-23 through 1.5-26 delivered secret-store mirrors for the
four major git platforms, but all four target the SaaS endpoints:
`api.github.com`, `gitlab.com/api/v4`, `api.bitbucket.org`,
`dev.azure.com/{org}/_apis`. Operators running self-hosted variants
(GitHub Enterprise Server, GitLab Self-Managed, Bitbucket Server,
Azure DevOps Server) can't use those stores as-is.

For three of the four platforms, the fix is straightforward: the SaaS
API clients already accept a configurable base URL, and the self-hosted
variants speak the same API. For Bitbucket it's a bigger lift: **Bitbucket
Server (formerly Stash) uses a completely different REST API from
Bitbucket Cloud**. The Cloud API lives under `/2.0/repositories/...`
while Server lives under `/rest/api/1.0/projects/...`. A new store class
is needed.

This story makes each existing SaaS store either configurable (GHES,
GitLab SM, Azure DevOps Server) or implements a sibling class
(Bitbucket Server). Shared test infrastructure validates the behaviour
against the docs of each variant, with opt-in integration tests gated
by env vars.

### Architecture summary

```
packages/secret-broker/src/stores/
  github-actions-store.ts          — Story 1.5-23; gains GHES base-URL config
  gitlab-ci-variables-store.ts     — Story 1.5-24; verified against GitLab SM
  bitbucket-pipelines-store.ts     — Story 1.5-25; renamed to BitbucketCloudPipelinesStore
  bitbucket-server-store.ts        — NEW; implements Bitbucket Server REST API 1.0
  azure-devops-variables-store.ts  — Story 1.5-26; gains Azure DevOps Server PAT + NTLM auth config
```

The four variants share a common `IGitPlatformSecretStore` interface
from the existing stories (list/get/put/delete by project + secret
name). This story adds variant-specific configuration without changing
the interface.

## User Story

As a **Tamma platform administrator running a self-hosted git stack**,
I want **to configure each git-platform mirror with an on-prem base URL and the appropriate auth type, and have every rotation cascade propagate to my internal CI/CD system the same way it does for SaaS**,
so that **my secret-rotation pipeline works in an air-gapped datacenter and I don't have to maintain separate tooling for on-prem vs cloud.**

## Acceptance Criteria

### AC1: GitHub Enterprise Server support in `GitHubActionsSecretStore`

- [ ] `packages/secret-broker/src/stores/github-actions-store.ts`
      accepts an optional `baseUrl` in its config:
  ```typescript
  interface GitHubActionsStoreConfig {
    installationId?: number;       // App-based auth (SaaS path)
    token?: string;                // PAT-based auth
    baseUrl?: string;              // e.g. 'https://ghe.example.com/api/v3'
    appId?: number;                // GHES App auth
    privateKeySecretRef?: string;
  }
  ```
- [ ] When `baseUrl` is set, Octokit is constructed with
      `{baseUrl: config.baseUrl}`. GHES URLs follow the pattern
      `https://<ghe-host>/api/v3` (for the REST API) and
      `https://<ghe-host>/api/graphql` (for GraphQL). The store's
      Octokit call uses only REST; GraphQL is not needed for the
      variables / secrets CRUD.
- [ ] The same store class handles both SaaS and GHES. A boolean
      `isEnterprise` derived from `baseUrl` presence drives minor
      behavioural tweaks:
  - GHES rate limits may be configured differently per instance;
    the store uses Octokit's built-in throttling plugin which
    respects whatever the server reports.
  - GHES may not have every API endpoint at version parity;
    `getCapabilities()` returns a minimal feature set by default
    and probes `GET /meta` for the server version on first use.
- [ ] GHES-specific auth: `appId` + `privateKeySecretRef` uses
      `@octokit/auth-app` exactly as the SaaS path; the difference is
      the `baseUrl`. PAT auth works without any change.
- [ ] Config validation (zod): `baseUrl` must be an absolute HTTPS
      URL ending in `/api/v3` (nudges operators to the correct
      convention; non-standard paths can still be accepted via a
      `strictBaseUrl: false` escape hatch).
- [ ] Unit tests mock Octokit and verify the `baseUrl` is passed
      through correctly. Existing unit tests continue to pass
      unchanged.
- [ ] Integration test (opt-in via `TAMMA_TEST_GHES_URL` +
      `TAMMA_TEST_GHES_PAT`): CRUDs a secret against a real GHES
      instance. CI does not run this by default — it's for manual
      operator validation against their own GHES.

### AC2: GitLab Self-Managed verification in `GitLabCIVariablesStore`

- [ ] `packages/secret-broker/src/stores/gitlab-ci-variables-store.ts`
      uses `@gitbeaker/node` which already accepts a `host`
      parameter. Confirm that `host: 'https://gitlab.internal.example.com'`
      works end-to-end against a self-managed instance.
- [ ] Config schema (zod) already has `host` from Story 1.5-24; no
      new field required. This story formalises the self-managed
      path by adding:
  - An explicit `isSelfManaged: boolean` derived field for diagnostics.
  - Documentation clarifying that `host` must NOT end in `/api/v4`
    (gitbeaker appends that automatically) and must be the server
    root.
- [ ] Auth: Self-managed GitLab supports the same auth modes as
      SaaS (PAT, project access token, OAuth, deploy token). The
      store passes through all of them without change.
- [ ] Capability probe: on first use against a self-managed host,
      the store calls `GET /api/v4/version` and caches the result.
      Some self-managed versions lack recent API features (e.g.
      the `masked_and_hidden` flag for variables was added in
      GitLab 17.4). The store reads the version and falls back to
      legacy behaviour if the instance is older.
- [ ] Unit tests cover:
  - SaaS host (`https://gitlab.com`) — existing path.
  - Self-managed host with a recent version — new masked feature
    used.
  - Self-managed host with an old version — fallback to legacy
    masked-variable semantics.
- [ ] Integration test (opt-in via `TAMMA_TEST_GITLAB_SM_HOST` +
      `TAMMA_TEST_GITLAB_SM_PAT`): CRUDs against a real self-managed
      instance.
- [ ] Documentation update: README clarifies that the SaaS store
      and the self-managed store are the same class; differentiation
      is purely via `host`.

### AC3: `BitbucketServerSecretStore` — new class

- [ ] **Bitbucket Server uses a different API surface** from Bitbucket
      Cloud. This AC mandates a new class rather than reusing the
      existing `BitbucketPipelinesSecretStore`.
- [ ] `packages/secret-broker/src/stores/bitbucket-server-store.ts`
      implements `IGitPlatformSecretStore` against the Bitbucket
      Server REST API 1.0:
  - Base URL pattern: `https://<bitbucket-host>/rest/api/1.0`
  - Auth: Bearer token via HTTP access token (Bitbucket Server's
    PAT equivalent). NO OAuth flow — operators use HTTP access
    tokens.
- [ ] **Important API difference**: Bitbucket Server's "project"
      is a top-level container, and repositories live under it. A
      secret is scoped to a repository, not directly to a project.
      This changes the store's key shape from
      `{projectKey, secretName}` to `{projectKey, repoSlug, secretName}`.
- [ ] Bitbucket Server historically does NOT have a first-class
      "repository secrets" API like GitHub Actions. The store
      therefore targets **Bitbucket Server Pipelines plugin**
      repository variables, which live under a different REST
      path. Endpoint patterns:
  ```
  GET    /rest/pipelines/1.0/projects/{projectKey}/repos/{repoSlug}/variables
  POST   /rest/pipelines/1.0/projects/{projectKey}/repos/{repoSlug}/variables
  PUT    /rest/pipelines/1.0/projects/{projectKey}/repos/{repoSlug}/variables/{key}
  DELETE /rest/pipelines/1.0/projects/{projectKey}/repos/{repoSlug}/variables/{key}
  ```
- [ ] Config schema (zod):
  ```typescript
  {
    baseUrl: string;                 // e.g. 'https://bitbucket.example.com'
    tokenSecretRef: string;          // HTTP access token as Tamma secret
    verifyTls?: boolean;             // default true; operator escape for self-signed
  }
  ```
- [ ] `verifyTls: false` is allowed for operators running with
      self-signed certs. When set, the HTTP client disables cert
      validation AND the store emits a prominent warning log on
      every request. Documented as "last resort for dev/test."
- [ ] Variable masking: Bitbucket Server supports `secured: true`
      on variables. The store always sets this.
- [ ] Capability probe: `GET /rest/api/1.0/application-properties`
      returns the server version. The store caches this and
      disables the pipelines path if the plugin isn't installed
      (detected by 404 on the pipelines endpoint), emitting a
      clear configuration error.
- [ ] Unit tests mock the HTTP client and cover: list, get, put,
      delete, secured-flag enforcement, missing-plugin detection,
      `verifyTls: false` warning emission.
- [ ] Integration test (opt-in via `TAMMA_TEST_BITBUCKET_SERVER_URL`
      + `TAMMA_TEST_BITBUCKET_SERVER_TOKEN`).

### AC4: Azure DevOps Server support in `AzureDevOpsVariablesStore`

- [ ] `packages/secret-broker/src/stores/azure-devops-variables-store.ts`
      from Story 1.5-26 accepts a new config field:
  ```typescript
  {
    orgUrl: string;                  // 'https://dev.azure.com/{org}' (SaaS) or 'https://azuredevops.example.com/{collection}' (Server)
    personalAccessTokenSecretRef: string;
    authMode?: 'pat' | 'ntlm';       // default 'pat'; Server deployments may use NTLM
    ntlmCredentialSecretRef?: string;
  }
  ```
- [ ] SaaS uses `https://dev.azure.com/{org}` + PAT. Server uses
      `https://<azdo-host>/{collection}` + either PAT or NTLM.
- [ ] PAT auth path works unchanged. The SaaS `azure-devops-node-api`
      client accepts a custom base URL, so the same client handles
      Server by passing the Server URL to `WebApi.createWithBearerToken`.
- [ ] NTLM auth path is new. Uses the `httpntlm` package:
  ```typescript
  if (authMode === 'ntlm') {
    const creds = await resolveSecret(ntlmCredentialSecretRef);
    // creds has { domain, username, password }
    // use httpntlm.ntlm(options) for each API call
  }
  ```
- [ ] NTLM is less common than PAT and comes with caveats: no
      connection pooling, slower per-call, and the credentials are
      domain + user + password (three fields stored as a structured
      Tamma secret with `mode: 'vault_copy'`).
- [ ] API endpoints for variable groups are the SAME on Server as
      on SaaS (both expose `GET /_apis/distributedtask/variablegroups`
      at API version 7.1), so once the HTTP client is configured
      with the right URL + auth, the store methods work unchanged.
- [ ] Capability probe: `GET /_apis/ConnectionData?api-version=7.1`
      returns server capabilities including the deployment type
      (Services vs Server) and version. The store caches this and
      uses it for diagnostic log tags.
- [ ] Config validation (zod): if `authMode === 'ntlm'`,
      `ntlmCredentialSecretRef` MUST be set and the referenced
      secret MUST have type `azure_ntlm_credentials` (a new secret
      type added specifically for this flow).
- [ ] Unit tests cover: PAT path against SaaS, PAT path against
      Server, NTLM path against Server (mocked `httpntlm`), missing
      NTLM credential rejection, capability-probe caching.
- [ ] Integration tests (opt-in) for PAT-on-Server and NTLM-on-Server
      with separate env vars.

### AC5: Shared self-hosted config surface

- [ ] Each store's config schema includes a standard optional
      field set for self-hosted deployments, defined once in
      `packages/secret-broker/src/stores/self-hosted-common.ts`:
  ```typescript
  export const selfHostedCommonConfig = z.object({
    verifyTls: z.boolean().default(true),
    caBundleSecretRef: z.string().optional(),
    connectTimeoutMs: z.number().int().min(100).max(120000).default(10000),
    requestTimeoutMs: z.number().int().min(100).max(300000).default(30000),
    proxyUrl: z.string().url().optional(),
  });
  ```
- [ ] `caBundleSecretRef` references a Tamma secret containing a
      PEM-encoded CA bundle. When set, the HTTP client uses it to
      validate the server cert. This is how operators with internal
      CAs get TLS validation without `verifyTls: false`.
- [ ] `proxyUrl` routes requests through an HTTP/HTTPS proxy —
      common in corporate networks where the broker can't reach
      external git hosts directly.
- [ ] Each store imports and merges `selfHostedCommonConfig` into
      its schema. Unit tests cover the CA bundle + proxy config.

## Dev Notes

### Requirements Context Summary

**Epic Context**: Stories 1.5-23 through 1.5-26 shipped git-platform
mirror stores for the SaaS offerings of the four major platforms.
Self-hosted variants were deferred with a note; this story closes
that deferral. After this story, every git-platform mirror Tamma
offers works against both the SaaS and on-prem endpoints, which
unblocks on-prem and regulated-industry deployments.

**Technical Context**: Three of the four platforms (GitHub, GitLab,
Azure DevOps) have API-compatible self-hosted variants where the SaaS
client library accepts a custom base URL. The fourth (Bitbucket
Server) has a completely different REST API and needs a new class.
Additional on-prem concerns — self-signed certs, corporate proxies,
NTLM auth, CA bundles — are shared across all four and handled via a
common config mixin.

**Integration Points**:
- **Stories 1.5-23–26**: each SaaS store is extended or joined by
  a sibling class for the self-hosted variant.
- **Story 1.5-16**: CA bundles, NTLM credentials, and HTTP access
  tokens are stored as Tamma secrets and resolved at call time.
- **Story 1.5-17**: no direct change; reuses the broker process.
- **Story 1.5-30 (cascade)**: the rotation cascade fans out to
  self-hosted targets the same way as SaaS targets; no cascade
  change required.

### Key Design Decisions

1. **Three platforms extend the SaaS class, one gets a new class**.
   GitHub Enterprise Server, GitLab Self-Managed, and Azure DevOps
   Server all expose API-compatible endpoints at a configurable
   base URL. The existing SaaS classes accept that URL and Just
   Work. Bitbucket Server's API is completely different — a
   different REST path structure, a different auth model, and
   the "secrets" concept lives in a plugin rather than the core
   product — so it gets its own class. Forcing one class to
   handle both Cloud and Server would be a tangle of conditionals
   with no reuse benefit.

2. **Self-hosted config is a shared mixin, not a per-store
   reinvention**. `verifyTls`, `caBundleSecretRef`,
   `connectTimeoutMs`, `requestTimeoutMs`, and `proxyUrl` are
   relevant to every self-hosted variant. Sharing the schema via
   `selfHostedCommonConfig` ensures consistency and lets operators
   configure all four stores the same way.

3. **`verifyTls: false` is loud**. When set, the store emits a
   warning on every request. This prevents operators from silently
   running with TLS off forever — the warning shows up in every
   rotation log and nudges them toward `caBundleSecretRef` as the
   permanent fix.

4. **NTLM is an Azure DevOps Server concern only**. No other git
   platform commonly authenticates with NTLM. Scoping NTLM to
   the Azure DevOps Server store keeps the NTLM dependency
   (`httpntlm`) out of the other stores and keeps the common
   config simpler. If a future variant needs NTLM, the mixin can
   be extended.

5. **Capability probes are cached per-instance**. A GHES version
   probe, a GitLab version probe, or an Azure DevOps connection
   probe happens once per store instance (not per request) and
   is cached for the store's lifetime. This avoids hammering
   the self-hosted endpoint with version-check traffic and keeps
   per-call latency low.

6. **Shared CRUD test fixture**. Every store implements the same
   interface; every store therefore deserves the same test suite.
   Refactoring the existing SaaS store tests to use a shared
   fixture is a one-time cost that pays out in consistency and
   makes adding future variants (GitHub Enterprise Cloud, for
   example, if that ships one day) trivial.

7. **Bitbucket Server's secrets live in a plugin**. This is the
   unavoidable reality of Bitbucket Server — the core product
   doesn't have a native secrets/variables API for CI. The
   Pipelines plugin is the de facto standard. The store fails
   loudly with a clear error if the plugin isn't installed, so
   operators know immediately that they need to install it before
   configuring Tamma.

8. **Integration tests are opt-in**. Running against a real GHES
   or self-managed GitLab requires infrastructure that not every
   contributor has. The tests are gated by env vars and CI does
   NOT run them by default. Operators can point them at their
   own instances for pre-deployment validation.

### Testing Strategy

- **Unit tests** per store, each using the shared
  `runGitPlatformStoreCrudTests` fixture with mocked HTTP clients.
- **Variant-specific unit tests** for the new behaviours: GHES
  capability probe, GitLab version-fallback, Bitbucket Server
  plugin detection, Azure DevOps NTLM path, CA bundle loading.
- **Integration tests** per variant (opt-in via env vars) that
  run the shared CRUD fixture against a real instance. These
  are intended for operator validation and release gating, not
  routine CI.
- **End-to-end cascade test** (AC8) exercises the full rotation
  pipeline against an in-test mock GHES to prove wiring works
  end-to-end without needing a real GHES.
- **Config validation tests** cover every invalid config case
  (NTLM without credential, `baseUrl` without protocol, conflicting
  auth fields) and assert helpful error messages.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| GHES API version drift breaks silently | Medium | Capability probe reads GHES version; store falls back to legacy behaviour on known-old versions; operator-visible warning in diagnostic output when the store detects version mismatch |
| Bitbucket Server Pipelines plugin not installed | High | Store detects 404 on the pipelines endpoint, emits a clear "plugin not installed" configuration error, refuses to operate rather than silently failing |
| NTLM credential leak in logs | Critical | `azure_ntlm_credentials` secret type routes through the same taint pipeline as every other Tamma secret; credentials are zeroised after each call; logger has a credential filter |
| Self-signed cert without CA bundle and `verifyTls: false` → MITM vector | Critical | `verifyTls: false` emits a per-call warning; README documents that this is "dev/test only"; the operator dashboard (Story 1.5-39) flags stores configured this way on a banner |
| Proxy credentials in `proxyUrl` embed plaintext | High | `proxyUrl` accepts only URLs without embedded credentials; if credentials are needed, they're separate fields backed by a Tamma secret; validation rejects `proxyUrl` with userinfo |
| Integration tests flake on slow self-hosted instances | Low | Integration tests are opt-in; `connectTimeoutMs` and `requestTimeoutMs` are configurable; failures are informational for the operator, not CI-blocking |
| Bitbucket Server API changes between plugin versions | Medium | Store pins to the plugin's v1.0 REST path; plugin version is captured in the capability probe; breaking change is detected on first use and emits a clear error |
| NTLM dependency `httpntlm` is unmaintained or vulnerable | Medium | Audit the package at story-time; if unmaintained, swap for a maintained alternative (`node-http-ntlm` or `nodentlm`); the store interface is narrow enough that swapping is low-risk |
| Azure DevOps Server collection URL format varies by install | Low | Config validation is permissive but logs the parsed URL at INFO so operators can see what Tamma resolved; opt-in integration test catches real-world format issues |
| Operator mistakes a GHES host for a SaaS host or vice versa | Low | Config validation nudges toward the correct convention (`/api/v3` suffix for GHES); startup log prints the resolved host + auth mode so mistakes are visible |
