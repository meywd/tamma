# Story 1.5-26: Bitbucket + Azure DevOps Secret Stores + Pipeline Tasks

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / LLM Safety)
**Status**: ready-for-dev
**Priority**: Medium
**Depends on**: Story 1.5-16 (interface), Story 1.5-17 (`IMirrorStore` + broker service), Story 1-11 (Bitbucket platform), future Azure DevOps platform story (soft dependency)

## Story

As a **Tamma operator using Bitbucket Cloud or Azure DevOps as my
primary git/pipeline platform**,
I want **real `IMirrorStore` implementations for both platforms plus
the reusable pipeline components their CI systems need to consume
Tamma-provisioned secrets (a Bitbucket Pipelines pipe and an Azure
Pipelines task)**,
so that **the last two Tamma-supported platforms reach parity with
GitHub, GitLab, Gitea, and Forgejo on LLM-safe secret management**.

## Context

Stories 1.5-23 through 1.5-25 shipped real mirrors for GitHub, GitLab,
Gitea, and Forgejo. This story completes the set by covering the two
remaining platforms on Tamma's support list: **Bitbucket Cloud** and
**Azure DevOps**.

These two platforms are grouped into a single story because each has
a smaller code volume than GitHub/GitLab, and because the pipeline
components both ship (a pipe for Bitbucket, a task for Azure) share
the same structural pattern: "a platform-specific reusable pipeline
component that calls Tamma's CI fetch endpoint to load secrets at
runtime."

Each platform is implemented as an **independent class** — unlike
Gitea/Forgejo (which share a base class), Bitbucket and Azure DevOps
have different enough APIs that a shared base class would be more
confusing than helpful. The shared story scaffolding means the work
can land as a single PR with coordinated testing, not that the code
shares structure.

This story explicitly does NOT cover:
- GitHub, GitLab, Gitea, Forgejo — previous stories.
- Bitbucket Server (self-hosted) — different API surface; a future
  story if operator demand materialises.
- Azure DevOps Server (self-hosted) — same concern.
- Revocation cascade — Story 1.5-30.
- Drift detection webhooks — Story 1.5-33.

## Bitbucket — ACs 2 through 8

### AC2: Bitbucket — Pipelines variables CRUD

- [ ] `BitbucketSecretStore.write(target, value, commitment)` where
      `target.scope.kind === 'repo'` calls
      `POST /2.0/repositories/{workspace}/{repo_slug}/pipelines_config/variables/`
      with body:
      ```json
      {
        "key": "<secret_name>",
        "value": "<plaintext>",
        "secured": true
      }
      ```
- [ ] If the variable already exists (400 with specific `fields.key`
      error), fall back to
      `PUT /2.0/repositories/{workspace}/{repo_slug}/pipelines_config/variables/{variable_uuid}`.
      The UUID must be fetched by calling the list endpoint and
      matching on `key`. A helper `upsertBitbucketVariable()` handles
      this fetch-then-PUT dance.
- [ ] `delete` calls
      `DELETE /2.0/repositories/{workspace}/{repo_slug}/pipelines_config/variables/{variable_uuid}`.
- [ ] `listAt` calls
      `GET /2.0/repositories/{workspace}/{repo_slug}/pipelines_config/variables/`
      and returns keys only. The `value` field is present in responses
      only for `secured: false` variables — a test asserts the mapper
      discards `value` regardless.

### AC3: Bitbucket — Workspace-scoped variables

- [ ] `write` with `target.scope.kind === 'org'` (Bitbucket's
      "workspace" concept) calls
      `POST /2.0/workspaces/{workspace}/pipelines-config/variables/`.
- [ ] Same upsert dance as repo scope.
- [ ] `delete` and `listAt` use the corresponding workspace endpoints.

### AC4: Bitbucket — Deployment environment variables

- [ ] `write` with `target.scope.kind === 'environment'` calls the
      deployment environment variables endpoint. Bitbucket's
      deployments are modelled as named environments with UUIDs that
      must be resolved from:
      `GET /2.0/repositories/{workspace}/{repo_slug}/environments/`
- [ ] After resolving the environment UUID, write via
      `POST /2.0/repositories/{workspace}/{repo_slug}/deployments_config/environments/{environment_uuid}/variables/`
- [ ] Environment UUIDs are cached per-process with a 5-minute TTL,
      matching the GitHub repo-id cache pattern from 1.5-23.
- [ ] If the environment does not exist, return a typed
      `EnvironmentNotFoundError` with a message pointing at Bitbucket's
      deployments UI. Do NOT auto-create.

### AC5: Bitbucket — `secured: true` default

- [ ] All Tamma-managed variables are created with `secured: true`
      (Bitbucket's equivalent of GitLab's `masked`). This hides the
      value in pipeline logs.
- [ ] A unit test asserts the default is propagated even when
      `target.metadata` is empty.

### AC6: Bitbucket — `tenant_root` refusal

- [ ] Same rule: `tenant_root` throws `UnsupportedScopeError` before
      any HTTP call.

### AC7: Bitbucket — Error mapping

- [ ] `packages/secret-broker/src/mirrors/bitbucket-error-mapper.ts`:
  | HTTP status | Error class |
  |---|---|
  | 401 | `BitbucketAuthError` — "invalid App password or OAuth token" |
  | 403 | `BitbucketPermissionError` — "insufficient workspace admin / pipelines_variables:write scope" |
  | 404 | `BitbucketTargetNotFoundError` — "workspace, repository, or environment not found" |
  | 400 (key conflict) | caught by upsert helper, not propagated |
  | 400 (validation) | `BitbucketValidationError` — "invalid variable key (must match `^[A-Z_][A-Z0-9_]*$`)" |
  | 429 | `BitbucketRateLimitError` — retryable, uses `X-RateLimit-Reset` header when present |
- [ ] **Bitbucket gotcha**: the API uses `"secured"` (not `"secret"` or
      `"masked"`) and the variable key regex is *stricter* than
      GitHub's — no lowercase, no hyphens. The store validates the
      key against the regex before the call and throws
      `BitbucketValidationError` with a clear message if it fails.
- [ ] **Bitbucket gotcha**: the delete endpoint requires the variable
      UUID, not the key. The upsert helper must fetch-then-delete,
      not delete-by-name. Tests pin this.

### AC8: Bitbucket Pipelines pipe

- [ ] `pipes/tamma-fetch-secrets/` ships a Bitbucket Pipelines pipe:
  - `pipe.yml` — pipe metadata (name, image, variables, documentation URL)
  - `Dockerfile` — `alpine:3.19` with `curl` and `jq` preinstalled
  - `pipe.sh` — entrypoint script that:
    1. Validates required env vars (`TAMMA_API_HOST`, `TAMMA_TENANT_ID`,
       `SECRETS`)
    2. Generates an OIDC token using Bitbucket's `BITBUCKET_STEP_OIDC_TOKEN`
       step variable (requires `oidc: true` on the step)
    3. `curl`s Tamma's CI fetch endpoint with
       `Authorization: Bearer $BITBUCKET_STEP_OIDC_TOKEN`
    4. Parses the JSON response and exports each secret via `export KEY="VALUE"`
       in a sourceable file written to `$BITBUCKET_CLONE_DIR/.tamma-secrets.env`
    5. Prints a masked confirmation line for each secret fetched
- [ ] `pipe.yml` documents usage:
      ```yaml
      pipe: docker://tammadev/tamma-fetch-secrets:1.0.0
      variables:
        TAMMA_API_HOST: api.tamma.dev
        TAMMA_TENANT_ID: $TAMMA_TENANT_ID
        SECRETS: DB_PASSWORD,API_KEY
      ```
- [ ] A README at `pipes/tamma-fetch-secrets/README.md` covers how
      operators add the pipe to their `bitbucket-pipelines.yml`, what
      env vars are required, and the `oidc: true` step flag requirement.
- [ ] Syntax validation: a unit test parses `pipe.yml` and `pipe.sh`
      via the Bitbucket Pipes `validate-pipe.sh` helper (if available)
      or a simpler YAML + shellcheck run. Both files must be valid.

## Azure DevOps — ACs 9 through 15

### AC9: Azure DevOps — Variable groups CRUD

- [ ] `AzureDevOpsSecretStore.write(target, value, commitment)` where
      `target.scope.kind === 'project'` calls
      `POST {org}/{project}/_apis/distributedtask/variablegroups?api-version=7.1`
      with body:
      ```json
      {
        "name": "<group_name>",
        "type": "Vsts",
        "variables": {
          "<secret_name>": {
            "value": "<plaintext>",
            "isSecret": true
          }
        }
      }
      ```
- [ ] The `group_name` is read from `target.metadata.variableGroupName`
      or defaults to `"tamma-managed"`. All Tamma-managed secrets for a
      given project live in a single variable group by default — a
      `tamma-managed` group is created the first time any secret is
      written.
- [ ] If the variable group already exists, the store fetches it via
      `GET {org}/{project}/_apis/distributedtask/variablegroups?groupName={name}&api-version=7.1`,
      merges the new variable into the existing `variables` map, and
      PUTs via
      `PUT {org}/{project}/_apis/distributedtask/variablegroups/{groupId}?api-version=7.1`.
- [ ] **Azure DevOps gotcha**: variable groups are **replace-only** at
      the group level — there is no "update a single variable" API. To
      update one variable, the store must read the whole group, mutate
      the map in memory, and PUT the whole group back. This means
      concurrent writes to the same group race — the store mitigates
      this with an advisory DB lock keyed on `(org, project, group_id)`.
- [ ] `delete(target)` removes the variable from the group's map and
      PUTs the updated group. If the group ends up empty, the store
      deletes the group via
      `DELETE {org}/{project}/_apis/distributedtask/variablegroups/{groupId}?api-version=7.1`.
- [ ] `listAt(scope)` returns the keys of the `variables` map of the
      default variable group. Assert the mapper never returns `value`
      even though the group PUT response includes `null` values for
      secret variables (Azure DevOps masks them on read).

### AC10: Azure DevOps — Org-level variable groups

- [ ] Azure DevOps variable groups are scoped to a project, not a
      workspace/org. There is no "organization-level secret" primitive.
      `target.scope.kind === 'org'` therefore throws
      `AzureDevOpsUnsupportedScopeError` — operators who want
      cross-project sharing must use Azure DevOps' library "link to
      other project" feature manually.
- [ ] Document this clearly in the error message and README.

### AC11: Azure DevOps — `isSecret: true` default

- [ ] All Tamma-managed variables are written with `isSecret: true`.
      Azure DevOps returns `null` for the value field of secret
      variables on subsequent reads; the store relies on this rather
      than attempting to re-encrypt.
- [ ] A unit test asserts the default is `true` and that passing
      `metadata.isSecret === false` results in an explicit warning log.

### AC12: Azure DevOps — `tenant_root` + `environment` refusal

- [ ] `tenant_root` and `environment` scopes both throw
      `UnsupportedScopeError`. Azure DevOps has "environments" as a
      concept but they do not own variables — variables live in
      variable groups that can be linked to environments via pipeline
      YAML. This linkage is a concern for the pipeline-author, not
      the mirror.

### AC13: Azure DevOps — Error mapping + auth

- [ ] `packages/secret-broker/src/mirrors/azure-devops-error-mapper.ts`:
  | HTTP status | Error class |
  |---|---|
  | 401 | `AzureDevOpsAuthError` — "invalid PAT or missing `vso.variablegroups_write` scope" |
  | 403 | `AzureDevOpsPermissionError` — "insufficient project permissions" |
  | 404 | `AzureDevOpsTargetNotFoundError` — "organization, project, or variable group not found" |
  | 400 | `AzureDevOpsValidationError` |
  | 409 | `AzureDevOpsConflictError` — caught by advisory lock retry |
  | 429 | `AzureDevOpsRateLimitError` — uses `Retry-After` header |
- [ ] **Azure DevOps gotcha**: authentication via Personal Access Token
      (PAT) uses HTTP Basic auth with an empty username and the PAT
      as password, encoded as `Basic base64(":" + pat)`. This is
      non-standard and trips people up. The store documents it in a
      top-of-file comment and the Story 1-11 (or stub) platform
      handles the encoding.
- [ ] **Azure DevOps gotcha**: the API version query parameter is
      required on every call (`?api-version=7.1`). Missing it returns
      a 404 with an unhelpful error page. A wrapper helper ensures
      `api-version` is always present.

### AC14: Azure DevOps — Advisory lock for group updates

- [ ] Because variable group updates are replace-only, two concurrent
      rotations of different secrets in the same group would race. The
      store acquires a Postgres advisory lock keyed on
      `hash('azure_devops', org, project, group_id)` before the
      read-mutate-write sequence, and releases it on completion or
      failure.
- [ ] A unit test simulates two concurrent writes to the same group
      and asserts they serialize — no lost update, both variables
      present in the final group.

### AC15: Azure DevOps Pipelines task

- [ ] `tasks/tamma-fetch-secrets-azure/` ships an Azure Pipelines task:
  - `task.json` — task metadata conforming to Azure Pipelines' task
    schema (`id`, `name`, `friendlyName`, `version`, `inputs`,
    `execution`)
  - `index.ts` — Node.js task entry point using the
    `azure-pipelines-task-lib` package
  - `package.json` with `azure-pipelines-task-lib` dependency
- [ ] `task.json` declares required inputs:
  - `tammaApiHost` (required, string)
  - `tammaTenantId` (required, string)
  - `secrets` (required, string, comma-separated)
- [ ] `index.ts` entry point:
  1. Reads inputs via `tl.getInput()`
  2. Retrieves the system-assigned Azure DevOps OIDC token via
     `tl.getEndpointAuthorizationParameter('SystemVssConnection', 'AccessToken', false)`
     OR uses workload-identity federation when available
  3. POSTs to `https://{tammaApiHost}/api/v1/ci/fetch-secrets` with
     the OIDC token in the `Authorization` header
  4. For each returned secret, calls
     `tl.setVariable(name, value, true /* secret */)` to expose it to
     subsequent tasks in the pipeline with masking
  5. Emits a summary in task output (names only, never values)
- [ ] `README.md` at `tasks/tamma-fetch-secrets-azure/README.md`
      documents installation (via a VSIX published to Visual Studio
      Marketplace, out of scope for this story — README notes the
      publishing step as a follow-up), usage in a YAML pipeline, and
      the required service connection configuration.
- [ ] Task syntax validation: a unit test runs `tfx build tasks validate`
      (via `tfx-cli` devDependency) against `task.json` and asserts
      no errors.

## Dev Notes

### Requirements Context Summary

**Epic Context**: Final story in the mirror implementation series.
After 1.5-26 ships, every git platform on Tamma's support list has a
real `IMirrorStore` implementation and the secret broker is usable
end-to-end across the Tamma operator matrix.

**Technical Context**: Bitbucket Cloud and Azure DevOps have the
quirkiest secret-management APIs of the seven platforms Tamma
supports. Neither resembles GitHub's clean per-secret PUT; both
require UUID resolution, upsert dances, or replace-only group
updates. This story captures the gotchas in both the code and the
dev notes so future maintainers don't hit the same walls.

**Integration Points**:
- **Story 1-11 (Bitbucket platform)**: reuses the existing HTTP client.
- **Future Azure DevOps platform story**: this story ships a stub if
  that full story hasn't landed; the stub is explicitly marked for
  replacement.
- **Story 1.5-17 (broker)**: `PlatformMirrorRegistry` wiring.
- **Story 1.5-21 (CI fetch endpoint)**: both the Bitbucket pipe and
  the Azure task call this endpoint at runtime.

### Key Design Decisions

1. **Two independent classes, not a shared base.** Bitbucket and
   Azure DevOps have nothing structurally in common beyond
   `IMirrorStore`. Forcing them into a base class would be an
   anti-pattern — the shared code would be near-empty and every
   method would be overridden anyway. The single-story grouping is
   a *scheduling* choice, not a *structural* one.

2. **Bitbucket upsert via fetch-then-PUT by UUID.** Bitbucket's
   variable delete endpoint takes the variable UUID, not the key,
   which means any write-by-name operation has to first list-to-get-uuid.
   The helper caches the UUID per `(workspace, repo_slug, key)` for
   the duration of a single HTTP request (not across requests, since
   UUIDs can change after deletion and recreation).

3. **Azure DevOps variable groups are replace-only.** The API has no
   per-variable update endpoint. Every write is a read-mutate-write
   on the full group. The advisory lock prevents concurrent writes
   from losing updates. This is a real limitation that callers should
   know about: rapid rotation across many secrets in the same group
   serialises, not parallelises.

4. **Default `tamma-managed` variable group per Azure DevOps project.**
   Rather than creating a new group per secret (hundreds of groups
   per project), Tamma consolidates all managed secrets into one
   group per project. Operators who need finer separation can pass
   `metadata.variableGroupName` to override.

5. **Azure DevOps `org` scope is refused, not emulated.** Azure
   DevOps has no org-level secrets primitive; the nearest equivalent
   is "variable group in a shared-services project linked to other
   projects via Library UI." Emulating this in Tamma would require
   the operator to maintain the linkage manually anyway, so the
   cleanest path is to refuse and tell the operator to use
   `scope: project` with an explicit project id.

6. **`environment` scope on Azure DevOps is refused.** Azure DevOps
   environments are pipeline-runtime constructs; they don't hold
   variables. Variable groups can be *linked* to environments in YAML
   pipelines, but the link is authored by the pipeline, not by the
   variable store. Returning an error is correct — the alternative
   would be to pretend the linkage happens automatically and silently
   break operator expectations.

7. **Bitbucket pipe uses OIDC, not long-lived credentials.** Bitbucket
   introduced `BITBUCKET_STEP_OIDC_TOKEN` with the `oidc: true` step
   flag. This matches the OIDC-everywhere pattern from 1.5-20/21 and
   means the pipe never carries a long-lived Tamma API token.
   Operators who need to run the pipe with the `oidc: true` flag
   have a required setup step; the README makes it loud.

8. **Azure Pipelines task uses `azure-pipelines-task-lib`.** This is
   the official Microsoft-supported SDK. Third-party alternatives
   exist but are unmaintained. The task is Node.js-based, matching
   Tamma's technology stack, and `tl.setVariable(name, value, true)`
   handles the masking primitive.

9. **Both platform components are flagged "publishing is out of
   scope."** Shipping a Bitbucket pipe to the Atlassian marketplace
   or a task to the Visual Studio Marketplace requires account setup,
   signing, and review — all of which are operator-facing concerns
   beyond this story. The code and test coverage live in the monorepo;
   publication is a follow-up tracked as an ops task.

10. **PAT-with-empty-username is encoded in a helper, not inline.**
    Every PR author who touches Azure DevOps auth in the future would
    otherwise relearn the Basic-auth encoding. A single
    `packages/platforms/src/azure-devops/auth.ts` helper owns it and
    has its own tests.

### Testing Strategy

- **Unit tests** with mocked HTTP clients per platform (`msw`
  intercepting the underlying `fetch`).
- **Concurrency test** for Azure DevOps advisory lock (two promises
  racing the same group, assert serialization).
- **Integration tests** against real Bitbucket and Azure DevOps,
  gated on env vars.
- **Pipe + task syntax validation** in CI so the pipeline components
  can't silently break.
- **Taint-tracking tests** across all layers for plaintext leakage.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Azure DevOps platform from 1-11 not available yet | High | Ship a minimal stub platform in this story, flag for replacement |
| Advisory lock deadlock under pathological load | Medium | Lock timeout (default 30s); operator can tune via env var |
| Bitbucket pipe Docker image not published | Low | Image lives in monorepo as a buildable Dockerfile; publication to Docker Hub is a follow-up ops task |
| Azure task not published to Marketplace | Low | Task code lives in monorepo; publication is follow-up |
| PAT authentication fragile | Medium | Dedicated helper with its own tests; Story 1-11 can add OAuth support later without touching this story |
| Variable group race condition under load | High | Advisory lock; concurrent write test pins the behavior |
| Bitbucket API uses `pipelines_config/` vs `pipelines-config/` inconsistency | Medium | Documented in comments near each endpoint call; tests pin the exact URL shapes |
| Bitbucket response body inconsistency (UUID in some responses, not others) | Medium | Defensive parsing with typed narrow-if-present |

### What's NOT in this story

- **No other git platforms.** All seven platforms now have mirrors
  after this story lands.
- **No Bitbucket Server (self-hosted).** Different API surface;
  future story if demand materializes.
- **No Azure DevOps Server (self-hosted).** Same.
- **No revocation cascade to platform mirrors.** Story 1.5-30.
- **No drift detection via webhooks.** Story 1.5-33.
- **No publication of the Bitbucket pipe to Atlassian's marketplace**
  or the Azure task to Visual Studio Marketplace. Both live in the
  monorepo; publishing is a follow-up ops task.
- **No OAuth 2.0 auth for Azure DevOps.** PAT only in v1. A future
  story can add OAuth + workload identity federation.
- **No Bitbucket OAuth app.** App password / token only in v1.
- **No SSH key import for either platform.** `generateSecretValue`
  already rejects SSH key types per Story 1.5-16.
