# Story 1.5-29: IRotationHandler + built-in handlers

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / Rotation)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-17 (TammaVaultStore + broker HTTP service), Story 1.5-18 (Secret Activities — for `adminPasswordSecretId` resolution pattern)

## Story

As a **Tamma operator running a multi-tenant deployment with live downstream systems**,
I want **a pluggable rotation handler framework with built-in handlers for Postgres, MySQL, Redis, GitHub App private keys, and HTTP webhooks**,
so that **when Tamma rotates a secret, the new value is automatically propagated to the downstream system that uses it — without operator-written glue code, without plaintext leaving the broker process, and with idempotent rollback on partial failure.**

## Context — Why this story exists

Stories 1.5-16 and 1.5-17 built the vault: a secret can be created, stored
encrypted, and rotated to a new value. But rotating the value inside Tamma is
only half the job. The downstream system that **uses** that secret — a
Postgres database, a Redis server, a Stripe API, a GitHub App — must also
accept the new value, or every service depending on that secret starts
failing at the moment of rotation.

Today, every secret system has a different way to push a new value:

- **Postgres**: `ALTER USER <role> WITH PASSWORD '<new>';` via an admin
  connection.
- **MySQL**: `ALTER USER <role>@'%' IDENTIFIED BY '<new>';` via mysql2.
- **Redis 6+ ACL**: `ACL SETUSER <user> ON ><new>` via ioredis.
- **GitHub App private key**: upload new key via GitHub's App key rotation
  endpoint (if stable) or operator-driven UI rotation.
- **HTTP webhook**: POST the new value to an operator-configured URL and
  trust the remote system to store it.
- **Stripe / AWS / GCP**: call the provider's API with cloud-specific auth.

We need a **uniform interface** that maps a secret rotation event to an
effect on a downstream system, without hard-coding each downstream type
into the rotation workflow. That's `IRotationHandler`.

This story defines the interface, registers five built-in handlers, and
provides the registry that `RotationCascadeWorkflow` (Story 1.5-30) queries
at runtime. Cloud-specific handlers (AWS IAM, GCP service accounts, Azure
Key Vault) are deferred to Story 1.5-29.1.

### Architecture summary

Rotation handlers live inside `packages/secret-broker/` — the same process
that holds plaintext. A handler receives the **decrypted** old value, the
**decrypted** new value, a config blob, and a `RotationContext`. It runs
the rotation and returns a `RotationHandlerResult` with the outcome. The
handler never returns plaintext in the result, and all error messages pass
through `redactSensitiveKeys()` from `packages/shared/src/telemetry/utils.ts`
before being logged or returned.

Handlers are registered at broker boot via `RotationHandlerRegistry.register(handler)`.
Operators can register custom handlers by providing a module path in
`secrets.rotation_handlers.custom_modules` in `.tamma/config.yaml`; the
broker loads them at startup alongside the built-ins. `RotationCascadeWorkflow`
(1.5-30) queries the registry by `type` string when invoking targets.

Handler authentication — e.g. the admin password used to connect to the
Postgres server running the rotation — is itself a Tamma-managed secret,
resolved via `adminPasswordSecretId` in the handler config. This is
recursive-but-bounded: the broker resolves `adminPasswordSecretId` to
plaintext using its own vault, uses that plaintext to authenticate to the
downstream system, performs the rotation, and zeroises both the admin
plaintext and the new-value plaintext before returning.

## User Story

As a **Tamma platform engineer**,
I want **built-in rotation handlers for Postgres, MySQL, Redis, GitHub App, and HTTP webhook backends**,
so that **a single `RotateSecretWorkflow` invocation propagates the new secret value to every downstream system that uses it — with zero-downtime where supported, audit logging, and rollback on failure.**

### AC3: Postgres rotation handler

- [ ] `PostgresRotationHandler` at
      `packages/secret-broker/src/rotation-handlers/postgres-handler.ts`
      implements `IRotationHandler` with `type: 'postgres'`.
- [ ] Config schema:
  ```typescript
  interface PostgresHandlerConfig {
    host: string;
    port: number;
    database: string;           // DB to connect to for the ALTER USER
    adminUser: string;
    adminPasswordSecretId: string;  // Tamma secret id for the admin creds
    targetRole: string;         // The role whose password we rotate
    sslMode?: 'require' | 'prefer' | 'disable';
    connectionTimeoutMs?: number;   // default 5000
    statementTimeoutMs?: number;    // default 10000
  }
  ```
- [ ] `rotate()` implementation:
  1. Resolves `adminPasswordSecretId` via the broker's vault store to a
     plaintext admin password.
  2. Constructs a `pg.Client` with `connectionTimeoutMillis` and
     `statement_timeout` enforced.
  3. Executes `ALTER USER ${targetRole} WITH PASSWORD $1` with the new
     value as a parameterised bind. NEVER string-interpolates the password
     into SQL.
  4. On success: returns `{success: true, sideEffects: {rotated_role: targetRole}}`.
  5. On auth failure (SQLSTATE `28P01`): returns
     `{success: false, errorCategory: 'auth_failed', errorMessage: ...}`.
  6. On connection failure: returns `errorCategory: 'connection_failed'`.
  7. On permission denied (SQLSTATE `42501`): returns
     `errorCategory: 'permission_denied'`.
  8. On statement timeout: returns `errorCategory: 'timeout'`.
  9. On any other PG error: returns `errorCategory: 'config_error'` with
     the raw error message passed through `redactSensitiveKeys`.
  10. Always closes the `pg.Client` in a `finally` block.
  11. Always zeroises the admin plaintext buffer via `.fill(0)` before
      returning.
- [ ] `rollback()` implementation:
  1. Same flow, but re-sets the password to `oldValue`.
  2. Intended to restore the previous state if another cascade target
     fails after Postgres has already accepted the new value.
- [ ] **Zero-downtime note**: Postgres does NOT support graceful password
      rotation (no "add secondary password" primitive). Every rotation is
      atomic — at commit time, the old password stops working and the new
      one starts. Document this clearly in the handler docstring so
      operators understand the rotation window is effectively zero but
      there IS a brief cut-over.
- [ ] Unit tests with a mocked `pg.Client` cover: happy path, auth failure,
      connection failure, timeout, permission denied, parameterised bind
      (no SQL injection), admin creds zeroised on success and on failure.
- [ ] Integration tests with a real Postgres container via `testcontainers`
      cover: rotation happy path + verifying old password stops working
      and new password works; rollback restores old password; rotation
      against a non-existent role returns `config_error`.

### AC5: Redis rotation handler (ACL-based)

- [ ] `RedisRotationHandler` at
      `packages/secret-broker/src/rotation-handlers/redis-handler.ts`
      implements `IRotationHandler` with `type: 'redis'`.
- [ ] Uses `ioredis` as the driver.
- [ ] Config schema:
  ```typescript
  interface RedisHandlerConfig {
    host: string;
    port: number;
    tls?: boolean;
    adminUser: string;           // typically 'default' or an admin ACL user
    adminPasswordSecretId: string;
    targetUser: string;          // ACL user whose password is being rotated
    commandTimeoutMs?: number;   // default 5000
  }
  ```
- [ ] `rotate()` executes `ACL SETUSER <targetUser> ON ><newPassword>` via
      ioredis. Note: Redis ACL `>` prefix adds a password; to fully replace
      the old password rather than appending, the handler executes a
      two-step sequence:
  1. `ACL SETUSER <target> resetpass` — clears all passwords.
  2. `ACL SETUSER <target> ON ><new>` — sets the new password.
- [ ] **Alternative zero-downtime path** (operator opt-in via
      `keep_old_password_for_ms` in config): the handler adds the new
      password without removing the old, waits the configured duration,
      then removes the old. This allows clients mid-connection to
      complete before rotation takes effect.
- [ ] Error categories mapped from ioredis errors
      (`NOAUTH`, `NOPERM`, `ETIMEDOUT`, etc.).
- [ ] `rollback()` clears the new password and re-adds the old via the
      same `resetpass` + `SETUSER` sequence.
- [ ] Unit tests with a mocked ioredis client.
- [ ] Integration tests with a real Redis 7 container via `testcontainers`,
      covering both the default rotation path and the zero-downtime path.

### AC7: HTTP webhook rotation handler

- [ ] `HttpWebhookRotationHandler` at
      `packages/secret-broker/src/rotation-handlers/http-webhook-handler.ts`
      implements `IRotationHandler` with `type: 'http_webhook'`.
- [ ] Config schema:
  ```typescript
  interface HttpWebhookHandlerConfig {
    url: string;                        // POST target
    signingSecretId: string;            // Tamma secret id for HMAC signing
    method?: 'POST' | 'PUT';            // default POST
    headers?: Record<string, string>;
    timeoutMs?: number;                 // default 15000
    retryOn5xx?: boolean;               // default true
    maxRetries?: number;                // default 3
    backoffMs?: number;                 // default 1000
  }
  ```
- [ ] `rotate()` implementation:
  1. Resolves `signingSecretId` to a plaintext HMAC signing key via the
     broker vault.
  2. Constructs the body as JSON:
     ```json
     {
       "rotation_id": "<rotationId>",
       "secret_id": "<secretId>",
       "tenant_id": "<tenantId>",
       "old_value_b64": "<base64(oldValue)>",
       "new_value_b64": "<base64(newValue)>",
       "timestamp": "<ISO8601>"
     }
     ```
  3. Computes HMAC-SHA256 over the JSON body using the signing key,
     hex-encodes, and sets header `X-Tamma-Signature: sha256=<hex>`.
  4. POSTs via `undici` (no external fetch polyfill) with the configured
     headers, timeout, and retry policy.
  5. On 2xx: returns `success: true`.
  6. On 4xx (not 429): returns `errorCategory: 'config_error'` — do NOT
     retry, the remote rejected the request.
  7. On 5xx or 429: retry with exponential backoff up to `maxRetries`. If
     all retries exhausted: `errorCategory: 'connection_failed'`.
  8. On timeout: `errorCategory: 'timeout'`.
  9. Always zeroises both value buffers before returning.
- [ ] `rollback()`: POSTs the same payload with `old_value_b64` and
      `new_value_b64` swapped, plus `"rollback": true` in the JSON. The
      remote is expected to honour the rollback. If the remote does not
      acknowledge (non-2xx), the handler returns an error and the cascade
      marks this target as "rollback failed" and alerts the operator.
- [ ] The `X-Tamma-Signature` format and verification steps are documented
      in `packages/secret-broker/README.md` under a "writing a webhook
      receiver" section so operators can implement compatible handlers.
- [ ] Unit tests with `undici` mocked (or MSW) cover: 2xx happy path,
      4xx fail-fast, 5xx retry-until-success, 5xx retry-exhausted, timeout,
      HMAC signature correctness (verify independently), rollback payload
      shape.

### AC8: `adminPasswordSecretId` resolution pattern

- [ ] A helper `resolveAdminCredential(store: TammaVaultStore, secretId: string,
      tenantId: string): Promise<Buffer>` lives in
      `packages/secret-broker/src/rotation-handlers/admin-credential-resolver.ts`.
- [ ] The helper:
  1. Queries the vault store for the secret's metadata via `getSecretMetadata`.
  2. Asserts the secret is `status: 'active'`. Revoked or rotating admin
     credentials cause the handler to fail fast with `errorCategory:
     'config_error'`.
  3. For `vault_only` and `vault_copy` modes: decrypts the admin credential
     and returns the plaintext buffer.
  4. For `platform_only` mode: throws — admin credentials MUST be stored
     in the vault, not on a platform, because the broker cannot read
     platform-stored secrets back (they're write-only at platform APIs).
     A config validation step at registration time REJECTS handler configs
     whose `adminPasswordSecretId` points to a `platform_only` secret.
- [ ] Caller is responsible for zeroising the returned buffer.
- [ ] Unit tests cover: happy path returning plaintext, revoked admin cred
      fails fast, `platform_only` admin cred rejected, missing secret
      rejected.
- [ ] A property-based test asserts: for N rotations against a single
      handler with a single `adminPasswordSecretId`, the plaintext buffer
      is zeroised (all bytes 0) after each call.

## Dev Notes

### Requirements Context Summary

**Epic Context**: This story is the first of three that implement automated
rotation propagation (1.5-29 = handlers, 1.5-30 = cascade workflow, 1.5-31 =
auto-rotate on leak). The handler framework is the pluggable extension
point that lets Tamma grow to support new downstream systems without
rewriting the rotation workflow itself.

**Technical Context**: Handlers run inside the broker process alongside
the vault because they need access to plaintext. The same trust boundary
that protects the vault protects the handlers. This is intentional: we
do NOT want handlers running in the main API process (which must never
see plaintext) or in a separate worker process (which would require a
plaintext-over-wire protocol that duplicates the broker's trust model).

**Integration Points**:
- **Vault store** (Story 1.5-17): handlers resolve `adminPasswordSecretId`
  via `TammaVaultStore.getSecretMetadata` + decryption, and receive the
  vault store instance via constructor DI.
- **Event store** (shared with `tamma-api`): handlers emit audit events
  `SECRET.ROTATION_HANDLER.INVOKED`, `SECRET.ROTATION_HANDLER.SUCCESS`,
  `SECRET.ROTATION_HANDLER.FAILED` through the broker's shared event
  emitter.
- **Logger**: handlers log via a Pino child logger with redaction bindings
  that strip `oldValue`, `newValue`, `adminPasswordSecretId`, and any
  header containing `authorization` or `x-tamma-signature`.
- **Story 1.5-30 (RotationCascadeWorkflow)**: looks up handlers in this
  story's registry and invokes them per target.

### Interface Definition

```typescript
// packages/secret-broker/src/rotation-handlers/rotation-handler.ts

import type { Logger } from 'pino';

export interface RotationContext {
  /** UUID v7 for this cascade invocation. */
  readonly rotationId: string;
  readonly secretId: string;
  readonly tenantId: string;
  /** 1-indexed retry attempt. */
  readonly attemptNumber: number;
  /** Pino child logger with redaction bindings applied. */
  readonly logger: Logger;
}

export interface RotationHandlerResult {
  success: boolean;
  errorCategory?:
    | 'connection_failed'
    | 'auth_failed'
    | 'permission_denied'
    | 'timeout'
    | 'config_error';
  /** Already passed through redactSensitiveKeys() at set time. */
  errorMessage?: string;
  /** Non-sensitive side effects for audit (e.g. "created_user_id": "..."). */
  sideEffects?: Record<string, string>;
}

export interface IRotationHandler {
  /** Unique discriminator — 'postgres', 'mysql', 'redis', etc. */
  readonly type: string;

  /**
   * Whether this handler supports rollback. Handlers without a `rollback`
   * method, or whose `rollback` throws `RollbackNotSupportedError`,
   * report `false`. The cascade uses this to decide whether to include
   * a target without operator opt-in.
   */
  readonly supportsRollback: boolean;

  /**
   * Propagate the new secret value to the downstream system.
   *
   * Receives BOTH old and new values: old is used for zero-downtime
   * rotation where supported and for idempotency checks; new is the
   * value to install. Handlers MUST NOT return either value in any
   * field of RotationHandlerResult. Handlers MUST zero-fill both
   * buffers and any derived admin credential buffers before returning.
   */
  rotate(
    oldValue: Buffer,
    newValue: Buffer,
    config: Record<string, unknown>,
    context: RotationContext,
  ): Promise<RotationHandlerResult>;

  /**
   * Revert the rotation. Handlers SHOULD be idempotent. Handlers that
   * cannot support rollback MUST throw RollbackNotSupportedError.
   */
  rollback?(
    oldValue: Buffer,
    newValue: Buffer,
    config: Record<string, unknown>,
    context: RotationContext,
  ): Promise<void>;
}

export class RollbackNotSupportedError extends Error {
  constructor(public readonly handlerType: string, public readonly reason: string) {
    super(`Handler '${handlerType}' does not support rollback: ${reason}`);
    this.name = 'RollbackNotSupportedError';
  }
}
```

### Key Design Decisions

1. **Handlers receive decrypted plaintext values**. They run in the broker
   process alongside the vault — same trust boundary. Running handlers
   in a separate worker process would require serialising plaintext over
   a wire protocol, doubling the number of places plaintext can leak.
   Since the broker already has plaintext in memory during rotation, the
   handlers might as well run in the same process where the values are
   already decrypted. Handlers MUST NOT return plaintext in any field of
   `RotationHandlerResult`, and taint-tracking tests enforce this.

2. **The admin password for the rotation handler is itself a Tamma secret**
   (the `adminPasswordSecretId` pattern). This is recursive-but-bounded:
   the broker resolves the admin password via its own vault, uses it to
   authenticate to the downstream system, then zeroises. The bounding
   rule is that `adminPasswordSecretId` MUST point to a `vault_only` or
   `vault_copy` secret — never `platform_only`. A config-time check
   rejects handler configs that violate this, so an operator cannot
   accidentally create a loop where the admin creds for rotating X are
   stored in X.

3. **Rollback is best-effort and handler-specific**. Not every downstream
   system supports rotation rollback. Postgres, MySQL, Redis, and HTTP
   webhook can all roll back (re-set the old password / re-POST the
   swapped payload). GitHub App cannot — once a key has been uploaded,
   reverting is outside Tamma's scope. Handlers that can't roll back
   throw `RollbackNotSupportedError`, and the cascade (Story 1.5-30)
   refuses to include such targets unless the operator explicitly opts
   in via `allow_unsupported_rollback: true` per target.

4. **Handlers are registered in a registry**. `RotationHandlerRegistry.register(handler)`
   at broker boot, one registry instance per broker process. The registry
   is queried by `type` string when the cascade runs. Custom handlers
   can be registered by operators via the
   `secrets.rotation_handlers.custom_modules` config, which loads
   operator-provided modules at boot and calls their `default(registry)`
   export. This lets operators add handlers (e.g. for internal services)
   without forking the broker.

5. **Testing uses testcontainers where possible**. Postgres, MySQL, and
   Redis handlers each have integration tests that spin up a real
   container via `testcontainers-node`, run a rotation, verify the old
   password stops working and the new one works, then run rollback and
   verify the old password works again. This keeps handler tests honest
   about actual DB behaviour — mocked `pg.Client` tests cover error paths
   and parameter binding, but integration tests cover the "does it
   actually rotate" question. The GitHub App handler does NOT have a
   real integration test (would burn real GitHub App keys); the HTTP
   webhook handler uses a local test server in-process.

6. **SQL injection defense via parameterised binds**. The Postgres and
   MySQL handlers both use driver-level parameter binding for the
   password value (`$1` / `?`). Never interpolate a password into SQL
   string, even though the password is Tamma-generated and "trusted" —
   the defense-in-depth principle says to use parameterised queries
   regardless of input trust, because a future change to the value
   generator could introduce special characters that break interpolation
   and open an injection path. Unit tests include a "password with SQL
   metacharacters" case to verify the bind path handles it.

7. **HTTP webhook signing uses HMAC-SHA256 over the raw body**. Signature
   format is `sha256=<hex>` in header `X-Tamma-Signature`, matching
   GitHub's webhook signing convention. The signing secret is itself a
   Tamma secret resolved via `signingSecretId`, keeping the pattern
   consistent: all handler-side credentials are Tamma-managed.

8. **Experimental flag for unstable handlers**. `GithubAppPrivateKeyHandler`
   is marked experimental at the interface level (`readonly experimental:
   true`). The registry warns on register, the cascade warns on invoke,
   and the ADR documents that experimental handlers can be removed or
   redesigned in a minor version bump without migration guarantees. This
   gives us a path to ship handlers that depend on external APIs whose
   stability is not under our control.

### Testing Strategy

- **Unit tests** for each handler with mocked drivers (pg, mysql2, ioredis,
  undici). Cover: happy path, each error category, parameter binding
  correctness, buffer zeroisation.
- **Integration tests** with `testcontainers-node` for Postgres, MySQL,
  Redis — real container, real rotation, real rollback.
- **Taint-tracking tests** across every handler for result serialisation
  and log output.
- **Property-based tests** for the `adminPasswordSecretId` resolver using
  `fast-check` to generate random plaintext and assert zeroisation.
- **Boot integration test** that calls `bootBroker()` and asserts all 5
  handlers appear in `registry.list()`.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| SQL injection via unparameterised password interpolation | Critical | Driver-level parameter binding only; unit test with SQL metacharacters; code review checklist requires grep for "PASSWORD '${" in handler diffs |
| Plaintext leaked in error message or log | Critical | Pino redaction bindings applied to handler child logger; `redactSensitiveKeys` on all `errorMessage` assignments; taint-tracking tests across all paths |
| Nonce / password reuse from buffer not zeroised | High | `Buffer.fill(0)` in `finally` for every handler; property-based test for admin credential resolver |
| GitHub App API changes breaking handler silently | Medium | Experimental flag + warning on every invoke; WebFetch current docs at implementation time; integration test is manual |
| Rollback leaving the downstream in an intermediate state | High | Rollback runs in the same transaction boundary as rotate where supported; for Postgres/MySQL this means a single client connection. Where not supported (GitHub App), `RollbackNotSupportedError` is thrown and cascade escalates to operator |
| `adminPasswordSecretId` pointing at a revoked secret | Medium | Resolver asserts `status: 'active'` and fails fast with `config_error` — cascade surfaces this clearly |
| Infinite rotation loop (admin creds rotated as part of a cascade that requires them) | High | Config-time check: `adminPasswordSecretId` cannot appear in the same cascade as one of its own rotation targets. Document as future-work for recursive detection across multiple cascades |
| Redis `resetpass` clearing passwords other than the one being rotated | Medium | `resetpass` only affects the target ACL user, not others. Document explicitly; integration test with a second ACL user on the same Redis instance verifies isolation |
| Mocked driver tests passing when real driver behaviour differs | Medium | testcontainers integration tests for the three DB handlers provide real-behaviour coverage; CI runs them on every PR that touches the handler files |

### What's NOT in this story

- **Cloud provider handlers** (AWS IAM, GCP service accounts, Azure Key
  Vault, HashiCorp Vault). These land in a follow-up story 1.5-29.1.
- **Rotation handler marketplace** (operators sharing handlers via a
  registry index). The custom-modules config supports loading local
  handlers; a shared registry is future work.
- **Zero-downtime rotation for Postgres** — Postgres has no primitive for
  "add a second password". A future version could implement the
  "create a parallel user, swap, delete old user" pattern, but that's
  a significant design change and out of scope here.
- **Distributed rotation** — rotating a secret across multiple instances
  of the same downstream (e.g. a Postgres cluster with read replicas).
  Handlers target a single host; multi-host is either handled upstream
  (via a load balancer / cluster admin) or via multiple cascade targets.
- **Handler performance benchmarking** — handlers should complete within
  seconds; the cascade (1.5-30) has a 2-minute soft alert threshold and
  10-minute hard timeout, so handler performance tuning can wait.
- **Post-rotation health checks** — after rotating, verifying the
  downstream system is actually reachable with the new password is a
  probe concern (Story 1.5-27), not a handler concern.
