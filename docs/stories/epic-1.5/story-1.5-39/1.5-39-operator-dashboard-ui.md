# Story 1.5-39: Operator dashboard UI for secrets, rotations, and alerts

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / Operations)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-17 (vault store + secret APIs), Story 1.5-19 (alerts + workflows), Story 1.5-30 (rotation cascade + targets API), Story 1.5-31 (auto-rotate inbox), Story 1.5-32 (secret import handle flow), Story 1.5-37 (notification channels API)

## Story

As a **Tamma operator managing a production deployment**,
I want **React dashboard pages that let me view secrets, approve auto-rotations, manage rotation targets, configure notification channels, and acknowledge orchestrator alerts — all without touching Postgres or the CLI**,
so that **I can run day-to-day secret operations from the same browser-based control surface I already use for the rest of the platform, and my less-technical teammates can do the same.**

## Context — Why this story exists

Epic 1.5's secret-management stories built a rich backend: vault
store, rotation cascade, leak detection, auto-rotate inbox, rotation
targets, notification channels, scheduled rotation. Every one of
those stories has an admin HTTP API but NO UI surface. Operators
interact with the system by curling the API, querying Postgres
directly, or (when desperate) editing tables by hand.

Several stories explicitly punted on UI:
- Story 1.5-30 mentions "operator dashboard UI for reviewing cascades"
  as future work.
- Story 1.5-31 mentions "operator dashboard UI" as future work for
  reviewing auto-rotation events.
- Story 1.5-19 describes `orchestrator_alerts` as "human operators
  query the table" for v1.

This story is the UI surface that closes all of those gaps at once.
It adds React pages to the existing `@tamma/dashboard` package,
reusing the established component conventions, the permission-guard
wrapper, and the service layer pattern.

Because this story consumes many backend APIs, it's structured so
each page can ship independently as its backend lands. The initial
landing of this story can include only the pages whose backends are
already merged; later PRs add the rest as the corresponding stories
merge.

### Architecture summary

```
  packages/dashboard/src/
    pages/secrets/
      SecretsListPage.tsx                 — /secrets
      SecretDetailPage.tsx                — /secrets/:id
      SecretImportPage.tsx                — /secrets/import
    pages/rotations/
      AutoRotationInboxPage.tsx           — /rotations/inbox
      RotationTargetsEditorPage.tsx       — /secrets/:id/rotation-targets
      RotationSchedulesPage.tsx           — /secrets/:id/rotation-schedule
    pages/alerts/
      AlertsInboxPage.tsx                 — /alerts
      AlertDetailPage.tsx                 — /alerts/:id
    pages/notifications/
      NotificationChannelsPage.tsx        — /settings/notifications
      NotificationChannelFormPage.tsx     — /settings/notifications/new,:id
    components/secrets/
      SecretRow.tsx
      SecretStatusBadge.tsx
      SecretMetadataPanel.tsx
      SecretHistoryTimeline.tsx
    services/
      secretsApi.ts
      rotationsApi.ts
      alertsApi.ts
      notificationsApi.ts
```

Every page sits behind a `RequirePermission` guard and uses the
existing `@tamma/dashboard` HTTP client + react-query conventions.
No plaintext secret value is ever fetched, rendered, or stored in
React state — the dashboard only shows metadata, fingerprints, and
audit data.

## User Story

As a **Tamma platform operator**,
I want **a single set of browser pages to manage secrets, approve auto-rotations, edit rotation targets, acknowledge alerts, and configure notification channels**,
so that **secret operations are visible and manageable without shell access, and my teammates can help me without needing Postgres credentials.**

      both gated by `requirePermission('settings:manage')` and

- [ ] Error state: retry button + error message (no stack trace

## Dev Notes

### Requirements Context Summary

**Epic Context**: This story is the operator-facing UI for every
secret-management feature shipped in Epic 1.5. It's the visible
front end for the invisible backend work in Stories 1.5-16 through
1.5-38. Without it, operators must curl the API or query Postgres,
which is neither sustainable nor delegatable to less-technical
teammates. The dashboard is what makes this system usable.

**Technical Context**: The dashboard is an existing React SPA in
`packages/dashboard/`. This story extends it with new pages and
components following the established patterns (pages under `pages/`,
components under `components/`, services under `services/`, router
entries in `router.tsx`). No new package, no new build tooling, no
new runtime dependencies beyond `@dnd-kit/sortable` for drag-and-drop
priority reordering.

**Integration Points**:
- **Story 1.5-17**: secrets CRUD API + vault store (source of
  metadata).
- **Story 1.5-19**: `orchestrator_alerts` + workflow status APIs.
- **Story 1.5-30**: rotation targets admin API.
- **Story 1.5-31**: auto-rotation inbox events + approve/reject API.
- **Story 1.5-32**: secret import handle flow.
- **Story 1.5-37**: notification channels CRUD + test endpoint.
- **Story 1.5-38**: rotation schedule CRUD + preview + run-now.
- **Story 16-7 (RBAC)**: `requirePermission` guard + nav conditional.
- **Story 17-2**: RLS on every backend query ensures the dashboard
  only sees current-tenant data.

### Key Design Decisions

1. **Pages can ship incrementally as backends land**. The story is
   deliberately structured so each page is self-contained: the
   secrets list and detail pages depend only on Story 1.5-17; the
   auto-rotation inbox depends on 1.5-31; the notification channels
   page depends on 1.5-37. A partial landing (e.g. secrets list +
   import only) is useful and tracked as sub-PRs under this story.
   The "done" bar is "all pages listed in the AC ship and pass
   their tests."

2. **No secret plaintext in the UI, ever**. Backend APIs do not
   return plaintext for secrets; the dashboard HTTP client has a
   global interceptor that asserts this at runtime. The only
   plaintext that ever touches the dashboard is a freshly-entered
   value on the import form (AC3) or a credential on the
   notification form (AC8), and both use `useRef` rather than
   React state to minimise memory residency.

3. **The pages live in the existing `@tamma/dashboard` package**.
   A new "secrets dashboard" package would duplicate the auth
   surface, the HTTP client, the routing infrastructure, the
   component library, and the build tooling. The existing
   dashboard already has everything these pages need; adding
   pages to it is strictly less work.

4. **`settings:*` permissions rather than a dedicated `secrets:*`
   namespace**. Secret operations are part of platform administration;
   the same owners who manage billing and user roles manage
   secrets. Creating a separate permission namespace would require
   every operator to be granted two roles and would make
   delegation harder. Reusing `settings:view` and `settings:manage`
   is consistent with the rest of the platform.

5. **Drag-and-drop priority reordering for rotation targets**.
   Priority matters for rollback ordering (Story 1.5-30 sorts
   rollback in reverse priority order). Operators think in terms
   of "Postgres should run first, then webhook" — dragging to
   reorder is the natural expression. A "priority number" input
   would work but requires the operator to track collisions.

6. **Auto-refresh off by default on the inbox**. Auto-refresh
   polls the backend every 30 seconds, which is fine for most
   operators but burns API quota and distracts when you're
   mid-action. Off-by-default with a visible toggle respects
   operator attention.

7. **Secret picker is a reusable component**. The rotation targets
   editor, the import form, the notification channels form, and
   the schedule page all need to pick a secret. A single
   `<SecretPicker filter={...} />` component with configurable
   filters prevents drift and ensures every caller gets the same
   metadata-only API contract.

8. **Accessibility is part of the AC, not a follow-on**. Secrets
   and alerts are high-stakes; operators use this UI under pressure
   and sometimes with screen readers. Treating a11y as a blocking
   requirement rather than a future story prevents the usual
   "ship fast then bolt on a11y later" drift.

### Testing Strategy

- **Unit tests** per page using Vitest + `@testing-library/react`
  with MSW for API mocking. Cover happy path, empty state,
  loading state, error state, permission denial.
- **Component tests** for shared components (SecretPicker,
  StatusBadge, HistoryTimeline) against a fixture of example data.
- **Accessibility tests** using `@axe-core/react` in the Vitest
  environment; every test renders the page and asserts zero
  serious/critical violations.
- **Playwright end-to-end** (AC12) runs the full owner flow against
  a running backend (mocked via MSW or a testcontainers stack).
- **Plaintext hygiene tests** inspect the rendered DOM and the
  component state for any hex / base64 / JWT-shaped strings and
  fail if found (outside of fingerprints, which are deliberately
  non-sensitive hashes).
- **Permission tests** mount each page with a member role and
  assert buttons are hidden / disabled appropriately.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Backend returns plaintext value by mistake, UI renders it | Critical | Global HTTP interceptor asserts no `value` field on any secret endpoint and throws; test fixture proves the interceptor catches a violation; runtime alert goes to the logger with a full-stack error for the bug-fix engineer |
| Operator pastes a secret into the form and the browser tab is hijacked before submit | High | Form fields use `useRef`; `beforeUnload` handler clears unsubmitted state; warning banner on the import form tells operators to save externally before submit |
| Drag-and-drop priority reordering produces inconsistent state across a race | Medium | After each drag, the UI PATCHes every affected target and refetches the list; optimistic updates are rolled back on error |
| Permission guard leaks nav entries to read-only members | High | `RequirePermission` wrapper controls both page access and nav rendering; unit tests mount the nav as a read-only member and assert specific entries are missing |
| Pagination loses filter state on navigation | Low | Filters stored in URL query params; back button preserves state |
| Secret picker exposes secrets the caller shouldn't see | Critical | Picker calls `GET /api/v1/secrets` which already filters by tenant + RLS; the picker has no special bypass |
| Playwright test is flaky because of backend timing | Medium | Playwright waits on explicit API response + visible state transition, not on fixed `wait(N)`; flakes investigated immediately |
| Color-only status indicators are invisible to colour-blind operators | Medium | Status badges always pair colour with icon + text; axe audit includes contrast checks |
| Notification channel test button leaks credentials into toast messages | High | Toast message shows only error category + generic message, never the raw `response_snippet`; full details go to the delivery log table which scrubs before storage |
| A page rendered against a stale backend version crashes on unknown field | Low | Every API response is zod-parsed; missing optional fields produce undefined rather than throw; unknown fields are ignored |
