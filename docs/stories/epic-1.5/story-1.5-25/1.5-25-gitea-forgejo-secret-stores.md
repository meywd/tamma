# Story 1.5-25: Gitea + Forgejo Secret Stores (`GiteaSecretStore` + `ForgejoSecretStore`)

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / LLM Safety)
**Status**: ready-for-dev
**Priority**: Medium
**Depends on**: Story 1.5-16 (interface), Story 1.5-17 (`IMirrorStore` + broker service), Story 1-11 (Gitea/Forgejo platform implementations)

## Story

As a **Tamma operator running a self-hosted Gitea or Forgejo instance**,
I want **real `IMirrorStore` implementations for both platforms that
share a common base class (since their Actions secrets APIs are
structurally identical) and differ only in minimum version detection
and default API base URL**,
so that **self-hosted git platforms get the same LLM-safe secret
provisioning as GitHub and GitLab, and so that the Tamma codebase does
not carry two nearly-identical copies of the same implementation**.

## Context

Stories 1.5-23 and 1.5-24 implemented real mirrors for GitHub and
GitLab. This story implements Gitea and Forgejo together. Gitea and
Forgejo are closely related — Forgejo is a community fork of Gitea
that diverged in 2022 — and their Actions secrets APIs are 90%
identical. Rather than writing two near-duplicate classes, this story
defines a shared base class `GiteaForgejoSecretStoreBase` and two thin
subclasses that override only:
1. The minimum supported version (Gitea ≥ 1.19, Forgejo ≥ 1.21)
2. The default API base URL (none — both require explicit configuration)
3. The `platformName` string returned to the registry
4. The server-capability detection logic for features that landed in
   different versions (environment secrets, in particular)

Both platforms' Actions secrets APIs use endpoints of the form
`/repos/:owner/:repo/actions/secrets/:name` and do NOT require
client-side encryption (unlike GitHub) — they encrypt at rest
server-side.

This story also extends the `scope-addressable-matrix.ts` helper from
Story 1.5-16 to include Gitea and Forgejo, recording which scope kinds
each platform supports at its minimum version.

Related work:
- Bitbucket + Azure DevOps mirrors → Story 1.5-26
- Revocation cascade → Story 1.5-30
- Drift detection webhooks → Story 1.5-33
- Gitea Actions CI runner fetch-secrets template → Story 1.5-40
  (self-hosted git variants owns the runner-template work since
  Gitea Actions runner configuration varies significantly across
  self-hosted installations)

## Acceptance Criteria

### AC1: Shared base class `GiteaForgejoSecretStoreBase`

- [ ] `packages/secret-broker/src/mirrors/gitea-forgejo-base.ts`
      exports an abstract `GiteaForgejoSecretStoreBase implements IMirrorStore`
      class.
- [ ] The class is abstract in the TypeScript sense: subclasses must
      implement:
      ```typescript
      protected abstract get platformKey(): 'gitea' | 'forgejo';
      protected abstract get minimumVersion(): string;  // semver
      protected abstract get minimumEnvironmentSecretsVersion(): string | null;
      ```
- [ ] Constructor signature:
      ```typescript
      constructor(options: {
        platform: GiteaPlatform | ForgejoPlatform;  // from 1-11
        logger: pino.Logger;
        eventStore: IEventStore;
      })
      ```
- [ ] The base class provides concrete implementations of `write`,
      `delete`, `listAt` that call the shared endpoints and use the
      subclass's version hooks to decide whether optional features
      (environment secrets) are available.
- [ ] The base class reuses whichever HTTP client is exposed by the
      parent platform — either a `fetch`-based client, a custom
      typed client, or whichever SDK Story 1-11 chose. The base class
      does not construct its own client.

### AC2: `GiteaSecretStore` subclass

- [ ] `packages/secret-broker/src/mirrors/gitea-mirror-store.ts` exports
      `GiteaSecretStore extends GiteaForgejoSecretStoreBase`.
- [ ] Overrides:
      ```typescript
      protected readonly platformKey = 'gitea';
      protected readonly minimumVersion = '1.19.0';
      protected readonly minimumEnvironmentSecretsVersion = '1.22.0';
      ```
- [ ] Registered in the broker's `PlatformMirrorRegistry` under key
      `'gitea'`.
- [ ] A single-file unit test asserts the subclass forwards to the
      base class and passes the platform-specific constants through
      the registry.

### AC3: `ForgejoSecretStore` subclass

- [ ] `packages/secret-broker/src/mirrors/forgejo-mirror-store.ts`
      exports `ForgejoSecretStore extends GiteaForgejoSecretStoreBase`.
- [ ] Overrides:
      ```typescript
      protected readonly platformKey = 'forgejo';
      protected readonly minimumVersion = '1.21.0';
      protected readonly minimumEnvironmentSecretsVersion = null;  // not yet supported
      ```
- [ ] Registered in the broker's `PlatformMirrorRegistry` under key
      `'forgejo'`.
- [ ] Unit test symmetric to AC2.

### AC4: Version detection at first call

- [ ] On the first method call against a given platform instance, the
      base class calls the platform's version endpoint (`GET /api/v1/version`
      for both) and caches the result on the instance.
- [ ] If the detected version is below `minimumVersion`, the method
      throws a typed `UnsupportedPlatformVersionError` with message:
      `"Gitea 1.18.3 is below the minimum required version 1.19.0 for Actions secrets. Upgrade or use a different mirror."`
      (substituting Forgejo / its minimum as appropriate).
- [ ] The version-detection call itself is wrapped with a 5-second
      timeout. On timeout the error message is:
      `"Failed to detect Gitea version within 5s at <base_url> — check network and credentials"`.
- [ ] A unit test seeds a mock client that returns `"1.18.3"` and
      asserts the error is thrown on `write`. A second test returns
      `"1.19.5"` and asserts `write` proceeds.

### AC5: Repo-scoped secret CRUD

- [ ] `write(target, value, commitment)` where
      `target.scope.kind === 'repo'`:
  1. `GET /repos/:owner/:repo` to assert existence and access (404 →
     `TargetNotFoundError`, 403 → `PermissionError`).
  2. `PUT /repos/:owner/:repo/actions/secrets/:name` with body
     `{ "data": "<plaintext>" }` (both platforms expect plaintext
     value in the `data` field — no client-side encryption).
  3. Update `tamma_vault_deploy_targets` row to `synced`.
  4. Emit `SECRET.DEPLOYED.SUCCESS`.
- [ ] `delete(target)` calls
      `DELETE /repos/:owner/:repo/actions/secrets/:name`.
- [ ] `listAt(scope)` where `scope.kind === 'repo'` calls
      `GET /repos/:owner/:repo/actions/secrets` and returns names only.
      Both Gitea and Forgejo already return names-only on this endpoint,
      but a defensive unit test asserts no `value`/`data` field leaks
      through.

### AC6: Org-scoped secret CRUD

- [ ] `write` with `scope.kind === 'org'` calls the org endpoints:
  - `PUT /orgs/:org/actions/secrets/:name`
  - `DELETE /orgs/:org/actions/secrets/:name`
  - `GET /orgs/:org/actions/secrets`
- [ ] Body shape is the same as repo scope: `{ "data": "<plaintext>" }`.
- [ ] Neither platform supports `visibility`/`selected_repository_ids`
      semantics (unlike GitHub). An org secret is visible to all repos
      in the org automatically. The store documents this in the error
      message if a caller passes `metadata.visibility` — the field is
      silently ignored with a `logger.warn` line recording the
      discrepancy.

### AC7: Environment-scoped secret CRUD with graceful degradation

- [ ] `write` with `scope.kind === 'environment'`:
  1. If `minimumEnvironmentSecretsVersion` is `null` (Forgejo), throw
     `EnvironmentSecretsUnsupportedError` with message pointing at the
     tracking issue.
  2. If the detected platform version is below
     `minimumEnvironmentSecretsVersion`, throw
     `EnvironmentSecretsUnsupportedError` with the version gap.
  3. Otherwise call `PUT /repos/:owner/:repo/environments/:env/actions/secrets/:name`
     (Gitea ≥ 1.22 endpoint shape — confirm against Gitea docs during
     implementation).
- [ ] `delete` and `listAt` use the corresponding endpoints.
- [ ] A unit test on Forgejo asserts the error is thrown without any
      HTTP call being made.
- [ ] A unit test on Gitea with a mocked version endpoint returning
      `"1.21.9"` asserts the error is thrown; a second test with
      `"1.22.0"` asserts the call proceeds.

### AC8: `tenant_root` scope is refused

- [ ] Same rule as GitHub (1.5-23 AC6) and GitLab (1.5-24 AC5):
      `tenant_root` throws `UnsupportedScopeError` before any HTTP call.

### AC9: Extend `scope-addressable-matrix.ts`

- [ ] `packages/platforms/src/scope-addressable-matrix.ts` (originally
      from Story 1.5-16 Task 4) is extended to include Gitea and
      Forgejo rows with the following truth table:

      | Platform | repo | org | project | environment | tenant_root |
      |----------|------|-----|---------|-------------|-------------|
      | gitea    | true | true| false   | version-dependent | false |
      | forgejo  | true | true| false   | false       | false       |

- [ ] For the `environment` case on Gitea, the helper returns a
      sentinel `'version-dependent'` (typed as a literal) rather than
      a plain boolean, forcing callers to handle the "we can't know
      statically" case explicitly.
- [ ] Existing unit tests (from 1.5-16 Task 4) cover all five scope
      kinds × all seven platforms. New rows add 2 × 5 = 10 cases;
      assert the expected truth values.

### AC10: Error mapping (shared)

- [ ] `packages/secret-broker/src/mirrors/gitea-forgejo-error-mapper.ts`
      defines `mapGiteaForgejoMirrorError(error: unknown, platform: 'gitea' | 'forgejo'): MirrorStoreError`:
  | HTTP status | Error class |
  |---|---|
  | 401 | `GiteaForgejoAuthError` — "invalid or expired access token" |
  | 403 | `GiteaForgejoPermissionError` — "insufficient scope (need `write:org` or `repo`)" |
  | 404 | `TargetNotFoundError` — "repository, organization, or environment not found" |
  | 409 | `GiteaForgejoConflictError` — "secret already exists (should upsert)" |
  | 422 | `ValidationError` — "invalid secret name or body" |
  | 5xx | `ServerError` — retryable |
- [ ] Unit tests per status per platform (2 × 6 = 12 cases).

### AC11: Rate limit handling

- [ ] Neither Gitea nor Forgejo ships a standardised rate-limit header
      set by default — operators configure rate limits in their
      instance's `app.ini`. The base class does NOT try to parse
      instance-specific headers. Instead it uses a blanket exponential
      backoff on any 429 response: 1s, 2s, 4s, 8s, 16s (max 5 attempts).
- [ ] On 5xx responses the same backoff applies.
- [ ] A unit test simulates a 429 then success and asserts the retry.

### AC12: Sync status tracking + audit events

- [ ] Matches Stories 1.5-23 / 1.5-24: update `tamma_vault_deploy_targets`
      to `synced` or `failed`; emit `SECRET.DEPLOYED.*`, `SECRET.REVOKED.*`,
      `SECRET.LISTED` with `platform: 'gitea' | 'forgejo'` tags.

- [ ] A `docker/docker-compose.gitea-forgejo-test.yml` file defines

  1. Repo-scoped write → list → delete

  4. (Forgejo only) Environment-scoped write → assert

  5. Version detection below minimum → assert

- [ ] Tests tear down the compose fixture in `afterAll`.
- [ ] If the compose file cannot be brought up (Docker daemon down,

## Dev Notes

### Requirements Context Summary

**Epic Context**: Gitea and Forgejo are the self-hosted sibling platforms
to GitHub and GitLab respectively. Operators running air-gapped or
compliance-sensitive Tamma deployments typically choose one of these two
over cloud git platforms. Supporting them is important for the
self-hosted operator persona even though their install base is smaller
than GitHub's.

**Technical Context**: The two platforms share ~90% of the same Actions
secrets API surface because Forgejo forked from Gitea at 1.18 and the
Actions subsystem has evolved in parallel. Writing two near-identical
classes would be a maintenance burden — whichever copy got a bug fix
first would drift out of sync with the other. A shared abstract base
class with thin platform subclasses is the right factoring: the base
class owns the wire protocol, subclasses own only the version
constants and capability flags.

**Integration Points**:
- **Story 1-11 (Gitea/Forgejo platforms)**: each mirror reuses the
  parent platform's HTTP client.
- **Story 1.5-17 (broker)**: `PlatformMirrorRegistry` wiring.
- **Story 1.5-16 (scope matrix)**: extends the existing helper.
- **Future story** (Gitea Actions runner + fetch-secrets template):
  tracked separately; this story only ships the write-side mirror.

### Key Design Decisions

1. **Abstract base class + thin subclasses.** 90% shared implementation
   with per-platform version constants and feature flags. The alternative
   — two sibling classes sharing via composition — was considered but
   rejected: the constants are compile-time, the shared methods genuinely
   share implementation, and the inheritance is a clean "base class owns
   protocol, subclass owns identity" split. This is one of the few
   places in the Tamma codebase where inheritance is clearly the right
   tool.

2. **Plaintext over TLS, no client-side crypto.** Both platforms accept
   plaintext values in the request body (`{ "data": "<value>" }`).
   Neither has GitHub-style sealed-box encryption. Taint-tracking test
   coverage is correspondingly more important because the plaintext
   briefly exists in the request body formatter.

3. **Version detection at first call, cached per instance.** The
   platform SDK from Story 1-11 may not expose the detected version
   — Tamma-side detection decouples from whatever Story 1-11 does.
   The 5s timeout matters because self-hosted instances can be very
   slow or reachable only via VPN.

4. **`'version-dependent'` sentinel for Gitea environment secrets.**
   Gitea added environment secrets in 1.22. A plain boolean lookup
   in the matrix would either have to lie (return `true` always and
   rely on runtime version check) or be conservative (return `false`
   always and block operators on 1.22+). The sentinel forces callers
   to handle the case explicitly — at compile time via exhaustiveness
   checks.

5. **No heroics around rate limits.** Both platforms' rate-limit
   header schemes are operator-configurable and not standardised.
   The store uses a blanket backoff on 429 rather than trying to
   parse headers. This is worse than GitHub's header-aware handler
   but correct — parsing unknown headers is strictly worse than
   backing off.

6. **`visibility` metadata is silently ignored, not rejected.** Gitea
   and Forgejo org secrets are visible to all org repos by default.
   A caller that passes `metadata.visibility: 'selected'` (meaningful
   on GitHub) is making a portable assumption — the store logs a
   warning but still performs the write. Rejecting would be more
   correct but would break cross-platform deployment configurations
   that target multiple platforms with the same metadata.

7. **Docker-compose fixture for integration tests.** The fixture is
   the only way to run real integration tests without relying on a
   hosted Gitea/Forgejo instance. It's gated by an env var so it
   doesn't run on every developer machine (Docker-in-Docker is
   unreliable), but does run in CI when explicitly requested via
   the fixture workflow.

8. **Gitea 1.22 environment secrets endpoint shape is resolved at
   implementation time.** At story-writing time the author was not 100%
   sure whether Gitea's environment secrets endpoint matches
   GitHub's `/repositories/{id}/environments/{env}/secrets/{name}`
   shape or a different `/repos/{owner}/{repo}/environments/{env}/secrets/{name}`
   shape. Implementation SHOULD consult Gitea's Swagger spec
   (`/api/swagger`) on a live 1.22+ instance before settling on the
   endpoint URL. If the shape turns out to differ from the stated
   URL, update this story's AC7 and proceed — the contract (version
   gating + graceful degradation) is the load-bearing requirement,
   not the exact URL.

### Testing Strategy

- **Unit tests** with a mocked HTTP client (`msw`) for all methods and
  both platforms.
- **Version-detection tests** for the 3 cases: below minimum, exactly
  minimum, above minimum.
- **Scope-matrix tests** for the new platform rows.
- **Integration tests** against a docker-compose fixture with real
  Gitea and Forgejo containers, gated by `GITEA_FORGEJO_TEST_COMPOSE=1`.
- **Taint-tracking tests** for plaintext in logs, errors, DB rows, events.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Gitea 1.22 endpoint shape differs from assumption | Medium | AC7 notes the uncertainty; implementation consults Swagger spec; fallback updates this story if URL differs |
| Forgejo API diverges from Gitea in a future release | Medium | Subclasses can override individual methods from the base class if needed; version detection catches silent drift |
| Docker-compose fixture flaky in CI | Medium | Health-wait with long timeout (60s); skip cleanly if Docker unavailable; retry once on first failure |
| Plaintext in request body logged by HTTP client | High | Taint-tracking test asserts plaintext does not appear in pino logs; HTTP client instrumentation is checked for body capture |
| Rate-limit backoff insufficient for slow instances | Low | Backoff caps at 5 attempts totaling ~31s; operators running very slow instances can raise via env var |
| Self-hosted operator has no admin token | N/A | Not Tamma's problem — document the requirement in README |

  manually. There is nothing to mirror to. Rejected.
