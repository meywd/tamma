# Story 1.5-22: `actions/fetch-secrets/` GitHub Action

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / CI Integration)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-21 (CI fetch endpoint)

## Story

As a **user of Tamma running workflows in GitHub Actions**,
I want **a first-party reusable Action at `tamma-dev/tamma/actions/fetch-secrets@v1`
that pulls my secrets into my job's environment using my runner's
ambient OIDC token**,
so that **I can replace brittle `env: MY_SECRET: ${{ secrets.MY_SECRET }}`
workflow boilerplate with a single `uses:` step that is workload-identity
authenticated, bound to my specific run, and provably tamper-evident
via commitment hashes**.

## Context

Story 1.5-21 built `POST /api/v1/ci/fetch-secrets`. This story builds
the client that every GitHub Actions user calls to hit that endpoint:
a reusable Action published from the Tamma monorepo at a stable path.

The Action sits between GitHub Actions' native OIDC token issuance
(via `@actions/core.getIDToken`) and the Tamma broker's `/api/v1/ci/fetch-secrets`
endpoint. Its responsibilities are:

1. Fetch a short-lived OIDC token scoped to `https://api.tamma.dev`
2. POST it alongside the list of requested secrets to the Tamma
   endpoint
3. Register every returned value with GitHub's log scrubber
   (`::add-mask::` via `core.setSecret`)
4. Write them to `GITHUB_ENV` so subsequent steps in the job can read
   them as environment variables
5. Optionally verify the returned commitment hashes match an
   expected set, failing the job on drift

The Action is distributed via the Tamma monorepo — not a separate
repository — because:

- The `uses: tamma-dev/tamma/actions/fetch-secrets@v1` path pattern
  lets users pin to the same repo that hosts the Tamma source, which
  is a trust story in itself (if you trust Tamma enough to give it
  your secrets, you can trust the Action published from the same repo)
- We avoid the problem of a second repo falling out of sync with the
  API contract in Story 1.5-21
- GitHub Actions supports `uses: owner/repo/path@ref` natively, so the
  path is a first-class citizen, not a workaround

This story explicitly does NOT cover:

- GitLab CI equivalent (future story)
- Gitea / Forgejo / Bitbucket equivalents (future stories)
- A separate `@tamma/fetch-secrets-action` npm package (distribution
  is via monorepo path only)
- Secret fetching during a `pull_request` event from a fork —
  GitHub Actions does not grant OIDC tokens to fork-originated
  workflows by default; this is a feature, not a limitation
- Caching secret values across runs on the same runner (each run
  re-fetches)

### AC2: `action.yml` metadata

- [ ] `actions/fetch-secrets/action.yml` declares:
  ```yaml
  name: 'Tamma — Fetch Secrets'
  description: 'Pulls secrets from Tamma into your job environment using OIDC'
  author: 'Tamma'
  branding:
    icon: 'lock'
    color: 'purple'
  inputs:
    tamma-url:
      description: 'Base URL of your Tamma instance'
      required: false
      default: 'https://api.tamma.dev'
    tenant-id:
      description: 'Tamma tenant ID (UUID)'
      required: true
    secrets:
      description: |
        Multiline mapping of env var name to Tamma secret id.
        Format: ENV_VAR_NAME: <secret-uuid>
        One pair per line. Comments (#) allowed.
      required: true
    auth-method:
      description: 'Auth method: oidc (default) or bootstrap-token'
      required: false
      default: 'oidc'
    export-to-env:
      description: 'Write values to GITHUB_ENV for subsequent steps'
      required: false
      default: 'true'
    verify-commitments:
      description: |
        Compare returned commitment against `expected-commitments`
        input. Fail job on mismatch.
      required: false
      default: 'false'
    expected-commitments:
      description: |
        Multiline mapping of secret id to expected commitment hex.
        Format: <secret-uuid>: <commitment-hex>
        Only consulted when verify-commitments=true.
      required: false
  outputs:
    secret-count:
      description: 'Number of secrets successfully fetched'
    fingerprints:
      description: 'JSON array of {id, envVarName, fingerprint} records'
  runs:
    using: 'node20'
    main: 'dist/index.js'
  ```
- [ ] Every input documented inline with no abbreviation. The
      README elaborates on edge cases but the `action.yml` is the
      canonical source for casual users.
- [ ] `fingerprints` output is a JSON string (Actions outputs are
      strings) that subsequent steps can `fromJSON()` to read.
      Each record contains `id`, `envVarName`, and `fingerprint` — 
      NEVER `value` or `commitment`. Fingerprints are the public,
      non-sensitive identifier for a secret.

### AC3: Input parser for the `secrets` multiline format

- [ ] `actions/fetch-secrets/src/parse-secrets-input.ts` exports:
  ```typescript
  export interface ParsedSecret {
    envVarName: string;
    secretId: string;
    expectedCommitment?: string;
  }

  export function parseSecretsInput(raw: string): ParsedSecret[];
  export function parseExpectedCommitments(raw: string): Map<string, string>;
  ```
- [ ] Grammar:
  - One pair per line
  - Leading/trailing whitespace ignored
  - Empty lines ignored
  - Lines starting with `#` ignored (comments)
  - Pair format: `<env-var-name>: <uuid>`
  - `env-var-name` must match `^[A-Z_][A-Z0-9_]*$` (shell env var
    conventions; reject lowercase to prevent confusion)
  - `uuid` must match a strict UUID v4/v7 regex
  - On any parse error, throw with a clear message including the
    line number
- [ ] Duplicate env var names within a single input → error
      `DUPLICATE_ENV_VAR`. Duplicate secret ids are fine (the user
      might want two env vars pointing at the same secret).
- [ ] Duplicate env var names ARE distinct from duplicate
      case-insensitive names — `FOO` and `foo` could never coexist
      anyway since lowercase is rejected.
- [ ] Maximum 200 pairs per invocation, matching Story 1.5-21's
      `secretIds.max(200)`. Exceeding → error `TOO_MANY_SECRETS`.
- [ ] `parseExpectedCommitments` parses the same format in reverse
      (`<uuid>: <hex>`). Hex must be exactly 64 chars (32 bytes of
      HMAC-SHA256).
- [ ] Exhaustive unit tests cover:
  - Valid single-pair input
  - Valid multi-pair with comments and blank lines
  - Malformed env var name → error
  - Malformed UUID → error
  - Too many pairs → error
  - Duplicate env var → error
  - Empty input → error `NO_SECRETS_REQUESTED`

### AC4: HTTP client for the Tamma fetch endpoint

- [ ] `actions/fetch-secrets/src/http-client.ts` exports:
  ```typescript
  export interface FetchSecretsClient {
    fetchSecrets(opts: {
      tammaUrl: string;
      tenantId: string;
      token: string;              // OIDC JWT or bootstrap token
      authMethod: 'oidc' | 'bootstrap-token';
      scope: SecretScope;
      secretIds: string[];
      runContext: RunContext;     // repo, workflow, job, runId, sha
    }): Promise<FetchSecretsResponse>;
  }
  ```
- [ ] Uses `@actions/http-client` (the first-party HTTP client for
      Actions), NOT `node-fetch` or plain `https` — the Actions
      http-client handles GitHub-specific proxy configuration and
      retry semantics for free.
- [ ] Timeout: 30 seconds (Actions' overall request timeout is 60s
      so we leave headroom for the rest of the Action to parse the
      response and set env vars).
- [ ] Retry: exponential backoff on 5xx responses only, max 3
      attempts. 4xx responses are terminal — the server has rejected
      our request and retrying won't help. 429 is treated as a
      retryable 5xx for this purpose, respecting `Retry-After`.
- [ ] Request body matches Story 1.5-21 AC2 exactly.
- [ ] Response parsing validates the shape and types — an unexpected
      response shape throws `INVALID_RESPONSE_SHAPE` with the HTTP
      status and a truncated preview of the body (first 200 chars,
      stripped of anything that looks like a secret value).
- [ ] All `Authorization` header values are passed verbatim. The
      header is NEVER logged; even on error paths, the error message
      redacts the header.
- [ ] A mock-based test suite using `@actions/http-client`'s built-in
      test mode (or `nock`) covers:
  - Success response → parsed correctly
  - 401 → throws `UNAUTHORIZED`
  - 403 → throws `FORBIDDEN` with response `code` field surfaced
  - 404 → throws `SECRET_NOT_FOUND`
  - 429 → retries with backoff, eventually succeeds or fails
  - 500 → retries with backoff, eventually throws `SERVER_ERROR`
  - Network error → throws `NETWORK_ERROR`
  - Timeout → throws `TIMEOUT`
  - Malformed JSON response → throws `INVALID_RESPONSE_SHAPE`

### AC5: Main entry point and orchestration

- [ ] `actions/fetch-secrets/src/index.ts` is the `main` entry. It:
  1. Reads inputs via `core.getInput` / `core.getMultilineInput`
  2. Parses the `secrets` input via `parseSecretsInput`
  3. Parses `expected-commitments` if `verify-commitments === 'true'`
  4. Builds the `runContext` from `process.env.GITHUB_*` variables:
     `GITHUB_REPOSITORY`, `GITHUB_WORKFLOW`, `GITHUB_JOB`,
     `GITHUB_RUN_ID`, `GITHUB_SHA`
  5. Determines the auth token:
     - If `auth-method === 'oidc'`:
       - Call `core.getIDToken('https://api.tamma.dev')` (or the
         configured `tamma-url`)
       - Handle `core.getIDToken` failures explicitly — the most
         common is missing `permissions: id-token: write` in the
         workflow. Error message points the user at the README
         section documenting the fix.
     - If `auth-method === 'bootstrap-token'`:
       - Read `TAMMA_CI_TOKEN` from env
       - If missing → clear error "TAMMA_CI_TOKEN env var is
         required when auth-method=bootstrap-token"
     - If `auth-method === 'oidc'` and `getIDToken` fails AND
       `TAMMA_CI_TOKEN` is set → fall back to bootstrap with a
       loud `core.warning()`. This is the "OIDC preferred, bootstrap
       fallback" model documented in Story 1.5-21 AC3.
  6. Call `FetchSecretsClient.fetchSecrets(...)`
  7. For each returned secret in order:
     - Call `core.setSecret(value)` BEFORE any other logging or
       env-var writing — this is the critical ordering that registers
       the value with GitHub's log scrubber
     - If `export-to-env === 'true'`: append
       `ENV_VAR_NAME<<DELIMITER\nvalue\nDELIMITER` to `GITHUB_ENV`
       using a random delimiter (handles multiline values safely per
       GitHub's documentation)
     - If `verify-commitments === 'true'`: look up the expected
       commitment for this secret's id in the parsed map; if the
       returned commitment does not match (constant-time comparison)
       → fail the job with `SECRET_COMMITMENT_DRIFT` and log ONLY
       the env var name and first 8 hex chars of both commitments
  8. Set outputs:
     - `secret-count`: string representation of the count
     - `fingerprints`: JSON-stringified array of `{id, envVarName,
       fingerprint}` records
  9. `core.info("Fetched N secrets")` (no secret content)
- [ ] On any error: `core.setFailed(error.message)`. The error
      message passes through a redaction pass that strips any byte
      sequence matching a recently-seen secret value.
- [ ] Every secret value Buffer is zeroised (`buffer.fill(0)`) after
      being written to GITHUB_ENV, to the extent Node allows. String
      values are GC'd normally — no special handling possible for
      strings beyond not logging them.
- [ ] The full flow works end-to-end in a test harness that mocks
      `@actions/core`, `@actions/http-client`, and `process.env`.

### AC6: Ordering — `::add-mask::` before anything else

- [ ] `core.setSecret(value)` MUST be called before the first
      invocation of `core.info`, `core.debug`, `core.warning`,
      `core.error`, `core.notice`, or any `console.log` that could
      include the value. In practice this means: inside the "for
      each returned secret" loop, `setSecret` is the FIRST action
      after parsing the response.
- [ ] A dedicated test uses a `@actions/core` mock that records the
      order of calls and asserts `setSecret` comes before any other
      core method on the secret's own value. Regression test for
      the "value leaked in a debug line" class of bug.
- [ ] Even before per-secret handling begins, the Action calls
      `core.setSecret(token)` on the OIDC token itself so the log
      scrubber masks it. GitHub already masks its own OIDC tokens
      but bootstrap tokens are ours and must be masked explicitly.

### AC7: Error messages never contain secret values

- [ ] Every `throw` in the Action code uses one of a small set of
      typed error classes:
  ```typescript
  class ActionError extends Error {
    constructor(public code: string, message: string);
  }
  class ParseError extends ActionError {}
  class AuthError extends ActionError {}
  class HttpError extends ActionError {}
  class VerificationError extends ActionError {}
  ```
- [ ] Error `message` fields are template strings with only
      identifier data (env var names, secret IDs, HTTP status
      codes, GitHub context values). They never interpolate a
      secret value, a commitment, or a token.
- [ ] A taint-tracking test injects a known plaintext into the test
      fixtures, triggers every error path, and asserts the plaintext
      does not appear in:
  - The output of `core.setFailed`
  - Stdout/stderr captured during the run
  - Any `core.info/debug/warning/error` call
- [ ] `core.setFailed` messages always include the error `code` so
      users can look it up in the README troubleshooting section
      without reading the full message.

## Dev Notes

### Requirements Context Summary

**Epic Context**: Story 1.5-22 closes the loop. 1.5-17 built the
vault. 1.5-20 built OIDC auth. 1.5-21 built the CI fetch endpoint.
1.5-22 is the piece users actually add to their workflows. If any of
the upstream stories have a bug, a user discovers it by running this
Action and getting a confusing error — so the error surface on the
Action side matters a lot.

**Technical Context**: A standard GitHub Action: node20 runtime,
`@actions/core` for inputs/outputs/masking, `@actions/http-client`
for HTTP, ncc for bundling. Published via monorepo path
`tamma-dev/tamma/actions/fetch-secrets@v1`. The `dist/` directory is
committed (Actions convention). Runtime has zero external
dependencies at install time — users just reference the path.

**Integration Points**:
- **Story 1.5-21's endpoint**: the one external API the Action calls
- **`@actions/core.getIDToken`**: GitHub's OIDC token minting
- **`GITHUB_ENV`**: where values land for subsequent steps
- **`::add-mask::` / `core.setSecret`**: GitHub's log scrubber
- **Nothing else**: no Tamma code is linked into the Action bundle;
  the Action is a pure client

### Key Design Decisions

1. **Monorepo path, not a separate repo.** Keeping the Action in the
   same repo as Tamma means the API contract in Story 1.5-21 and the
   client in this story are always built from the same commit. Users
   pin `@v1` and get a client that matches whatever server version
   they're running, assuming they upgrade both in lockstep (as
   documented). Separate repos invite drift.

2. **Stable path across minor versions.** `actions/fetch-secrets/`
   is part of the public API. Moving it would break every user's
   `uses:` line. Breaking changes to the path require a major
   version bump and a migration guide — we treat the path like any
   other API surface.

3. **`dist/` committed.** This is the GitHub Actions convention.
   Alternative approaches (build-on-use via a `pre` hook, or
   publishing to a CDN) are slower, less reliable, and outside the
   norms the Actions community expects. ncc-bundled committed
   `dist/` is the well-trodden path.

4. **`@actions/http-client`, not `node-fetch`.** The first-party
   client handles corporate proxies, runner-specific retry logic,
   and user-agent conventions without us having to care. It's the
   default in every well-built Action we could find.

5. **Constant-time comparison for commitments.** Even though
   commitments are not themselves secret, an attacker who can observe
   timing on a leaked commitment verification could potentially
   derive information. Cheap to do right, so do it right.

6. **Zero retries on 4xx, exponential backoff on 5xx.** 4xx means
   the server has told us "no" for a reason we understand; retrying
   is pointless and noisy. 5xx means the server is broken; retrying
   with backoff is the right move. 429 is a special case treated
   like a retryable 5xx with `Retry-After` honored.

7. **Ordering of `setSecret`.** The Action must call
   `core.setSecret(value)` before any other core method references
   the value. This is the one ordering constraint that matters — a
   `core.info("got secret", value)` called before `setSecret` would
   leak the value into the log. The test suite asserts this
   invariant via a mock that records call order.

8. **Typed errors with codes.** Every failure mode has a stable
   `code` string (`UNAUTHORIZED`, `FORBIDDEN`,
   `SECRET_COMMITMENT_DRIFT`, etc.). Users look up the code in the
   README troubleshooting table. Free-form error messages rot over
   time; codes are stable.

9. **OIDC preferred, bootstrap fallback.** The Action tries OIDC
   first (the right answer), falls back to bootstrap only if
   explicitly enabled by the presence of `TAMMA_CI_TOKEN` in the
   environment. A loud `core.warning` reminds the user to migrate.
   This matches Story 1.5-21 AC3.

10. **Outputs limited to non-sensitive data.** `secret-count` is a
    number. `fingerprints` is a list of opaque identifiers. Values
    and commitments are deliberately NOT outputs — if a user wants
    downstream steps to read values they go via `GITHUB_ENV` where
    GitHub's masking applies.

### Testing Strategy

- **Unit tests** for each module in isolation with full coverage of
  error paths.
- **Mocked end-to-end tests** that exercise the entry point against
  mocked `@actions/core`, `@actions/http-client`, and environment
  variables.
- **Ordering tests** that assert `setSecret` is called before any
  other core method on a given value.
- **Taint-tracking tests** that inject known plaintexts and assert
  they never appear in any output.
- **Post-merge integration tests** against a real Tamma staging
  instance to catch server-side regressions that unit tests miss.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Secret value leaks into log via `core.info` before `setSecret` | Critical | Ordering test + taint test; code review checklist item |
| `dist/` out of sync with source | High | `check-action-dist.yml` CI check fails PRs that forget to rebuild |
| User forgets `permissions: id-token: write` in their workflow | High | Clear error message pointing at README section; troubleshooting table |
| Multiline secret values break `GITHUB_ENV` parsing | High | Random-delimiter approach per GitHub docs; test with a value containing `\n`, `=`, and `<<EOF` |
| ncc bundle pulls in a malicious transitive dep | High | Dependencies pinned in `package.json`; `pnpm audit` runs in CI; only two runtime deps both owned by `@actions` |
| Action breaks on GitHub's node runtime update | Medium | Pin `node20`; `action.yml` declares the runtime explicitly; integration test catches breakage |
| User points at a malformed secret id | Low | Parser rejects with clear error including line number |
| User copies a bootstrap token into workflow YAML | Medium | README explicitly warns against this and shows the `env:` approach instead |
| `fingerprints` output is too large for a single Actions output | Low | Max 200 secrets × ~80 bytes per record ≈ 16KB — well within the 1MB output limit |
| OIDC token refresh within a single Action invocation fails | Low | Action is a single shot; tokens are valid for the life of the run; no refresh needed |

## What is NOT in scope

- GitLab / Gitea / Bitbucket / Azure DevOps Action equivalents
- Publishing the Action to the GitHub Marketplace (that's a separate
  release-time concern with its own branding/screenshot requirements)
- npm distribution as `@tamma/fetch-secrets-action`
- A "container" Action variant (Dockerfile) — node20 is sufficient
- Secret caching across runs on the same runner
- Offline mode / air-gapped Tamma instances
- Action-side metrics or telemetry (the server records everything)
- Ability to fetch a secret by "slug" rather than UUID (future ergonomic
  improvement; out of scope here)
- Composite Action variant that wraps multiple operations
