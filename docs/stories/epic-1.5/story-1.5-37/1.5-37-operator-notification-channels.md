# Story 1.5-37: Operator notification channels (Slack / Email / PagerDuty / Webhook)

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / Operations)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-17 (TammaVaultStore + broker HTTP service), Story 1.5-19 (`alert_orchestrator` + `orchestrator_alerts` table), Story 1.5-16 (secret interface for channel credential storage)

## Story

As a **Tamma operator running a multi-tenant deployment**,
I want **a pluggable notification system that fans out every `alert_orchestrator` write to Slack, email, PagerDuty, and generic HTTP webhooks in addition to the `orchestrator_alerts` Postgres table**,
so that **when a secret rotation stalls at 2am I hear about it on my phone via PagerDuty rather than discovering it the next morning by querying the alerts table.**

## Context — Why this story exists

Story 1.5-19 delivered `alert_orchestrator` in its v1 form: the tool
writes to a Postgres `orchestrator_alerts` table and emits a DCB event.
The rationale at the time was "durable storage + audit first, push
channels later." Story 1.5-31 (auto-rotate) then inherited the same
contract: when a forced-rotation workflow fires, it also writes to
`orchestrator_alerts` and stops there.

That gap — no push notifications beyond the table — is the problem this
story closes. Operators running production deployments need the alert to
reach them wherever they are: Slack for routine issues, PagerDuty for
wakeups, email for digest summaries, and generic webhooks for custom
integrations (ServiceNow, Opsgenie, internal ticketing, etc.).

The design is a pluggable fan-out: `alert_orchestrator` continues to
write to `orchestrator_alerts` (unchanged — that's the source of truth)
and additionally enqueues a delivery job for every channel configured
for the tenant. Each channel has its own `INotificationChannel`
implementation, its own retry policy, and its own audit log. Channels
can be added, removed, or temporarily disabled without touching the
alert pipeline itself.

### Architecture summary

```
  alert_orchestrator(payload)
        │
        ▼
  INSERT into orchestrator_alerts  ──► (source of truth, unchanged)
        │
        ▼
  NotificationDispatcher
        │  listEnabled(tenantId) from notification_channels
        ▼
  ┌──────────┬──────────┬──────────┬──────────┐
  │  Slack   │  Email   │ PagerDuty│ Webhook  │
  └──────────┴──────────┴──────────┴──────────┘
        │         │         │         │
        ▼         ▼         ▼         ▼
  delivery_attempts rows + per-channel retry queue
```

All channels share a common retry envelope (exponential backoff with
jitter, max 5 attempts over 10 minutes) and a common audit trail in
`notification_delivery_log`. Channel-specific config (Slack webhook
URL, SMTP credentials, PagerDuty integration key) is stored encrypted:
the sensitive bits are themselves Tamma secrets via the Story 1.5-16
`ISecretStore`, and the channel config table stores only the secret
reference, not plaintext.

## User Story

As a **Tamma platform administrator**,
I want **to configure one or more notification channels per tenant and have every orchestrator alert delivered to all of them with retries and a visible delivery log**,
so that **I can trust that the alerting subsystem will wake the right person via the right medium without me having to build a separate monitoring stack around Postgres polling.**

### AC1: `notification_channels` schema migration

- [ ] A migration file at
      `database/migrations/026_notification_channels.sql` creates the
      `notification_channels` table:
  ```sql
  CREATE TABLE IF NOT EXISTS notification_channels (
    id                    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id             UUID NOT NULL,
    name                  TEXT NOT NULL,
    channel_type          TEXT NOT NULL CHECK (channel_type IN ('slack','email','pagerduty','webhook')),
    enabled               BOOLEAN NOT NULL DEFAULT true,
    config                JSONB NOT NULL,
    credential_secret_id  UUID REFERENCES tamma_vault_secrets(secret_id) ON DELETE RESTRICT,
    severity_filter       TEXT[] NOT NULL DEFAULT ARRAY['low','medium','high','critical'],
    created_at            TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at            TIMESTAMPTZ NOT NULL DEFAULT now(),
    created_by            TEXT NOT NULL,
    UNIQUE (tenant_id, name)
  );
  CREATE INDEX IF NOT EXISTS idx_notification_channels_tenant
    ON notification_channels (tenant_id, enabled);
  ```
- [ ] Row-level security enabled matching Story 17-2 pattern:
      `SELECT / UPDATE / DELETE` restricted to
      `tenant_id = current_setting('app.current_tenant_id')::uuid`.
- [ ] `ON DELETE RESTRICT` on `credential_secret_id` — a channel with
      an attached credential secret cannot be orphaned by revoking the
      secret without first detaching it from the channel. This prevents
      silent channel failure.
- [ ] `config` is JSONB; its shape is channel-specific (Slack config
      differs from PagerDuty config). Schema validation happens at the
      channel handler level on create/update.
- [ ] `severity_filter` lets operators route (for example) only
      `critical` alerts to PagerDuty but all alerts to Slack. Default
      is "all severities."
- [ ] Second table in the same migration:
  ```sql
  CREATE TABLE IF NOT EXISTS notification_delivery_log (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id         UUID NOT NULL,
    channel_id        UUID NOT NULL REFERENCES notification_channels(id) ON DELETE CASCADE,
    alert_id          UUID NOT NULL REFERENCES orchestrator_alerts(id) ON DELETE CASCADE,
    attempt_number    INT NOT NULL,
    status            TEXT NOT NULL CHECK (status IN ('pending','success','failed','abandoned')),
    error_category    TEXT,
    error_message     TEXT,
    duration_ms       INT,
    response_snippet  TEXT,
    attempted_at      TIMESTAMPTZ NOT NULL DEFAULT now()
  );
  CREATE INDEX IF NOT EXISTS idx_delivery_log_alert
    ON notification_delivery_log (alert_id, attempted_at DESC);
  CREATE INDEX IF NOT EXISTS idx_delivery_log_channel
    ON notification_delivery_log (channel_id, attempted_at DESC);
  ```
- [ ] RLS on `notification_delivery_log` tied to the same
      `app.current_tenant_id` setting.
- [ ] Migration is idempotent and ships with a rollback script.

### AC2: `INotificationChannel` interface + dispatcher

- [ ] `packages/api/src/notifications/channel.ts` exports:
  ```typescript
  export interface INotificationChannel {
    readonly type: 'slack' | 'email' | 'pagerduty' | 'webhook';
    validateConfig(config: unknown): ChannelConfig;     // throws on invalid
    send(alert: AlertPayload, config: ChannelConfig, credential: ChannelCredential | null): Promise<DeliveryResult>;
  }

  export interface DeliveryResult {
    success: boolean;
    errorCategory?: 'auth_failed' | 'rate_limited' | 'network' | 'timeout' | 'invalid_payload' | 'remote_error';
    errorMessage?: string;
    durationMs: number;
    responseSnippet?: string;   // first 500 chars of remote response, for operator debugging
  }
  ```
- [ ] `packages/api/src/notifications/dispatcher.ts` exports
      `NotificationDispatcher` with method:
  ```typescript
  interface INotificationDispatcher {
    dispatch(tenantId: string, alert: AlertPayload): Promise<DispatchSummary>;
  }
  ```
  which:
  1. Loads all enabled channels for `tenantId` (sets `SET LOCAL app.current_tenant_id`).
  2. Filters by `severity_filter` against `alert.severity`.
  3. For each matching channel: resolves `credential_secret_id` to
     plaintext (via `ISecretStore` from Story 1.5-16), calls
     `channel.send(alert, config, credential)`, captures result.
  4. Writes one `notification_delivery_log` row per attempt.
  5. On transient failure (`network`, `timeout`, `rate_limited`,
     `remote_error`), enqueues a retry with exponential backoff.
  6. Returns a `DispatchSummary` listing per-channel final status.
- [ ] `dispatch()` is idempotent: called twice with the same
      `(alertId, channelId)` it does NOT produce duplicate successful
      deliveries. An in-flight `(alertId, channelId)` row with
      `status='pending'` blocks a concurrent `dispatch` call from
      re-enqueuing.
- [ ] The dispatcher is `alert_orchestrator`-facing: the Story 1.5-19
      Fastify route for `alert_orchestrator` is extended to call
      `dispatcher.dispatch(tenantId, alert)` after committing the
      `orchestrator_alerts` insert, within the same request handler but
      AFTER the insert commits (so dispatch failure never blocks alert
      durability).
- [ ] Dispatcher unit tests mock each channel and verify fan-out,
      severity filtering, and retry enqueueing.

### AC3: `SlackChannel` implementation

- [ ] `packages/api/src/notifications/channels/slack-channel.ts`
      exports `SlackChannel` implementing `INotificationChannel`.
- [ ] Config schema (zod): `{webhookUrlSecretRef: string}`. The Slack
      incoming-webhook URL is sensitive (it's a bearer capability for
      posting to that channel) and is stored as a Tamma secret. The
      config only references the secret.
- [ ] `send()` builds a Slack block-kit payload with:
  - Header: `[severity] alert.reason — alert.subject`
  - Fields: tenant, workflow id, secret id (if present), timestamp
  - Context: link back to the operator dashboard (Story 1.5-39, once
    that lands) using the configured `app.tamma.dev` base URL
- [ ] POST via `fetch` with `application/json` body, 10s timeout,
      validates 200 response.
- [ ] Error categorisation:
  - HTTP 429 → `rate_limited` (retryable)
  - HTTP 5xx or network errors → `remote_error` / `network` (retryable)
  - HTTP 401/403 → `auth_failed` (not retryable, alerts operator on next admin dashboard load)
  - HTTP 400 with `invalid_payload` response body → `invalid_payload` (not retryable)
- [ ] Unit tests for happy path, 429 retry, malformed URL, timeout.

- [ ] Error categorisation:
  - SMTP 5xx, timeout, network error → retryable
  - SMTP 535 (auth rejected) → `auth_failed`, not retryable
  - Malformed address → `invalid_payload`, not retryable
- [ ] Unit tests use `nodemailer`'s `streamTransport` to capture sent

### AC6: `WebhookChannel` implementation (generic HTTP with HMAC signing)

- [ ] `packages/api/src/notifications/channels/webhook-channel.ts`
      exports `WebhookChannel` implementing `INotificationChannel`.
- [ ] Config schema (zod):
  ```typescript
  {
    url: string;                     // target endpoint
    method: 'POST' | 'PUT';          // default POST
    signingSecretRef: string;        // Tamma secret for HMAC-SHA256 signing
    customHeaders?: Record<string, string>;   // operator can add Authorization etc.
    maxPayloadBytes?: number;        // default 64kb
  }
  ```
- [ ] `send()` POSTs a JSON payload:
  ```json
  {
    "version": 1,
    "alertId": "<uuid>",
    "tenantId": "<uuid>",
    "timestamp": "<iso8601>",
    "severity": "<low|medium|high|critical>",
    "reason": "<reason>",
    "subject": "<subject>",
    "payload": { ... full alert payload ... }
  }
  ```
- [ ] Adds HMAC-SHA256 signature header:
      `X-Tamma-Signature: sha256=<hex>` where the HMAC is over the raw
      body bytes using the resolved signing secret.
- [ ] Also adds `X-Tamma-Timestamp` and `X-Tamma-Alert-Id` headers.
- [ ] Receivers verify by recomputing the HMAC. The docs include a
      reference receiver snippet in Node and Python.
- [ ] Payload size cap: if the alert payload serialises to more than
      `maxPayloadBytes`, the dispatch truncates `custom_details` and
      adds a `_truncated: true` flag. Prevents runaway webhook sends.
- [ ] 15s HTTP timeout (higher than other channels because operators
      may point at slow in-house endpoints).
- [ ] Error categorisation same as Slack.
- [ ] Unit tests: signature computation, payload size cap, HMAC
      verification round-trip, retry on 5xx.

### AC7: Retry envelope with exponential backoff

- [ ] A shared `NotificationRetryPolicy` in
      `packages/api/src/notifications/retry-policy.ts`:
  - Max 5 attempts total.
  - Backoff: 5s, 15s, 45s, 2m, 5m (capped by `max_delay=5m`).
  - Jitter: +/- 20%.
  - Only retryable error categories (`network`, `timeout`,
    `rate_limited`, `remote_error`) are retried; non-retryable
    failures terminate after the first attempt.
  - Total retry budget per attempt: 10 minutes. After that, the
    delivery is marked `abandoned` in `notification_delivery_log`
    and the operator gets a durable record they can query.
- [ ] Retry is driven by a simple background worker that polls
      `notification_delivery_log` for `status='pending'` rows with
      `attempted_at < now() - backoff_window`. For MVP this runs
      inside the API process (no separate worker pod); a TODO comment
      documents moving it to the broker or a dedicated worker if the
      alert volume grows.
- [ ] Retry worker tests use `vi.useFakeTimers()` to fast-forward
      through the backoff schedule without real delays.

### AC9: Taint tracking + plaintext hygiene

- [ ] Plaintext handling in channel `send()` methods:
  - The resolved credential (Slack URL, SMTP password, PagerDuty key,
    HMAC key) is a `Buffer` that is zeroised immediately after the
    outbound request completes.
  - No credential appears in any log line.
  - No credential appears in `notification_delivery_log.response_snippet`.
- [ ] `response_snippet` is capped at 500 chars and scanned against the
      Story 1.5-28 leak detector before being stored. If the detector
      flags it (the upstream echoed our credential back, which some
      misconfigured servers do), the snippet is replaced with
      `[REDACTED: leak detected in response]`.
- [ ] Alert payloads are taint-tracked: `alert_orchestrator` already
      tags its events; the dispatcher inherits that taint. Unit test
      verifies an alert with a tainted field is NOT stringified
      verbatim into the email/Slack body — the taint pipeline replaces
      it with `[redacted]` first.

## Dev Notes

### Requirements Context Summary

**Epic Context**: This story closes the notification-delivery gap left
by Story 1.5-19's deliberately-minimal `alert_orchestrator`
implementation. At the time of 1.5-19 the priority was durable storage
and audit; this story adds the push side. Downstream stories (1.5-31
auto-rotate, 1.5-30 rotation cascade) already emit alerts through the
`alert_orchestrator` tool — they get the new notification channels for
free.

**Technical Context**: The notification subsystem lives in
`packages/api/src/notifications/` alongside the existing admin routes.
It depends on `ISecretStore` from Story 1.5-16 for credential
resolution (Slack webhooks, SMTP passwords, PagerDuty keys, HMAC
signing keys are all stored as Tamma secrets) and on the
`orchestrator_alerts` table from Story 1.5-19 for the alert source.
The retry worker runs in-process in the API for MVP; a comment marks
the migration path to a dedicated worker.

**Integration Points**:
- **Story 1.5-16**: channel credentials stored via `ISecretStore`.
- **Story 1.5-17**: same Postgres instance hosts
  `notification_channels` / `notification_delivery_log` tables.
- **Story 1.5-19**: `alert_orchestrator` Fastify route calls
  `NotificationDispatcher.dispatch()` after committing the alert.
- **Story 1.5-28**: leak detector scrubs `response_snippet` before
  storage.
- **Story 16-7 / 17-2**: admin routes use the shared RBAC gate +
  RLS tenant isolation pattern.
- **Event store**: audit events flow to the DCB stream.

### Key Design Decisions

1. **Fan-out happens after the `orchestrator_alerts` insert commits,
   not inside the same transaction.** If the channel dispatch fails or
   hangs, the alert is still durably stored. Operators can always query
   the table even if every channel is broken. This separation is the
   whole reason Story 1.5-19 shipped the table-first design: it's the
   source of truth, and push notifications are an enhancement layered
   on top.

2. **Channel credentials are Tamma secrets, not config fields.** A
   Slack webhook URL is a bearer capability; leaking it lets anyone
   post to that channel. Storing the URL in `notification_channels.config`
   as plaintext would defeat the whole vault story. Instead, the
   sensitive bit goes into `ISecretStore` with `mode: 'vault_copy'` so
   the dispatcher can retrieve it at delivery time, and the channel
   config only stores the secret reference. Same pattern for SMTP
   passwords, PagerDuty keys, HMAC signing keys.

3. **Retry worker is in-process in the API for MVP.** Alert volume is
   bounded (operators don't get more than a few alerts per hour under
   normal conditions, and under pathological conditions the retry
   budget caps total work at 5 attempts per alert per channel). A
   separate worker pod is overkill and adds deployment complexity.
   If the volume profile changes — e.g. if the LLM starts generating
   many alerts per minute via the polling contract — the retry worker
   can move to the broker or a dedicated pod without changing the
   public API.

4. **Non-retryable failures terminate fast.** Auth failures, invalid
   payloads, and 4xx responses (other than 429) are operator config
   errors. Retrying them wastes the retry budget and delays the
   operator seeing the failure in the delivery log. The dispatcher
   records a `failed` row immediately and moves on.

5. **PagerDuty dedup key is `tamma-<alertId>`.** Retries and workflow
   replays can produce multiple `dispatch()` calls for the same
   `alertId`. PagerDuty dedupes on the routing key so those all
   merge into a single incident rather than paging the operator
   multiple times. The idempotency guard in the dispatcher handles
   the Slack/email side where dedup is not built in.

6. **Webhook payload is versioned at v1.** The outer envelope has
   `version: 1` and all receivers are expected to check it. When a v2
   payload shape is needed (e.g. adding new fields that break old
   receivers), we add a v2 channel type rather than silently breaking
   existing webhooks.

7. **`POST /test` bypasses the retry envelope.** An operator testing
   a channel wants to see the immediate failure, not wait 10 minutes
   for the retry budget to exhaust. The test route calls the channel
   directly and returns the raw `DeliveryResult`.

8. **`severity_filter` is a list, not a minimum threshold.** An
   operator might want PagerDuty for only `critical`, Slack for
   `medium + high + critical`, and email for everything. A list
   expresses this cleanly; a minimum threshold would force the
   operator to create two separate PagerDuty channels to route
   different severities differently.

### Testing Strategy

- **Unit tests** for each channel (Slack, Email, PagerDuty, Webhook)
  using mocked `fetch` / nodemailer / HTTP servers. Cover happy path,
  every error category, retry classification.
- **Dispatcher unit tests** with mocked channels verifying fan-out
  order, severity filtering, idempotency guard, retry enqueueing.
- **Integration tests** against a real Postgres test container for
  the schema migration, the RLS isolation, and the admin CRUD routes.
- **End-to-end test**: boot the API, create a webhook channel
  pointing at a local test HTTP server, call `alert_orchestrator`,
  assert the test server received exactly one signed request with a
  valid HMAC.
- **Retry envelope tests** use `vi.useFakeTimers()` to advance through
  the 5/15/45/120/300 second backoff schedule without real delays.
- **Taint tests** scan every emitted log line and every stored row
  for credential plaintext; assert zero hits.
- **Opt-in integration tests** (env-gated) for SMTP via Mailpit and
  Slack via an operator-provided test webhook URL.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Channel dispatch hangs the API request thread | High | Dispatcher runs fan-out fire-and-forget after the alert row commits; individual channel `send()` calls have per-channel timeouts (10-15s); the alert response returns as soon as the row is committed |
| Credential leak in `notification_delivery_log.response_snippet` | Critical | Leak detector scrubs the snippet before storage; cap at 500 chars; unit test with a known credential in a mocked response asserts `[REDACTED]` replacement |
| Webhook signing key compromised → attacker can forge webhook calls | High | Signing key is a Tamma secret subject to the normal rotation pipeline (Story 1.5-30 cascade can rotate it); receivers are expected to reject payloads older than 5 minutes via the `X-Tamma-Timestamp` header |
| PagerDuty incident spam from retry loops | Medium | Dedup key = `tamma-<alertId>`; PagerDuty deduplicates identical dedup keys within the same incident window; retries within the budget don't create new incidents |
| Retry worker starves the API event loop under load | Medium | Retry worker processes one pending row at a time with a 500ms sleep between pulls; worker can be moved out-of-process later without API contract change |
| Operator configures a channel pointing at localhost and every alert is lost | Low | `POST /test` endpoint lets operators verify at configure time; the delivery log shows failed attempts with exact error for post-hoc debugging |
| Fan-out storm when a single event triggers many workflows (e.g. mass rotation) | Medium | `NotificationDispatcher` honours a per-channel rate limit from config (default 1/sec sustained, 10 burst); overflow rows stay pending and drain on schedule |
| Channel creation allows referencing a secret the caller doesn't own | Critical | `validateConfig` + the admin route explicitly check `tenant_id` match on the referenced secret via RLS; cross-tenant access returns 400 |
| Email channel fans out to many recipients and one bad address fails the whole send | Medium | SMTP `sendMail` returns per-recipient results; dispatcher records a success if any recipient accepted and a partial-failure note in `response_snippet` |
