# Story 1.5-35: Cloud provider rotation handlers — AWS IAM, GCP, Azure

**Epic**: Epic 1.5 — Foundation & Core Infrastructure (extension)
**Category**: MVP-Critical (Security / Cloud Integration)
**Status**: ready-for-dev
**Priority**: High
**Depends on**: Story 1.5-17 (TammaVaultStore), Story 1.5-29 (IRotationHandler framework), Story 1.5-30 (RotationCascadeWorkflow)

## Story

As a **Tamma operator whose downstream systems include AWS IAM access keys, GCP service accounts, Azure Key Vault secrets, and Azure AD application credentials**,
I want **rotation handlers that know how to rotate each of those cloud credential types using the platform's own SDK**,
so that **when Tamma rotates a secret that's deployed to a cloud provider, the new credentials are installed in the provider's own credential store and the old ones are revoked — with two-phase deploys where the platform supports it and clean rollback on failure.**

## Context — Why this story exists

Story 1.5-29 shipped five built-in `IRotationHandler` implementations:
Postgres, MySQL, Redis, GitHub App (experimental), and HTTP webhook. It
explicitly deferred cloud providers to a follow-up story:

> Cloud-specific handlers (AWS IAM, GCP service accounts, Azure Key
> Vault) are deferred to Story 1.5-29.1.

This is that story, renumbered to 1.5-35 to match the current numbering
scheme. It adds four handlers — or five, depending on how you count
Azure — each implementing the same `IRotationHandler` interface and
registered into the same `RotationHandlerRegistry`.

### Which handlers, and why these four

1. **AWS IAM access key** — the highest-impact cloud credential type
   for most Tamma operators. IAM user access keys are widely used by
   CI systems, SDK clients, and legacy service integrations. AWS IAM
   supports two active access keys per user (via `CreateAccessKey` +
   later `DeleteAccessKey`), which gives us a true two-phase rotation
   with an overlap window.

2. **GCP service account key** — the equivalent on GCP. Service account
   keys are JSON blobs created via `projects.serviceAccounts.keys.create`
   and deleted via `projects.serviceAccounts.keys.delete`. GCP permits
   multiple keys per service account, so two-phase rotation works.

3. **Azure Key Vault secret** — updates a secret value in Azure Key
   Vault. Key Vault stores secret history (old versions remain queryable
   by version id), which makes this closer to a "push new value"
   operation than a keypair rotation. Rollback means pointing at the
   previous version.

4. **Azure AD application client secret** — rotates the client secret
   on an Azure AD app registration. Uses the Microsoft Graph API. Unlike
   IAM keys, Azure AD supports up to 2 active client secrets on an app,
   so two-phase rotation is possible.

All four handlers follow Story 1.5-29's pattern: live in the
`secret-broker` process, receive decrypted plaintext, use the
`adminPasswordSecretId` recursive-but-bounded pattern for their own auth,
never return plaintext in results, and zeroise buffers in `finally`.

## User Story

As a **Tamma platform engineer managing a production deployment whose services authenticate to AWS, GCP, and Azure**,
I want **`RotationCascadeWorkflow` to natively know how to rotate IAM access keys, GCP service account keys, and Azure secrets when those cloud credentials are downstream targets of a Tamma-managed secret rotation**,
so that **I can run end-to-end credential rotation across my cloud providers without writing custom handlers or operator glue code.**

## Acceptance Criteria

### AC1: `AwsIamAccessKeyHandler`

- [ ] `AwsIamAccessKeyHandler` at `packages/secret-broker/src/rotation-handlers/aws-iam-access-key-handler.ts` implements `IRotationHandler` with `type: 'aws_iam_access_key'`.
- [ ] Config schema:
  ```typescript
  interface AwsIamAccessKeyHandlerConfig {
    region: string;                           // IAM is global but the client needs a region
    iamUserName: string;                      // the IAM user whose keys we rotate
    adminCredentialSecretId: string;          // Tamma secret containing the admin creds used to call IAM
    propagationDelayMs?: number;              // default 60_000 — time to wait between create and delete
    maxActiveKeysAtRest?: 1 | 2;              // default 1; if 2, we leave the new key active and don't delete the old
    endpoint?: string;                        // for LocalStack testing
  }
  ```
- [ ] `rotate()` implementation:
  1. Resolves `adminCredentialSecretId` via the broker vault to an
     `{ accessKeyId, secretAccessKey, sessionToken? }` tuple. The
     plaintext format for AWS admin creds is a JSON blob; the secret's
     `type` is `arbitrary` and the broker decrypts and `JSON.parse`s it.
  2. Constructs `IAMClient` from `@aws-sdk/client-iam` with the resolved
     admin creds and the configured region/endpoint.
  3. Calls `ListAccessKeys(UserName)` to check current state:
     - If 0 active keys: CreateAccessKey → return the new pair.
     - If 1 active key: CreateAccessKey (now 2 active) → wait
       `propagationDelayMs` → UpdateAccessKey to `Inactive` on the old
       key → DeleteAccessKey on the old key → return the new pair.
     - If 2 active keys: return `errorCategory: 'config_error'` with
       message "user already has 2 active keys; manual cleanup
       required". AWS caps at 2 keys per user; a rotation that assumed
       0 or 1 active keys cannot proceed.
  4. On success: returns `{ success: true, sideEffects: { new_access_key_id: '<id>', old_access_key_id: '<id>' } }`. NEVER returns the secret access key in `sideEffects`.
  5. The new access key pair IS the rotated value — `newValue` passed to `rotate()` is ignored in the sense that the handler OVERWRITES what the caller planned to rotate to with the AWS-generated pair. This is the **inverse rotation pattern**: for cloud-managed credentials, the platform generates the value, and Tamma stores what the platform generated. The handler returns the generated pair via a special `generatedValue` field in `RotationHandlerResult` (see AC6).
- [ ] `rollback()` implementation:
  1. Parses `sideEffects.new_access_key_id` from the forward-pass result.
  2. Calls `DeleteAccessKey` for that key.
  3. If the old key was deleted in the forward pass, rollback cannot recreate it (AWS does not retain deleted key material). Returns `{ success: false, errorCategory: 'config_error', errorMessage: 'cannot recreate deleted access key; old credentials are gone' }`.
  4. If the old key was merely `Inactive`, calls `UpdateAccessKey` back to `Active`.
- [ ] **Minimum IAM permissions** documented in the handler's top-of-file comment:
  ```
  iam:ListAccessKeys
  iam:CreateAccessKey
  iam:UpdateAccessKey
  iam:DeleteAccessKey
  ```
  Resource: `arn:aws:iam::<account>:user/<iamUserName>`. The handler's
  admin credential MUST be scoped to these permissions and this
  resource only — the README documents a sample IAM policy.
- [ ] Unit tests mock `@aws-sdk/client-iam` via `aws-sdk-client-mock` and cover: happy path (1→2→1 active keys), 0-key happy path, 2-key refusal, propagation delay respected, admin creds zeroised on success and failure, rollback happy path, rollback after old-key-deleted.
- [ ] Integration test runs against **LocalStack** via `testcontainers`:
  1. Spin up LocalStack with `iam` service.
  2. Create an IAM user with one access key.
  3. Run the handler.
  4. Assert the new key works (call `GetCallerIdentity` with it).
  5. Assert the old key no longer works.
  6. Run rollback and assert the new key no longer works.

### AC2: `GcpServiceAccountKeyHandler`

- [ ] `GcpServiceAccountKeyHandler` at `packages/secret-broker/src/rotation-handlers/gcp-service-account-key-handler.ts` implements `IRotationHandler` with `type: 'gcp_service_account_key'`.
- [ ] Config schema:
  ```typescript
  interface GcpServiceAccountKeyHandlerConfig {
    projectId: string;
    serviceAccountEmail: string;
    adminCredentialSecretId: string;           // GCP admin creds (a service account key itself, recursive pattern)
    propagationDelayMs?: number;
    keyType?: 'USER_MANAGED' | 'SYSTEM_MANAGED';   // default USER_MANAGED
    privateKeyType?: 'TYPE_GOOGLE_CREDENTIALS_FILE' | 'TYPE_X509_PEM_FILE';  // default JSON creds file
  }
  ```
- [ ] Uses `@google-cloud/iam` (or `googleapis` as a fallback — both packages wrap the REST API; the story picks `@google-cloud/iam-credentials` + the direct IAM service account key API via `googleapis.iam('v1')`, depending on library maturity at implementation time).
- [ ] **SDK library choice is a research-at-implementation-time decision**. The story's Dev Notes cover the selection criteria; the implementer confirms via `WebFetch` the current recommended library for service account key rotation at the time of implementation.
- [ ] `rotate()` flow:
  1. Resolves `adminCredentialSecretId` to a GCP service account key JSON.
  2. Constructs an IAM client authenticated with that key.
  3. Lists existing keys via `projects.serviceAccounts.keys.list`. GCP permits up to 10 user-managed keys per service account (hard cap), so the two-phase path is usually safe.
  4. Creates a new key via `projects.serviceAccounts.keys.create` with the configured `privateKeyType`. The response includes a base64-encoded `privateKeyData` field.
  5. Waits `propagationDelayMs`.
  6. Deletes the old key (the key passed in as `oldValue` — matched by key id parsed from the JSON blob's `private_key_id` field) via `projects.serviceAccounts.keys.delete`.
  7. Returns the new key JSON via `generatedValue` in `RotationHandlerResult`.
- [ ] `rollback()`: same caveat as AWS IAM — GCP does not retain deleted private key material. If the old key was deleted, rollback cannot recreate it. The handler deletes the new key and returns a `config_error` explaining the old credentials are gone.
- [ ] **Minimum GCP permissions** documented:
  ```
  iam.serviceAccountKeys.create
  iam.serviceAccountKeys.delete
  iam.serviceAccountKeys.list
  ```
  Resource: `projects/<projectId>/serviceAccounts/<serviceAccountEmail>`.
  Operators typically grant this via `roles/iam.serviceAccountKeyAdmin`
  scoped to the target service account.
- [ ] Unit tests mock the GCP client and cover: happy path, key-cap-exceeded (10 keys), admin creds zeroised, private key data redacted in logs, old key match by `private_key_id`.
- [ ] Integration test: GCP does not have a LocalStack equivalent for
  IAM. The integration test is SKIPPED in CI unless
  `GCP_INTEGRATION_TEST_PROJECT` env var is set, in which case it runs
  against a real test project. README documents the setup.

### AC3: `AzureKeyVaultSecretHandler`

- [ ] `AzureKeyVaultSecretHandler` at `packages/secret-broker/src/rotation-handlers/azure-keyvault-secret-handler.ts` implements `IRotationHandler` with `type: 'azure_keyvault_secret'`.
- [ ] Config schema:
  ```typescript
  interface AzureKeyVaultSecretHandlerConfig {
    vaultUrl: string;                      // https://<vault-name>.vault.azure.net
    secretName: string;
    adminCredentialSecretId: string;       // Azure service principal creds (tenant, client id, client secret)
    retainOldVersions?: boolean;           // default true — Key Vault keeps version history anyway
    contentType?: string;                  // default 'text/plain'
  }
  ```
- [ ] Uses `@azure/keyvault-secrets` (`SecretClient`) and `@azure/identity` (`ClientSecretCredential`).
- [ ] `rotate()` flow:
  1. Resolves `adminCredentialSecretId` to `{ tenantId, clientId, clientSecret }`.
  2. Constructs `ClientSecretCredential` and `SecretClient(vaultUrl, credential)`.
  3. Calls `setSecret(secretName, newValueString, { contentType })`. Azure Key Vault automatically versions secrets, so this is a pure push — no two-phase needed, no delete required. The old version remains accessible by version id.
  4. Returns `success: true` with `sideEffects: { new_version_id: '<uuid>', old_version_id: '<uuid>' }`.
- [ ] `rollback()`:
  1. Calls `getSecret(secretName, { version: sideEffects.old_version_id })` to verify the old version still exists.
  2. Calls `setSecret(secretName, <oldValue>)` to push a new "latest" pointing at the old bytes. Note: this is a NEW version with the old content, not a rollback to the old version id. Azure Key Vault has no "revert to version X" primitive.
  3. The `oldValue` buffer is re-pushed. Plaintext stays in the broker process.
- [ ] **Minimum Azure permissions** documented:
  ```
  Microsoft.KeyVault/vaults/secrets/setSecret/action
  Microsoft.KeyVault/vaults/secrets/getSecret/action
  ```
  Via the Key Vault access policy or RBAC role `Key Vault Secrets Officer`.
- [ ] Unit tests mock `@azure/keyvault-secrets` and cover: happy path, auth failure (401), forbidden (403), vault not found (404), admin creds zeroised.
- [ ] Integration test: Azure does not offer a local emulator for Key Vault. Test is SKIPPED in CI unless `AZURE_INTEGRATION_TEST_VAULT` is set.

### AC4: `AzureAdClientSecretHandler`

- [ ] `AzureAdClientSecretHandler` at `packages/secret-broker/src/rotation-handlers/azure-ad-client-secret-handler.ts` implements `IRotationHandler` with `type: 'azure_ad_client_secret'`.
- [ ] Config schema:
  ```typescript
  interface AzureAdClientSecretHandlerConfig {
    tenantId: string;
    applicationObjectId: string;            // the app registration's object id (NOT the app id)
    adminCredentialSecretId: string;        // admin SP with Application.ReadWrite.All
    propagationDelayMs?: number;
    secretDisplayName?: string;             // default 'tamma-rotated-<timestamp>'
    validityDays?: number;                  // default 180
  }
  ```
- [ ] Uses `@microsoft/microsoft-graph-client` with a custom auth provider built on `@azure/identity`.
- [ ] `rotate()` flow:
  1. Resolves `adminCredentialSecretId` to `{ tenantId, clientId, clientSecret }` for the admin SP.
  2. Acquires a Graph token.
  3. Calls `POST /applications/{id}/addPassword` with a `passwordCredential` object specifying `displayName`, `endDateTime`. Graph returns the new `secretText` (base64 client secret) ONCE — this is the only time the full secret is available.
  4. Captures the returned `secretText` into a `Buffer`, passes it back via `generatedValue` in the result.
  5. Waits `propagationDelayMs`.
  6. Calls `POST /applications/{id}/removePassword` with the old secret's `keyId` (parsed from the handler's `oldValue` metadata — see AC6 for how old value carries key id).
  7. Zeroises all plaintext buffers.
- [ ] `rollback()`: same problem as AWS/GCP — once a client secret is removed via Graph, the bytes are not retrievable. Rollback calls `removePassword` for the new secret and returns `config_error` explaining the old secret cannot be restored.
- [ ] **Minimum Graph permissions**: `Application.ReadWrite.OwnedBy` or `Application.ReadWrite.All`. Documented in the README with a sample permission grant.
- [ ] Unit tests mock Graph client and cover: happy path, auth failure, app not found, admin creds zeroised, secretText captured and zeroised.
- [ ] Integration test: SKIPPED in CI unless `AZURE_AD_INTEGRATION_TEST_TENANT` and `AZURE_AD_INTEGRATION_TEST_APP` are set.

### AC6: `generatedValue` extension to `RotationHandlerResult`

- [ ] Story 1.5-29's `RotationHandlerResult` is extended with an optional `generatedValue` field:
  ```typescript
  interface RotationHandlerResult {
    success: boolean;
    errorCategory?: ...;
    errorMessage?: string;
    sideEffects?: Record<string, string>;
    // NEW:
    generatedValue?: Buffer;              // set when the platform generated the new value
    generatedValueMetadata?: {            // identifiers for later reference
      keyId?: string;
      version?: string;
      format?: 'aws_access_key_pair_json' | 'gcp_service_account_key_json' | 'azure_client_secret' | 'raw';

  }
  ```
- [ ] When `generatedValue` is set, `RotationCascadeWorkflow` (Story 1.5-30) uses the returned buffer as the authoritative new value and writes it into `TammaVaultStore` via `rotateSecret(..., { actualNewValue: generatedValue })`. This closes the loop: the rotation cascade re-stores the platform-generated credentials back in Tamma's vault.
- [ ] Taint tracking: `generatedValue` is a `Buffer` and is zeroised by the cascade after consumption. A new invariant test asserts `generatedValue` bytes never appear in logs or in the non-`generatedValue` fields of the result.
- [ ] `generatedValue` is incompatible with `rollback` for most platforms — documented explicitly in each handler's source comment. Rollback can revoke the new value but cannot recreate the old one.
- [ ] Story 1.5-30 (`RotationCascadeWorkflow`) gets a small update in this story's scope: handling the `generatedValue` field in the single path where it calls the handler and writes back to the vault. The cascade's other behaviour is unchanged.

## Dev Notes

### Requirements Context Summary

Story 1.5-29 gave us a rotation handler framework with five
on-prem-flavored backends. Real production Tamma deployments rotate
credentials that mostly live in clouds, not just in local databases.
Without these handlers, operators would write custom rotation glue
(either their own `IRotationHandler` implementations, or out-of-band
scripts that Tamma cannot audit). Shipping first-class cloud handlers
means the cascade handles end-to-end rotation natively.

### Key Design Decisions

1. **Handlers live in the broker process, same as Story 1.5-29**. The
   cloud SDKs read plaintext credentials and make authenticated API
   calls; those calls need to happen wherever the plaintext lives. The
   broker already has plaintext in memory during rotation, so the
   handlers run there. Isolating them to a separate "cloud worker"
   process would require a plaintext-over-wire protocol, which we
   explicitly avoid.

2. **`generatedValue` is the inverse rotation pattern**. For Postgres
   and MySQL, Tamma generates the new value and tells the downstream
   "here's your new password". For AWS IAM, GCP, and Azure AD, the
   platform generates the value and gives it to us. The handler
   returns the generated bytes via `generatedValue`, and the cascade
   writes them back into Tamma's vault. This is a one-line change in
   the cascade and a new field in the result type. Handlers that use
   Tamma-generated values (Postgres, MySQL, Redis, HTTP webhook) don't
   set `generatedValue`.

3. **Rollback is lossy for three of four cloud handlers**. AWS IAM,
   GCP service account keys, and Azure AD client secrets all generate
   credential material that the platform does NOT retain after
   deletion. Once you've deleted the old AWS secret access key, the
   bytes are gone — no API to recover them. Rollback can delete the
   new credentials (revoking the rotation) but cannot restore the old
   ones. Azure Key Vault is different: it retains version history, so
   rollback can re-push the old bytes as a new version. Each handler's
   `rollback` docstring documents this explicitly.

4. **Recursive admin creds via `adminCredentialSecretId`**. Same
   pattern Story 1.5-29 establishes: the admin credentials needed to
   authenticate to the cloud provider ARE themselves Tamma-managed
   secrets. For AWS, the admin is another IAM user (or an IAM role
   assumed via STS — future extension). For GCP, the admin is another
   service account key. For Azure, the admin is a service principal
   with `Application.ReadWrite.All` Graph permission. Tamma resolves
   the admin creds from its own vault at handler-invocation time,
   uses them, and zeroises. Config validation rejects
   `adminCredentialSecretId` pointing at `platform_only` secrets and
   at the same secret being rotated (no infinite recursion).

5. **SDK selection differs per provider**. AWS: `@aws-sdk/client-iam`
   (v3, modular). GCP: `@google-cloud/iam-credentials` vs `googleapis`
   — decided at implementation time via `WebFetch`. Azure Key Vault:
   `@azure/keyvault-secrets` + `@azure/identity`. Azure AD:
   `@microsoft/microsoft-graph-client` + custom auth provider. No
   attempt to abstract "a cloud SDK" across providers — the shapes are
   too different and the abstraction would leak.

6. **LocalStack is the only realistic local integration for AWS**. GCP
   and Azure do not offer local emulators for IAM / KMS / Graph that
   are good enough to test credential flows. AWS IAM handler gets a
   full CI integration test via LocalStack. GCP and Azure handlers
   ship with unit tests only, plus opt-in integration tests against
   real projects gated behind env vars. README documents how to run
   those manually.

7. **`enable_cloud: true` by default, opt-out via config**. Most Tamma
   deployments touch at least one cloud provider. Defaulting to
   registering all four handlers matches the principle that secure
   behaviour is the default. Operators who don't use cloud providers
   can flip the flag to save boot time and avoid importing the SDKs.
   When disabled, the cloud SDK packages are dynamic-imported on
   demand, so disabling the feature actually skips loading them.

8. **AWS two-phase rotation uses propagation delay, not a second
   active key forever**. The `maxActiveKeysAtRest: 1` default means
   after rotation we're back down to one key. `maxActiveKeysAtRest: 2`
   (opt-in) leaves both keys active indefinitely — useful if the
   operator wants a blue/green setup where the old key is retained
   for emergency rollback. The propagation delay (default 60 seconds)
   gives consumers time to pick up the new credentials before the old
   ones become invalid.

### Testing Strategy

- **Unit tests**: each handler with mocked SDKs. Cover happy path,
  each error category, admin cred zeroisation, parameter binding,
  buffer zeroisation after return.
- **AWS IAM integration**: LocalStack + `testcontainers`, real
  rotation against a real IAM user, assert old key stops working and
  new key works, assert rollback revokes.
- **GCP / Azure integration**: opt-in tests gated on env vars,
  documented in README, not run in CI.
- **Taint tracking**: per-handler and cross-handler property-based
  tests.
- **Boot integration**: `bootBroker()` test asserts all nine handlers
  register successfully and dynamic-import only happens when
  `enable_cloud: true`.
- **`generatedValue` integration**: test that `RotationCascadeWorkflow`
  writes the generated bytes back to the vault correctly for each
  handler.

### Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| AWS key deletion before consumers have picked up the new key | High | Default `propagationDelayMs: 60_000` tunable per handler config; operator docs recommend monitoring for 401s post-rotation |
| 2-active-key cap on AWS hit by operators who haven't cleaned up | Medium | Handler checks key count first and fails fast with clear error; README documents the `ListAccessKeys` + manual cleanup path |
| GCP / Azure deleted-credential rollback impossibility | High | Documented in handler source + README + ADR; rollback returns explicit error category; the cascade treats this as "rollback unsupported in failure mode" and escalates to the operator |
| Admin cred JSON parse failure allowing handler to proceed with partial creds | Critical | `parseAs` helper asserts all required fields present; unit test with missing fields |
| Plaintext generated value leaked via `sideEffects` field | Critical | Invariant test asserts `generatedValue` bytes never appear in `sideEffects`; code review rule: `sideEffects` fields are metadata only |
| GCP service account key rotation creating >10 keys and hitting cap | High | Handler lists keys first, fails fast if >= 10 exist, points operator at manual cleanup |
| Azure AD app with existing 2 client secrets blocking rotation | Medium | Graph `addPassword` fails with explicit error; handler maps to `config_error` with message "app already has 2 secrets, remove one manually" |
| Graph API rate limiting during bulk rotations | Medium | Handler retries once on 429 with Retry-After respect; cascade handles repeated 429 as `connection_failed` after retry cap |
| Wrong SDK version breaking signature compatibility | Medium | Versions pinned in `package.json`; integration test catches breakage |
| LocalStack IAM fidelity diverging from real AWS IAM | Medium | Integration test covers the flow LocalStack supports; known divergences (e.g. some edge cases around key activation timing) documented in `.dev/findings/` and covered by the opt-in real-AWS test |
| Azure Key Vault rate limits on bulk secret pushes | Low | Single-secret rotation is far below Key Vault limits; documented as non-issue |
