## Story

As a **Tamma platform engineer wiring LLM agents to the secret broker**,
I want **a dedicated MCP server that exposes every secret-management operation as an MCP tool
with strictly-typed schemas, authenticated against both the broker and the LLM session, and
routed through `LlmWorkflowLaunchRegistry` for duplicate-goal guarding**,
so that **LLM agents can create, rotate, verify, probe, revoke, list, update, transfer, merge,
deploy, mirror, check, and alert on secrets through a single curated tool catalog — without
any plaintext ever crossing the LLM's awareness boundary, without any `exec_shell` or raw SQL
leaking through the same MCP connection, and with every operation flowing through a durable
workflow that can be replayed and audited.**

## Overview

Stories 1.5-18 and 1.5-19 both explicitly deferred MCP wiring to Epic 12. Epic 12 Story 12-1
(`IToolExecutor` interface and registry) defined the *mechanism* for LLM-callable tools, but
no Epic 12 story covers secret-management specifically. This story closes the gap with a
dedicated MCP server package — `packages/mcp-servers/secret-management/` — that exposes every
user-facing secret-broker operation as an MCP tool.

The design follows three principles from Story 1.5-16's Decision 10 (curated tool catalog):

1. **Only secret-management tools exposed on this server.** No `exec_shell`, no raw SQL, no
   file I/O. If the LLM needs any of those, it must connect to a different MCP server. This
   is enforced by the server code itself, not by configuration — the tool list is hard-coded.

2. **Every tool goes through a workflow, not a direct broker call.** The MCP server does not
   call `TammaVaultStore` directly; it invokes the Elsa workflow from Story 1.5-19 via an
   HTTP broker endpoint. This preserves durability, replay, audit, and duplicate-goal
   guarding through `LlmWorkflowLaunchRegistry`.

3. **Two-layer authentication.** The MCP server authenticates to the broker using a
   long-lived `TAMMA_BROKER_API_KEY` (rotatable via Story 1.5-29). The LLM's connection to
   the MCP server is authenticated per-session using a short-lived orchestrator session token
   (from Story 11.3's session model, or Story 12-1's equivalent). Both layers must succeed.

A new `packages/mcp-servers/secret-management/` package hosts the server. It starts as part of
the Tamma orchestrator process (in self-hosted mode) or as a sidecar container (in SaaS mode).
On LLM connection, it delivers the Story 1.5-16 system-prompt directive — "you have access to
secret-management tools; you must never attempt to read a plaintext secret" — as the MCP
server's `instructions` field.

## Acceptance Criteria

### AC1: New package `packages/mcp-servers/secret-management/` exists

- Package scaffolded with `package.json`, `tsconfig.json`, `vitest.config.ts`
- Exports a `SecretManagementMcpServer` class with `start()` / `stop()` lifecycle
- Built on the official MCP TypeScript SDK (`@modelcontextprotocol/sdk`)
- Exported via workspace resolution (`@tamma/mcp-server-secret-management`)

### AC2: Twelve MCP tools exposed

The server exposes exactly these twelve tools — no more, no less. The tool list is hard-coded
in the server source and cannot be extended at runtime.

1. **`create_secret`** — wraps `CreateSecretWorkflow` (Story 1.5-19). Inputs match
   `CreateSecretInput` from Story 1.5-16. Output: `{ workflowId, secretId, commitment, fingerprint }`.
2. **`rotate_secret`** — wraps `RotateSecretWorkflow` (1.5-29). Inputs: `{ secretId, reason }`.
   Output: `{ workflowId, newCommitment, newFingerprint, rotationId }`.
3. **`verify_secret`** — wraps `VerifySecretActivity` via a short verification workflow.
   Inputs: `{ secretId, expectedCommitment }`. Output: `{ match, verificationLevel, details }`.
4. **`probe_secret`** — wraps `ProbeSecretWorkflow` (1.5-27). Inputs:
   `{ secretId, probeType, probeConfig, timeoutMs? }`. Output:
   `{ success, errorCategory?, errorMessage?, durationMs }` (redacted).
5. **`revoke_secret`** — wraps `RevokeSecretWorkflow`. Inputs: `{ secretId, reason }`.
   Output: `{ workflowId, revokedAt }`.
6. **`list_secrets`** — read-only activity (no workflow — idempotent query). Inputs:
   `{ scope?, tags?, limit?, cursor? }`. Output: `{ secrets: SecretMetadata[], nextCursor? }`
   — metadata only, never values.
7. **`get_secret_metadata`** — wraps `GetSecretMetadataActivity`. Inputs: `{ secretId }`.
   Output: `SecretMetadata`.
8. **`find_secrets_by_fingerprint`** — Inputs: `{ fingerprint }`. Output:
   `{ matches: SecretMetadata[] }`.
9. **`deploy_secret_to`** — wraps `DeploySecretWorkflow`. Inputs:
   `{ secretId, deployTarget }`. Output: `{ workflowId, deployedAt }`.
10. **`mirror_secret_to`** — wraps `MirrorSecretWorkflow`. Inputs:
    `{ secretId, mirrorScope }`. Output: `{ workflowId, mirroredAt }`.
11. **`check_workflow`** — read query against the Elsa workflow state store. Inputs:
    `{ workflowId }`. Output: `{ state, currentStep?, error?, startedAt, updatedAt }`. The
    polling primitive LLMs use to wait for workflow completion.
12. **`alert_orchestrator`** — emits an operator alert via the 1.5-30 alert bus. Inputs:
    `{ severity, message, context? }`. Output: `{ alertId, emittedAt }`. Used by LLMs to
    escalate stuck workflows.

(Note: the three metadata-CRUD operations from Story 1.5-44 — `update_secret_metadata`,
`transfer_secret`, `merge_secrets` — are also exposed as MCP tools. That brings the total tool
count on this server to 15. AC2 above describes the core 12 required by this story; AC3
extends the list with the three 1.5-44 tools, which are wired here but whose underlying
workflows are owned by 1.5-44.)

### AC3: Metadata CRUD tools from Story 1.5-44

- `update_secret_metadata`, `transfer_secret`, `merge_secrets` are registered on the same
  MCP server alongside the 12 core tools
- Their schemas are imported from the `@tamma/shared/secret-store` types added by Story
  1.5-44
- Their workflow launches go through `LlmWorkflowLaunchRegistry` identically to every
  other tool

### AC4: Tool schemas use JSON Schema matching the broker's TypeScript types

- Every tool's input schema is a `JSONSchema7` generated from the TypeScript input type
  (via `typescript-json-schema` at build time, committed to the repo so runtime schema
  drift is impossible)
- Every tool's output schema is likewise generated and committed
- A build-time check asserts the generated schemas match the committed ones; any drift
  fails CI

### AC5: Broker HTTP client

- A `HttpBrokerClient` class encapsulates all communication with the secret broker HTTP
  endpoints (reusing the pattern from Story 1.5-18's Elsa-side activities)
- Authenticates with `TAMMA_BROKER_API_KEY` (Bearer token)
- Timeout defaults: 30s for workflow-starting calls, 10s for reads
- Retries: 3 attempts with exponential backoff for transient failures
  (`network_error` / 5xx), zero retries for 4xx
- All HTTP errors mapped to MCP error responses with stable error codes

### AC6: Per-session LLM authentication

- The MCP server accepts connections only with a valid orchestrator session token in the
  MCP connection's `initialize` request
- Session tokens are issued by the orchestrator when an agent is started and are validated
  via a call to `/internal/v1/sessions/validate` on the orchestrator API
- Invalid token → MCP `initialize` returns `AuthenticationError` and the connection is
  closed
- Each session is scoped to one tenant and one user; all downstream tool calls are
  decorated with those identity fields before reaching the broker

### AC7: System prompt delivery

- On MCP `initialize`, the server's `instructions` field contains the Story 1.5-16 system
  prompt text: the LLM is told that every secret operation is mediated by workflows, that
  plaintext is never returned, that duplicate-goal workflows will be blocked, and that it
  should poll with `check_workflow` rather than loop
- The exact prompt text is loaded from `packages/shared/src/prompts/secret-management-system-prompt.txt`
  (a new file committed in this story)
- A test asserts the prompt contains all five required directives

### AC8: Duplicate-goal guarding via `LlmWorkflowLaunchRegistry`

- Every tool that starts a workflow goes through the registry from Story 1.5-19
- The registry's `tryLaunch(goalKey, startFn)` method is called with a goal key derived
  from `(tenantId, userId, tool name, canonical input hash)` — the canonical hash
  excludes any fields that shouldn't block duplicate detection (description, tags)
- If the registry refuses the launch (duplicate already in flight), the tool returns
  `{ duplicateOf: workflowId, message: '...' }` and emits
  `SECRET.WORKFLOW.BLOCKED_DUPLICATE`
- Integration test: two back-to-back `create_secret` calls with identical canonical input
  result in exactly one workflow start

### AC9: Tool catalog curation is enforced structurally

- The MCP server's tool registration code is a literal array of 15 entries (12 from AC2 +
  3 from AC3), not a registry or plugin-loaded list
- There is no API to add tools at runtime
- A test asserts the server advertises exactly 15 tools and no more

### AC10: Full replay safety

- Every tool call flows through a durable workflow (except `list_secrets`,
  `get_secret_metadata`, `find_secrets_by_fingerprint`, `check_workflow` — which are
  read-only and explicitly non-durable)
- Read-only tools are flagged with `readOnly: true` in their tool metadata
- Write tools cannot be called with `dryRun: true` — dry-run is handled at the workflow
  level, not the tool level

### AC11: Taint tracking

- A taint-tracking test per tool: inject a sentinel plaintext into the underlying workflow
  / broker response, call the tool through the MCP server, assert the sentinel never
  appears in the MCP tool response, the MCP server logs, the broker HTTP client logs, or
  the session token metadata
- The same sentinel is injected into each tool's error path and the assertion repeats

### AC12: Rate limiting for LLM-driven tool calls

- A per-session rate limit on tool calls: default 60/min across all tools on this server,
  with a 10/min sub-limit on the expensive tools (`create_secret`, `rotate_secret`,
  `probe_secret`)
- Exceeding either limit returns an MCP `RateLimitExceededError` — the LLM is expected to
  back off and retry
- The rate limiter is per (tenantId, userId, sessionId)

### AC13: Integration with Epic 12

- The MCP server is consumed by the Epic 12 tool-loop infrastructure from Story 12-1 via
  the standard MCP protocol
- The `ShellExecuteTool` and `FileReadTool` etc. from 12-1 are NOT exposed by this server
  — they come from a different MCP server connection
- A documented integration test shows the orchestrator connecting to both servers
  simultaneously and the LLM calling tools from each without confusion

### AC14: Observability

- Every tool call emits a structured log line with `{ tool, tenantId, userId, sessionId,
  workflowId?, durationMs, success }`
- Every tool call emits a Prometheus counter `tamma_mcp_secret_tool_calls_total{tool, outcome}`
- p95 tool latency is captured in `tamma_mcp_secret_tool_duration_seconds{tool}`
- An audit event `MCP.SECRET_TOOL.INVOKED` is emitted per tool call, with tags
  `{ tool, tenantId, userId, sessionId }` and data `{ durationMs, outcome }`

## Dev Notes

### Requirements Context Summary

**Epic Context:** The broker's activities (1.5-18) and workflows (1.5-19) are the durable
primitives; the MCP server is the surface LLMs actually use them through. Without it, every
LLM agent would need custom client code for every secret operation. The deferred item from
Stories 1.5-18 and 1.5-19 was "MCP wiring — responsibility of Epic 12." Epic 12 Story 12-1
built the generic tool-executor interface, but has no secret-management-specific story —
that gap is what this story closes.

**Technical Context:** The crucial design point is that every tool invocation is a thin
wrapper around a durable workflow. The MCP server does not perform secret operations — it
starts a workflow and returns a workflow ID for polling via `check_workflow`. This preserves
durability, replay, audit, duplicate-goal guarding, and no-plaintext-exposure.

**Integration Points:**
- **1.5-16** — system prompt + tool schemas match `ISecretStore` signatures
- **1.5-17** — broker endpoints implemented by `TammaVaultStore`
- **1.5-18 / 1.5-19** — activities + workflows wrapped here; `HttpBrokerClient` pattern
  shared; `LlmWorkflowLaunchRegistry` consulted on every write tool
- **1.5-27** — `probe_secret` wraps `ProbeSecretWorkflow`
- **1.5-29 / 1.5-30 / 1.5-31** — rotation, cascade, and auto-rotate reachable from here
- **1.5-42** — post-rotation health checks run automatically after `rotate_secret`
- **1.5-44** — three metadata-CRUD tools
- **Epic 12 Story 12-1** — this MCP server is one of many external servers 12-1 connects to

### Implementation Guidance

**Key Design Decisions:**

1. **Tool catalog is literal and hard-coded.** The registration is a fixed array, not a
   dynamic registry. Adding a tool requires editing this file, passing review, and deploying.
   A mutable catalog would break the "curated surface" guarantee.

2. **Every write tool is a workflow, every read tool is an activity.** Reads are idempotent
   and fast — no durability needed. Writes go through workflows for replay + audit.

3. **Duplicate-goal guarding is mandatory for workflow-starting tools.** An LLM that loops on
   `create_secret` while waiting for the first call would flood the system;
   `LlmWorkflowLaunchRegistry` returns "already in flight" and the LLM polls with
   `check_workflow`.

4. **System prompt via MCP `initialize.instructions`, not tool docs.** The protocol has a
   field for exactly this; every mainstream client respects it. Tool-description prompts
   fragment.

5. **Two-layer auth: broker-level + session-level.** `TAMMA_BROKER_API_KEY` is a capability
   grant ("this MCP server may call the broker"); the session token is an identity grant
   ("this session belongs to user X in tenant Y"). Both must succeed.

6. **Rate limiting at the MCP server, not the broker.** The broker has per-secret probe
   limits (1.5-27) but no per-session limit; per-session belongs where LLM traffic
   converges. 60/min default catches runaway loops without blocking legitimate workflows.

7. **No `exec_shell`, no raw SQL, no filesystem tools here.** Mixing tool families on one
   server breaks curation — an LLM asking for a secret could accidentally invoke
   `exec_shell`. Dedicated servers per capability surface are safer.

**Technical Specifications:**

- **Directory structure:** `packages/mcp-servers/secret-management/src/` contains
  `server.ts` (the `SecretManagementMcpServer` class), `tools/` (one file per tool — 15
  total, three sourced from Story 1.5-44), `broker-client.ts` (`HttpBrokerClient`),
  `session-auth.ts` (session token validation), `rate-limiter.ts` (per-session token
  bucket), `schemas/*.json` (generated JSON schemas, committed). `test/` colocates
  `*.test.ts` files per module.

- **Environment variables:**
  - `TAMMA_BROKER_API_KEY` — required, broker-level auth bearer
  - `TAMMA_BROKER_BASE_URL` — required, broker HTTP endpoint (default
    `http://localhost:4001`)
  - `TAMMA_ORCHESTRATOR_BASE_URL` — required, for session validation
  - `TAMMA_MCP_SECRET_RATE_LIMIT_GLOBAL` — optional, default 60 (per minute)
  - `TAMMA_MCP_SECRET_RATE_LIMIT_EXPENSIVE` — optional, default 10

- **Error code mapping:**
  ```typescript
  export const MCP_SECRET_ERROR_CODES = {
    MCP_SESSION_INVALID: 'MCP_SESSION_INVALID',
    MCP_BROKER_UNREACHABLE: 'MCP_BROKER_UNREACHABLE',
    MCP_WORKFLOW_LAUNCH_BLOCKED_DUPLICATE: 'MCP_WORKFLOW_LAUNCH_BLOCKED_DUPLICATE',
    MCP_RATE_LIMIT_EXCEEDED: 'MCP_RATE_LIMIT_EXCEEDED',
    MCP_SCHEMA_VALIDATION_FAILED: 'MCP_SCHEMA_VALIDATION_FAILED',
    MCP_TOOL_NOT_FOUND: 'MCP_TOOL_NOT_FOUND',

  ```

### Risks and Mitigations

| Risk | Severity | Mitigation |
| ---- | -------- | ---------- |
| LLM expects `exec_shell` on this server and hits a tool-not-found loop | Medium | System prompt enumerates the 15 tools; `MCP_TOOL_NOT_FOUND` error returns the available list |
| Compromised broker API key grants full broker access | **Critical** | `TAMMA_BROKER_API_KEY` rotated by 1.5-29; read from env, never logged, never returned in errors |
| Forged session token → cross-tenant access | **Critical** | Session validated against orchestrator on every `initialize`; tokens short-lived and opaque; mandatory session-auth test suite |
| Duplicate-goal false positive blocks legitimate retry | Medium | Goal key excludes timestamp + reason; `check_workflow` is the polling escape hatch; goal-key derivation documented in runbook |
| Rate limit too tight for bulk operations | Medium | Expensive-tool sub-limit is the tight budget; reads generous; bulk work runs as scheduled workflows, not LLM loops |
| Schema drift between TS types and committed JSON | Medium | Build-time drift check fails CI; committed schemas make semantic changes reviewable |
| MCP protocol version mismatch | Low | Pinned SDK version; supported client versions in README |
| Plaintext leak via tool response | **Critical** | Every response flows through broker's `sanitizeProbeResult` / `redactSensitiveKeys`; taint-tracking test per tool |
| `alert_orchestrator` spam abuse | Medium | Rate-limited as expensive tool (10/min); alert-bus sink from 1.5-30 deduplicates |

## Logging Requirements

Infrastructure and deployment components MUST use structured logging via pino/ILogger
(never `console.log` in production code).

- **INFO**: MCP server started, session authenticated (`sessionId`, `tenantId`, `userId`),
  tool invocation started/completed (`tool`, `outcome`, `durationMs`), workflow launched
  (`workflowId`), duplicate blocked (`existingWorkflowId`)
- **DEBUG**: Tool schema validated, broker client retry (`attempt`), rate-limit bucket
  consumed, system prompt delivered, session token validated
- **WARN**: Session auth failed, rate limit exceeded (`bucket`), schema validation rejected
  input, tool not found, broker HTTP 5xx after all retries
- **ERROR**: MCP server init failed, broker client config invalid (`TAMMA_BROKER_API_KEY`
  missing), session-validation endpoint unreachable, workflow launch endpoint returned
  unexpected error shape, Prometheus metric registration failed
- **Structured context**: Always include `{ tool, tenantId, userId, sessionId, workflowId? }`.
  NEVER log tool input contents (tags, descriptions, probe configs may echo sensitive
  data), broker API keys, session tokens, or workflow outputs beyond
  `{ workflowId, state, durationMs }`. Tool responses are redacted upstream; log lines
  reference only structural fields.
- **Credential safety**: The MCP server never handles plaintext; log lines reference
  identifiers only. Session tokens are `[REDACTED]` in any diagnostic output.
  `TAMMA_BROKER_API_KEY` is loaded once at startup and never reaches log formatters — an
  explicit test asserts `JSON.stringify(config)` does not contain the key.
