## Story

As a **Tamma operator or tenant owner**,
I want Tamma to detect secret leaks in two channels — LLM tool output before it reaches the model, and Git commits after GitHub flags them — and to automatically trigger rotation for any leaked secret that Tamma manages,
so that a hallucinating LLM or a careless commit cannot expose tenant credentials for longer than it takes for the next workflow step to run.

## Overview

Story 1.5-17's `TammaVaultStore.findSecretsByFingerprint()` gives us the primitive needed to answer "is this leaked string one of our secrets?" without ever having plaintext at the call site. This story builds two detection channels that exercise that primitive and, on a match, start the `AutoRotateWorkflow` child workflow (Story 1.5-31) to rotate the affected secret.

**Channel 1 — LLM tool output scanning** (inbound interception):
- A wrapper middleware intercepts every response from an LLM tool call BEFORE it is returned to the model
- The response text is passed through a fast `PatternScanner` that runs:
  - **Fingerprint check**: for every candidate substring, compute `HMAC(substring, fingerprintKey)` and call `TammaVaultStore.findSecretsByFingerprint(hmac)` — exact match for secrets *we own*
  - **Regex library**: known public formats (GitHub PAT `ghp_*`, AWS access key `AKIA*`, Stripe key `sk_live_*`, Google API key `AIza*`, JWT `eyJ...`, generic high-entropy base64)
- On a fingerprint hit → `SECRET.LEAK_DETECTED` event + `AutoRotateWorkflow` child workflow
- On a regex-only hit → `SECRET.LEAK_DETECTED` event with `secretId: null` → notify operator, do NOT auto-rotate (nothing to rotate)
- The tool response is *not* modified by the scanner — redaction of LLM-facing text is the job of the prompt pipeline (1.5-26), not this story

**Channel 2 — GitHub secret-scanning webhook** (outbound after-the-fact):
- Subscribe to GitHub's `secret_scanning_alert` webhook event — GitHub runs its own known-pattern scanner on every push and fires this event when it finds a match in a commit
- Handler at `POST /api/v1/webhooks/github/secret-scanning` in `packages/api`
- Validate webhook signature using the existing GitHub App webhook signature helper from Story 1.5-11
- GitHub's alert payload includes the *leaked secret value* (the bytes it found in the commit). We compute `HMAC(leakedValue, fingerprintKey)` and look it up via `findSecretsByFingerprint()`
- If it's ours → `SECRET.LEAK_DETECTED` + `AutoRotateWorkflow`
- If it's not → emit the alert for operator visibility (for logging only; we don't own it and can't rotate it)

**Channel 3 — trufflehog on Tamma-authored PRs**:
- Owned by Story 1.5-34 (non-GitHub git leak scanning via trufflehog). This story does not wire trufflehog — Channels 1 and 2 are the in-scope detection surface.

Regex rules loaded from `packages/secret-broker/src/scanner/rules.yml` — 20+ patterns covering at minimum: GitHub PAT (`ghp_`, `github_pat_`), GitHub App installation token (`ghs_`), AWS access key (`AKIA[0-9A-Z]{16}`), AWS secret key (40-char base64), Stripe live key (`sk_live_`), Stripe test key (`sk_test_`), Stripe restricted key (`rk_live_`), Google API key (`AIza[0-9A-Za-z_-]{35}`), Slack bot token (`xoxb-`), Slack user token (`xoxp-`), Slack webhook (`https://hooks.slack.com/`), OpenAI key (`sk-[A-Za-z0-9]{48}`), Anthropic key (`sk-ant-`), JWT (`eyJ[A-Za-z0-9_-]+\\.eyJ[A-Za-z0-9_-]+\\.[A-Za-z0-9_-]+`), SSH private key header (`-----BEGIN [A-Z ]+PRIVATE KEY-----`), generic high-entropy hex ≥32 chars, generic high-entropy base64 ≥40 chars with Shannon entropy ≥ 4.5 bits/char
4. Each rule has fields: `id`, `name`, `pattern` (regex), `confidence`, `entropyThreshold?` — operator can add rules by editing the YAML, no code change needed
5. Fingerprint scan: for each regex match, compute `crypto.createHmac('sha256', fingerprintKey).update(matchText).digest()` and query `TammaVaultStore.findSecretsByFingerprint(hmac)`. Fingerprint scan also runs independently for ALL substrings of plausible secret lengths (16–256 chars, split on whitespace and common delimiters) — regex is a performance hint, fingerprint is ground truth
6. `LlmOutputInterceptor` middleware in `packages/secret-broker/src/interceptors/llm-output.ts`: wraps the existing LLM tool-call return path, runs scanner, emits `SECRET.LEAK_DETECTED` events (one per hit), starts `AutoRotateWorkflow` via the workflow client for fingerprint hits; does NOT mutate the tool response text
7. Interceptor attaches to the `IAgentProvider` and `IAIProvider` tool-loop paths — wiring is the decorator pattern from the `SecureAgentProvider` work (see MEMORY.md `hashed-purring-teapot` plan), so adding the interceptor is a single registration call in the provider factory
8. `POST /api/v1/webhooks/github/secret-scanning` route in `packages/api`:
   - Validates `X-Hub-Signature-256` using the existing helper from 1.5-11
   - Parses GitHub's `secret_scanning_alert` payload (action `created` | `resolved` | `reopened` | `revoked`)
   - For `created`: extracts `secret` (the leaked value) and `secret_type`
   - Computes fingerprint HMAC and calls `findSecretsByFingerprint()`
   - Emits `SECRET.LEAK_DETECTED` with `source: 'git_commit'`, `repo`, `commitSha?`, `secretId?`
   - Starts `AutoRotateWorkflow` if `secretId` is non-null
9. `LeakDetectionWorkflow` Elsa workflow: `Classify → Evaluate → StartChildWorkflow(AutoRotateWorkflow) [conditional] → EmitAuditEvent`
10. `SECRET.LEAK_DETECTED` event shape (emitted by both channels):
    ```typescript
    {
      type: 'SECRET.LEAK_DETECTED',
      tags: { tenantId, secretId?, source: 'llm_output' | 'git_commit' | 'trufflehog', severity: 'critical' | 'high' | 'medium' },
      data: {
        scanKind: 'fingerprint' | 'regex',
        ruleId?: string,
        matchPreview: string,   // "ghp_...1a2b" — first 4 + last 4
        toolName?: string,      // for llm_output
        repo?: string,          // for git_commit
        commitSha?: string,
        confidence: 'high' | 'medium' | 'low'
      }
    }
    ```
11. **No raw leaked bytes in events.** `matchPreview` is bounded to first 4 chars + `...` + last 4 chars. Full match is HMACed and stored in a separate `leak_fingerprint_log` append-only table for forensic linkage; the HMAC is NOT reversible

15. End-to-end test: inject a synthetic LLM tool response containing a known-to-be-ours secret value → scanner detects → event emitted → `AutoRotateWorkflow` mock child workflow invoked with correct `secretId`
16. **`SECRET.LEAK_DETECTED` with `source: 'trufflehog'` is defined in the event schema (AC10) so Story 1.5-34 can emit it.** The actual `TrufflehogScanActivity` + PR gate wiring lives in Story 1.5-34; this story only reserves the `source` enum value and ensures the event router accepts it.

### Requirements Context Summary

**Epic Context:** Detection is the second leg of the secret-broker security model (the first being confinement via 1.5-16 / 1.5-17, the third being active probing via 1.5-27). A secret that escapes confinement must be detected as quickly as possible. The two channels chosen for v1 are the two that cover the overwhelmingly-most-likely leak vectors in an autonomous-LLM-driven development system:

1. **LLM output**: the LLM hallucinates a credential it saw in training data, or echoes back a credential from a prior tool response, or is tricked by a prompt injection into exfiltrating one. This is Tamma's biggest novel risk and the one traditional SAST doesn't address.
2. **Git commits**: the LLM writes code that hardcodes a credential and commits it. GitHub already runs the world's best secret scanner on every push (built from their entire PAT history) — we just need to subscribe.

**Technical Context:** The `findSecretsByFingerprint` method added in Story 1.5-17 (this session's work — see worktree diff) is the key primitive: it lets us ask "do we own the secret whose HMAC equals X?" without ever exposing plaintext. Both channels rely on it. The fingerprint key itself is stored in the broker's vault master-key envelope and is never rotated (rotating it would invalidate all stored fingerprints) — this is an accepted design trade-off documented in 1.5-17.

**Integration Points:**
- Story 1.5-17 (TammaVaultStore): `findSecretsByFingerprint()` is the core dependency; this story uses it heavily
- Story 1.5-11 (GitHub App Integration): reuses `verifyGitHubWebhookSignature()` helper
- Story 1.5-18 (Secret Activities): reuses `StartChildWorkflowActivity` pattern
- Story 1.5-19 (Workflow infrastructure): event bus, workflow client, child workflow invocation
- Story 1.5-27 (ProbeSecretWorkflow): SIBLING — does not call each other. 1.5-27 is active (ask the secret), 1.5-28 is passive (observe the world).
- Story 1.5-30 (Operator notifications): consumes `SECRET.LEAK_DETECTED` events to notify operators via the notification UX
- Story 1.5-31 (AutoRotateWorkflow): **hard dependency** — the child workflow this story starts. Must exist for E2E test.

### Implementation Guidance

**Key Design Decisions:**

1. **Fingerprint first, regex second.** Fingerprint scanning is authoritative for secrets *we own* — a match is a confirmed leak. Regex scanning is heuristic for secrets *anyone might own* — a match is a "notify operator, but we can't rotate" signal. Running fingerprint first means the common case (our secret leaked) gets the high-confidence path, and regex only labels results that aren't already identified.

2. **Interceptor is observe-only.** The interceptor does NOT rewrite or redact the LLM tool response text. Redacting text mid-flight would interfere with prompt engineering, break content hashes used elsewhere, and create a "mask made the model confused" failure mode. Redaction of LLM-facing content is the job of the prompt pipeline in Story 1.5-26 (a separate, earlier intervention point). This story's job is to *notice* leaks and *react*, not to *hide* them.

3. **Events carry `matchPreview`, not `matchedText`.** The raw leaked bytes are never stored in an event, log line, or trace. `matchPreview` is the first 4 + `...` + last 4 characters, which is enough for human operators to recognize a credential type in a notification ("ghp_...1a2b is leaked") without constituting a second copy of the secret.

4. **YAML rules, not code rules.** Pattern rules live in `rules.yml` so ops can add new patterns without a deploy. This is standard practice (GitHub secret scanning, truffleHog, gitleaks all do this). The tradeoff: a malicious rule edit could trigger rotations, so `rules.yml` lives under `packages/secret-broker/src/scanner/` (code-reviewed) and is baked into the image, NOT loaded from a volume mount. "Operators can add rules" means "operators submit a PR".

5. **Fingerprint scan runs on all plausible substrings, not just regex matches.** Regex is a performance hint, not a correctness filter. A novel credential format Tamma stores (e.g., a new tenant adds a `tamma_xxx_*`-prefixed key) won't match any regex, but WILL match a fingerprint. So fingerprint scanning runs on every substring in the 16–256 char range split on delimiters, regardless of whether regex matched. This is expensive — but the HMAC computation is ~1µs per substring and `findSecretsByFingerprint()` is an indexed lookup, so 10KB of LLM output produces ~1000 candidate substrings and scans in <10ms end-to-end.

6. **Webhook dedup by `alert.id`.** GitHub may redeliver webhooks under network failures. We persist `alert.id` in `github_secret_alerts` with a unique constraint and no-op on duplicates. This is idempotency, not auth — signature validation runs first.

7. **Scanner does not call `AutoRotateWorkflow` directly.** The interceptor emits an event and starts the Elsa `LeakDetectionWorkflow`, which *then* starts `AutoRotateWorkflow` as a child. This moves all orchestration logic into an auditable state machine (replayable, inspectable, stoppable by operator) instead of embedding it in inline middleware.

8. **Trufflehog is owned by Story 1.5-34.** This story ships the two highest-leverage channels (fingerprint-first LLM output scanner + GitHub secret-scanning webhook). Trufflehog is a great third channel but adds ~80MB binary, requires CI integration, and has its own false-positive rate to tune — all of which Story 1.5-34 (non-GitHub git leak scanning) handles end-to-end. This story reserves the `source: 'trufflehog'` enum value so 1.5-34 can emit into the same event schema without a migration.

**Technical Specifications:**

- **Rule YAML schema:**
  ```yaml
  version: 1
  rules:
    - id: github-pat-classic
      name: "GitHub Personal Access Token (classic)"
      pattern: "ghp_[A-Za-z0-9]{36}"
      confidence: high
    - id: aws-access-key
      name: "AWS Access Key ID"
      pattern: "AKIA[0-9A-Z]{16}"
      confidence: high
    - id: stripe-live-key
      name: "Stripe Live Secret Key"
      pattern: "sk_live_[A-Za-z0-9]{24,}"
      confidence: high
    - id: jwt
      name: "JSON Web Token"
      pattern: "eyJ[A-Za-z0-9_-]+\\.eyJ[A-Za-z0-9_-]+\\.[A-Za-z0-9_-]+"
      confidence: medium
    - id: high-entropy-base64
      name: "High-Entropy Base64"
      pattern: "[A-Za-z0-9+/]{40,}={0,2}"
      confidence: low
      entropyThreshold: 4.5
  ```

- **Scanner flow:**
  ```
  LlmOutputInterceptor.intercept(toolName, text, ctx)
    → CompositeScanner.scan(text)
       → FingerprintScanner — returns high-confidence hits (secretId present)
       → PatternScanner     — returns heuristic hits (ruleId present)
       → merge + dedupe by offset
    → for each hit:
         emit SECRET.LEAK_DETECTED event (matchPreview only)
         if fingerprint hit:
            workflowClient.start('LeakDetectionWorkflow', { scanResults: [hit], source: 'llm_output' })
                → LeakDetectionWorkflow → StartChildWorkflow('AutoRotateWorkflow', { secretId })
    → return text UNMODIFIED
  ```

- **Webhook handler flow:**
  ```
  POST /api/v1/webhooks/github/secret-scanning
    → verifyGitHubWebhookSignature(rawBody, X-Hub-Signature-256, webhookSecret)
    → if action == 'created':
        fingerprint = HMAC-SHA256(alert.secret, fingerprintKey)
        secretId = await findSecretsByFingerprint(fingerprint)
        if (alreadySeen(alert.id)) return 200
        workflowClient.start('LeakDetectionWorkflow', {
          scanResults: [{ kind: 'fingerprint', secretId, matchPreview: preview(alert.secret), confidence: 'high' }],
          source: 'git_commit',
          repo: alert.repository.full_name,
          commitSha: alert.locations?.[0]?.details?.commit_sha
        })
    → return 200
  ```

- **Preview function:**
  ```typescript
  function preview(s: string): string {
    if (s.length < 10) return '***';
    return `${s.slice(0, 4)}...${s.slice(-4)}`;
  }
  ```

- **`leak_fingerprint_log` table:**
  ```sql
  CREATE TABLE leak_fingerprint_log (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    fingerprint_hmac BYTEA NOT NULL,
    source TEXT NOT NULL,           -- 'llm_output' | 'git_commit' | 'trufflehog'
    alert_ref TEXT UNIQUE,          -- nullable for llm_output, populated with alert.id for git_commit
    tenant_id UUID REFERENCES tenants(id),
    secret_id UUID REFERENCES secrets(id)  -- nullable if unknown fingerprint
  );
  CREATE INDEX idx_leak_fp_hmac ON leak_fingerprint_log (fingerprint_hmac);
  CREATE INDEX idx_leak_fp_tenant_time ON leak_fingerprint_log (tenant_id, created_at DESC);
  ```

### Risks and Mitigations

| Risk | Severity | Mitigation |
| ---- | -------- | ---------- |
| **False-positive rotation**: scanner flags a legitimate high-entropy value as a secret and triggers rotation of an unrelated credential. | **Critical** | Fingerprint scan is authoritative — only it triggers auto-rotation. Regex-only hits emit events for operator review, they do NOT start `AutoRotateWorkflow`. The fingerprint path cannot false-positive because it's HMAC equality against our own stored fingerprints. |
| **Scanner performance on large tool outputs** (e.g., a `cat` of a 1MB file) blocks the tool-call hot path. | **High** | Max scannable size is 256KB; larger inputs are sampled (first 128KB + last 128KB). FingerprintScanner deduplicates identical substrings before HMAC. Perf test asserts 10KB in <50ms, 256KB in <500ms. |
| **Interceptor bug drops tool output** — a bug in the middleware could prevent the tool response from reaching the LLM. | **High** | Interceptor is *observe-only* by contract. A try/catch wraps all scanner logic; on exception, log + emit `SECRET.SCANNER_ERROR` event and return the tool response unchanged. Scanner failure must never block the critical path. Test: inject a scanner that throws, assert tool response still returned. |
| **Fingerprint oracle via timing**: an attacker observes "did my query to `findSecretsByFingerprint` take longer, suggesting a match?" | **Medium** | The lookup is an indexed B-tree query in Postgres; hit vs miss timing differs by microseconds. Production network jitter dwarfs that. Accepted — a constant-time path is not practical at the DB layer and the attacker would need privileged query access to exploit it. |
| **GitHub webhook replay** creates duplicate rotation. | **Medium** | `alert.id` unique constraint in `github_secret_alerts` table; check on receipt, return 200 without triggering work. |
| **Rule YAML parse failure** at startup crashes the broker. | **Medium** | Parser validates each rule compiles as a regex; on failure, log `ERROR` and skip the rule (do not crash broker). Health check reports "N of M rules loaded"; alert fires if count drops below baseline. |
| **Operator fatigue from low-confidence events** — 100 regex-only hits/day would train operators to ignore the feed. | **Medium** | Regex-only events are tagged `severity: medium` or `low`; fingerprint events are `severity: critical`. Notification UX (1.5-30) defaults to critical-only. Low-severity events go to an audit log, not a pager. |
| **Rules drift between Tamma and GitHub** — GitHub adds a new token type we don't have. | **Low** | Fingerprint-first architecture means new Tamma-owned secrets are covered automatically. For non-Tamma secrets, we rely on GitHub's webhook channel — which will always be up-to-date with GitHub's own patterns. Regex rules are for defense-in-depth, not primary coverage. |
| **Trufflehog binary supply chain** | **Medium** | Owned by Story 1.5-34; the trufflehog binary hash is pinned there. Not a risk in this story. |
| **Prompt-injection scanner bypass**: LLM is tricked into encoding the secret (base64, rot13, etc.) before emitting it. | **Medium** | Known limitation. Pattern scanner catches common base64. A decoder pass (base64, hex, rot13) before fingerprinting is a judgment-call extension — no dedicated story exists yet; if operator experience shows bypass attempts, a new story can be filed against the next open slot. |

## Logging Requirements

Infrastructure and deployment components MUST use structured logging via pino/ILogger (never `console.log` in production code).

- **INFO**: Scanner initialized (`rulesLoaded`, `rulesSkipped`), leak detected (`source`, `severity`, `secretId?`, `matchPreview`), webhook received (`alert.id`, `action`, `repo`), child workflow started (`workflowId`, `secretId`)
- **DEBUG**: Rule matched (`ruleId`, `offset`), fingerprint queried (count), false positive suppressed (entropy below threshold), webhook dedup hit (`alert.id`)
- **WARN**: Scanner exception caught (returned tool response unchanged), rule compilation failed at startup (`ruleId`, `error`), webhook signature slow, unknown webhook action, regex-only hit with no fingerprint match (lower confidence signal), leak_fingerprint_log insert conflict
- **ERROR**: `rules.yml` parse failed, fingerprint key unavailable, webhook signature helper crashed, child workflow invocation failed, scanner completely unavailable
- **Structured context**: Always include `{ tenantId, source, severity, ruleId?, secretId? }`. NEVER log `matchedText` or any raw bytes from an LLM tool response — only `matchPreview` and rule metadata. NEVER log the GitHub webhook `alert.secret` field.
- **Credential safety**: `matchPreview` is the only form in which any fragment of a detected secret may appear in a log line. The interceptor has a dedicated test asserting no raw match bytes reach pino log calls. Webhook handler extracts `alert.secret` only to compute the HMAC, then discards it.
- **Audit events**: `SECRET.LEAK_DETECTED` is the canonical record — logs are for debugging only. Every leak detection also writes a row to `leak_fingerprint_log` for forensic queries without plaintext exposure.
