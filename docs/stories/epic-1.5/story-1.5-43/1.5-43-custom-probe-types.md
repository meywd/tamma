## Story

As a **Tamma operator running secrets against systems Tamma doesn't ship a built-in probe for
(SSH servers, OAuth2 client secrets, TLS certs, Stripe, AWS, arbitrary SaaS APIs)**,
I want **a plugin framework that lets me register new probe types without modifying
`@tamma/secret-broker` core**,
so that **my custom probes participate in the same rate limiting, redaction, audit, and
health-check pipelines as the built-in types — and so that I can ship additional probe types
with Tamma itself without bloating the core package.**

## Overview

Story 1.5-27 implemented 5 built-in probe types: `http_bearer`, `database_connect`,
`jwt_sign_verify`, `smtp_auth`, `github_token`. The registry was designed to be dynamic, but
the plugin machinery — discovery, sandboxing, config schema validation, safe loading — was
explicitly not implemented. This story closes that gap with two deliverables:

1. **A plugin framework** — `IProbeHandlerPlugin`, plugin discovery via `plugins/probes/*.js`,
   schema-validated config, VM-sandboxed execution, UI listing of loaded plugins.
2. **5 additional built-in probe types** shipped alongside the framework — `ssh_connect`,
   `tls_cert_expiry`, `oauth2_client_credentials`, `stripe_api_key`, `aws_credentials` — to
   prove the framework works for a range of real-world targets and to cover the most common
   non-built-in cases out of the box.

The plugin framework's security stance is strict: custom probe handlers run inside a Node.js
`vm` context with a restricted globals proxy, an outbound network allowlist declared at
registration time, no filesystem access, and a hard 10-second execution cap. They receive the
plaintext as a `Buffer` (same as built-in handlers) but can only return a shape-constrained
`ProbeResult`. The plugin loader refuses to load any plugin that does not expose a
JSON-Schema-declared config, an explicit `allowedHosts` list, and a signed (or at minimum
checksummed) plugin manifest.

Plugins register via a `plugins/probes/` convention rather than an imperative API: the broker
scans that directory at startup, validates each file against the `IProbeHandlerPlugin`
contract, and adds the handler to the shared `ProbeHandlerRegistry`. No restart is required to
load a new plugin file — the broker watches the directory and re-scans on change, debouncing
to avoid thrashing during bulk deploys.

## Acceptance Criteria

1. `IProbeHandlerPlugin` interface exists at
   `packages/secret-broker/src/probes/plugin-types.ts`, extending `IProbeHandler` from Story
   1.5-27 with the following additional members:
   ```typescript
   interface IProbeHandlerPlugin extends IProbeHandler {
     readonly manifest: ProbeHandlerManifest;
   }

   interface ProbeHandlerManifest {
     probeType: string;                     // unique across all handlers
     displayName: string;
     description: string;
     version: string;                       // semver
     author: string;
     configSchema: JSONSchema7;              // validates the probe config object
     allowedHosts: string[];                 // hostname or CIDR allowlist
     timeoutMsDefault: number;
     timeoutMsCeiling: number;               // capped at 60000
     checksum: string;                       // sha256 of the plugin file contents, checked at load
   }
   ```

2. The plugin loader is `PluginLoader` at
   `packages/secret-broker/src/probes/plugin-loader.ts` with method
   `loadFromDirectory(dir: string): Promise<PluginLoadReport>`. The report contains
   `{ loaded: string[], rejected: Array<{ file: string, reason: string }> }`. Loading does not
   throw on individual plugin errors — it logs, reports, and skips the bad file.

3. Plugins are `.js` files (not `.ts`) to avoid transpilation at runtime. A build step
   compiles custom plugins from TypeScript to JavaScript ahead of deployment. The loader
   rejects any non-`.js` file in `plugins/probes/`.

4. Each plugin file must `module.exports = { default: ProbeHandlerPlugin }` where the default
   export is an object satisfying `IProbeHandlerPlugin`. The loader uses Node.js
   `require()` on a per-plugin `vm.Script` context (not the real `require`) so the plugin
   never gains access to the broker's process globals.

5. The plugin VM context exposes only:
   - `Buffer`
   - `console` (redirected to `pino` at DEBUG level, prefixed with `[probe:${probeType}]`)
   - `fetch` (monkey-patched to reject any URL whose hostname does not match the plugin's
     `allowedHosts`, SSRF-safe by default: RFC1918 + loopback + link-local + metadata
     endpoints always rejected)
   - `setTimeout` / `clearTimeout` / `setImmediate`
   - `URL`, `URLSearchParams`, `TextEncoder`, `TextDecoder`, `crypto` (the `node:crypto`
     module)
   - NO `process`, `fs`, `child_process`, `net`, `tls`, `http`, `https`, `dgram`, `require`
     (a fake require that only resolves a curated allowlist of safe modules)
   - NO access to environment variables beyond a curated `TAMMA_PROBE_PLUGIN_ENV` object

6. Plugin execution is wrapped in an `AbortController` with `manifest.timeoutMsCeiling` as the
   outer bound. If the plugin exceeds its declared timeout, its VM context is torn down and
   the handler returns `ProbeResult { success: false, errorCategory: 'timeout', ...}`.

7. Plugin config validation happens before every `probe()` invocation using `ajv` against the
   `manifest.configSchema`. Invalid config returns
   `ProbeResult { success: false, errorCategory: 'config_error', errorMessage: <redacted validation errors> }`
   without loading plaintext or entering the VM.

8. The existing `ProbeRateLimiter` from Story 1.5-27 applies equally to plugin probes — no
   plugin can bypass the default 10/min per-secret budget or the 60/min tenant cap.

9. The existing redaction pipeline (`sanitizeProbeResult` + literal taint scan) from Story
   1.5-27 is applied to every `ProbeResult` a plugin returns, before it crosses the
   broker HTTP boundary. A taint-tracking test per plugin probe type is mandatory.

10. The `GET /internal/v1/probes` endpoint is added to the broker HTTP service. It returns a
    list of currently-loaded handlers (built-in + plugin) with their manifests, for
    consumption by the dashboard. Built-in handlers expose a synthetic manifest with
    `author: 'tamma-core'`.

11. Five additional built-in probe handlers are implemented under
    `packages/secret-broker/src/probes/` as normal `IProbeHandler`s (NOT as plugins — they
    ship with core and benefit from tighter coupling to shared utilities):
    - **`ssh_connect`** — attempts SSH key-based auth against a host+port using
      `ssh2.Client.connect({ host, port, username, privateKey: value })`, runs `uptime` or
      equivalent trivial command, disconnects. Errors: `auth_failed` on
      `ERR_SSH_AUTH_FAILED`, `network_error` on `ECONNREFUSED`/`ETIMEDOUT`, `timeout` on
      abort.
    - **`tls_cert_expiry`** — **offline** check. Parses the secret as a PEM-encoded
      certificate, extracts `notAfter`, returns `success: true` when
      `notAfter > now + config.minRemainingDays` (default 30 days), otherwise
      `success: false` with `errorCategory: 'expired'` (new category — see AC 12). Zero
      network I/O.
    - **`oauth2_client_credentials`** — issues a `POST` to `config.tokenEndpoint` with
      `grant_type=client_credentials&client_id=...&client_secret=<value>`, asserts a 2xx
      response with a valid `access_token` field, returns `success: true`. Errors: 401/400
      → `auth_failed`, 5xx → `server_error`.
    - **`stripe_api_key`** — issues `GET https://api.stripe.com/v1/account` with
      `Authorization: Bearer <value>`, asserts 200, parses the response to assert the
      `object: 'account'` field is present. 401 → `auth_failed`, 429 → `rate_limited`.
    - **`aws_credentials`** — issues AWS STS `GetCallerIdentity` using the `@aws-sdk/client-sts`
      client with the secret parsed as either a `{ accessKeyId, secretAccessKey }` JSON object
      or an `AccessKeyId:SecretAccessKey` colon-string. Config allows specifying the STS
      endpoint region. Errors: `InvalidClientTokenId` / `SignatureDoesNotMatch` →
      `auth_failed`, network → `network_error`.

12. `ProbeErrorCategory` is extended (with full backward compat) to include `expired`, used
    by `tls_cert_expiry` and reserved for any future "credential-is-structurally-valid-but-
    past-its-shelf-life" cases. All existing code continues to handle the original 8
    categories.

13. Each new built-in handler has its own `*.test.ts` file covering happy path, each error
    category it produces, config validation, timeout, and taint tracking.

14. Plugin framework tests at `packages/secret-broker/src/probes/plugin-loader.test.ts` cover:
    - Loads a valid plugin
    - Rejects a plugin with a checksum mismatch
    - Rejects a plugin with missing manifest fields
    - Rejects a plugin that tries to import `fs` from inside the VM
    - Rejects a plugin that tries to `fetch()` a disallowed host
    - Rejects a plugin that tries to `fetch()` an RFC1918 address even if `allowedHosts`
      lists it (hard-coded SSRF defense)
    - Enforces config schema validation
    - Enforces per-plugin timeout ceiling
    - Watches the plugin directory and reloads on change (debounced)

15. A reference example plugin lives at `packages/secret-broker/examples/plugins/vault-echo.js`
    with a matching manifest, used as the fixture for plugin-loader tests and as
    documentation.

16. The broker `README.md` gains a "Writing a custom probe plugin" section documenting the
    interface, manifest requirements, VM sandbox rules, rate-limit obligations, and the
    checksum-signing process.

## Dev Notes

### Requirements Context Summary

**Epic Context:** Tamma's probe registry was built to be dynamic precisely so that operators
and tenants could add their own probe types without waiting on core releases. Story 1.5-27
shipped the registry but not the plugin machinery, so today "custom probe" is a theoretical
capability — you can register a handler in code, but there's no safe way to load one from
disk at runtime. This story closes the gap with a production-grade plugin framework AND
ships a first wave of additional built-in types so operators have reasonable coverage even
before they write a single plugin.

**Technical Context:** The plugin framework's design philosophy is "deny by default, explicit
allowlist for everything." Plugins get a `Buffer` with the plaintext, a restricted `fetch`, a
restricted `require`, and nothing else — no filesystem, no process, no arbitrary network, no
environment variables. This is deliberately more restrictive than the "give them a sandbox
and hope" approach taken by most plugin frameworks; probes handle plaintext and therefore
the blast radius of a compromised plugin is catastrophic.

**Integration Points:**
- **Story 1.5-27** — `ProbeHandlerRegistry` is extended; rate limiter, redaction pipeline,
  audit events, and the `ISecretStore.probeSecret()` contract are unchanged
- **Story 1.5-42** — post-rotation health checks can resolve to plugin probe types via the
  `probeType?: string` override on rotation targets
- **Story 1.5-17** — `TammaVaultStore` still dispatches through the registry; no changes
- **Story 1.5-29** — custom rotation handlers can declare a custom `healthProbeType` that
  resolves to a plugin-registered probe

### Implementation Guidance

**Key Design Decisions:**

1. **`.js` only, no runtime transpilation.** Operators compile their TypeScript plugins
   ahead of deployment; the broker never runs a TypeScript compiler at runtime. This keeps
   the loader simple, eliminates a whole class of supply-chain attacks via malicious
   transformer plugins, and makes plugin loading deterministic.

2. **VM context, not worker threads, in v1.** Worker threads would give better isolation
   (separate V8 heap) but add a full IPC serialization layer and complicate the timeout
   tearing-down path. The `vm` module with a curated globals proxy gives enough isolation
   for v1 — plugins cannot access process globals, cannot `require()` arbitrary modules, and
   cannot call `eval`. Upgrading to worker threads is tracked as a follow-up.

3. **SSRF defense is hard-coded, not configurable.** Even if a plugin's `allowedHosts` lists
   `169.254.169.254` (AWS metadata endpoint) or `10.0.0.1` (internal RFC1918), the
   monkey-patched `fetch` rejects it. This prevents a malicious plugin manifest from
   declaring an allowlist that opens an SSRF hole.

4. **`tls_cert_expiry` is offline.** Unlike the other new probes, it has zero network I/O.
   This is important because cert-expiry checks need to be cheap and run often — rate
   limiting them equivalent to auth checks would wreck the operator experience.

5. **Checksums, not signatures, in v1.** A proper code-signing flow requires a signing key
   management story of its own. Checksums provide tamper detection for the "did the file
   get modified since I committed it" case, which is the case that actually matters for
   local deployments. Full signing is tracked as a follow-up.

6. **New `expired` error category is a category, not a status field.** Making expiry a
   separate category means dashboards and alerting rules can filter for it without parsing
   error messages. Backward compat is preserved because `ProbeResult.errorCategory` is
   already optional and callers that handle the existing 8 categories and use a default
   branch continue to work.

7. **Built-in handlers don't use the plugin machinery.** They are `IProbeHandler`, not
   `IProbeHandlerPlugin`, because they ship with core and are code-reviewed inline. Making
   them plugins would force them through the VM sandbox unnecessarily and break
   type-checked access to shared utilities.

**Technical Specifications:**

- **Plugin discovery flow:**
  ```
  Broker startup
    → PluginLoader.loadFromDirectory('plugins/probes/')
      → For each *.js file:
          → read file, compute sha256
          → read manifest from sibling .manifest.json (or embedded export)
          → verify checksum matches manifest
          → construct vm.Context with restricted globals
          → require() plugin in context
          → validate default export against IProbeHandlerPlugin interface
          → compile config JSON Schema with ajv
          → register in ProbeHandlerRegistry
          → emit PROBE.PLUGIN.LOADED audit event
  ```

- **VM globals whitelist:**
  ```typescript
  const pluginGlobals = {
    Buffer, URL, URLSearchParams, TextEncoder, TextDecoder,
    console: pluginConsole,  // redirected to pino
    fetch: sandboxedFetch,   // allowlist + SSRF defense
    setTimeout, clearTimeout, setImmediate,
    crypto: cryptoModule,    // node:crypto, curated
    require: sandboxedRequire, // allowlist: crypto, url, util
  };
  ```

- **Error code additions:**
  ```typescript
  export const PROBE_PLUGIN_ERROR_CODES = {
    PROBE_PLUGIN_CHECKSUM_MISMATCH: 'PROBE_PLUGIN_CHECKSUM_MISMATCH',
    PROBE_PLUGIN_MANIFEST_INVALID: 'PROBE_PLUGIN_MANIFEST_INVALID',
    PROBE_PLUGIN_SANDBOX_VIOLATION: 'PROBE_PLUGIN_SANDBOX_VIOLATION',
    PROBE_PLUGIN_LOAD_FAILED: 'PROBE_PLUGIN_LOAD_FAILED',
  } as const;
  ```

### Risks and Mitigations

| Risk | Severity | Mitigation |
| ---- | -------- | ---------- |
| VM sandbox escape via prototype pollution or V8 bug | **Critical** | Restricted globals proxy; no user-controlled `eval`; upgrade to worker threads tracked as follow-up; document that v1 sandbox is defense-in-depth, not absolute |
| Malicious plugin exfiltrates plaintext via `fetch` | **Critical** | Host allowlist + hard-coded SSRF defense + taint-tracking test per plugin type; checksummed load path makes silent replacement detectable |
| Plugin consumes all broker CPU via infinite loop | **High** | `AbortController` + VM context teardown at timeout; per-plugin ceiling capped at 60s |
| Plugin leaks plaintext in error messages (third-party library echo) | **High** | Existing `sanitizeProbeResult` + literal taint scan; mandatory taint-tracking test per plugin |
| Plugin checksum collides | Low | sha256 is collision-resistant; full signing flow tracked as follow-up |
| `tls_cert_expiry` false positives on cert chains | Medium | Only parses the leaf cert; documents that chain validation is not the probe's responsibility |
| AWS STS rate limits on `aws_credentials` bulk rotations | Medium | Rate limiter applies; document that STS has its own 5000/min limit which is well above probe budgets |
| SSH fixture server flakes on CI | Low | Use `ssh2.Server` with fixed-seed host keys; random-port binding to avoid collisions |

## Logging Requirements

Infrastructure and deployment components MUST use structured logging via pino/ILogger (never
`console.log` in production code).

- **INFO**: Plugin loaded (`probeType`, `version`, `author`), plugin unloaded, plugin
  reloaded on file change, new built-in handler executed (`probeType`, `durationMs`),
  `GET /internal/v1/probes` served
- **DEBUG**: Plugin VM context constructed, config schema compiled, plugin require()
  resolved a module from the allowlist, plugin timeout set, checksum verified
- **WARN**: Plugin load rejected (every rejection reason is a separate WARN line with
  `{ file, reason }`), sandbox violation attempted (module access, fetch host), config
  schema validation failed at runtime, plugin returned a failure (`errorCategory`), taint
  scan replaced bytes (escalate)
- **ERROR**: Plugin VM context crashed, plugin exceeded timeout and did not cleanly abort,
  `GET /internal/v1/probes` handler failed, directory watcher crashed, AWS STS client
  initialization failed
- **Structured context**: Always include `{ probeType, manifestVersion, durationMs,
  secretId?, tenantId? }`. NEVER log plaintext, probe config fields that might contain a
  credential (even if the schema allows them), plugin source code, or raw AWS STS
  `InvalidClientTokenId` details (AWS error messages can echo AccessKeyId prefixes).
- **Credential safety**: Plugin execution happens inside the VM; plaintext buffers zeroed
  in `finally`; log lines reference `secretId` and `probeType` only; sandbox-violation
  logs include attempted target (module name, host) but never the plaintext being probed
- **Audit events**: `PROBE.PLUGIN.LOADED`, `PROBE.PLUGIN.UNLOADED`,
  `PROBE.PLUGIN.LOAD_REJECTED`, `PROBE.PLUGIN.SANDBOX_VIOLATION` are the canonical record;
  log lines are for debugging only and can be sampled.
