## User Story

As a **product owner**,
I want to nest work items under a bounded hierarchy and reorder a backlog by dragging — and I want an accepted `BacklogOrdering` document from Story 41-3 to be *applied* to that order in one operation,
So that prioritisation produced by a workflow becomes the actual order of the actual backlog, instead of an accepted document nobody can act on.

## Acceptance Criteria

1. **Reparenting endpoint** `POST /api/work-items/{id:guid}/parent` accepting `{ parentId | null }`. Rejects with `400` naming the rule when: `TrackerHierarchy.CanParent(parent.Kind, child.Kind)` is false; the move would exceed `TrackerHierarchy.MaxDepth`; the parent is the item itself or one of its descendants (cycle); or parent and child are in different projects.

2. **Depth and cycle checks are computed from the persisted chain**, not from the request, and are performed inside the same transaction as the write. A concurrency test drives two simultaneous reparents that would jointly create a cycle and asserts exactly one succeeds.

3. **Move endpoint** `POST /api/work-items/{id:guid}/move` accepting `{ afterId? , beforeId? }` and writing exactly **one** row: `Rank = Rank.Between(after.Rank, before.Rank)`. A test asserts a single `UPDATE` statement and that no other row's `Rank` changes.

4. **Kind change is a validated transition, not a free field.** `PATCH /api/work-items/{id}` changing `kind` re-validates the item against its current parent *and* all its current children, and rejects `400` with the violating relationships listed. A test moves a `Story` with `Task` children to `kind: task` and asserts rejection.

5. **Subtree read** `GET /api/work-items/{id:guid}/subtree` returning the item and its descendants to `MaxDepth`, each with its `Rank`, in one query (recursive CTE), ordered so a client can render a tree without a second sort.

6. **Roll-up counts.** `GET /api/work-items` and the subtree read return, per item, `childCount` and `childCountByStatus`. Computed in SQL, not by N+1 reads; a test asserts the query count is constant in the number of items returned.

7. **Apply seam** `POST /api/projects/{projectId:guid}/apply-ordering` accepting `{ documentId }`. It:
   - reads the `DocumentInstance` by id, **requires `DocumentType == "backlog-ordering"` and `Status == "accepted"`**, rejecting `409` otherwise, naming which condition failed;
   - resolves each referenced item by its ~~`issueId`~~ **`itemId`** string *[CORRECTED 2026-08-01 — the document field is `itemId` (`Types/BacklogOrdering.cs:15`); see Amendment A5]* to a work item in the project;
   - orders the entries by **`BacklogItem.Rank`** (the document's own 1..N gap-free integer field, `Types/BacklogOrdering.cs:16`), **never by array position** *[CORRECTED 2026-08-01 — see Amendment A5]*;
   - assigns monotone increasing `Rank`s in the document's order, in **one bulk update in one transaction**;
   - returns a per-item outcome list (`applied` / `not-found` / `wrong-project`), and applies the resolvable subset rather than failing wholesale.

8. **The apply seam is idempotent and non-destructive.** Applying the same accepted document twice is a no-op on the second run. Items in the project that the document does not reference **keep their relative order and are placed after the applied set**, never dropped or randomised. A test asserts both.

## Technical Notes

- The recursive CTE is the reason `MaxDepth` is bounded at all: a `WITH RECURSIVE` with a depth guard is a fixed-cost query; an unbounded one is not, and a cycle introduced by a bug becomes an infinite scan rather than a rejected write. The CTE carries `WHERE depth < TrackerHierarchy.MaxDepth` (6) as a belt-and-braces alongside AC2's write-time check — **referencing the constant, never a literal**, because 44-0 raised it from 3 to 6 exactly once and a hardcoded `3` here would have survived that change silently.
- `move` deliberately does not accept an index. An index is a position in a list the client last saw, which is stale the moment anyone else drags; `(afterId, beforeId)` is a statement about neighbours and is correct under concurrency — worst case it produces a rank between two items that have since moved, which is a visible, harmless outcome rather than a wrong one.
- The apply seam is a **tracker** operation that *reads* a document. It is not a document-lifecycle step, emits no `DOCUMENT.*` event, and does not mutate the document. 41-3's workflow is unchanged and unaware of it.
- Non-referenced items being appended after the applied set (AC8) is a deliberate choice over interleaving: a `BacklogOrdering` produced against a snapshot will always be missing items filed since, and burying newly-filed work in the middle of an old ordering is the worse surprise.

**A3 — The governance ratchet forbids the obvious implementation path, and neither the story nor the plan mentioned it.** New in AC11. `GovernedEndpointCoverageSweepTests` reads `EndpointDataSource` off a booted host, so the three new routes are discovered whether or not anyone remembers them (`GovernedEndpointCoverageSweepTests.cs:96-103`), and every in-scope mutating endpoint must be bound or baselined (`:110-125`). The baseline is a one-way ratchet: `PinnedCount = 216` (`KnownUngovernedEndpoints.cs:128`) must equal `PinHistory[^1]`, `PinHistory = [237, 216]` (`:142`), and `TheRatchetPin_IsMechanicallyShrinkOnly` asserts each element is strictly less than its predecessor (`GovernedEndpointCoverageSweepTests.cs:269-295`). **Therefore new routes cannot be baselined** — the path 44-2 took for its ten (justification `binding-owned-by Story 44-2`, e.g. `KnownUngovernedEndpoints.cs:210-211`) is closed to 44-3, because 44-2's entries were seeded *before* the ratchet turned. **This makes `.Governs` mandatory for the new routes, not optional.** Two riders: `PinnedInScopeCount` (`:157`) *must* be bumped 237 → 240, because the sweep pins the size of the mutating surface separately and a bound route stays in scope; and 44-3 should **not** bind 44-2's existing ten — that would decrement `PinnedCount` and require appending to `PinHistory`, which is legal but is 44-2/43-9's ledger, not this story's.

**A4 — 44-2's rank-uniqueness constraint was real and covered by no acceptance criterion.** New in AC12. 44-2's amendment A1 hands 44-3 a hard constraint (`story-44-2/…-catalog-descriptors.md:130-149`) and its plan repeats it as a boxed "⚠️ CONSTRAINT ON 44-3" (`story-44-2/implementation-plan.md:55-65`), and 44-2 shipped a test written specifically for this story to flip: `TrackerEndpointsTests.Duplicate_ranks_within_a_project_are_accepted_today` (`:651-671`), whose own message says *"when it does, this test is the one to flip"*. **This story, as drafted, mentioned none of it in any AC.** The failure is compound — a duplicate rank inside one project *plus* a rekey — and 44-2 could only pin the premise because the rekey surface is 44-3's. AC12 takes the **`(Rank, Id)` tie-break** branch: `Id` is immutable, `Key` is not (`RekeyAsync`, `IWorkItemRepository.cs:149-158`), and the tie-break is a query + cursor change (`WorkItemRepository.cs:106-116`, `TrackerService.cs:485-497`) with **no schema change** — which keeps this story's "Data & Migrations: **None**" true, where the unique-index branch would have falsified it by opening a second tenant migration against 44-1 D4's explicit scarcity rule. AC12 also requires the compound test 44-2 could not write, and requires it to be red before the change.

**A5 — the apply seam's body shape was guessed wrong three ways.** The plan's `BacklogOrderingEntry(string IssueId, string? Rationale, decimal? Value, decimal? Effort)` and AC7's "resolves each referenced item by its `issueId` string" are wrong against the shipped record (`Types/BacklogOrdering.cs:13-20`): the field is **`itemId`**, not `issueId` (`:15`); **`value` and `effort` are free-text `string`s, not nullable decimals** — deliberately, "estimate units differ per team, so the vocabulary is deliberately NOT closed" (`:9-11`), and the validator requires both to be non-whitespace (`:121-124`); and the entry carries its **own 1-based `int? Rank`** (`:16`) which the validator forces to be the unique gap-free 1..N sequence (`:140-184`), so **document order is `BacklogItem.Rank`, not array position**. Reading array position would silently apply a different order than the one a human accepted, in exactly the case a producer emits `items` unsorted — a bug with no failing test unless you look for it. Separately, the "`issueId` join costs nothing" bullet was carried over from the epic README §2, which is about `DocumentInstance.IssueId`, a different field; `BacklogItem.ItemId` is unconstrained (`:105-110`). See the new "Cross-Story Contract with 41-3" section for C1 (anchor) and C2 (`itemId` meaning).

**A6 — the 2026-07-28 Added AC overstated what is left to do.** Self-edge rejection and canonical lower-id-first storage already ship in 44-1's repository (`WorkItemRepository.cs:488-495`, `:536-538`). Cross-project rejection and the HTTP surface do not. Scoped inline above.
