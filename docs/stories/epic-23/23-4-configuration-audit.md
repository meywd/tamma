# Story 23-4: Configuration Audit

Status: planned

## Summary

Build a configuration audit screen that shows all config sources, validates every setting, highlights missing required values, shows diffs against defaults, and tracks configuration change history. Operators can see exactly what is configured, where it came from, and whether it is valid.

## Acceptance Criteria

### Config Sources Overview

1. The page shows a table of all configuration sources with priority order:
   - Source 1: Environment variables (highest priority)
   - Source 2: User provider settings (`~/.tamma/providers.json` / user.settings DB)
   - Source 3: Repository config (`.tamma.yml` from git)
   - Source 4: Dashboard/API overrides (ConfigService in-memory)
   - Source 5: Default values (hardcoded in code)
2. Each source shows: name, type, location/path, status (active/inactive), last modified timestamp.

### Config Key Inventory

3. A searchable table lists every configuration key in the system:
   - Agents config keys: `defaults.providerChain`, `defaults.maxBudgetUsd`, `defaults.allowedTools`, per-role overrides
   - Security config keys: `sanitizeContent`, `validateUrls`, `gateActions`, `maxFetchSizeBytes`, `blockedCommandPatterns`
   - Provider config keys: per-provider `apiKey`, `defaultModel`, `baseUrl`, `timeoutSeconds`
   - Engine config keys: `pollIntervalMs`, `workingDirectory`, `approvalMode`, `ciPollIntervalMs`, `ciMonitorTimeoutMs`, `mergeStrategy`, `deleteBranchOnMerge`
   - GitHub config keys: `authMode`, `owner`, `repo`, `issueLabels`, `excludeLabels`, `botUsername`
   - Server config keys: `port`, `host`, `jwtSecret`, `corsOrigins`, `enableAuth`
   - ELSA config keys: `enabled`, `serverUrl`, `apiKey`
4. Each row shows:
   - Key name (dotted path, e.g., `agents.defaults.providerChain`)
   - Current value (REDACTED for secrets: apiKey, jwtSecret, passwords -- shows `****` + last 4 chars)
   - Source (which config source provided this value)
   - Default value (for comparison)
   - Validation status: valid (green check), invalid (red X), warning (yellow triangle)
   - Validation message (e.g., "Provider name must match /^[a-z0-9]...$/")
   - Last modified timestamp
   - Data type (string, number, boolean, array, object)

### Missing Configuration Alerts

5. A red alert banner at the top lists all REQUIRED configuration keys that are missing or invalid:
   - Missing provider chain (empty `defaults.providerChain`)
   - Missing GitHub token/app credentials
   - Missing JWT secret in production mode
   - Missing working directory
   - Invalid regex in `blockedCommandPatterns`
6. Each alert includes: key name, expected format, and a "Fix" link that scrolls to the key in the table.

### Config Diff View

7. A "Compare to Defaults" toggle shows a side-by-side diff:
   - Left: current active configuration
   - Right: default configuration
   - Additions (green), modifications (yellow), deletions (red)
   - Only non-default values are highlighted
8. The diff is generated by deep-comparing the current config against the hardcoded defaults in ConfigService.

### Provider Config Validation

9. For each configured AI provider:
   - Name and model
   - API key presence (yes/no, with redacted prefix)
   - "Test Connection" button that:
     - Calls the provider's `isAvailable()` method (or a lightweight API call)
     - Reports: success, latency, error message
     - Shows the model list if the provider supports `listModels()`
   - Last validated timestamp
   - Validation history (last 5 results)

### Git Platform Config Validation

10. For the configured git platform (GitHub/GitLab):
    - Auth mode and token/app configuration
    - "Test Connection" button that:
      - Calls the platform's API to verify token validity
      - Lists accessible repositories (first 5)
      - Reports rate limit remaining
    - Owner/repo reachability status
    - Webhook configuration status (if applicable)

### Environment Variable Completeness

11. A panel lists all environment variables that Tamma reads:
    - `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GITHUB_TOKEN`, `OPENROUTER_API_KEY`
    - `DATABASE_URL`, `ELSA_SERVER_URL`, `OPENSEARCH_URL`, `RABBITMQ_MANAGEMENT_URL`
    - `JWT_SECRET`, `ELSA_SIGNING_KEY`, `RABBITMQ_USER`, `RABBITMQ_PASSWORD`
    - `NODE_ENV`, `LOG_LEVEL`, `PORT`
    - Custom `apiKeyRef` values from provider chain entries
12. Each variable shows: name, set (yes/no), source (env, .env file), redacted value.
13. Variables referenced by `apiKeyRef` in provider chains that are NOT set are flagged as errors.

### Config Change History

14. A timeline shows configuration changes over time:
    - Each change entry: timestamp, user who made the change (from JWT), key changed, old value (redacted), new value (redacted), source (API/CLI/dashboard)
    - Changes are recorded by instrumenting ConfigService.update*() methods
    - History is stored in-memory (last 200 changes) and optionally in PostgreSQL
15. "Restore" button on any history entry (owner-only) that reverts to that configuration state.

## API Endpoints Needed

- GET /api/monitoring/config/inventory -- returns all config keys with values, sources, validation
- GET /api/monitoring/config/sources -- returns config source metadata
- GET /api/monitoring/config/diff -- returns diff between current and default configuration
- GET /api/monitoring/config/env-vars -- returns environment variable completeness check (redacted values)
- GET /api/monitoring/config/missing -- returns list of missing/invalid required configuration
- POST /api/monitoring/config/validate-provider -- body: `{ provider: string }`, tests provider connectivity
- POST /api/monitoring/config/validate-platform -- tests git platform connectivity
- GET /api/monitoring/config/history -- returns config change history, query params: `limit`, `since`
- POST /api/monitoring/config/restore -- body: `{ historyEntryId: string }`, restores a previous config

## Implementation Notes

- Secret redaction is enforced server-side. The API NEVER returns full API keys, JWT secrets, or passwords. The redaction logic: if key name contains `apiKey`, `secret`, `password`, `token`, return `****` + last 4 chars (or `****` if less than 8 chars).
- Config inventory is built by reflecting over `TammaConfig` interface fields plus the ConfigService state.
- Provider validation: create a temporary provider instance, call `isAvailable()`, dispose immediately. Do NOT reuse running providers.
- Platform validation: call `platform.getRepository(owner, repo)` and catch errors.
- Change history: add an `onConfigChange` callback to ConfigService that records `{ timestamp, userId, key, oldValue, newValue }`.
- Restore is implemented as a ConfigService.update*() call with the historical value, creating a new change history entry.
