# Implementation Plan — Story 31-13: Full PR Operation Support

**Story brief**: [`31-13-full-pr-operations.md`](./31-13-full-pr-operations.md)
**Ruling governance model**: `docs/stories/epic-43/story-43-11/43-11-automation-level-model-and-per-action-levels.md` (Amendments 2–4, the caller-kind re-audit, the Dial-governed / Machinery tables)
**Plan verified against the working tree**: 2026-08-03. Every file:line below was re-checked; where the story or 43-11 cites something the tree contradicts, the contradiction is recorded in §Blocked / contradictions rather than planned around.

## Scope & Deliverable

When this story is done:

1. The engine can **close, reopen, comment on, review-comment on, request reviewers for, label, and draft-toggle** a pull request through the same mediated, governed, audited plane it already uses for branch/PR/merge/release — 7 new `/api/v1/git/{owner}/{repo}/pull-requests/{n:int}/…` routes, each `.Governs(...)` + `.EnforcesGovernance()` per 43-9 D15.
2. Each verb is a catalog action at its 43-11 zone level: `git.pull-request.close` 35, `.reopen` 35, `.comment` 35, `.review-comment` 40, `.request-reviewers` 35, `.label` 35, `.set-draft` 35.
3. The three **already-live, uncatalogued** engine issue routes gain catalog keys and enforcement: `git.issue.create` 35, `git.issue.comment` 35, and the label pair `git.issue.labels.set` / `git.issue.labels.remove` 35 (two keys, not the story's one — see contradiction C2). Their four `KnownUngovernedEndpoints` baseline entries are deleted; the ungoverned baseline **shrinks** by 4.
4. The GitHub implementation is live end to end (workflow client → route → mediation → GitHub REST/GraphQL), with the close→reopen round trip proven by test (AC4). GitLab/Gitea/Forgejo/Null drivers answer the new abstraction verbs with the `capability_unsupported` error the interface contract prescribes; the compat matrix records per-driver support via a new `PlatformCapability.PrLifecycle` flag (GitHub only).
5. At the shipped dial (70) nothing changes behaviour: every new key sits at 35/40, below 70, so all new and newly-governed routes stay automated. Only a lowered dial or an explicit tightening gates them. That is the point.

Out of scope (per story): delete PR (platform cannot), merge (exists), branch ops (exist). Also out: implementing the new verbs on GitLab/Gitea/Forgejo for real (their platforms support most of them; that is 31-4/31-6 follow-up work recorded in the compat matrix), and `POST /api/engine/trigger-ci` (uncatalogued but a CI route, not a git route — 43-11 flags it; nobody in this batch owns it, left recorded).

## Blocked / contradictions

Read these before step 1. None is silently planned around.

- **C1 — AC1 as written ("implemented for the GitHub driver with an integration test") is unpassable at the `Tamma.Platforms.GitHub` plane.** All 12 `IGitPlatformClient` methods in `GitHubPlatformClient.cs` are stubs logging "not yet wired through the abstraction" and returning `ServiceUnavailable` (12 hits, e.g. `:60,:111,:180,:191,:206`), and the 31-10 GitHub integration harness is a single `[Ignore]`d placeholder (`Tamma.Platforms.IntegrationTests/GitHubIntegrationTests.cs:36-38`, "GitHub_HarnessNotYetWired"). The **live** GitHub implementation in this repo is `GitHubIntegrationService` (`Tamma.Api/Services/GitHubIntegrationService.cs`, raw REST), reached via `GitMediationService` — that is where branch create, PR create, merge, release, and issue update actually run today. **Decision (D1 below): the working verbs land on the live surface; the abstraction gains the verbs with the GitHub driver keeping its existing stub posture, commented as 31-3's remaining lane.** "Integration test" is satisfied the way GitHub is tested today: `GitMediationServiceTests` + canned-HTTP-handler tests against `GitHubIntegrationService` (`Tamma.Api.Tests/GitHub/GitHubIntegrationServiceTests.cs`), plus `[Category("GitHub")]` cases staged in the ignored 31-10 harness so they activate when it lands. If the product owner requires the platform-driver plane to perform these verbs for real, 31-3's wiring must land first — that is a different story and this one would be blocked on it.
- **C2 — the story's single `git.issue.label` key cannot bind the two live label routes.** The routes are `POST /api/engine/issue-labels` and `DELETE /api/engine/issue-labels/{repo}/{issueNumber}/{label}` (`Program.cs:3125-3126`). 43-8's binding sweep compares a descriptor's `SiteKey` **ordinally** against exactly one route's `{METHOD} {RawText}` (`GovernedEndpointBindingSweepTests.cs:52-53,:89-98`), and SiteKey uniqueness is enforced in the effect namespace (`ActionDescriptor.cs` SiteKey docs). One member, two routes → the second route can never bind. **Resolution: two keys, using 43-11's own Missing-actions naming — `git.issue.labels.set` + `git.issue.labels.remove`, both 35** (43-11 `:1424` proposed exactly this pair). The story's Scope-4 count "3 issue keys" becomes 4; recorded here and in the story's change log when this lands.
- **C3 — the zone levels 35/40 are illegal thresholds until 43-11's widening lands.** `AutonomyDial.Min` is still `70` (`AutonomyDial.cs:27`) and `ActionCatalog` boot-validates every descriptor via `AutonomyDial.IsValidThreshold` (`ActionCatalog.cs:181-183`) — a descriptor at 35 **throws at catalog build** today. 43-11's own implementation plan performs the `Min = 70 → 1` edit and makes the level parameter required on all six descriptor helpers. **31-13's catalog step is hard-blocked on 43-11 landing.** (Deliberately NOT worked around by shipping at `AutonomyDial.Min` and re-levelling later — that re-does 43-11's migration and ships keys that lie about their zone.)
- **C4 — "throw PLATFORM_NOT_SUPPORTED" contradicts the abstraction's no-throw contract.** `IGitPlatformClient.cs:12-15`: "drivers MUST NOT throw on platform errors"; the established shape for a missing verb is `PlatformResult` failure with `PlatformError.InvalidRequest(Code: "capability_unsupported", …)` (`IGitPlatformClient.cs:74-80`, tested in `PlatformErrorTests`). **Resolution: non-GitHub drivers return that, not an exception.** No `PLATFORM_NOT_SUPPORTED` constant is added to `GitFailureCodes` either — the mediation plane is GitHub-only today and never reaches another driver, so the wire code would be dead; when multi-platform mediation exists, mapping `capability_unsupported` to a wire code belongs to that story.

## Design Decisions

- **D1 — The working GitHub implementation lives on the live surface (`GitHubIntegrationService` + `GitMediationService`), not the stub driver.** Reason: that is where every existing mediation verb runs (C1), it is the only path with auth, cross-tenant guard, per-tenant token resolution, and DCB audit already composed, and AC4 (workflow closes and reopens a PR end to end) is only reachable through it. The abstraction still gains the verbs (Scope 1 names `IGitPlatformClient` explicitly) so the driver contract is complete; `GitHubPlatformClient` answers them with its uniform "not yet wired" `ServiceUnavailable` posture, each carrying a comment naming 31-3 as the wiring owner. *Rejected:* building a second GitHub REST client inside `Tamma.Platforms.GitHub` so the driver is "real" — duplicates every GitHub call site in a plane nothing consumes, and 31-3 exists precisely to converge these two planes once, not twice.
- **D2 — One route per catalog key, forced by the binding sweep (C2).** Verbs that are one platform call get one route; the PR label add/remove pair becomes **one route** (`PUT …/labels` with `add`/`remove` arrays in the body, mirroring `UpdateIssueRequest.AddLabels/RemoveLabels`) bound to the single `git.pull-request.label` key — so the PR side keeps the story's one label key. The issue side cannot do this (its two routes are live, called by `IssueCallbackClient` and `HttpTriageApplyClient`, and restructuring them breaks deployed engine callers), so it splits into two keys instead. *Rejected:* one shared key for both issue label routes (structurally impossible, C2); consolidating the issue routes (breaks live callers for a naming preference).
- **D3 — New PR routes join the `/api/v1/git/{owner}/{repo}/pull-requests/{n:int}/…` EngineServiceOnly family, not the `/api/engine` group.** The story says "mirroring the existing issue-comment/label shape", which is the *composition* shape (comment + labels + state in one mediation service), not the auth plane. The `/api/v1/git` family already carries guard→token→platform→one-event and the D15 two-line governance idiom; the `/api/engine` group is the legacy callback plane whose routes this story is cataloguing precisely because they grew ungoverned. *Rejected:* new `/api/engine/pr-*` callbacks — reproduces the governance blind spot the story exists to close.
- **D4 — Route + key table (7 PR routes, 7 PR keys; 4 issue keys on 4 existing routes):**

  | `POST /api/v1/git/{owner}/{repo}/pull-requests/{n:int}/reopen` | `effect:git.pull-request.reopen` | 35 |

  All 11 descriptors: `ActionRisk.Mutating`, `Reversible: true` (close↔reopen invert; comments/labels/reviewers/draft are editable on-platform), group `SourceControlWrite` for the PR verbs (beside `git.pull-request.create/merge`) and `IssueTracking` for the issue verbs (beside `git.issue.patch`), `Enforceable: true`, levels written as **integer literals** per 43-11 D2. Review-comment sits at 40 because it *is* review output (story Scope 3; 43-11 zone "Approve PRs").
- **D5 — GitHub verb → API mapping, one deliberate oddity.** Close/reopen: `PATCH /repos/{o}/{r}/pulls/{n}` with `state: closed|open`. PR comment: reuse `PostIssueCommentAsync` (a PR comment IS an issue comment on GitHub — no new integration-service method). PR labels: reuse `AddIssueLabelsAsync`/`RemoveIssueLabelAsync` with the PR number. Review comment: new `PostPullRequestReviewCommentAsync` → `POST /repos/{o}/{r}/pulls/{n}/comments` (`body`, `commit_id`, `path`, `line`, `side`); the head-commit SHA is fetched from the PR when the caller omits it. Request reviewers: **promote** the private best-effort `TryRequestReviewersAsync` (`GitHubIntegrationService.cs:369`) to a public `RequestReviewersAsync` returning a typed `IntegrationResult` — the swallow-errors posture was right for a create-PR side effect and is wrong for a first-class governed verb. **Set-draft: GitHub REST cannot toggle draft; it is GraphQL-only** (`convertPullRequestToDraft` / `markPullRequestReadyForReview`, keyed by the PR `node_id`). Implementation: fetch PR → `node_id` → one `POST /graphql` mutation, isolated in one private helper. *Rejected:* declaring set-draft unsupported on GitHub (the story names it in Scope 1 and the platform does support it, just not over REST).
- **D6 — Non-GitHub drivers return `capability_unsupported`; the compat matrix records it with one new flag.** `PlatformCapability.PrLifecycle = 12` (appended per the enum's own rule), advertised by **GitHub only** in `PlatformKindCapabilityMatrix`. GitLab/Gitea/Forgejo/Null implement the 6 new interface members as one-line `InvalidRequest("capability_unsupported", …)` returns (C4). Their platforms mostly support these verbs — the absent flag records "driver doesn't do it yet", which is exactly what the matrix is for ("the contract those stories must satisfy", `PlatformKindCapabilityMatrix.cs:25-27`). *Rejected:* per-verb capability flags (11 flags for one honesty bit nobody branches on yet); implementing the verbs on Gitea/GitLab now (out of this story's lane; keeps the batch's waves disjoint).
- **D7 — Only 6 members are added to `IGitPlatformClient`, not the story's 8.** `PostReviewCommentAsync` already exists as `CreatePullRequestReviewCommentAsync` (`IGitPlatformClient.cs:81`) and `PostPullRequestCommentAsync` already exists as `CreateIssueCommentAsync` (`:93`, "issue **or PR** number"). Duplicating them under new names would fork the contract. Added: `ClosePullRequestAsync`, `ReopenPullRequestAsync`, `RequestReviewersAsync`, `AddPullRequestLabelsAsync`, `RemovePullRequestLabelAsync`, `SetDraftAsync`. (The label pair stays two methods at the abstraction — interface callers are per-call anyway; the *route* consolidation in D2 is a governance-plane concern.)
- **D8 — All 7 PR verbs get `TammaApiClient` methods now, each `[PerformsEffect(...)]`, in one commit with the pin bumps.** AC4 needs close/reopen from the workflow plane; 41-17 (review output) needs review-comment; posting the rest one story later would move the exact-surface pin (37) and `EffectPerformingSites` (17) twice. `KnownNonEffectClientMethods` (19) is **not touched** — every new method performs an effect, so the D17 ratchet stays still. *Rejected:* adding only close/reopen (two pin moves across two stories for no review benefit).
- **D9 — Enforcing the four engine issue routes is behaviour-preserving at the shipped dial, and that claim is pinned.** New keys sit at 35; the shipped dial is 70; `dial >= level` ⇒ automated — the same day-one-identical argument 43-9 AC2 made, and the anti-no-op pair (a 200-at-defaults test AND a 409-when-tightened test) proves the gate is real rather than absent. Per Amendment 4 the dial governs the LLM path only; these routes ARE the LLM's path (called by `IssueCallbackClient` / `HttpTriageApplyClient` from workflows). Their `WorkflowsManage` auth is unchanged — governance keys on the action, not the caller's badge.

## Risks

- **Set-draft is GraphQL-only on GitHub.** A REST-only client grows a second protocol for one verb. Contained in one private helper with its own canned-response test; if the product owner refuses the GraphQL dependency, GitHub set-draft degrades to `capability_unsupported` and the catalog row stays (declarative until wired) — that choice must be explicit, not silent.
- **Review-comment anchoring is fiddly** (`commit_id`/`path`/`line`/`side`; stale SHAs → 422). Mapped to `InvalidRequest("invalid_anchor")` and surfaced key-free; 41-17 inherits a typed failure it can react to instead of a 500.
- **Enforcing live triage routes.** At dial 70 nothing changes (35 < 70, pinned by the anti-no-op pair). A tenant that lowers its dial below 35 will 409 triage label/comment/create calls — that is the dial doing its job, but `ApplyTriageResultActivity` / `IssueCallbackClient` callers surface it as a typed failure, not a hang; verified by the 409 test.
- **Three stories edit the same count-pin files in one batch.** Merge order is arbitrary but each landing must re-run the two sweeps and re-base the arithmetic in its own commit; the history-line convention in `ActionVocabularyCountTests` exists exactly for this.
- **The stub GitHub driver keeps drifting from the live surface** (C1/D1). The 6 new stub members widen 31-3's remaining gap by design; the comment on each names 31-3 so the wiring story can grep its debt.
- **`git.pull-request.close` at 35 assumes reversibility via reopen.** True only while the branch survives; a close after branch deletion is effectively final. Recorded on the descriptor summary; the level stays 35 per the story's own reasoning ("reversible — reopen exists").
