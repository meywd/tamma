# Implementation Plan — Story 39-4: Document Types Batch 2 — Plan, Design, Review (unified), TriageDecision, Diagnosis, TestSpec

## Scope & Deliverable

When this story is done, `apps/tamma-elsa/src/Tamma.Core/Documents/Types/` contains six new typed documents — `Plan`, `Design`, `Review`, `TriageDecision`, `Diagnosis`, `TestSpec` — each as a payload record (+ nested records/closed enums), an `IDocumentType` implementation (`Validate`/`RenderContract`/`Examples`), and a `DocumentTypeRegistry` registration, taking the registered-count pin from 4 to 10 (vocabulary complete). `Review` is the keystone: one subject-referenced shape with a closed `ReviewDecision` enum and a blocking-issues⇒not-approvable executable rule, plus a fail-loud legacy reader covering BOTH verdict shapes `ReviewAggregationHelper.ParseRoleVerdict` accepts today (parse failure → typed error, never a defaulted "concerns" document). Every type with an existing parser/helper baseline provably subsumes that baseline's rejections and round-trips its passing fixtures. No existing parser, helper, workflow, or prompt cell is touched — diff surface is `Tamma.Core/Documents/**` and `Tamma.Core.Tests/**` only.

## Design Decisions

- **D1 — `ReviewDecision` enum and the legacy mapping table.** Members `Approve | RequestChanges | NeedsDiscussion` (wire `"approve"`/`"request-changes"`/`"needs-discussion"`, `[Wire]` per 39-2 convention). The legacy reader maps, case-insensitively: `"approve"`/`"APPROVE"` → `Approve`; `"REQUEST_CHANGES"` → `RequestChanges`; `"NEEDS_DISCUSSION"` → `NeedsDiscussion`; legacy string `"concerns"` → `RequestChanges` (today "concerns" triggers the revision/discussion round — `RequestChanges` is the revision-triggering decision in the 39-6 lifecycle); code-review's `"COMMENT"` → `NeedsDiscussion` (non-blocking, non-approving). Anything else → `TammaError` code `DOCUMENT.REVIEW.UNKNOWN_DECISION` — never a default. AC8's four-row pin is a strict subset of this table.
- **D2 — Severity vocabulary from the baselines, blocking = Critical.** Survey: plan-review cells emit `critical|major|minor|suggestion`; code-review cells emit `critical|major|minor|style`; `ReviewCommentSeverity` adds `Info`. Closed enum `ReviewSeverity { Critical, Major, Minor, Suggestion }` (wire lowercase), with legacy read aliases `"style"`→`Suggestion`, `"info"`→`Suggestion`, `"blocker"`→`Critical`. `ReviewSeverityExtensions.IsBlocking()` returns true only for `Critical` — AC3 hangs off this single function. The story's illustrative `Blocker|Major|Minor|Nit` is overridden by the survey the story itself mandates ("pick the vocabulary by surveying what the three baselines emit"; `critical` is the dominant spelling in every baseline).
- **D3 — `ReviewSubject` is a closed two-kind union.** `kind: "document"` (requires `documentId` + `documentType`, the latter a valid `DocumentTypeKey` wire) or `kind: "diff"` (requires `repository` + at least one of `prNumber`/`commitSha`). Unknown kind or missing required members → violation. This is how one type serves plan review (subject=document:plan), task review (subject=document:plan of tasks), and code review (subject=diff) — and how "code is not a document type" is honored: the diff gets a *reference*, not a schema.
- **D4 — Legacy compatibility is explicit reader/writer methods, not a lenient schema.** Static `Review.FromLegacyVerdictJson(string json, ReviewSubject subject)` ingests both `ParseRoleVerdict` shapes (string verdict; object verdict with `summary`/`blockingIssues[]` → issues with `severity=Critical`, `category="blocking"`, description = the string). It throws `TammaError DOCUMENT.REVIEW.LEGACY_UNPARSEABLE` on garbage — the pessimistic-default question is settled by the lifecycle (repair ring → `ValidationExhausted`), never encoded in the type. A legacy-ingested review whose issues lack a suggested fix deserializes fine but FAILS `Validate` (violation `ISSUE_MISSING_FIX`) — deliberate: incomplete legacy content goes to repair, it is not laundered. Similarly `Diagnosis.FromLegacyJson`/`ToLegacyJson` bridge the snake_case wire (`analysis_summary`, `suggested_fix`, `affected_files`) the old `ParseDiagnosisResponse` reads, because a camelCase re-serialization would "parse" into an empty (gate-failing) result. Canonical wire stays camelCase everywhere (39-2 D8); legacy spellings live only in the paired reader/writer, pinned by tests.
- **D5 — `Plan` keeps a root-level `files` list for the transition window.** Payload: `tasks[]` each with `id`, `description`, `files[]` (per-task file map), `dependsOn[]`, `testing`; plus optional root `files[]` preserved verbatim. Reason: `PlanValidationHelper.ValidatePlan` requires root `tasks|steps` AND `fileMap|files|filesToModify` — round-trip (AC8) must re-serialize to JSON the old checker still passes. Validator rules run on `tasks[]` only; the root list is carry-through. Sizing (2–8h) is `Decomposition`'s rule (39-3), not `Plan`'s — the README table for Plan lists file map / resolvable deps / testing only.
- **D6 — `TriageDecision` enums = the Story 26-1 vocabulary `TriagePoDecisionHelper` clamps to, with its documented synonym folds.** `TriagePriority { Urgent, High, Normal, Low }` (read aliases `"critical"`→Urgent, `"medium"`→Normal — the helper's own doc: "urgent/critical and normal/medium synonyms map to the same label"); `TriageIssueType { Bug, Feature, Chore, Question, Security, Docs }`; `TriageComplexity { Trivial, Simple, Medium, Complex, Epic }`; `TriageAutomation { TammaAuto, TammaAssist, NeedsHuman }` (wire `"tamma-auto"` etc.). Out-of-vocab → violation `OUT_OF_VOCABULARY` naming field+value (the clamp-and-flag behavior moves to the visible repair/review layer). `reasoning` required non-empty. The helper's `llm-failed`/`unparsed`/`skipped` status markers do NOT enter the payload — they are lifecycle outcomes (`ValidationExhausted` territory), per the story's technical note. **Tension noted:** the producing prompt cell `product_owner/triage-intake.md` instructs a *different* vocabulary (`P0|P1|P2|P3`, `severity`, `ownerRole`) that the helper already clamps away today; this story defines the type from the 26-1 vocabulary per AC6 (story wins) and the prompt divergence is 39-15/39-16 migration scope — record it in story-completion notes, change no prompt here.
- **D7 — `Design` adds alternative IDs without breaking the old reader.** Payload: `summary`, `alternatives[]{id,name,tradeoffs}`, `recommendation` (rationale string), `recommendedAlternativeId`. `DesignParsing.ParseProposal` ignores unknown members and reads `recommendation` as a string, so round-trip is lossless where the old model has fields and additive where it doesn't. Rules: ≥1 alternative (`NO_ALTERNATIVES`), each with non-empty tradeoffs (`ALTERNATIVE_MISSING_TRADEOFFS`), non-empty summary (subsumes ParseProposal's fail-closed rule), `recommendedAlternativeId` must match a listed alternative (`RECOMMENDATION_UNKNOWN_ALTERNATIVE`).
- **D8 — Cross-parser subsumption/round-trip tests (which invoke the old `Tamma.Activities`/`Tamma.ElsaServer` parsers) live in `Tamma.Activities.Tests`, NOT `Tamma.Core.Tests`.** Settled decision (reconciling with 39-2's posture, same as 39-3 D7): `Tamma.Core.Tests` gains NO `ProjectReference` to `Tamma.ElsaServer`/`Tamma.Activities` — it stays dependency-light and Docker-free, holding only the PURE new-type validation tests (Validate rules, enum pins, contract tokens, in-memory round-trip of the typed record against itself). The cross-parser halves — those that call the PUBLIC baselines (`ReviewAggregationHelper.ParseRoleVerdict`, `PlanValidationHelper.ValidatePlan`, `TriagePoDecisionHelper.ParseDecision`, `DesignParsing.ParseProposal`) to prove two-parsers-one-truth — are added to `Tamma.Activities.Tests`, which ALREADY references `Tamma.ElsaServer` (it tests these same helpers) and `Tamma.Core` (the new types). The two INTERNAL parsers (`WriteTestsActivity.ParseTestGenerationResponse`, `AIDiagnosisActivity.ParseDiagnosisResponse`) are in-assembly there, so those round-trip conditions can be asserted directly rather than by shape-comment. `InternalsVisibleTo` is unnecessary and `Tamma.Activities` is not modified. AC9's diff surface is read to admit the cross-parser test files under `Tamma.Activities.Tests`.
- **D9 — Shared dependency-graph check lives in one internal helper.** `Tamma.Core/Documents/Types/DependencyGraphCheck.cs` (internal static): unique-ID, dangling-ref, self-ref, and cycle detection reporting the actual cycle path. If 39-3 lands first with its own helper for `Decomposition`, reuse it and skip creating this file; if 39-4 lands first, 39-3 adopts this one. Either way exactly one implementation exists (lockstep noted in Sequencing).
- **D10 — `Review` models a single reviewer's review; issue `category` stays a free non-empty string.** Aggregation/quorum is 39-7 (explicitly out of scope). Category vocabularies differ per baseline (`bug|security|performance|convention|test-coverage` vs free text in plan-review) — closing it now would guess; require non-empty (`ISSUE_MISSING_CATEGORY`) and leave closure to a later story if 39-7 needs it. Reviewer provenance (role) rides the envelope's `ProducedBy` — not duplicated in the payload (AC2's "via the envelope's `ProducedBy`").

## Implementation Steps

1. **CREATE `apps/tamma-elsa/src/Tamma.Core/Documents/Types/Review.cs`** — the keystone. Follow the `[Wire]`-enum file shape of `Tamma.Core/Agents/AgentRole.cs` for the enums; records use explicit `[JsonPropertyName]` + `required` per 39-2 D8.

   ```csharp
   namespace Tamma.Core.Documents.Types;
   public enum ReviewDecision { [Wire("approve")] Approve, [Wire("request-changes")] RequestChanges, [Wire("needs-discussion")] NeedsDiscussion }
   public enum ReviewSeverity { [Wire("critical")] Critical, [Wire("major")] Major, [Wire("minor")] Minor, [Wire("suggestion")] Suggestion }
   // + XxxExtensions: ToWire/Parse (TammaError DOCUMENT.REVIEW.UNKNOWN_DECISION / UNKNOWN_SEVERITY), ReviewSeverityExtensions.IsBlocking()

   public sealed record ReviewSubject   // D3: closed two-kind union
   {
       [JsonPropertyName("kind")]         public required string Kind { get; init; }          // "document" | "diff"
       [JsonPropertyName("documentId")]   public Guid? DocumentId { get; init; }
       [JsonPropertyName("documentType")] public string? DocumentType { get; init; }          // DocumentTypeKey wire
       [JsonPropertyName("repository")]   public string? Repository { get; init; }
       [JsonPropertyName("prNumber")]     public int? PrNumber { get; init; }
       [JsonPropertyName("commitSha")]    public string? CommitSha { get; init; }
   }
   public sealed record ReviewIssue(
       [property: JsonPropertyName("severity")]     ReviewSeverity Severity,
       [property: JsonPropertyName("category")]     string Category,
       [property: JsonPropertyName("description")]  string Description,
       [property: JsonPropertyName("suggestedFix")] string SuggestedFix,
       [property: JsonPropertyName("file")]         string? File = null,
       [property: JsonPropertyName("line")]         string? Line = null);
   public sealed record Review
   {
       [JsonPropertyName("subject")]  public required ReviewSubject Subject { get; init; }
       [JsonPropertyName("decision")] public required ReviewDecision Decision { get; init; }
       [JsonPropertyName("summary")]  public required string Summary { get; init; }
       [JsonPropertyName("issues")]   public required IReadOnlyList<ReviewIssue> Issues { get; init; }
       [JsonPropertyName("aggregatedFrom")] public IReadOnlyList<Guid>? AggregatedFrom { get; init; } // OPTIONAL panel provenance (39-7 D7): null for single reviews; when present, non-empty + duplicate-free (validated). Defined HERE so it stays inside 39-7's diff surface.
       public static Review FromLegacyVerdictJson(string json, ReviewSubject subject); // D4; throws DOCUMENT.REVIEW.LEGACY_UNPARSEABLE
   }
   ```

## Risks & Mitigations

- **`Review` shape misses a consumer's need (39-5/39-6/39-7 all read it).** Mitigation: every payload member maps to a named downstream reader — `decision` → 39-5 guardrail + 39-6 REVIEW→REVISE branch; `issues[].severity` → the blocking guardrail; `subject` → 39-7 panel grouping and code-review routing; `summary` → escalation lineage display. Anything without a consumer stayed out (no quorum fields, no reviewer id in payload).
- **Decision-mapping choice for `"concerns"`/`"COMMENT"` proves wrong for 39-6 routing.** Mitigation: the mapping lives in ONE function (`FromLegacyVerdictJson` via the D1 table) and is pinned by a `[TestCase]` table — changing a row is a one-line, test-visible edit, and no legacy string is stored in documents (only enum wires), so no data migration ever hinges on it.
- **Referencing `Tamma.ElsaServer` from `Tamma.Core.Tests` drags Elsa packages into the unit-test build.** Mitigation: precedent exists (`Tamma.Activities.Tests` does exactly this to test the same helpers); the referenced classes are pure static (no Elsa runtime touched at test time). Fallback if the build graph objects: move only the cross-parser assertions behind replicated, source-named conditions (the D8 internal-parser treatment) — no production code changes either way.
- **Vocabulary tightening breaks un-migrated producers silently.** Mitigation: AC9 — no consumer rewiring; old parsers keep running untouched until 39-14/39-15, and the story-completion notes (step 12) enumerate every deliberate divergence with affected prompt cells named (`triage-intake` P0-vocab, `style`/`info` severities, legacy fix-less issues).
- **39-3/39-4 land order scrambles the registry pin and graph helper.** Mitigation: both are single-file, conflict-visible edits (registry list + pin test + ratchet list); Sequencing section defines the rule for whichever lands second.
