# Implementation Plan — Story 39-12: Pilot Migration — IssueDecomposition onto the Lifecycle

## Scope & Deliverable

When this story is done, `IssueDecompositionWorkflow` (DefinitionId `issue-decomposition`, unchanged, so no dispatch call site moves) is a thin binding over `DocumentLifecycleWorkflow`: it assembles the issue context (the `consumes` side), dispatches `document-lifecycle` with `documentType = "decomposition"` and the `(senior_developer, decompose-issue)` producer cell, and mirrors the legacy `DECOMPOSITION.*` events onto the lifecycle's typed exits. The hand parser (`DecompositionParsing`), its models, and the `DecompositionError` Finish terminal are deleted; every non-success exit is a typed lifecycle outcome escalated with lineage; the workflow declares `[ResumeBehavior]` and passes the 39-10 structural gate with no allowlist entry; accepted `Decomposition` documents and their `Review`s are readable through the 39-11 store for Stories 2-15/2-16. The whole 39-2..39-11 stack is thereby proven end-to-end on one production workflow.

## Design Decisions

- **D1 — The binding keeps the public surface byte-stable: DefinitionId, inputs, outputs.** `builder.DefinitionId = "issue-decomposition"`, `builder.Version = WorkflowVersions.ComputedVersion`, same inputs (`sessionId`, `issueId`, `issueTitle`, `repository`, `issueNumber`, `workItemJson`, `tenantId`), same outputs (`sessionId`, `status`, `decomposition`, `subtaskCount`, `contextIds`) plus additive `outcome`/`documentId`. `status` stays `"completed"` on acceptance (compat) and gains `"rejected"`/`"escalated"` (the old failure path exposed no outputs at all — strictly additive). `BuildWorkItem` is kept verbatim (still the work-item composer for both the context scan and the producer variables). Dispatch call sites (orchestrator/triage routing dispatch by definition id at runtime; no compiled call site exists — verified by grep) are untouched, per the story's migration-order note.
- **D2 — "No bespoke parse/branch/terminal" means: no parse, no success-flag gate, no error Finish; typed-result routing is allowed.** The binding contains ZERO `Finish` activities and zero parsing. It does contain exactly three `FlowDecision`s, each routing a TYPED value, never raw LLM output: `FreshRun` (39-10 re-entry position == `Produce` → run the pre-produce region), `LifecycleAccepted` (lifecycle result `status == "accepted"`), and `WasCompleteReEntry` (suppress duplicate `DECOMPOSITION.COMPLETED` when re-entry short-circuited, position == `Complete`). The rewritten structure test pins this exact `FlowDecision` id set and asserts every graph leaf is the single output-exposure region — the AC3 "no dead ends" structural proof. If story text is read as forbidding ALL branches, the 39-10 idempotency rule (no double emissions) and AC4 (compat events) are unsatisfiable; the tension is resolved as "no branch that impersonates the quality decision" — all quality routing lives inside `document-lifecycle`.
- **D3 — Legacy events are mirrored by the binding at the equivalent transitions.** `DECOMPOSITION.STARTED` + `DECOMPOSITION.CONTEXT_GATHERED` before dispatching the lifecycle (fresh runs only — a re-entry is not a new decomposition); `DECOMPOSITION.COMPLETED` (with `subtaskCount`) when the lifecycle exits `accepted` on a fresh/resumed run; `DECOMPOSITION.FAILED` when it exits `rejected` OR `escalated`, with `Detail` naming the typed outcome wire (`validation-exhausted` etc.) so the LOUD event now points at a typed escalation, not a dead terminal (AC4's parenthetical). `DecompositionEvents.cs` and `EmitDecompositionEventActivity.cs` are NOT modified — same constants, same data shape (`subtaskCount`/`detail`), so consumers/dashboards see no regression. The generic `DOCUMENT.*`/`APPROVAL.*`/`ESCALATION.*` events are emitted by 39-6/39-8 machinery inside the lifecycle instance — this story emits none of them.
- **D4 — The accepted payload comes out of the lifecycle as a `documentJson` output — a 39-6 hook, filed back, not a decomposition special case.** 39-6's planned outputs (`status`/`outcome`/`documentId`/`lifecycleResult`) do not include the accepted body, which this binding needs for the `decomposition` output and `subtaskCount`. Per the story's technical note ("the fix belongs in THOSE components"), add `documentJson` (the accepted revision's payload) to `DocumentLifecycleWorkflow`'s terminal `SetOutputs` + its structure-test pin, coordinated with 39-6 (one-line addition if already merged). Fallback if vetoed: a read through 39-10's `ILifecycleReEntryService.GetDocumentBodyAsync(documentId)` — worse (extra service hop), so the output is the plan of record.
- **D5 — Contract gate (AC7): teach the dispatch enumeration to see THROUGH lifecycle bindings, then update the binding entry's parser authority.** After the rewrite, `EnumerateAllDispatchPairs` no longer discovers `(senior_developer, decompose-issue)` (the pair rides `document-lifecycle` inputs), which would trip ContractBindingTests' clause-(c) staleness guard on the kept `Bindings` entry AND `EveryKnownContributingWorkflow_StillEmitsPairs` (the set contains `IssueDecompositionWorkflow`). Fix generically: extend `ScanLlmCallDispatches`/`EnumerateAllDispatchPairs` to ALSO walk `DispatchWorkflow` sites whose definition id is `"document-lifecycle"` and materialize `(producerRole, producerAction)` from the Input delegate — the same materialization that resolves the current `DecomposeIssueLlm` lambda (constants via `AgentRole.SeniorDeveloper.ToWire()` / `AgentAction.DecomposeIssue.ToWire()` materialize fine). This keeps the pair discovered, attributed to `IssueDecompositionWorkflow` (its `ExpectedContributingWorkflows` entry survives with an updated comment), keeps the `Bindings` entry non-stale, and automatically covers 39-13/14/15 bindings. The entry itself changes `Parser` to `"DecompositionDocumentType.Validate"` with a comment naming `Tamma.Core.Documents.Types.DecompositionDocumentType` as the authority — token groups unchanged (39-3 D2 pinned the wire shape verbatim: `"summary"`, `"subtasks"`, `"id"`, `"title"`, `"description"`, `"acceptanceCriteria"`, `"estimateHours"`, `"complexity"`, `"dependsOn"`).
- **D6 — Full parser retirement, no adapter, no producer-side normalization in the pilot.** Delete `DecompositionParsing.cs`, `Models/DecompositionModels.cs` (`IssueDecomposition`/`Subtask`/`SubtaskComplexities` — grep-verified: no consumers outside the old workflow/parser/tests), and `DecompositionParsingTests.cs`; prune the decomposition fixture rows from 39-3's `BaselineSubsumptionTests`/`RoundTripCompatibilityTests` (their transition-window purpose — "old parser still parses" — ends when the old parser ceases to exist; the validator-side coverage stays in `DecompositionDocumentTypeTests`). The strict validator (`UNKNOWN_COMPLEXITY`, `SIZING_OUT_OF_RANGE`) replaces the parser's synonym folding; a drifting label now drives a repair/revise turn instead of silent normalization. If pilot telemetry shows churn, the fix is a policy/seam change filed to 39-6/39-9 (their plans anticipate exactly this), never re-leniency here.
- **D7 — Resume declaration: `[ResumeBehavior(ResumeMode.LatestStateReEntry)]`, with `ComputeReEntryPositionActivity` in the binding graph; allowlist entry burned.** The binding itself never suspends on a bookmark (the accept-gate suspend happens inside the dispatched `document-lifecycle` child instance; the parent waits via `WaitForCompletion=true`), so `BookmarkSuspend` would be dishonest. 39-10 clause (c) requires the re-entry node for this mode — and the position output is exactly what D2's `FreshRun`/`WasCompleteReEntry` gates consume: position ≠ `Produce` skips the context scan and the STARTED/CONTEXT_GATHERED emissions; the child lifecycle performs its own re-entry (skip produce/review, resume at review, or short-circuit accepted). Remove `IssueDecompositionWorkflow` from 39-10's `LegacyResumeAllowlist` — the first burn-down, satisfying AC6's "WITHOUT an allowlist entry".
- **D8 — Rules, reviewer, repair: all policy passthrough, nothing hardcoded.** The binding gains an optional `acceptanceRulesJson` input forwarded verbatim to the lifecycle (empty → `AcceptanceRules` defaults per 39-6 D4 / 39-5 AC5); reviewer selection arrives via the lifecycle's `"document-review"` dispatch driven by rules (39-6 D10 / 39-7) — the binding names no reviewer cell (story technical note). The 39-9 managed-layer repair ring stays OFF (its `EnabledDocumentTypes` defaults empty); all pilot tests run with it off, per the story's "the pilot must pass with repair OFF". The lifecycle's own bounded repair/revise rounds are governed by the resolved rules.
- **D9 — AC1's `consumes/produces` declaration is realized in 39-2's `WorkflowDocumentInterface` list.** The `issue-decomposition → decomposition` entry (seeded `Provisional` by 39-2 D6) gets its flag flipped off — the declaration is now backed by a real lifecycle binding. `AmbiguityAboveThreshold` is unreachable for this type (decomposition carries no ambiguity score, no threaded score input) — noted, not special-cased.

## Risks & Mitigations

- **The entire prerequisite stack is unlanded.** Largest risk by far; this story is intentionally the integration proof.
