# Implementation Plan — Story 39-7: Review Producers — single reviewer + panel onto the unified Review type

## Scope & Deliverable

When this story is done, `apps/tamma-elsa/src/Tamma.ElsaServer/Workflows/` holds three new dispatchable workflows: `SingleReviewerWorkflow` (`DefinitionId = "review-single-reviewer"`) — one policy-selected `(role, action)` `llm-call` per run yielding exactly one **validated** unified `Review` envelope with a bounded validation/repair ring and a typed failure on exhaustion (never a defaulted `"concerns"` review); `PanelReviewWorkflow` (`DefinitionId = "review-panel"`) — fans out N single-reviewer runs over a policy-configured roster, persists every member review, and aggregates via a pure helper into an aggregate `Review` referencing its member ids; and `DocumentReviewWorkflow` (`DefinitionId = "document-review"`) — the thin router honoring the definition-id contract 39-6 D10 pinned for its REVIEW stage. Aggregation/quorum is pure logic over `IReadOnlyList<Review>` in `Workflows/Helpers/`, default-configured to reproduce `ReviewAggregationHelper.AggregateVerdicts`, with a parity harness replaying the recorded verdict fixtures as 39-14's retirement evidence. `PlanReviewWorkflow` and the triage panel are untouched.

## Design Decisions

- **D1 — Three workflows, not one mode-switched producer.** `SingleReviewerWorkflow` (`"review-single-reviewer"`, AC1), `PanelReviewWorkflow` (`"review-panel"`, AC2), and `DocumentReviewWorkflow` (`"document-review"`) — the last is a ~120-line router that reads `ReviewerSelection.Mode` from `acceptanceRulesJson` (fallback `AcceptanceDefaults.Rules`) and dispatches one of the two producers, mapping outputs onto 39-6 D10's contract (`success`/`reviewJson`/`reviewDocumentId`). Rationale: AC1/AC2 each demand an independently dispatchable producer; 39-6 demands one stable entry definition id; a mode input inside one workflow would tangle the panel roster graph into the single path. The story leaves this open ("decided in design") — this is the decision.
- **D2 — Panel fan-out = static 7-role superset roster with per-role membership gates, each member dispatching the single-reviewer sub-workflow.** The roster is the domain of `RolePhaseMap.GetReviewActionForRole` (architect, senior_developer, security, developer, tester, devops, product_owner) as a `static readonly AgentRole[]` (the `TriagePanelReviewWorkflow.PanelRoles` idiom). Elsa graphs are static, policy rosters are dynamic — so each role's chain is `InPanel? (FlowDecision on configured PanelRoles) → DispatchWorkflow("review-single-reviewer") → CaptureMemberResult → next role`. "N single-reviewer runs" (AC2) is literal: dispatch-per-member reuses ONE implementation of dispatch/validate/persist, so member reviews are persisted with lineage for free. Vocabulary static, composition dynamic.
- **D3 — Reviewer action derivation lives in a new pure helper, not in `RolePhaseMap`.** `ReviewerSelectionHelper` (new, `Workflows/Helpers/`): document subject → `RolePhaseMap.GetReviewActionForRole(role)`; diff subject → a local `GetDiffReviewActionForRole` map (senior_developer/developer → `CodeReview`, architect → `CodeReviewArchitecture`, security → `CodeReviewSecurity`, tester → `CodeReviewCoverage`; devops/product_owner → `TammaError REVIEW.PRODUCER.ROLE_NOT_ON_DIFF_PANEL`). An explicit `reviewerAction` input overrides derivation; either way the pair is validated at Init via `AgentRoleExtensions.Parse`/`AgentActionExtensions.Parse` + `RolePhaseMap.IsRoleEligibleForPhase` (fail-loud `TammaError REVIEW.PRODUCER.INVALID_REVIEWER`) — AC4's runtime half. `RolePhaseMap` stays untouched (outside AC9's diff surface); the helper's map is drift-pinned by test instead.
- **D4 — Reply mapping is canonical-first, legacy-cell-shape second, garbage → typed violations — never a default.** `ReviewProducerHelper.MapReviewerReply(llmResponse, subjectJson)`: (1) try canonical `Review` deserialization via `DocumentJson.Options`; (2) else map the CURRENT cell shape — top-level `issues[]` (`severity`→`ReviewSeverity` with 39-4's read aliases, `category`, `issue`→`Description`, `recommendation`→`SuggestedFix`, `task`→`File`-adjacent context folded into description) + the verdict half delegated to `Review.FromLegacyVerdictJson` (39-4 D4); (3) unparseable → a violations list, NOT a review. The full-cell issues[] mapping lives HERE (39-4 scoped its reader to `ParseRoleVerdict` parity; the cell-shape concern is workflow-layer). Every mapped payload then runs `DocumentTypeRegistry.Resolve(DocumentTypeKey.Review).Validate(...)` — blocking-issues⇒not-approvable enforced by the 39-4 validator, per AC1. `ParseRoleVerdict`'s parsing half is thereby superseded; `PlanReviewWorkflow` keeps calling it untouched until 39-14.
- **D5 — Bounded repair inside the single-reviewer producer; bounds from `AcceptanceRules`.** Invalid/unparseable output consumes a repair attempt: violations (domain-phrased) + `ReviewDocumentType.RenderContract()` are folded via `ValidationFeedbackHelper.AppendFeedback` into a declared feedback variable (input `feedbackVariableName`, default `workItemJson` for review cells — every reviewer cell declares it; a supplied-but-undeclared variable is silently dropped at render, the `ValidationFeedbackHelper` lesson) and the SAME dispatch node re-runs. `attempts >= MaxValidationRepairAttempts` (from `acceptanceRulesJson` input, `AcceptanceDefaults` fallback — 39-6 D4 discipline) → outputs `success=false`, `failureKind="validation-exhausted"` (llm-call `success=false` likewise consumes an attempt; exhaustion of only-failed-calls → `failureKind="llm-failed"`). The 39-6 caller maps these to `ValidationExhausted`/`ReviewUndecidable` — this workflow emits the typed failure, it does not choose the lifecycle outcome.
- **D6 — Aggregation vocabulary: `PanelDecisionRule { Unanimous, Majority }` + `MinimumUsableReviews`; the blocking veto is an INVARIANT, not a knob.** Pure `ReviewPanelAggregation` helper. Decision computed over usable members' `ReviewDecision`s; any member carrying a blocking issue (`ReviewSeverityExtensions.IsBlocking()`) forces the aggregate to `RequestChanges` regardless of rule — structurally re-proven because the aggregate's `Issues` are the concatenation of member issues, so an `Approve` aggregate with a member's Critical issue would fail `ReviewDocumentType.Validate` (`APPROVE_WITH_BLOCKING_ISSUES`). **Default config = Unanimous + MinimumUsableReviews = roster size ⇒ `AggregateVerdicts` parity.** Documented deliberate divergences (AC3/AC8): (a) empty panel → `EmptyPanel` undecidable (old: `All()` on empty ⇒ approved — a bug we do not reproduce); (b) garbage member → failed member → `BelowQuorum` undecidable (old: laundered to `"concerns"` ⇒ pessimistic non-approve); (c) `NeedsDiscussion` counts as non-approve (matches old `"concerns"`). Triage gap for 39-15: `TriagePanelAggregationHelper`'s `partial` maps to Decided-with-`failedRoles`-recorded once `MinimumUsableReviews < roster`; its verdictless PO-decision phase becomes lifecycle ACCEPT — recorded as a finding, not built here.
- **D7 — Aggregate provenance: additive optional `aggregatedFrom` member on the `Review` payload (lockstep with 39-4).** AC2 requires the aggregate to reference member review ids in its provenance. The envelope has only single-parent lineage, so the payload carries `[JsonPropertyName("aggregatedFrom")] IReadOnlyList<Guid>? AggregatedFrom` (null for single reviews; validation: when present, non-empty and duplicate-free) plus `ProducedBy.WorkflowDefinitionId = "review-panel"` marking the producer. **Tension noted:** AC9's diff surface ("new producer workflows + helpers + tests + `WorkflowVersions.cs` registration") does not include `Tamma.Core/Documents/Types/Review.cs`; AC2's provenance requirement wins (story text). Since 39-4 is unimplemented, the preferred resolution is folding the field into 39-4's implementation before it lands (zero diff here); if 39-4 lands first, this story makes the one additive out-of-surface edit, called out in the PR.
- **D8 — Persistence pending 39-11 = event stream + outputs.** Each member and aggregate envelope is serialized in full into its `DOCUMENT.PRODUCED.SUCCESS`/`DOCUMENT.VALIDATED.SUCCESS` event `DataJson` (durable in `domain_events` via the existing drain) and returned in workflow outputs (`memberReviewsJson`). "Never discarded post-aggregation" (AC2) holds because member emission happens inside each single-reviewer run, before aggregation exists. 39-11 later adds the queryable store without changing this contract.
- **D9 — Drift-guard treatment: shared `DataDrivenDispatchAllowList` + a producer-pair classification test with its own supplementary table.** The single-reviewer llm-call dispatch is data-driven (role/action from inputs), so it cannot materialize a constant pair for `TaxonomyDriftBuildTests` — it joins 39-6 D3's `DataDrivenDispatchAllowList` (whichever of 39-6/39-7 lands first CREATES the list per that spec; the other appends — lockstep). AC4's build-gate half: a new test inside `ContractBindingTests` iterates `ReviewerSelectionHelper.AllDispatchablePairs` (the 7 document pairs + 5 diff pairs) and asserts each is in `Bindings` ∪ `IntentionallyUnbound` ∪ a NEW `ReviewProducerDispatchablePairs` justified table. The new table exists because pairs only reachable via policy (e.g. `(architect, code-review-architecture)`) are emitted by no compiled site, and adding them to `IntentionallyUnbound` would trip its staleness guard. A reviewer cell reachable by the producers but absent from all three tables fails the build. Neither new workflow joins `ExpectedContributingWorkflows` (they contribute zero constant pairs — documented inline).
- **D10 — No reviewer-to-reviewer discussion rounds.** The PlanReview rebuttal/PO-decision phases are deliberately NOT ported (story technical note: revision-with-notes is the 39-6 lifecycle's REVISE, performed by the reviewed producer). Any genuine need discovered during 39-14 is recorded as a `.dev/findings/` entry, not built speculatively.
- **D11 — Panel decision-rule knob home: workflow input now, `ReviewerSelection` later.** 39-5's planned `ReviewerSelection` has `Quorum` but no decision-rule member. The panel workflow takes `panelDecisionRule` input (wire `"unanimous"`|`"majority"`, default `"unanimous"`) and maps `ReviewerSelection.Quorum` → `MinimumUsableReviews` (null → roster size). Recommend 39-5 adds `DecisionRule` to `ReviewerSelection` before landing (open question); when it does, the router threads it and the input becomes the override.
