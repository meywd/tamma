# Implementation Plan — Story 39-15: Remaining Producers Migration — Triage, TestSpec, TaskCreation, Diagnosis

## Scope & Deliverable

When this story is done, every remaining document-producing workflow is a thin binding over `DocumentLifecycleWorkflow`: `task-creation` produces a typed `Plan` (task breakdown), `test-case-creation` produces a `TestSpec` with lineage to its `Plan`, a new `debug-diagnosis` binding produces `Diagnosis` documents that `DebuggingWorkflow`'s untouched fix/retry loop consumes, and the triage family collapses onto one `TriageDecision` lifecycle per item (`triage-context-gathering` → a `Findings` binding on the 39-13 Research recipe; the 4-role panel becomes the lifecycle REVIEW stage via 39-7; the PO decision becomes the ACCEPT gate). The `ValidationErrors`/`OutErr` retry plumbing, `TriagePanelReviewWorkflow`, `TriagePanelAggregationHelper`, and `AIDiagnosisActivity`'s hand-built prompt path are deleted; `TriageContextHelper`/`TriagePoDecisionHelper`/`TriageItemCycleHelper` shrink to adapters over the typed deserializers. The build-time graph check then asserts the universal property: every document-producing `llm-call` pair rides a lifecycle binding, the `ContractBindingTests` allowlist holds only genuinely-prose/code cells, and the 39-10 resume allowlist is empty.

## Design Decisions

- **D1 — Wave order per the story's technical note; every binding instantiates the 39-14 PlanGeneration recipe verbatim.** TaskCreation → TestCaseCreation (near-clones) → Debug diagnosis (careful seam) → Triage family (most workflows). All DefinitionIds unchanged (`task-creation`, `test-case-creation`, `debugging`, `issue-triage`, `triage-item-cycle`, `triage-context-gathering`, `triage-po-decision`) so no compiled call site moves — SingleIssueCycle L317/L494 and the TDD/CI `"debugging"` dispatches stay byte-stable. Each binding: `[ResumeBehavior(ResumeMode.LatestStateReEntry)]`, `ComputeReEntryPositionActivity`, exactly one `DispatchWorkflow("document-lifecycle")` with constant `producerRole`/`producerAction` (so the 39-12 D5 binding walk materializes the pair), typed exit routing via a pure helper, zero `Finish`, zero `DispatchWorkflow("llm-call")`, zero parsing, legacy output names preserved + additive `outcome`/`documentId`/`status`.
- **D2 — TaskCreation produces documentType `"plan"` (39-4's mapping of `create-tasks`), disambiguated by producer, consuming the architect's `Plan`.** Cell `(senior_developer, create-tasks)`; declared `consumes: [plan] / produces: plan`. The `planJson` input remains the runtime carrier (the parent passes it); the consumed plan's `documentId` — resolved via `FetchLatestAcceptedDocumentActivity` (39-14's activity) when the store has it — threads into the lifecycle's lineage anchor (`parentDocumentId`, the 39-2 envelope member for consumed-parent links; `supersedesDocumentId` stays reserved for revision chains). **Noted ambiguity, filed as an open question to 39-4/39-11:** two accepted `"plan"` documents per issue (system plan and task breakdown) make `GetLatestAcceptedAsync("plan")` ambiguous — the disambiguator is `ProducedBy.WorkflowDefinitionId` (`"plan-generation"` vs `"task-creation"`); 39-11's read API needs a producer filter, or 39-4 mints a distinct `"task-plan"` key. This plan proceeds on the producer-filter resolution and does not fork the type. Feedback carrier: `feedbackVariableName = "contextFindings"` (the declared template variable the current retry comment names — the `ValidationFeedbackHelper` render-drop lesson). Legacy output `tasksJson` = the `tasks` array raw text projected from the accepted `Plan` documentJson (`""`→`"[]"` on non-accept) so the parent's tasks-gate (~L1358, bare-array read) and empty-tasks failure edge (L905-911) fire unchanged; `error` = typed failure detail.
- **D3 — TestCaseCreation produces `"test-spec"`, consumes `[plan]`, and the task-ID binding check is a cross-document validation seam filed back to 39-2/39-6 — not a binding-local branch.** Cell `(tester, write-tests)`; `parentDocumentId` = the consumed task-breakdown `Plan`'s id (input `tasksJson` remains the runtime carrier; store lookup per D2's producer filter fills the lineage anchor). AC2's "a case referencing a nonexistent task is a validator failure flowing through the rings" cannot be expressed payload-only (`TestSpecDocumentType.Validate` sees no `Plan`), so: add to `DocumentLifecycleWorkflow` an optional input `validationContextJson` (default `""` = skip) that VALIDATE forwards to a new default-implemented interface member `IDocumentType.ValidateWithContext(payload, contextJson)` (DIM defaulting to `Validate(payload)`); `TestSpecDocumentType` overrides it to check every `case.taskId` against the Plan's task ids (violation `CASE_UNKNOWN_TASK_ID`, message naming the id — domain-phrased for the repair ring). The binding passes the consumed plan JSON as the context. Both edits are additive, lockstep with the 39-2/39-6 owners, one structure-test pin each — the 39-13 D6 "fix the generic layer, never a family special case" discipline. Feedback carrier: `"testTarget"` (the declared variable the current retry comment names). Legacy output `testCasesJson` = the `testCases` array raw text from the accepted `TestSpec`.
- **D4 — Debug diagnosis: a NEW `DebugDiagnosisWorkflow` binding (`DefinitionId "debug-diagnosis"`, documentType `"diagnosis"`, cell `(senior_developer, debug-rootcause)`); `DebuggingWorkflow` keeps its loop and consumes the typed document.** Today's `AIDiagnosisActivity` hand-builds a prompt and calls `MediatedLlmText` with role `senior_developer` — migrating production onto the lifecycle simultaneously restores the llm-call-mediation invariant (registry cell, not ad-hoc prompt). The binding's producer variables carry the serialized debug context (`errorContext`/`codeContext`/`gitContext`/`testContext`/`reproductionContext`/`previousAttemptsJson` folded into the `debug-rootcause` template's declared variables — verify declared names against the template at implementation, folding into an existing carrier if undeclared, per the render lesson). Inside `DebuggingWorkflow`: `aiDiagnosis` + `serializeDiagnosis` + the `diagnosisProduced` parse gate are replaced by `DispatchWorkflow("debug-diagnosis")` + a typed-exit gate; on accept, `hypothesesJson` is populated via `Diagnosis.ToLegacyJson` (39-4's snake_case bridge) so `SelectHypothesisActivity`/`RefineHypothesisActivity`/`CompileDebugReportActivity` and the fix/test/refine loop are UNTOUCHED (AC4's "retry orchestration stays"). Per-attempt lineage: the binding takes optional `supersedesDocumentId`; `DebuggingWorkflow` threads the prior attempt's diagnosis id on re-diagnosis so attempt N's `Diagnosis` supersedes attempt N−1's (the technical note's time-travel). `DEBUG.DIAGNOSIS.SUCCESS/FAILED` keep emitting at the same transitions. `TddWithDebugRetryWorkflow`/`CiWithDebugRetryWorkflow` are edited minimally: `debugging` gains an additive `diagnosisDocumentId` output; the orchestrators capture it and, on the escalation path, read the accepted `Diagnosis` through `FetchLatestAcceptedDocumentActivity` for the escalation detail (the AC4 "typed read from the store instead of an informal parse") — their retry loops, budgets, and `debuggerEscalated` health gate are untouched. **Scope note:** `RefineHypothesisActivity` mutates hypothesis state code-side (loop bookkeeping, not document production) and stays; if implementation finds it makes its own LLM call, that call is out of this story's diagnosis-production scope and is filed, not migrated. Likewise `Tamma.Activities/TDD/WriteTestsActivity.cs` produces CODE (git-validated), not a `TestSpec` — untouched.

## Risks & Mitigations

- **Broadest blast radius in the epic (7 workflows, 4 helpers, ~12 test suites).** Mitigation: the recipe is fourth-generation (39-12→13→14); the wave order lands cheap near-clones first; each family is independently green before the next starts.
- **Triage restructure changes panel semantics (input-side panel → REVIEW-of-draft).** The panel now critiques a draft decision instead of feeding the PO raw assessments — a real behavioral change. Mitigation: D5 documents it; the producer variables still carry `contextJson` (Findings) so the draft is context-informed; suggestedLabels' informational role moves into review issues; recorded in `.dev/findings/` + story-completion notes; quality regressions are rules-tunable (rounds/roster), not code.
- **Shared-cell rebind (`developer/context-scan`) and the two-plans-per-issue ambiguity.** Mitigation: both carried as explicit open questions with named fallbacks (D5, D2); neither blocks the wave order's first three families.
- **Cross-document validation seam rejected by 39-2/39-6 owners.** Mitigation: DIM default keeps every existing type source-compatible; fallback (worse, documented): the binding pre-validates task-IDs and injects a synthetic violation via the repair ring's feedback input — the check stays in the rings either way, never a parse branch.
- **`triage-intake`/`debug-rootcause` template rewrites race 39-16.** Mitigation: contract blocks are regenerated from the document types in both orderings; whoever lands second reconciles mechanically (the blocks are generated content, 39-16's single-source design).
- **Double emissions / double apply on re-entry.** Mitigation: D6 gates mirrors on re-entry position; D8's apply-idempotence gate; ExecutionTests (e) pins exactly-once terminals.
