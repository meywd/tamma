# Implementation Plan — Story 39-18: Real-Time Channels — workflow↔orchestrator and user↔orchestrator (SignalR)

## Scope & Deliverable

When this story is done, `Tamma.Api` hosts two SignalR hubs: `OrchestratorChannelHub` (engine/agent traffic, service-principal/orchestrator-only, tenant-partitioned) and `UserChannelHub` (dashboard users, tenant+user-folded groups derived server-side from the authenticated principal). A closed, drift-tested channel message set lives in `Tamma.Core/Documents/Channels/` (reusing 39-5's `AcceptanceRequest`/`AcceptanceDecision`, adding `TaskAssigned`, `EscalationRaised`, `EscalationDisposition`, `GuidanceQuery`/`GuidanceReply`, `AgentConversationMessage`). Every request/escalation/guidance/task message is persisted to a new per-tenant `channel_outbox` table BEFORE any hub send, with connect-time replay of unacked rows and idempotent ack — the transport is never source of truth, and decisions land ONLY through 39-8's idempotent resume surface (the hub's decision methods delegate to it, never apply anything themselves). The 39-6 engine publishes via a new engine→API hop (`POST /api/engine/channel/outbox`, mirroring the DCB event drain), and an ADR records the SSE-vs-SignalR scope split and the single-instance stance. This story also ships `PersistedOrchestratorInbox` — the production implementation of 39-17's `IOrchestratorInbox` over the same `channel_outbox`, which is how the resident in-process orchestrator agent receives work (the SignalR hub is the remote/test client path; both read the one outbox).

## Design Decisions

- **D1 — SignalR (ASP.NET Core native), zero new server packages; ADR records the scope split and the scale-out stance.** `Tamma.Api` is `Microsoft.NET.Sdk.Web` on net8.0 — server-side SignalR ships in the shared framework (`AddSignalR()`/`MapHub<T>()`); only test/client sides need `Microsoft.AspNetCore.SignalR.Client`. No concrete constraint rules SignalR out (per the story's default). CREATE `.dev/decisions/story-39-18-realtime-channels-design.md` (naming per `story-31-1-git-platform-design.md`): (a) CLAUDE.md's "SSE over WebSocket" stands for one-way streaming (`AdminTenantEventsSseEndpoint`, `/api/engine/events/state|logs` remain SSE); SignalR is scoped to bidirectional request/decision conversation only; (b) fan-out is single-instance in-process, same as `ILlmRunStreamBus` — cross-process (Redis backplane / Postgres LISTEN-NOTIFY) is the SAME deferred open decision, decided once for both; the outbox makes single-instance safe, just slower on failover (say it loudly, per the story).
- **D2 — BOTH hubs are hosted in `Tamma.Api`; "engine-internal surface" is honored as a TRUST POSTURE, not a process boundary (story-vs-repo tension, recorded).** The story's technical note reads as "orchestrator hub in the engine like the `*ResumeEndpoint` family", but `Tamma.ElsaServer` references only `Tamma.Activities` (no tenant DB, no user auth) and the engine ALREADY crosses to the API for durable writes (`EventPersistenceMiddleware` → `POST /api/engine/events`). An engine-hosted hub could not persist or replay the outbox. Resolution honoring the note's intent: two SEPARATE hub classes (never one hub with per-method role checks), the orchestrator hub gated by a service-principal/orchestrator-only policy (the same trust class as `EngineServiceOnly` — the posture of the resume family), mounted at `/hubs/orchestrator` and excluded from public API docs/nginx exposure; workflows still "publish via the engine": 39-6's `PublishAcceptanceRequestActivity` → this story's `EngineChannelPublisher` (in `Tamma.Activities`) → `POST /api/engine/channel/outbox` (`EngineServiceOnly`) → outbox row + hub fan-out. Recorded in the ADR.
- **D3 — Message contracts: new records in `Tamma.Core/Documents/Channels/`; 39-5's acceptor records are REUSED, never redefined.** `AcceptanceRequest`/`AcceptanceDecision` already have one canonical home (`Tamma.Core/Documents/Policy/`, 39-5 steps 3–4) — AC1's list is satisfied by reference. NEW: `TaskAssigned`, `EscalationRaised`, `EscalationDisposition`, `GuidanceQuery`, `GuidanceReply`, `AgentConversationMessage`, wrapped in a `ChannelEnvelope` (message id = `UuidV7`, tenant id, `[JsonPolymorphic]` `kind` discriminator over a closed derived set, count-pinned). `EscalationRaised` embeds the 39-8 lineage payload (`escalationId`, outcome wire name, serialized `DocumentLineage`) — one shape, shared with the `ESCALATION.TRIGGERED` event data. A new `[Wire]` enum `ChannelAudience { orchestrator | user }` names the two channels (deliberately distinct from 39-8's three-member `ApprovalChannel`, which classifies who RESUMED, not where a message travels). The decision-session id inside `AcceptanceRequest` IS the 39-8 bookmark session id (already pinned by 39-5/39-6) — no join table.
- **D4 — Outbox: one tenant-resident `channel_outbox` table, one row per recipient, idempotent ack.** Copy the `EmailOutboxMessage` shape (status transitions, lease semantics) minus SMTP: `Id` (the `ChannelEnvelope` message id, UuidV7 → time-ordered replay without a sequence column), `TenantId`, `Audience` (wire string), `RecipientUserId` (`NULL` = the tenant's orchestrator agent; user-audience messages fan out at WRITE time to one row per 39-20-eligible recipient, so ack is per-user), `Kind`, `PayloadJson` (jsonb), `DecisionSessionId?`, `Status` (`pending | delivered | acked`), `Attempts`, `CreatedAt/DeliveredAt/AckedAt`. `AckAsync(tenantId, messageId, recipientUserId?)` is idempotent (acking an acked row is a no-op returning false). **Per-mode ownership (two-scoping-models rule, written down):** SaaS — rows keyed by `tenant_id`, delivered to that tenant's agent and users; single-user — the sole user's personal tenant IS the tenant (same physical home as `email_outbox`/`prompt_overrides` per Story 28-1 PR D), the sole user is the only recipient — zero code-path split. The outbox is operational plumbing: queryable, never a second source of truth (AC6) — decisions/tasks/chat each have their own event family of record.
- **D5 — Hub groups are derived from the authenticated principal ONLY; there is no client-invokable join surface.** `UserChannelHub.OnConnectedAsync` computes groups `tenant:{tenantId}` and `user:{tenantId}:{userId}` from the JWT claims (`tenantId`, `sub` — the `JwtService` claim names); `OrchestratorChannelHub.OnConnectedAsync` computes `orchestrator:{tenantId}` after the policy has already refused non-orchestrator principals. NEITHER hub declares any public method that takes a group name — forged group-join is structurally impossible, and a reflection test pins that no hub method parameter can influence group membership (AC5's refusal clause, made a build-time property rather than a runtime check). Task traffic targets per-user groups computed via `ITaskAudienceResolver` (D9); chat replies target exactly `user:{tenantId}:{fromUserId}` — per-user conversation isolation.
- **D6 — Delivery = write-time push + connect-time replay + a slow sweeper; degraded mode is "the row waits".** `ChannelOutboxService.EnqueueAsync` persists (SaveChanges) FIRST, then best-effort publishes to the group (a hub send to zero connections is a silent no-op — exactly the degraded case). On `OnConnectedAsync`, the hub replays that consumer's unacked rows in `Id` (UuidV7) order and marks them `delivered`. A `ChannelOutboxSweeper : BackgroundService` (copy `OutboxSmtpSender` options: `PollInterval` ~15s, `RunOnStartup` test gate, cross-tenant drain via the `IEmailOutboxRepository.ClaimNextPendingAsync`-style repository walk) re-publishes stale `pending`/`delivered`-but-unacked rows — covering crash-between-persist-and-publish and missed reconnect races. Duplicate delivery is safe by construction: consumers dedupe on message id, ack is idempotent, and a duplicate decision submission hits the 39-8 404/409 discipline (AutoBurn bookmark) — no double-resume. **No timeout anywhere converts an unanswered request into a decision** (AC7; mirrors 39-8 D8's no-SLA stance).
- **D7 — Hub decision methods DELEGATE to the 39-8 resume path; the hub never applies anything.** `OrchestratorChannelHub.SubmitDecision(sessionId, decisionJson, ...)` calls the same service the public endpoint uses (39-8 step 6's `IElsaWorkflowService.ResumeDocumentDecisionAsync` behind the `DocumentDecisionEndpoints` validation logic, extracted into a shared `DocumentDecisionSubmissionService` if 39-8 lands it endpoint-inline — coordinate; whichever lands second extracts). Channel derivation stays server-side (`ApprovalChannels.Derive` sees the orchestrator principal → `orchestrator`). `SubmitEscalationDisposition` delegates to 39-8's `EscalationDispositionService`. `SubmitGuidanceReply` writes the reply outbox row + `GUIDANCE.PROVIDED` event and publishes back to the requesting workflow's watchers. Result (incl. 404/409) returns to the hub caller so the agent observes idempotency outcomes. Users acting on tasks do NOT get a hub method at all — acting travels today's REST resume endpoints (AC3, canon: "decisions land only via the idempotent resume surface").
- **D8 — Audit alignment: this story emits ONLY `GUIDANCE.*`; every other kind's event of record belongs to its owning story, and a correspondence test pins the wiring.** `APPROVAL.REQUESTED/PROVIDED` + `ESCALATION.*` are emitted by 39-8's gate/lifecycle/disposition (already on the durable drain before the publish hop fires — persist-before-publish holds stream-side too). `TASK.*` is 39-20's; `CHAT.*` is 39-19's. NEW here: `GUIDANCE.REQUESTED` / `GUIDANCE.PROVIDED` constants (mirroring `APPROVAL.*` naming), emitted by `ChannelOutboxService` via `IEventRepository.AppendAsync` when a guidance message is enqueued (fail-loud — the event IS part of the operation, the 39-8 D9 posture, not `PromptEventsService` best-effort). For conversation traffic the events of record (`CHAT.MESSAGE.RECEIVED/SENT`) are emitted by **39-19's `OrchestratorChatService`** — the single component chat passes through (record RECEIVED → agent turn → record SENT → relay; settled design review 2026-07-21). The outbox records nothing for conversation kinds and mints no recorder seam: the only chat entry points (`UserChannelHub.SendAgentMessage`, `OrchestratorChannelHub.SendAgentReply`) hand off to `OrchestratorChatService` rather than enqueueing conversation kinds directly, so nothing can cross un-evented (AC6) structurally — a conversation envelope only exists because the recording service created it.
- **D9 — 39-20 is stubbed behind its canonical interface, fail-closed.** Task delivery scoping calls `ITaskAudienceResolver` (the canonical async+role shape pinned across 39-17/18/19/20: `Task<bool> CanSeeAsync(Guid userId, TaskRef task)` / `Task<IReadOnlyList<AudienceMember>> EligibleAudienceAsync(TaskRef task, string roleWire)` — tasks are role-addressed, design review 2026-07-21: fan-out targets every role-holder in the audience, not one user). If 39-20 has not landed, CREATE the minimal interface at `apps/tamma-elsa/src/Tamma.Api/Services/Access/ITaskAudienceResolver.cs` with the canonical `TaskRef(Guid TenantId, Guid? InitiatorUserId, string? RepoKey, string? IssueId)` parameter record, and register `InitiatorOnlyTaskAudienceResolver` (`CanSeeAsync` ⇔ initiator; `EligibleAudienceAsync` = {initiator}) — fail-closed: nobody extra sees anything until the real model lands. If 39-19's `ConservativeAudienceResolver` (audience-or-initiator — a strict-superset stub) has already landed, keep that registration instead: one default stub, never two. 39-20 replaces the implementation (owning the canonical `TaskRef`/`AudienceMember` shapes); this story's tests run against a capturing fake, so no test churn.
- **D10 — Hub authentication: JWT via `access_token` query for browsers; a dedicated `OrchestratorChannel` policy for the engine/agent side.** Browser WebSockets cannot set `Authorization`; MODIFY the existing `JwtBearerEvents.OnMessageReceived` (Program.cs ~L1407, beside the cookie fallback) to also accept `ctx.Request.Query["access_token"]` when `ctx.HttpContext.Request.Path.StartsWithSegments("/hubs")` — the standard ASP.NET SignalR pattern, scoped to hub paths only. New policy `OrchestratorChannel` = authenticated AND (`ServicePrincipalRequirement` passes OR the principal carries 39-8 D6's orchestrator claim `tamma:principal-type = orchestrator`) — a tenant member/admin/owner JWT fails it (AC5's "reject non-orchestrator principals"); until 39-17 lands, tests mint the claim directly (the 39-8 pattern).

   ```csharp
   namespace Tamma.Core.Documents.Channels;
   public enum ChannelAudience { [Wire("orchestrator")] Orchestrator, [Wire("user")] User }
   [JsonPolymorphic(TypeDiscriminatorPropertyName = "kind")]
   [JsonDerivedType(typeof(AcceptanceRequested), "acceptance-request")]     // wraps Policy.AcceptanceRequest
   [JsonDerivedType(typeof(DecisionProvided), "acceptance-decision")]       // wraps Policy.AcceptanceDecision + decider + rulesReference
   [JsonDerivedType(typeof(TaskAssigned), "task-assigned")]
   [JsonDerivedType(typeof(EscalationRaised), "escalation-raised")]
   [JsonDerivedType(typeof(EscalationDisposition), "escalation-disposition")]
   [JsonDerivedType(typeof(GuidanceQuery), "guidance-query")]
   [JsonDerivedType(typeof(GuidanceReply), "guidance-reply")]
   [JsonDerivedType(typeof(AgentConversationMessage), "agent-conversation")]
   public abstract record ChannelMessage;
   public sealed record TaskAssigned(Guid TaskId, Guid DecisionSessionId, string AssignedRole,
       string Basis /* AssignmentBasis wire */, string DocumentTypeKey, Guid DocumentId,
       string IssueId, int AutonomyLevel, string? RulesReference) : ChannelMessage;
       // Role-addressed (design review 2026-07-21): the payload carries the ASSIGNED ROLE, never a single assignee.
       // Delivery is per-recipient via outbox fan-out — the actual recipient is the outbox row's RecipientUserId
       // (one row per audience member from ITaskAudienceResolver), NOT a field in this payload.
   public sealed record EscalationRaised(string EscalationId, string Outcome, string LineageJson,
       string IssueId, string? RulesReference) : ChannelMessage;
   public sealed record GuidanceQuery(Guid QueryId, string CorrelationId, string Question, string? ContextJson) : ChannelMessage;
   public sealed record GuidanceReply(Guid QueryId, string Reply) : ChannelMessage;
   public sealed record AgentConversationMessage(Guid ConversationId, Guid UserId, string Direction /* "user->agent"|"agent->user" */, string Text) : ChannelMessage;
   public sealed record ChannelEnvelope(Guid MessageId /* UuidV7 */, Guid TenantId,
       ChannelAudience Audience, Guid? RecipientUserId, ChannelMessage Message, DateTimeOffset CreatedAt);
   ```

## Risks & Mitigations

- **Prerequisite stack (39-2/39-5/39-6/39-8) is plan-only.** Largest schedule risk. Mitigation: the transport core (outbox, hubs, auth, sweeper — steps 2, 4–8) compiles against only this story's types; the 39-5-wrapping records and the ACCEPT end-to-end assertion are the last mile; every consumed name is pinned in the sibling plans.
- **D2's hub-placement reading of the story's technical note could be challenged in review.** Mitigation: the ADR records the reasoning (engine has no tenant DB; events already cross engine→API; trust posture preserved via the dedicated policy + separate hub + nginx exclusion); if review insists on an engine-hosted hub, only step 5's host and step 3's transport swap — the message set, outbox, and user hub are unaffected.
- **SignalR group sends silently no-op with zero subscribers** — a bug here looks like "message lost". Mitigation: that is exactly why the outbox is the truth; integration test (d) pins the recover-on-connect path, and the sweeper covers missed races.
- **Single-instance fan-out on multi-pod deployments** (an agent connected to pod A misses a publish from pod B). Mitigation: inherited `ILlmRunStreamBus` stance, said loudly in the ADR; the sweeper (DB-driven) delivers cross-pod eventually; the backplane decision is deferred once, for both surfaces.
- **Chat crossing before 39-19's service exists.** Chat relay is OFF until 39-19's `OrchestratorChatService` lands — the hubs' chat methods hand off to it (stand-in refuses with agent-offline), and the outbox accepts conversation kinds only from that path — a conscious, documented posture (AC6 over feature completeness), noted in the route comment.
- **Access-token-in-query leakage.** Query strings can land in logs. Mitigation: scope the read strictly to `/hubs` paths; Serilog request logging already redacts query on hub paths — verify and, if absent, add the path filter in the same Program.cs edit; note in the ADR.
