# Implementation Plan — Story 39-13: Assessment Family Migration — Research, Ambiguity, Clarify, DesignProposal

## Scope & Deliverable

When this story is done, the four assessment workflows (`research`, `ambiguity-scoring`, `clarifying-questions`, `design-proposal` — DefinitionIds unchanged) are thin bindings over `DocumentLifecycleWorkflow`, producing typed `Findings`, `AmbiguityAssessment`, `Clarification`, and `Design` documents through the shared produce→validate→review→revise→accept loop. `WaitForDesignApprovalActivity` and `WaitForClarifyingAnswersActivity` are retired: design acceptance rides 39-8's generic decision gate and Clarify's wait-for-answers rides a new generic `WaitForDocumentInputActivity`, with `DesignResumeEndpoint`/`ClarifyResumeEndpoint` preserved as thin adapters onto the generalized resume surface. Ambiguity-above-threshold becomes the typed `AmbiguityAboveThreshold` lifecycle outcome (threshold read from 39-5 `AcceptanceRules`, never a workflow constant), routed by the orchestrator into the Clarification lifecycle. `ResearchParsing`/`AmbiguityParsing`/`ClarifyParsing`/`DesignParsing` and their models are deleted; the 39-10 resume allowlist loses four entries; the legacy `RESEARCH.*`/`AMBIGUITY.*`/`CLARIFY.*`/`DESIGN.*` event vocabularies keep emitting alongside `DOCUMENT.*`.

## Design Decisions

- **D1 — Four bindings, public surface byte-stable, 39-12 recipe verbatim.** DefinitionIds, input names, and legacy output names are unchanged; outputs gain additive `outcome`/`documentId`. No compiled call site dispatches any of the four definition ids (grep-verified — dispatch is runtime, by id), so nothing upstream moves. Each binding: `[ResumeBehavior(...)]`, `ComputeReEntryPositionActivity`, fresh-run gate for pre-lifecycle emits, `DispatchWorkflow("document-lifecycle")` with constant `producerRole`/`producerAction` (so the 39-12 D5 binding walk materializes the pairs), typed exit routing via helper, zero `Finish`, zero `DispatchWorkflow("llm-call")`, zero parsing.
- **D2 — Clarification is ONE document type, TWO lifecycle runs, suspend in the binding between them.** Per the story's technical note (one type, phase semantics owned by 39-3's `Clarification`), the binding dispatches the lifecycle twice: Run A produces `Clarification{phase:questions}` via `(product_owner, clarify-requirements)`; the binding then delivers the accepted questions (existing `DeliverClarifyingQuestionsActivity`) and suspends on the new generic input gate (D3); on resume it dispatches Run B via `(product_owner, incorporate-answers)` producing `Clarification{phase:resolution}` with `supersedesDocumentId` = Run A's document (lineage chain). **Noted tension:** the story's stage mapping ("produced/validated/delivered → suspend → … → accepted") shows one acceptance, but the canon's "the accept gate always submits" means Run A also ends at an accept gate. Resolved in the story's favor semantically — the *document* is accepted once, at resolution; Run A's gate is the orchestrator sanity-check on the questions (self-decided at higher autonomy, rules-tunable) — and recorded as an open question for 39-5 (phase-aware or type-level lightening of the questions-phase gate).
- **D3 — Clarify's suspend generalizes to `WaitForDocumentInputActivity` + `DocumentInputResumeEndpoint`, NOT onto the decision gate.** Answers are domain input, not an `AcceptanceDecision`, and the decision gate deliberately has no SLA (39-8 D8) while an unanswered stakeholder question must still time out loudly (`CLARIFY.ANSWERS.TIMED_OUT`). So this story mints the second generic gate in the 39-8 style: canonical builder `LifecycleBookmarks.ForDocumentInput(tenantId, sessionId)` (added to 39-10's `LifecycleBookmarks`), durable `DelayFor` SLA copied from `WaitForClarifyingAnswersActivity` (`Clarify:AnswerTimeoutMinutes` config key preserved), tolerant `ReadInput` via `ResumeInput`. `ClarifyResumeEndpoint` becomes a thin adapter: same `ResumeRequest(SessionId, TenantId, Answers, Respondent)` record, same 400/404/409/200 behavior, forwarding to the generic input-resume service with keys `{Received:true, InputJson:answers}`.
- **D4 — Design acceptance = the 39-8 generic gate; the legacy endpoint is an adapter keyed by the same session id.** The binding threads its `sessionId` into the lifecycle as the decision-session id (filed-back 39-6 hook, D6b) so `DesignResumeEndpoint`'s existing payload (`SessionId, TenantId, Approved, Feedback, Reviewer`) can compute `LifecycleBookmarks.ForDecisionSession(tenantId, sessionId)` and resolve the very gate the lifecycle suspended on. Mapping: `Approved=true` → decision kind `accept`; `Approved=false` → kind `reject` with `notes=Feedback` (39-8 AC7(b) rejection path → lifecycle exits `rejected`, `DESIGN.PROPOSAL.REJECTED` mirrored). 404/409/400 posture identical (delegated to the generic endpoint's lookup). `DESIGN.REVIEW.TIMED_OUT` becomes unreachable — 39-8 D8 arms no SLA on decisions; the constant stays (drift-safe), the change is documented in the story-completion notes and the read-back test's timeout rows retarget mechanically. "Design pinned to human assignment by default" is 39-5 configuration: ship a per-type system default rules entry for `design` (autonomy floor / reviewer selection per whatever field 39-5 landed) — coordinate; if no such field exists yet, file to 39-5 and record the gap.
- **D5 — Delivery-to-issue survives via a filed-back pre-ACCEPT delivery hook (39-6), not a publisher decorator.** Legacy Clarify/Design post the document to the issue *before* the human decides. Clarify's delivery lives in the binding (between runs — no hook needed). Design's must run inside the lifecycle child before the gate: add to `DocumentLifecycleWorkflow` an optional input `deliveryWorkflowDefinitionId` (default `""` = skip) dispatched on each entry to ACCEPT with `{documentJson, documentType, issueId, repository, issueNumber, sessionId, tenantId}`; this story creates the tiny `DesignDeliveryWorkflow` (`DefinitionId "design-proposal-delivery"`) wrapping `DeliverDesignProposalActivity` + the `DESIGN.PROPOSAL.GENERATED`/`DELIVERED` emits. Rejected alternative (decorating `IAcceptanceRequestPublisher`) documented: it would strand the legacy events outside the workflow event drain.
- **D6 — Filed-back 39-6/39-12 hooks (all additive, lockstep-coordinated):** (a) `documentJson` output extended from "accepted payload" (39-12 D4) to "latest *validated* payload on every exit" — needed for legacy `designProposal` output on the rejected path and for the `score` in `AMBIGUITY.SCORED`/`CLARIFICATION_TRIGGERED` on the escalated path; (b) optional `decisionSessionId` input (D4); (c) `deliveryWorkflowDefinitionId` input (D5); (d) accept/reject decision notes exposed in `lifecycleResult` (legacy `Detail` on `DESIGN.PROPOSAL.APPROVED/REJECTED`). Each is a one-to-few-line lifecycle edit plus its structure-test pin; per the 39-12 precedent, fixes belong in the generic layer, never as family special cases.
- **D7 — `AmbiguityAboveThreshold` is the lifecycle's exit, produced by the 39-5/39-6 policy machinery; the binding only mirrors and the orchestrator only routes.** The binding passes `acceptanceRulesJson` through (empty → `AcceptanceRules` defaults) and deletes the legacy `threshold` input, `AmbiguityThresholds`, and the `ComputeDecision`/`ShouldClarify` branch. Whether the check fires post-VALIDATE (39-6 D8's deterministic guardrail) or at the gate as `AcceptanceEscalationReason.AmbiguityAboveThreshold` (39-5 D10), the observable contract is identical: exit `escalated` with outcome wire `ambiguity-above-threshold` and the assessment in lineage. **Noted tension:** the story says "an *accepted* AmbiguityAssessment's score exceeds…" while 39-6 D8 short-circuits before REVIEW — resolved as: the typed outcome + persisted assessment + lineage is the contract; the envelope state on the over-threshold path is `Escalated`, and the plan does not reorder 39-6's stages. The binding contains NO dispatch of `clarifying-questions` (AC4's "no bespoke inter-workflow branch edge" — pinned structurally); the test's stub orchestrator consumes the escalation and dispatches the Clarification lifecycle with the assessment `documentId` as lineage input. **Behavior note:** legacy default threshold was 0.5 (`AmbiguityThresholds.DefaultClarify`); 39-5's `AmbiguityEscalationThreshold` default is 0.7 — flagged to the 39-5 owner and recorded in `.dev/findings/`.
- **D8 — Event mirroring per family (39-12 D3 pattern; constants files untouched).** Research: `STARTED`+`CONTEXT_GATHERED` pre-lifecycle (fresh runs only), `COMPLETED` (accepted; `findingCount`/`confidence` read from `documentJson`), `FAILED` (rejected/escalated, detail names the outcome wire). Ambiguity: `STARTED` pre; on exit with a validated assessment emit `SCORED` (score from `documentJson`), then `BELOW_THRESHOLD` (accepted) or `CLARIFICATION_TRIGGERED` (outcome `ambiguity-above-threshold`, threshold from effective rules); `FAILED` on other outcomes. Clarify: `QUESTIONS.GENERATED` (Run A validated/accepted), `QUESTIONS.DELIVERED` (binding deliver), `ANSWERS.RECEIVED` (input-gate resume), `REQUIREMENTS.CLARIFIED` (Run B accepted), `QUESTIONS.FAILED`/`INCORPORATION.FAILED` (respective run non-accepted), `ANSWERS.TIMED_OUT` (input-gate SLA). Design: `GENERATED`+`DELIVERED` from the delivery workflow (D5), `APPROVED`/`REJECTED` on exit, `FAILED` on escalated. All emissions gated on re-entry position (no duplicates on resume).
- **D9 — Parser retirement is total; shape knowledge lives in the document types.** Delete `ResearchParsing`, `AmbiguityParsing`, `ClarifyParsing`, `DesignParsing` + their model files (keep `ClarifyDeliveryResult`/`DesignDeliveryResult` — the deliver activities' result types) + `ResearchParsingTests`, `AmbiguityParsingTests`, `AmbiguityThresholdsTests`; prune the four families' rows from 39-3's compat suites (39-12 D6 rationale — the transition window ends with the parser). `DeliverClarifyingQuestionsActivity`/`DeliverDesignProposalActivity` formatting helpers get mechanical edits to deserialize the 39-3/39-4 typed payloads (`Clarification`, `Design`) instead of the deleted models.
- **D10 — Resume declarations:** Research/Ambiguity/Design bindings `[ResumeBehavior(ResumeMode.LatestStateReEntry)]` (the child lifecycle owns the accept-gate bookmark; parent waits with `WaitForCompletion=true` — 39-12 D7). Clarify `[ResumeBehavior(ResumeMode.Both)]` (its own input-gate bookmark + re-entry). All four `LegacyResumeAllowlist` entries removed. Clarify's re-entry positions extend the binding's fresh-run gate: position derived from the document store (no Clarification → fresh; questions accepted but no resolution → skip Run A, re-deliver only if never delivered, re-arm the input gate; resolution accepted → short-circuit outputs).

## Risks & Mitigations

- **Four migrations + two generic gates in one story — scope.** Mitigation: the 39-12 recipe amortizes each binding to a mechanical rewrite; the in-story order lands value incrementally; the input gate (step 3) is a copy of a five-times-proven pattern.
- **Filed-back 39-6 hooks (D6) drift or get vetoed.** Mitigation: all four are additive with structure-test pins; fallbacks exist (document-store read for payloads via 39-11; a mapping table in the design adapter if `decisionSessionId` is refused — worse, documented) but the hooks are the plan of record.
- **Endpoint-preservation regressions (the #15/#437 class).** Mitigation: adapters translate payloads only — lookup/injection lives in the generic endpoints; the untouched `*ResumeApiTests` pin the public contract; read-back matrices are retargeted, never deleted.
- **Threshold default change (0.5 → 0.7) and Design/Clarify timeout-semantics changes surprise operators.** Mitigation: D4/D7 record both explicitly; `.dev/findings/` entry + story-completion notes; thresholds are admin-editable per 39-5, so parity is a config choice, not code.
- **Clarify Run A's accept gate adds an interaction the story's mapping didn't show.** Mitigation: D2 documents the canon constraint ("accept always submits"); rules-tunable; open question filed to 39-5 rather than an if-else that skips the decision.
- **Double emissions on re-entry/resume.** Mitigation: D8/D10 gate every legacy emit on re-entry position; ExecutionTests (c) pins exactly-once delivery.
