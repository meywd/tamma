# Implementation Plan — Story 39-20: Teams, Roles, Repo Access & Task Routing

## Scope & Deliverable

When this story is done, the control plane holds a first-class access model — `teams` + `team_members` + a minimal `repositories` catalogue + `repo_access_grants` (`read | contribute | admin`, closed vocabulary) — managed over tenant-scoped CRUD endpoints (org-endpoint pattern, owner/admin gated via new `Permissions.Matrix` keys) and an admin dashboard screen. One `ITaskAudienceResolver` in `apps/tamma-elsa/src/Tamma.Api/Services/Access/` implements the visibility predicate (`CanSeeAsync(userId, task)` ⇔ initiated-workflow ∨ repo-access, team-transitive) plus the ordered, permission-filterable `EligibleAudienceAsync(task, roleWire)` set (of `AudienceMember`), backed by a precomputed per-user repo-scope cache. A `TaskAssignmentService` (implementing 39-17's `ITaskAssignmentService` seam) server-validates every assignment against that set and emits `TASK.ASSIGNED/REASSIGNED/COMPLETED` DCB events with the eligibility basis and autonomy context. Existing tenants' repos are grandfathered tenant-visible (no lockout); single-user mode collapses to the sole owner of a personal tenant with zero teams and zero code-path splits in consumers.

## Design Decisions

- **D1 — The access model is CONTROL-PLANE-resident, keyed by `tenant_id` like `tenant_memberships` — NOT the user_id-XOR-tenant_id pattern.** Teams, grants, and the repo catalogue are org *structure* referencing `users(id)` and `tenants(id)` (both CP tables, `Ignore`d in `TenantDbContext`), exactly like `tenant_memberships` and `tenant_platform_installations`. The XOR pattern is for tenant-owned *config* (prompts, rules); applying it here would orphan team rows from their member FKs. The two-scoping-models rule is still answered per mode, written down before code: **SaaS** — the tenant owns teams/grants, owner/admin mutate, members read; **single-user** — the sole user is auto-owner of the personal tenant, owns zero teams, and every repo is tenant-visible, so the same predicate yields "sees/does everything" with no mode branch anywhere (AC7). New tables join `ConfigureControlPlaneEntities` + `Migrations/ControlPlane`, and the `ConfigureTenantEntities` ignore-list (~L1435) gains the four entities.
- **D2 — Repo identity: a minimal explicit `repositories` catalogue, grandfathered tenant-visible.** Repo registration today is implicit (`github_installation_repos` is GitHub-only and keyed by installation; `tenant_platform_installations` has no per-repo rows; workflows carry `RepoFullName` strings). Per the story's technical note the minimal explicit row is in scope: `RegisteredRepo` (`Id`, `TenantId`, `PlatformKind`, `RepoFullName`, `ExternalId?`, `Visibility ∈ tenant|restricted`, timestamps, `DeletedAt?`), unique `(TenantId, PlatformKind, RepoFullName)`. **Default posture (decided + documented, AC2):** `Visibility='tenant'` — every tenant member has implicit `contribute`; flipping a repo to `restricted` activates grant-only access. The migration backfills rows from `github_installation_repos ⋈ github_installations (TenantId IS NOT NULL)` as `tenant` — existing tenants keep today's "everything visible" behavior, no lockout. A task referencing a repo with **no catalogue row** resolves as tenant-visible *within the already-authorized tenant* (the tenant boundary itself stays `GitRepoAuthorizer`'s job — Story 38-1, unchanged); this fail-open-inside-the-fence posture is the grandfather clause generalized, recorded in the D12 design doc.
- **D3 — Access levels are a closed string vocabulary with a CHECK constraint + a static rank helper; no `Tamma.Core/Documents` dependency.** `RepoAccessLevels` (`Read="read" < Contribute="contribute" < Admin="admin"`, `IsValid`, `Rank`, `IsAtLeast`) mirrors `TenantRoleHierarchy` exactly. Persisted as text with `ck_repo_access_grants_level` (house pattern `ck_users_platform_role`). This keeps 39-20 compile-independent of 39-2/39-5 — it can land first (it is P0 for every user-facing story). The 39-5 `AssignmentBasis` wire strings `initiator`/`repo-access` are used as string constants in `TaskEvents`; when 39-5 lands, `TaskAssignmentService` accepts its enum at the seam (one-line adoption, noted in Dependencies).
- **D4 — Composition rule (AC6), documented + tested: effective repo access = MAX(tenant-role implied, direct grant, team grants); team roles never bypass tenant roles.** Implied by tenant role: `owner`/`admin` ⇒ `admin` on every tenant repo (they already hold `repos:manage`); `member` ⇒ `contribute` on `Visibility='tenant'` repos, nothing on `restricted`. Grants (direct or via team membership) only ever ADD access. Team-membership role (`member | maintainer`) is *team-scoped*: a `maintainer` may manage that team's member list (alongside tenant admin/owner) but gains zero repo power from the role itself — repo power comes only from the team's grants. Pure static `EffectiveAccess.Compute(tenantRole, repoVisibility, IEnumerable<string> grantLevels)` makes the rule a unit-testable function.
- **D5 — ONE resolver, canonical name, replacing the 39-18 stub in place.** `ITaskAudienceResolver` stays at `apps/tamma-elsa/src/Tamma.Api/Services/Access/ITaskAudienceResolver.cs` (the exact path 39-18 D9 creates; if 39-18 has not landed, this story creates it there). The task-ref record is widened to the canonical `TaskRef(Guid TenantId, Guid? InitiatorUserId, Guid? RepositoryId, string? RepoFullName, string? IssueId, Guid? DocumentId, string? RequiredPermission)` — 39-18's `ChannelTaskRef` fields are a strict subset, so the rename+widen is mechanical for whichever story lands second. `CanSeeAsync` is the pure visibility predicate (initiator ∨ repo-access, ANY level — `RequiredPermission` deliberately ignored here); `EligibleAudienceAsync` additionally filters by `Permissions.HasPermission(tenantRole, task.RequiredPermission)` (e.g. "acceptance of a Plan requires `workflows:manage`") and orders deterministically: initiator first (basis `initiator`), then repo-access candidates by effective level rank desc, tenant-role rank desc, `UserId` asc — the SET is ordered and stable; the CHOICE stays orchestrator policy (story technical note).
- **D6 — Cheap by precompute: `UserRepoScopeCache`, event-invalidated + TTL-bounded.** Copy `EntitlementSnapshotCache` (singleton, `ConcurrentDictionary` keyed `(TenantId, UserId)`, `TimeProvider` TTL — default 60s): entry = `UserRepoScope(IReadOnlySet<Guid> RepoIds, bool TenantWideVisibility, string TenantRole, string MaxLevelByRepo…)` built by one repository query (direct grants ∪ team grants via membership ∪ tenant-visible set). Every mutation in this story's services calls `InvalidateTenant(tenantId)`; tenant-membership changes made by `OrgEndpoints` (outside this story's write path) are covered by the TTL — recorded honestly in the design doc rather than spraying invalidation calls through `OrgEndpoints` (revisit if 60s staleness ever matters). `EligibleAudienceAsync` uses the inverse query (`GetRepoAudienceAsync`) uncached — assignment is orders of magnitude rarer than delivery/listing.
- **D7 — Assignment is server-validated in `TaskAssignmentService`; the agent literally cannot address an out-of-set user.** Implements 39-17's `ITaskAssignmentService` (interface at `Tamma.Api/Services/Orchestrator/ITaskAssignmentService.cs`; if 39-17 has not landed, this story CREATES it there with the signature pinned in 39-17 step 6 and registers the real implementation — replacing `RefusingStubTaskAssignmentService` otherwise). `AssignAsync` re-derives `EligibleAudienceAsync` server-side and returns a typed refusal (`AssignmentResult.RefusedNotEligible`) for any assignee outside it — no exception path an agent could swallow into success. `ReassignAsync`/`CompleteAsync` live beside it; 39-8's resume surface and 39-19's Task View call `CompleteAsync` in lockstep (their wiring, this story's service + tests).
- **D8 — `TASK.*` events are fail-loud (the stream IS the assignment record); team/grant CRUD events are best-effort per the org precedent.** `TASK.ASSIGNED/REASSIGNED/COMPLETED` are appended via `IEventRepository.AppendAsync` *inside* the service call — an append failure fails the assignment (who-was-asked-and-why must be reconstructable from the stream alone, AC5). `TEAM.*`/`REPO.*` CRUD events copy `OrgEndpoints.EmitTenantEvent` fire-and-forget semantics (the user-visible side effect is the row change, same as `TENANT.MEMBER_ROLE_CHANGED.SUCCESS`).
- **D9 — Endpoints follow the org path-tenant pattern, but the gate is `Permissions.Matrix` evaluated against the FILTER-derived role.** Routes mount under `/api/v1/orgs/{tenantId}/…` with `RequireTenantMembershipFilter`; handlers read the path-tenant role from `HttpContext.Items[RequireTenantMembershipFilter.TenantRoleItemKey]` and gate writes with `Permissions.HasPermission(role, "teams:manage" | "repos:manage")` — matrix extension (AC6), not a parallel `IsAtLeast` fork, and correct for path-tenant routes where the JWT role claim may describe a different active tenant. New keys, each with the standard story-39-20 comment: `["teams:manage"] = ["admin","owner"]`, `["repos:manage"] = ["admin","owner"]`, `["tasks:assign"] = ["admin","owner"]` (human reassignment surface; the orchestrator's own assignments ride the service-principal path through D7, not this key).
- **D10 — Workflow initiation enforcement ships as `IWorkflowInitiationAuthorizer`, composing the existing tenant fence with the new user grain.** `AuthorizeAsync(userId, tenantId, repoFullName)` = `GitRepoAuthorizer.AuthorizeAsync` (tenant boundary, unchanged) AND effective access ≥ `contribute` (D4). Denials emit `REPO.ACCESS_CHECK.DENIED` (auditable refusal — feeds 39-19 AC2). There is no user-facing "start workflow on repo X" endpoint today (webhooks auto-start; `/api/adl/*` resumes are decisions, gated separately) — the primary consumer is 39-19's chat dispatch (lockstep); shipping the authorizer here keeps the predicate implemented once (AC3/AC4).
- **D11 — The "no consumer re-implements the predicate" clause is a reflection pin test.** Modeled on 39-17's `OrchestratorMediationPinTests`: assert `ITaskAudienceResolver` has exactly one production implementation (`TaskAudienceResolver`), and that `ITeamRepository`/`IRepoAccessRepository` appear in constructor signatures ONLY of `TaskAudienceResolver`, `UserRepoScopeCache`, `TeamService`, `RepoAccessService` (the CRUD services) — any hub/endpoint/orchestrator class touching raw grant data fails the build-time pin. Comment names story 39-20 as the authority.
- **D12 — Design doc, not scattered comments.** CREATE `.dev/decisions/story-39-20-access-model-design.md` (naming per `story-31-1-git-platform-design.md` precedent cited in 39-18 D1) recording: D2's default posture + grandfather backfill + no-row fallback, D4's composition rule, D6's TTL-vs-invalidation trade, and the schema note the story's technical note asks for.
- **Story-vs-canon tensions: none.** The story calls the resolver name "illustrative"; the canon fixes `ITaskAudienceResolver` — kept canonical. AC1's "gated `users:manage`-style (owner/admin)" describes reach, not the literal key (`users:manage` is owner-only today) — D9's new admin+owner keys honor the parenthetical.

## Risks & Mitigations

- **Consumer stories are plan-only; enforcement claims (AC4) could rot until they land.** Mitigation: everything this story controls is enforced and tested here (assignment refusal, initiation authorizer, resolver); consumer wiring obligations are named in 39-18/39-19's plans and re-pinned by their tests; the D11 pin test makes bypass a build failure, not a review catch.
- **Contract drift on the two shared seams (`TaskRef` vs 39-18's `ChannelTaskRef`; `ITaskAssignmentService` shape vs 39-17).** Mitigation: both sibling plans explicitly cede the canonical shape to 39-20 ("may widen", "39-20 supplies the real resolver"); the swap is a rename + field superset; coordinate at merge, whichever lands second adopts.
- **Grandfather backfill misses non-GitHub repos** (`tenant_platform_installations` has no per-repo rows). Mitigation: the D2 no-catalogue-row fallback (tenant-visible within the authorized tenant) means an unbackfilled repo behaves exactly as today; rows appear lazily when an admin first restricts or grants (the endpoints upsert catalogue rows by full name), documented in the design doc.
- **Fail-open reading of the D2 fallback.** It is open only INSIDE a tenant that already passed `GitRepoAuthorizer` — cross-tenant stays fail-closed (Story 38-1 tests untouched). Said loudly in the design doc + a resolver test pins that a foreign-tenant `TaskRef` yields `CanSee=false` for every non-member.
- **Cache staleness after `OrgEndpoints` membership changes (D6).** A removed member could see stale-scoped deliveries for up to the TTL. Mitigation: 60s default TTL, documented; hub delivery is also gated per-connection by auth; revisit with explicit invalidation hooks if audit flags it.
- **Scope creep toward a full RBAC engine** (per-branch permissions, custom roles). Mitigation: closed three-level vocabulary + the D4 max-composition rule is the whole model; anything finer is a new story.
