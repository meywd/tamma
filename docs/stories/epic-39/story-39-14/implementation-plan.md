# Implementation Plan — Story 39-14: Planning Family Migration — PlanGeneration + PlanReview onto the Unified Review

## Scope & Deliverable

When this story is done, `PlanGenerationWorkflow` (DefinitionId `plan-generation`, unchanged) is a thin binding over `DocumentLifecycleWorkflow`: it fetches the accepted `Decomposition` from the 39-11 store (the consumes side), dispatches `document-lifecycle` with `documentType = "plan"` and the `(architect, plan-system-design)` producer cell, and exposes the accepted `Plan` (or a typed outcome) to its unchanged callers. The bespoke validation-retry loop (`ValidationErrors` loop-back, `OutErr` terminal) and the entire 3-phase PlanReview debate pipeline are deleted: plan review runs inside the lifecycle via 39-7's producers (7-role panel by default policy), panel discussion rounds ARE lifecycle revise rounds, and `PlanReviewWorkflow` (DefinitionId `plan-review`, kept for the SingleIssueCycle call site) shrinks to a deterministic read-through shim over the document store — no LLM call, no verdict parsing. `ReviewAggregationHelper` and `PlanValidationHelper` are retired; both bindings declare resume behavior and burn their 39-10 allowlist entries. This is the second lifecycle migration and the first two-link typed chain (Decomposition → Plan).

## Design Decisions

- **D1 — `plan-generation` becomes the FULL Plan lifecycle; `plan-review` becomes a deterministic read-through shim. The parent is untouched.** AC1-AC3 put review + revise INSIDE the Plan lifecycle, which makes SingleIssueCycle's separate `ReviewPlan` dispatch redundant — but the story's technical note pins definition ids/call sites stable. Resolution (tension noted): keep both definition ids live and the parent byte-identical. `PlanGenerationWorkflow` (rewritten) runs produce → validate → review(panel) → revise → accept and outputs the accepted `planJson` (+ additive `status`/`outcome`/`documentId`/`decision`/`reviewNotes`); on any non-accept exit `planJson` is `""`, so the parent's EXISTING empty-plan failure edge fires `CYCLE.STEP_FAILED` — no parent edit needed. `PlanReviewWorkflow` (rewritten) makes NO llm-call: it reads the latest accepted `Plan` + its `Review` lineage for the issue from the document store and maps to the legacy output shape (`decision`: accepted → `"approved"`, anything else → `"needsHuman"` with the typed outcome in `reviewNotes`; `deferred`/`split` → `"[]"`, `discussionLog` → round projection from lineage, `suggestionsJson` → `"[]"`). The parent's Approved path proceeds; NeedsModification/Defer/Split become unreachable from the shim (D2). This satisfies AC2's substance — no independent produce-verdict pipeline exists — while honoring the call-site freeze.
- **D2 — Defer/split retire from the review surface (documented behavior change).** Today only the PO-decision phase could emit `defer`/`split`; the unified `Review` decision enum (39-4 D1) has no such members, and scope routing is the orchestrator's job (epic canon: the acceptor is an actor). The shim always outputs empty `deferred`/`split`; the parent's branches stay compiled but dormant. Recorded in story-completion notes + a `.dev/findings/` entry; if product wants defer/split back, it lands as an orchestrator accept-decision capability (39-17), never a reviewer verdict.
- **D3 — Behavior carry-over via binding-local default rules: rounds 3, repair 2, 7-role panel.** Today's effective budgets are PlanGeneration `maxRetries = 2` and PlanReview `maxRounds = 3`; 39-5's generic defaults are rounds 2 / repair 2 / single reviewer. To avoid silently changing quality/cost in the mechanism swap (story technical note), `PlanBindingHelper.DefaultPlanRulesJson()` builds `AcceptanceRules` with `MaxRevisionRounds = 3`, `MaxValidationRepairAttempts = 2`, `ReviewerSelection` = panel over the `RolePhaseMap.GetReviewActionForRole` 7-role roster, used only when the `acceptanceRulesJson` input is empty. A stored per-document-type override for `"plan"` (39-5 storage) always wins via the passthrough. Rebuttal anonymization and the PO-decision phase are NOT ported (39-7 D10 — revision-with-notes is the lifecycle's REVISE; a genuine need becomes a `.dev/findings/` entry).
- **D4 — `consumes: [Decomposition]` is a real store read, folded into a DECLARED template variable.** The binding fetches the latest accepted `Decomposition` for the issue (39-11 `GetLatestAcceptedAsync` semantics, via the D8 read seam) and merges its JSON into the `contextFindings` producer variable ahead of `poSummary` — NOT under a new `decompositionJson` key, which the shared Plan-family template does not declare and would silently drop at render (the `ValidationFeedbackHelper` lesson; its doc comment forbids adding placeholders to the ~17-cell shared body). Issue identity: `issueId` input when provided, else `PlanBindingHelper.DeriveIssueId(repository, issueNumber)` → `"{repo}#{number}"` (the `TriageItemCycleHelper` L84 precedent — SingleIssueCycle passes no `issueId`). Missing decomposition (legacy runs) → proceed with `workItemJson` alone, `Detail = "no-accepted-decomposition"` on the started event — the DECLARATION (39-2 interface list: `plan-generation` consumes `[decomposition]`, produces `plan`, Provisional flag flipped) is build-time; runtime absence is tolerated this story and revisited when the 39-12 chain is universal.
- **D5 — AC6's "existing event vocabulary": survey finding — the two workflows emit NO dedicated `PLAN.*` DCB constants.** Grep-verified: their only in-workflow DCB emissions are `CONTEXT.STORE_ROLE.STARTED/COMPLETED/FAILED` (from `StoreRoleFindingActivity`, per persisted role review/rebuttal/`po-decision-round-{N}`); everything else is the parent's `CYCLE.*` (untouched per D1, continues automatically) and the dispatched llm-call's own events. Preservation mapping: (a) per-member/per-round review persistence transition → `DOCUMENT.PRODUCED/VALIDATED/REVIEWED` with `documentType="review"` + the 39-11 store (strictly richer); (b) the binding keeps ONE `StoreRoleFindingActivity` node persisting the final aggregate review to the vector store (`Role = "plan-review"`) so the `CONTEXT.STORE_ROLE.*` family continues at its equivalent transition and the KB keeps receiving review content; (c) round count, today reconstructable only from `po-decision-round-{N}` role strings, is reconstructable from `DOCUMENT.REVISION_STARTED`/`DOCUMENT.REVIEWED` round tags — the AC6 replay test asserts both families and the round arithmetic. Story-vs-reality tension (story presumes a dedicated family) resolved by this survey-backed mapping; no new legacy-looking constants are minted.
- **D6 — Verdict-fork proof (AC5) = deletion + structure pins + assembly scan.** The old free-form path dies by construction: `ReviewAggregationHelper` (sole src consumer: `PlanReviewWorkflow`) and `PlanValidationHelper` (sole src consumer: `PlanGenerationWorkflow`) are DELETED, so no parser-backed verdict dispatch can compile. Pins: both planning workflows contain ZERO `DispatchWorkflow("llm-call")` nodes; the rewritten `PlanGenerationWorkflow` has exactly two `DispatchWorkflow` sites (store-fetch is an activity, lifecycle dispatch is `"document-lifecycle"`); a reflection test asserts the `Tamma.ElsaServer` assembly contains no type named `ReviewAggregationHelper`/`PlanValidationHelper`. The compile-time same-type half (review output type == accept gate input type == `Review`) is 39-6/39-7 machinery; this story's test asserts the planning graphs reach review ONLY through the lifecycle dispatch.
- **D7 — Test-retirement blast radius: three sibling suites prune their old-parser dependencies.** Deleting the two helpers breaks (a) 39-4's `PlanTypeTests` subsumption rows and `ReviewLegacyCompatTests` cross-checks (both invoke the old parsers directly per its D8), (b) 39-7's `ReviewParityTests` old-side (`ParseRoleVerdict`/`AggregateVerdicts` invocations — its plan names this story as the retirement consumer), (c) `ValidationRetryFeedbackTests`' PlanGeneration section. Per the 39-12 D6 precedent, transition-window suites end when the old parser ceases to exist: prune the old-side invocations with pointer comments (behavior stays pinned on the typed side: `PlanDocumentType`/`ReviewDocumentType` validators + the ported decision tests, step 8). `ValidationFeedbackHelper` STAYS (AC8's "reduces to the shared helper": still consumed by `TaskCreationWorkflow`/`TestCaseCreationWorkflow` (39-15 scope) and by 39-6 D11's `BuildRevisionVariables`) — its doc comment is updated to name the lifecycle as the Plan-family consumer. `TriagePanelAggregationHelper`'s `<see cref="ReviewAggregationHelper"/>` doc reference is rewritten (dangling cref = CS1574).
- **D8 — Store read seam: `FetchLatestAcceptedDocumentActivity`, resolved via `context.GetService<ILifecycleReEntryService>()`.** Both rewritten workflows need engine-side reads (binding: latest accepted `decomposition`; shim: latest accepted `plan` + its review lineage). 39-11 ships endpoints + repository but no engine read activity; 39-10's `ILifecycleReEntryService` is the in-process consumer of `GetLatestAcceptedAsync`. Create ONE activity in `Tamma.Activities/Documents/` wrapping that service (the `EventPersistenceMiddleware` service-resolution pattern, `NullLifecycleReEntryService` ⇒ empty result, never a throw); if the landed 39-10 interface lacks a latest-accepted-body read, extend it in lockstep (the 39-12 D4 "file the hook back" discipline). Filed against 39-10/39-11, one activity, reused by 39-13/39-15.
- **D9 — Resume declarations: binding `LatestStateReEntry` with the compute-position gate; shim `LatestStateReEntry` trivially (pure read).** `PlanGenerationWorkflow`: `[ResumeBehavior(ResumeMode.LatestStateReEntry)]` + `ComputeReEntryPositionActivity` (`DocumentType = "plan"`) gating a `FreshRun` decision — position ≠ Produce skips decomposition-fetch and re-dispatch duplication; the child lifecycle performs the actual mid-round re-entry (AC7's "crash after round-2 reviews → re-enter at round-2 revise" is 39-6/39-10 behavior, asserted here on the plan type). `PlanReviewWorkflow` (shim): declares `LatestStateReEntry` with the compute node present (clause (c)); a re-run is a harmless idempotent read. Both entries removed from `LegacyResumeAllowlist` — the "allowlist shrinks by two" AC7 clause. No `FlowDecision` in either graph routes raw LLM output (the 39-12 D2 reading of "no bespoke branch").
