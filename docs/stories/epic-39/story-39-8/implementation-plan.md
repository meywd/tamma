# Implementation Plan — Story 39-8: Escalation & Approval Surface — events, suspend/resume, lineage payload

## Scope & Deliverable

When this story is done, the platform has ONE generic document-decision gate and ONE exception surface: an `ApprovalEvents` DCB family (`APPROVAL.REQUESTED/PROVIDED`, `ESCALATION.TRIGGERED/RESOLVED`) with a drift-tested closed `channel` set (`orchestrator | user | api`) and denormalized `durationMs`; a reusable `WaitForDocumentDecisionActivity` that suspends any lifecycle on a tenant-folded, unguessable bookmark and maps the injected decision onto 39-5's `AcceptanceDecision`; a `DocumentDecisionResumeEndpoint` in the engine mirroring `DesignResumeEndpoint`'s security posture byte-for-byte (404 cross-tenant, 409 collision), fronted by a tenant-scoped `POST /api/documents/decisions/{sessionId}/resume` in `Tamma.Api` that derives tenant, decider, and channel server-side; and an escalation disposition surface (`POST /api/documents/escalations/{escalationId}/resolve`) that emits `ESCALATION.RESOLVED`. Every `ESCALATION.TRIGGERED` carries the full 39-6 document lineage — never a bare failure string. Story 4-6 is marked superseded, and the two legacy ad-hoc escalation call-sites are reconciled as documented migration debt.

## Design Decisions

- **D1 — Vocabulary in `Tamma.Core`, plumbing in `Tamma.Activities/Documents/`, per the project graph.** `ApprovalChannel` (`orchestrator | user | api`) and `EscalationDisposition` (`resolved | overridden | abandoned`) are NEW `[Wire]` enums in `Tamma.Core/Documents/` (drift-tested closed sets; 39-18's typed messages will reuse them). The `ApprovalEvents` constants class, the gate, and the escalation emit activity live in `Tamma.Activities/Documents/` beside 39-6's `DocumentEvents.cs` (the story's "sibling `ApprovalEvents.cs`"). This works for both hosts: `Tamma.ElsaServer → Tamma.Activities` and `Tamma.Api → Tamma.Activities` are both existing project references (verified in the csproj files), so no constant is duplicated.
- **D2 — ONE canonical bookmark builder: `WaitForDocumentDecisionActivity.DecisionBookmarkName(tenantId, sessionId)` → `document-decision-{tenant}-{session}`.** Tenant segment normalized via the existing `WaitForMergeApprovalActivity.NormalizeSegment` (same transform both sides); session is the unguessable decision-session Guid 39-6 mints at Init (39-5 D5: the decision-session id IS the bookmark session id). `DocumentDecisionResumeEndpoint.BookmarkName(...)` delegates to it, exactly as `DesignResumeEndpoint.BookmarkName` delegates to `ApprovalBookmarkName` — suspend/resume names can never drift (AC4/AC5, technical note 2).
- **D3 — The gate emits both `APPROVAL.*` events itself, via `TammaEventEmitter` → `EventDrain`.** `Execute` emits `APPROVAL.REQUESTED` immediately before creating the bookmark (request+suspend is one atomic site, so "fires whenever the ACCEPT stage publishes and suspends" is structural); the resume callback emits `APPROVAL.PROVIDED`. Emitting inside the engine (not the endpoint) keeps the events on the durable drain with full workflow tag context, and means the endpoint stays a thin resume seam like its five siblings.
- **D4 — `durationMs` comes from a `RequestedAtUtc` workflow-variable input, not activity-instance state.** The callback runs on a rehydrated activity, so Execute-time locals are gone. Proven-API solution: the caller sets a workflow variable `AcceptRequestedAtUtc = now` in the same step that builds the `AcceptanceRequest` (39-6 D5's `BuildAcceptanceRequest`), and the gate takes it as a required `Input<string>` (ISO-8601) — callbacks re-reading `Input`s after rehydration is proven by `WaitForDesignApprovalActivity.OnTimeoutAsync` calling `SessionId.Get(context)`. Empty/unparseable value → `TammaError DOCUMENT.DECISION.MISSING_REQUESTED_AT` at Execute (fail-loud; 39-6's structure test pins the wiring). Rejected alternatives: Elsa `ActivityExecutionContext` persisted properties (no repo precedent, unverified survival semantics) and bookmark payloads (payloads participate in bookmark matching — collision-semantics risk). `APPROVAL.REQUESTED` data also carries `requestedAtUtc`, so AC3's "computable from the paired event" holds stream-side too.
- **D5 — Decision payload contract: endpoint validates, gate fail-closes — and a Reject decision exists (story-vs-canon tension, story wins).** Resume input keys (the exact-keys discipline of `DesignResumeEndpoint` ↔ `ReadDecision`): `DecisionJson` (serialized 39-5 `AcceptanceDecision`), `Feedback`, `DeciderId`, `DeciderDisplay`, `Channel` (wire string), `RulesReference`. **Settled (design review 2026-07-21):** `Reject(string Reason)` is the fourth `AcceptanceDecision` kind (wire `kind: "reject"`; 39-5's derived-type count pin is 4) — and it is **human-only: the orchestrator cannot reject without escalating.** A `Reject` resumed by a principal whose server-derived channel is `orchestrator` is clamped to `Escalate(RejectRequiresHuman)` by 39-5's guardrail (39-6 applies it); `user`/`api` deciders pass through to the `Rejected` terminal. The public endpoint 400s any `kind` outside `accept | request-revision | reject | escalate` before forwarding (the `AllowedDesignDecisions` posture); the gate's pure `ReadDecision` additionally fail-closes an unparseable `DecisionJson` to `Escalate(AcceptorJudgment, "unreadable decision payload")` — the serializing-dispatcher lesson (#15/#437): never mis-branch on garbage while returning 200. Gate outcomes: `[FlowNode("Accept", "RequestRevision", "Reject", "Escalate")]`; outputs `DecisionJson`, `Feedback`, `DeciderId`, `Channel`, `DurationMs`. Guardrail clamping stays in 39-6's `ApplyGuardrails` step (39-5 owns the function) — the gate transports, it does not judge.
- **D6 — Channel semantics: `REQUESTED` is always `orchestrator`; `PROVIDED`/`RESOLVED` carry the server-derived resume channel.** There is one routing path (canon): every request goes to the orchestrator, so `APPROVAL.REQUESTED.channel = "orchestrator"` structurally. On resume, `Tamma.Api` derives the channel from the authenticated principal — a principal carrying the orchestrator service claim (`tamma:principal-type = orchestrator`, minted by the 39-17 host when it lands; constant defined here) → `orchestrator`; any other authenticated human session → `user`; a non-interactive service credential (engine shared-secret / API-key auth scheme) → `api`. Derivation is a pure static `ApprovalChannels.Derive(ClaimsPrincipal)` (unit-tested); NEVER read from the request body. Until 39-17 lands, tests mint the claim directly — the rule is data, not a mode branch.
- **D7 — Decider + effective-rules reference are stamped by the server, not asserted by the caller.** `DeciderId`/`DeciderDisplay` derive from the principal via the `AdlEndpoints.ResolveApprover` pattern (I2 — copied into the new endpoint class). The "effective-rules + autonomy reference it decided under" (AC1) is NOT client input either: 39-6 threads `RulesReference` (the `ResolvedAcceptanceRules` source+version+autonomy summary from the `AcceptanceRequest`) into the gate as an input, and the gate stamps it into both `REQUESTED` and `PROVIDED` data — orchestrator decisions become auditable without trusting the orchestrator's self-report.
- **D8 — No SLA timer on the decision gate (deliberate).** Unlike the design/escalation gates, no `DelayFor` timeout is armed: suspended-on-bookmark is a legal resumability posture (39-10), the orchestrator/Task-View liveness policy belongs to 39-17/39-19, and a silent timeout would be a decision nobody took. Recorded here so the omission reads as intent; the `DelayFor` pattern pointer (`WaitForDesignApprovalActivity` step 2) is the retrofit seam if policy arrives.
- **D9 — `ESCALATION.TRIGGERED` has one emit site: the lifecycle's escalated exit region; disposition is an API-level event append.** All four unhandleable outcomes AND guardrail always-escalate hits route through 39-6's `BuildOutcome`/escalated terminal, so one `EmitEscalationEventActivity` node there covers AC1's both clauses. Its data embeds the full serialized `DocumentLineage` (39-6 D7) + the typed outcome wire name + `rulesReference` + a freshly minted `escalationId` (`UuidV7`) tag. `DOCUMENT.ESCALATED` (39-6) and `ESCALATION.TRIGGERED` (39-8) are deliberately both emitted: the former is the document-family state transition, the latter the exception-surface record with lineage/channel/timing — documented in both catalogues so it never reads as accidental double-emission. Because the lifecycle has already exited when an escalation exists, disposition (`ESCALATION.RESOLVED`) is not a workflow resume: a `Tamma.Api` endpoint appends the event via a new `EscalationDispositionService` (adapting the `PromptEventsService` shape but FAIL-LOUD, not best-effort — here the event IS the operation), pairing on `escalationId` to compute `durationMs` and refusing a duplicate disposition with 409.
- **D10 — Public-surface RBAC: `AuthenticatedAny`, deviating from the adl group's `WorkflowsManage` — story text wins.** AC5 says "SaaS deciders are tenant members per RBAC", and the whole point of orchestrator-assigned decisions (Task View, 39-20) is that member users decide. `WorkflowsManage` (owner/admin) would 403 exactly the assigned decider. Security still holds: tenant folding + 128-bit session id (cross-tenant 404, unguessable within tenant). Per-assignee authorization ("only the user the orchestrator assigned") is 39-20's `ITaskAudienceResolver` — recorded as explicit migration debt in the route-group comment, the convention-store-deviation style. Single-user mode folds the sole user's scope (ambient tenant null → `none` segment), same as the design gate.
- **D11 — AC8 reconciliation: document as migration debt, change no behavior.** `EscalateReviewActivity` already emits `CODE_REVIEW.ESCALATED` at the raise point and `CodeReviewWorkflow` emits `CODE_REVIEW.ESCALATION_RESOLVED` (~L528) — the mentorship-scoped 4-6 partial. Retro-emitting `ESCALATION.TRIGGERED` from those paths would double-count escalation dashboards and has no `documentId`/lineage to carry. The story explicitly sanctions the documentation option; record it in the story-completion notes with file pointers (`EscalateReviewActivity.cs`, `SingleIssueCycleWorkflow.cs` merge-gate "Escalated" region) as 39-14/39-15 migration debt.
- **Story-vs-canon tensions: one, settled in D5** (the Reject decision kind AC7(b) requires vs. the formerly three-member `AcceptanceDecision`; design review 2026-07-21 added `Reject` as a human-only fourth kind — orchestrator-channel Reject clamps to Escalate). The canon's `POST /api/documents/decisions/{sessionId}/resume` route shape and the story's "e.g." agree; D10's RBAC deviation is intra-repo (adl precedent), not story-vs-canon.

## Risks & Mitigations

- **Prerequisite stack (39-2/39-5/39-6) is plan-only.** Largest schedule risk. Mitigation: steps 1–2, 5–7 depend only on 39-2/39-5's small model surface; step 8 has the harness-workflow fallback; every consumed name is pinned in the sibling plans (drift = mechanical rename).
- **`RequestedAtUtc`-as-input (D4) leans on Elsa re-reading inputs in callbacks.** Proven by the design gate's timeout callback, but pin it: the round-trip test asserts `durationMs > 0` across a genuine suspend/resume against real EF persistence, so a runtime-behavior change fails CI, not production.
- **Dashboard double-counting from `DOCUMENT.ESCALATED` + `ESCALATION.TRIGGERED` (D9).** Mitigation: both catalogues document the split; 39-11's queries are told (Events section stability note) to treat `ESCALATION.*` as the exception surface and `DOCUMENT.*` as state history.
- **Channel derivation drifts once 39-17/39-18 land real principals.** Mitigation: `ApprovalChannels.Derive` is one pure function with pinned tests; the claim constant lives beside it; extending the closed set requires a conscious enum edit that trips the count pin.
- **RBAC deviation (D10) read as a mistake.** Mitigation: route-group comment records the deviation + the 39-20 debt, exactly like the convention-store precedent; `DocumentDecisionApiTests` pins member access so a future "harden to WorkflowsManage" edit is a conscious test change.
- **Disposition race (two resolvers).** `AppendAsync` has no unique constraint on `escalationId`; the 409 check is read-then-write. Acceptable: a rare double-RESOLVED is visible and reconcilable on the stream (last-write-wins for dashboards); noted in the service doc comment rather than adding a table this story doesn't need.
