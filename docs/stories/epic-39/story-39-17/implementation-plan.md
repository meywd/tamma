# Implementation Plan — Story 39-17: Orchestrator Agent — long-running LLM process with platform context and tools

## Scope & Deliverable

When this story is done, `apps/tamma-elsa/src/Tamma.Api/Services/Orchestrator/` hosts one long-running orchestrator agent instance PER TENANT: a `BackgroundService` host managing per-tenant lifecycle (start on demand, idle without token burn, evict), each instance holding a persistent conversation session, a closed drift-tested toolset (git read, event-store query, log search, workflow control, document/lineage reads, `kb_search`/`rag_query`, `get_acceptance_rules`, issue/platform reads) that emits `ORCHESTRATOR.TOOL_INVOKED` on every invocation and is hard-scoped to its tenant. The agent consumes every `AcceptanceRequest` off a 39-18 inbox seam, routes it per the autonomy dial (decide itself via a typed `AcceptanceDecision` through the 39-8 resume path, or assign to a 39-20-eligible user), consumes escalations/guidance/chat, and is fully replayable from the DCB stream. A per-tenant agent config (provider/model, context budget, spend limits) is stored user_id-XOR-tenant_id and admin-editable over `/api/orchestrator/config`. A scripted fake turn runner makes the whole loop deterministic in tests; real-LLM behavior is exercised only when a provider is configured (the 39-9 posture). An ADR records the hosting decision.

## Design Decisions

- **D1 — Host in `Tamma.Api` as a hosted service, NOT on the agent-dispatch executor stack; record as ADR.** The Epic 32 pivot moved every provider credential, the gate/budget/metering chain, and the one tool loop (`InlineToolLoopRunner`) into `Tamma.Api`; the engine is a thin client and its guardrails (TAMMA001, `ActivitiesGuardrailTests`) forbid provider access there. The `AgentDispatch` stack (`IAgentExecutor`/`LocalExecutor`/`GitHubActionsExecutor` + `AgentMonitorService`) runs *external CLI coding processes* per task with artifact collection — the wrong shape for a resident, DB-coupled, tenant-scoped decision loop (it would need its own credential channel, its own DB surface, and a process per tenant). The ADR (`.dev/decisions/story-39-17-orchestrator-agent-hosting.md`, step 1) records: hosted service in `Tamma.Api`, riding the ManagedAgent substrate; agent-dispatch evaluated and rejected with the above; revisit only if per-tenant process isolation becomes a compliance requirement.
- **D2 — The mediation-invariant "allowlist" is a new pin in `Tamma.Api`, zero engine-guardrail edits.** Because the host lives in `Tamma.Api`, `ActivitiesGuardrailTests`/`EngineExternalCallAnalyzerTests` need NO weakening (they police `Tamma.Activities`/`Tamma.ElsaServer` only — assert untouched). The story's "allowlist the agent host explicitly and narrowly" lands as `OrchestratorMediationPinTests`: reflection over the `Tamma.Api` assembly asserts the ONLY constructors consuming `IInlineToolLoopRunner` are `ManagedAgent` and this story's `ToolLoopTurnRunner`, with a comment naming story 39-17 as the authority. The llm-call workflow invariant is untouched: the agent is not a workflow turn and dispatches no `llm-call`.
- **D3 — One loop, extended for conversations, not forked.** `InlineToolLoopRunner.AgenticToolLoop` currently news up its message list and uses the DI-global `IToolExecutorRegistry`. Add `RunConversationAsync(provider, providerConfig, model, messages, maxTokens, temperature, tools, loopConfig, registryOverride, correlationId, ct)` to `IInlineToolLoopRunner`: the loop core is parameterized on `(List<ConversationMessage> messages, IToolExecutorRegistry registry)`; the existing `RunAsync` passes a fresh list + the DI registry (byte-identical, pinned by test). The orchestrator passes its session transcript + the audited per-tenant registry (D5). This honors the runner's "exactly one copy of the loop, never a fork" doc-comment.
- **D4 — Turn composition mirrors `ManagedAgent`, conversation-aware, via `IOrchestratorTurnRunner`.** A new `ToolLoopTurnRunner` composes: per-tenant config (D8) → `ISaaSProviderGate`-equivalent enablement + `IBudgetGuard` (per-decision token/USD budget from config) → `IProviderCredentialResolver` (BYOK→platform) → `RunConversationAsync` → `IProviderPricingService` cost + spend accounting. The interface exists so tests substitute `ScriptedTurnRunner` (AC7): a scripted fake that *executes its scripted tool calls through the real audited registry it is handed* (so tool scoping + `ORCHESTRATOR.TOOL_INVOKED` emission are genuinely exercised) and then returns a scripted final message. Real-LLM behavior (actual reasoning quality) is exercised only with a configured provider; the story-completion notes must list that as the unverified remainder (AC7 last clause).
- **D5 — Closed toolset = per-tenant-constructed `IToolExecutor`s inside an auditing registry; never the global DI tool set.** The DI registry carries the coding-agent tools (file write, shell, tests) — the orchestrator must not see them. `OrchestratorToolCatalog.Build(OrchestratorToolContext ctx)` constructs the closed set (D6) principal-bound at construction (the 39-5 `GetAcceptanceRulesToolFactory` D6 precedent), wrapped in `AuditedToolRegistry : IToolExecutorRegistry` which emits `ORCHESTRATOR.TOOL_INVOKED` (tool name, SHA-256 args digest — never raw args, correlation/decision-session id, tenant + acting-user tags) around every `ExecuteAsync`. Write-capable tools (workflow dispatch/resume/cancel) are constructed only when `ctx.ActingUserId is null` (agent-as-principal) or the acting user passes the 39-20 permission seam — individually allowlisted, everything else read-only (AC2).
- **D6 — Tool names are a pinned closed set.** `git_read` (log/diff/blame/show/ls-files/file-content only — a read-only allowlist subset of the `GitOperationsTool` pattern, new class, NOT reusing the write-capable `git_operations`), `event_store_query` (wraps `IEventRepository.QueryEventsAsync` — the Story 4-7 surface, hard tenant guard already structural), `log_search` (see D7), `workflow_control` (list/inspect via `GetWorkflowStatusAsync`, dispatch via `StartWorkflowAsync`, resume/cancel via the `ElsaWorkflowService` methods — the three write verbs individually flagged), `document_get` + `document_lineage` (39-11 `IDocumentInstanceRepository`/`LineageAssembler`), `kb_search` + `rag_query` (39-21 seam; until it lands, backed by the `KbEndpoints` sidecar service path), `get_acceptance_rules` (39-5's factory — one registry entry among many, per the story note), `issue_read` (platform reads via `IPlatformResolver`/`IGitPlatformClient.GetRepoAsync`/`GetPullRequestAsync`/`GetFileContentAsync`). Drift test pins the exact name set and the write-capable subset (AC2's "drift-tested like the taxonomy").
- **D7 — `log_search` v1 searches the structured records that exist: the tenant's DCB stream + provider diagnostics.** There is no persisted application-log store in the repo (verified — logging goes to stdout via `Microsoft.Extensions.Logging`). Shipping a fake log store is out of scope; `log_search` fronts `QueryEventsAsync` (type-prefix + time-window + actor) plus the `ProviderDiagnostic` rows via `IDiagnosticsService`, and its description says exactly that. Recorded honestly here and in the tool description; a real log pipeline is future work, not this story.
- **D8 — Per-tenant agent config: `orchestrator_agent_configs` table, XOR principal, JSONB payload (AC6).** Mirrors `prompt_overrides`/39-5 D3: tenant-resident, `user_id` XOR `tenant_id`, one `ConfigJson` holding `OrchestratorAgentConfig` (provider key, model, context budget: `MaxSessionTokens`/`CompactAfterTurns`, spend: `MaxTokensPerDecision`, `MaxUsdPerDay`, `IdleEvictAfterMinutes`) with validated safe defaults in static `OrchestratorAgentDefaults` (fail-loud validation, drift-pinned). **Per-mode ownership, written down before code (AC6):** single-user — the sole user owns the one agent + config (keyed `user_id`); SaaS — the tenant owns them (keyed `tenant_id`), owner/admin edit, members read; no per-user layer. Admin surface `GET/PUT/DELETE /api/orchestrator/config` with a new `orchestrator:manage` permission (`Permissions.Matrix` extension, admin+owner — never a fork). Dashboard screen is NOT in scope (endpoints satisfy "admin-editable"; the 39-5 admin-page precedent makes a later screen mechanical — noted in Risks).
- **D9 — Statefulness: the session is a cache; the stream is the memory of record.** `OrchestratorSession` holds the transcript with compaction (when turns exceed `CompactAfterTurns` or estimated tokens exceed `MaxSessionTokens`, older turns are folded into a summary block via `ContextCompactor`-style truncation — deterministic v1, no LLM summarization call). Restart re-hydration (AC1): on instance start, seed the session with a bootstrap context block built from `QueryEventsAsync` (recent `ORCHESTRATOR.*`/`APPROVAL.*`/`ESCALATION.*`/`DOCUMENT.*` for the tenant) + 39-11 latest-accepted reads; pending work comes ONLY from the inbox (D10), never from remembered context. What is always re-derivable (the design note in the story): every decision input (request payload is persisted by 39-18/39-8), every past decision (`APPROVAL.PROVIDED`), every tool trail (`ORCHESTRATOR.TOOL_INVOKED`).
- **D10 — 39-18 is consumed through one seam: `IOrchestratorInbox`.** `SubscribeAsync(tenantId)` yields pending-then-live typed items (`AcceptanceRequest`, `EscalationRaised`, `GuidanceQuery`, `AgentConversationMessage` — the canonical 39-18 message names); `AckAsync(tenantId, itemId)` marks delivery complete. This story ships `InMemoryOrchestratorInbox` (default DI + test fake); 39-18 swaps in the persisted-outbox/SignalR implementation behind the same interface. Idempotent decision delivery (AC1) is the 39-8 discipline: the agent resumes via `IElsaWorkflowService.ResumeDocumentDecisionAsync`; a 404/409 (`GateNotFound`/already-resumed) ⇒ ack-and-drop, never a second answer. Channel on self-decisions is `orchestrator` — the agent's in-process identity carries 39-8 D6's orchestrator principal constant.
- **D11 — Routing is one code path reading the dial (AC3).** `OrchestratorAgentInstance` pre-gates with `AcceptanceGuardrails.TryPreGate`, then runs the turn; the LLM's final message must parse to a typed `OrchestratorTurnOutcome` (`DecideSelf(AcceptanceDecision)` | `AssignToUser(userId, basis)` — 39-5's `AcceptanceRouting` vocabulary). Unparseable ⇒ fail-closed to `AssignToUser` (an eligible user must look) or `Escalate` when none resolves. Self-decisions are clamped by `AcceptanceGuardrails.Clamp` BEFORE resume (a scripted Accept on a blocking review becomes Escalate — pinned; likewise a scripted `Reject` becomes `Escalate(RejectRequiresHuman)` — **the orchestrator cannot reject without escalating**, design review 2026-07-21: its effective self-decision set is Accept | RequestRevision | Escalate, and rejection always passes through a human). Assignments call `ITaskAssignmentService` (39-20 seam, stubbed): it server-validates assignee ∈ `ITaskAudienceResolver.EligibleAssignees(task)` and emits `TASK.ASSIGNED` with basis + autonomy context; an out-of-set assignment returns a typed refusal the agent must re-route. There is NO `if (autonomy >= X)` branch in host code — the level rides in the prompt context and rules payload; the same scripted scenario at 70 vs 100 is a *provider-script* difference, not a code branch (canon: "read when needed, never a mode branch").
- **D12 — Chat/guidance duties are seams with per-user attenuation (AC4).** `HandleGuidanceAsync` answers `GuidanceQuery` (recorded by 39-18's `GUIDANCE.REQUESTED`/`GUIDANCE.PROVIDED` events, emitted fail-loud by its `ChannelOutboxService` on the guidance traffic — one family, owned by 39-18); `HandleConversationAsync(userId, message)` serves 39-19 chat — the toolset for that turn is rebuilt with `OrchestratorToolContext.ActingUserId = userId` so tools carry X's authorization (write tools drop out unless permitted; reads filter through the 39-20 seam), pinned by a cross-user test. Chat transcript events (`CHAT.MESSAGE.RECEIVED/SENT`) are 39-19's constants, recorded by 39-19's `OrchestratorChatService` around `HandleConversationAsync` (record RECEIVED → agent turn → record SENT → relay; settled design review 2026-07-21). This story only DEFINES the `IChatTranscriptRecorder` contract — it registers no default and never invokes it; the chat service ctor-requires the recorder, so no reply path exists without the event hook (AC5), structurally. Escalation disposition calls 39-8's `EscalationDispositionService` (emits `ESCALATION.RESOLVED`).
- **D13 — Per-tenant isolation is structural, not prompted (AC1/AC6).** Every tool is constructed over tenant-scoped seams that already throw on empty/foreign tenant (`EventRepository` via `ITenantDbContextFactory`, 39-11 repository, tenant-folded resume). The registry (`OrchestratorAgentRegistry`) keys instances by tenant id; sessions/inboxes are per-instance fields; nothing static. Single-user mode: exactly one instance keyed by the sole user (ambient tenant null), same code path (`ITammaModeProvider` consulted only at identity construction).
- **Story-vs-canon tensions: none found.** The canon block and story 1.2.0 agree (per-tenant agent, closed audited toolset, single routing point, ACCEPT never an llm-call). The one judgment call is D7's `log_search` backing — the story lists "logging (structured log search)" as a tool but no log store exists; D7 is the honest minimal reading, flagged for review.

## Risks & Mitigations

- **Widest lockstep surface in the epic (39-5/39-8/39-18/39-20).** Mitigation: every consumed name is pinned in a sibling plan; all cross-story contracts enter through four small interfaces (`IOrchestratorInbox`, `ITaskAssignmentService`, `IChatTranscriptRecorder`, `IOrchestratorTurnRunner`) — drift is a mechanical rename, and the host ships `Enabled=false` by default (step 8) so partial landings never mis-route production decisions.
- **`InlineToolLoopRunner` refactor (D3) regresses the managed endpoint.** Mitigation: parameter-threading only, no logic moves; `InlineToolLoopRunnerConversationTests` pins the legacy path; `ManagedAgentTests` already cover the composition.
- **Scripted harness proves plumbing, not judgment.** Real routing quality is unverifiable without a configured provider (story-acknowledged, 39-9 posture). Mitigation: guardrails + server-side eligibility validation bound the blast radius of bad judgment; step 10 documents the gap explicitly.
- **Token/spend runaway in a long-lived session.** Mitigation: per-decision budget via `IBudgetGuard` before every turn, `MaxUsdPerDay` accumulator in the instance, compaction bounds context, idle = no LLM call structurally (event-driven loop), idle eviction; defaults conservative and drift-pinned.
- **Toolset scope creep (agent quietly gains write tools).** Mitigation: the drift test pins names + the write subset; `AuditedToolRegistry` is the only registry the runner sees; adding a tool is a conscious pinned-test edit.
- **Config admin UI expectation.** D8 ships endpoints only; if review reads AC6's "admin-editable" as UI, the 39-5 dashboard-page precedent is a mechanical 0.5–1 day follow-on — flagged, not silently absorbed.
