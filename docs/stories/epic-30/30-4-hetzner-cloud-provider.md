# Story 30-4: Hetzner Cloud Provider — Cloud API + cloud-init Bootstrap

Status: todo (planning brief, 2026-04-20)

## Story

As a **platform administrator**,
I want a `HetznerCloudTenantProvider` that provisions a dedicated VPS per tenant via the Hetzner Cloud API — server create with a cloud-init template that installs Docker, pulls the tamma-engine image, and launches engine + Postgres containers,
so that premium tenants (EU data-residency, bigger workloads, predictable performance) can run on dedicated infrastructure without the platform being locked to Cranl.

## Acceptance Criteria

1. `HetznerCloudTenantProvider : ITenantInfrastructureProvider` with `ProviderKey = "hetzner"`. `GetCapabilities`:
   - `SupportedTopologies = DedicatedCompute | DatabaseOnly`
   - `Regions = ["nbg1", "fsn1", "hel1", "ash", "hil"]` (Nuremberg, Falkenstein, Helsinki, Ashburn, Hillsboro — as of 2026-04 Hetzner zones)
   - `Features = DedicatedDb | AutoscaleCompute (manual via resize) | BackupManagement (via Hetzner)`
2. `ProvisionAsync` (DedicatedCompute topology):
   - Calls `POST /v1/servers` with: chosen `server_type` (e.g. `cx22` starter, `cx42` pro), `image = docker-ce` (or ubuntu-24.04 + user-data), chosen `location`, operator SSH key id, `user_data = <rendered cloud-init template>`.
   - Waits for server status `running` (max 90 s per Hetzner SLA).
   - Polls the configured `/health` endpoint on the returned IP until 200 (max 5 min for cloud-init to finish Docker install + container pull).
3. `user_data` template renders a cloud-init YAML that:
   - Installs Docker CE (uses Hetzner's `docker-ce` image or idempotently installs on a plain Ubuntu image).
   - Writes an `.env` file with the tenant's initial secrets (DATABASE_URL, TAMMA_SHARED_SECRET, API keys) fetched from Epic 29's cabinet at provision time.
   - Writes a `docker-compose.yml` with two services: `postgres` (Postgres 17, named volume for data) and `tamma-engine` (pulled from Tamma's registry, tagged with the version ops chose).
   - Runs `docker compose up -d`.
   - Creates a non-root `tamma` user; disables password SSH; leaves the operator's SSH key as the only access path.
   - Installs unattended-upgrades.
4. `DatabaseOnly` topology short-circuits the engine install — writes only Postgres into the compose file. Engine runs on shared Tamma infrastructure; `ResolveEndpointsAsync` returns `EngineHost = <shared host>`, `DbUrl = postgres://tamma:<pw>@<hetzner-ip>:5432/tamma_tenant`.
5. Initial DB password and `TAMMA_SHARED_SECRET` are generated by 29-7 / 29-8 at provision time — the Hetzner provider asks Epic 29 for values rather than generating its own. The cabinet rows exist before cloud-init runs (registered in 30-2's `RegisterSecretsActivity`).
6. `ResolveEndpointsAsync` returns the server IP + the configured port (engine on 8080, Postgres on 5432 behind a firewall rule). Uses Hetzner's "server firewall" feature to restrict 5432 to the shared Tamma control plane IP range; engine port open to the tenant's registered custom domain (optional) or the default `*.tamma-tenants.net` DNS alias.
7. `DeprovisionAsync` calls `DELETE /v1/servers/:id`. Idempotent — 404 = already gone, treated as success. Cleans up the Hetzner firewall rule + any floating IPs attached.
8. `GetStatusAsync` returns from Hetzner's server status + a probe of the engine's `/health`. Five probe failures in a row ⇒ `Unhealthy` + alert; otherwise `Ready`.
9. Secret rotation path: when Story 29-7 rotates the tenant DB password, it calls back into the Hetzner provider via a new `UpdateTenantEnvAsync(tenantId, { DATABASE_URL: new })` method that SSHes into the box and writes the new `.env` + `docker compose restart tamma-engine`. SSH uses the operator key managed out-of-band. (Alternative: Hetzner Cloud-Init Configurator mode that accepts secrets via a one-time webhook — deferred to Epic 1.5's secret handlers.)
10. Integration test uses a fake `IHetznerCloudApiClient` (WireMock): full provision → success; provision with timeout on server-running poll → compensation; deprovision path; rotation push hook.

## Technical Context

### Why a dedicated Hetzner backend

Hetzner is Tamma's existing operator and the platform's cheapest
infrastructure per-euro. Cranl runs *on* Hetzner (via third-party
abstraction), but Cranl's plan constraints + MENA-gated regions + its
`api.cranl.com` downtime = single point of failure. A direct Hetzner
Cloud backend:

- Cuts out the Cranl middleman for tenants that don't need Cranl's UX.
- Gives operators fine control over sizing / region / pinning.
- Supports workload isolation for compliance customers (SOC 2, ISO
  27001 — each tenant on its own VPS).

### cloud-init as the bootstrap primitive

Research notes §2 confirm cloud-init + docker-ce is the idiomatic
Hetzner Cloud bootstrap path. Keeping the template declarative (not a
procedural bash script) makes it easier to review and version.

The template lives in
`apps/tamma-elsa/src/Tamma.Api/Services/Provisioning/Hetzner/cloud-init-tenant.yaml.tmpl`
with Scriban (or built-in Razor-lite) substitution. Rendering is a pure
function of `{ tenantId, secrets, engineImageTag, postgresVersion }`.

### SSH key management

The operator's public key is registered with Hetzner and referenced
by id in the server-create call. Private key lives on the control
plane in Epic 29's cabinet as `platform:ssh/hetzner-operator-key` so
rotating it is a first-class flow.

### Out-of-scope

- Multi-region failover (future).
- Automatic backup schedule (Hetzner UI handles it for now).
- Floating IP / load-balancer configurations (future tier).
- Horizontal scaling (single-server-per-tenant model).
