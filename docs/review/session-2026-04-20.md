### 2.1 Phase-3 RLS connection-string split

#### FINDING 1 — **P0** — Fail-closed plane is dead code

- **Where**: `apps/tamma-elsa/src/Tamma.Data/Repositories/*.cs` (all 21 files), `apps/tamma-elsa/src/Tamma.Api/Endpoints/*.cs` (DashboardEndpoints.cs:21/81, OrgEndpoints.cs:512/570, …), `apps/tamma-elsa/src/Tamma.Api/Services/Provisioning/CranlTenantProvisioner.cs:47,52`, `apps/tamma-elsa/src/Tamma.Api/Services/Provisioning/CranlProvisioningWorkflow.cs:31,39`, `apps/tamma-elsa/src/Tamma.Api/Services/Provisioning/NullTenantProvisioner.cs:19,22`.
- **Problem**: `TammaAppDbContext` is registered in DI (`DependencyInjection.cs:87`) and overrides `EnforceTenantFilter => true` (`TammaAppDbContext.cs:45`), but nothing injects it. A `grep -rn "TammaAppDbContext" apps/tamma-elsa/src/` returns hits only in the `Tamma.Data` project itself (definition + two doc cross-refs in `ITenantConnectionResolver.cs`). All 21 repositories in `Tamma.Data/Repositories/` inject `TammaDbContext`, and every endpoint that takes a DbContext directly (DashboardEndpoints, OrgEndpoints, ITenantConnectionResolver consumers) also uses `TammaDbContext`. The query-filter code path where `EnforceTenantFilter == true` executes only in `QueryFilterAndInterceptorTests`; production never reaches it.
- **Why it matters**: audit/orgs/002 and audit/orgs/004 are now marked "fixed" in the remediation docs (commit `a2d706a` — "mark Phase-3 connection-string split findings fixed"). They are *not* fixed for requests; the scaffold is in place but the runtime is still on the permissive path. Combined with the fact that `Program.cs:195-198` logs a warning when `TammaAppDb` is absent and *silently falls back to the admin string*, production deployments without an explicit `ConnectionStrings:TammaAppDb` get **zero** of the advertised isolation even for the `TammaAppDbContext` injection sites (if any existed).
- **Fix**: either (a) migrate repository/endpoint injections to `TammaAppDbContext` in a follow-up story and update the remediation doc to mark orgs/002 as "scaffold only — not live", or (b) revert the "fixed" audit markers. Current state is worse than no fix: reviewers and future agents will trust a false remediation signal.

#### FINDING 2 — **P1** — Users RLS policy leaks NULL-tenant rows

- **Where**: `apps/tamma-elsa/src/Tamma.Data/Migrations/20260419021119_Phase2RlsAndTriggers.cs:195-200`.
- **Problem**: the standard tenant policy is `"TenantId" IS NULL OR "TenantId" = NULLIF(current_setting(...), '')::uuid`. Comments at `Phase2RlsAndTriggers.cs:47-52` and the users model filter at `TammaDbContext.cs:120-161` acknowledge users can have `TenantId = NULL` during registration (before `EnsurePersonalTenantMiddleware` materialises the tenant). Once the app-role connection is wired (see P0 #1), every tenant's session will see every in-flight / orphaned / accidentally-null user row. Same for `api_keys`, `agent_configs`, `provider_diagnostics`, `provider_health`, `sanitization_rules`, `prompt_overrides`, `workflow_definitions`, `workflow_instances`, `domain_events`, `user_invites`, and `github_installations`.
- **Why it matters**: the NULL-bypass was deliberate (admin/background services need it on the admin connection), but it was never scoped off the app role. The comment "Rows with `TenantId IS NULL` (system defaults, service keys) are permitted globally so platform-level data still works" is at odds with the intent to serve per-request end-user queries from this role.
- **Fix**: drop the `TenantId IS NULL OR` branch from the standard-table policies; move genuinely-global rows (service keys, system defaults) to the `api_keys.Scope = 'service'` pattern (which IS already special-cased at lines 206-220). The `users` table should never have `TenantId = NULL` reachable via the app role — either finalise the `EnsurePersonalTenantMiddleware` write before any app-role query runs, or gate this table behind the admin role permanently.

#### FINDING 3 — **P2** — `prevent_tenant_id_change` allows `uuid → NULL`

- **Where**: `apps/tamma-elsa/src/Tamma.Data/Migrations/20260419021119_Phase2RlsAndTriggers.cs:53-63`.
- **Problem**: the trigger raises when `OLD.TenantId IS NOT NULL AND OLD.TenantId IS DISTINCT FROM NEW.TenantId`. `DISTINCT FROM` treats NULL as a value, so `uuid → NULL` is blocked. Good. `NULL → uuid` is permitted (design choice for registration). But an UPDATE that flips `TenantId = NULL` from a NULL row (NULL → NULL) also passes, and — more subtly — the trigger does NOT cover rows that were created with `TenantId = uuid` already: any downstream UPDATE that sets it back to NULL is blocked as intended. Net: the tenant-id immutability guarantee depends on a row always being created non-NULL by the runtime, which is the opposite invariant from the query-filter design (which assumes NULL is common).
- **Fix**: align the two. Either commit to non-NULL on create (update users entity + middleware to force a tenant before insert, drop the NULL branch) or acknowledge NULL as a legitimate transient state and update documentation. Currently the two layers pull in different directions.

#### FINDING 4 — **P2** — `tamma_app` role ships with hard-coded password

- **Where**: `Phase2RlsAndTriggers.cs:97-103`.
- **Problem**: the migration `CREATE ROLE tamma_app LOGIN PASSWORD 'changeme'`. Comment says "production deploys must override via ALTER ROLE", but there's no runbook reference inline and no CI gate to catch a container image that forgot this. If a deployment mis-wires `ConnectionStrings:TammaAppDb` to use `password=changeme`, auth succeeds and RLS is live — but the password is the *literal string in the migration source*.
- **Fix**: either generate a random password at migration time + write it to a secrets output, or refuse to create the role entirely and require operators to create it out-of-band with their own password.

### 2.2 Epic 19 agent dispatch

#### FINDING 5 — **P1** — Webhook signal registry is not tenant-scoped

- **Where**: `apps/tamma-elsa/src/Tamma.Activities/AgentDispatch/WebhookSignalRegistry.cs:75-115` (`AgentWebhookSignalKey`), `apps/tamma-elsa/src/Tamma.Api/Services/GitHub/InstallationRouterService.cs:435-441` (publish call).
- **Problem**: the registry key has no installation id, tenant id, or app id. The three alias forms (`run:{repo}:{runId}`, `branch:{repo}:{branch}`, `branch:{repo}:{branch}:{sessionId}`) can all collide across tenants. `WorkflowRunId` is globally unique per GitHub App installation, so the `run:` form is safe in practice; `branch:` is NOT — branch names like `tamma/issue-42` are guaranteed to collide across installations, and the webhook publisher (`InstallationRouterService.cs:435`) constructs the publish key with `SessionId: null`, causing it to publish only under the `branch:{repo}:{branch}` alias (no session-disambiguator). Any monitor awaiting on a branch-only waiter in tenant A can be woken by a webhook from tenant B who happens to use the same branch in a fork.
- **Why it matters**: the monitor then returns a `workflow_run_url` and `artifacts_url` belonging to tenant B, which the collector (`AgentResultCollectorService.DownloadResultArtifactAsync`) will attempt to download using tenant A's installation token. Best case: GitHub returns 404 (tenant A can't read tenant B's run). Worst case: cross-tenant shared org or fork where tenant A DOES have read access — tenant A sees tenant B's agent output.
- **Fix**: include the installation id (resolvable from both sides) in the key. Webhook side has `installation.id` on every payload; monitor side has `installationId` on the dispatch response. Prepend `install:{id}:` to every alias.

#### FINDING 6 — **P1** — Artifact download is unbounded

- **Where**: `apps/tamma-elsa/src/Tamma.Api/Services/GitHub/OctokitGitHubActionsClient.cs:191-220` (`DownloadArtifactZipAsync`), `apps/tamma-elsa/src/Tamma.Activities/AgentDispatch/AgentResultCollectorService.cs:168-189` (caller).
- **Problem**: `stream.CopyToAsync(ms, ct)` with no cap. GitHub Actions artifacts can be up to 10 GB (free tier) / unlimited (enterprise). `ParseResultJson` (line 192-233) then parses the full JSON into `JsonDocument` — another unbounded allocation.
- **Why it matters**: a compromised agent in a customer repo can upload a giant `tamma-result` artifact, then trigger collection (either via webhook in the Phase 4 mode or poll). The Tamma API process OOMs and drops every other tenant's request. DoS across tenants from a single untrusted agent.
- **Fix**: cap at ~4 MB. `AgentResultArtifact` is a small JSON shape (paths + counts + a log summary); 4 MB leaves room for verbose logs. Enforce via a `LimitedStream` wrapper in `DownloadArtifactZipAsync` that throws when exceeded, catch in `AgentResultCollectorService` and return `null` so the compare-API fallback kicks in.

#### FINDING 7 — **P2** — Result file path on LocalExecutor is predictable / attackable on shared hosts

- **Where**: `apps/tamma-elsa/src/Tamma.Activities/AgentDispatch/LocalExecutor.cs:184-193` (`ResolveWorkingDirectory`).
- **Problem**: default working dir is `Path.GetTempPath() / "tamma" / SafeId(sessionId)`. `SafeId` lowercases + allows `[A-Za-z0-9_-]`. On a shared host (classic cloud VM, multi-tenant container) an unprivileged process can pre-create `exec-request-<sessionId>.json` as a symlink to an attacker-controlled file. `File.WriteAllTextAsync` follows the symlink and overwrites — not directly exploitable since we control the content, but the `exec-result-<sessionId>.json` read at line 146 WILL follow a symlink that points at attacker output.
- **Why it matters**: the attack requires predicting the session id. Session ids in this codebase are not documented to be random-high-entropy; if an attacker can discover one (via logs, events, or observation) they can forge the agent result.
- **Fix**: create the temp dir with `Directory.CreateDirectory(…, UnixFileMode.UserReadWriteExecute)` + explicitly reject the result path if it is a symlink. Or inject a `TAMMA_AGENT_TMP` env that defaults to a location owned by the Tamma service user.

#### FINDING 8 — **P2** — `ParseResultJson` accepts arbitrary string fields without length limits

- **Where**: `apps/tamma-elsa/src/Tamma.Activities/AgentDispatch/AgentResultCollectorService.cs:192-233`.
- **Problem**: `agent_log_summary`, `error_message`, `commit_sha`, `branch_name` etc. are all `ReadString` with no length clamp. `AgentResultArtifact` is then propagated into `AgentExecutionResult` which is returned to Elsa workflow state (persisted to `workflow_instances.Result` jsonb column). A malicious agent can inject multi-MB strings into each field and bloat the DB.
- **Fix**: cap each string at the column's practical ceiling (2 KB for error_message / branch_name / commit_sha; 32 KB for agent_log_summary) during parse.

#### FINDING 9 — **P2** — `DefaultProcessRunner.Task.Delay(250)` race for stream drain

- **Where**: `apps/tamma-elsa/src/Tamma.Activities/AgentDispatch/DefaultProcessRunner.cs:115-116`.
- **Problem**: `await Task.WhenAny(Task.WhenAll(outTcs.Task, errTcs.Task), Task.Delay(250))`. After `WaitForExitAsync` returns, the async stream readers may not have drained. The 250ms grace is a magic number — a chatty child that exits cleanly but has buffered output in flight can lose the tail of its stderr. For a timeout path this is fine (we killed the tree anyway), but for a clean `ExitCode == 0` with a failure result written to the output file, losing the tail of the diagnostic log makes post-mortem harder.
- **Fix**: don't race. Await `Task.WhenAll(outTcs.Task, errTcs.Task)` unconditionally after exit. The synchronous callbacks only fire after `BeginOutput/ErrorReadLine` has seen EOF, which is guaranteed after the process has exited.

### 2.3 Octokit GitHub App + libsodium

#### FINDING 10 — **good** — JWT issuance is correct

- `OctokitGitHubAppClient.GenerateJwt` (lines 210-223) uses 9-minute expiry with 60s clock-skew, `notBefore = now - 60s`, `iat = now - 60s`, RS256 via cached `RSA` + `SigningCredentials`. Safely under GitHub's 10-minute hard cap; `CacheSignatureProviders = false` avoids a cross-tenant leak on provider reuse. Good.

#### FINDING 11 — **P2** — Installation token cache has no eviction on 401

- **Where**: `OctokitGitHubAppClient.cs:187-203`. Exposes `InvalidateInstallationToken` (line 180) for callers to flush a stale token, but no caller uses it in the paths I reviewed (`LibsodiumGitHubSecretsProvisioner`, `OctokitGitHubActionsClient`, `InstallationRouterService`). A token revoked at the GitHub end (install suspended, app rotation mid-flight) will continue to be returned from the cache for up to 55 minutes, with every call 401-ing.
- **Fix**: wrap Octokit calls in a retry that catches `AuthorizationException` / `401`, calls `InvalidateInstallationToken`, and retries once.

#### FINDING 12 — **P2** — Rate-limit handling logs but does not back off

- **Where**: `OctokitGitHubAppClient.LogRateLimitExceeded` (260-267), `LogAbuseDetected` (269-274), `LibsodiumGitHubSecretsProvisioner.cs:115-128`.
- **Problem**: both sites return a `github_rate_limited` / `github_abuse_detected` failure code but there's no honoring of `ex.Reset` / `ex.RetryAfterSeconds` — the next call proceeds immediately and will 403 again. For the secrets provisioner this means a single abuse-detection event on one repo poisons every subsequent repo in the batch (they all race past the gate in parallel and all hit the limit).
- **Fix**: the provisioner's per-repo `try/catch` should check `RetryAfterSeconds`, signal the gate to back off the whole batch, and either retry or fail-fast the remaining repos. At minimum, returning `Failed` results for the remaining queued tasks would be clearer than N independent failures.

#### FINDING 13 — **P2** — Sealed box ciphertext is not wiped from memory

- **Where**: `LibsodiumGitHubSecretsProvisioner.EncryptSealedBox` (167-173). Plaintext `secretValue` (which is the installation's `TAMMA_API_KEY`) is passed by reference through `InstallationRouterService.EnsureInstallationKeyAsync:292`. The `messageBytes` allocation at line 170 holds the plaintext for the duration of `SealedPublicKeyBox.Create`. Not wiped after use.
- **Fix**: use `CryptographicOperations.ZeroMemory(messageBytes)` after the `Create` call. Low-exploitability but trivial to fix.

### 2.4 Cranl tenant provisioning

#### FINDING 14 — **P2** — 8-hex-char resource name collisions

- **Where**: `apps/tamma-elsa/src/Tamma.Api/Services/Provisioning/CranlProvisioningWorkflow.cs:391-392` (`ShortenForName`).
- **Problem**: 8 hex chars = 32-bit space = ~65k-tenant birthday probability of first collision. Project/db/app names collide across tenants on the same Cranl org. The failure mode is opaque — Cranl returns "resource already exists" and the provisioner flips to Failed with `cranl_api_error:409:…` which isn't actionable.
- **Fix**: 16 hex chars (64-bit, >4B birthday) or use the full no-hyphen uuid. Names become uglier in the Cranl UI but provisioning works at scale.

#### FINDING 15 — **P2** — `BuildEnvironmentText` writes `TAMMA_SHARED_SECRET` in plaintext to Cranl

- **Where**: `CranlProvisioningWorkflow.cs:326-343`.
- **Problem**: `TAMMA_SHARED_SECRET` is the HMAC key the tenant engine uses to authenticate back to the control plane. It's handed to Cranl via `PutEnvironmentAsync` as plaintext env text. The README on Cranl is the trust boundary; whoever reads that environment payload in Cranl storage sees the HMAC secret. Fine if Cranl encrypts-at-rest + has strong auth, but the Tamma side has no way to know.
- **Fix**: document the trust assumption prominently; or mint a per-tenant secret via `RandomNumberGenerator.GetBytes(32)` so a Cranl-side compromise doesn't let the attacker forge control-plane calls for *other* tenants.

#### FINDING 16 — **P2** — `TenantSecretProtector` dev-fallback derives key from `Cranl:ApiKey`

- **Where**: `TenantSecretProtector.cs:104-114`.
- **Problem**: when `Cranl:EncryptionKey` is absent, the protector derives a key via HKDF from the Cranl API key with a fixed public salt and info string. If an operator rotates `Cranl:ApiKey` without setting `Cranl:EncryptionKey` first, every previously-encrypted `cranl_database_url_encrypted` becomes undecryptable on startup. The warning log at line 104 does not block startup.
- **Fix**: hard-require `Cranl:EncryptionKey` when `Cranl:ApiKey` is present (throw at `FromConfiguration`). Dev-mode convenience here is a footgun.

#### FINDING 17 — **good** — AES-GCM nonce generation is correct

- `TenantSecretProtector.Encrypt` (121-138) uses `RandomNumberGenerator.GetBytes(12)` per call, prepends nonce, 16-byte tag suffix. No key-nonce reuse risk. Good.

## 3. Things done well (keep doing)

- **Signature verification order**: webhook body is buffered, signature verified, then delivery-id idempotency check, then JSON parse, then dispatch. No TOCTOU. (`GitHubEndpoints.cs:122-216`)
- **Interceptor safety**: `TenantContextInterceptor.ApplyTenantBindingAsync` is defensively logged-and-continued rather than hard-failing, with a clear justification in the doc comment that relies on EF query filters + RLS as the safety net.

- **`CranlProvisioningWorkflow` resumability**: each step checks "did the previous step already produce this?" before acting. Re-entrant from any intermediate state, which matches the queue-handler-driven invocation model.
- **JWT correctness + cache-signature-providers-off**: the RSA signing setup in `OctokitGitHubAppClient` gets the subtle `CryptoProviderFactory { CacheSignatureProviders = false }` right, preventing a documented per-key leak.
